# 프로젝트 결정 권한과 장애 대응

허브 PM은 main 코디네이터다. 워크트리 PM은 태스크 계약 안의 실행을 맡고 막힌 결정과 근거를 허브에 보낸다. 같은 세션이 두 역할을 맡으면 그 자리에서 아래 절차를 수행한다.

## A. 결정 주체

실제 조치와 대상, 현재 합의, 기존 승인·위임을 대조해 다섯 질문에 답한다. 하나라도 ‘예’면 owner에게 해당 번호를 붙여 요청한다. 모두 ‘아니오’면 담당 PM이 결정한다. 워크트리 작업자의 owner 요청은 허브가 전달한다. 회신까지 해당 조치만 보류하고 독립 작업은 계속한다.

| 항목 | 예·아니오 질문 | 판정 근거 |
|---|---|---|
| A-1 합의 변경 | 조치가 합의된 목적·목표·범위·완료 기준(`P-n`)을 실질적으로 바꾸는가? | 필수 태스크 보류·기준 미달 마감·결과 축소도 ‘예’다. 기준을 유지하는 검증 강화는 ‘아니오’다. 영향이 불분명하면 먼저 PROJECT.md·브리프와 실제 결과를 대조한다. 해당 조치만 보류하고 독립 작업은 계속한다. 영향이 있거나 대조 뒤에도 합의 영향 여부를 가릴 수 없으면 이 항목으로 요청한다. |
| A-2 복구·외부 영향 | 조치가 이 worktree의 Git으로 되돌릴 수 없거나 외부로 나가는가? | 푸시·병합·배포·외부 전송·결제·저장소 밖 데이터 삭제가 해당한다. 대상과 범위를 특정한 기존 owner 승인에 따른 같은 조치와 AGENTS.md·저장소 규칙이 이미 위임한 조치는 ‘아니오’다. 하네스 장애를 푸는 작은 도구 수정을 허브가 main에서 고치고 커밋·필요시 재설치하는 S1 위임이 여기에 해당한다. |
| A-3 안전 기준 | 보안 검사·필수 테스트·독립 검토를 생략하거나 약화하는가? | 다른 제공자를 호출할 수 없을 때 같은 제공자의 새 세션으로 검토하는 B1은 ‘아니오’다. 검토 자체의 생략, 두 제공자 경로 모두 미실행, 필수 증거가 미확인인 채 진행은 ‘예’다. BL261124_04 적용 전에는 남은 blocking을 안고 진행하는 조치도 ‘예’다. |
| A-4 사용자 자산 | 새 권한·새 계정을 쓰거나, 비밀 노출·사용자 데이터 외부 공개·새 유료 비용이 생기는가? | 이미 위임받은 권한으로 내부 자료를 읽는 등 기존 위임 범위의 정상 사용은 ‘아니오’다. |
| A-5 사람이 수행 | 사람만 할 수 있는 실기 확인·사람 확인 이미지 또는 아직 받지 않은 새 사람 승인이 필요한가? | 이미 받은 승인 원문이 있는 경우 실행 전 확인을 적용한다. |

**B1 기존 위임.** 태스크의 구현 전·후 독립 검토와 백로그 검토에서는 먼저 다른 제공자를 시도한다. 호출이 불가능하면 그 이유와 미실행을 기록하고, PM이 `--allow-same-provider` 또는 호스트의 별도 새 세션으로 같은 제공자 검토를 진행한다. 이 대체 검토는 `cross: false`로 기록한다. 같은 제공자까지 미실행이면 A-3에 따라 결정 요청을 보낸다. 실행된 교차 검토의 fail은 별도 맥락 폴백으로 대체할 근거가 되지 않는다. B1과 S1의 출처는 [BL261124_05의 owner 결정 기록](../../../backlogs/BL261124_05_허브_PM_결정_권한과_어드바이저/BACKLOG.md#결정기록)이다. 사전·사후 검토는 [같은 reviewer 배정 원칙](task-steps.md)을 따른다.

BL261124_04의 검토 예산은 검토 회차를 센다. 예산 소진 뒤 위험 수용이 적용되면 증거가 있고 영향이 작은 잔여 지적에 한해 BL261124_04의 기준을 함께 대조한다. 필수 증거 미확인 또는 안전 기준 완화는 A-3으로 판정한다. 아래 공동 시도의 단위는 허브와 워크트리가 함께 적용한 조치다.

owner 결정 뒤에도 적용되는 게이트의 요건과 현재 계약을 확인한다. 검토가 한 번도 실행되지 않았다면 PRE-REVIEW의 `waiver` 근거가 성립하지 않는다. 필수 결과가 여전히 미확인이면 보완 관측 또는 적법하게 변경된 계약에 따라 다시 판정한다.

조치의 결과가 불확실하면 증거를 더 확인한다. ‘판단이 서지 않음’만으로는 요청을 만들지 않는다. 조사 뒤 A 항목에 해당하지 않는 되돌릴 수 있는 선택은 PM이 추천안으로 진행하고 이유를 기록한다.

### 실행 전 승인 확인

A로 결정 주체를 고른 뒤, 승인 게이트에 입력하는 쪽이 원문과 실행 대상을 다시 대조한다. A-2의 승인과 실행을 나눠 owner가 승인하고 허브가 main에서 실행한다. 푸시·병합·배포의 입력자는 허브이며 `merge --yes`에는 병합 미리보기 커밋 전체 SHA를 대조한다. `waiver`의 `by: user`와 `review-note --by user`의 입력자는 워크트리 PM이며 현재 대상과 해시를 대조한다. 승인 원문이 없거나 조건·대상이 다르면 입력을 보류하고 해당 요청을 보낸다. 대상과 범위가 일치하면 그 승인으로 진행한다. 워크트리는 푸시·배포·삭제·외부 전송을 수행하지 않고, 이 조치나 병합이 필요할 때 허브로 인계한다.

- [참여 소통 원장](../../../docs/HANDOFF.md)을 쓰는 프로젝트는 `decision_request`(`to: owner`)와 출처가 있는 `decision_reply`를 같은 요청·제안 지문으로 묶는다. 원문은 원장의 로컬 본문에 둔다. 허브 자체 실행은 답 ID·지문·출처를 담은 짧은 영수증을 `pace project log --ref`로 연결한다. owner 승인에 근거해 위임할 때는 `delegate`의 basis `approved`를 사용한다. 검토 게이트의 근거 파일에도 같은 영수증을 연결하고 입력자가 로컬 원문을 확인한다.
- 원장을 쓰지 않는 프로젝트는 Orca 사용 여부와 관계없이 프로젝트 내부 근거 파일에 원문·출처와 대상·범위를 연결한다. 검토 게이트의 근거가 태스크 폴더 안이어야 하면 태스크의 `evidence/`에서 해당 근거를 연결한다. 프로젝트 밖 작업의 승인은 로컬 `$PACE_HOME/approvals/`의 업무별 파일에 원문·출처·대상·범위·지문을 기록한다. 작업 로그에는 요약과 근거 참조를 남긴다.

## B. 허브의 장애 대응

1. 작업자의 `escalation` 또는 질문에서 계약·재현 조건·증거 원문을 확인하고 허브가 저장소에서 확인한 방법으로 재현한다. 계획·산출물의 심각한 오류와 승인된 설계에서 벗어나는 대안도 이 절차로 다룬다. 반복 검토는 [reviewer의 원장 단계](reviewer.md#반복-실패-진단과-사용자-결정)를 함께 따른다.
2. 원인 층을 가린다. 환경 문제는 허브가 조사하고, 설계 문제는 대안을 비교한다. 필요하면 다른 제공자의 두 번째 의견을 받는다. 조치를 적용하기 전에 합의와 실제 영향에 A를 적용한다. 도구·하네스 수정도 A-3의 안전 기준 완화 여부를 확인한다. A에 해당하면 owner 결정을 기다린다.
3. 작은 도구·하네스 결함은 owner의 S1 위임과 AGENTS.md의 main 작업 절차에 따라 허브가 결정 후 수정하고 필요시 재설치한다. 병합 대기 중이면 main 커밋은 병합 뒤로 미루고, 격리 사본의 수정·검증 등 기존 게이트와 검증 대상을 보존할 안전한 우회를 찾는다. 허브는 결정·근거·재검증 기준을 회신한다. 막힌 조치만 보류하고 독립 작업을 이어간다. 작업자는 회신을 `(main 판단)`으로 기록하고 적용 뒤 재검증해서 태스크를 재개한다.
4. **허브 회신 → 워크트리 적용 → 재검증**을 마쳐야 공동 시도 1회다. 상한은 2회다. 재검토에서 blocking이 3→1→1이었던 [실측](../../../.pace/brain/pages/concept/검토-반복-실패-하네스.md#실측)을 참고한 초기값이다. 2회 뒤에는 안전하게 되돌릴 수 있는 차선(선택 태스크 보류, 이슈로 기록 후 독립 작업 진행)을 고르고 C에 따라 사후 요약한다. 필수 태스크 보류나 기준 미달 마감이면 A-1로 요청하고 그 조치를 보류한다. 원인이 풀렸다는 도구 수정·환경 복구·결정 증거가 생기면 보류 태스크를 재개한다.

## C. owner에게 전할 내용

| 구분 | 내용과 기록 |
|---|---|
| 결정 요청 | 해당 A 번호, 대상과 근거, 선택지, 추천과 이유를 담는다. 원장 사용 시 `decision_request`를 `to: owner`로 보내고 답을 `decision_reply`에 연결한다. |
| 승인 요청 | 병합·배포·푸시 등은 실행 대상과 범위(해당 커밋·해시 포함)를 특정한다. 기존 승인이 맞으면 재사용한다. 원장의 요청·응답과 실행 영수증은 위 실행 전 확인을 따른다. |
| 사후 요약 | 되돌릴 수 있는 설계 선택이나 선택 태스크 보류처럼 PM이 대신 정한 사항은 근거 기록 뒤 실제 결과를 한 줄씩 모아 다음 대화 또는 완료 보고에 붙인다. 원장을 쓰면 상태 안내 `status`, 그 밖에는 프로젝트 결정·완료 보고에 기록한다. 장애의 단순 상태 알림은 B 조사와 회신으로 처리한다. |
