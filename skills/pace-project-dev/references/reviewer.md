# reviewer — 변경 검토

구현한 세션과 **다른 새 맥락**에서 검토한다. 파일을 고치지 않고 지적만 돌려준다.

## 넘길 것

[goal-review.md](goal-review.md)의 1단계를 먼저 한다. 호출자는 상위 목적/목표와 결과물만 주고 첫 판단을 회수한다. 아래 작업 문서는 그 기록 뒤 2단계에서만 받는다. 산출물 자체가 계획 문서인 경우의 구별·오염 시 새 맥락·규모 비례도 정본을 따른다.

TASK.md(목적·기준·접근), 이 태스크의 전체 diff(`git diff` — 커밋 전 작업본 또는 태스크 시작 커밋 이후), 관련 기준 문서(SKILL.md §5), 바뀐 언어의 `pace-tech-handbook` 색인(`references/<언어>/INDEX.md`), 필요하면 `security.md` 체크리스트.

## TASK 증명 범위와 판정 주체

형식 경계는 머리 목록의 `- TASK 형식: v2`다. 표지가 없는 옛 TASK에는 이 절의 새 요구(누락 blocking 포함)를 적용하지 않고 기존 기준으로 검토한다. 절 존재만으로 새 형식을 추정하지 않는다. 중복·미지원 표지는 거부한다. 게이트와 verify도 같은 표지를 읽는다. 표지 제거·기록 위조는 기존 이력 조작처럼 우회 가능한 한계이며 기계가 진정성을 보증하지 않는다.

새 TASK는 기준·테스트 앞 `## 증명 범위`에 `- 판정 주체:`의 비어 있지 않은 값, 포함, 범위 밖(이유·넘길 곳)을 쓴다. 게이트는 절 누락·빈 절(HTML 주석만 있는 절 포함)·판정 주체 누락/빈 값을 거부한다. 포함·범위 밖의 충분성은 reviewer의 의미 판정이다.

증명 범위·판정 주체가 비면 그것 자체만 **blocking 1건**으로 내고 다른 지적을 늘어놓지 않는다. 단건 억제는 게이트가 거부하는 구조 누락(절 없음·주석뿐인 절·주체 줄 없음·값 공백)에 한한다. 미정·TBD 같은 실제 텍스트의 의미적 불충분성에는 나머지 지적을 억제하지 않는다. 구조 누락을 채운 다음 verify는 아직 평가하지 못한 목적·필수 안전까지 전체 검토한다(rereview_of null, 실패 집계는 유지). blocking은 적힌 증명 범위로 목적·기준을 증명할 수 없을 때다. 현재 적힌 범위가 이미 목적·기준을 충분히 입증한다면 그 밖으로 확대하라는 요구는 목적 증명에 필요하지 않아도 should_fix로 남긴다. 합의 범위 밖이라는 이유로 note로 바꾸지 않는다. should_fix는 범위 변경 승인이나 반영 의무가 아니며 확장은 별도 합의를 받는다. 범위 자체가 목적에 비해 좁으면 blocking이며 범위 밖 선언으로 검토를 피할 수 없다.

판정 주체의 권한도 대조한다. 사람의 결정이 정답인 기준은 승인받은 사람의 원문을 왜곡·누락 없이 옮기고 불완전하면 미확인으로 드러내면 통과다. 작성자나 자동 검사가 그 결정을 대신하거나 필수 안전 기준(보안·데이터·되돌리기 어려운 행동)을 범위 밖으로 빼면 blocking이다. 재검토에서는 이 규칙도 직전 blocking 해소와 바뀐 줄이 만든 새 결함 범위 안에서 적용한다.

## 사전 검토 이력 보존

PM은 검토 차수마다 최초 판정과 재검토 원문을 고유한 증거 경로에 보존한다. 비밀·민감정보를 검사하고 원문을 잃었거나 복사할 수 없으면 추정 복원하지 않고 그 한계를 남긴다. 지적마다 등급·내용·판정 근거, 반영/미반영과 이유, 수정 위치, 같은 reviewer의 재검토 결과와 남은 사항을 연결한다. TASK-CLOSE와 해당 review 로그에 증거 경로를 연결해 실제 원문과 처리 이력을 확인한다. 기록의 존재만으로 독립성이나 의미 판정을 증명하지 않는다.

## 구현 전 TASK 검토

**재검토와 반복 실패는 도구가 단계를 정한다.** fail이면 지적을 반영하고 `pace agent verify`를 다시 부른다 — 도구가 원장의 직전 fail을 기준점으로 골라 그 원문과 바뀐 줄을 주는 **자동 재검토**다(아래 [반복 실패](#반복-실패-진단과-사용자-결정)). 같은 대상이 연속 3회 fail이면 근본 진단, 진단 뒤에도 fail이면 사용자 결정이다. 계획 단계의 경계 사례는 구현 후 검토와 테스트에서 잡는다. TASK.md 자체가 결과물이다. 다른 제공자 CLI로 받을 때는 `pace agent verify --kind task`를 쓴다 — 기본(`goal`) 프롬프트는 TASK·테스트 표 열람을 금지해 검토자가 자기 열람을 독립성 위반으로 지적한다. 1단계에는 상위 목적과 TASK.md만 전달하고 첫 판단을 받은 뒤 2단계에서 PROJECT·브리프를 전달해 대조하며 목적·범위·기준의 관찰 가능성, 테스트의 검출력, 접근·위험 및 누락을 검토한다. 구현 후 diff는 아직 요구하지 않는다. PM은 대상과 제공자·방법·결과, blocking과 should_fix 처리 및 재검토를 기록한다. blocking이 남거나 검토가 실행되지 않으면 구현하지 않는다 — 예외는 [반복 실패](#반복-실패-진단과-사용자-결정)의 사용자 결정으로 붙인 PRE-REVIEW `waiver`(고친 뒤 TASK 해시)뿐이다. 지적 수정이나 검토 대상의 실질적 변경은 `verify`를 다시 불러 자동 재검토를 받는다. purpose에는 합의된 상위 목적과 판정 기준만 넣고 작성자의 지적 대응·자체 판정은 넣지 않는다(독립성 — 검토자는 바뀐 줄로 대응을 직접 본다). 같은 대상의 reviewer 판정은 처음부터 `verify`로 받아 원장을 잇는다 — 도구 밖 reviewer(서브에이전트 등)의 판정은 원장에 남지 않아 반복 실패 단계가 작동하지 않는다. 한 대상의 검토 주기(첫 검토부터 pass·사용자 결정까지)는 경로를 바꾸지 않는다 — `verify`가 미실행(종료 10)일 때만 그 주기 전체를 도구 밖 reviewer로 받고, 같은 세션 재검토(불가능하면 직전 원문·바뀐 부분을 새 세션에 전달)와 함께 연속 fail·진단·결정을 PM이 이 절의 규칙대로 세어 `pace project log`에 기록한다. 주기 중간에 경로를 섞지 않는다 — 원장에 fail이 쌓인 뒤 verify가 미실행(종료 10)이면 다른 제공자를 다시 확인하고, 안 되면 같은 대상에 `verify --allow-same-provider`(교차 아님으로 기록)로 원장을 잇는다. 원장은 대상의 실제 경로(폴더+파일 이름)로 구분하므로 구현 후 검토 diff는 같은 경로(예: `evidence/impl-diff.patch`)를 차수마다 갱신해 `verify`·`review-note`에 쓰고, 차수별 원문은 `review-records/`가 보존한다. 반복 실패 단계는 1단계 `verify` 판정으로 움직인다 — `goal-review.md` 2단계에서 나온 blocking은 PM이 고치되 원장에는 반영되지 않는다(알려진 한계, 프로젝트 이슈). pass 뒤 대상이 실질적으로 바뀌면 원장 구간이 새로 시작돼 다음 verify는 전체 검토다. PM이 판정을 확인하고 범위·목적 변경은 사용자에게 올린다.

다른 제공자를 우선하며 발동 실패·제공자 미확인 등 사유를 남기고 같은 제공자의 별도 새 세션으로 대체한다. 같은 제공자는 교차 검증이 아니다. 양쪽 모두 실행되지 않으면 미검토로 기록한다. 구현 후 최초 검토는 사전 검토와 별도 새 맥락이다. 이 절차는 파일 편집을 기술적으로 차단하거나 검토의 의미를 자동으로 보증하지 않는다. 우회 또는 허위 기록도 가능하므로 PM과 독립 검토자가 실제 증거와 판정을 확인한다.

## 관점

1. **기준 반영**: TASK 기준이 모두 구현됐고, 범위 밖 변경이 섞이지 않았다.
2. **결함**: 기준대로 구현해도 남는 결함 — 경계값, 오류 뒤 부작용, 기존 동작 회귀, 동시성·상태 꼬임.
3. **테스트 검출력**: 테스트가 결함 구현에서 실제로 실패하는가.
4. **설계 일관성**: 승인된 설계·기준 문서·주변 코드와 맞는가.
5. **보안**: 입력 검증, 비밀, 권한, 파일·셸 경로 (`security.md`).
6. **교본 대조**: 바뀐 코드를 언어 색인의 안티패턴과 대조한다. 지적에는 교본·절 이름을 근거로 붙인다. 주변 코드와 같은 방식이어도 보안 문제면 `blocking`이고, 성능 문제나 안티패턴이면 `should_fix`다(새 코드에 퍼뜨리지 않는다).

## 지적 등급

| 등급 | 해당 | 처리 |
|---|---|---|
| `blocking` | 기준 누락, 결함이 통과하는 구멍, 회귀, 항상 통과하는 테스트, 보안 결함 | **구현 전이면 구현 차단, 구현 후면 커밋 차단** — 고치고 다시 검토. 반복 실패의 사용자 결정(아래)만 예외이며, 그때도 계약 목표가 미달·미확인이면 `판정: 막힘`으로 done하지 않는다(goal-review) |
| `should_fix` | 이름·문구 불일치, 약한 테스트, 중복, 더 단순한 방법 | 반영하거나 남김+이유 |
| `handoff` | 구현 중 정할 상세, 다음 태스크로 넘길 것 | TASK-CLOSE "남긴 것" |

불확실한 결함을 낮은 등급으로 내리지 않는다. 함수 배치·이름 같은 선택은 결함이 아니라 handoff다.
재검토(원장의 기준점이 있어 `rereview_of`가 붙는 호출 — 진단·결정·pass 뒤 첫 검토는 전체 검토)에서는 직전 blocking의 해소 여부와 그 수정이 만든 새 결함만 본다. 현재 산출물 전체는 해소 판단의 맥락이고, 바뀌지 않은 부분의 새 지적은 note로 남기며 이번 판정·수정 대상이 아니다(`verify`의 자동 재검토가 이 범위를 지시한다).

## 반환

```
판정: pass (blocking 0) | fail
독립 목표 대조: 맞음 | 어긋남 | 미확인 — <1단계 기록·근거>
목표 달성: 달성 | 미달 | 미확인 — <관측·한계·올릴 단계>
F1 [blocking] <파일:줄> — <문제> → <고칠 방법>
F2 [should_fix] … (근거: typescript/INDEX — <절>)
교본: <색인> — <대조 결과>
```

같은 reviewer 지적이 두 번 이어지고 실질 결함이 아니라 절차·열람 지적이면 structure 층(검토 도구·방식) 문제로 보고 3회를 기다리지 않는다 — 재검토를 더 돌리지 않고 증거 원문(노출 범위·오류 문구)과 함께 코디네이터나 사용자에게 올려 도구를 먼저 고친다. 이 시점은 diagnose 단계가 아니라 `review-note --diagnosis`를 받지 않는다. 도구 결함으로 무효인 그 fail 검토들은 근거(진단 문서)와 함께 `pace agent review-note --target <대상> --void --record review-records/R<n>.json --summary "<도구 결함>" --file <근거>`로 무효 처리한다 — normal 단계의 실행된 fail 검토만 받는다(도구가 강제: diagnose·ask_user 단계에서는 진단·결정으로만 넘어가고, pass·중단 복구는 무효 처리하지 않는다). 무효 검토는 횟수·기준점에서 빠지므로 도구를 고친 뒤 대상이 그대로여도 다시 검토할 수 있다(남은 유효 fail이 있으면 그 기준점의 재검토 — 그 기준점과 대상이 같아 거부되면 그 지적을 아직 반영하지 않았다는 뜻이다. 없으면 전체 검토).

판정은 등급으로 정해진다: blocking이 하나라도 있으면 fail. 실제 목표 이탈·목표 검증 누락은 blocking이며 기준을 모두 채웠다고 낮추지 않는다. 첫 판단과 2단계 대조, 달성/미확인의 근거를 마감에 연결한다.

검토 pass(blocking 0)는 목표 달성 확인을 대신하지 않는다. 해당 계약 목표가 미달/미확인이면 검토 pass여도 마감 불가이며, goal-review에 따라 막힘으로 두고 보완 관측/수정을 요청한다. PM은 검토 판정과 목표 달성 판정을 구별해 합산한다.

## 반복 실패: 진단과 사용자 결정

같은 대상의 독립 검토가 거듭 fail할 때 지적을 하나씩 막는 땜질 반복을 끊는다. 도구(`pace agent verify`)가 대상 폴더의 `REVIEW-LOG.jsonl`에 판정을 자동으로 쌓고 단계를 정한다([AGENT-CALL](../../../docs/AGENT-CALL.md)). 사전 검토와 구현 후 검토에 같은 절차를 쓴다.

**단계 읽기.** verify 출력의 `escalation.stage`를 **받은 그 호출에서 즉시** 따른다. 세 번째 fail을 기록한 호출은 종료 0과 `stage: diagnose`를, 진단 뒤 첫 fail은 종료 0과 `stage: ask_user`를 낸다. 종료 16은 이미 열린 단계에서 다음 호출이 차단됐다는 뜻이다 — 16을 기다렸다가 행동하지 않는다. 예외로 실행 중단 복구(`recovered`)로 그 호출에서 3회가 차면 종료 0 신호 없이 처음부터 16이 나온다 — 그때도 `stage`대로 한다. 서로 다른 blocking이어도 같은 대상의 연속 fail이면 센다. `unknown` 판정은 세지 않으니 원문을 확인한다. 출력의 `recovered`(실행 중단 복구)는 실제 blocking과 구분해 다룬다.

**diagnose — 근본 진단.** 지적별 수정을 멈추고 실패들(차수별 원문·blocking)을 모아 원인 층을 가린다.

| 층 | 묻는 것 | 예 |
|---|---|---|
| structure | 검토 도구·방식이 문제인가? 같은 절차 지적, 열람 불가, 매번 처음부터 전체 검토 | verify 프롬프트·옵션, 재검토 범위 미지정 |
| planning | 목표·범위·전제가 문제인가? 지적이 합의 자체를 흔드는가 | 범위가 넓거나 기준이 관찰 불가 |
| design | 계획이 실제 환경·제품 동작과 어긋났는가? 지적이 같은 뿌리에서 갈라지는가 | 다른 OS 기준 계획, 경로 금지 목록 땜질 |
| other | 위에 없으면 근거와 함께 | |

그 층에서 근본적으로 고친다(예: 계획을 실제 환경 기준으로 다시 씀, 땜질을 구조로 대체). 진단 문서를 `evidence/`에 남기고 `pace agent review-note --target <대상> --diagnosis --layer <층> --summary "<진단·조치>" --file <진단 문서>`로 기록한다. 진단이 합의된 목적·목표·범위 변경을 요구하면 고치기 전에 사용자 결정(SKILL.md §6)을 받는다. 진단 뒤 첫 검토는 원장이 기준점을 고르지 않는 **새 기준 전체 검토**다 — 직전 원문을 purpose에 넣어 범위를 좁히지 않는다.

**ask_user — 사용자 결정.** 더 고치기 전에 사용자에게 다음을 짧게 보고한다: 대상, 실패 추이(차수별 blocking 수), 진단과 고친 층, 남은 지적의 성격(실제 누락 / 검출력·세부 갈래 / 합의와 다른 해석, 중단 복구는 따로), 선택지, 추천과 이유. 사용자의 답은 PM이 **말 그대로** `evidence/`에 남긴다(요약으로 대체하지 않는다 — 도구는 파일이 비어 있지 않은지만 보며 사람의 결정인지는 PM 책임). 그 뒤 `pace agent review-note --target <대상> --decision --choice "<선택>" --summary "<사유>" --file <결정 원문>`.

| 선택 | 다음 행동과 기록 |
|---|---|
| 고치고 다시 검토 | decision 기록 → 고침 → 다음 verify는 전체 검토. pass면 PRE-REVIEW에 그 pass |
| 고치고 구현 진행(사전 검토) | decision 기록 → 고침 → PRE-REVIEW에 `waiver`(사용자·날짜·사유·결정 원문·**고친 뒤** TASK 해시). 원장 결정만으로는 사전 검토 게이트를 통과하지 않는다 |
| 고치고 tester만 / 이슈로 남기고 마감(구현 후) | decision 기록 → 결정 원문을 TASK-CLOSE 리뷰 절에 링크, 남긴 blocking은 이슈와 "남긴 것"에. PRE-REVIEW waiver와는 다른 기록이다 |
| 범위 조정 | §6 계약 변경으로 다룬다 |

## 사전 검토 기록 v1

새 TASK의 `- 사전 검토: v1`에 대응해 태스크 폴더의 `PRE-REVIEW.json`을 작성한다. PM은 각 시도의 실제 출처·제공자와 결과를 확인하고 검토 원문을 같은 태스크 내부 일반 파일로 보존한다. 예시의 해시는 다음 Node 명령으로 현재 TASK의 UTF-8 본문에서 CRLF만 LF로 정규화하고 상태 값을 제외해 구한다(`node -e '...' TASK.md`):

```js
const fs = require('node:fs'), crypto = require('node:crypto');
const task = fs.readFileSync(process.argv[1], 'utf8');
console.log(crypto.createHash('sha256').update(task.replace(/\r\n/g, '\n').replace(/^- 상태: .+$/m, '- 상태:')).digest('hex'));
```

```json
{"version":1,"author":"openai","attempts":[{"hash":"64자리 SHA-256","provider":"anthropic","cross":true,"status":"pass","blocking":0,"evidence":"evidence/review.md","continuity":"new"}]}
```

제공자는 실제 제공자를 일관되게 식별하는 소문자 영문으로 시작하는 64자 이내 영문·숫자·밑줄·하이픈 식별자(예: `openai`, `anthropic`, `google`)다. 도구명이 아닌 모델 회사명을 사용하고 같은 회사는 동일한 식별자로 기록한다. 별칭의 동등성과 제공자 진위는 기계가 검증하지 않는다. 판정은 `pass`·`fail`·`unavailable`, 연속성은 `new`·`same`·`changed`다. `unavailable`과 `changed`는 `reason`이 필요하다. 같은 제공자 대체는 같은 해시에 대해 다른 제공자의 `unavailable` 및 이유가 선행해야 하며 `cross:false`다. 증거는 비어 있지 않은 일반 파일이어야 하며 pass에 양수 blocking을 적을 수 없다. 교차 검토 fail이 같은 해시에 있으면 같은 제공자 대체로 해소할 수 없다. fail 뒤 pass는 `same` 또는 사유가 있는 `changed` 연속성을 기록한다. 배열 마지막 항목의 pass·blocking 0과 현재 해시가 일치해야 한다. **사용자 게이트 예외:** 실행된 검토(pass·fail)가 있는데도 pass에 이르지 못해 사용자가 진행을 명시적으로 승인하면, 이력은 그대로 두고 최상위에 `"waiver":{"by":"user","date":"YYYY-MM-DD","reason":"…","evidence":"evidence/<사용자 결정 원문>.md","hash":"<현재 TASK 해시>"}`를 붙인다. 에이전트·코디네이터가 스스로 쓰지 않으며 TASK가 바뀌면 무효다. waiver는 사전 검토 게이트에만 쓴다 — 구현 후 검토의 반복 실패는 waiver가 아니라 위 [사용자 결정](#반복-실패-진단과-사용자-결정)과 TASK-CLOSE 링크로 다룬다. 마커 제거나 pass 위장은 예외가 아니라 우회다. 검토 후 변경 시 재검토를 받고 이력을 추가한다. CRLF와 LF 차이는 무시하지만 홀로 있는 CR이나 BOM 변경은 해시를 바꾼다. 정규화 전 CRLF 원본 해시로 만든 기록은 재검토·재기록한다. 과거 마커 없는 태스크는 기존 검사로 읽는다. 마커 제거, 이력·증거 조작은 우회할 수 있으며 check는 진정성·의미·실제 구현 전 시점을 보장하지 않는다.

**원장에서 옮겨 적기.** `verify`가 쌓은 원장(`REVIEW-LOG.jsonl`)에서 **이 TASK를 대상으로 실제 실행된** review 항목을 차례로 시도로 옮긴다 — `interrupted`(실행 중단 복구) 항목은 판정 원문이 없으므로 옮기지 않고 횟수·보고에만 반영하며, `void`로 무효 처리된 검토도 옮기지 않는다(원장·기록에 근거와 함께 남는다. 다음 시도의 reason에 무효 사실을 적는다): `hash`=원장 hash(같은 정규화), `status`=verdict(`unknown`은 옮기지 않고 원문을 확인해 다시 검토), `blocking`=원문의 blocking 수, `evidence`=`review-records/R<n>.json`, `provider`=원장 provider. `continuity`는 첫 항목 `new`, 그 뒤 자동 재검토는 `changed`(reason: 자동 재검토·rereview_of), 진단·결정 뒤 전체 검토는 `changed`(reason: 진단 뒤 새 기준 전체 검토) — fail 뒤 pass를 `new`로 적으면 게이트가 거부한다. diagnosis·decision 항목은 시도가 아니므로 옮기지 않고, 사전 검토를 사용자 결정으로 넘기면 `waiver`를 붙인다. `cross`는 작성자 제공자와 provider가 다르면 true다. 미실행(verify 종료 10)은 원장에 없으므로 `unavailable` 시도는 그 출력(`--out` 사본)을 증거로 따로 적는다.
