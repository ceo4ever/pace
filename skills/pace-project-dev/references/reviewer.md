# reviewer — 변경 검토

구현한 세션과 **다른 새 맥락**에서 검토한다. 파일을 고치지 않고 지적만 돌려준다.

## 넘길 것

[goal-review.md](goal-review.md)의 1단계를 먼저 한다. 호출자는 상위 목적/목표와 결과물만 주고 첫 판단을 회수한다. 아래 작업 문서는 그 기록 뒤 2단계에서만 받는다. 산출물 자체가 계획 문서인 경우의 구별·오염 시 새 맥락·규모 비례도 정본을 따른다.

TASK.md(목적·기준·접근), 이 태스크의 전체 diff(`git diff` — 커밋 전 작업본 또는 태스크 시작 커밋 이후), 관련 기준 문서(SKILL.md §5), 바뀐 언어의 `pace-tech-handbook` 색인(`references/<언어>/INDEX.md`), 필요하면 `security.md` 체크리스트.

## TASK 증명 범위와 판정 주체

형식 경계는 머리 목록의 `- TASK 형식: v2`다. 표지가 없는 옛 TASK에는 이 절의 새 요구(누락 blocking 포함)를 적용하지 않고 기존 기준으로 검토한다. 절 존재만으로 새 형식을 추정하지 않는다. 중복·미지원 표지는 거부한다. 게이트와 verify도 같은 표지를 읽는다. 표지 제거·기록 위조는 기존 이력 조작처럼 우회 가능한 한계이며 기계가 진정성을 보증하지 않는다.

새 TASK는 기준·테스트 앞 `## 증명 범위`에 `- 판정 주체:`의 비어 있지 않은 값, 포함, 범위 밖(이유·넘길 곳)을 쓴다. 게이트는 절 누락·빈 절(HTML 주석만 있는 절 포함)·판정 주체 누락/빈 값을 거부한다. 포함·범위 밖의 충분성은 reviewer의 의미 판정이다.

증명 범위·판정 주체가 비면 그것 자체만 **blocking 1건**으로 내고 다른 지적을 늘어놓지 않는다. 단건 억제는 게이트가 거부하는 구조 누락(절 없음·주석뿐인 절·주체 줄 없음·값 공백)에 한한다. 미정·TBD 같은 실제 텍스트의 의미적 불충분성에는 나머지 지적을 억제하지 않는다. 구조 누락을 채운 다음 verify는 아직 평가하지 못한 목적·필수 안전까지 전체 검토한다(rereview_of null, 실패 집계는 유지). blocking은 적힌 증명 범위로 목적·기준을 증명할 수 없을 때다. 현재 적힌 범위가 이미 목적·기준을 충분히 입증한다면 그 밖으로 확대하라는 요구는 목적 증명에 필요하지 않아도 should_fix로 남긴다. 합의 범위 밖이라는 이유로 note로 바꾸지 않는다. should_fix는 범위 변경 승인이나 반영 의무가 아니며 확장은 별도 합의를 받는다. 범위 자체가 목적에 비해 좁으면 blocking이며 범위 밖 선언으로 검토를 피할 수 없다.

판정 주체의 권한도 대조한다. 사람의 결정이 정답인 기준은 승인받은 사람의 원문을 왜곡·누락 없이 옮기고 불완전하면 미확인으로 드러내면 통과다. 작성자나 자동 검사가 그 결정을 대신하거나 필수 안전 기준(보안·데이터·되돌리기 어려운 행동)을 범위 밖으로 빼면 blocking이다. 재검토에서는 이 규칙도 직전 blocking 해소와 바뀐 줄이 만든 새 결함 범위 안에서 적용한다.

## 사전 검토 이력 보존

PM은 검토 차수마다 최초 판정과 재검토 원문을 고유한 증거 경로에 보존한다. 비밀·민감정보를 검사하고 원문을 잃었거나 복사할 수 없으면 추정 복원하지 않고 그 한계를 남긴다. 지적마다 등급·내용·판정 근거, 반영/미반영과 이유, 수정 위치, 같은 reviewer의 재검토 결과와 남은 사항을 연결한다. TASK-CLOSE와 해당 review 로그에 증거 경로를 연결해 실제 원문과 처리 이력을 확인한다. 기록의 존재만으로 독립성이나 의미 판정을 증명하지 않는다.

## 구현 전 TASK 검토

**재검토와 반복 실패는 도구가 단계를 정한다.** fail이면 지적을 반영하고 `pace agent verify`를 다시 부른다 — 도구가 원장의 직전 fail을 기준점으로 골라 그 원문과 바뀐 줄을 주는 **자동 재검토**다(아래 [반복 실패](#반복-실패-진단과-사용자-결정)). 단계와 기록은 아래 반복 실패 절을 따르고, 조치 전 결정 주체는 [결정 권한 정본](decision-rights.md)의 A로 판정한다. 계획 단계의 경계 사례는 구현 후 검토와 테스트에서 잡는다. TASK.md 자체가 결과물이다. 다른 제공자 CLI로 받을 때는 `pace agent verify --kind task`를 쓴다 — 기본(`goal`) 프롬프트는 TASK·테스트 표 열람을 금지해 검토자가 자기 열람을 독립성 위반으로 지적한다. 1단계에는 상위 목적과 TASK.md만 전달하고 첫 판단을 받은 뒤 2단계에서 PROJECT·브리프를 전달해 대조하며 목적·범위·기준의 관찰 가능성, 테스트의 검출력, 접근·위험 및 누락을 검토한다. 구현 후 diff는 아직 요구하지 않는다. PM은 대상과 제공자·방법·결과, blocking과 should_fix 처리 및 재검토를 기록한다. blocking이 남거나 검토가 실행되지 않으면 구현하지 않는다 — 예외는 [반복 실패](#반복-실패-진단과-사용자-결정)의 사용자 결정으로 붙인 PRE-REVIEW `waiver`(고친 뒤 TASK 해시)뿐이다. 지적 수정이나 검토 대상의 실질적 변경은 `verify`를 다시 불러 자동 재검토를 받는다. purpose에는 합의된 상위 목적과 판정 기준만 넣고 작성자의 지적 대응·자체 판정은 넣지 않는다(독립성 — 검토자는 바뀐 줄로 대응을 직접 본다). 같은 대상의 reviewer 판정은 처음부터 `verify`로 받아 원장을 잇는다 — 도구 밖 reviewer(서브에이전트 등)의 판정은 원장에 남지 않아 반복 실패 단계가 작동하지 않는다. 한 대상의 검토 주기(첫 검토부터 pass·사용자 결정까지)는 경로를 바꾸지 않는다 — `verify`가 미실행(종료 10)일 때만 그 주기 전체를 도구 밖 reviewer로 받고, 같은 세션 재검토(불가능하면 직전 원문·바뀐 부분을 새 세션에 전달)와 함께 연속 fail·진단·결정을 PM이 이 절의 규칙대로 세어 `pace project log`에 기록한다. 주기 중간에 경로를 섞지 않는다 — 원장에 fail이 쌓인 뒤 verify가 미실행(종료 10)이면 다른 제공자를 다시 확인하고, 안 되면 같은 대상에 `verify --allow-same-provider`(교차 아님으로 기록)로 원장을 잇는다. 원장은 대상의 실제 경로(폴더+파일 이름)로 구분하므로 구현 후 검토 diff는 같은 경로(예: `evidence/impl-diff.patch`)를 차수마다 갱신해 `verify`·`review-note`에 쓰고, 차수별 원문은 `review-records/`가 보존한다. 반복 실패 단계는 1단계 `verify` 판정으로 움직인다 — `goal-review.md` 2단계에서 나온 blocking은 PM이 고치되 원장에는 반영되지 않는다(알려진 한계, 프로젝트 이슈). pass 뒤 대상이 실질적으로 바뀌면 원장 구간이 새로 시작돼 다음 verify는 전체 검토다. PM이 판정을 확인하고 합의 영향은 [A-1](decision-rights.md#a-결정-주체)로 대조한다.

다른 제공자가 미실행이면 [A-3의 B1](decision-rights.md#a-결정-주체)에 따라 사유를 남기고 같은 제공자의 별도 새 세션으로 대체한다. 대체 검토에는 `cross: false`를 기록하고, 양쪽 모두 미실행이면 허브와 검토를 복구한다. 검토 생략·완화가 실제 제안이면 A-3 결정을 요청한다. 구현 후 최초 검토는 사전 검토와 별도 새 맥락이다. 이 절차는 파일 편집을 기술적으로 차단하거나 검토의 의미를 자동으로 보증하지 않는다. 우회 또는 허위 기록도 가능하므로 PM과 독립 검토자가 실제 증거와 판정을 확인한다.

## 관점

관리 단위의 각 검토에는 질문 하나를 둔다.

| 종류 | 판정 질문 |
|---|---|
| 백로그 | 이 백로그로 프로젝트에 착수하면 owner에게 다시 묻지 않고 합의한 목표까지 갈 수 있는가? |
| 구현 전 | 이 계획이 목적을 증명할 수 있는가? |
| 구현 후 | 이 변경을 내보내도 되는가? |


1. **기준 반영**: TASK 기준이 모두 구현됐고, 범위 밖 변경이 섞이지 않았다.
2. **결함**: 기준대로 구현해도 남는 결함 — 경계값, 오류 뒤 부작용, 기존 동작 회귀, 동시성·상태 꼬임.
3. **테스트 검출력**: 테스트가 결함 구현에서 실제로 실패하는가.
4. **설계 일관성**: 승인된 설계·기준 문서·주변 코드와 맞는가.
5. **보안**: 입력 검증, 비밀, 권한, 파일·셸 경로 (`security.md`).
6. **교본 대조**: 바뀐 코드를 언어 색인의 안티패턴과 대조한다. 지적에는 교본·절 이름을 근거로 붙인다. 주변 코드와 같은 방식이어도 보안 문제면 `blocking`이고, 성능 문제나 안티패턴이면 `should_fix`다(새 코드에 퍼뜨리지 않는다).

## 지적 등급

| 등급 | 해당 | 처리 |
|---|---|---|
| `blocking` | 기준 누락, 결함이 통과하는 구멍, 회귀, 항상 통과하는 테스트, 보안 결함 | **구현 전이면 구현 차단, 구현 후면 커밋 차단** — 고치고 다시 검토. 반복 실패의 사용자 결정(아래)만 예외이며, 그때도 계약 목표가 미달·미확인이면 `판정: 막힘`으로 done하지 않는다(goal-review) |
| `should_fix` | 이름·문구 불일치, 약한 테스트, 중복, 더 단순한 방법 | 반영하거나 남김+이유 |
| `note` | 구현 중 정할 상세, 다음 태스크로 넘길 것 | TASK-CLOSE "남긴 것" |

불확실한 결함을 낮은 등급으로 내리지 않는다. 함수 배치·이름 같은 선택은 note로 남긴다.
재검토(원장의 기준점이 있어 `rereview_of`가 붙는 호출 — 진단·결정·pass 뒤 첫 검토는 전체 검토)에서는 직전 blocking의 해소 여부와 그 수정이 만든 새 결함만 본다. 현재 산출물 전체는 해소 판단의 맥락이고, 바뀌지 않은 부분의 새 지적은 note로 남기며 이번 판정·수정 대상이 아니다(`verify`의 자동 재검토가 이 범위를 지시한다).

## 반환

태스크와 백로그의 `pace agent verify`에서는 프롬프트가 정한 `pace-review` JSON 블록을 한 개 작성한다. 지적마다 번호, 등급, 질문의 하위 항목 ID, 파일과 줄, 실패 조건, 재현 수단, 확신도를 남긴다. 질문 밖 지적은 note로 기록하며 사전 검토의 구현 방식은 구현 후 검토로, 백로그의 설계·구현 방식은 프로젝트 설계로 넘긴다. 질문에 연결된 blocking의 위치·실패 조건·재현 수단이 빠지면 도구가 should_fix로 기록한다. 원래 등급과 강등 사유를 보존한다. 형식을 판독하지 못하면 unknown이다. 원문의 마지막 판정은 도구 판정과 대조하는 자료다.

단위 밖 `goal` 검토와 호스트에서 받는 반환:


```
판정: pass (blocking 0) | fail
독립 목표 대조: 맞음 | 어긋남 | 미확인 — <1단계 기록·근거>
목표 달성: 달성 | 미달 | 미확인 — <관측·한계·올릴 단계>
F1 [blocking] <파일:줄> — <문제> → <고칠 방법>
F2 [should_fix] … (근거: typescript/INDEX — <절>)
교본: <색인> — <대조 결과>
```

같은 reviewer 지적이 두 번 이어지고 실질 결함이 아니라 절차·열람 지적이면 structure 층(검토 도구·방식) 문제로 보고 3회를 기다리지 않는다 — 재검토를 더 돌리지 않고 증거 원문(노출 범위·오류 문구)과 함께 [B](decision-rights.md#b-허브의-장애-대응)로 허브에 이관해 원인을 재현하고 도구를 먼저 고친다. 이 시점은 diagnose 단계가 아니라 `review-note --diagnosis`를 받지 않는다. 도구 결함으로 무효인 그 fail 검토들은 근거(진단 문서)와 함께 `pace agent review-note --target <대상> --void --record review-records/R<n>.json --summary "<도구 결함>" --file <근거>`로 무효 처리한다 — normal 단계의 실행된 fail 검토만 받는다(도구가 강제: diagnose·ask_user 단계에서는 진단·결정으로만 넘어가고, pass·중단 복구는 무효 처리하지 않는다). 무효 검토는 횟수·기준점에서 빠지므로 도구를 고친 뒤 대상이 그대로여도 다시 검토할 수 있다(남은 유효 fail이 있으면 그 기준점의 재검토 — 그 기준점과 대상이 같아 거부되면 그 지적을 아직 반영하지 않았다는 뜻이다. 없으면 전체 검토).

판정은 등급으로 정해진다: blocking이 하나라도 있으면 fail. 실제 목표 이탈·목표 검증 누락은 blocking이며 기준을 모두 채웠다고 낮추지 않는다. 첫 판단과 2단계 대조, 달성/미확인의 근거를 마감에 연결한다.

검토 pass(blocking 0)는 목표 달성 확인을 대신하지 않는다. 해당 계약 목표가 미달/미확인이면 검토 pass여도 마감 불가이며, goal-review에 따라 막힘으로 두고 보완 관측/수정을 요청한다. PM은 검토 판정과 목표 달성 판정을 구별해 합산한다.

## 반복 실패: 진단과 사용자 결정

이 절은 검토 원장의 단계·조치·보고를 다룬다. 원장은 단계와 연속 fail을 계산하고, PM은 **모든 수정 직전**에 합의된 목적·목표·범위와 조치의 실제 영향을 확인한다. 진단에서 근본 조치를 정할 때, 진단 뒤 fail의 조치를 정할 때, 재검증에서 새 지적을 고칠 때 모두 적용한다. 이미 승인된 구체적 조치를 다시 승인받지는 않으며 새로운 영향이 생기면 다시 분류한다.

**단계 읽기.** 태스크는 루트와 `evidence/` 원장을 합산하고 사전·구현 후 예산을 따로 쓴다. 백로그는 폴더마다 한 예산을 쓴다. 단계마다 전체 검토 1회, 직전 유효 판정과 변경을 보는 범위 재검토 1회, 총 호출 4회가 상한이다. 중단·무효·unknown은 판정에서 빠지고 호출에는 남는다. 대상 변경·pass·결정 기록 뒤에도 예산이 유지된다. verify가 `budget.exhausted`를 내면 같은 단계의 다음 실행은 종료 16과 `reason: budget_exhausted`로 막힌다.

소진 출력의 `classify_followup`을 받으면 허브가 [결정 권한 B](decision-rights.md#b-허브의-장애-대응)로 다음 조치를 판정한다. 필요한 수정 확인은 직전 지적 ID와 원래 위치, 최신 해시에 묶는다. 횟수 문턱에서는 허브가 구조 원인·수정·확인 범위를 기록하고 필요한 독립 확인을 수행한다. 진단과 누적 횟수·판정을 사후 보고한다. 실제 합의 변경은 A-1, 증거 공백·잔여 blocking을 안고 진행하거나 필수 검증을 생략·완화하는 선택은 A-3으로 요청한다.

일반 산출물의 기존 관문에서는 세 번째 fail과 진단 뒤 첫 fail에 종료 0과 `escalation.stage: diagnose` 또는 `ask_user`가 붙는다. 기록 없이 다시 호출하면 종료 16이다. `ask_user`는 호환용 단계 이름이며 필요한 결정 기록을 먼저 남긴다. `recovered`가 있는 응답에도 같은 단계를 적용한다. 일반 산출물의 진단은 중단 복구(`interrupted`)도 센다. unknown과 중단 기록은 재검토 기준점에서 빠진다.

진단 표지가 열린 동안에는 `review-note --diagnosis`로 기록한다. 그 기록 직후는 normal이다. 확정된 조치를 적용하고 `verify` 전체 검토로 넘어간다. `review-note --decision` 입력은 그 검토가 fail로 끝나 `ask_user` 단계가 열린 뒤에만 한다. 진단·normal에서 필요한 owner 응답은 원문을 진단 근거나 프로젝트 기록에 연결한다.

### 조치 전 영향 분류

[결정 권한 정본 A](decision-rights.md#a-결정-주체)로 실제 조치를 대조하고, 근거가 부족하거나 조치에서 막히면 [B](decision-rights.md#b-허브의-장애-대응)로 허브와 해결한다. owner에게 요청하는 경우 확인한 증거와 남은 불확실성, 해당 A 번호를 붙인다. 원장이 센 회차와 blocking 수는 근본 조치 시점을 알려 준다.

### diagnose — 원인 층의 근본 조치

지적별 땜질을 멈추고 실패 원문과 차수별 blocking을 모아 원인 층을 가린다: structure(도구·검토 방식), planning(목표·범위·전제), design(설계와 실제 환경·제품 동작), other(근거 명시). 같은 영역 재지적이면 그 설계를 다시 진단한다.

이미 합의한 OS·환경에 다른 환경의 설계를 적용해서 여러 지적이 생기면 `design`이다. 예를 들어 macOS 환경의 계획에 Windows의 PATH·서비스 등록·종료 방식을 가져온 경우 실제 환경 기준의 설계를 다시 쓴다. 환경 자체를 결정한 목표나 전제가 틀렸다면 `planning`으로 판별한다.

워크트리 PM은 세 차례 근거와 진단을 허브에 보내 B로 근본 조치를 정한다. 단독 PM은 같은 절차를 수행한다. 근본 조치에 A를 적용한다. A 밖 조치는 PM이 결정하고 진단 증거를 남긴다. A에 걸리는 조치는 owner 결정 뒤 적용한다. diagnose 단계에서는 decision 대신 확인된 승인 원문 위치 또는 원장 영수증을 진단 증거에 연결한다. `pace agent review-note --target <대상> --diagnosis --layer <층> --summary <진단·조치> --file <진단 증거>`로 기록한다. 진단 뒤 첫 verify는 새 기준 **전체 검토**이며 이전 지적으로 purpose를 좁히지 않는다.

### ask_user — 분류에 따른 결정 기록

이 절은 일반 산출물의 기존 단계에 적용한다. 필수 검증을 생략하거나 남은 blocking을 안고 진행하는 조치는 A-3으로 owner에게 요청한다.

A 밖 조치는 PM이 `evidence/`의 근거 파일에 **분류 이유·근본 조치**를 쓰고 `pace agent review-note --target <대상> --decision --by pm --choice <선택> --summary <사유> --file <근거>`로 기록한다. 근본 조치 → 전체 재검증 → 사후 보고로 간다. PM 결정은 waiver가 아니며 사전 검토는 현재 TASK 해시에 대한 pass를 받아 PRE-REVIEW에 연결한다. 같은 영역이 또 지적되면 위 원인 층을 다시 진단한다.

A에 해당하는 결정은 허브를 거쳐 수정 전에 요청한다. 해당 번호와 **대상·실패 추이·진단과 고친 층·남은 지적 성격·선택지·추천과 이유**의 6요소를 붙인다. [실행 전 승인 확인](decision-rights.md#실행-전-승인-확인)에 따라 워크트리 PM이 원문과 현재 대상을 대조한다. `pace agent review-note --target <대상> --decision --by user --choice <선택> --summary <사유> --file <승인 근거>`로 기록한다. 원장을 쓰면 로컬 원문을 확인하고 근거 파일에는 답 ID·지문·출처를 담은 영수증을 연결한다. 결정에 맞춰 아래의 수정·검증 순서를 수행한다.

| 사용자 선택 | 후속 기록·행동 |
|---|---|
| 고치고 다시 검토 | user decision → 수정 → 전체 검토 |
| 고치고 구현 진행(사전 검토) | user decision → 수정 → 고친 뒤 TASK 해시가 승인 대상인지 확인 → PRE-REVIEW waiver(by user·날짜·사유·승인 근거·고친 뒤 TASK 해시) |
| 고치고 tester만 / 이슈로 남기고 마감(구현 후) | user decision·원문을 TASK-CLOSE 리뷰에 연결하고 남긴 blocking을 이슈·남긴 것에 기록. 계약 목표 미달·미확인이면 done 금지 |
| 범위 조정 | [A-1](decision-rights.md#a-결정-주체)로 처리 |

재검증의 normal 단계에서 새 위험을 발견하면 수정 전에 실제 조치를 A로 분류한다. 지적의 해결에 미승인 실제 사용자 데이터 전송이 필요하면 전송에 필요한 owner 결정을 먼저 받는다. 해당 승인 원문의 근거를 `pace project log`에 연결하고 normal 단계의 검증을 잇는다. `review-note`의 decision은 `ask_user`, diagnosis는 `diagnose`에 사용한다.

### 보고와 감사

PM 경로의 사후 보고는 **무엇이 반복됐는지·고친 층·채우거나 덜어낸 것·재검증 결과**의 4요소를 TASK-CLOSE 리뷰 절과 [C의 사후 요약](decision-rights.md#c-owner에게-전할-내용)에 남긴다. 사용자 경로는 위 6요소를 수정 전에 보고하고 결정 원문·승인 직전 대상 해시(또는 diff 없음)·승인 뒤 첫 수정 기록을 연결한다. 커밋 시각만으로 승인 전 수정 여부를 주장하지 않는다.

새 decision의 by는 pm/user 필수다. 옛 by 없는 결정은 단계 계산에 계속 쓰되 주체를 unknown(미확인)으로 보고하며 user로 추정하지 않는다. PRE-REVIEW waiver는 사용자만 허용한다. 기록의 존재는 의미·진정성·실제 수정 시점을 자동 보증하지 않는다.

## 사전 검토 기록 v1

새 TASK의 `- 사전 검토: v1`에 대응해 태스크 폴더의 `PRE-REVIEW.json`을 작성한다. PM은 각 시도의 실제 출처·제공자와 결과를 확인하고 검토 원문을 같은 태스크 내부 일반 파일로 보존한다. 예시의 해시는 다음 Node 명령으로 현재 TASK의 UTF-8 본문에서 CRLF만 LF로 정규화하고 상태 값을 제외해 구한다(`node -e '...' TASK.md`):

```js
const fs = require('node:fs'), crypto = require('node:crypto');
const task = fs.readFileSync(process.argv[1], 'utf8');
console.log(crypto.createHash('sha256').update(task.replace(/\r\n/g, '\n').replace(/^- 상태: .+$/m, '- 상태:')).digest('hex'));
```

```json
{"version":1,"author":"openai","attempts":[{"hash":"64자리 SHA-256","provider":"anthropic","cross":true,"status":"pass","blocking":0,"evidence":"evidence/review.md","continuity":"new"}]}
```

제공자는 실제 제공자를 일관되게 식별하는 소문자 영문으로 시작하는 64자 이내 영문·숫자·밑줄·하이픈 식별자(예: `openai`, `anthropic`, `google`)다. 도구명이 아닌 모델 회사명을 사용하고 같은 회사는 동일한 식별자로 기록한다. 별칭의 동등성과 제공자 진위는 기계가 검증하지 않는다. 판정은 `pass`·`fail`·`unavailable`, 연속성은 `new`·`same`·`changed`다. `unavailable`과 `changed`는 `reason`이 필요하다. 같은 제공자 대체는 같은 해시에 대해 다른 제공자의 `unavailable` 및 이유가 선행해야 하며 `cross:false`다. 증거는 비어 있지 않은 일반 파일이어야 하며 pass에 양수 blocking을 적을 수 없다. 교차 검토 fail이 같은 해시에 있으면 같은 제공자 대체로 해소할 수 없다. fail 뒤 pass는 `same` 또는 사유가 있는 `changed` 연속성을 기록한다. 배열 마지막 항목의 pass·blocking 0과 현재 해시가 일치해야 한다. **사용자 게이트 예외:** 실행된 검토(pass·fail)가 있는데도 pass에 이르지 못해 사용자가 진행을 명시적으로 승인하면, 이력은 그대로 두고 최상위에 `"waiver":{"by":"user","date":"YYYY-MM-DD","reason":"…","evidence":"evidence/<승인 근거>.md","hash":"<현재 TASK 해시>"}`를 붙인다. 입력 전 [원문과 현재 TASK 해시](decision-rights.md#실행-전-승인-확인)를 대조한다. 원장이 있으면 태스크 내부 일반 근거 파일은 로컬 원문을 가리키는 영수증으로 연결한다. TASK가 바뀌면 예외는 무효다. waiver는 사전 검토 게이트에만 쓴다 — 구현 후 검토의 반복 실패는 waiver가 아니라 위 [사용자 결정](#반복-실패-진단과-사용자-결정)과 TASK-CLOSE 링크로 다룬다. 마커 제거나 pass 위장은 예외가 아니라 우회다. 검토 후 변경 시 재검토를 받고 이력을 추가한다. CRLF와 LF 차이는 무시하지만 홀로 있는 CR이나 BOM 변경은 해시를 바꾼다. 정규화 전 CRLF 원본 해시로 만든 기록은 재검토·재기록한다. 과거 마커 없는 태스크는 기존 검사로 읽는다. 마커 제거, 이력·증거 조작은 우회할 수 있으며 check는 진정성·의미·실제 구현 전 시점을 보장하지 않는다.

**원장에서 옮겨 적기.** `verify`가 쌓은 원장(`REVIEW-LOG.jsonl`)에서 **이 TASK를 대상으로 실제 실행된** review 항목을 차례로 시도로 옮긴다 — `interrupted`(실행 중단 복구) 항목은 판정 원문이 없으므로 옮기지 않고 횟수·보고에만 반영하며, `void`로 무효 처리된 검토도 옮기지 않는다(원장·기록에 근거와 함께 남는다. 다음 시도의 reason에 무효 사실을 적는다): `hash`=원장 hash(같은 정규화), `status`=verdict(`unknown`은 옮기지 않고 원문을 확인해 다시 검토), `blocking`=원문의 blocking 수, `evidence`=`review-records/R<n>.json`, `provider`=원장 provider. `continuity`는 첫 항목 `new`, 그 뒤 자동 재검토는 `changed`(reason: 자동 재검토·rereview_of), 진단·결정 뒤 전체 검토는 `changed`(reason: 진단 뒤 새 기준 전체 검토) — fail 뒤 pass를 `new`로 적으면 게이트가 거부한다. diagnosis·decision 항목은 시도가 아니므로 옮기지 않고, 사전 검토를 사용자 결정으로 넘기면 `waiver`를 붙인다. `cross`는 작성자 제공자와 provider가 다르면 true다. 미실행(verify 종료 10)은 원장에 없으므로 `unavailable` 시도는 그 출력(`--out` 사본)을 증거로 따로 적는다.
