# 독립 리뷰어

리뷰어는 작성자와 분리된 새 맥락에서 목적·계약·결과를 판단한다. 배정과 권한은 [역할과 검증 책임](verification.md#역할과-검증-책임), 다른 제공자 확인과 대체는 [교차 검증](cross-verify.md)을 따른다.

## 넘길 것

- 상위 목적, 확인할 산출물과 버전, 필요한 안전 기준. 사전 검토의 산출물은 TASK.md다.
- 구현 후·큰 산출물은 [목표 대조](goal-review.md)의 첫 독립 판단을 회수한 뒤 작업 문서를 넘긴다. 최초 판정에 작성자의 결론이나 지적 대응을 넣지 않는다.
- 실제 열람 범위, 자동 주입 맥락, 검토자·제공자와 변경 사유를 남긴다. 원문과 판정은 같은 시도의 증거로 보존한다.

## TASK 증명 범위와 판정 주체

누가 어떤 증거로 목적을 확인하는지 본다. 증명할 범위와 넘길 범위를 구별하고, 합의한 안전 기준 및 사람의 승인 원문을 대조한다. 작은 계획은 목표·수용 기준·증명 범위에 집중한다. 계획의 규모와 검증 방법은 [태스크 단계](task-steps.md)를 따른다.

## 사전 검토 이력 보존

넘기는 시점의 TASK와 원문을 연결한다. `verify`나 [외부 검토의 고정 및 사전 검토 기록](../../../docs/AGENT-CALL.md#외부-검토의-고정-및-사전-검토-기록)을 사용한다. 새 판정은 새 시도로 남기고 실패·미실행 증거도 보존한다.

## 구현 전 TASK 검토

**이 계획이 목적을 증명할 수 있는가?** 목적, 관찰 가능한 기준, 시험이 실패를 검출하는 조건을 대조한다. 기준·증명·안전에 영향 없는 구현 방식 의견은 질문 밖 note로 인계한다. 원문과 도구 등급이 다르면 질문 범위와 실제 영향에 맞춰 판정을 대조한다. 취향 지적은 note로 다음 단계에 인계한다. 기존 사전 검토 원문과 적용 판정으로 사전 기록을 확인하고, 도구가 이를 막으면 B에서 오분류를 재현해 복구한다. 취향을 만족시키기 위한 구현 수정이나 재검토는 요구하지 않는다. 필수 검증을 그대로 수행하는 동안 A-3 요청은 열지 않는다. 외부 시스템의 계획은 발견한 선례와 실제 환경을 확인한다.

## 관점

- 구현 후에는 **이 변경을 내보내도 되는가?** 합의 기준, 재현 가능한 결함·회귀와 안전 영향을 확인한다.
- 백로그는 **이 백로그로 프로젝트에 착수하면 owner에게 다시 묻지 않고 합의한 목표까지 갈 수 있는가?** 준비된 목표·순서·근거와 남은 결정을 확인한다.
- 의도나 검토자 권한으로 증명하지 않는다. 실행 결과, 재현 위치, 확인한 관측과 근거의 한계를 기록한다.

## 지적 등급

blocking·should_fix·note 중 도구가 적용한 등급과 원문을 함께 본다. 의미 있는 blocking에는 합의 목적·기준·안전 영향과 재현 근거를 남긴다. should_fix는 반영하거나 사유를 기록한다. 질문 밖 note는 관련 다음 단계에 인계한다. 필수 증거가 불충분하면 관측을 보완한다.

## 반환

`pace-review` JSON 블록의 현재 질문·필수 기준·판정 형식은 `verify`가 요청한다. 원문이 붙어 있어도 도구가 계산한 판정과 기준별 결과를 확인한다. 사람이 답할 근거가 미확인이라면 판정을 보류한다. 새·옛 반환 형식의 차이와 판독 실패는 [호출 정본](../../../docs/AGENT-CALL.md#에이전트-호출)을 참조한다.

reviewer와 tester는 직전 지적·변경 줄·최신 재현을 대조한다. 같은 부류가 재발하면 해당 지적의 선택값으로 `recurrence: "same_class"`, 직전 수정이 지적된 예만 고쳤고 같은 부류의 다른 사례가 남으면 `recurrence: "superficial_fix"`를 쓴다. 위치·재현·직전 기록을 근거로 적으며 모르면 선택값을 생략한다. tester는 구조화 출력이 있는 경로에서 같은 값을 쓰고 텍스트 반환에서는 같은 평가를 근거와 함께 적는다. `pace agent verify`의 검토를 준비하는 PM은 선택값의 뜻과 근거 작성 방법을 `--purpose-file`로 안내한다. 같은 대상을 재검토할 때 직전 지적과 바뀐 줄은 `verify`가 원장에서 제공한다. 선택값은 기존 판정과 도구의 증거 기반 신호를 유지한다.

## 반복 실패: 진단과 사용자 결정

원장이 정한 직전 판정과 바뀐 줄로 재검토한다. 직전 지적의 미해소 부분과 수정이 만든 결함은 이번에 고치고 재검토한다. 영향 밖 지적은 note로 둔다. 지적 반영 뒤 같은 `verify`를 호출하면 해당 범위로 재검토한다. 정상 단계의 기록이 중단 복구뿐이면 전체 검토로 열린다. 단계가 `diagnose`로 바뀌면 중단과 실제 blocking을 나눠 진단한다.

도구가 반환한 `followup`·`escalation`을 따른다. 예산 관리 단위에서 `upper_review`가 반환됐을 때 상위 검토를 연다. 같은 경위에서도 기존 `ask_user`가 반환됐다면 아래 결정 기록과 전체 재검증 경로를 적용한다.

### 태스크와 백로그의 수정 확인과 상위 검토

소진부터 반복 실패까지의 전체 대응은 아래 순서로 확인한다. 이미 마친 단계의 근거는 원장에서 대조한다.

- **일반 예산 소진** — 첫 소진에서 소진 보고와 직전 지적·재현 근거를 [B](decision-rights.md#b-허브의-장애-대응)로 허브에 올린다. 허브 회신의 조치를 적용한 뒤, 도구가 허용하면 `review-note --joint`로 근거를 기록하고 독립 공동 검토를 받는다. 각 회차의 원문·조치·판정을 같은 예산 단위로 기록한다. 반복 실패를 보고할 때는 최초 소진부터 이 절차를 거친 근거를 연결한다.
- **공동 한도 이후** — 허브와 구조 진단 및 필요한 수정·독립 재검증의 근거를 확정한다. 수정 확인은 직전 지적과 최신 변경의 영향에 묶는다. 검토 재개 범위는 B와 도구가 반환한 상태로 확인한다. 일반·공동 경로가 모두 막히면 허브와 진단·근본 조치·독립 확인 경로를 먼저 확정한다. 필요한 독립 재검증을 수행하고 성공·실패의 근거와 누적 회차를 사후 보고한다.
- **상위 검토** — 도구가 이 단계를 반환하면 새 맥락의 원인·해결안 대조와 적용 뒤 한정 확인을 이어 받는다. 조치 전 영향은 아래의 A 분류를 따른다.

#### 호출 주체와 기회

도구 출력에서 상위 검토·소진을 조기 권고보다 먼저 확인한다. 호출 전에 실패 원문과 바뀐 줄을 대조한다. 직전 수정이 같은 부류의 다른 실패를 남겼는지, 같은 영역이 다시 지적됐는지 확인한다. 지정 역할의 호출과 모델 적용은 [팀 호출 정본](../../../docs/TEAM.md#문제-해결자-호출과-실제-적용)을 따른다. 역할 원본이나 정해진 실행이 미확인이면 B에서 해결한다. 호출 입력과 읽기 범위는 그 기회의 근거로 한정한다.

| 관측 | 호출 주체와 다음 행동 |
|---|---|
| 태스크 예산 안 `test_failures`, `recurring_area`, `superficial_fix` | 워크트리 PM이 목표·실패 원문·바뀐 줄을 넘겨 `pace-troubleshooter`를 한 번 부른다. 단독 PM은 같은 책임을 맡는다. PM이 해법의 영향을 판정하고 구현자에게 적용을 맡긴 뒤 기존 검토로 재검증한다. |
| 예산 관리 단위 `budget_exhausted` 또는 해당 종료 16 | 워크트리 PM은 소진 보고·직전 지적·재현 근거를 허브에 인계하고 그 기회에 전문가를 부르지 않는다. 허브는 공동 시도마다 한 번 부른다. |
| 예산 밖 일반 산출물의 `review_failures` | 그 단계 PM이 `normal`에서 부른다. 이미 도구가 반환한 `diagnose`·`ask_user`의 처리는 해당 절을 따른다. `normal`의 조기 호출로 원장 진단을 만들지 않는다. |
| B 절차의 검토·검사 장애, 백로그 검토 | [허브](coordinator.md#문제-해결자-호출)가 재현·원인 판별 단계에서 부른다. 백로그 검토의 조치 결정은 허브가 하고 기획자가 적용한 뒤 독립 재검증한다. |
| `verify`의 `escalation.stage: upper_review` 또는 `review-record`의 `followup.action: upper_review` | 발동 결과는 종료 0일 수 있다. 워크트리 PM은 수정을 멈추고 실패 원문·구조 진단 기록·바뀐 줄을 허브에 인계한다. 호출과 결정은 [허브](coordinator.md#문제-해결자-호출)의 몫이다. |
| 신호 없는 첫 실패 | 직전 독립 지적을 고치고 기존 절차를 따른다. |

같은 대상과 단계에서 같은 근거 회차에 함께 나온 신호는 한 기회다. 조기 호출, 뒤 공동 시도 1·2, 각 `upper_review`는 별개 기회다. 전문가 호출은 자문이며 검토 예산에 더하지 않는다. 조기 호출 뒤 독립 재검증은 기존 단계의 유효 검토 회차다. 예산 안에서는 자문 반환을 프로젝트 `log.jsonl`과 호출 원장에만 남긴다. `review-note --diagnosis`는 절차가 정한 허브 구조 진단에 사용한다. 조기 자문을 거기에 쓰면 다음 독립 실패가 상위 검토를 발동할 수 있다.

#### 호출과 증거 연결

[호출 원장 정본](../../../docs/WORK-PROCESS.md#에이전트-호출-원장)을 사용한다. 한 기회에 `caller`, 단위·단계·발동 근거·회차를 포함한 `opportunity`, 원장 `callId`, 반환 상대 경로를 담은 JSON 근거를 둔다. 실제 `pace agent run`의 한 시도 ID·시각을 유지하고 `ref`로 그 근거를 보강한다. 프로젝트는 `pace project log … --ref`로, 백로그는 해당 폴더의 단계 근거와 `calls/log.jsonl`로 연결한다. 조기 워크트리 1회와 공동 1·2회가 이어지면 각각 `worktree_pm`, `hub_pm`, `hub_pm`과 각기 다른 `opportunity`를 각 기회의 실제 시도 ID에 연결한다. 예산 밖 일반 산출물의 caller는 `document_pm`이다. 상위 단계의 반환은 [허브 근거](coordinator.md#문제-해결자-호출)와 같은 시도 ID로 확인한다. 실제 호출 후 새 행의 범위·에이전트·호스트·시각을 대조해 시도를 고른다. 어느 행인지 확인할 수 없으면 결합을 보류한다.

### 조치 전 영향 분류

모든 수정 직전 [A](decision-rights.md#a-결정-주체)를 실제 조치에 적용한다. 합의를 바꾸는 조치는 A-1, 필수 검증 생략·완화 또는 미확인 증거·잔여 blocking 수용은 A-3으로 요청한다. 확인한 증거와 남은 불확실성, 대상·선택지·추천을 허브에 보낸다. [실행 전 승인 확인](decision-rights.md#실행-전-승인-확인)으로 원문과 실행 대상을 대조한다.

normal 단계에서 새 위험이 생기면 A를 다시 적용한다. 필요한 승인 원문의 근거는 `pace project log`에 연결하고 normal 단계의 `verify`로 이어 간다. 일반 산출물의 `review-note --decision`은 `ask_user`가 열린 대상에 쓴다. 태스크·백로그에서 실제 A-3 요청을 열었다면 [호출 정본](../../../docs/AGENT-CALL.md#독립-검토)의 요청과 승인 입력을 따른다.

### diagnose — 원인 층의 근본 조치

`diagnose` 신호를 받으면 지적별 수정을 멈추고 공통 원인 층을 조사한다. 합의한 OS에 다른 OS의 동작을 옮겨 실패했다면 설계 층으로 보고 실제 환경과 대조한다. 워크트리에서 막힌 조치는 [B](decision-rights.md#b-허브의-장애-대응)로 허브와 확정한다.

조치에 A를 적용하고, 필요한 승인을 확인한 뒤 근본 조치를 적용한다. 적용 내용·근거와 필요한 승인 원문을 `review-note --diagnosis`에 연결한다. `--decision`은 다음 절의 `ask_user`에 쓴다. 진단 기록에 성공했으면 바로 `verify`로 전체를 검토한다.

### ask_user — 분류에 따른 결정 기록

기존 `ask_user`는 결정 주체 분류 신호다. A 밖 조치는 영향 분류 이유와 근본 조치를 `--decision --by pm`으로 기록하고 수정한 뒤 `verify`로 최신 대상의 모든 필수 기준을 독립 검토한다. A에 해당하면 대상, 실패 추이, 진단과 고친 층, 남은 지적, 선택지, 추천과 이유를 [C의 결정 요청](decision-rights.md#c-owner에게-전할-내용)에 담는다.

현재 대상에 맞는 승인 원문을 확인하고 `--decision --by user`로 연결한 뒤 승인된 조치를 수행한다.

- 사용자 승인으로 다시 검토할 때는 승인된 수정 뒤 전체를 검토한다.
- 사전 검토를 예외로 진행할 때는 실제 사용자 근거와 고친 TASK의 해시를 PRE-REVIEW의 `waiver`에 `by: user`로 남긴다.
- 구현 후 남은 지적을 수용할 때는 승인 원문은 TASK-CLOSE 리뷰에 연결하고, 남은 blocking은 이슈와 TASK-CLOSE의 남긴 것에 기록한다. 필수 기준 미달·미확인은 별도 합의가 필요하다.

### 보고와 감사

사후 보고에서도 원장의 실패·중단·unknown(미확인)을 구별한다. 담당 PM이 해결한 건은 결정과 이유, 적용한 조치, 독립 재검증의 근거와 결과, 남은 일을 기록한다. 무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과를 TASK-CLOSE 리뷰 절과 [C의 사후 요약](decision-rights.md#c-owner에게-전할-내용)에 남긴다.

## 사전 검토 기록 v1

`pace agent review-pre`로 원장과 원문에서 PRE-REVIEW.json을 생성한 뒤 현재 TASK에 맞는지 확인한다. 통과하면 기록된 허가 범위 안에서만 진행한다. 원래 지적 위치의 작은 수정은 보호 위치와 실제 diff를 게이트가 확인할 때 이어가고, 허용 경계를 벗어나면 새 검토를 받는다. 기존 사용자 예외는 승인 원문과 현재 해시를 확인한다.

옛 사전 기록의 해시를 직접 대조할 때는 아래 코드를 `node -e '<코드>' TASK.md`로 실행한다.

```js
const fs = require('node:fs'), crypto = require('node:crypto');
const task = fs.readFileSync(process.argv[1], 'utf8');
console.log(crypto.createHash('sha256').update(task.replace(/\r\n/g, '\n').replace(/^- 상태: .+$/m, '- 상태:')).digest('hex'));
```
