# reviewer — 변경 검토

구현한 세션과 **다른 새 맥락**에서 검토한다. 파일을 고치지 않고 지적만 돌려준다.

## 넘길 것

[goal-review.md](goal-review.md)의 1단계를 먼저 한다. 호출자는 상위 목적/목표와 결과물만 주고 첫 판단을 회수한다. 아래 작업 문서는 그 기록 뒤 2단계에서만 받는다. 산출물 자체가 계획 문서인 경우의 구별·오염 시 새 맥락·규모 비례도 정본을 따른다.

TASK.md(목적·기준·접근), 이 태스크의 전체 diff(`git diff` — 커밋 전 작업본 또는 태스크 시작 커밋 이후), 관련 기준 문서(SKILL.md §5), 바뀐 언어의 `pace-tech-handbook` 색인(`references/<언어>/INDEX.md`), 필요하면 `security.md` 체크리스트.

## 사전 검토 이력 보존

PM은 검토 차수마다 최초 판정과 재검토 원문을 고유한 증거 경로에 보존한다. 비밀·민감정보를 검사하고 원문을 잃었거나 복사할 수 없으면 추정 복원하지 않고 그 한계를 남긴다. 지적마다 등급·내용·판정 근거, 반영/미반영과 이유, 수정 위치, 같은 reviewer의 재검토 결과와 남은 사항을 연결한다. TASK-CLOSE와 해당 review 로그에 증거 경로를 연결해 실제 원문과 처리 이력을 확인한다. 기록의 존재만으로 독립성이나 의미 판정을 증명하지 않는다.

## 구현 전 TASK 검토

**사전 검토는 최대 2회다.** 2회차에도 blocking이 남으면 3회차를 돌리지 않고 남은 지적과 증거를 붙여 사용자에게 올린다(진행·범위 축소·게이트 예외). 계획 단계의 경계 사례는 구현 후 검토와 테스트에서 잡는다. TASK.md 자체가 결과물이다. 다른 제공자 CLI로 받을 때는 `pace agent verify --kind task`를 쓴다 — 기본(`goal`) 프롬프트는 TASK·테스트 표 열람을 금지해 검토자가 자기 열람을 독립성 위반으로 지적한다. 1단계에는 상위 목적과 TASK.md만 전달하고 첫 판단을 받은 뒤 2단계에서 PROJECT·브리프를 전달해 대조하며 목적·범위·기준의 관찰 가능성, 테스트의 검출력, 접근·위험 및 누락을 검토한다. 구현 후 diff는 아직 요구하지 않는다. PM은 대상과 제공자·방법·결과, blocking과 should_fix 처리 및 재검토를 기록한다. blocking이 남거나 검토가 실행되지 않으면 구현하지 않는다. 지적 수정이나 검토 대상의 실질적 변경은 같은 reviewer 세션에 재검토를 맡긴다. 같은 세션이 불가능하면 사유와 이전 지적·수정 내용을 새 세션에 전달하고 연속성 한계를 기록한다. PM이 판정을 확인하고 범위·목적 변경은 사용자에게 올린다.

다른 제공자를 우선하며 발동 실패·제공자 미확인 등 사유를 남기고 같은 제공자의 별도 새 세션으로 대체한다. 같은 제공자는 교차 검증이 아니다. 양쪽 모두 실행되지 않으면 미검토로 기록한다. 구현 후 최초 검토는 사전 검토와 별도 새 맥락이다. 이 절차는 파일 편집을 기술적으로 차단하거나 검토의 의미를 자동으로 보증하지 않는다. 우회 또는 허위 기록도 가능하므로 PM과 독립 검토자가 실제 증거와 판정을 확인한다.

## 관점

1. **기준 반영**: TASK 기준이 모두 구현됐고, 범위 밖 변경이 섞이지 않았다.
2. **결함**: 기준대로 구현해도 남는 결함 — 경계값, 오류 뒤 부작용, 기존 동작 회귀, 동시성·상태 꼬임.
3. **테스트 검출력**: 테스트가 결함 구현에서 실제로 실패하는가.
4. **설계 일관성**: 승인된 설계·기준 문서·주변 코드와 맞는가.
5. **보안**: 입력 검증, 비밀, 권한, 파일·셸 경로 (`security.md`).
6. **교본 대조**: 바뀐 코드를 언어 색인의 안티패턴과 대조한다. 지적에는 교본·절 이름을 근거로 붙인다. 주변 코드와 같은 방식이어도 보안 문제면 `blocking`이고, 성능 문제나 안티패턴이면 `should_fix`다(새 코드에 퍼뜨리지 않는다).

## 지적 등급

| 등급 | 해당 | 처리 |
|---|---|---|
| `blocking` | 기준 누락, 결함이 통과하는 구멍, 회귀, 항상 통과하는 테스트, 보안 결함 | **구현 전이면 구현 차단, 구현 후면 커밋 차단** — 고치고 다시 검토 |
| `should_fix` | 이름·문구 불일치, 약한 테스트, 중복, 더 단순한 방법 | 반영하거나 남김+이유 |
| `handoff` | 구현 중 정할 상세, 다음 태스크로 넘길 것 | TASK-CLOSE "남긴 것" |

불확실한 결함을 낮은 등급으로 내리지 않는다. 함수 배치·이름 같은 선택은 결함이 아니라 handoff다.
두 번째 검토부터는 직전 blocking의 해소 여부와 그 수정이 만든 새 결함만 본다.

## 반환

```
판정: pass (blocking 0) | fail
독립 목표 대조: 맞음 | 어긋남 | 미확인 — <1단계 기록·근거>
목표 달성: 달성 | 미달 | 미확인 — <관측·한계·올릴 단계>
F1 [blocking] <파일:줄> — <문제> → <고칠 방법>
F2 [should_fix] … (근거: typescript/INDEX — <절>)
교본: <색인> — <대조 결과>
```

같은 reviewer 지적이 두 번 이어지고 실질 결함이 아니라 절차·열람 지적이면 재검토를 더 돌리지 않고 증거 원문(노출 범위·오류 문구)과 함께 코디네이터나 사용자에게 올린다 — 검토 도구 자체의 결함일 수 있다.

판정은 등급으로 정해진다: blocking이 하나라도 있으면 fail. 실제 목표 이탈·목표 검증 누락은 blocking이며 기준을 모두 채웠다고 낮추지 않는다. 첫 판단과 2단계 대조, 달성/미확인의 근거를 마감에 연결한다.

검토 pass(blocking 0)는 목표 달성 확인을 대신하지 않는다. 해당 계약 목표가 미달/미확인이면 검토 pass여도 마감 불가이며, goal-review에 따라 막힘으로 두고 보완 관측/수정을 요청한다. PM은 검토 판정과 목표 달성 판정을 구별해 합산한다.

## 사전 검토 기록 v1

새 TASK의 `- 사전 검토: v1`에 대응해 태스크 폴더의 `PRE-REVIEW.json`을 작성한다. PM은 각 시도의 실제 출처·제공자와 결과를 확인하고 검토 원문을 같은 태스크 내부 일반 파일로 보존한다. 예시의 해시는 다음 Node 명령으로 현재 TASK의 UTF-8 본문에서 CRLF만 LF로 정규화하고 상태 값을 제외해 구한다(`node -e '...' TASK.md`):

```js
const fs = require('node:fs'), crypto = require('node:crypto');
const task = fs.readFileSync(process.argv[1], 'utf8');
console.log(crypto.createHash('sha256').update(task.replace(/\r\n/g, '\n').replace(/^- 상태: .+$/m, '- 상태:')).digest('hex'));
```

```json
{"version":1,"author":"openai","attempts":[{"hash":"64자리 SHA-256","provider":"anthropic","cross":true,"status":"pass","blocking":0,"evidence":"evidence/review.md","continuity":"new"}]}
```

제공자는 실제 제공자를 일관되게 식별하는 소문자 영문으로 시작하는 64자 이내 영문·숫자·밑줄·하이픈 식별자(예: `openai`, `anthropic`, `google`)다. 도구명이 아닌 모델 회사명을 사용하고 같은 회사는 동일한 식별자로 기록한다. 별칭의 동등성과 제공자 진위는 기계가 검증하지 않는다. 판정은 `pass`·`fail`·`unavailable`, 연속성은 `new`·`same`·`changed`다. `unavailable`과 `changed`는 `reason`이 필요하다. 같은 제공자 대체는 같은 해시에 대해 다른 제공자의 `unavailable` 및 이유가 선행해야 하며 `cross:false`다. 증거는 비어 있지 않은 일반 파일이어야 하며 pass에 양수 blocking을 적을 수 없다. 교차 검토 fail이 같은 해시에 있으면 같은 제공자 대체로 해소할 수 없다. fail 뒤 pass는 `same` 또는 사유가 있는 `changed` 연속성을 기록한다. 배열 마지막 항목의 pass·blocking 0과 현재 해시가 일치해야 한다. **사용자 게이트 예외:** 실행된 검토(pass·fail)가 있는데도 pass에 이르지 못해 사용자가 진행을 명시적으로 승인하면, 이력은 그대로 두고 최상위에 `"waiver":{"by":"user","date":"YYYY-MM-DD","reason":"…","evidence":"evidence/<사용자 결정 원문>.md","hash":"<현재 TASK 해시>"}`를 붙인다. 에이전트·코디네이터가 스스로 쓰지 않으며 TASK가 바뀌면 무효다. 구현 후 검토는 예외 대상이 아니다. 마커 제거나 pass 위장은 예외가 아니라 우회다. 검토 후 변경 시 재검토를 받고 이력을 추가한다. CRLF와 LF 차이는 무시하지만 홀로 있는 CR이나 BOM 변경은 해시를 바꾼다. 정규화 전 CRLF 원본 해시로 만든 기록은 재검토·재기록한다. 과거 마커 없는 태스크는 기존 검사로 읽는다. 마커 제거, 이력·증거 조작은 우회할 수 있으며 check는 진정성·의미·실제 구현 전 시점을 보장하지 않는다.
