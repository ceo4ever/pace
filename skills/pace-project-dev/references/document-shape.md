# 문서 형식과 추적

템플릿은 개발 업무의 예시다. 업무와 읽는 사람에 맞게 메모·비교표·연구 노트·기획서 등을 고르되, **목표/상위 목적 → 선택한 전략과 이유 → 이번 단계/결정 → 관측 결과**를 거슬러 설명할 수 있어야 한다. 큰 일은 대안·근거를 드러내고 작은 일은 짧게 판단한다. 새 고정 칸·별도 전략 문서를 매번 만들지 않는다.

## 가장 작은 연결

기존 목적에 상위 목표/전략 링크와 이번 단계의 기여를 한 문장으로 쓴다. 설계·접근·결정 기록에는 고른 길과 이유를, 결과/마감에는 관측을 연결한다. 링크만으로 관계를 알 수 없으면 짧게 설명한다.

- 백로그 목표: 누구의 어떤 결과를 위해 이 길을 고르는가, 상위 목적과 근거.
- 브리프 목적: 백로그의 어느 목표·전략을 이번 결과가 수행하는가.
- 프로젝트 목적/설계: 브리프의 목표·선택을 어떤 실행으로 잇는가.
- 태스크 목적/접근: 프로젝트 기준/전략 중 무엇에 기여하는가.
- 결정: 관련 목표/전략 링크 + 선택과 이유. 기존 결정 메모·`project log --ref`와 짧은 메시지로 충분하다. 새 번호/문서를 만들 의무는 없다.
- 결과: 선택한 길로 목표가 달성됐는지 실제 근거와 대조한다. 연결이 있다고 목표 타당성·결과 달성이 자동 증명되지는 않는다.

하네스를 쓰지 않는 작은 일은 대화의 목적·선택·관측만으로 충분하다. 하네스를 쓰면 업무별 본문을 아래 구조 안에 쓰거나 별도 산출물을 링크한다. 링크만 두고 계약 목적/기준을 비우지 않는다. 일반 업무 산출물에 P-n·T-n 형식을 강요하지 않는다.

## 명령이 읽는 구조와 자유 영역

다음은 기존 명령과 함께 쓰는 계약 파일의 구조다. 일반 보고서에 이 절을 강제하지 않는다. 형식 검사는 사고 검증의 보조 수단이다.

| 대상·소비자 | 보존할 구조 | 업무에 맞게 고를 부분 |
|---|---|---|
| BACKLOG: intent check·backlog brief·project new --from | BL 폴더/BACKLOG.md, 상태, `## 목표`, `## 진행 현황` 기존 5칸 표(브리프·상태·선행·프로젝트·비고)·BR 파일 연결 | 목표 본문·근거·추가 절·산출물 |
| BR: intent check·project new/done | BR##_이름.md 유일 번호·상태, `## 목적`·`## 범위`·`## 완료 기준`; BR 번호↔T 번호 | 범위/관찰 기준 서술·비교표·산출물 링크 |
| PROJECT: intent check·project | P### 폴더/PROJECT.md, 상태·출처·브랜치/worktree 머리, `## 목적`·`## 재료`·`## 기준` P-n 표. 태스크 사용 시 `## 태스크` 4칸 표(T·이름·상태·커밋). 설계의 정본 목록은 finish가 읽음 | 목적/재료/설계 본문·추가 절. 태스크 없는 프로젝트는 태스크 표 생략 |
| TASK/마감: project check/done | TASK.md 상태·`## 기준` T-n 표. 새 `- TASK 형식: v2`는 `## 증명 범위`와 비어 있지 않은 `- 판정 주체:` 값(주석·코드 예제 제외); 표지 없는 옛 TASK는 호환. TASK-CLOSE.md의 `- 태스크: … 판정: 통과`, `## 기준 대조` 동일 ID/결과 `통과`, 비지 않은 `## 단위 테스트`·`## E2E`·`## 리뷰`·`## 남긴 것`, 적은 증거 파일의 실재 | 목적/재료/접근 본문·검증 계층. 코드 테스트가 안 맞으면 해당 없음 이유와 적합한 문서/관측 검증을 기록 |
| 프로젝트 마감: project finish | P-n 기준 대조, 보안·정본 반영 표(브레인 포함), 지표 링크/해석, 완료 태스크·태그 커밋·정본/증거 검사 | 업무별 결과 해석·회고·관측 형태. 목표 달성은 별도 판단 |
| 정의서: 실행 선언 | docs/README.md의 `검사`·`보안 검사`·`worktree 준비` 라벨 | 나머지 업무 설명. 선언 라벨은 한 번씩 유지 |

소비자: `src/intent/handoff.ts`는 BACKLOG/BR/PROJECT 종류별 필수 절·중복 절·임의 표의 빈 칸·주석뿐인 절·자리 표시를 검사한다. 추가 절도 주석만 쓰지 않고, 모든 표의 비고·커밋 외 칸은 채운다. TASK/CLOSE는 받지 않는다. `src/project/harness.ts`는 태스크/기준 표·마감과 done 때 BR/현황 상태 동기화를 담당한다. `src/project/backlog.ts`는 생성·번호·브리프 행 추가를 담당한다. 정책상 남길 계약·검증 내용은 파서가 덜 읽는다는 이유로 버리지 않는다.

자유 표는 명령이 표를 읽는 절 밖(목적·범위 등 본문이나 별도 고유 `##` 절)에 둔다. 명령이 읽는 절(진행 현황·기준·태스크·기준 대조·정본 반영) 안에 표를 더 넣으면 하네스가 같은 절의 표 행을 합쳐 읽어 오인/중복 매칭할 수 있다. `##` 제목은 겹치지 않게 하고 본문 소제목은 `###`를 쓴다. `###`를 써도 같은 명령용 절 안에 업무 표를 추가해도 된다는 뜻은 아니다.

## 구조를 더 줄일지 비교

| 선택 | 얻는 것 | 비용·판단 |
|---|---|---|
| 필수 절/ID/표 삭제·업무별 개명 | 계약 파일의 표면 형식 감소 | 파서·상태 동기화·기존 자료 호환 변경. 자유 본문으로 해결 가능해 채택하지 않음 |
| 모든 일에 같은 개발 문서 | 작성 형식 일치 | 읽는 사람/업무와 안 맞고 작은 일에 부담. 채택하지 않음 |
| 계약 최소 구조 보존 + 본문/산출물 선택 | 추적·게이트 호환과 업무별 표현 보존 | 이번 선택. 작은 일은 프로젝트 자체 생략, 하네스 사용 시 필요한 절은 짧게 의미 있게 작성 |

예시: 비개발 업무의 의사결정 메모·근거 대조표. 가상 판단을 실제 성과나 사용자 판정으로 치지 않는다.

TASK 형식 구조 파서는 전체 Markdown 렌더러가 아니다. 여러 줄에 걸친 인라인 코드 등 복잡한 혼합 구문은 오판할 수 있으므로 머리 목록과 증명 범위는 템플릿의 일반 텍스트 필드로 작성한다. 표지 제거·본문 위조는 이력 조작과 같은 진정성 한계다.
