# 태스크 단계 세부

1. **분석** — `pace project task P### "<이름>"`으로 대기 행을 연다. 목적·재료를 쓰고 앞 태스크가 넘긴 일을 확인한다.

2. **설계** — TASK에 목적·기준 `T-n`·테스트와 [증명 범위·판정 주체](reviewer.md#task-증명-범위와-판정-주체)를 쓴다. 기준마다 실패를 검출할 가장 간단한 시험을 연결한다. 접근은 핵심 한두 줄로 쓴다. 기준 문서는 SKILL.md §5에서 고른다. 코드의 설계·테스트는 해당 교본과 대조한다.
   **기준 범위 한정** — `## 증명 범위`의 포함은 변경 영향 경로(이 변경이 실제로 건드리는 진입점·데이터·흐름)로 쓰고 기준 `T-n`은 그 경로로 한정한다. 변경이 건드리지 않는 기존 동작은 범위 밖에 "기존 동작 — 기존 회귀 시험"으로 적는다. 구현 후 reviewer 줄(`필요`·`생략`)은 같은 경로에 대한 경계·상태·흐름 사실 질문으로 정한다. owner·캡틴 결정이 TASK 기준과 달라지면 PM이 TASK를 고치고 [A-1](decision-rights.md#a-결정-주체)로 기록한 뒤 범위 재검토를 받는다.
   **외부 시스템 선례** — Telegram·OS 서비스·다른 CLI를 다루는 태스크는 설계 전에 브레인에서 선례를 검색하고 기존 도구의 동작을 확인한다. 발견한 사례와 현재 환경의 차이 또는 검색했으나 찾지 못한 결과를 TASK의 `선례` 한 줄에 적어 독립 검토에 넘긴다.
   **구현 전 검토** — TASK의 목적·기준·시험을 작성자와 다른 제공자의 새 맥락에 넘긴다(Claude PM → Codex, Codex PM → Claude). 미실행은 [B1](decision-rights.md#a-결정-주체)로 복구한다. [독립 리뷰어](reviewer.md) 판정과 사전 기록이 허용한 범위에서 구현한다. 실제 합의 변경은 SKILL.md §6을 따른다.

3. **구현** — 사전 검토 통과 뒤 계약을 구현한다. 변경이 허가 경계를 넘으면 검토를 다시 받는다.

4. **테스트** — 선언 검사와 E2E를 수행한다. 구현 후 배정의 정의는 이 절 하나다.
   - **tester**는 모든 태스크에서 새 맥락으로 돈다([tester.md](tester.md)).
   - **reviewer**는 TASK의 `구현 후 reviewer`가 `필요`이거나, `생략`이어도 PM이 구현 diff를 보고 필요하다고 판단하면 부른다. 부른 이유 또는 `reviewer 생략 — 이유`를 TASK-CLOSE에 적는다. 도구는 TASK 값으로 막거나 열지 않는다. reviewer는 tester가 통과시킨 diff에만 부르고 구현 diff만 넘긴다 — 결과 문서·증거 대조는 tester 몫이다. 매 호출 세 묶음 12항목 전체를 묻는다([reviewer.md](reviewer.md#관점)).
   - **재호출**: 직전 reviewer 판정이 pass가 아니거나 tester 통과 뒤 수정 diff가 생겼으면 reviewer를 다시 부른다. 수정 diff는 tester를 통과한 뒤에 넘긴다. 예외: 직전 reviewer가 pass이고 수정 diff가 화면 문구·제품 문서만 고쳤으며 그 diff에 경계·상태·흐름(A·B·C) 사실 질문을 적용한 답이 모두 "아니오"면 tester만 다시 본다(판단과 답을 TASK-CLOSE에 적는다). 스킬·참조 문서(`skills/**`, `docs/**`의 절차·권한·게이트 문서)는 에이전트의 흐름 규칙이라 이 예외에 들지 않는다. 예산 소진이나 헝크 없는 diff(모드·이름만)로 도구가 재호출을 거부하면 [반복 실패](reviewer.md#태스크와-백로그의-수정-확인과-상위-검토) 절차대로 허브에 인계한다.
   - **시각 기록(필수)**: TASK-CLOSE `## 리뷰`에 tester와(불렀으면) reviewer의 회차마다 `요청 시각`(PM 검증 요청)과 `회수 시각`(판정 결과 수신 — 배정 시작 회신이 아니다)을 반드시 적는다. 시각은 `date` 출력이나 같은 사건의 `log.jsonl` 행 `ts`에서 옮기고, 검토 원장 `call`·`review` 행이나 커밋 시각으로 대신하지 않는다.
   실패를 고친 뒤 위 순서로 다시 확인하고 [반복 실패](reviewer.md#반복-실패-진단과-사용자-결정)의 도구 상태를 따른다. should_fix는 반영하거나 이유를 기록한다. 질문 밖 note의 인계는 남긴 것에 적는다. TASK-CLOSE의 리뷰 절에는 시도별 판정과 교본 대조를 남긴다.
   **상한 뒤 수정 확인** — [결정 권한 B](decision-rights.md#b-허브의-장애-대응)에 따라 직전 지적과 변경에 범위를 묶는다(구현 후 reviewer는 해소 확인과 함께 diff 전체 12항목을 묻는다). 합의 기준에 필요한 구조 수정과 독립 재검증을 수행하고 근거와 결과를 사후 보고한다. 검증을 생략하거나 완화하는 선택은 A-3 절차를 따른다.
