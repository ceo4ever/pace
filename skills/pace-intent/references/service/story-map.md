## Looks at

The user's activities laid left to right (the backbone), the stories under each activity top to bottom by priority, and horizontal slices that make releases each usable end to end.

## Key questions

- What are the big activities in order (the backbone)?
- Under each activity, which stories are needed for the simplest working version?
- What is the thinnest slice that lets the user complete the whole journey once?
- Which slices can be released and learned from separately?

## Common gaps

- Release 1 builds one activity deeply and leaves others missing, so nothing works end to end.
- Stories are technical tasks, not user actions.
- No slice line — everything is "MVP".

## Turning gaps into questions

Propose the backbone and a first slice; ask the user only to confirm the slice line, with the recommended thin slice first.
Example: "첫 버전은 어디까지? ① 기획→생성→내 계정 1곳 발행까지 한 줄로(추천 — 처음부터 끝까지 한 번 돌아야 검증돼요) ② 기획·생성만 ③ 세 플랫폼 발행까지 — 첫 백로그의 브리프 수가 달라져요."

## Tensions

- With **MoSCoW**: MoSCoW ranks features in isolation; the story map ranks by end-to-end usefulness — when they disagree, ask whether a Must is useless without a Could.
- With **Lean Canvas**: the canvas wants the differentiator early; the thin slice may leave it out — ask whether release 1 must include the differentiator.

## When not to use

L0 documents; a single feature with one story.

## Output form

Form: backbone activities as columns, stories as rows, slice lines labelled 릴리스 1 · 2 · 이후.
Link to first layer: journey stages become activities; each slice becomes a brief (C) or the task list (B).
When to produce: L2+ when splitting into briefs or tasks.

## Closing

End with the release 1 slice written as one sentence ("사용자는 … 을 처음부터 끝까지 한 번 할 수 있다") and the list of briefs it produces.
