## Looks at

The parts a given document type must contain so the reader can act on it — not a fixed template, but a list of must-haves per type.

## Key questions

- Which document type is it, and does the reader's organisation have its own format?
- Which must-have parts are missing for this type?
- Which parts are optional and can be dropped for this reader?

Must-haves by type:

| Type | Must contain |
|---|---|
| Report (보고서) | key message · period/scope · results vs. plan · issues and asks · next steps |
| Proposal (제안서) | problem · proposed solution · alternatives considered · cost/effort · expected effect · decision requested |
| PRD | purpose and success metric · users and jobs · scope (in/out) · requirements with acceptance criteria · open questions |
| Business plan (사업계획서) | summary · problem and customer · solution and value · market · business model · marketing and sales · organisation and team · funding request and use · financial projections |

## Common gaps

- A proposal without alternatives or cost, so it cannot be approved.
- A PRD without out-of-scope and acceptance criteria.
- A report without "what I need from you".

## Turning gaps into questions

Fill must-haves from context; ask only for numbers or decisions the user owns, one at a time, recommending a placeholder when unknown.
Example: "제안서의 예산 칸은? ① 범위로 적기(추천 — 아직 견적 전) ② 확정 금액 ③ 이번엔 빼기 — 승인권자는 보통 금액을 먼저 봐요."
If the organisation has its own format (attached or in project docs), follow it and map the must-haves into it.

## Tensions

- With **audience**: the reader may want one page while the skeleton has six parts — merge parts rather than drop a must-have.
- With **MoSCoW**: for a PRD, scope cutting decides which requirements stay; the skeleton only says the in/out section must exist.

## When not to use

Free-form messages, prompts, or a type not in the table — use the audience and SCQA lenses alone.

## Output form

Form: the outline of the chosen document type with each must-have filled, labelled `가정`, or marked `미결`.
Link to first layer: answers from other lenses fill the parts (purpose ladder → purpose, assumption map → open questions, GWT → acceptance criteria).
When to produce: whenever the request names a document type.

## Closing

End with a checklist result: every must-have of the type is present, assumed, or open — none silently missing.
