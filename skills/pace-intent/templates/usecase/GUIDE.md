# Use cases — `usecase`

Generated by `pace intent render <docs>` from `docs/plan.json`; this folder holds `template.html` (layout and render code), `schema.json` (page data, `x-pace` metadata), `example.html` (the example rendered), and this guide. While planning, read only this guide, [schema.json](schema.json), and the example data [../_example/plan.json](../_example/plan.json) — never the HTML (D12). Screen text is in the user's language.

## When to make it

L1: one or two use cases for the change. L2: all. L3: only the core ones (details go to split backlogs).

## First-layer lens questions

Drawing this document exposes these gaps:

- Who is the primary actor, and which external systems take part?
- What must be true before (pre) and after (post)?
- For every basic step: what can go wrong? Each `예외` alternative needs an `AC`.
- Does a use case need a sequence (external system, async/long work, auth delegation, payment, ≥3 participants with several failure points)? Write the reason in `sequence`.

## IDs and links

`UC-n` (use case), `A-n` (actor). Steps and alternatives point to `SCR-n`; alternatives to `AC-n`; `features` to `F-n`.

## Data in plan.json

`actors[]` (`external`, `docs` with official `url` and `checked` date for external systems), `usecases[]` (`steps`, `alts` with kind `대안`/`예외`), optional `relations[]` (`include`/`extend`). Full shape: [../_base/plan.schema.json](../_base/plan.schema.json).

## Checks

`usecase-fields`, `exception-ac`, `steps-screens`, `id-refs`.

## When not to use

L0 documents. A single-screen tweak with no new behaviour (write a GWT line instead).
