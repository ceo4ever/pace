# 프로젝트 정의와 최신화

프로젝트는 **무엇을, 왜** 하는지 정의하는 것이다. 이 스킬이 만든 문서·메모리는 이후 모든 작업의 맥락이 된다.

| 산출물 | 역할 |
|---|---|
| `AGENTS.md` (+ `CLAUDE.md`의 `@AGENTS.md`) | 모든 LLM 도구가 매 세션 읽는 진입점: 일하는 법 요약과 길 안내 |
| `docs/README.md` | 저장소 정의서: 개요·구성·환경·작업 프로세스·문서 표(용도·적용 범위) — `pace project` 하네스가 명령과 기준 문서를 여기서 읽는다 |
| 유형별 문서 (`docs/`) | 근거가 있을 때만: ARCHITECTURE·CONVENTIONS 등 |
| `.pace/test-map.json` | 개발 프로젝트 검사 단위·공통 경로의 기계 판독 정본 (초안 승인 뒤 작성) |
| 프로젝트 메모리 | 진행 상황·지킬 것·이슈·할 일 (`pace memory --project`) |
| `backlogs/BL{YYMMDD}_{NN}_{한글명}/` | 작업 방식으로 백로그를 고르면 첫 백로그 |
| `projects/README.md` | 작업 방식으로 프로젝트를 고르면 — 실행 폴더 안내(git은 빈 폴더를 남기지 않아 안내 파일로 폴더를 만든다) |

형식 원본: `references/project-docs.md`(정의서·AGENTS.md), `references/backlog-format.md`(백로그),
`references/analysis.md`(분석·대조 방법), `references/test-map.md`(검사 구성·최신화). 쓰기 전에 해당 파일을 읽는다.

## 원칙

- **분석이 먼저**다. 코드·설정에서 알 수 있는 것은 묻지 않고 기본값으로 보여 주며 확인만 받는다.
- 질문은 **한 번에 하나**, 번호와 전체 개수(Q1/6)를 붙인다. 객관식에는 "기타(직접 입력)"를 둔다. 선택지 UI가 있는 도구는 그것을 쓴다.
- 모든 문서는 **초안 → 사용자 검토 → 반영 → 확정** 순서. 기존 파일은 승인 없이 덮어쓰지 않는다.
- 구조·방법(HOW) 서술에는 근거 파일 경로를 단다. 근거가 없으면 쓰지 않는다.
- 명령은 **실제로 돌려 본 것만 "확인됨"**으로 적는다. 오래 걸리거나 부수효과가 있는 명령(배포·DB 변경 등)은 실행 전에 묻는다.
- 기존 파일을 고치기 전 git 상태를 본다. 커밋 안 된 변경이 있으면 알린다. git이 없으면 `docs/backup/{파일명}_{YYYYMMDDHHMM}.md`로 복사해 둔다.

## 0. 모드 판별 (묻지 않는다)

| 모드 | 판별 (프로젝트 루트 기준) | 진행 |
|---|---|---|
| 최신화 | `AGENTS.md` 또는 `.pace/memory/` 있음 | §1 → §4 |
| 기존 | 코드·문서는 있는데 위 둘이 없음 | §1 → §2(4문) → §3 |
| 신규 | 거의 빈 폴더 | §1(짧게) → §2(6문) → §3 |

세션 부트의 "현재 위치"(PACE 프로젝트 / 정의 없음 / 새 프로젝트)가 같은 판별이다.

## 1. 분석 (모든 모드)

`references/analysis.md`의 절차를 따른다.

1. **레이아웃**: 깊이 2~3으로 훑어 코드·문서·작업·미분류 디렉터리로 나눈다(config 파일 기준).
2. **구성과 스택**: 구성 요소(Frontend·Backend·Batch·Mobile·문서 등)별 경로와 스택, 레포 구조(단일·멀티레포·멀티서비스).
3. **환경**: 빌드·테스트·실행·린트 명령 후보를 config에서 찾고(예: `package.json` scripts, `Makefile`, `pyproject.toml`, `build.gradle`), 짧은 것은 실행해 확인한다. 포트·환경변수·외부 서비스.
4. **기존 문서·지침**: README, `docs/`, `CLAUDE.md`·`GEMINI.md`·`.cursorrules`의 규칙 — 흡수할 후보.
5. **검사 구성**: 개발 프로젝트는 `references/test-map.md`에 따라 단위·공통·미분류와 전체 검사 범위를 분석하고 구성·문서 초안을 제안한다.
6. **(최신화) 변경 맥락**: `pace memory status --project`, 이력(`.pace/memory/history.md`), `git log`로 마지막 문서 갱신 뒤 바뀐 것.

팀 설치·변경 여부는 이 스킬에서 판단하지 않는다. 팀 설계는 초기화를 마친 뒤 사용자가 [pace-team](../pace-team/SKILL.md)으로 진행한다(§5 마무리 안내).

코드 영역이 2개 이상이거나 빌드 모듈이 10개 이상이면, 도구에 서브에이전트가 있을 때 영역별로 나눠 분석하고 결과를 종합한다. 없으면 직접 순서대로 한다.

## 2. 인터뷰

시작할 때 "질문 N개를 하나씩 드리겠습니다"라고 알린다. 앞 답을 다음 질문에 반영한다.

**신규 (6문)**

| # | 질문 | 형식 |
|---|---|---|
| Q1 | 이 프로젝트는 무엇을 하려는 건가요? | 자유 서술 |
| Q2 | 어떤 유형인가요? 개발 / 일반(기획·문서·운영) / 혼합 — Q1을 보고 추천 표시 | 객관식 |
| Q3 | 지금 어느 단계인가요? 이제 시작 / 진행 중 / 기존 프로젝트 합류 | 객관식 |
| Q4 | (개발·혼합) 구성 요소와 스택 — 예: `web/` Next.js · `api/` FastAPI / (일반) 만들 산출물과 읽는 사람 | 객관식 복수 + 직접 |
| Q5 | 꼭 지킬 것·하지 말 것이 있나요? 예: 특정 라이브러리만 / 보안·규제 / main 직접 커밋 금지 / 없음 | 객관식 복수 + 직접 |
| Q6 | 작업은 어떻게 관리할까요? 백로그(기획) + 프로젝트(실행) / 프로젝트만 / 나중에 — 프로젝트는 `pace project`(`projects/P###`, worktree·게이트). 백로그를 고르면 첫 백로그 주제도. 브랜치 방식(프로젝트마다 worktree / main 직접)도 함께 확인 | 객관식 |

**기존 (4문)** — 분석 요약(구성 요소·스택·감지한 명령·기존 문서)을 먼저 보여 준다.
Q1 목적 → Q2 분석 결과가 맞나요? (고칠 곳) → Q3 꼭 지킬 것·하지 말 것 → Q4 작업 관리 방식(신규 Q6과 같음)

**최신화**: 묻지 않고 §4로 간다. 대규모 변화일 때만 §4-4에서 방향을 묻는다.

## 3. 작성 (신규·기존)

`references/project-docs.md`의 형식으로, 아래 순서대로 각각 초안 → 검토 → 확정한다.

1. `docs/README.md` — 인터뷰 답과 분석 결과로. 환경 표의 명령에는 확인 여부를 표시한다. 하네스 라벨(`검사`·`보안 검사`·`worktree 준비`·`의존성 감사`)은 이름을 바꾸지 않는다. Node 저장소의 `worktree 준비`는 `npm ci --no-audit --no-fund`를 기본으로 제안하고 `의존성 감사`는 `npm audit --omit=dev`를 제안한다.
   정의서는 지도로 쓴다 — `references/project-docs.md`의 "정의서 크기와 분리 기준"을 따른다. 초안을 측정하고(`references/analysis.md` "정의서 측정"), 기준을 넘는 상세는 서브 문서로 분리해 문서 표에 등록한다. 확정은 4의 문서 등록까지 마친 최종 초안을 측정한 뒤다.
   이미 `docs/README.md`가 있으면(문서 목차 등) 덮어쓰지 않고, 정의서 절을 그 안에 합칠지 / 기존 내용을 다른 이름으로 옮길지 묻는다. 루트 `README.md`는 사용자용으로 두고 정의서로 쓰지 않는다.
2. `AGENTS.md` — 60줄 이내. 확인된 필수 명령, 굳은 규칙(Q5), 길 안내. 이미 있으면 기존 내용을 보존하고 빠진 절만 제안한다. `CLAUDE.md`가 없으면 `@AGENTS.md` 한 줄로 만들고, 있으면 맨 위에 그 한 줄을 넣는다.
3. 검사 구성 — `references/test-map.md`의 근거·미분류·실행 확인을 담은 `.pace/test-map.json` 초안을 사용자에게 보여 승인된 내용만 작성한다.
4. 유형별 문서 — `references/project-docs.md`의 "유형별 선택 문서" 조건에 맞는 것만. 작성 뒤 `references/analysis.md`의 1:1 대조를 한다. 각 문서를 정의서 문서 표에 등록한다(용도·적용 범위·참조 시점은 기본값을 제안하고 확인). 1에서 분리한 서브 문서도 같은 표에 등록한다. 등록을 마친 정의서를 다시 측정해 "정의서 크기와 분리 기준" 안일 때 정의서를 확정한다 — 넘으면 1로 돌아가 분리한다.
5. 프로젝트 메모리:
   - `pace memory status --project --body "<단계 · 다음 할 일 · 막힌 것>"`
   - Q5 중 아직 굳지 않은 규칙은 `--type rule --project` (굳은 규칙은 AGENTS.md에만)
   - 분석 중 발견한 문제는 `--type issue --project`(근거 포함), 바로 할 일은 `--type todo --project`
6. 백로그 (Q6에서 골랐을 때) — `references/backlog-format.md`대로 `pace backlog new`·`brief`로 BL 폴더의 BACKLOG.md와 첫 BR 브리프(영어 brief)까지 만든다. 백로그 → 프로젝트, 브리프 → 같은 번호 태스크이며 완료 백로그에는 덧붙이지 않는다. 진행 상황(`status`)이 그 백로그를 가리키게 한다. 단, 새 폴더에서 `pace backlog init`이 Git 저장소를 만들었더라도 첫 commit 전(unborn HEAD)에는 `new`·`brief`를 실행할 수 없고, 기존 하네스의 main 체크아웃 조건도 충족해야 한다. 사용자가 저장소 첫 commit과 main 조건을 갖추기 전에는 이 명령들을 실행했다고 보고하지 않는다.
   프로젝트 (Q6에서 골랐을 때) — `references/project-docs.md`의 `projects/README.md` 형식으로 안내 파일을 만든다(이미 있으면 보존). 프로젝트 폴더는 `pace project new`가 만든다.
7. 브레인 — 항상 `pace brain init`(빈 골격, 비용 없음 — 없으면 나중에 남길 곳이 없어 지식이 흩어진다). 분석·인터뷰에서 코드만 봐서는 이유를 알 수 없는 결정이 나왔으면 `pace-brain` 스킬로 페이지를 남긴다.

## 4. 최신화

**절대 규칙**: 자동으로 덮어쓰지 않는다. 보고하고 승인받은 것만 고친다.

**4-1. 대조** — §1 분석 결과와 현재 문서를 비교해 일치 / 불일치 / 문서에 없음 / 실제에 없음으로 나눈다.

| 대상 | 무엇을 본다 |
|---|---|
| 정의서 | 이름이 `docs/README.md`인지(`docs/PROJECT.md`면 이름 변경 제안 — 링크도), 개요의 단계, 구성 요소 표, 환경 표, 작업 프로세스, 문서 표(미등록 문서·사라진 문서·용도·적용 범위 빈칸·범위 패턴이 실제 경로와 안 맞음), "정의서 크기와 분리 기준" 측정(`references/analysis.md` "정의서 측정" — 크기, 절 한도, 구성 요소 비고 칸, 미등록 최상위 코드 폴더, 미등록 문서, 서브 문서 크기) |
| 환경 | 명령을 다시 감지하고 다시 실행해 확인. 사라진·바뀐 명령, 새 구성 요소, 포트·환경변수 변화. 하네스 라벨 `검사`·`보안 검사`·`worktree 준비`(·선택 `의존성 감사`)가 선언됐는지와 실행 결과(없으면 finish가 경고만 낸다) |
| AGENTS.md | 명령·규칙이 실제와 맞는지, 60줄 초과, 정의서와 중복, 정의서 링크 |
| 유형별 문서 | 구조·방법 서술을 코드와 1:1 대조 (`references/analysis.md`) |
| 일반 프로젝트 문서 | 상호 참조 유효성, 용어 일관성, 정보 충돌, 날짜·단계 정합성 |

검사 구성도 `references/test-map.md`에 따라 파일·명령·누락 후보와 대조해 변경을 제안한다. 사용자 승인 전 기존 파일은 보존한다.

**4-2. 메모리·백로그 점검**

- 진행 상황(`status`)이 git·이력·백로그와 맞는지
- 오래된(⚠) 이슈·할 일 — 근거를 다시 확인해 해결됐으면 닫기 제안
- 프로젝트 `rule` 중 굳은 것 → AGENTS.md 졸업 후보, 15개 초과면 정리 제안
- 백로그 BACKLOG.md 진행 현황 표와 BR 브리프 파일의 상태가 어긋나는지
- 정의서가 프로젝트 방식인데 `projects/README.md`가 없는지 (없으면 만들자고 제안)
- 브레인: `pace brain lint` — 오류는 고치고, 경고(고아·빠진 링크·근거 없음·summary 없음)는 보고에 포함. `pace brain ingest-scan`으로 아직 담지 않은 문서 확인

**4-3. 브레인과 새 문서** — 브레인이 없으면 `pace brain init`을 제안하고, 백로그 결정 표·대화에만 있는 결정의 이유·실측 결과·함정을 브레인 페이지 후보로 올린다. 새 문서는 "문서에 없음"이 기존 문서에 자연스럽게 들어가지 않거나, `references/project-docs.md`의 선택 문서 조건을 새로 만족하면 후보로 올린다.

**4-4. 변화 수준**

| 수준 | 조건 | 진행 |
|---|---|---|
| 경미 | 기존 문서 갱신만, 새 문서 후보 없음, 반영 예정본(제안을 모두 반영한 정의서)을 측정해도 기준 안 | 요약 보고 후 4-5 |
| 대규모 | 새 문서 후보, 정의서가 "정의서 크기와 분리 기준"을 넘음(분리 필요), 문서 범위 밖 도메인·스택, 디렉터리 구조 대폭 변경, 사용자 요청 중 하나 | 요약 보고 + 방향 질문: 전체 반영 / 핵심만 / 특정 문서만 / 직접 입력 — 확정 전 진행 금지. 정의서 분리는 측정값과 구체적 분리 제안(옮길 절·칸과 서브 문서 이름)을 함께 보이고, 승인되면 원문 그대로 옮겨 분리·문서 표 등록 → 다시 측정해 기준 안인지와 하네스 선언 보존을 확인한다 |

**4-5. § 단위 보고와 반영** — 파일별로 절(§) 단위 변경을 보여 주고 절마다 승인·거부를 받는다. 승인된 절만 고친다. 정의서 분리는 원문 이동·대상 서브 문서·문서 표 행·링크 갱신 네 가지를 한 단위로 보이고 함께 승인·반영한다 — 이 중 일부만 승인할 수 없다(원문만 덜어내고 대상 문서·등록·링크를 빼면 상세가 사라진다). 반영한 뒤 실제 반영본을 다시 측정해 대조한다 — 기준을 넘거나 한 단위가 갈렸으면 승인 범위와 관계없이 확정하지 않고 남은 초과와 분리 제안을 다시 보고한다. 사용자가 분리를 끝내 거부하면 그 원문은 정의서에 그대로 두고, 남은 초과를 측정값과 함께 프로젝트 메모리 `issue`로 남긴 뒤 승인된 다른 절만 마무리한다.

```
■ docs/README.md (정의서 측정: 40,703B · 구성 요소 8,730자 · 비고 한도 초과 10행 · 미등록 src/dashboard/)
  § 환경: `npm test` → `npm run check` (실행 확인됨)
  § 구성 요소: batch/ 추가 (근거: batch/package.json)
```

## 5. 마무리

신규·기존·최신화 모두 현재 워크스페이스의 역할 정의와 등록 상태를 확인한다. `pace workspace list`에 현재 경로가 없으면 `pace workspace register <현재 경로>`로 유효한 `.pace/AGENT.md`를 생성하거나 기존 정의의 ID를 연결한다. 무효 정의는 원문을 보존해 오류를 보고한다. 등록 실패는 성공으로 취급하지 않는다.

완료할 때 작업 폴더에서 `pace backlog init`을 실행한다. 공용 화면 정본은 PACE 설치본의 `src/dashboard/backlog/`이며 프로젝트에는 진입 HTML·`backlogs/dashboard/data.js`·`backlogs/dashboard/.gitignore`와 Git 밖 `backlogs/dashboard/local.js`만 둔다. 진입 HTML에는 PC 경로가 없고, 설치본의 공용 JS/CSS file URL은 이 PC 전용 local.js에만 있다. 설치 위치나 PC가 바뀌면 init·refresh가 local.js만 다시 쓰고, 수정되지 않은 예전(v1, file URL 포함) 진입점은 init이 새 형식으로 바꾼다. 추가 사용자 파일은 보존한다. 사용자 편집·판별할 수 없는 화면은 원문을 보존하며 전환하지 않았음을 보고한다. 조회하는 PC에는 PACE가 설치돼 있어야 한다. 다른 PC·clone에서 local.js가 없으면 화면이 init 안내를 보이므로 `pace backlog init`(또는 refresh)으로 이 PC를 연결한다 — 커밋할 변경은 생기지 않는다. 전환 후 HTML 수정·기존 복사본 삭제 등 변경 목록을 보고하고 사용자 커밋 뒤 프로젝트 하네스를 진행한다. 자동 add/commit 또는 stray 보호 우회는 하지 않는다. 현재 경로부터 상위로 Git 저장소를 조회해 기존 저장소 루트·인덱스·`.gitignore`·`.git/info/exclude` 정책을 유지한다. 저장소가 없는 경우에만 현재 폴더에서 `git init`한 뒤 같은 Git 수집기를 사용한다. 이 경우 dashboard 생성·갱신·조회는 첫 commit 전에도 가능하다. 다만 `pace backlog new/brief`와 프로젝트 하네스는 첫 commit이 있고 main 체크아웃 조건을 충족한 저장소에서만 실행한다. opi가 만든 새 저장소가 그 선행조건을 충족하지 않으면 dashboard를 생성하고 조회 가능한 상태로 마친 뒤, 하네스를 실행하지 않은 이유와 사용자가 첫 commit/main 조건을 갖춰야 함을 보고한다. 자동 add·commit·remote·push나 자동 브랜치 변경은 하지 않으며, 해당 조건이 갖춰졌다고 추정해 하네스 성공을 주장하지 않는다. Git 미설치·손상 `.git`·조회/권한 오류는 저장소 없음으로 오인하지 않고 실패시킨다. 새 저장소는 HOME 또는 파일시스템 루트 자체에서 만들지 않는다. 초기화 후 대시보드 생성이 실패하면 새 `.git`은 보존되며 실제 저장소 경로와 `pace backlog init` 재시도 안내를 확인한다. 성공 출력의 절대 대시보드 경로를 사용한다. 숨김·민감 이름·심볼릭 링크를 제외하고 기존 크기 제한을 적용한다. 읽을 수 없는 자료 경로가 있으면 기존 snapshot을 유지하고 원인과 실패를 보고한다.

`pace backlog refresh`는 기존 완성 대시보드만 갱신한다. 대시보드가 전혀 없으면 생성하지 않고 `pace backlog init` 안내와 함께 건너뛴다. 부분 설치는 기존 파일을 보존하고 init 복구 안내 오류로 끝낸다. `pace backlog init`의 부분 복구·전환은 남은 UI가 수정하지 않은 공용 진입점이고 snapshot이 유효한 경우에만 허용한다. 다르면 자료를 보존하고 충돌 오류·수동 확인 경로를 안내한다. `pace backlog new/brief`는 Git 전용 명령이다. 최초 생성은 opi 요청에 포함되므로 별도 생성 승인을 반복하지 않는다.

1. 만든·고친 파일, 확인하지 못한 것(추측으로 채운 곳, 실행 확인 못 한 명령)을 보고한다.
2. 진행 상황을 갱신한다: `pace memory status --project --body "프로젝트 정의(또는 최신화) 완료 — 다음: …"` — §4-5에서 정의서 분리가 거부·미확정이면 "완료"로 적지 않고 정의서 미확정과 남긴 `issue`를 함께 적는다
3. 커밋은 사용자 확인 뒤에 한다.
4. 팀 설계를 안내한다 — 팀 원본(`.pace/team/agents/` 또는 옛 경로 `.pace/team/<이름>.md`)이 없으면 "에이전트 팀 설계는 pace-team으로 진행할 수 있습니다", 있으면 "pace-team으로 팀을 점검·갱신할 수 있습니다"를 한 줄로 알린다. 직접 실행하지 않는다.
5. 사용자의 원래 요청이 있었으면 바로 이어서 한다(개발이면 백로그의 첫 단계, 문서면 그 문서 작성). 셋업만 요청했으면 무엇을 할지 묻는다.

백로그·프로젝트 원본 문서를 직접 편집했다면 커밋 전에 해당 폴더에서 `pace backlog refresh`를 실행한다. 완성 대시보드가 없는 폴더는 최초 생성하지 않고 `pace backlog init` 안내 후 건너뛴다. 부분 설치는 파일을 보존하고 init 복구 안내 오류로 알린다.
