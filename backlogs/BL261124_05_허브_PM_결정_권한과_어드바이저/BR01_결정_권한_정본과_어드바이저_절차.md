## 목적

허브·워크트리 PM이 같은 기준으로 "누가 결정하는가"를 판정하고, blocking을 owner에게 넘기지 않고 함께 풀게 한다([백로그 목표](BACKLOG.md#목표)).

## 범위

- **정본 새 문서** `skills/pace-project-dev/references/decision-rights.md`:
  - **A. 사용자 전용 닫힌 목록** — 모델이 예/아니오로 답할 질문으로 쓴다. 하나라도 "예"면 owner 결정, 모두 "아니오"면 PM 결정.
    1. 합의 변경: 조치가 합의된 목적·목표·범위·완료 기준(`P-n`)을 실질적으로 줄이거나 바꾸는가 — 문장을 고치지 않아도 필수 태스크 보류·기준 미달 마감·결과 축소면 "예"(검증 강화는 아니오). 영향이 불분명하면 PM이 먼저 합의 문서(PROJECT.md·브리프)와 조치의 실제 결과를 대조해 확인하고, 그동안 그 조치만 보류하고 독립 작업은 계속한다. 확인 결과 영향이 있거나, 확인해도 영향 여부를 가릴 수 없을 때만 결정 요청을 올린다.
    2. 되돌릴 수 없음·밖으로 나감: 이 worktree의 git으로 되돌릴 수 없거나 밖으로 나가는가(푸시·병합·배포·외부 전송·결제·저장소 밖 데이터 삭제) — 단, owner가 이미 승인한 범위의 같은 행위(승인 원문이 대상·범위를 특정)는 다시 묻지 않는다("아니오"). **AGENTS.md·저장소 규칙이 이미 위임한 행위(main 작은 일 직접 커밋, main에서 설치 `scripts/install.sh` 재실행)도 "아니오"**다(owner 결정 S1, 2026-11-25) — 작은 도구 수정은 허브가 main에서 고치고 커밋하며 필요하면 재설치하고, owner에게는 사후 요약만 한다(A-4의 기존 위임 예외와 같은 꼴). 이 예외 밖의 위 행위들은 **승인은 owner**, **실행은 허브 PM(main)**이다 — 워크트리는 `workerSpec`의 금지(푸시·배포·삭제·외부 전송 안 함)를 그대로 유지하고, 필요하면 허브에 요청한다.
    3. 안전 기준 완화: 보안 검사·필수 테스트·독립 검토를 생략하거나 약하게 하는가. **다른 제공자(반대 회사 AI)를 호출할 수 없을 때 같은 제공자 새 세션으로 폴백하는 것은 "아니오"(PM)**, 검토 자체를 생략하는 것은 "예"다(owner 결정 B1, 2026-11-25) — TASK 검토·백로그 검토 모두에 적용하고, PM이 진행하며 미실행 사유와 `cross: false`(교차 아님)를 기록한다. BL261124_04의 예산 소진 뒤 PM 위험 수용(증거가 있고 영향이 작은 잔여 지적만)이 이 항목에 걸리는지의 경계는 설계에서 BL04와 함께 확정한다 — 증거 `미확인` 상태의 수용은 "예"(BL04 BR01과 같은 뜻).     4. 사용자 자산: 새 권한·새 계정 사용·비밀 노출·사용자 데이터 외부 공개·새 유료 비용이 생기는가 — 기존 위임 범위 안의 정상 사용(이미 쓰는 권한으로 내부 자료 읽기 등)은 "아니오".
    5. 사람만 가능: 실기 확인·사람 확인 이미지, 또는 **아직 받지 않은 새** 사람 승인이 필요한가 — 이미 받은 승인 원문의 확인은 아래 실행 전 확인에서 처리하며 이 항목에 걸리지 않는다.
  - **두 층 규칙**: 위 목록은 **결정 주체**를 고른다. 이와 별도로 **실행 전 승인 확인**을 둔다 — `merge --yes`, waiver `by: user`, review-note `--by user`, 푸시·배포 같은 사람 승인 게이트 입력 전에 입력자는 그 대상(프로젝트·커밋·해시)을 특정하는 owner 승인 원문의 위치를 확인하고 기록에 연결한다. 확인 주체는 게이트를 입력하는 쪽이다 — 허브(푸시·`merge --yes`)와 워크트리 PM(waiver·review-note `--by user` 입력자, `reviewer.md:93`). 원문이 없거나 대상이 다르면 입력하지 않는다(사람 인증 채널은 범위 밖). 승인 원문은 새 장치를 만들지 않고 P009 T09의 **소통 원장**을 쓴다 — 결정·승인 요청은 `decision_request`(to: owner), owner 답은 `decision_reply`(제안 해시에 묶임). `approved`는 레코드 종류가 아니라 위임(`delegate`)의 basis다(`docs/HANDOFF.md:44-50`) — owner 승인에 근거해 작업을 위임할 때만 쓴다. 허브 자체 실행(푸시·`merge --yes`)의 근거는 `decision_reply` ID·지문을 `pace project log --ref` 영수증에 연결한다(`docs/HANDOFF.md:98`). 원장은 프로젝트별 선택 사항이므로(`coordinator.md:84` "프로젝트가 … 원장을 쓰면") 원장을 쓰지 않는 프로젝트는 Orca 안팎과 무관하게 프로젝트 내부 근거 파일로 대신하고 그 차이를 정본에 적는다. 프로젝트 밖 승인(main 작은 일 등)의 기록 위치는 설계에서 정한다.
  - "판단이 서지 않음"은 올림 사유가 아니다 — 조사하고, 남은 불확실성이 되돌릴 수 있는 선택이면 추천안으로 진행하고 기록한다.
  - **B. blocking 어드바이저 절차(허브)**: 증거 원문 열람·재현 → 원인 층 판별(도구·하네스 결함은 main에서 수정, 환경은 허브가 조사, 설계는 허브가 대안 비교 뒤 결정) → 작업자에게 **질문이 아니라 결정과 근거**를 돌려준다. 기존 owner 범주였던 "계획·산출물의 심각한 오류"(`reviewer.md:79,81,87`)와 "승인된 설계와 다른 방향"(`SKILL.md:85`, `coordinator.md:42`)은 B(허브 결정)로 옮긴다 — 조치가 A에 걸릴 때만 owner다. **공동 시도 1회** = 허브의 결정 회신 → 워크트리 적용 → 재검증 한 주기. 공동 시도는 2회 상한 — 이 값은 검토 재검토 실측에서 유추한 **초기값(가정)**이다: 브레인 실측(`.pace/brain/pages/concept/검토-반복-실패-하네스.md` 실측 절)에서 범위를 지정한 재검토는 blocking이 3→1→1로 줄었다. 첫 재검토에서 크게 줄고 두 번째에서는 줄지 않았으며 0에 닿지 않았다 — 2회면 줄어드는지 멈췄는지가 드러나므로 2회 뒤에는 같은 방식을 되풀이하지 않고 차선으로 전환한다. BL261124_04 예산과 숫자는 같지만 단위가 다르다(BL04는 검토 회차, 여기는 공동 시도) — 설계에서 BL04와 관계를 맞춘다. 그 뒤에는 되돌릴 수 있는 차선(태스크 보류·이슈로 남기고 진행)을 고르되 그 차선이 A에 걸릴 때만 올린다. 보류한 태스크는 원인이 풀렸다는 증거(도구 수정·환경 복구·결정)가 생기면 재개하고, 남은 독립 태스크는 보류와 무관하게 계속한다. 도구·하네스 결함의 main 수정은 기존 절차(coordinator 반복 지적 절, AGENTS의 작은 일 main 직접 커밋·설치는 main)와 A-2의 위임 예외(S1)를 따른다. 병합 대기 프로젝트가 있으면 main 커밋을 미루는 `SKILL.md:71`(병합 대기 중 main 커밋 금지, eval S4 `scenarios.md:19`)과 이 main 수정의 관계 — 수정을 병합 뒤로 미룰지, 해당 프로젝트 finish를 다시 돌릴지 — 는 설계에서 확정한다. 고위험 설계 결정은 다른 제공자의 두 번째 의견을 받을 수 있다. BL261125_01(문제 해결 전문가 에이전트) BR02가 이 절차의 "재현·원인 판별"을 그 에이전트 호출로 바꿀 예정이다(허브는 결정자로 남는다).
  - **C. owner 보고 3종**: 결정 요청(A 항목 번호·선택지·추천과 이유), 승인 요청(병합·배포·푸시), 사후 요약(PM이 대신 정한 것 한 줄씩, 다음 대화에 묶어서). 상황만 전하는 "막혔다" 보고는 하지 않는다. 소통 원장 레코드와 대응시킨다 — 결정 요청·승인 요청은 `decision_request`(to: owner), owner 답은 `decision_reply`(`docs/HANDOFF.md:33-34`). 허브 자체 실행은 그 `decision_reply` ID·지문을 `pace project log --ref` 영수증에 연결하고, 승인에 근거한 위임만 `delegate`의 basis `approved`를 쓴다. 사후 요약은 승인을 구하지 않으므로 승인 레코드를 만들지 않는다 — 후보로 `status` 레코드(상태 안내, 실행 승인 근거 아님, `docs/HANDOFF.md:39`)를 설계에서 검토한다.
