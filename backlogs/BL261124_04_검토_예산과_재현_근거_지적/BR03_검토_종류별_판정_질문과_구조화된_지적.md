## 목적

검토 종류마다 판정 질문을 하나로 고정한다. 판정은 검토자가 쓴 마지막 단어가 아니라 도구가 구조화된 지적에서 계산한다. 그래서 질문 밖 지적(사전 검토·백로그 검토의 구현·설계 방식 지적)은 도구가 note로 낮추고 관문을 막지 못한다([백로그 목표](BACKLOG.md#목표) 고른 길 3, owner 결정 Q1(a)·Q2(a)).

## 범위

- **종류 식별**: verify가 검토 종류를 안다. 지금은 `goal|task` 둘뿐이다(`src/agent/verify-cli.ts:130-131`). 백로그 검토는 BR01이 정한 식별 방식을 쓴다. 구현 후 reviewer 검토도 구별한다. tester는 verify를 거치지 않으므로(`skills/pace-project-dev/references/tester.md`) 문서 기준으로만 둔다.
- **판정 질문(종류별 하나)**: `src/agent/verify.ts:71-72`의 공통 "묻는 것"(목표·다른 길·빠진 것·추적)을 종류별 판정 질문으로 바꾼다.
  - 백로그 검토: "이 백로그로 프로젝트에 착수하면 owner에게 다시 묻지 않고 합의한 목표까지 갈 수 있는가?" 하위 확인은 목표가 상위 목적·owner 원문에 맞는가 / 완료 기준이 판정 가능한가 / 순서·선행·다른 백로그와 충돌이 없는가 / owner 결정이 남아 있지 않은가다(하위 확인은 허브 전달).
  - 구현 전 TASK 검토: "이 계획이 목적을 증명할 수 있는가?" 기준이 관찰 가능한가, 테스트가 결함에서 실패하는가, 범위가 목적을 덮는가를 본다. P008 증명 범위 규칙(`verify.ts:74-79`)은 이 질문의 하위로 유지한다.
  - 구현 후 reviewer: "이 변경을 내보내도 되는가?" 기준 충족, 재현 근거 있는 결함·회귀·보안 없음을 본다(질문 문장은 허브 전달).
  - tester(문서만, `tester.md`): "기준마다 증거로 통과하는가?"(허브 전달)
  - 기존 `goal` 1단계 목표 대조(백로그·태스크 밖 산출물)는 지금 질문을 유지할지 설계에서 정한다.
- **구조화된 지적**: verify가 지적을 정해진 형식으로 받는다. 형식은 등급, 판정 질문(하위 확인)과의 연결, 위치(`파일:줄`), 실패 시나리오, 재현 수단, 확신도다. 형식은 JSON 블록 등 설계에서 정한다. 도구가 형식을 검사하고 판정(pass/fail)을 계산한다. 검토자가 쓴 마지막 줄 판정(`src/agent/review-log.ts:76-81`)과 다르면 도구 계산이 이기고, 차이를 기록한다. 형식을 아예 못 읽으면 지금처럼 `unknown`으로 둔다.
- **도구 강등**: (1) 판정 질문에 연결되지 않은 blocking은 note로 낮춘다. 사전 검토의 구현 방식 지적은 "구현 후 검토로 넘김" 표지를 붙인다. 백로그 검토의 설계·구현 방식 지적은 "프로젝트 설계로 넘김" 표지를 붙인다. (2) 위치·시나리오·재현 중 하나라도 없는 blocking은 should_fix로 낮춘다. 보안·데이터 손실·되돌리기 어려운 행동의 예외는 BR04가 정한다. 강등은 원장 기록에 원래 등급과 사유로 남긴다.
- **등급 이름 정합**: verify의 `note`(`verify.ts:73`)와 reviewer 정본의 `handoff`(`reviewer.md:46`)를 하나로 맞춘다.
- **문서**: `reviewer.md` 관점·지적 등급(`:31-49`), `tester.md` 판정 절(`:12`), `cross-verify.md:9` 지적 등급, `docs/AGENT-CALL.md:12`를 새 질문과 형식에 맞춘다. 팀 원본(`.pace/team/agents/pace-reviewer.md`·`pace-tester.md`)에 어긋나는 문장이 있으면 pace-team 갱신 절차로 맞춘다.
- **문구 고정 시험**: `test/agent-verify.test.ts:34`(네 질문)·`:39-47`·`:119-120`은 의도적으로 갱신한다. 종류별 질문이 각 종류 프롬프트에만 나오는 시험으로 바꾼다. `test/project-dev-skill.test.ts:96-115`의 옛 올림 문구 금지(`verify.ts` 포함)는 지킨다.
- **민감 경로**: 없음.
- 제외: 영향 문턱·증거 상태(BR04), 허가 범위(BR05), 예산(BR01).

## 완료 기준

시험으로 확인한다.

- 종류별 프롬프트에 그 종류의 판정 질문만 있고 다른 종류의 질문은 없다(백로그·사전 검토·구현 후 각각).
- 가짜 실행기 응답으로 확인한다.
  - 사전 검토에서 질문에 연결되지 않은 구현 방식 blocking 1건만 있으면 → 판정 pass, 그 지적은 note와 "구현 후 검토로 넘김" 표지로 기록된다.
  - 백로그 검토에서 설계 방식 blocking만 있으면 → pass, note와 "프로젝트 설계로 넘김" 표지로 기록된다.
  - 위치·시나리오·재현을 갖추고 질문에 연결된 blocking → fail.
  - 위치가 없는 blocking → should_fix, 강등 사유가 기록된다.
  - 마지막 줄은 fail인데 구조화된 지적에 유효 blocking이 없으면 → 도구 계산 pass, 차이가 기록된다.
  - 위 항목 중 "질문과 연결된 blocking → fail"은 회귀 방지(지금도 fail)이고, 나머지는 지금 코드(마지막 줄 판정)에서 실패한다.
- 실제 다른 제공자 verify 1회 이상으로 새 형식 응답을 받아 원문을 증거로 남긴다(fixture와 구별). 형식을 따르지 않은 응답이 오면 그 사실과 도구 처리 결과를 증거로 남긴다.
- `npm run check`가 통과한다.
