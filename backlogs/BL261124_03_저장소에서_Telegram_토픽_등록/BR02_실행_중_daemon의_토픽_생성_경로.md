# BR02 실행 중 daemon의 토픽 생성 경로

- 상태: 대기
- 백로그: [BL261124_03_저장소에서_Telegram_토픽_등록](BACKLOG.md)

<!-- 개발 업무의 예시. 형식·추적 정본: pace-project-dev의 references/document-shape.md. -->

## 목적

BR01로 추가한 워크스페이스를 재기동 없이 실행 중 daemon에 반영하고 Telegram 토픽까지 만들어 결속한다([백로그 목표](BACKLOG.md#목표)). 브라우저의 `/new`가 하던 일을 저장소 안에서 끝낸다.

## 범위

- **Gateway 명령 `workspace_add`**: 로컬 Gateway(127.0.0.1, 토큰 소지자 = 기기 관리자)에 새 요청을 더한다.
  - `/new`와 같은 단계를 재사용한다 — 경로 검증(realpath·dev·ino) → 설정 기록(멱등) → 코어 등록 → 토픽 의도 → `createForumTopic` → 결속 표 기록.
  - 토픽 생성 결과가 불명확하면(재시도 가능 오류·저장 실패) 지금 `/new`처럼 "포럼에서 확인하고 그 토픽에서 `/bind <이름>`"을 안내한다.
  - 같은 이름의 토픽이 이미 결속돼 있으면 새로 만들지 않는다.
- **CLI 연결**: `pace daemon workspace add`는 daemon이 실행 중이면 설정을 직접 쓰지 않는다. Gateway `workspace_add`(등록 ID·경로)를 부르고, daemon이 BR01 대조(활성·등록 ID·경로) → 직렬 설정 기록 → 코어 등록 → 토픽을 한 흐름으로 처리한다. 응답을 잃은 재요청은 멱등이다(같은 등록 ID는 토픽을 하나만 만든다). 결과로 토픽 이름과 결속 여부를 출력한다. 토픽 ID·chat ID는 출력하지 않는다.
- **기존 `/new <이름> <절대경로>`의 권한(설계 질문 — 캡틴 결정 필요)**: 허용된 Telegram 사용자가 지금은 임의의 로컬 경로를 원격으로 추가할 수 있다. 이 경로에도 "등록부 활성 항목만" 규칙을 적용할지, 그대로 둘지를 프로젝트 설계 때 캡틴에게 묻는다(권고: 등록부 활성 항목만 허용).
- **Telegram 쪽 편의**: General `/new <이름>`에서 경로를 생략하면 **daemon 설정에 이미 있는**(BR01로 추가한) 워크스페이스만 토픽을 만든다. 등록부에만 있는 저장소는 Telegram에서 노출하지 않는다.
- **보안**:
  - Gateway 인증·Origin 거부는 그대로 둔다.
  - 요청 경로는 Gateway가 받은 값을 그대로 믿지 않고 daemon이 다시 검증한다.
  - 토큰·식별자는 로그·응답에 남기지 않는다(redact). Bot API 요청 본문(토픽 이름)·CLI 출력·daemon 로그에 로컬 절대 경로를 싣지 않는다.
  - 이 경로로 생긴 워크스페이스도 접근 기본값은 read-only이고, 쓰기는 작업별 승인 그대로다.
- 제외: 워크스페이스 삭제·토픽 삭제(후속).

## 완료 기준

- 단위·통합 시험(가짜 Telegram API)으로 다음을 확인한다.
  - 실행 중 daemon에 add → 재기동 없이 코어에 반영 + 토픽 생성 + 결속 표 기록, 같은 요청 재시도는 멱등.
  - 토픽 생성 확정 실패 → 의도 정리 + 안내, 결과 불명 → `/bind` 안내 + 의도 유지.
  - 인증 없는 Gateway 요청 → 거부.
  - daemon 꺼짐 → 설정만 기록 + 다음 기동 안내.
  - General `/new <이름>` → 설정에 있는 이름만 생성, 등록부에만 있는 이름은 거부.
- 실사용 1회(캡틴이 요청한 진입점부터): 등록부에 없는 시험 저장소의 **하위 폴더**에서 에이전트에게 원문 요청("이 저장소 Telegram 토픽 등록해줘")을 한다. 다음을 확인한다(캡틴 확인).
  - 에이전트가 최상위 저장소를 고른다.
  - 확인 화면을 거쳐 전역 등록과 daemon 추가가 된다.
  - 토픽이 생기고, 그 저장소에만 둔 표식을 묻는 첫 읽기가 맞게 답한다.
  - 응답·로그에 경로·토큰이 없다.
  - daemon이 꺼져 있거나 Telegram 어댑터를 쓸 수 없을 때는 "설정 반영"과 "토픽 결속" 상태를 각각 보고한다.
  - 끝나면 운영으로 유지할지 캡틴이 정한다.
- 동시성 시험: Gateway `workspace_add`와 Telegram `/new`가 겹쳐도 설정 유실·중복 토픽이 없다. 응답 유실 뒤 재요청도 같다.
