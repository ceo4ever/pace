## 목표

태스크 구현 뒤 검증에서 **tester와 reviewer가 맡는 질문을 시점·목적별로 나눈다**. 지금은 사후 reviewer가 TASK 기준 충족을 다시 판정하다가 실행 증거가 없어 `unknown`이 나오고, 재검토를 반복하며 호출 예산을 쓴다. 이 반복을 줄이면서, 읽기 검토로만 잡히는 설계 결함(교착, 감사 이력 누락, 확정 데이터의 소급 변경, 아무것도 검증하지 않는 시험)은 계속 잡는다.

- **상위 목적**: PACE는 owner가 자리를 비워도 프로젝트가 자율로 끝까지 가고, 품질을 지키면서 검토·검사 반복에 시간과 토큰을 낭비하지 않는다([BL261125_01 목표](../BL261125_01_문제_해결_전문가_에이전트/BACKLOG.md#목표)와 같은 축).
- **owner 원 제안(fin-link P045 경험, 허브 전달)**: 구현 전 계획 검토는 reviewer가 계속 맡는다. 구현 뒤에는 tester가 중심이 되고, reviewer는 보안·권한·DB처럼 위험한 변경에만 붙인다. 화면 문구·배치 재확인에서는 reviewer를 뺀다. 대가로 읽어야만 보이는 결함을 놓칠 수 있다.
- **owner와 확정한 수정안**(2026-11-27 허브 정리, 2026-11-28 owner A-1 "단순화"로 2·3을 갱신 — 확정 순서는 [결정·기록](#결정기록)):
  1. **시점별 질문**
     - 사전 reviewer: 기존 질문("이 계획이 목적을 증명할 수 있는가?")을 유지하고, TASK의 `구현 후 reviewer: 필요 | 생략` 판단이 TASK 내용과 맞는지 판정하는 일을 더한다. `생략`인데 아래 사실 질문에 "예"가 있으면 blocking이다.
     - 사후 tester: 기준마다 실행 증거로 통과하는지 판정한다. 기준 충족의 판정 주체이며 tester.md를 그대로 쓴다.
     - 사후 reviewer: 목적은 **실행 검증의 사각지대를 줄이는 것**이다. 하기로 하지 않은 일을 하는지, 시험이 묻지 않은 곳에 결함이 있는지 본다. TASK 기준 충족은 다시 판정하지 않는다(tester 몫). 계획의 타당성도 판정하지 않는다(사전 검토 몫). 따라서 사후 reviewer에게 TASK 기준별 실행 증거를 요구하지 않는다. 입력은 TASK와 diff이고 목표 대조 1단계는 하지 않는다(Q1).
  2. **위험 묶음 3개** — 사후 reviewer를 부르면 **항상 세 묶음의 모든 점검 항목(12항목)**을 묻는다. 해당하지 않는 항목은 "해당 없음(이유)"로 답한다:
     - **묶음 경계(A)** — 누가 할 수 있나: 권한·인가, 개인정보, 보안에 민감한 동작(비밀, 외부 전송, 셸, 삭제). 질문: 허용되지 않은 주체나 입력이 닿을 수 있는 경로가 생겼는가? 점검: 새 진입점마다 인가를 확인하는 위치 / 거부 기본값 / 원문·비밀이 응답·로그·이력에 새는가 / 외부 입력이 셸·경로·쿼리로 그대로 가는가.
     - **묶음 상태(B)** — 무엇이 남나: 데이터 저장·삭제, 스키마·마이그레이션, 감사 이력, 확정 데이터 정정. 질문: 기준에 적히지 않은 데이터를 바꾸거나, 남겨야 할 기록을 빠뜨리는가? 점검: 쓰기마다 감사 이력 / 과거·확정 데이터의 소급 변경 / 마이그레이션 왕복과 기존 행 / 시험이 저장 뒤 다시 조회해서 단언하는가.
     - **묶음 흐름(C)** — 어떤 순서로 가나: 동시성·잠금·트랜잭션, 실패·복구·재시도, 상태 전이·게이트 판정. 질문: 순서가 어긋나거나 중간에 실패할 때 결과가 깨지는가? 점검: 잠금 순서와 교착 / 트랜잭션 밖 부작용 / 부분 실패의 잔여물과 롤백 / 시험이 덮지 않은 분기 조합.
