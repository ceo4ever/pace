## 목적

반복 실패를 끊을 독립 문제 해결 전문가 `pace-troubleshooter`를 [BR01](BR01_xhigh_등급과_호환_코드.md)의 `xhigh` 등급으로 정의하고, 실제로 그 모델·effort로 불리는지와 해결 능력을 확인한다([백로그 목표](BACKLOG.md#목표), 고른 길 1~3). 이 BR은 팀 원본·생성물·문서·eval만 다루고 `src/**` 코드를 바꾸지 않는다(허브 결정 2026-11-26 17:40 분할). 선행은 BR01 병합이다.

## 범위

- **호출 수단** — **설계 첫 단계에서 실측한다**(착수 전 검토 1 반영(허브 결정 2026-11-26 17:43)): 두 후보 수단((가) native 서브에이전트, (나) `pace agent run` 실행 인자)을 모두 조사한다. 각 수단이 Claude·Codex 양쪽 호스트에서 지정 모델·effort를 실제 런타임 관측(호스트 세션 기록 등)으로 입증할 수 있는지 확인한다. 관측이 안 되는 수단은 그 사유를 증거에 기록하고, 양쪽 호스트에서 입증 가능한 수단을 고른다. 한 후보가 관측 불가여도 다른 후보로 고를 수 있다(착수 전 공동 시도 1 — 허브 결정 2026-11-26 17:46). 도구 응답만으로는 부족하다 — `AgentResult`에는 런타임 effort가 없고 model은 요청값일 수 있다(`src/agent/contract.ts:75-79`). 아래 실제 적용 관문은 고른 수단의 재확인이다. 문제 해결 에이전트를 무엇으로 부를지 정한다. 후보는 (가) 호스트 서브에이전트(native 생성물 `.claude/agents`·`.codex/agents`)와 (나) PACE 도구 경로 `pace agent run --agent claude|codex --model --effort`(`src/cli.ts:158`, 실행 인자로 전달)다. 호출 주체(허브/워크트리 × Claude/Codex)별 제공자와 기본 수단을 표로 정한다. 제약:
  - `pace agent verify`는 구성원·tier를 받지 않는다(`src/cli.ts:164` 사용법).
  - `upper_review`의 근본 검토 기록(`review-note --upper-review --file`)은 근거 JSON에 reviewer(작성자·작업자와 다름), provider, 이전과 다른 context, cross(false면 `cross_unavailable`), analysis를 요구한다. 두 번째 근본 검토는 contract·backlog도 요구한다(`src/agent/review-followup.ts:436-443`, BL261124_04 BR09). 고른 호출 수단은 이 값을 반환·기록에서 얻을 수 있어야 한다.
  - tier 해석은 `project start --role`(`src/team/worker-role.ts:74`)과 native 생성물(`src/team/sync.ts:47`)에서만 일어난다. 체인 경로의 effort 정규화(`src/agent/chain.ts:37-40`, Codex `max`→`xhigh` `:44`)는 `pace agent run --chain` 근거일 뿐이고, native 생성물은 effort를 정규화 없이 그대로 쓴다(`src/team/sync.ts:24-25`). P009 T01에서 Claude native 정의 effort high가 실제 medium으로 관측됐으므로(`docs/TEAM.md:103`, `projects/P009_…/tasks/T01_…/evidence/tester-stage2.json`) Claude `high` 기본값이 바로 그 위험한 값이다 — 아래 실제 적용 관문이 필수다.
  - 고른 수단에 PACE 코드 변경이 필요하면(예: 구성원 이름으로 부르는 새 옵션) 이 BR에서 만들지 않고 새 백로그로 발의한다. 이 BR은 지금 있는 수단 중에서 고른다.
- **호스트가 모델을 거부할 때**: 미배포·계정 권한·데이터 보존 요건(claude-api 스킬: Fable 5.2는 30일 보존이 필요하고 ZDR 조직은 400) 등으로 거부되면 처리 방식을 설계에서 정한다 — 선택지: (가) 차하위 모델로 대체 실행하고 실제 모델을 기록, (나) 호출을 보류하고 호출한 PM에게 거부 사유를 돌려준다. 호출 절차(호출한 PM이 수행)로 정하고 코드는 바꾸지 않는다. 어느 쪽이든 조용히 바꾸지 않고 요청값·실제값을 기록에 남긴다(BR03 병합 전이면 증거 파일). **차하위 모델 실행은 장애 기록일 뿐 최상위 모델 요건의 충족으로 인정하지 않는다** — 그 상태로 요건을 충족으로 보거나 마감하려면 A-1이다.
- **팀 구성원 `pace-troubleshooter`**(역할 종류 reviewer, tier `xhigh`):
  - `pace team new pace-troubleshooter --role reviewer`로 만들고, BR01이 고른 호환 방식에 따라 tier를 `xhigh`로 바꾸거나(재설치 순서 강제) 별도 위치에 등급 승격을 둔다(파일·키 분리). 계약 v1 실행 전 대조 문단과 점검 표지를 보존하고, `pace team sync`로 `.claude/agents`·`.codex/agents`를 생성한다(직접 편집 금지).
  - BL261124_05 BR01(완료, P011)이 팀 원본 전부와 템플릿(`templates/team/member.md:29` 실행 전 대조 보충 문단)에 보충 문단을 넣었으므로, 이 원본은 그 템플릿으로 만든다.
  - **맡는 일**: 호출한 PM이 준 목표·실패 원문을 받아 문제 해결 목표를 달성하는 해결안과 검증 계획을 제시한다.
  - **하지 않는 일**: 작업본 수정·커밋, 결정 대행(결정은 호출한 PM, owner 결정은 BL261124_05 정본), 증거 없이 원인 확정, 실패한 땜질의 연장안. **검토 판정을 내리지 않으며 `pace agent verify`(독립 검토)를 대체하지 않는다** — 역할 종류 reviewer는 작성자 독립성을 위한 분류다.
  - 결정 경로: 해결안은 호출한 PM에게 돌려준다(HANDOFF 수신자 = 호출자).
- **지침 본문(최신 LLM 기준)** — 단계 번호를 나열하지 않고 목표·판단 기준·반환 계약만 준다(최신 모델에 과처방하면 품질이 떨어진다). 담을 판단 기준: 막힌 목표를 먼저 다시 확인하고(목표가 틀렸으면 그것이 답), 요약이 아닌 원문 증거로 재현하고, 여러 원인 후보를 반증으로 좁히고, 원인 층(structure·planning·design·구현)을 판별하고, 부류를 없애는 안을 땜질보다 우선한다.
  - 반환 계약(필수 항목): 막힌 목표, 확인한 증거와 재현 결과, 원인 층과 근거(`파일:행`), 해결안 비교(목표 달성 방식·비용·위험·되돌리기), 추천과 이유, 검증 계획(해결을 증명할 관찰과 실패 시 다음 수), 남은 불확실성. 확인과 추정을 구분한다. **pass·fail 같은 판정 필드는 두지 않는다.**
- **팀 측정·마감 부담**: 조건부로만 부르는 구성원은 호출이 없는 구간마다 미사용 후보(`src/project/team-metrics.ts:358` `unusedRoleCandidates`)가 되고, finish는 그 후보를 회고 `unusedRoles`에 모두 적게 한다(`docs/TEAM-METRICS.md:116`). 이 조건부 역할 미사용 처리는 **BL261125_02 BR02가 소유 — 여기서는 구현하지 않음**. 이 BR은 그 분류 장치(필수 역할 표지 `.pace/team/required-roles.json`, `docs/TEAM-METRICS.md:54`)를 `pace-troubleshooter`에 적용해 호출 없는 구간이 비참여 구분(호출 조건 미발생 / 기록 부족 / 실제 미사용)으로 기록되게 한다. 미사용을 삭제 근거로 쓰지 않는 기존 원칙은 유지한다.
- **필수 역할 요건 등록(BL261125_02 정본 형식)**: `skills/pace-team/references/required-roles.md`의 문제 해결자 자리(`:42`)에 이 BR 소관 요건 행을 요건 ID(`TS-NN`)·요건 문장·근거·선행 장치·요건 버전·구분(고정 요건/기본값(권고))으로 등록한다. 소관 요건: 정의(맡는 일, 결정 경로 — HANDOFF 수신자 = 호출자), 역할 종류(reviewer), 등급(`xhigh`)·모델(Claude `claude-fable-5-2`·Codex `gpt-6.2-astra`)·effort(Claude `high`·Codex `medium`) — owner 결정이므로 고정 요건, 선행 장치는 BR01 —, 지침 본문 판단 기준, 반환 계약, 하지 않는 일(검토 판정 아님·verify 대체 아님 포함), 모델 거부 처리, 실제 적용 관문. eval로 값이 바뀌면(effort 상향 등) 바뀐 값으로 등록하고 요건 버전을 올린다. 그때 BR01 기본값 변경은 별도 코드 변경으로 낸다. 호출 신호 행은 BR02, 호출 절차 행은 BR04, 호출 기록 행은 BR03이 등록한다. ## 완료 기준

- **BR06 소관 요건 ID 대조표**: 위 소관 요건이 `required-roles.md`에 요건 ID로 등록돼 있고, BL261125_02 BR01 점검 장치(`pace-team` 필수 역할 점검)로 `pace-troubleshooter`를 점검한 대조표에서 BR06 소관 요건 ID가 모두 충족이다(등급·모델·effort는 BR01 시험과 아래 관문 증거로, 실제 적용 관문 ID는 관문 증거로 판정). 대조표를 이 태스크 증거로 남긴다. 문제 해결자 전 요건의 최종 대조표는 [백로그 PROJECT-CLOSE 목표 달성 판정](BACKLOG.md#목표)에서 닫는다.
- `pace-troubleshooter` 원본·생성물이 있고, `pace team list`·`pace team sync --check --json`이 차이·오류 없이 통과한다. BL261125_02 BR02의 필수 역할 표지(조건부 호출)가 이 구성원에 적용돼 있다.
- **실제 적용 관문**: 정한 호출 수단으로 Claude·Codex 각각 이 구성원을 실제로 불러 런타임 model·effort가 요청값과 같은지 확인하고 증거를 남긴다(전달과 적용을 구별 — `docs/TEAM.md:155`). **불일치·미확인이면 done하지 않는다** — 대체 경로(다른 호출 수단, 실행 인자 전달 등)로 맞춘 뒤 다시 실측한다. 대체 경로 시도는 **2개까지**다 — 그 뒤에도 불일치·미확인이면 결과를 "미확인"으로 기록하고 BL261124_05 A-1 결정 요청(기준 미달 마감 여부)을 올린다. 모델 거부 시 정한 처리(대체 또는 보류)가 동작하는 것도 확인한다.
- **능력 확인(eval)**: 과거 반복 실패 사례 2건 이상(예: P001 사전 검토 14회, P005 T04)으로 실행한다.
  - 입력: 사례마다 당시 실패 원문이 실제로 남아 있는지 먼저 확인하고, 없으면 다른 사례로 바꾼다. 실행은 해결 이전 커밋 checkout(또는 사후 정답 문서를 뺀 사본)에서 새 맥락으로 한다.
  - 대조군: 같은 입력을 기존 high 등급(같은 지침, 현재 high 매핑)으로도 실행한다.
  - 선택 항목(effort 비교 축): 기본 effort에서 실패한 사례에 한해 한 단계 위 effort(Claude `xhigh`, Codex `high`)로 1회 더 실행해, effort 상향의 이득을 비교하는 근거로 쓴다.
  - 판정: 작성자가 아닌 쪽(독립 리뷰어 또는 다른 제공자)이 반환의 필수 항목 충족과, 원인 층·추천안이 실제 최종 해결(사후 기록)과 같은 층을 가리키는지 판정한다. 통과 문턱(예: 사례의 과반 일치, 대조군 이상)은 실행 전에 고정한다.
  - effort 판단 근거: 사례별 실행 시간·토큰([BR03](BR03_에이전트_호출_기록.md) 형식, 병합 전이면 같은 항목의 증거 파일)을 함께 남겨, 기본 effort를 더 올릴지 판단할 수 있게 한다. 판정 근거와 원응답을 증거로 보존한다. BR06은 BR03을 선행으로 두지 않는다.
