## 목표

검토·테스트가 반복 실패하거나 겉만 고치는 상황에서 허브 PM·워크트리 PM이 **초기에** 부르는 **문제 해결 전문가 에이전트**를 팀에 둔다. 이 에이전트는 작성자와 독립된 새 맥락에서 원인을 판별하고, **문제 해결 목표를 달성하는 해결안과 검증 계획을 제시**한다. Claude·Codex 각각의 최상위 모델로 실행하되 effort는 도구별 기본값(Claude `high`, Codex `medium`)에서 시작하고, 더 올릴지는 실측으로 정한다. 지침은 최신 LLM이 가장 잘 일하는 방식으로 쓴다. 모든 팀 에이전트 호출의 에이전트·모델·effort·실행 시간·사용 토큰을 프로젝트 `log.jsonl`에 남기고(BR03), 이 기록을 팀 모델·effort 최적화 판단의 근거로 삼는다.

- **상위 목적**: PACE는 owner가 자리를 비워도 프로젝트가 자율로 끝까지 가고, 품질을 지키면서 검토·검사 반복에 시간과 토큰을 낭비하지 않는다.
- **현장 문제(owner, 2026-11-25)** — 아래 경우가 너무 자주 나와 검토를 10번 넘게, 리뷰를 20번 하게 된다:
  1. 지속적인 검토 오류
  2. 반복되는 테스트 오류
  3. 경계 근처에서 고쳐도 계속 오류
  4. 구조적인 문제인데 단편적인 접근으로 핵심을 못 보고 겉만 고치는 경우
  5. 기타 오류로 에스컬레이션이 필요한 경우
- **근거(2026-11-25 확인)**:
  - 이 역할의 전담자가 없다. 팀은 lead·implementer·reviewer·tester 4명뿐이다(`.pace/team/agents/` — 팀 적용 `84d686a`는 `.pace/team/`에 두었고 `de32245`가 `agents/`로 옮겼다). 역할 종류도 lead·maker·reviewer·coordinator뿐이다(`src/team/model.ts:5`). 역할 후보표에도 진단·문제 해결 원형이 없다(`skills/pace-team/references/role-archetypes.md`).
  - 검토 반복 fail의 진단은 **작성자 PM 자신**이 하고, 3회 fail 뒤에야 시작한다(`src/agent/review-log.ts:14` `DIAGNOSE_AFTER = 3`, `skills/pace-project-dev/references/reviewer.md` diagnose 절). 같은 맥락의 작성자가 자기 땜질을 진단하므로 문제 4에서 빠져나오기 어렵다.
  - 테스트 반복 실패, 경계 재발, 겉만 고친 수정에는 도구 신호가 없다. 규칙 문장(`SKILL.md` §6 "장애나 같은 실패 3회는 근거와 함께 허브에 보내 B로 해결", reviewer.md "지적별 땜질을 멈추고")뿐이다.
  - 실측: P001 사전 검토 14회(`coordinator.md:23`), P005 T04 9회·11회. 진단 뒤 전체 검토도 새 갈래를 찾아 사용자 결정까지 가는 일이 많았다(브레인 `.pace/brain/pages/concept/검토-반복-실패-하네스.md` 실측 절).
  - 모델·effort는 등급 단위로만 지정된다. 등급은 high·medium·low 셋이다(`src/core/worker-tiers.ts:7`). 새 구성원은 역할 종류로 lead·reviewer는 high, maker·coordinator는 medium을 자동 배정받는다(`src/team/store.ts:92`). 이 저장소 원본의 tier는 lead·reviewer·tester가 high, implementer가 medium이다(`.pace/team/agents/*.md` frontmatter, tester는 역할 종류 reviewer) — 그래서 high 등급 매핑을 올리면 lead·reviewer·tester가 함께 바뀐다.
  - `pace agent` 체인 경로에서 effort `xhigh`는 Claude·Codex 모두 고유값으로 받는다(`src/agent/chain.ts:37-40`). Claude는 `max`도 받고, Codex는 `max`를 `xhigh`로 바꾼다(`:44`). native 생성물은 이 정규화를 거치지 않고 effort를 그대로 쓴다(`src/team/sync.ts:24-25`).
  - Claude Fable 5.2의 API 기본 effort는 high이고, high에서 시작해 xhigh는 이득이 측정된 곳에서만 쓰라고 권한다(claude-api 스킬, 2026-11-03 캐시). Codex 모델의 공식 기본 effort는 미확인이다.
- **고른 길**:
  - (1) 새 팀 구성원 `pace-troubleshooter`(역할 종류 reviewer — 작성자와 독립)를 둔다.
  - (2) 이 구성원 전용 **최상위 등급 `xhigh`**를 추가한다. 기존 high·medium·low 매핑과 다른 구성원은 바꾸지 않는다. 모델은 Claude `claude-fable-5-2`, Codex `gpt-6.2-astra`(owner 지정)이다. effort는 tier 문자열이 아니라 도구별 기본값 Claude `high`, Codex `medium`이다(owner 결정 2026-11-25 — 현재 규칙 `docs/TEAM.md:83`의 예외). 더 올릴지는 BR01 능력 eval의 실측(해결 일치율 대비 시간·토큰)으로 판단한다.
  - (3) 에이전트는 **해결안과 검증 계획까지 제시**하고, 결정은 PM이, 수정은 구현자가 한다(owner 결정 2026-11-25 — 작성자 독립성 유지).
  - (4) 현장 문제 1~5를 도구가 셀 수 있는 신호로 바꾸고, 지금의 3회보다 **이르게** 호출한다. 문턱은 과거 검토 원장에서 재서 정한다(BR02).
  - (5) 팀 에이전트 호출마다 에이전트·모델·effort·실행 시간·토큰을 `log.jsonl`에 기록한다 — 호스트 훅 자동 기록을 기본으로, 훅이 값을 주지 않으면 PM이 `pace project log`로 기록한다(BR03).
- **버린 길**:
  - (1) high 등급을 최상위 모델로 올림 — lead·reviewer·tester까지 비용이 커지고, 전문가를 부를 시점 문제는 그대로 남는다.
  - (2) 호출하는 PM이 매번 `--model`·`--effort` 값을 손으로 지정 — 빠뜨리기 쉽고 의도값을 정의에서 검토할 수 없다(`docs/TEAM.md:97`). 도구가 등급에서 값을 해석해 실행 인자로 넘기는 경로(`pace agent run --model --effort`)는 BR01 호출 수단 후보로 남는다.
  - (3) BL261124_05 B 절차의 원인 판별을 허브 PM이 직접 수행 — 허브는 맥락이 많이 쌓인 코디네이터라 깊은 진단이 무겁고, 작성자 쪽 맥락에 묶인다. 대신 B 절차의 원인 판별 단계를 이 에이전트에 위임하고 결정은 허브에 남긴다.
  - (4) 에이전트가 직접 수정 — 진단자와 수정자가 같아지면 다음 검토의 독립성이 깨진다.
- **관련·순서**:
  - 순서: 이 백로그는 **BL261125_02 병합 뒤 착수**한다(PM 결정 2026-11-25, 순서 고정). 그 뒤 BR01·BR03은 서로 병행할 수 있다. BR02는 BR01 병합과 BL261124_04 BR01 뒤에 착수한다(PM 결정 2026-11-25 — 순서 BL261124_05 → BL261124_04 BR01 → BR02, BR02가 BL04 예산과의 관계를 정하므로 BL04 BR01이 먼저다). BL261124_05 BR01은 P011로 완료돼 B 절차와 팀 원본·템플릿 보충 문단이 이미 있다 — `pace-troubleshooter`는 보충 문단이 들어간 템플릿으로 만들고, BR02가 그 B 절차의 재현·원인 판별 단계를 이 에이전트 호출로 연결한다.   - BL261124_04(검토 예산): 기본 예산(전체 1회 + 범위 재검토 1회)이 "연속 fail 2회"와 겹치므로 호출 뒤 재검증 1회를 예산 안에 둘지 BR02에서 BL04와 맞춘다. BR02 신호 3(같은 영역)은 BL04 BR02의 구조화된 지적(위치)을 선행으로 쓰거나 자체 위치 기록 방식을 정한다.

    5. **공유 형식은 BL261125_02가 정하고 이 백로그가 따른다**: 조건부 역할 미사용 처리(`src/project/team-metrics.ts:291`)와 필수 역할 표지 위치·형식은 BL261125_02 BR02 소유(이 백로그 BR01 제외) — BR01의 `xhigh` 등급 위치는 그 형식을 따르거나 같은 원칙(옛 판독기가 보지 않는 별도 파일·키)으로 정한다. 호출 기록이 채택 판정·팀 집계를 시작시키지 않는 규칙은 BL261125_02 BR02가 정하고 BR03이 따른다. BR03 호출 기록은 BL261125_02 BR03 갱신 모드가 이후 읽는 근거다.
