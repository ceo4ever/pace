## 목적

현장 문제 1~4를 도구가 셀 수 있는 신호로 바꾼다([백로그 목표](BACKLOG.md#목표), 고른 길 4). 예산 단위(태스크·백로그)는 P013 예산의 소진 출력을 신호 1로 읽고, 예산 안 조기 호출은 신호 2~4가 낸다. 예산 밖 일반 산출물만 지금의 diagnose 문턱(3회)보다 **이른** 문턱을 과거 기록으로 정한다(2026-11-26 근거 최신화). 분할 기준은 **신호 생성(BR02) vs 호출 절차(BR04)**다 — 신호를 받아 누가 어떻게 부르고 인계·결정·기록하는지는 [BR04](BR04_호출_절차_연결.md)가 맡는다(허브 결정 2026-11-26 분할).

## 범위

- **도구 호출 신호** — 문턱은 이 브리프에서 확정하지 않고 설계에서 과거 기록으로 정한다:
  1. 검토 오류 — P013 병합으로 축소(2026-11-26):
     - 예산 단위(태스크 단계·**백로그** — BL261124_04 BR01): 단계마다 유효 판정 2회(`src/agent/review-budget.ts:9` `ROUND_LIMIT = 2`)에서 소진된다. 소진 출력(`verify`·`review-hand` 종료 16, `reason: budget_exhausted`, `followup`)이 이미 있다. 이 BR은 새 문턱을 만들지 않고 그 출력을 신호 1로 읽는다. 예산 안 1회 fail에서 부르는 조기 호출은 신호 2~4가 맡는다.
     - 예산 밖 일반 산출물: diagnose 문턱은 지금 3회다(`src/agent/review-log.ts:20` `DIAGNOSE_AFTER`). 이보다 이른 문턱은 과거 원장(`projects/**/REVIEW-LOG.jsonl`)에서 2연속 fail 사례 중 다음 검토에서 pass로 수렴한 비율을 재서 정한다. 대상을 바꾸지 않은 재검토는 거부되므로 "수정 없이 수렴"은 잴 수 없다(`src/agent/verify-cli.ts:109`). 비율이 높으면 2회 단독 문턱은 과잉 호출이므로 결합 조건(예: 같은 영역 재지적 + 연속 fail 2회)도 대안으로 비교한다. verify 출력에 호출 권고 신호를 낸다.
  2. 테스트 오류: 같은 시험(이름 또는 파일)이 문턱만큼 연속 실패한다. 지금은 시험 이름·파일 단위의 실패 기록이 없다 — `src/test-runner/`는 결과를 파일에 쓰지 않고, `log.jsonl`의 `gate` 사건은 check·done·finish의 성공·실패와 사유 분류(command·contract·state)만 남긴다(`src/project/metrics.ts:32-37`). 어떤 실행을 세는지(`npm run check`·`pace test changed`·태스크 check 게이트 중 무엇)와 기록 위치를 정하고, 기록 밖에서 돌린 실행(직접 `node --test` 등)은 세지 않음을 명시하거나 PM 판정 질문으로 보완한다.
  3. 경계 재발: 같은 파일·영역을 고친 뒤 같은 영역에서 다시 지적·실패가 난다. 입력은 BL261124_04 BR03(구조화된 지적, P013 T03 병합 — 충족)의 지적 위치(`location`, `src/agent/structured-review.ts:54`)다. BL04의 같은 지적 판정(`src/agent/review-recovery.ts:67` `sameFinding`)은 지적 ID와 위치 문자열이 모두 같을 때만 참이어서 수정 확인용으로만 쓴다. 조기 신호용 "같은 영역 재발" 비교 기준(예: 같은 파일·같은 기준 ID·근접 위치)은 이 BR 설계에서 정한다(착수 전 검토 1 반영(허브 결정 2026-11-26 17:43)). 시험 실패의 영역은 신호 2의 기록 위치를 쓴다.
  4. 겉만 고침: 도구 대리 지표(같은 파일 연속 수정 + 같은 등급 재지적)로 잡는다. 반환 형식 항목("같은 부류 재발 / 겉만 고침 의심")은 BR05(구조화 검토 스키마)와 BR04(`reviewer.md` 안내)가, PM 판정 질문은 BR04가 맡는다.
- **출력**: 신호 1~4는 verify 출력 또는 프로젝트 기록에 호출 권고(신호 종류·단위·근거 회차)로 낸다. 이 출력을 PM·허브 절차로 잇는 일은 BR04(스킬 문서)와 BR05(`workerSpec` 지시)다.
- **필수 역할 요건 등록(BL261125_02 정본 형식)**: 문제 해결자 **호출 신호** 요건 행(신호 1~4와 문턱)을 `skills/pace-team/references/required-roles.md` 문제 해결자 자리에 요건 ID·근거·선행 장치·요건 버전(새 행은 정본 규칙의 초기 버전)으로 등록하고 이 태스크에서 판정한다.
- **제외**: 호출 주체·절차·PM 연결, 신호 5(B 절차), 반환 형식 항목, `upper_review` 호출 연결, 예산 흐름 eval(BR04), `workerSpec` 지시·검토 반환 스키마(BR05), 등급 코드(BR01), 구성원 정의(BR06), 호출 기록 형식(BR03), 검토 예산·공동 시도 상한·escalation(BL261124_04 BR01·BR02), `upper_review` 단계 판정·차단(BL261124_04 BR09, P013 T09 — 완료). 소진 판정·출력 자체(BL261124_04 BR01 — 완료, 이 BR은 읽기만).

## 완료 기준

- 신호 1~4의 문턱과 근거가 설계 문서에 있다 — 신호 1은 예산 밖 일반 산출물에 대해 과거 원장에서 잰 수렴 비율과 결합 조건 비교 결과를 적는다. 예산 단위는 기존 소진 출력을 읽는다고 적는다.
- 신호 1~3과 신호 4 (나) 도구 대리 지표(같은 파일 연속 수정 + 같은 등급 재지적)가 도구 출력(또는 기록)에 나타나는 것을 시험으로 확인한다. 문턱 직전에서는 나오지 않는 음성 대조와, 기록 밖 시험 실행이 세지지 않는 경우를 포함한다.
- 신호 3 인수 사례: 지적 ID나 줄이 바뀐 같은 영역 재발은 잡고, 같은 파일의 무관한 지적은 잡지 않는 것을 시험으로 확인한다.
- 신호 생성 코드(`src/**`)·시험·설계 문서만 바꾼다. 예외: 필수 역할 정본 `skills/pace-team/references/required-roles.md`의 호출 신호 요건 행 등록. 스킬 절차 문서(BR04)·`workerSpec` 지시(BR05)는 바꾸지 않는다.
- **BR02 소관 요건 ID 대조표**: 호출 신호 요건 ID가 정본에 등록돼 있고, BL261125_02 BR01 점검 장치로 점검한 대조표에서 그 ID가 충족(근거: 위 시험·설계 문서)인 것을 이 태스크 증거로 남긴다.
