# 교차 검증 2단계

- 검토자: codex · openai · gpt-6.1-sol · cross true · read-only

**독립 목표 대조:** 목표는 상위 목적과 대체로 맞습니다. 인터뷰 → 실제 수행·기록 → 플레이북 생성 → 새 세션 자율 실행 → 변경 복구·학습으로 이어지며, 화면·위치·액션·추출과 기존 fin-link 보호도 포함합니다. 이번에 확인한 BR 원문에는 1단계의 주요 우려를 해소하는 구체적인 완료 기준이 있습니다. 다만 운영 명령의 실패 처리와 승인 유지 규칙에는 실행 안전을 좌우하는 빈틈이 남습니다.

**목표 달성: 미확인.** 평가 대상은 대기 상태인 계획서입니다. 목표를 입증할 검증 계획은 상당히 보강됐지만, 실제 생성·주행·복구·호환성 검증 결과는 제공되지 않았습니다. 형식 검사나 테스트 통과 계획을 실제 달성으로 대신하지 않습니다.

**검토 범위·독립성:** 이번에는 사용자 메시지에 합쳐 제공된 BACKLOG와 BR01~BR06 전체, 상위 목적, 1단계 첫 판단 원문, 작성자의 반영 주장에 노출됐습니다. 지정된 `stage2-target.md`를 도구로 별도 열지는 않았습니다. TASK·별도 테스트 표·작성자 마감/자체 판정·별도 지적 대응 문서는 읽지 않았습니다. 호스트의 AGENTS.md·환경·도구·스킬 목록에는 노출됐으며, 별도 부트·메모리·brain·스킬 본문은 읽지 않았습니다. 파일 변경은 없습니다.

호출자는 같은 검토자(codex)의 2단계라고 명시했습니다. 검토 주체 변경은 통보되지 않았으나, 동일 실행 주체 여부를 별도로 검증하지는 않았습니다. 이번 판정은 이전 판단과 반영 주장을 알고 수행한 **후속 대조**이며, 새로운 맹검 판단은 아닙니다. 1단계 원문은 그대로 보존하며 아래는 그에 대한 추가 판정입니다.

1. **[blocking] 운영 명령이 일부 실행된 뒤 실패했을 때의 재개 계약이 없습니다.**  
   BR04는 운영 명령으로 여러 단계를 수행하고, 실패하면 단계별 주행으로 넘어갑니다. BACKLOG에는 실제로 명령 하나가 S04~S11을 수행하는 사례가 있습니다. 등록까지 성공한 뒤 후속 조회에서 실패하면, 단순한 단계 주행 전환은 등록을 다시 수행할 수 있습니다.

   BR05의 결과 불명 처리 원칙은 적절하지만, 운영 명령이 내부 단계별 실행 상태와 조회 근거를 제공해야 이 원칙을 적용할 수 있습니다. 명령 안의 위험 행동에도 단계별 관문이 적용되는지 명시돼야 합니다.

   **올릴 단계:** BR03·BR04의 운영 명령 계약과 BR05 검증. 부분 성공·시간 초과를 주입해 완료 단계 식별, 위험 행동 전 승인, 조회 후 재개, 중복 실행 0을 확인해야 합니다.

2. **[should_fix] 승인에 묶는 ‘플레이북 버전’과 학습 후 승인 유지가 충돌합니다.**  
   BR05는 버전이 달라지면 재확인하도록 하면서, 확인 후 수정이 반영되면 다음 주행에는 묻지 않도록 합니다. 학습 반영으로 버전이 바뀌는 경우 어느 버전에 승인을 부여하는지 불명확합니다.

   검증된 후보의 내용과 적용될 버전에 승인을 묶고, 반영 후 해당 승인이 유지되는 조건을 정해야 합니다. 승인 이후 후보 내용·계정·업무·위험 행동이 바뀌면 재확인하는 기준도 함께 검증해야 합니다.

   **올릴 단계:** BR05 승인·버전 설계. 이는 합의된 자율 실행 범위를 바꾸는 문제가 아니라 그 범위를 일관되게 구현하는 문제입니다.

3. **[should_fix] 개인정보 보호 기준이 초기 작성 과정과 모든 원본 저장물까지 일관되게 이어지지 않습니다.**  
   BR05는 진단·학습의 저장 지점을 구체적으로 다룹니다. 반면 BR03은 인터뷰 기록과 사용자 답을 저장하지만, 계정·인증·개인정보 답변 중 무엇을 기록하지 않아야 하는지 명시하지 않습니다. BR02의 API 요청 “값 없이” 규칙도 URL·선택자·`steps.json`·`flow.html` 등에 실값이 섞이는 경우까지 명확하게 포괄하지 않습니다.

   마지막에 비밀 검사를 통과하는 것만으로는 작성 도중 이미 저장된 개인정보를 방지하기 어렵습니다. 초기 기록부터 원본·중간 파일·최종 생성물까지 저장 허용 범위를 정하고, 민감 값을 넣은 초기 생성 시나리오로 검증해야 합니다.

   **올릴 단계:** BR02·BR03 데이터 설계와 BR06 완료 기준. 1단계 지적 5는 크게 개선됐지만 완전히 닫히지는 않았습니다.

4. **[note] 새 세션 재현과 빠르기 검증은 실질적으로 보강됐습니다.**  
   새로 확인한 BR06은 생성 세션의 맥락 없이, 다른 입력으로 목표를 수행하도록 요구합니다. 이는 1단계 지적 1의 핵심을 해소합니다. 성공 여부·시간·도구 호출·화면 탐색·추출 정확도 비교도 있어 지적 2의 파일 크기 대용 지표 문제를 해소합니다.

   다만 단일 실행의 시간 차이는 변동성이 큽니다. 같은 조건의 비교와 반복 관측을 정하면 판단이 더 안정적입니다. D2의 “첫 수행 성공”은 작성 과정의 증거로, BR06은 생성물의 재사용 가능성 증거로 구분하면 됩니다.

   **올릴 단계:** BR06 검증 설계.

5. **[note] fin-link 무영향은 계획 수준에서는 이전 blocking을 해소했습니다.**  
   이번에 읽은 BR01·BR06에는 설치 전후 목록·해시 비교, 기존 사본 유지, 테스트 4종, 설치 후 새 세션의 스킬 공존과 기존 시작 안내 확인이 있습니다. 생성물 바이트 동일성만 보던 이전 근거보다 충분히 넓어졌습니다.

   따라서 1단계 지적 3은 **계획의 blocking에서 실제 증거 확인 항목으로 변경**합니다. 다만 현재 보장된 것은 검증 계획이며, 실제 무영향 판정은 해당 결과를 확인한 뒤 가능합니다.

   **올릴 단계:** BR01·BR06 실행 검증.

6. **[should_fix] 브리프 선행 관계와 완료 기준의 의존성이 어긋납니다.**  
   현황 표에서 BR04의 선행은 BR02뿐인데, BR04 완료에는 BR03 생성물이 필요합니다. BR03도 BR04 주행 규약을 참조합니다. 스키마가 같다는 사실만으로 생성기와 실행기의 의미 해석까지 일치하지는 않습니다.

   공통 실행 계약을 먼저 확정하고 BR03·BR04를 구현하거나, BR04 완료의 선행에 BR03을 명시해야 합니다. 다른 전략으로는 대표 업무 하나의 생성→새 세션 실행→복구를 먼저 연결한 뒤 공통 규약을 추출할 수 있습니다. 현재 분할도 가능하지만 통합 위험을 BR06까지 미루지 않아야 합니다.

   **올릴 단계:** 브리프 순서·통합 전략.

결정 추적성은 대체로 좋습니다. D1·D2는 사용자 목적 5·7, D3는 목적 2, D4·D5는 목적 6, D6·D9는 목적 3·8로 연결됩니다. 특정 파일 구조와 인터뷰 방식은 목적을 구현하는 전략으로 볼 수 있습니다. 목적·목표·범위를 바꾸기보다 **운영 명령 안전 계약, 승인 버전 규칙, 초기 개인정보 처리, 통합 순서**를 보완할 사안입니다.
