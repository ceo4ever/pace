# BL261118_02 허브 PM main 직접 프로젝트 하네스 정비

## 목표

허브 PM(main 코디네이터, 예: 알투)이 프로젝트를 직접 수행할 때 worktree를 만들지 않고 **main에서 프로젝트로 진행하되, worktree 프로젝트와 같은 하네스(착수 기록·커밋 게이트·마감 검사·독립 검토 관문)가 적용**되게 한다. 상위 목적은 PACE 작업 하네스의 원칙 — "기억이 아니라 계약·게이트·기록으로 진행하고, 완료는 검증으로 증명한다" — 를 실행 위치와 관계없이 지키는 것이다.

근거(2026-11-18 P003 실측, 코드·브레인 확인):

- main 직접 경로는 `start`를 거치지 않아 착수 기록(상태 `진행`·착수 결정 log.jsonl)과 commit-msg 훅이 없다 — P003 진행 초기에 log.jsonl 누락·상태 `정의` 유지(캡틴 지적 뒤 수동 보완). 훅은 `project/P###` 브랜치에서만 동작한다(`src/project/harness.ts:693`).
- main 직접 finish는 정본 반영 diff 검사(`harness.ts:1331`)·의존성 감사(`:1364`)를 건너뛰고, 브레인 행은 커밋 전 변경만 본다(`:1324`). 그런데 프로젝트 밖 미커밋 변경은 금지한다(`:1259`). 브레인 페이지 `brain-at-project-gates`의 "한계"와 `작업-하네스-실측-함정`의 "main 직접 마감 순서(구현 먼저 커밋)"가 맞물려, **브레인을 고치고 PROJECT-CLOSE 브레인 행을 `반영`으로 쓴 main 직접 프로젝트는 finish를 통과할 수 없다**(P003 재현, 이슈 `main-직접-finish-브레인-반영-검사-모순`).
- 독립 검토 관문(`PRE-REVIEW.json`, `src/project/pre-review.ts`)은 태스크에만 적용되고 태스크 없는 프로젝트에는 없다. 검증은 별도 세션(tester ∥ reviewer, 다른 제공자 우선)이 맡는다는 원칙(`references/verification.md`, 브레인 `작업-하네스-흐름` "검증 책임과 중복 실행")은 이미 있으나 확인 장치가 비어 있다.
- main에서 진행하면 다른 worktree 프로젝트의 `병합 대기`(main 커밋 금지, SKILL.md §4)와 부딪힐 수 있다.

고른 길: main 직접 경로를 **worktree와 같은 하네스로 끌어올린다** — 시작 커밋을 기록하고 그 이후 프로젝트 태그 커밋으로 변경을 귀속시켜(공통 계약), 기존 관문(사전 검토·커밋 게이트·마감 검사)을 그대로 넓힌다. 새 장치보다 기존 장치의 적용 범위를 넓히는 쪽을 우선한다.

버린 길: (1) 허브 직접 수행을 금지하고 항상 worktree — 짧은 일에도 worktree 준비 비용, 캡틴 결정으로 기각. (2) main 직접은 아주 작은 일만 허용하는 기준만 두기 — 오늘 문제의 원인은 "main이라서"가 아니라 "main에서 하네스가 빠져서"라 근본 해결이 아님. (3) 검토 필수 장치 신설 — 이미 있는 사전 검토 관문을 넓히면 됨.

결과(관찰 가능): main 직접 프로젝트 하나를 착수 → 구현 커밋 → **별도 세션의 reviewer·tester 검증(대상 = 그 커밋)** → finish까지 하네스만으로 끝까지 진행할 수 있고(브레인 변경 포함), 다음 중 하나라도 있으면 하네스가 막는다: 착수 기록 없음, 프로젝트 커밋의 태그 누락, reviewer·tester 기록 없음, 구현 세션의 자체 검증, 검토 뒤 변경 미재검토, 정본·브레인 미반영. worktree 프로젝트의 기존 동작은 바뀌지 않는다.

## 공통 계약 — main 직접 프로젝트의 변경 집합

BR01·BR02·BR03·BR04·BR05가 함께 따른다. main에는 다른 작업(메모리·백로그·다른 프로젝트 병합)도 들어오므로 `시작 커밋..HEAD`만으로는 프로젝트 변경을 가를 수 없다.

1. **커밋 귀속**: main 직접 프로젝트의 커밋은 제목에 `(P###)` 또는 `(P###/T##)` 태그를 단다. 태그 없는 main 커밋은 프로젝트 변경이 아니다. 진행 중인 main 직접 프로젝트의 변경 집합 경로를 태그 없이 고치는 커밋은 BR03 게이트가 **거부**한다. 예외: `finish`가 상태를 `완료`로 바꾼 뒤 직접 만드는 마감 커밋은 하네스 소유 파일만 담고 finish 실행 표식이 있을 때 게이트가 허용한다(BR03).
2. **변경 집합(귀속)** = 시작 커밋 이후 그 태그가 붙은 커밋의 파일 경로 + 미커밋 변경 경로. "어느 경로가 이 프로젝트 것인가"만 정한다. 하네스 소유 파일(PROJECT·PROJECT-CLOSE·TASK-CLOSE·log.jsonl·METRICS·목차·대시보드 자료·프로젝트 메모리)은 빼고 따로 다룬다.
2-0. **반영 판정(순변경)**: finish(BR02)의 정본·브레인 "반영"은 변경 집합 경로 중 **시작 커밋과 마감 시점 작업본 사이에 실제 차이가 남은 경로**만 인정한다(`git diff <시작 커밋> -- <경로>`). 고쳤다가 다른 커밋이 되돌린 경로는 반영이 아니다.
2-1. **검증 유효성(내용)**: 검토 대상은 커밋 목록이 아니라 **변경 집합 파일들의 내용 해시**다. 마감 때 같은 경로들의 현재 내용 해시를 다시 계산해 다르면 재검토가 필요하다 — 태그 없는 커밋이 같은 파일을 고치거나 되돌린 경우, rebase·amend도 이것으로 잡는다. 하네스 소유 파일 변경은 해시에 넣지 않아 마감 커밋이 검증을 무효화하지 않는다. TASK·BR·BACKLOG처럼 하네스가 상태만 고치는 문서는 **하네스가 쓰는 상태 줄·현황 표 상태 칸을 정규화한 내용**으로 해시해, `done`의 상태 갱신이 재검토를 요구하지 않게 한다.
2-2. **관문 층위**: 커밋 훅(BR03)은 형식·상태(착수 기록·진행 상태·태그·점유)만 본다 — 검토 기록은 보지 않는다. 검토 기록은 태스크 `done`(태스크 단위 변경)과 `finish`(프로젝트 최종 변경)가 본다(BR04). 그래서 첫 구현 커밋이 검토를 요구하는 순환이 없다.
2-3. **별도 세션의 증명**: reviewer·tester 결과는 `pace agent run`·`verify`가 **검증 모드로 실행해 남긴 결과 파일**로만 인정한다 — 손으로 쓴 기록은 인정하지 않는다. 지금 `pace agent`는 `--resume`으로 기존 세션을 이어 쓸 수 있고(`src/cli.ts:950`), 세션 ID가 비어 있을 수 있으며, 결과에 역할·검토 대상이 없다(`src/agent/contract.ts` `AgentResult`) — 그래서 BR04가 검증 모드를 더한다: `--resume` 거부(새 세션 강제), 하네스가 발급한 **실행 ID**와 역할·대상 내용 해시·제공자·모델·세션 ID(보고된 경우)를 결과 파일에 함께 기록. 관문은 실행 ID·역할·대상 해시가 맞는 결과만 인정한다. 같은 제공자는 사유 기록 시 허용하되 교차 검증으로 표시하지 않는다.
3. **배타 점유**: main 직접 프로젝트가 `진행`인 동안 다른 프로젝트의 `merge`는 막고, `병합 대기` 프로젝트가 있으면 main 직접 착수·태그 커밋을 막는다(BR05). 충돌이 생기면(점유 중 병합 필요 등) 프로젝트를 `보류`로 두고 사용자 결정 뒤 재개한다. 보류 중에는 다른 병합·태그 없는 커밋이 허용되며, 재개 때 2-1로 검증 유효성을 다시 판정한다(달라졌으면 재검토).
4. 책임 분담: `start --main` 진입점은 BR01이 소유하고 BR03(훅 설치)이 덧붙인다. 커밋 훅은 BR03이 소유하고 BR05의 점유 판정을 호출한다. finish는 BR02가 소유하고 BR04의 검증 관문을 호출한다. 통합 시험은 각 소유 브리프에서 상대 브리프가 끝난 뒤 한다(진행 현황 선행 칸).
