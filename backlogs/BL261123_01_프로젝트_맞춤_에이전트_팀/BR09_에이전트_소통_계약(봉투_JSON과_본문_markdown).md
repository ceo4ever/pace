## 목적

팀 에이전트 사이의 주고받기를 **기록되고 검사되는 계약**으로 만든다(목표3·목표4). 자연어로만 주고받으면 생기는 문제를 막는다 — 근거(roblox-studio P002, 2026-11-23~24, 그쪽 코디네이터 요청·캡틴 승인 2026-11-24):
- 캡틴 원문과 해석이 섞여 전달됨("Play 4번" → 코디네이터가 확인 없이 "Play 1번+4판"으로 해석 → 판정 정정).
- 위임 기록이 없어 에이전트별 활동을 증거 파일을 뒤져 사후에 셈(리드 단독 구현, 제작 에이전트 호출 0을 마감 뒤에야 파악).
- 위임에 증명 범위·판정 주체 칸이 없어 사전 검토 반복(PACE P008이 TASK에 넣은 것과 같은 원인).

## 증명 범위

- **판정 주체**: 이 브리프는 계약의 **목표와 지켜야 할 불변식**까지만 정한다. 불변식을 실제로 지키는 기록 방식·칸·명령 동작은 P009 **T09 TASK 설계**가 정하고, 그 TASK의 사전 검토(증명 범위 포함, P008 규칙)와 시험이 판정한다. 현장 효과는 BR08 실증이 판정한다.
- **포함**: 아래 불변식, 하네스 연결(stats·finish), 다른 브리프와의 경계, T09가 반드시 답할 설계 질문 목록.
- **범위 밖**: 칸 이름·종류 수·실패 시 표기·명령 인자 같은 구현 세부 — T09 TASK로 넘긴다(아래 "T09가 답할 설계 질문"). 이 브리프의 예시 칸(roblox-studio 시범의 7종 등)은 출발점이며 T09가 바꿀 수 있다.

## 범위

- **형식 방향**: 메시지 = JSON 머리 한 줄(짧은 값) + 본문 markdown(경로 참조). 전부 JSON은 버린다 — 긴 한글 본문 이스케이프 실패, 캡틴용 가독성, 판단·진단은 칸에 맞지 않음. 출발점은 roblox-studio 시범 `tools/handoff.mjs`(7종: delegate·result·decision_request·captain_input·lock·unlock·status, 6개 시험).
- **불변식**(T09 설계와 시험이 지켜야 하는 것):
  1. **원문 보존**: 캡틴 원문은 해석과 분리해 그대로(길어도 온전히) 남고, 기록된 원문은 대조 가능한 출처 위치를 가진다.
  2. **해석 확인**: 원문을 그대로 옮기지 않고 실행·판정을 바꾸는 해석은 캡틴 확인(승인·정정·거절) 전에는 실행 근거가 될 수 없다. 승인은 확인을 요청한 그 해석에만 적용된다 — 다른 해석에 재사용할 수 없다.
  3. **실행 전 대조 책임**: 위임을 받은 쪽은 실행 전에 지시가 근거(캡틴 원문·확인된 해석 또는 계약)와 같은 범위인지 대조하고, 달라졌거나 근거가 불명확하면 보류하고 올린다. 이 책임은 BR02 정의 원본의 "올리는 형식"에 들어간다.
  4. **위임 종결**: 위임은 지정된 판정 주체가 증명 범위에 맞는 증거를 확인했을 때만 닫힌다. 부분·차단 결과는 위임을 닫지 않는다.
  5. **기록 없는 주고받기 없음**: 위임·결과·결정 요청·캡틴 입력은 주고받는 시점에 프로젝트 기록(`handoffs.jsonl`)에 남는다. 기록에 실패하면 보내지 않는다.
  6. **잠금은 실제 사건**: 잠금 기록은 BR05 장치의 실제 획득·해제·회수에서만 생긴다.
  7. **집계 일치**: 캡틴 개입은 BR01의 **요청 단위 도달 분류** 한 정의로 센다 — 같은 요청은 project log와 이 기록에 걸쳐 한 건이다.
- **하네스 연결**: `pace project stats` 팀 항목(BR06)이 이 기록에서 위임·결과·종결·결정 요청 수를 에이전트별로 내고, `pace project finish`는 열린 위임(특히 부분·차단)이 있으면 경고한다.
- **시범과의 관계**: roblox-studio `tools/handoff.mjs`는 참고 구현이다. PACE가 정본을 가지면 그 저장소는 PACE 명령으로 옮긴다(BR08). 시범 결과는 관측 범위를 밝혀 받고, BR06 비교에는 같은 정의로 다시 센 값만 쓴다.
- **T09가 답할 설계 질문**(독립 검토에서 나온 것 — T09 TASK가 답하고 사전 검토로 확인): ① 해석 확인 사슬(원문 → 확인 요청 → 답 → 위임)을 어떤 필수 칸으로 강제하고, 위임 내용이 승인된 해석을 벗어난 경우 무엇을 자동 거부하고 무엇을 수동 대조로 남기는가 ② 근거 없는 위임(`basis: none` 같은 표시)의 경계와 감사 방법 ③ 전송 시도 기록 — 실패해 메시지 ID가 없을 때의 표현, 시도 직후 기록 주체, project log와 공유할 요청 ID 입력 경로 ④ 판정 주체 이름의 자기 신고 한계를 어디까지 받아들이는가 ⑤ finish의 열린 위임 **경고는 필수**이고, 경고에 더해 차단까지 할지(어떤 조건에서)만 T09가 정한다.
- 제외: 에이전트 대화 내용 자체의 품질 판정, 메시지 전송 수단(Orca·서브에이전트) 변경.

## 완료 기준

- T09 TASK가 위 설계 질문 ①~⑤에 답하고, 불변식 1~7마다 그것을 지키는 장치와 시험을 대응시킨 표를 가진다(사전 검토 통과).
- 불변식마다 통과·거부 시험이 있다 — 특히 ② 확인 전 해석·다른 해석에 대한 승인 재사용·승인 해석을 벗어난 위임의 거부(예: 원문 "Play 4번", 확인받은 해석 "Play 4판", 위임이 "Play 1번+4판"이면 거부 또는 보류), ④ 판정 주체가 아닌 종결 거부, ⑤ 기록 실패 시 미발송, ⑦ 같은 요청의 중복 없는 집계.
- PACE 쪽 임시 프로젝트에서 정상 작업 경로로 위임 → 결과 → 종결, 원문 → 확인 → 위임 흐름이 기록되고 `stats`·finish 경고가 나온다.
- 실행 순서: P009에서 T09는 T02(팀 원본의 이름·올리는 형식)·T05(잠금 사건) 뒤, T06(측정)·T08(첫 적용) 전에 연다. T09는 P009 worktree가 이 브리프의 최종 판정 커밋을 담은 main을 반영한 뒤 worktree의 BR09 파일을 읽고 연다. 두 호스트 현장 추적과 감사(근거 없는 위임 대조·원문 출처 대조·보류 기록)는 BR08 실증 표에서 확인한다.
