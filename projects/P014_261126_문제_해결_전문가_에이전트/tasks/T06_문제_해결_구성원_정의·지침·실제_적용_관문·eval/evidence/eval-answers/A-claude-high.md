# T-2 반복 실패 해결안: 성공한 쓰기 경로 검증 (사례 A)

## 결론

성공한 쓰기가 실제로 실행된 것은 증거로 충분합니다. 하지만 그 실행이 "대상 운영자의 인라인 버튼 승인" 때문이었는지는 증명되지 않았습니다. 기계 기록이 남는 것은 실행 결과뿐이고, 누가 어느 경로로 승인했는지는 캡틴의 화면과 진술에만 의존합니다. R9와 R10이 같은 경계를 지적한 이유가 이것입니다. 증거를 더 덧붙이는 방식은 이미 두 번 실패했습니다. 해결 방향은 승인 기록을 기계 증거로 만들고, 새 시도에서 음성 대조와 함께 다시 관찰하는 것입니다.

## 1. 막힌 목표와 상위 목적 점검

- **목표** (`case.md:3`): 대상 운영자가 특정 새 쓰기 요청을 Telegram 인라인 버튼으로 승인합니다. 그리고 그 시도만 실행이 시작됐음을 실제 사례로 확인합니다.
- **판단**: 목표 자체는 상위 목적인 "쓰기는 지정 운영자 승인 뒤에만 실행"에 맞습니다. 바꿀 필요가 없습니다.
- **수용 기준에 빈칸이 있습니다**: 무엇을 "실제 사례 확인"으로 인정할지가 정해지지 않았습니다. 그래서 보고자와 검토자가 증거의 경계를 놓고 계속 엇갈렸습니다(추정). 해결안에서 이 기준을 먼저 고정합니다.

## 2. 확인한 원문 증거와 재현 상태

**확인한 것**
- 근거 자료는 `case.md` 한 파일뿐입니다.
- `case.md:9`가 인용한 `R10.review.snapshot`, `evidence/s3.json`, `evidence/s3-supplement.json`은 작업 폴더에 없습니다. 검색으로 확인했고, 그래서 이 파일들의 실제 내용은 검증하지 못했습니다.
- R9의 원문도 없습니다. "R9와 R10이 같은 경계를 문제 삼았다"는 `case.md:11`의 서술을 입력으로만 썼습니다.

**재현**: 범위 밖이라 실행하지 않았습니다. 아래 검증 계획의 관찰은 모두 제안입니다.

## 3. 원인 분석

T-2 행(`case.md:9`)을 주장 단위로 나눠 증거 등급을 매겼습니다.

| 주장 | 증거 | 등급 |
|---|---|---|
| 승인 전 대기, 실행기 0, 파일 불변 | `s3.json` (`case.md:11`에 따르면 **1차 시도**의 것) | 1차에 대해서는 기계 증거. 2차에 대해서는 근거 혼선 |
| 성공 시도의 승인 대기와 완료 알림 | `s3-supplement.json` | 기계 증거. 다만 승인자는 담고 있지 않음 |
| 실행 전 트리가 최초 커밋과 같음, `approved.txt`만 바뀜, 나머지 6개 해시 불변 | 스냅숏과 해시 | 기계 증거. "실행이 일어났다"는 것은 충분히 뒷받침됨 |
| 승인자가 대상 운영자이고 버튼으로 눌렀음 | 캡틴이 붙여 준 화면. 버튼이 사라진 것을 "처리됨"으로 해석 | **사람 증언**. 버튼이 사라진 것은 승인 경로나 누른 사람을 증명하지 못함 |
| 관리자 경로 미사용 | 토큰 사용 거부 기록. 원문 스스로 "접속 로그가 없어 기계 증명은 아님"이라고 씀 | **음성 증거 없음** |
| 그 시도만 시작됨, 순서 보장 | 단위 시험 S-7, S-22, S-8c | 실제 사례가 아님. 목표의 "실제 사례"를 대신할 수 없음 |

**원인 층과 근거**
1. **설계 층 (주원인)**: 승인 콜백과 실행 시작을 잇는 기계 기록이 없습니다. 콜백을 누른 사용자, 승인 경로(버튼인지 관리자 경로인지), 시도 ID가 기록되지 않습니다. 관리자 경로에는 접속 로그가 없습니다(`case.md:9`, 확인된 사실). 그래서 어떤 증거를 덧붙여도 "관리자 경로가 아니었다"와 "대상 운영자가 눌렀다"를 증명할 수 없습니다. 같은 부류의 지적이 R9와 R10에서 반복된 것과 맞아떨어집니다.
2. **기획 층 (보조원인)**: 성공 시도의 증거 경계가 섞였습니다. 1차 시도의 `s3.json`이 2차 성공의 근거로도 인용됐습니다(`case.md:9`와 `case.md:11` 대조). 또 실제 사례가 필요한 순서 보장을 단위 시험으로 채웠습니다.
3. **확인 필요 (추정)**: 요청자는 "캡틴 계정"인데, 캡틴이 "대상으로 정한 운영자"와 같은 사람인지 원문에 명시가 없습니다. 같은 사람이면 요청자와 승인자가 같은 자기 승인 구도도 기준에 허용되는지 정해야 합니다.

**성공 원인 (요청하신 조사)**
- **확인된 것**: 1차 시도는 편집 외 도구(셸)를 써서 거부됐습니다. 2차는 허용 도구(Edit)로 실행됐습니다. 그래서 2차가 실행되고 쓰기가 성공한 것은 도구 정책과 정합하고 증거로도 확인됩니다.
- **증명되지 않은 것**: 2차의 승인이 대상 운영자의 버튼 때문이었는지는 증명되지 않았습니다. 관리자 경로로 승인했어도 버튼이 같은 방식으로 사라지는지는 코드가 없어 확인하지 못했습니다(추정 대상).

## 5. 검증 계획 (모두 제안, 실행하지 않음)

**사전 고정**
- 대상 운영자의 Telegram user id를 설정 원문에서 기록합니다.
- 수용 기준을 아래 해소 관찰 3~4번처럼 기계 기록 기준으로 합의합니다.
- 관리자 경로 로그의 감지력을 확인합니다. 대조용 관리자 호출을 1회 하고, 다른 더미 요청에 대해 `path=admin` 기록이 남는지 봅니다.

**해소를 증명할 관찰**
1. 새 쓰기 요청 R을 만듭니다(새 시도 ID). R은 `awaiting_approval` 상태이고, 실행기는 0이며, 트리 해시는 그대로여야 합니다.
2. 대상 운영자가 R의 버튼을 누릅니다.
3. 감사 기록에서 `from.id`가 대상 운영자이고, `path=button`이며, `attempt_id`가 R이어야 합니다.
4. 실행 시작 이벤트의 승인 참조가 3번 기록과 같아야 합니다.
5. 기대한 파일만 기대 바이트로 바뀌고 나머지 해시는 그대로이며, 완료 알림이 도달해야 합니다.

**음성 대조 (재발 여부를 가르는 관찰)**
- 동시에 대기 중인 다른 요청 R′: R을 승인한 뒤에도 R′은 `awaiting_approval` 상태이고 실행기 0이어야 합니다. 이것으로 "그 시도만 시작됨"을 확인합니다.
- 대상이 아닌 테스트 계정이 R′의 버튼을 누릅니다: 거부되어야 하고, 실행이 없어야 하며, 거부 기록이 남아야 합니다.
- 검증 시간 동안 `path=admin` 기록이 0건이어야 합니다. 이 결과는 사전 단계에서 로그 감지력을 확인했을 때만 의미가 있습니다.
- 완료 뒤 같은 콜백을 다시 보냅니다: 두 번째 실행이 없어야 합니다.

**실패 시 다음 수**
- 감사 기록에 `from.id`나 경로가 비어 있으면 구현 층 문제입니다. 콜백 처리기의 기록 지점을 고칩니다.
- R′이 같이 시작되면 승인과 시도의 결합에 결함이 있는 것입니다(설계 층). 검증을 멈추고 승인 키를 시도 ID에 묶도록 재설계해야 합니다.
- 비대상 계정의 승인이 통과하면 권한 검사 결함입니다. 이것은 T-2보다 우선하는 보안 문제로 올립니다.
- 관리자 경로에 로깅을 넣을 수 없으면 B안의 차단 방식으로 대체하고, 그 한계를 보고서에 명시합니다.

## 6. 남은 불확실성

- `s3.json`, `s3-supplement.json`, R9와 R10 리뷰 원문, 코드가 없어서 다음을 확인하지 못했습니다.
  - 현재 승인 처리기가 이미 `from.id`를 기록하고 있는지
  - 관리자 경로로 승인해도 버튼이 사라지는지
  - 2차 성공 시도의 증거가 실제로 어느 파일에 있는지
- 캡틴이 대상 운영자와 같은 사람인지, 그리고 자기 승인이 허용되는지는 정해지지 않았습니다. 수용 기준을 정할 때 결정해야 할 사항입니다.
- A안을 적용할지, 로그 보관 정책을 어떻게 할지는 호출 PM이 정할 사항입니다. owner 결정이 필요한지는 정본 A에 따라 PM이 판단합니다.
