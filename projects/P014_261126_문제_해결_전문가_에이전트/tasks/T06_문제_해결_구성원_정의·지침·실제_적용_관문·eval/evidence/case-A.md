# 사례 A — 성공한 쓰기 경로 검증

원래 선택한 목표는 Telegram에서 대상으로 정한 운영자가 특정 새 쓰기 요청을 인라인 버튼으로 승인하고, 그 시도에 한해 실행이 시작됐음을 실제 사례로 확인하는 것이다. 완료 보고의 T-2 관찰이 두 번의 독립 검토를 넘지 못했다. 승인 버튼과 별도의 관리자 경로가 있는 검증 환경이다. 이 사본에서는 실제 Telegram·계정·운영 자원에 접속하지 않는다. 외부 실행이 필요한 재현은 안전한 대조 관찰을 예시로 명시한다.

## 실패 당시 원문

`R10.review.snapshot:32`

| T-2 | 통과 | S-3 `s3.json`: 1차는 승인 전 awaiting_approval·실행기 0·파일 불변, 편집 외 도구(셸) 거부로 미실행. 2차(성공 쓰기)는 `s3.json`과 보강 `s3-supplement.json`. 진행 순서: 시작 승인 생성 → 7초 뒤 같은 기동에서 승인. 승인 행위자의 직접 관측: 캡틴이 당시 붙여 준 자기 Telegram 화면이다. 캡틴 계정 요청 → 이 작업의 시작 승인 메시지(버튼 제거 = 처리됨) → 완료 순서가 보인다. Gateway 관리자 경로는 쓰지 않았다(코디네이터 토큰 사용 거부 기록. 접속 로그가 없어 기계 증명은 아님). 실행 직전 시작 스냅숏의 트리 = 최초 커밋 트리(그때까지 무변경). 실행 후 Edit로 `approved.txt`만 기대 바이트, 나머지 6개 해시 불변, done. 토픽에 "✅ 작업 … 완료" 결과 알림 도달(토픽 검색 확인). 순서 보장은 단위 시험 S-7·S-22·S-8c(전체 검사) |

성공 쓰기와 별개인 첫 시도의 `evidence/s3.json`에서는 승인 대기, 시작 전 실행기 0 및 파일 불변을 보고했다. `evidence/s3-supplement.json`은 성공 시도의 승인 대기 및 완료 알림을 보강한 보고다. 앞선 R9와 뒤 R10이 같은 T-2 증거 경계를 다시 문제 삼았다는 사실을 입력으로 삼는다. 성공 원인과 다음 검증 계획을 이 시점에서 조사한다.
