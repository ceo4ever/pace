# P014 T02 1단계 독립 목표 대조 (첫 판정, 2단계는 실행 안 함)

**결론:** 네 가지 신호는 모두 구현돼 있고, 기존 검사 결과·검토 예산·판정·원장 기록의 계약은 코드상 유지됩니다. 다만 수정이 필요한 쪽(should_fix)으로 1건, 근거와 범위의 한계로 몇 건이 있습니다. 테스트는 제가 다시 돌리지 않았습니다. `focused-tests.txt`에 적힌 7건 모두 통과라는 기록만 근거로 봤습니다.

## 1. 신호별 대조

| 신호 | 위치 | 판정 |

| ① 일반 산출물 검토의 연속 실패 | `src/agent/review-signals.ts:16`, `src/agent/verify-cli.ts:464` | 충족. 예산이 없는 검토에서 기존 단계가 `normal`일 때만 냅니다. 유효한 fail이 정확히 2번째일 때 한 번만 냅니다. `void`·`interrupted`·`stale` 기록은 빼고, pass·decision·diagnosis가 오면 셉니다를 처음부터 다시 셉니다. 3번째 실패는 기존 `escalation`이 처리합니다. 예산이 있는 단위는 기존 예산 소진을 신호 ①로 쓰므로 새로 내지 않습니다. |

**기존 계약 유지 근거**
- 신호는 출력 JSON의 `troubleshooterSignals`와 출력 문자열에만 붙습니다. 원장과 기록 파일에는 남지 않는다는 것을 테스트가 확인합니다(`test/agent-review-log.test.ts` 추가분).
- 영역 신호는 원장 기록과 예산 상태를 읽은 뒤에 계산합니다. 추가 호출은 없고, 다음 경우에는 내지 않습니다: 예산 소진 회차, 상위 복구 진행 중, 후속 확인 회차.
- 시험 쪽은 `withSignals`가 결과 문자열 뒤에 덧붙이기만 합니다. 종료 코드는 그대로이고, 예외는 `catch → ""`로 끝납니다.
- `execute.ts`는 기존 분기를 `try/finally`로 감쌌을 뿐입니다. `failures`·`unknown`·`break` 처리는 원래와 같습니다.

## 2. 저장소와 경로 경계
- **영역 경로:** 절대 경로는 저장소 루트 기준 상대 경로로 바꾼 뒤 `permissionPath`로 검사합니다. 여기서 `..`, `.`, `\`, `:`, 제어 문자, `.git`이 거부됩니다. 경로에 비밀로 보이는 값이 있으면(`hasSecret`) 제외합니다. 테스트가 `../src/...` 거부를 확인합니다.
- **시험 이력 저장 위치:** 저장 위치는 `<공통 git 폴더>/worktrees/<이름>/pace/test-signals/log.jsonl`이고, 아래 조건을 모두 만족할 때만 씁니다.
  - 브랜치가 `project/P###`이다.
  - `projectWorktreeMainRoot` 확인을 통과한다(진행 중이거나 병합 대기인 프로젝트의 실제 worktree).
  - git 폴더의 실제 경로가 공통 `worktrees` 폴더 아래로 확인된다.
  - 경로 중간에 링크가 없다(`safeTeamPath`).
- **이력 파일 보호:** 추가하기 전에 `readTeamEvents`로 확인해서 링크, 하드링크, 32MiB 초과, 형식 손상을 거부합니다. 쓸 때도 `O_NOFOLLOW`와 `nlink===1`을 다시 확인합니다. 심볼릭 링크로 바꿔 놓으면 바깥 파일이 그대로 남는다는 것을 테스트가 확인합니다.
- **추적 파일 영향:** git이 추적하지 않는 위치라 `git status`가 바뀌지 않고, main 체크아웃에서는 기록하지 않습니다(테스트로 확인).

## 3. 결함과 한계

**F1 (should_fix): 영역 신호의 "직전 시도"가 다른 산출물일 수 있음.** 예산이 있는 단위에서 기준점은 `budget?.latest`입니다(`verify-cli.ts:341`). 예산은 같은 태스크의 여러 원장이 공유하므로, 이 기준점이 다른 원장의 다른 산출물일 수 있습니다. 그런데 `previousSnapshot`을 대상이 같은지 확인하지 않고 그대로 넘깁니다(`:452`). 그러면 `changedInReview`가 서로 다른 패치의 같은 파일 구역을 비교하게 되고, ④ 겉만 고침 신호가 잘못 나올 수 있습니다. 판정과 원장에는 영향이 없는 권고 신호이지만, "같은 대상의 두 연속 시도"라는 전제와 어긋납니다. 대상이 같을 때만 ④를 내도록 막을 것을 권합니다. 테스트는 원장이 하나인 경우만 다룹니다.

**F2 (note): 직전 시도의 판정이 `unknown`이어도 기준점이 됨.** 테스트가 바로 이 경우(unknown → fail)를 씁니다. 지적 하나하나의 유효성은 거르지만, 판정 단위로 보면 "유효한 두 시도"는 아닙니다. 의도한 설계인지 사람이 확인해야 합니다.

**L1: 문턱 근거의 범위.**
- `convergence.json`은 기준 커밋 `4c7621d`의 검토 원장만 집계합니다. 유효 fail이 2번 이어진 뒤 다음 판정은 실패 20건, 통과 7건입니다(관측 27건, 미관측 0건).
- 27건 중 19건이 P009 T06 한 태스크에서 나왔고, 이를 빼면 실패 5건, 통과 3건(n=8)입니다.
- 시험 신호의 문턱 2에는 별도의 이력 근거가 없습니다. 검토 근거를 그대로 옮겨 쓴 것으로 봐야 합니다.
- 드라이버 스크립트의 집계 규칙은 `reviewFailureSignal`과 같습니다. 드라이버의 `rereview_of != record` 조건은 사실상 아무 효과가 없습니다.

**L2: 시험 신호가 적용되지 않는 범위.**
- vitest 단위는 관측하지 않습니다(`execute.ts`의 `kind !== "vitest"` 조건).
- `pace test <단위>` 실행, main 체크아웃, 전체 검사로 넘어간 경우도 기록되지 않습니다.
- 이력 파일은 계속 커지기만 하다가 32MiB를 넘으면 신호가 소리 없이 멈춥니다. 안전한 쪽으로 멈추고 검사 결과에는 영향이 없습니다.

**L3: 근거 회차 표시.** 일반 검토 신호의 `unit.ref`는 대상 이름(예: `TASK.md`)이고, 근거는 원장 기준 상대 기록 경로입니다. 해당 실행의 출력 안에서는 충분하지만, 출력만 따로 떼어 보면 어느 원장인지 알 수 없습니다. 시험 신호의 근거는 무작위 `testAttempt` 번호라서 worktree 로컬 이력에서만 다시 추적할 수 있습니다.

## 4. 근거와 귀속의 한계
- 판단 근거: `implementation.patch`, `convergence.json`과 그 드라이버 스크립트, `focused-tests.txt`, 그리고 후보 코드(`verify-cli.ts` 290–470행, `changed.ts` 120–187행, 신호 모듈이 의존하는 `event-log`·`handoff-files`·`harness`·`team-input`·`store`·`resource-lock`·`review-permission`·`secrets`의 해당 함수).
- 확인하지 않은 것: `reviewStage`의 단계 전환 문턱(2번 fail이 `normal`인지)은 테스트 결과로만 받아들였습니다. `readReviewState`·`budget` 내부 구현과 `structured-review.ts`의 `effective`·`reason` 산출도 직접 읽지 않았습니다.
- 테스트 통과는 직접 재현하지 않았습니다. `focused-tests.txt`에 기록된 결과일 뿐입니다.

## 5. 독립 노출과 자동 주입
- **자동 주입:** 세션 시작 때 `CLAUDE.md`→`AGENTS.md` 프로젝트 지침, git 상태 요약(파일 이름 목록과 최근 커밋 제목), 부트를 생략한다는 훅 문구가 자동으로 들어왔습니다.
- **요청에서 받은 정보:** 상위 목적 문장(네 가지 신호, 계약 유지)을 요청자에게서 받았습니다.
- **간접 노출:** 패치에 포함된 `required-roles.md`의 TS-01~05 요건 문장을 읽었습니다. BR02를 직접 열지는 않았지만, 그 요약이 사실상 판정 기준 노릇을 했으므로 독립성이 그만큼 줄었습니다.
- **열지 않은 것:** TASK 문서, 승낙 문서, 마감 문서, 백로그 문서, 다른 검토 기록은 찾지도 열지도 않았습니다.
- 2단계는 실행하지 않았습니다.
