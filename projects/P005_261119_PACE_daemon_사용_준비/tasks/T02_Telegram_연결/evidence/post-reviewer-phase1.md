# P005 T02 독립 리뷰 1단계 판정 (비식별 관측만 근거)

## 받은 범위와 읽은 범위
- **받은 것:** 메시지에 붙어 온 JSON 8개뿐입니다. operational-setup, live-allow-initial, live-deny, live-allow-restored, allow-initial-stop, deny-stop, final-runtime-restoration, secret-observations입니다.
- **읽지 않은 것:** 파일, 소스, TASK·PROJECT·BR 문서, 작업자 결론은 열거나 찾지 않았습니다. 도구 호출, 명령 실행, 보조 호출(advisor 포함)도 하지 않았습니다.
- **검증 수준:** 모듈·설정 해시를 실제 파일과 대조하지 않았습니다. 모든 판단은 자기보고된 boolean과 숫자에 기대고 있습니다.

## 종합 판정: **조건부 달성** (핵심 3요소 모두 근거 있음, 보완 권고 있음)

| 목표 요소 | 판정 | 근거 |
|---|---|---|
| 포럼 그룹 연결 구성 | 달성 | `botVerified`, `forumVerified`, `botMemberVerified`, `webhookAbsent`, `configLoaderPass`가 모두 true입니다. getMe, getChat, getWebhookInfo, getChatMember 4종 API로 확인했습니다. 허용 사용자는 1명이고, 기존 장치·설정은 보존됐습니다. |
| 허용 사용자 응답 | 달성 | 처음 허용 단계와 복원 단계 모두 새 요청 1건에 상태 응답 1건, 발송 1건이 나왔고, 거절 증가분은 0입니다. |
| 불허 사용자 거절 | 조건부 달성 | 거절 증가분 1, 상태 응답 0, 발송 0입니다. 새 작업과 API 실패는 없었습니다. |
| 토큰 비노출 | 범위 내 달성 | daemon 파일 4개, 셸 기록, CLI status·logs, 단계별 API 파라미터·응답(10~12건)에서 토큰 일치가 0건입니다. 자식 프로세스 출력에도 토큰이 없었습니다. |
| 정리·원복 | 달성 | 단계마다 중지됐고, 락이 없고, 포트를 다시 잡을 수 있습니다. 설정 해시와 모듈 해시는 처음과 같고, 허용 사용자도 원복됐습니다. |

## 목표 정합
- 측정 항목이 태스크 목표 3요소(연결 구성, 허용·불허 처리, 토큰 비노출)와 그대로 맞습니다.
- 응답 실측 → 거절 실측 → 다시 응답하는 순서라서, 거절 결과가 봇 고장이 아니라 허용 목록 판정 때문이라는 해석을 뒷받침합니다.
- 상위 목적인 "작업을 맡기고 결과 받기"는 이번 태스크 범위 밖으로 봅니다. 이번에는 상태 조회만 확인했고, 새 작업은 0건이며 workspace도 0개입니다.

## 한계
1. **거절 실측은 실제 제3자 계정이 아니라 런타임 제외 방식입니다** (`runtimeExclusionOnly: true`). 같은 실제 사용자를 메모리 안의 허용 목록에서 빼고 보낸 것으로 해석됩니다. 판정 경로는 검증되지만, 다른 user id·다른 채팅·봇 계정이 보낸 입력은 검증되지 않았습니다.
2. **거절이 무응답 방식입니다** (발송 0). 보안상 적절하지만, 목표의 "거절"을 안내 메시지까지 포함하는 뜻으로 정의했다면 맞지 않습니다. TASK 기준을 확인해야 합니다.
3. **토큰 검사는 원문 일치 방식으로 보입니다.** URL 인코딩, 부분 문자열, base64 같은 변형은 검사했다는 표시가 없습니다. 또 API 실패가 0건이라 오류 경로(요청 URL이 예외 메시지·로그에 찍히는 경우)는 실행되지 않았습니다.
4. **포럼 토픽 라우팅은 명시적으로 검증되지 않았습니다.** `topicCreationNotRequired`이고, 메시지가 어느 토픽/General에서 처리됐는지는 boolean으로 드러나지 않습니다.
5. **표본이 작습니다.** 단계마다 요청 1건이고, 명령도 status 하나뿐입니다.
6. **ACL 상속 의존:** 원본 env와 파일 ACL은 `protected: false`(상속)이고 디렉터리만 protected입니다. 예상 밖 허용은 0건이라 현재 상태는 괜찮지만, 상위 디렉터리 권한이 바뀌면 보호도 함께 영향을 받습니다.
7. **독립 검증이 불가능합니다.** 식별자와 메시지 내용을 내보내지 않는 설계 때문에, 실제 Telegram과 실시간으로 통신했는지와 단계 순서·시각을 이 자료만으로 교차 확인할 수 없습니다.

## 보완 권고 (차단 사유 아님)
- 허용 목록에 없는 실제 별도 계정, 또는 다른 채팅에서 거절을 1회 실측합니다.
- API 오류를 유도한 뒤(잘못된 chat 등) 로그와 출력에서 토큰을 재검사합니다. URL 인코딩된 형태도 검사 대상에 넣습니다.
- 토픽 안 메시지와 General 메시지의 처리 결과를 boolean으로 기록합니다.
- 거절 시 무응답이 의도된 사양인지 TASK 기준과 대조합니다. 이 확인은 2단계에서 해야 합니다.
