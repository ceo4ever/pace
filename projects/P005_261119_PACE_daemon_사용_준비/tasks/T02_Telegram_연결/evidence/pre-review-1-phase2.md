# T02 Telegram 연결 TASK.md 사전 검토 2단계 (1단계 판단 보존 + PROJECT·BR02·소스 대조)

blocking 1건 때문에 판정은 fail입니다. TASK의 목적·기준 방향은 맞지만, 접근이 허용한 "설치 마법사의 숨김 입력" 경로를 쓰면 승인되지 않은 Windows 로그온 등록이 반드시 일어납니다.

## 받은/읽은 범위
- **이번 단계:** 호출 메시지에 붙은 원문만 봤습니다. PROJECT.md, BR02, 그리고 `install-wizard.ts runDaemonInstall`, `cli.ts telegram init`, `adapter.ts`(connect·disconnect·권한 분기·general), `index.ts runDaemon` 발췌입니다. 파일 열기, 파일 변경, 보조 호출은 하지 않았습니다.
- **1단계에서 읽은 것:** `TASK.md` 하나입니다.
- **원문을 받지 못한 함수:** `offerTelegram`, `applyAutostart`, `writeTelegramSecret`, `isAllowed`/`actorOf`, `initState`, `redact`, `createTelegramAdapter`는 원문을 받지 못했습니다. 이 함수들에 걸린 판단은 그 한계 안에 있습니다.
- **자동 맥락:** 1단계와 같습니다. SessionStart 훅 문구와 호스트가 붙인 계정 맥락이 있었고, 검토에는 쓰지 않았습니다. 인증 정보나 계정 정보는 출력하지 않습니다.
- **검토 주체:** 1단계와 같은 세션, 같은 제공자(Claude, Opus 5.5)입니다. 1단계 뒤 대화가 이어져 있으므로 두 단계가 서로 독립된 주체는 아닙니다. 주체를 바꾸지 않았으니 바뀐 이유도 없습니다.
- **미실행:** Telegram 연결, 전송, 운영 변경의 실제 결과는 실행하지 않았습니다. 이 검토는 계획만 판정합니다.

## 독립 목표 대조
- **목표 정합성:** TASK의 목적과 T-1~T-3은 PROJECT P-2와 BR02 완료 기준에 맞습니다. 사용자·채팅 ID를 증거에서 빼는 T-3 요구는 PROJECT 설계 문단에서 나온 것입니다. workspace, maxConcurrent, 시작 방식을 제외한 것도 PROJECT의 "캡틴 확인 사항" 및 T03·T04 분리와 맞습니다.
- **목표 달성:** **미달 위험**입니다. 접근이 허용한 입력 경로 중 하나가 승인 범위 밖 운영 변경을 일으킵니다(아래 B-1). 불허 거절 관측은 실행 가능성이 아직 **미확인**입니다.
- **올릴 단계:** 접근 절(입력 경로)과 테스트 S-2·S-4·대체 절차입니다. 목적·목표·범위는 바꿀 필요가 없으므로 사용자에게 물을 것은 없습니다.

## 지적

**B-1 [blocking] 숨김 입력 경로를 쓰면 로그온 등록이 반드시 따라옵니다.**
- `runDaemonInstall`에서 `offerTelegram`은 계획 확인에 동의해 `yes = true`가 된 뒤에만 호출됩니다. 그 다음에는 조건 없이 `applyAutostart(env, false)`가 실행됩니다.
- 확인을 거절하면 함수가 바로 끝나서 Telegram 입력 단계에 가지 못합니다. 결국 이 경로로 토큰을 넣으면 `--yes`를 쓰지 않아도 Windows Run 등록이 함께 일어납니다.
- 이어서 daemon 시작 제안까지 나옵니다. 체인이 없으면 agent setup도 따라 실행됩니다.
- 이는 T01 결정 메모의 "로그온 제외", TASK 자신의 금지 사항, T03 범위를 모두 어깁니다. S-2의 "로그온 미실행" 확인은 일이 벌어진 뒤에야 잡아냅니다.
- BR02 범위가 이 경로를 허용하더라도, 지금 승인 상태에서는 TASK가 이 경로를 막아야 합니다.
- **고칠 방향:** 접근과 S-2에서 설치 마법사를 빼고, `telegram init` 표준 입력만 남깁니다.

**S-1 [should_fix] stdin 입력을 어떤 방식으로 할지 정해야 합니다. 1단계 #3을 이렇게 구체화했습니다.**
- `telegram init`은 `readFileSync(0)`으로 읽습니다. 콘솔에서 직접 타이핑하면 화면에 토큰이 그대로 보이고, Windows에서는 입력 끝을 알리는 조작도 필요합니다. 즉 숨김 입력이 아닙니다.
- 명령줄에 리터럴로 적어 파이프하면 PSReadLine 기록에 남습니다.
- 숨김 입력(`Read-Host -AsSecureString` 같은 방식)으로 받아 변수에서 파이프하는 절차를 정하고, 리터럴 사용은 금지해야 합니다. 셸 기록도 S-5 검사 대상에 넣습니다.
- 참고로 `--chat-id` 값은 CLI 설계상 argv와 셸 기록에 남습니다. 그 기록을 증거로 옮기지 않는다고 적어 둡니다.

**S-2 [should_fix] 실제 거절 관측 수단을 정해야 합니다. 1단계 #2를 강화했습니다.**
- 받은 소스로는 기존 관측 수단에 거절이 드러나지 않습니다.
  - `writeStatus`에는 어댑터 stats가 없습니다.
  - `/status`는 `host.overview()`만 보여 줍니다.
  - 거절 분기는 `stats.rejectedUsers++`만 하고 log를 남기지 않습니다.
- 그래서 관측하려면 계측이 필요합니다. 제품 정책을 바꾸지 않는 조건은 다음과 같습니다.
  - (a) 시험용 실행기에서 runDaemon을 부르기 전에 설치본 TelegramAdapter prototype의 `connect`만 감싸 인스턴스 참조를 잡습니다. 분기와 반환값은 건드리지 않습니다.
  - (b) **`o.adapters`로 두 번째 Telegram 어댑터를 넣는 것은 금지합니다.** 시크릿이 있으면 runDaemon이 어댑터를 따로 만들기 때문에 poller가 중복됩니다.
  - (c) 설치본 모듈 해시가 바뀌지 않았는지 확인하고, 클래스를 export·patch할 수 있는지 S-1에서 미리 확인합니다.
- 계측이 안 되면 T-2는 "미확인"이 아니라 **미달**이고 태스크를 닫지 않는다고 명시해야 합니다.
- 보조 증거로 상태 파일의 update offset이 진행됐는지 보는 방법도 검토할 만합니다. 다만 `initState` 원문이 없어 가능한지는 미확인입니다.

**S-3 [should_fix] 허용 목록 대체·복원 절차가 빠졌습니다. 1단계 #4를 유지하고 강화했습니다.**
- 설치 마법사가 실행 중 daemon에서는 바뀐 설정이 재시작 전까지 적용되지 않는다고 안내합니다. 즉 config는 기동할 때 읽힙니다.
- 따라서 임시 제외 대체 절차는 다음 순서여야 하고, 이것이 테스트 행으로 있어야 합니다.
  1. 정지
  2. 허용 목록에서 제외(원자적 갱신)
  3. 기동
  4. 거절 관측
  5. 정지
  6. 복원
  7. 기동
  8. 허용 사용자 응답 재확인
- 실패할 때 시크릿과 config를 되돌리는 절차도 함께 필요합니다.
- `allowedUsers.telegram`의 값 형식(`actorOf`가 만드는 actor와 같은 형식인지)은 원문이 없어 미확인입니다. S-1에서 확인하도록 넣습니다.

**S-4 [should_fix, 새 지적] 기동만 해도 외부 송신이 발생합니다.**
- `connect()`는 `setMyCommands` 호출과 General 알림("기기 … 연결됨")을 자동으로 보냅니다. 명령을 보내기 전에도 그룹으로 메시지가 나간다는 뜻입니다.
- 실제 전송 승인을 받을 때 이 자동 송신도 범위에 들어간다고 TASK에 적어야 합니다. S-5의 "송신 결과" 검사도 이 송신을 포함해야 합니다.
- "송신 결과"를 무엇으로 수집할지(계측 지점이 무엇인지)도 아직 정해지지 않았습니다.

**N-1 [note] 1단계 #1(S-3이 PACE 통로를 증명하지 못함)을 should_fix에서 note로 낮췄습니다.**
- 소스상 `/status`는 `host.overview()`만 쓰고 LLM이나 체인을 거치지 않습니다. 따라서 체인 왕복은 검증하지 못합니다.
- 그래도 BR02 완료 기준은 문자 그대로 "daemon이 응답"이고, 실제 읽기는 PROJECT P-4와 T04가 맡습니다. 그래서 범위상 결함은 아닙니다.
- 허용과 거절을 가르는 검출력도 있습니다. allowedUsers를 잘못 읽으면 S-3이 실패하고, 모두 허용하는 결함이면 S-4가 실패합니다.

**N-2 [note] 그룹 명령에서 `/status@봇이름`을 쓰는 경우를 확인해야 합니다.**
- 이 형식은 getMe로 봇 이름을 확인하지 못하면 무시됩니다(`ignored`).
- 허용 사용자 시험에서 응답이 없을 때 원인을 가를 수 있도록 S-3에 "@ 없이 보내기"나 getMe 확인을 넣습니다.
- 불허 사용자 시험은 `isAllowed` 판정이 mention 처리보다 먼저라서 영향이 없습니다.
- privacy mode 지적(1단계 #6)도 유지합니다.

**N-3 [note] 시크릿 저장 보호(1단계 #5)를 유지합니다.** PROJECT는 입력 경로만 정하고 있습니다. `writeTelegramSecret`이 파일 권한을 어떻게 다루는지는 원문이 없어 미확인입니다.

**N-4 [note] 추적성(1단계 #8)을 갱신했습니다.**
- 범위 제외 결정은 PROJECT의 캡틴 확인 사항과 T01 결정 메모로 추적됩니다.
- BR02 상태가 "대기"인데 T02는 "진행"이라 서로 맞지 않습니다. 문서 동기화가 필요합니다.
- S-6의 증거 재사용 기준이 흐리다는 지적(1단계 #7 후반)은 유지합니다.
