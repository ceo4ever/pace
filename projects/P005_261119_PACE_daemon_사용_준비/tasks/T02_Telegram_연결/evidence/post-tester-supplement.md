# P005 T02 독립 tester 보완 검토 (앞 판단 보존)

**판정: fail (보류).** 기능 결함 때문이 아닙니다. 저장소 전체 검사(`npm run check`) 결과를 아직 받지 못했기 때문입니다. B2는 해소됐고 T-1~T-3과 복원은 pass입니다. 전체 검사가 정상 종료로 확인되면 pass로 바꿀 수 있습니다.

## 받은 범위와 하지 않은 것
- **받은 자료:**
  - 추가 감사 소스: `execution-initial-stop.mjs`, `execution-deny-stop.mjs`, `execution-final-local-check.mjs`, `execution-record-scan.mjs`
  - 해시와 출처 기록: `local-check-source-provenance.json`, `record-scan-source-hash.json`, 갱신된 `execution-source-hashes.json`
  - 결과: `repository-sensitive-records-scan.json`, `security-check-result.json`, `security-check.log`, `post-review-resolution.md`
- **하지 않은 것:** 파일 열람, 소스·명령 실행, Telegram 실측 재실행, 파일 변경, 다른 세션 호출(advisor 포함)은 하지 않았습니다. 사용자·그룹·토큰 원문은 받지도 읽지도 않았습니다.
- **직접 검증하지 못한 것:**
  - 해시는 다시 계산하지 않았고, 원본과 결과 해시가 일치한다는 코디네이터의 대조를 그대로 받았습니다.
  - `instance.ts`, `bin/pace.ts`, `adapter.ts`의 본문은 받지 않았습니다.
  - 감사 사본이 원본과 공백 한 곳만 다르다는 주장은 원본을 직접 받지 않았으므로, 기록된 두 해시를 근거로 인정했습니다.

## B2 해소 여부: 해소 (한계 있음)

### 정지 증거 (initial-stop, deny-stop)
- 두 스크립트 모두 `acquireInstance`로 인스턴스를 잡고, status가 stopped인지, lock이 없는지 확인한 뒤 release합니다. 하나라도 어긋나면 throw하므로, 정지가 확인되지 않으면 결과 파일이 생기지 않습니다. 결과 파일 내용과도 맞습니다.
- 한계:
  - 두 스크립트는 각 런타임이 exit 0으로 끝났는지는 단언하지 않습니다. deny-stop은 상태 파일을 콘솔에 출력할 뿐입니다. 따라서 이 두 단계의 "정상 정지 exit 0"은 증거 파일이 아니라 기록 서술에만 근거합니다.
  - 정지 판정의 의미는 `instance.ts`에 달려 있는데, 이 모듈은 해시 고정 범위 밖입니다(F4에서 이미 인정된 한계).

### 최종 복원 (final-local-check)
- 다음을 차례로 단언합니다.
  - allow-restored 런타임이 stopped·exit 0으로 끝났는지
  - `live-allow-restored.json`이 passed인지
  - 인스턴스 정지와 lock 부재
  - config 해시가 setup 기준값과 같은지
  - 디스크의 허용 사용자가 입력값과 같은지
  - 모듈 다섯 개 재확인과 시크릿 파일 ACL
- `deviceDiskUntouched`는 상수로 기록되지만, config 해시가 같다는 단언이 그 의미를 대신 보장합니다.
- 복원은 pass입니다.

### 상태·로그 토큰 검사 (T-3)
- 검사 방식:
  - 파일 4개(status.json·daemon.log·state.json·telegram.json)는 UTF-8로 읽어 토큰과 정확히 일치하는지 봅니다.
  - PSReadLine ConsoleHost 기록도 같은 방식으로 봅니다.
  - 설치 CLI `status`(exit 3 기대)와 `logs`(exit 0 기대)의 stdout+stderr도 비교합니다.
  - 하나라도 일치하면 throw하고 증거를 저장하지 않습니다(fail-closed). BR02의 "`pace daemon logs`에 토큰 원문 없음"을 소스로 확인할 수 있습니다.
- 시각 정합성: 소스 수정 시각(10:50:05.232) 바로 뒤에 두 결과가 생성됐습니다(.714, 10:50:06.256). exit 3으로 고친 뒤 다시 실행했다는 서술과 맞습니다. exit 0만 허용하던 이전 버전의 원문은 사라졌지만, 현재 결과를 만든 것은 현재 소스입니다.
- 미검사 범위:
  - PowerShell 기록은 ConsoleHost 경로 하나만 봤습니다. VS Code 호스트나 Bash 기록은 보지 않았습니다.
  - 로그 회전 파일이 있다면 직접 검사하지 않았습니다. CLI `logs` 출력이 일부를 대신합니다.
  - 요청 URL, API 예외 객체, 메모리 덤프, 이벤트 로그는 보지 않았습니다. 이미 명시된 한계입니다.

### 기록 전체 비노출
- 검사 범위: T02 폴더 전체(하위 포함, 심볼릭 링크가 있으면 throw), PROJECT·log.jsonl, 프로젝트 메모리, 원본 백로그·BR02, 생성 대시보드 103개 파일입니다.
- 실제 입력 토큰·chat ID·사용자 ID 모두 일치 0건입니다.
- 한계:
  - chat ID는 입력 형식(`-` 접두) 그대로만 찾았습니다. `-100`을 뺀 변형 표기는 찾지 않았습니다.
  - 스캔 이후에 생긴 파일(이번 resolution 문서 등)은 범위 밖입니다. 문서에 적힌 대로 마감 전에 다시 돌려야 합니다.

### 선언 비밀 검사
- `node scripts/secret-scan.ts`가 exit 0으로 2,688개 파일을 통과했습니다.
- 앞선 두 번의 실패는 감사 사본의 코드 표현을 비밀로 오인한 경우였습니다. 공백만 추가해 넘겼고, 원본과 감사본의 해시를 각각 기록했습니다. 실제 값 비교는 0건이고 제외 목록이나 제품은 바꾸지 않았으므로 회피로 보지 않습니다.
- 원본과 감사본이 바이트 단위로 같다는 주장을 철회한 것도 적절합니다.

## 남은 blocking
- **B1. 저장소 전체 검사 결과 미수신.** 대기 상태일 뿐 기능 결함이 아닙니다. 결과가 정상 종료이고 새 실패가 없으면 해소됩니다.
- **B2.** 해소됐습니다.
- 이번 자료에서 새 기능 결함은 찾지 못했습니다.

## 마감 전 조건 (blocking 아님)
- 파일이 추가된 뒤 record-scan과 선언 비밀 검사를 다시 실행해야 합니다.
- T04로 넘길 것: 응답 토픽과 reply 대상, non-getUpdates 호출 전체의 메서드별 건수, 실제 다른 계정 거절. 필요하면 VS Code 호스트 셸 기록과 로그 회전 파일도 포함합니다.
