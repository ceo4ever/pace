# T02 Telegram 연결 TASK.md 사전 검토 (1단계 첫 판단)

## 노출 범위
- **읽은 파일:** `TASK.md` 하나. 작업 디렉터리에는 이 파일만 있었습니다.
- **열지 않은 문서:** 요청대로 PROJECT.md, BR02, BACKLOG는 열지 않았습니다. 그래서 P-2 원문과의 대조는 못 했습니다.
- **열지 않은 소스:** `src/daemon/cli.ts`, `adapter.ts`, 브레인 페이지도 열지 않았습니다. 재료 절에 적힌 코드 관련 내용은 확인하지 않은 주장으로 다뤘습니다.
- **자동 맥락:** SessionStart 훅이 "자식 세션, 부트 생략" 문구를 넣었습니다. 호스트가 사용자 계정 맥락을 붙였지만 검토에는 쓰지 않았습니다. 메모리 파일은 읽지 않았습니다.
- **받지 않은 것:** 작성자 마감, 자체 판정, 이전 지적과 그 대응 문서는 받지도 읽지도 않았습니다.
- **검토 주체:** 1단계는 이 세션(Claude, 새 맥락)이 맡았습니다. 2단계는 이 호출로 실행되지 않았습니다.

## 첫 판단
- **독립 목표 대조:** 상위 목적은 자리 밖에서 Telegram으로 이 PC의 PACE에 **조회와 작업**을 맡기고 결과를 받는 것입니다. 이 태스크의 목표는 보호된 토큰 입력과 허용 목록으로 연결을 준비하고, 허용·불허 요청 처리와 토큰 비노출을 실제로 검증하는 계획을 만드는 것입니다. TASK의 목적·기준(T-1~T-3)은 이 목표와 방향이 맞습니다. 작업 위임, 쓰기, 상시 기동을 T03 이후로 미룬 범위 구분도 타당합니다.
- **목표 달성:** **일부 미확인**입니다. 연결 구성(T-1)과 토큰 비노출(T-3) 계획은 이 목표를 이룰 만합니다. 다만 허용 요청 검증(S-3)이 `/status`에 그쳐서 PACE 본체까지 가는 통로를 증명하는지 확인되지 않습니다. 불허 검증(S-4)은 계측 방법을 실제로 쓸 수 있는지가 확인되지 않았습니다.
- **근거와 한계:** TASK 본문만 근거로 했습니다. `/status`가 어댑터나 daemon에서 바로 처리되는지, stats를 기존 경로로 볼 수 있는지는 코드를 보지 않아서 판단하지 못했습니다.
- **올릴 단계:** 테스트(S-3, S-4)와 접근(토큰 입력 방식, 복원 절차)입니다. 목적·목표 자체를 바꿀 필요는 없어서 사용자에게 물을 것은 없습니다.

## 지적

1. **[should_fix] S-3이 `/status` 응답만으로 "PACE에 메시지를 보내고 답을 받는 통로"를 증명한다고 보기 어렵습니다.** `/status`를 어댑터나 daemon의 명령 처리기가 직접 답한다면 PACE host나 체인으로 가는 메시지 경로는 검증되지 않습니다. 그 경로가 망가진 구현에서도 S-3은 통과합니다.
   - 고칠 방향(둘 중 하나):
     - 쓰기 없는 읽기 전용 일반 조회를 하나 추가해 실체인 왕복 응답을 관측합니다. T01에서 실체인 읽기는 이미 확인했습니다.
     - 체인 왕복은 T03 범위라고 TASK에 적고, T-2의 "응답"이 어느 계층의 응답인지 밝힙니다.

2. **[should_fix] S-4의 관찰 래퍼를 실제로 쓸 수 있는지 확인되지 않았고, 계측이 안 될 때 처리가 정해지지 않았습니다.**
   - 제품 코드를 바꾸지 않고 runDaemon 안의 같은 TelegramAdapter 인스턴스를 감싸려면 prototype을 덮어쓰거나 별도 launcher를 써야 합니다. 그러면 S-3("runDaemon 본체 사용")과 실행 경로가 달라질 수 있습니다. 감싸는 과정에서 동작이 바뀌지 않았다는 것도 따로 검증해야 합니다.
   - 계측이 안 되면 "미확인으로 보고"한다고 했는데, 그 경우 T-2가 미달이 되어 태스크를 닫을 수 없다는 점을 적어야 합니다.
   - 먼저 기존 status 출력이나 daemon 로그로 rejectedUsers를 볼 수 있는지 확인하고, 볼 수 없을 때만 래퍼를 쓰는 순서를 권합니다.
   - "작업 생성 없음"을 무엇으로 관측할지(작업 큐, 체인 호출 로그 등)도 정해져 있지 않습니다.

3. **[should_fix] 토큰 stdin 전달 방식이 정해지지 않아 셸 기록에 남을 위험이 있습니다.** "stdin 전달"을 `echo <token> | pace telegram init`처럼 하면 argv에는 안 들어가도 PowerShell PSReadLine 기록에 남습니다.
   - 대화형 숨김 입력(TTY에서 직접 입력, 또는 `Read-Host -AsSecureString` 같은 방식)만 허용하고, 명령줄 리터럴이나 파이프는 금지한다고 S-2 조건에 넣어야 합니다.
   - S-5 검사 대상에 셸 기록도 넣는 것을 권합니다.

4. **[should_fix] 불허 사용자 대체 절차와 실패 시 원상복구 검증이 빠졌습니다.**
   - 허용 사용자를 임시로 빼는 대체 절차를 쓰면, 복원 단계와 복원 뒤 다시 허용되는지 확인하는 단계가 테스트 표에 있어야 합니다.
   - S-2나 S-3이 실패했을 때 시크릿과 config를 되돌리는 절차, 제한 기동 뒤 프로세스 정지를 확인하는 절차도 없습니다.

5. **[note] "보호된 토큰 입력"에서 저장 단계 보호가 기준에 없습니다.** 저장된 시크릿 파일의 위치가 저장소 밖인지, 파일 권한(ACL)이 적절한지는 T-1이나 T-3에 넣을 만합니다. P-2가 이를 요구하는지는 PROJECT를 보지 않아 확인하지 못했습니다.

6. **[note] 봇 privacy mode 확인이 빠졌습니다.** 포럼 그룹에서 privacy mode가 켜져 있으면 봇은 명령만 받습니다. 지금 `/status` 시험에는 문제가 없지만, 상위 목적인 일반 메시지 작업 위임을 위해 S-1의 준비 확인 항목에 넣는 것을 권합니다.

7. **[note] 범위 경계가 일부 모호합니다.**
   - "설치 마법사의 숨김 입력"을 허용했는데, 마법사가 `--yes` 없이도 로그온 등록 단계로 넘어가는지 S-1에서 확인한다고 적어 두는 것이 좋습니다.
   - S-6의 "T01 증거 재사용 가능성 판단"은 무엇을 재사용할 수 있는지 기준이 흐립니다.

8. **[note] 결정 추적은 대체로 됩니다.**
   - 기준마다 P-2가 연결되어 있습니다.
   - 금지 항목에는 재료 근거가 있습니다. `install --yes` 금지는 cli.ts 근거에, 무응답만으로 통과 금지는 adapter.ts 근거에, webhook·offset 자동 해제 금지는 브레인 근거에 연결됩니다.
   - 범위 밖으로 둔 workspace, 쓰기, maxConcurrent 변경이 어느 상위 결정에서 나왔는지는 PROJECT를 보지 않아 확인하지 못했습니다.
