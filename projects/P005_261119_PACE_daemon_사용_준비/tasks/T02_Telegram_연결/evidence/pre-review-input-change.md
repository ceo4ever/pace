# T02 Telegram 연결 TASK 변경분 재검토 3회차 (캡틴 승인 반영)

새 blocking은 없어 판정은 pass입니다. 다만 단계 사이에 들어온 메시지와 응답을 해당 시험 요청과 구분하는 방법이 아직 계획에 없습니다. 이것이 거짓 거절·허용 증거로 이어질 수 있어 실제 전송 전에 고칠 것을 권합니다(C-1).

## 받은 범위와 continuity
- **이번 턴:** 호출 메시지에 붙은 수정 TASK 원문만 봤습니다. `.env`, 운영 config, 시크릿, 소스 파일은 열지 않았고 파일 변경과 보조 호출도 하지 않았습니다. 민감정보는 출력하지 않습니다.
- **근거로 쓴 앞 턴 자료:** 최초 `TASK.md`, PROJECT, BR02, 소스 발췌, 그리고 1차 fail, 2회차 pass 판정입니다.
- **원문 없이 판단한 부분:** `runDaemon`이 config 객체를 받는지, stop-request 처리 방식, 단일 인스턴스 잠금, offset 저장 방식은 원문이 없어 **미확인**입니다.
- **자동 맥락:** 앞 턴과 같습니다. SessionStart 훅 문구와 호스트가 붙인 계정 맥락이 있었고, 검토에는 쓰지 않았습니다.
- **continuity:** 같은 세션, 같은 제공자(Claude, Opus 5.5)의 4번째 검토 호출입니다. 이전 판정을 기억한 채 보므로 이전 단계와 독립적이지 않습니다. 검토 주체는 바뀌지 않았습니다.
- **미실행:** 캡틴 승인 내용, `.env` ACL·형식 확인 결과, "Bot API·기동 미실행"이라는 서술은 전달받은 주장일 뿐이고 직접 확인하지 않았습니다. Telegram 연결·전송·기동·거절 관측의 실제 결과도 모두 미실행입니다.

## 직전 pass와의 차이
1. **입력 출처:** SecureString 입력 대신 캡틴이 지정한 저장소 밖 ACL 제한 `.env`를 메모리로 읽어 CLI stdin으로 넘깁니다.
2. **설정 처리:** device 별칭은 운영 config에 쓰지 않고, 기동용 config 메모리 사본에만 씁니다. 운영 config에는 allowedUsers만 병합하고 설치본 로더로 검증합니다.
3. **불허 시험:** 디스크의 허용 목록을 바꿨다 되돌리는 방식 대신, 메모리 사본의 허용 목록만 비웁니다. 각 단계에서 운영 config 해시가 같은지 확인합니다.
4. **실행 통제:** 각 시험은 별도 Node 프로세스이고 10분 기한, 소유 PID 확인 뒤 정상 정지, 독립 감독 프로세스를 둡니다. 각 단계 시작 전에 main·캡틴과 전송 시점을 맞춥니다.
5. **실패 규칙:** API call 관측이 실패하면 T-3 미확인, 거절 계측이 실패하면 T-2 미달입니다.

## 판정

**입력 보호: 기준과 승인 범위에 맞습니다.**
- 토큰은 BR02·PROJECT가 정한 대로 `telegram init` stdin으로 들어갑니다. 원래 출처가 평문 `.env`인 것은 캡틴의 결정이고 저장소 밖에 있습니다.
- argv, 환경변수, 중계 파일은 금지되어 있습니다.

**운영 권한 유지(런타임 config 사본): 방향이 좋습니다.**
- 운영 허용 목록과 device는 디스크에서 한 번도 바뀌지 않습니다. 강제 종료돼도 임시 권한이 디스크에 남지 않습니다. 이전 S-4r의 복원 실패 위험이 구조적으로 사라졌습니다.
- 불허 단계에서 사본 주입이 안 먹히면 거절 통계가 오르지 않습니다. 이 경우 시험은 실패로 드러나므로 거짓 통과로 이어지지는 않습니다.

**종료·재기동: 기한, 감독, 소유 PID 정지, 기존 daemon 비접촉이 갖춰져 있습니다.** 실행 방식은 충분합니다.

**관측 타이밍: 보완이 필요합니다(C-1).**

## 지적

**C-1 [should_fix] 단계 사이에 들어온 update를 해당 시험 요청과 구분하는 방법이 없습니다.**
- 정지 중이나 준비 전에 보낸 메시지는 다음 기동의 첫 getUpdates에서 처리됩니다.
- offset이 저장되지 않는다면 이전 단계에서 처리한 update도 다시 들어옵니다.
- 소스상 `isAllowed` 판정이 메시지 나이 검사보다 먼저입니다. 그래서 오래된 메시지도 불허 단계에서는 `rejectedUsers`를 올립니다. 복원 단계에서는 오래된 메시지에도 "너무 오래된 메시지" 응답이 나갑니다.
- 그 결과 거절 증거나 허용 응답 증거가 엉뚱한 메시지에서 생길 수 있습니다.
- "준비 전 메시지를 시험 요청으로 추정하지 않는다"는 의도는 적혀 있지만 방법이 없습니다.
- **고칠 방향:**
  - 기동 뒤 첫 polling 결과를 call 래퍼로 확인하고, 밀린 update를 다 처리한 다음에 통계 기준값을 잡습니다. 그 뒤에 "준비"를 알립니다.
  - 판정은 준비 시각 이후의 증가분만 봅니다. 기대값은 정확히 1건입니다.
  - 응답은 해당 요청에 대한 /status 응답인지 메모리에서만 대조합니다. ID와 본문은 기록하지 않습니다.

**C-2 [should_fix] config 사본을 runDaemon에 넣을 수 있는지와, 안 될 때 처리가 정해지지 않았습니다.**
- `runDaemon`이 config 객체를 받는지 원문이 없어 미확인입니다.
- 받지 못하면 로더를 덮어써야 하는데, 이는 "동작 변경 없음" 원칙에 어긋납니다. 디스크 방식으로 돌아가는 길은 승인 반영 절에서 대체됐습니다.
- device 덮어쓰기가 무시되면 `connect()`가 호출되는 순간 실제 기기 이름이 그룹으로 나갑니다. 이 알림은 되돌릴 수 없습니다.
- **고칠 방향:**
  - S-1에서 소스로 주입 경로를 확인하고, 그 사본이 어댑터의 `host.device`까지 전달되는지 확인합니다.
  - 확인이 안 되면 기동하지 않고 질문한다고 명시합니다.
  - "정상 config 사본"은 운영 파일을 설치본 로더로 읽은 결과에 device만 덮어쓴 것임을 적습니다.

**C-3 [should_fix] 대체된 옛 서술이 본문에 그대로 남아 있습니다.**
- 남아 있는 서술은 SecureString 입력 문단, "별칭을 별도 승인받아 설정", S-1의 "device 표기 확정", 그리고 접근 절의 "finally에서 원래 허용 목록을 원자적으로 복원"·"원래 바이트로 복원"입니다.
- 승인 반영 절이 우선한다는 문장은 있습니다. 그래도 실행자가 디스크를 쓰는 옛 절차를 따를 여지가 있어 정리하는 것이 좋습니다.
- 머리말 "사전 검토: v1"도 그대로입니다(이전 R-5).

**C-4 [note] `.env` 사용 후 처리가 정해지지 않았습니다.** 시크릿 파일이 저장된 뒤에도 같은 토큰의 평문 사본이 남습니다. 보존할지 폐기할지를 캡틴 결정으로 기록하는 것을 권합니다. 에이전트가 임의로 지우지는 않습니다.

**C-5 [note] 별도 Node 실행기가 운영 홈에 쓰는 것과 잠금을 확인해야 합니다.**
- 실행기는 운영 홈에 status, logs, Telegram state를 씁니다. 승인된 제한 기동 범위로 볼 수 있습니다.
- 다만 `runDaemon`을 직접 부를 때도 단일 인스턴스 잠금이 걸리는지 확인해야 합니다. 시험 중 `pace daemon start`가 함께 실행되면 poller가 중복될 수 있습니다.
- getChat, getWebhookInfo 호출이 캡틴 승인 문구("Telegram 연결")에 들어가는지 명시하는 것을 권합니다.

## 목표 정합
- 목적과 T-1~T-3은 그대로입니다.
- 실행 범위는 캡틴 승인 범위 안에 있습니다. 승인 범위는 연결, 메뉴, 연결·재기동 알림, /status, 임시 제외·복원입니다. 워크스페이스, 작업 실행, 상시 기동, Windows 등록은 제외되어 있습니다.
- 실제 결과는 미실행이라 목표 달성 여부는 **미확인**입니다.
- C-1과 C-2는 승인이나 기준을 이미 어긴 것이 아니고 아직 확인되지 않은 위험이라 should_fix로 분류했습니다. 다만 C-1을 고치지 않으면 T-2 증거가 실제로 무효가 될 수 있습니다.
