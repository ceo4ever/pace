# P005 T04 TASK 사전 검토 v1: 2단계 대조 판단

**판정: pass. blocking 0건, non-blocking 6건.** 1단계 판단(pass, blocking 0)은 그대로 둡니다.

**검토한 범위:** 1단계 TASK에 더해 PROJECT, BR04, 그리고 받은 소스 발췌만 봤습니다. 발췌는 `adapter.ts`의 수신·미등록 토픽·등록 토픽 처리, `core.ts`의 recoverLocked·verifyQuarantines·정지·decideLocked·expireApprovalLocked, `runner.ts` 주석, `index.ts`의 defaultReap입니다. 발췌 밖의 코드는 보지 않았습니다. 확인하지 못한 것은 sweeper, 정지 뒤 running 처리 끝부분, 콜백 응답 문구, release CLI, 런처입니다. 파일 변경, 명령, 도구, 보조 호출은 하지 않았고, 운영 실측도 하지 않았습니다.

## 목표 정합
PROJECT P-4와 BR04 완료 기준(읽기·쓰기 각 1회 성공, 재시작 뒤 승인 무효, needs_review, 막힌 곳 처리)이 T-1~T-5에 빠짐없이 대응합니다. TASK에 기준을 더 넣을 필요는 없습니다.

## 주제별 대조

**1. 개인정보보호 모드에서 그룹 메시지가 봇에 전달되는지: 실현 가능, 형식 명시 필요**
- 어댑터는 텍스트 메시지만 처리합니다. 허용 사용자가 아니면 아무 응답도 하지 않습니다.
- `/cmd@봇명`은 이 봇을 가리킬 때만 `@봇명`을 떼고 처리하고, 다른 봇을 가리키면 무시합니다.
- 슬래시로 시작하지 않는 일반 텍스트는 그대로 LLM 요청으로 전달됩니다. 그래서 "@봇명 …" 멘션 문장이나 봇 메시지에 대한 답장으로 보낸 읽기·쓰기 요청은 Telegram이 전달만 해 주면 처리됩니다. 앞의 `@봇명`이 프롬프트에 섞이는 것은 해가 없습니다.
- 승인·거절 버튼(callback_query)은 개인정보보호 모드와 상관없이 전달됩니다.
- **non-blocking:** `/bind@봇명 <이름>`, `/write@봇명`, `/read@봇명`, 그리고 "멘션 또는 봇 메시지에 대한 답장" 형식을 S-2와 S-3에 적어 두기를 권합니다. 1단계 권고 3을 구체화한 것입니다.

**2. 기존 토픽 bind와 실제 체인: 계획과 소스가 일치**
- `/bind`는 등록된 workspace인지, 다른 토픽에 이미 결속됐는지만 확인합니다. createForumTopic이나 관리자 권한이 필요 없습니다.
- 결속된 토픽의 텍스트는 `sink.message`를 거쳐 runner 체인으로 갑니다. `/write`는 `/access write`, `/read`는 `/access read-only`로 바뀝니다.
- 토픽 ID 1은 General로 처리되므로, 검증 토픽은 캡틴이 새로 만든 토픽이어야 합니다. 계획과 맞습니다.

**3. 정상 정지와 새 boot에서의 승인 무효 구분: 계획이 정확함, 1단계 권고 1 해소**
- 정상 정지는 pending 상태의 write_start 승인을 invalidated로, 작업을 expired로 바꿉니다. 이때 note가 "daemon 정지로 승인 대기가 만료됨"이라서 TTL 만료의 "승인 기한 초과"와 구별됩니다.
- 재기동 뒤 이전 버튼을 누르면, decideLocked가 상태 검사보다 bootId 검사를 먼저 하므로 항상 "이전 기동에서 발급된 승인"으로 거부됩니다.
- 따라서 두 경로를 사유 문자열과 note로 구분할 수 있습니다. 승인 요청자와 같은 대화·같은 사용자만 결정할 수 있다는 조건도 S-3의 "같은 사용자/대화"와 맞습니다.
- TTL이 지난 뒤 누른 버튼은 "이미 처리됨(expired)"으로 거부됩니다. S-4e와 맞습니다.

**4. running 쓰기 중단, 실행기 소유 증명, 격리와 release: 기대 결과는 맞음, 실행 세부 보완 필요**
- 비정상 종료 뒤 재기동하면 recoverLocked가 격리를 먼저 저장하고, 작업을 needs_review로 바꾸고, 자동 재실행하지 않는다고 알립니다. 이 시점에 남은 pending 승인도 모두 invalidated로 바뀝니다.
- runner가 `onProcess`를 호출하지 않으므로 `task.procs`가 비어 있습니다. 그리고 win32에서는 defaultReap이 항상 unconfirmed를 돌려줍니다. 결국 격리는 자동으로 풀리지 않고 반드시 수동 release가 필요합니다. 계획의 기대와 맞습니다.
- 제품이 PID를 기록하지 않으므로, 강제 종료 전에 OS 프로세스 트리에서 PID, 시작 시각, 명령을 고정해 두는 계획의 방식이 유일한 증명 수단입니다. 타당합니다.
- **non-blocking ①:** Windows Job Object가 daemon 종료와 함께 자손을 이미 정리했을 수 있습니다. 이 경우 "고정해 둔 PID+시작시각의 프로세스가 없음"을 회수 증명으로 인정한다는 분기를 S-5에 적기를 권합니다. 지금 문안은 살아 있는 자손이 있다는 전제입니다.
- **non-blocking ②:** T03 Run 런처나 감시 구성이 비정상 종료 뒤 daemon을 자동으로 다시 띄우지 않는지 사전에 확인하기를 권합니다. 자동 재기동이 끼면 "정상 재기동"이라는 통제된 순서가 깨집니다.
- **non-blocking ③:** release CLI가 실제로 있는지, 그리고 release가 needs_review 상태를 바꾸지 않는지를 S-5q 사전 확인에 넣기를 권합니다. 발췌에는 해당 코드가 없습니다.
- **non-blocking ④:** 강제 종료는 정상 stop이 아니라 프로세스 강제 종료여야 합니다. 정상 stop은 running 작업을 다르게 처리할 수 있지만 그 부분 코드는 받지 않았습니다. 이 점을 명시하기를 권합니다.

**5. 시험 뒤 승인 상태 복원: 타당**
- `/write` 설정은 토픽 대화에 계속 남는 접근 설정입니다. 쓰기 시험이 끝나면 `/read@봇명`으로 read-only로 되돌리고, 상태 확인으로 기록하라고 S-3 또는 S-6에 적기를 권합니다. 1단계 권고 5를 구체화한 것입니다.
- **non-blocking:** 회수를 증명하지 못하면 검증용 작업사본의 격리가 계속 남습니다. 이것을 허용되는 최종 상태로 볼지 캡틴에게 확인받는 항목에 넣기를 권합니다. 이 작업사본에서는 이후 쓰기가 막히기 때문입니다.

## 1단계 대비 변경 근거
- **권고 1(S-4r 판별력):** bootId 검사가 먼저 실행되고 사유 문자열과 note가 다르다는 것을 소스에서 확인해 해소했습니다.
- **권고 3(요청 수신 경로)과 권고 5(정책 복원 시점):** 어댑터의 멘션 처리와 `/write`·`/read` 변환에 맞춰 구체화했습니다.
- **권고 2(미실측 처리)와 권고 4(TTL 값, 전체 검사 명령):** 그대로 유지합니다.
- **새로 추가:** 4번의 ①~④와 5번의 격리 최종 상태 확인입니다. 모두 non-blocking이며, 합격 기준을 새로 만들지 않고 기존 S-5, S-5q, S-6의 실행 세부를 보완하는 내용입니다.
