# T04 사전 검토 v3 반복 실패 진단 (2026-11-23)

P007 하네스(reviewer.md "반복 실패: 진단과 사용자 결정") 기준. v3 검토 11회(pre-review-3 ~ 3k)는 새 검토 원장 도입 전이라 `REVIEW-LOG.jsonl`에 없다 — 도구 단계 대신 이 문서로 진단을 남기고, **이 진단 뒤 첫 검토가 fail이면 사용자 결정**으로 올린다(원장이 비어 있어도 같은 규칙을 PM이 지킨다).

## 실패 모음

| 영역 | 검토 | 지적 요지 |
|---|---|---|
| 첫 기동 안전 | 3e·3f | offset 전진·60초 관찰만으로 묵은 업데이트 소진을 증명 못 함 |
| | 3g·3h | launchd 서비스 환경의 실행기 PATH 미확인 |
| | 3k#1 | 설정 기준점이 첫 폴링보다 늦음 |
| 실패 정리 분기 | 3f#2 | S-0s 중단과 공통 정리의 충돌 |
| | 3g#2 | daemon이 내려간 뒤 `/read` 복원 불가 |
| | 3h(should_fix) | 재기동 전후 관측 구분 |
| | 3i | 정상 종료·승인 대기 상태에서 정리가 끝나지 않음 |
| | 3j#1·#2 | S-0s 이상 뒤 재기동, 읽기 중단의 회수·격리 누락 |
| 종료 상태 판정 | 3k#2 | `/status`로 접근 모드 복원을 판정 못 함 |

매 회 reviewer는 목표 정합(P-4·BR04)과 정상 경로 T-1~T-4의 검출력은 **추적된다**고 판정했다. 지적은 전부 실패·예외 경로와 그 정리 절차에 있다.

## 원인 층: 설계

- 구조(도구·게이트) 문제가 아니다 — 검토는 매번 다른 실제 분기를 찾았고 근거(코드 줄)가 정확했다.
- 기획(목적·범위) 문제가 아니다 — 목표 정합은 매 회 일치.
- **설계 문제다**: 사람이 한 단계씩 진행하는 실사용 시험의 안전을, 가능한 실패 분기마다 자동 정리 절차를 글로 미리 열거해서 확보하려 했다. 분기 공간(어느 단계 × daemon 상태 × 작업 상태 × 결속 여부)은 열거로 닫히지 않아 수정할 때마다 새 분기가 드러났다. 땜질 흔적: 정리 경로가 v3 동안 1문단 → 예외 문단 + 4단계 분기로 커졌다.

## 그 층에서 고치는 방법

1. **정리 분기 열거를 불변 규칙 하나로 바꾼다** — 계획에 없는 관측·실패가 나오면: 더 진행하지 않고 daemon을 그 상태 그대로 두거나(내려갔으면 내려간 채) `pace daemon stop`만 하고, 설정·state.json·프로세스를 **읽기만** 해서 캡틴에게 보고한다. 재기동·취소·등록 해제·release 같은 복구 행동은 캡틴이 그 보고를 보고 정한다. 계획에 미리 적는 정리는 **알려진 정상 상태에서 시작하는 종료 절차(S-6) 하나**뿐이다.
2. **첫 기동 안전은 관측 근거 대신 기준 대조 하나로**: S-0s는 설치가 의도한 키별 값과의 대조, 서비스 PID 환경의 명령 해석, 60초 동안 작업 0이면 통과. 어긋나면 1번 규칙. 묵은 업데이트 부재는 캡틴 확인(S-0 조건)과 이 대조로 판정하고, 증명 불가한 부분은 제약으로 남긴다.
3. **종료 상태 판정은 파일 판독으로**: 접근 모드는 state.json의 그 대화 값, workspace는 config·로더 판독, 기동은 새 boot·서비스 PID. Telegram 응답은 보조(전달 확인)로만 쓴다.

범위·기준(T-1~T-5)과 사용자 결정은 바꾸지 않는다. "운영 복원"(T-5)은 실패 시 캡틴이 정한 복구 결과까지 포함해 TASK-CLOSE에 기록한다.
