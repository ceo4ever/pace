# P005 T04 TASK 사전 검토 v1: 첫 판단

**판정: pass. blocking 0건, non-blocking 5건**

**검토한 범위:** 받은 T04 TASK 본문만 봤습니다. PROJECT, BR04, 소스, T02/T03 문서는 열지 않았습니다. 파일 변경, 명령, 도구, 보조 호출은 하지 않았습니다. 재료 절에 적힌 코드 동작(core.ts, runner.ts, adapter.ts)은 TASK의 서술을 사실로 두고 판단했습니다. 그 서술이 실제 소스와 맞는지는 확인하지 않았습니다.

## 1. 목표 정합: 충족
- T-1과 T-2가 Telegram 요청이 실제 LLM 실행기를 거쳐 읽기와 승인된 쓰기로 끝나고, 사용자가 결과를 받는지 확인합니다. 상위 목적인 "자리 밖에서 작업을 맡기고 결과 받기"의 핵심과 맞습니다.
- /status, 모사 실행기, Gateway 주입, state.json 편집으로 성공을 대신하는 것을 명시적으로 금지합니다.
- T-3과 T-4가 거절, 만료, 재기동 뒤 이전 승인, 실행 중 쓰기 중단 복구를 하나씩 별도 기준으로 다룹니다. P-4 범위와 맞습니다.
- 동시 모델 두 작업 부하 시험을 뺀 것도 이유가 적혀 있어 타당합니다.

## 2. 계획 실현 가능성: 가능
- 봇을 관리자로 올리거나 createForumTopic을 쓰지 않고, 캡틴이 만든 토픽에서 /bind하는 방식이라 현재 권한으로 실행할 수 있습니다.
- 순서가 맞습니다. 만료(S-4e)를 본 뒤에 재기동 무효화(S-4r)를 하고, 격리를 남기는 S-5를 마지막에 둡니다.
- 쓰기가 너무 빨리 끝나거나 자식 프로세스 소유를 확인할 수 없을 때는 "미실측으로 보고"하는 탈출 경로가 있습니다.
- 만료 대기 약 600초 동안 전체 검사를 함께 돌려 시간을 효율적으로 씁니다.

## 3. 안전성과 검출력: 충분
- 쓰기는 합성 fixture 파일에만 합니다. 기준 Git HEAD, index, 파일 바이트를 보존하고, 운영 source checkout에는 쓰지 않습니다.
- 기존 폴더를 덮어쓰지 않고, config는 해당 항목만 원자적으로 병합합니다.
- 프로세스는 PID, 시작 시각, 명령과 계보로 소유를 확인한 뒤에만 회수하고, 다른 프로세스는 건드리지 않습니다.
- 회수를 증명하기 전에는 release하지 않고, needs_review를 done으로 바꾸지 않습니다.
- 기대 답을 파일에만 두고 요청에는 넣지 않아, 실제로 파일을 읽었는지 검출할 수 있습니다.
- 비밀과 식별자를 내보내지 않고, 별칭·boolean·건수·해시만 남깁니다.

## Non-blocking 보완 권고
1. **S-4r 판별력:** 정상 정지만으로 pending이 이미 무효화되면, 이전 버튼 거부가 "이전 boot 승인 거부" 때문인지 "이미 만료된 상태" 때문인지 구분되지 않습니다. 어느 쪽이어도 실행이 막히면 T-3 pass로 볼지 정하고, 어느 경로였는지 상태와 사유로 기록하라고 명시하기를 권합니다.
2. **S-5 미실측 처리:** 실행이 먼저 끝나 중단 시험을 못 하면 T-4를 fail로 볼지, 보류로 두고 후속 판단을 받을지 미리 정해 두면 판정 분쟁을 줄일 수 있습니다. 재시도 횟수 상한도 함께 정하기를 권합니다.
3. **S-3 요청 수신 경로:** 봇이 일반 멤버라 privacy 모드라면 멘션, 명령, 답장만 받을 수 있습니다. S-2처럼 /write 전환 뒤 쓰기 요청도 봇명 멘션이나 명령 형식으로 보낸다고 적기를 권합니다.
4. **값 확정:** 실제 TTL을 config에서 확인해 기록하기를 권합니다. TASK에는 "약600초"로만 적혀 있습니다. S-6의 "태스크 전체 검사"가 정확히 어떤 명령인지도 적어 두면 좋습니다.
5. **정책 복원 시점:** 쓰기 시험 뒤 해당 토픽을 다시 read-only로 되돌리는 시점을 S-3 또는 S-6 단계에 명시하기를 권합니다. 지금은 T-5의 "승인 정책 복원"으로만 적혀 있습니다.
