# T04 다른 PC 인계

P005는 진행 중이다. T01 에이전트 체인, T02 Telegram 연결, T03 로그인 자동 시작은 각 태스크의 마감 문서와 증거에 기록돼 있다. T04는 독립 사전 검토를 통과했고 캡틴이 전체 복구 시험을 승인했다.

## 여기까지 확인한 결과

- 기존 Telegram 그룹의 검증 토픽에서 `pace-p005-t04` 결속 성공 응답을 캡틴이 확인했다. 이 PC에서도 General 이외 토픽 하나에 해당 이름이 결속된 것을 확인했다. [결속 및 관측 준비](evidence/read-observer-ready.json)
- 캡틴에게 결속 성공 메시지에 답장해 `fixture.txt` 원문을 읽는 시험을 안내했다. 11월 22일 12:13 KST 관측 기한까지 새 작업이나 Telegram offset 진전이 없었다. 인계 직전에도 마지막 수신은 11:42 KST였고, 작업과 승인 기록은 0건이었다. 캡틴의 발송 여부와 응답 수신은 미확인이다. [마지막 읽기 관측](evidence/read-observation.json) · [관측 기한](evidence/read-observer-timeout.json)
- 이 PC의 설치본 daemon을 활성 작업과 대기 승인 없이 정상 종료했다. 종료 뒤 설치본 daemon 프로세스가 없고 로그인 자동 시작 항목은 그대로다. 합성 Git 작업사본은 깨끗하며 기준 파일 해시가 일치한다. 작업공간 등록과 결속은 이 PC에 남아 있다. [종료 및 인계 상태](evidence/handoff-state.json)

## 새 PC에서 이어가기

1. 새 PC의 설치본과 default 실행기 체인, Telegram 연결과 허용 사용자, daemon 소유권, 기본 읽기 전용 정책과 승인 TTL을 확인한다. 토큰은 기존 승인 방식의 보호된 로컬 입력으로 설정한다. 이 PC의 설정, 시크릿, 토픽 결속 및 수신 offset, 승인·작업 상태는 로컬 데이터다. 새 PC에서 같은 봇이 수신하는 동안 이 PC 로그인으로 자동 실행되는 경우까지 포함해 동시에 두 poller가 동작하지 않게 한다.
2. 새 PC에 별도 비민감 Git 작업사본을 준비하고, 예상값이 요청에 들어가지 않도록 새 합성 읽기 표식을 만든다. 이전 토픽은 같은 그룹·봇·허용 사용자와 검증 토픽임을 확인하고, 그 토픽의 결속이 새 PC에서 등록한 작업공간을 가리킬 때 재사용한다. 결속이 없으면 캡틴이 기존 검증 토픽에서 `/bind@<봇이름> pace-p005-t04`를 실행한다.
3. 관측을 준비한 다음 먼저 캡틴에게 기존 읽기 요청을 실제로 보냈는지와 응답을 받았는지 확인한다. 이미 보냈으면 새 요청 전에 확인 가능한 응답과 상태를 대조한다. 읽기 근거가 없고 중복 실행 우려가 해소되면, 캡틴이 결속 성공 봇 메시지에 답장해 `fixture.txt 파일을 읽고 파일 내용만 그대로 답해 주세요. 파일은 변경하지 마세요.`를 보낸다. 캡틴의 응답 수신 확인과 로컬의 실행 결과·파일 무변경을 대조한다.
4. 읽기가 성공하면 [TASK.md](TASK.md)의 S-3부터 이어간다. 승인된 실제 쓰기, 거절, 실제 TTL 만료 및 늦은 승인 거부, 재기동 전 승인 무효와 재사용 거부, 실행 중 쓰기 강제 중단 후 `needs_review`·격리·자동 재실행 부재가 남았다. 실행기 소유 확인과 회수·파일 검토 뒤 별도 승인으로만 격리를 해제한다. 시험 뒤 읽기 전용과 정상 운영을 확인하고 승인된 시험 등록만 해제한다. 이 PC에 남은 시험 등록도 정리 대상이며, 파일·Git·토픽·메시지는 보존한다.
5. T04 마감 검사와 독립 판정, 프로젝트 finish는 실측 완료 뒤 진행한다. T03의 실제 Windows 재로그인 자동 기동과 콘솔 비표시 확인은 병합 후 인수 항목이다.
