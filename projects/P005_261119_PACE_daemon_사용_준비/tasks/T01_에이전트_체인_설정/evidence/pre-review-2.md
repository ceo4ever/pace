## 이전 blocking: 해소됨
이전 지적은 "Windows unelevated 수정이 들어간 실행 파일인지, 그리고 시험과 운영의 실행 파일이 같은지 확인하지 않는다"였습니다. 수정 TASK에서 해소된 근거는 다음과 같습니다.
- **같은 실행 파일:** 시험 대상과 운영 대상을 같은 설치본 `pace.ts`(0.1.1)로 못박았습니다. worktree 소스 CLI는 기록과 하네스에만 쓴다고 분리했습니다. 이것으로 시험한 것과 운영할 것이 같은 파일이 됩니다.
- **수정 포함 확인:** S-0에서 세 가지를 실측하고, 실제로 시험한 모듈의 해시를 남깁니다.
  - f385e03b가 v0.1.1의 조상인지(git ancestry)
  - main과 설치본의 p-executor SHA-256이 같은지
  - 설치본에 `windows.sandbox=unelevated`가 있는지
- **불일치 시 처리:** 설치하지 않고 코디네이터에 보고합니다. 접근 절에는 "수정 미반영이면 그 실행기의 운영 활성화를 멈추고 제외 여부를 질문한다"는 처리도 있습니다.
- **남은 경계:** daemon 로그온 환경에서도 같은 실행 파일과 PATH가 쓰이는지는 T03·T04로 넘겼다고 명시되어 있습니다. 1차 handoff와 일치합니다.

## 수정이 만든 새 지적

1. **[should_fix] S-3p 양성 대조군이 사용자 전역 상태를 바꿀 수 있습니다.** S-3p는 "S-3과 같은 합성 프롬프트"를 쓰기 허용 모드로 실행합니다. 그런데 S-3 요구 목록에 `git config`와 폴더 밖 절대 경로 쓰기가 있습니다. 쓰기가 허용된 에이전트가 이를 `git config --global`이나 사용자 홈 경로로 해석하면, 실제 사용자 설정이 바뀝니다. "임시 시험 경로만 허용"은 의도일 뿐 강제 수단이 아닙니다. 다음을 넣어야 합니다.
   - 프롬프트에서 git config 대상을 격리 저장소의 `--local`로, 쓰기 경로를 미리 만든 합성 절대 경로로 명시
   - 사용자 전역 git 설정 파일의 해시(내용은 읽지 않고)와 시험 경로 밖 쓰기 여부를 S-3p 전후로 비교하는 검사

   이 문제는 격리 시험 안의 위험이고 운영 결정과는 무관합니다. 실제 피해 가능성이 작고 미리 정해 두면 막을 수 있어서 blocking이 아니라 should_fix로 둡니다.

2. **[should_fix] S-0의 기대 결과 "main과 설치본 모듈 동일"이 과하게 엄격합니다.** 목표는 "수정이 들어 있고, 시험한 모듈과 운영 모듈이 같다"입니다. main은 나중에 바뀔 수 있어서, 수정이 들어 있는데도 해시가 달라 S-0이 실패할 수 있습니다. 이렇게 잘못 실패해도 코디네이터 보고로 끝나므로 안전성 문제는 아닙니다. 기대 결과를 다음 두 가지로 고치면 진짜 동일성 기준이 됩니다.
   - f385e03b 포함, 설치본에 unelevated 옵션 있음
   - S-0에서 기록한 해시와 S-2·S-3 실행 시, S-4 반영 시의 설치본 해시가 같음

   지금은 같은지 비교하는 단계가 없습니다.

3. **[note] 검토 이력 문구.** 접근 절의 "별도 세션의 첫 판단과 PROJECT·BR01 대조를 제공했다"는 1·2단계가 서로 다른 세션이었다고 읽힐 수 있습니다. 실제로는 작업자와 분리된 같은 검토 세션에서 1단계를 먼저 하고, 1단계를 알고서 2단계를 진행했습니다. 그대로 기록하기를 권합니다. 머리말의 "사전 검토: v1"도 2회차를 반영하지 않았습니다.

4. **[note] 경로 표기.** 재료에 설치본의 절대 경로가 적혀 있고, 그 안에 로컬 사용자 폴더 이름이 들어 있습니다. 증거에서 사용자 식별자를 빼라는 PROJECT 원칙에 맞추려면 `%USERPROFILE%` 기준의 상대 표기가 낫습니다.
