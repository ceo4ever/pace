# T01 TASK.md 구현 전 사전 검토 (1단계 첫 판단)

## 노출 범위와 독립성
- **읽은 파일:** 작업 폴더의 `TASK.md` 하나뿐입니다. 폴더 목록을 확인했을 때도 이 파일만 있었습니다.
- **열지 못한 문서:** TASK가 링크한 PROJECT.md(P-1·운영 선택·민감 경로), BACKLOG, BR01은 이 폴더 밖이라 열지 않았습니다. 그래서 P-1과 일치하는지는 TASK 본문에 쓰인 범위에서만 판단했습니다. `src/agent/*`, AGENTS.md, docs/README.md도 열지 않았습니다.
- **자동으로 붙은 맥락:** 시작 훅이 "PACE-BOOT 부트 생략" 문구를 넣었고, 호스트가 사용자 계정 맥락을 첨부했습니다. 둘 다 검토에 쓰지 않았습니다. 메모리 파일은 읽지도 쓰지도 않았습니다.
- **독립성:** 작성자 마감, 자체 판정, 이전 지적과 그 대응 문서는 받거나 읽지 않았습니다. 다른 검토자(advisor)도 부르지 않았으므로 검토 주체는 바뀌지 않았습니다. 이 호출은 1단계 첫 판단만 다룹니다. 2단계를 실행했다고 주장하지 않습니다.

## 첫 판단
- **상위 목적과 목표가 맞는지:** 맞습니다. Telegram으로 원격 조회와 작업을 맡기려면 daemon이 쓸 기본 체인과 읽기 전용 안전성이 먼저 있어야 합니다. 그래서 T01의 범위(체인 준비, 읽기 성공, 쓰기 차단 입증)는 적절한 첫 단계입니다. 원격 "작업", 즉 쓰기를 허용하는 경로는 이후 태스크로 미룬 것으로 읽힙니다.
- **목표 달성:** 미확인입니다. 구현 전이고, T-1과 T-3은 캡틴 결정이 나와야 진행됩니다.
- **근거와 한계:** TASK 본문만 근거로 판단했습니다. PROJECT의 P-1 원문과 BR01은 확인하지 못했습니다.
- **고칠 단계:** 계획 단계(테스트 표)입니다. 목표나 전략을 바꿀 필요는 없습니다.

## 지적

1. **[should_fix] S-3이 결함 있는 구현에서도 통과할 수 있습니다.** "변경 거부 관찰"의 범위가 정해져 있지 않습니다. 읽기 전용 강제가 등록되지 않았더라도 모델이 프롬프트를 보고 스스로 쓰지 않으면 파일은 그대로이고, 이것을 거부로 오해할 수 있습니다.
   - "거부"를 실행기 또는 CLI가 낸 권한 거부 이벤트나 샌드박스 오류로 한정해야 합니다. 모델이 말로 거절하거나 아예 시도하지 않은 경우는 미확인으로 처리합니다.
   - **양성 대조군**을 추가해야 합니다. 같은 프롬프트를 쓰기 허용 모드로 돌려 파일이 실제로 생기는지 봅니다. 그래야 프롬프트가 쓰기를 실제로 유도하고, 전후 비교가 변화를 잡아낸다는 것이 입증됩니다.

2. **[should_fix] 쓰기 경로를 하나만 시험합니다.** 파일 도구(Write/Edit)뿐 아니라 셸 명령(리다이렉트, `git` 명령)으로 쓰는 경우도 시도해야 합니다. 작업 폴더 밖의 절대 경로, 예를 들어 임시 폴더 안의 다른 디렉터리에 쓰는 경우도 포함해야 합니다. win32에서는 Codex 샌드박스가 읽기 전용을 제대로 강제하지 못할 수 있습니다. 그 경우 해당 실행기를 제외할지 결정할 경로를 접근 절에 미리 적어 두기를 권합니다.

3. **[should_fix] 검증한 설정과 운영에 반영한 설정이 같은지 확인하지 않습니다.** S-2와 S-3은 임시 PACE_HOME에서 실행기별로 검증하고, S-4는 실제 홈에 반영합니다. 두 설정의 실행기, 방식(p 또는 ACP), 읽기 전용 플래그, 순서가 같다는 대조가 없습니다. 그러면 "검증된 체인을 반영했다"는 결론이 추적되지 않습니다. 반영한 뒤 agent-chains.json의 해당 항목을 검증 때 쓴 설정과 대조하는 단계가 필요합니다.

4. **[should_fix] 체인 수준의 동작을 시험하지 않습니다.** T-1이 "대체 순서"를 확정한다고 하지만, 시험은 실행기별로만 있습니다. 다음 두 가지를 관찰할 시험이 하나 있어야 합니다.
   - default 체인 이름으로 요청했을 때 기대한 실행기가 선택되는지
   - `chain.ts`가 읽기 전용 미검증 실행기를 실제로 제외하는지

   필요하면 1순위 실행기가 실패할 때 대체로 넘어가는 경우도 봅니다.

5. **[should_fix] T-1의 "기존 설정 보존"이 반영 뒤에는 검증되지 않습니다.** S-1은 반영 전 무변경만 봅니다. S-4에는 적용 전후 비교가 없습니다. agent-chains.json의 다른 체인이나 키, 그리고 다른 설정 파일이 바뀌지 않았는지 비교해야 합니다. 비밀은 빼고 해시나 키 목록 수준으로 하면 됩니다.

6. **[note] T-3의 기대 결과가 좁습니다.** 기대 결과가 "default 체인 없음 오류가 사라진다"뿐이어서, 다른 차단 오류가 새로 생겨도 통과합니다. "install 계획에 차단 오류 없음, 또는 남은 오류 목록 기록"으로 넓히기를 권합니다.

7. **[note] daemon 실행 맥락과 대화형 실행의 차이.** daemon은 서비스 계정, PATH, 로그인 세션이 대화형 `pace agent run`과 다를 수 있습니다. 이번에 `--start`를 금지한 것은 타당합니다. 다만 "daemon 맥락에서 실행기 인증과 경로가 유효한가"는 후속 태스크로 넘긴다고 명시해 두면 상위 목적까지 추적이 끊기지 않습니다.

8. **[note] S-5와 작업자 추가 금지가 충돌합니다.** 접근 절에서 이미 코디네이터 확인으로 넘겼으므로 적절합니다. 검토 제공 방식이 정해지면 제공자와 독립성 수준을 TASK-CLOSE에 기록해야 합니다.
