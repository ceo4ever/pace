## 지적 항목별 재판정

**① device 보존: should_fix 해소(측정 근거를 교체)**
- 원래 `devicePreserved: true`는 측정값이 아니었다는 점을 그대로 둡니다. 근거는 이번 보완 관측으로 바꿉니다.
- 원문을 보면 config에 `device`가 없을 때 `parseConfig`가 `defaultConfig()`의 hostname 파생값을 씁니다. index.ts의 `status()`는 `config.device`를 그대로 status에 기록합니다.
- 관측 결과는 다음과 같습니다.
  - config 전체 해시가 T02 종료, T03 기준점, 현재(14:59)에서 모두 같습니다.
  - config에 명시 device가 없습니다(`explicitDevice=false`).
  - 로드된 값이 hostname 기본값과 같습니다.
  - 실행 중인 daemon의 status device가 로드된 값과 같습니다.
- 따라서 운영 device는 바뀌지 않았다고 판단합니다.
- 한계: 값이 hostname에서 파생되므로, 이 보존은 같은 hostname을 전제로 합니다.

**② Run 값 정확 일치: 해소**
- `ownsRunValue`는 trim한 뒤 대소문자를 무시하고 비교합니다. 그래서 원래 증거의 `registryOwnedExact`는 엄밀한 의미의 정확 일치가 아니었습니다.
- 보완 관측에서 현재 Run 값이 `launcherRunValue`의 전체 기대 문자열과 대소문자까지 같았습니다(`runFullStringCaseSensitiveExact=true`).
- 런처 바이트 일치는 이미 확인됐으므로, T-4의 등록 정확성을 충족합니다.

**③ 로그 검사 범위: 범위 축소로 수용**
- 이제 범위를 "CLI 로그 마지막 1000줄의 토큰 원문 일치 0"으로만 주장합니다. 그 밖의 것을 주장하지 않으므로 증거와 주장이 맞습니다.

**④ 기동 알림 건수와 첫 실패 원인: 미관측으로 남기고 수용**
- 둘 다 T-1~T-4의 합격 조건이 아닙니다. 미관측이라고 명시했으므로 blocking으로 보지 않습니다.

## 잔여 한계 (blocking 아님)

- **첫 기동 실패 원인:** registration-start 실패의 정확한 조건이 보존되지 않았습니다. "포트 확보 직후 준비 확인 경합"은 추정입니다. 설치본 start가 running 전에 0을 반환하는지는 확인되지 않았습니다. 재현되면 제품 결함으로 이슈나 백로그에 기록하는 것을 권합니다.
- **알림 미측정:** 기동 때 Telegram 알림이 몇 건 왔는지, 중복 실행 때 추가 알림이 없었는지는 세지 않았습니다.
- **부하 범위:** 유휴 daemon과 전체 검사 1회만 병행했습니다. 실제 모델 작업 2개 부하는 T04에서 봅니다. 순간 최저 메모리나 시스템 전체 OOM이 없었다는 것은 보장하지 않습니다.
- **skip 9건:** T03과 관련 없는 skip이 9건 있습니다(POSIX/sh, install.sh 등).
- **병합 후 인수:** 같은 사용자로 실제 재로그온한 뒤 수동 start 없이 다음을 확인해야 합니다. 새 boot, 단일 인스턴스, Run/런처/설정 일치, 사람이 본 콘솔 비표시입니다. 확인 전에 최신 기준점을 새로 만들어 두어야 하고, 이 확인이 끝나야 todo를 완료할 수 있습니다. 승인을 받았거나 지금 기동 중이라는 사실로 이 확인을 대신하지 않습니다.
