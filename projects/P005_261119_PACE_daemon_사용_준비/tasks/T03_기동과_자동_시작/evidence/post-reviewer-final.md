# T03 보완 판정: device 보존·Run 값 재검토

**접근 범위:** 이번에 받은 읽기 전용 비교 결과와 설치본 원문 발췌(`config.ts`, `index.ts`, `autostart.ts`)만 봤습니다. 실행, 파일 열기, 보조 호출은 하지 않았습니다. 이전 기준과 한계는 그대로 둡니다.

```
판정: pass (blocking 0)
독립 목표 대조: 맞음 — 1단계와 2단계 기록 그대로
목표 달성: 합의된 병합 전 목표 달성. 실제 재로그온 자동 기동과 콘솔 비표시는 미실측이며 병합 후 인수로 넘어감
```

## 직전 지적의 해소

**F1 [blocking] device 보존 → 해소**
- 설치본은 config에 `device`가 없으면 `defaultDeviceName()`, 즉 `normalizeDeviceName(hostname())`을 씁니다.
- 실제 config에는 명시된 device가 없습니다. config 전체 해시는 T02 종료 시점, T03 기준점, 현재 상태에서 모두 같습니다.
- 실행 중인 daemon은 `status`에 `config.device`를 기록합니다. 그 값이 설치본 `loadConfig`의 device와 같습니다.
- 그래서 T03이 device를 바꿀 수 있는 경로인 config가 그대로였고, 현재 실제 기동도 같은 파생값을 씁니다.
- 남는 조건: 이 결론은 T02 이후 hostname이 바뀌지 않았다는 전제에 기대고 있습니다. T02 당시의 device 값과 직접 비교하지는 않았습니다.
- 조치: 원래의 고정값 `devicePreserved: true`는 측정값이 아니라고 증거와 노트에 정정 표기하고, 이번 보완 관측에 연결해야 합니다. 마감 기록에 반드시 남깁니다.

**F3 [should_fix] Run 값 정확성 → 해소**
- `ownsRunValue`는 앞뒤 공백을 지우고 대소문자를 무시해 비교합니다. 그래서 원래의 "exact"라는 이름은 과장이었습니다.
- 보완 관측에서 현재 Run 값이 `launcherRunValue(home)` 전체 문자열과 대소문자까지 같음을 확인해 T-4의 정확 등록 근거가 생겼습니다.

## 남는 한계 (blocking 아님, 명시만 하면 됨)

- **F2:** 기동·재기동마다 오는 Telegram 알림의 건수와 발생 여부는 관측하지 않았습니다. 중복 실행 때 알림이 늘지 않는다는 판단도 소스 분기에서 추론한 것입니다.
- **F4:** 로그 검사는 CLI 출력 마지막 1000줄에서 토큰이 일치하는지만 봤습니다. chat·user ID는 검사 대상이 아니었습니다.
- **초기 준비 확인 실패:** 실패한 정확한 조건(predicate)과 원인은 확인하지 못했습니다. 초기 컨트롤러 원문도 없습니다. 첫 기동 프로세스는 인계 확인으로 대신했습니다. 제품 코드는 바뀌지 않았고, 재기동 경로는 정식 검증됐습니다.
- **부하 범위:** 메모리 관측은 데몬 대기 상태와 검사 1회에 한정됩니다. 모델 작업 2개의 부하 시험은 T04 몫입니다.
- **handoff H1~H3 유지:**
  - H1: 준비 경합 가능성을 이슈나 메모리에 기록
  - H2: 루트 교체 skip
  - H3: 재로그온 인수 todo, 체크리스트, 새 기준점

## S-6 판정

S-6 조건은 모두 충족했습니다.
- 유효한 전체 검사: 종료 코드 0, 991 통과·0 실패·9 건너뜀, 원문 SHA 일치
