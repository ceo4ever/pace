# P005 T03 독립 tester 1단계 판단

**받은 범위:** 관측 JSON 9개만 읽었습니다. lifecycle, memory-summary, system-memory-events, repository-check, pre-relogon-final-state, execution-failure, initial-owner-verification-gap, sensitive-records-scan, security-check입니다. TASK, PROJECT, BR, 작업자 결론, 소스는 받지 않았습니다. 도구 실행, 명령, 파일 변경, 보조 호출은 하지 않았습니다.

## 1. 목표 정합
- 관측 항목이 T03 병합 전 목표 네 가지(시작 등록, 기동/정지/재기동, 단일 인스턴스, 검사 병행 자원)에 맞게 짜여 있습니다.
- 사용자가 병합 후 인수로 넘긴 두 항목(실제 재로그온 자동 기동, 콘솔 표시)은 `not yet observed` 또는 `false`로 정직하게 남아 있습니다. 넘긴 범위와 일치합니다.

## 2. 달성 판단: 조건부 달성, 병합 전 보완 1건 필요
- **기동, 정지, 재기동:** 근거가 충분합니다.
  - 기동 확인, 정지 exit 0, 정지 상태 exit 3, lock과 port 해제를 확인했습니다.
  - 재기동은 exit 0이고 boot가 새로 바뀌었으며, 재기동 후 실행 중입니다.
- **단일 인스턴스:** 근거가 충분합니다.
  - 두 번째 start는 exit 0이고 PID와 boot가 같았습니다. 즉 이미 떠 있으면 새로 띄우지 않습니다.
  - 중복 run은 exit 2로 끝났고 기존 소유 프로세스는 바뀌지 않았습니다.
- **로그인 시작 등록:** 최종 상태는 정확합니다(Run 값, launcher, UTF-16LE BOM, 설치된 node와 bin 경로 일치).
  - 다만 `priorRunValueExisted`와 `launcherExistedBefore`가 true입니다. 이번 실행은 등록이 없는 상태에서 새로 만드는 경로를 관측하지 못했습니다.
- **검사 병행 자원:** 근거가 충분합니다.
  - 약 12.5분 동안 152개 샘플을 오류 없이 수집했고, 모두 같은 daemon이었습니다.
  - 최저 가용 메모리는 약 11.9 GiB, daemon 최대 working set은 약 93 MiB였습니다.
  - OOM 신호와 시스템 메모리 이벤트는 모두 0건입니다.
  - 전체 검사는 1000건 중 991건 pass, fail 0입니다.
- **설정과 비밀 보존:** config, device, secret 모두 변경 없음입니다. 로그 토큰 일치 0건, 민감값 일치 0건, secret-scan exit 0입니다.

## 3. 핵심 한계
1. **첫 기동 실패 원인이 확정되지 않았습니다.** 첫 `registration-start` 단계 실패의 상세가 보존되지 않았고, 원인은 "포트 확보와 lock/status 초기화 사이의 경합"이라는 추정뿐입니다.
   - 이후 lifecycle 검증은 그 실패 뒤 살아 있던 프로세스를 채택해서 진행했습니다.
   - 그래서 깨끗한 상태에서 install부터 첫 start까지가 한 번에 성공하는 경로는 검증되지 않았습니다.
   - 이 경합이 제품 쪽(start가 준비 완료 전에 반환)인지 tester controller 쪽인지도 관측만으로는 구분할 수 없습니다. 제품 쪽이라면 결함입니다.
2. **신규 등록 경로를 관측하지 못했습니다.** 위 2절의 기존 Run 값과 launcher 때문입니다.
3. **부하 조건이 제한적입니다.** daemon은 유휴 상태였고 실제 모델 작업은 0건이었습니다. 실사용 작업을 처리하는 동안의 자원 사용은 관측 범위 밖입니다.
4. **skip 9건이 있습니다.** 대부분 POSIX와 sh 전용입니다. 다만 "Windows 설치 실행 경로는 별도 실기 검증 필요"와 루트 교체 훅 미동작 2건은 Windows 쪽 공백입니다. T03과의 관련성은 소스가 없어 판단할 수 없습니다.
5. **모듈 해시와 브랜치 대응을 확인할 수 없습니다.** 해시가 병합 대상 브랜치와 일치하는지, readiness polling 보완이 반영된 뒤 측정된 해시인지 알 수 없습니다.

## 4. 병합 전 필요한 보완
- **(필수)** 등록과 프로세스가 없는 깨끗한 상태에서 install과 첫 start를 반복 실행해 보아야 합니다. 이때 실패 조건을 그대로 남겨야 합니다. 이를 통해 경합의 실재 여부와 위치(제품인지 controller인지)를 확정합니다. 제품 쪽이면 start가 준비 완료까지 제한 시간 안에서 기다리도록 수정한 뒤 재측정해야 합니다.
- **(권장)** Run 값과 launcher가 없는 상태에서 새로 등록하는 경로를 1회 관측합니다.
- **(권장)** 2단계에서 TASK, BR, 소스와 모듈 해시를 대조하고, skip 2건이 T03과 관련 있는지 확인합니다.
- 재로그온 자동 기동과 콘솔 표시는 이관된 대로 병합 후 인수 항목으로 유지합니다.
