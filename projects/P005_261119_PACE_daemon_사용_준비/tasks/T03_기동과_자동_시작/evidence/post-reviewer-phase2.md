# T03 독립 리뷰 2단계: 판정

**접근 범위:** 전달받은 자료만 읽었습니다. TASK, PROJECT, BR03, 후속 todo, 역할 기준, PRE-REVIEW, execution-notes, installation-preparation, 감사 소스 5종과 해시, relogon-checklist, 검사 원문 시작·끝 부분, 그리고 1단계의 관측 JSON입니다. 코디네이터가 직접 확인했다는 (a)~(e)는 그대로 전제로 썼습니다. 명령·API 호출, 파일 변경, 보조 호출, 감사 소스 실행, 실측 재실행은 하지 않았습니다. 설치본의 `ownsRunValue`·`buildLauncher`·device 저장 위치 소스와 TASK 기간 전체 diff는 받지 않았습니다.

```
판정: fail (blocking 1)
독립 목표 대조: 맞음
목표 달성: 대부분 달성. device 보존만 미확인
```

## 1단계 판단과의 대조

**독립 목표 대조: 맞음.** 1단계에서 본 목표(수명주기, 단일 인스턴스, 정확한 등록과 현재 기동, 검사 병행 관측, 재로그온 이관)는 P-3, T-1~T-4, BR03의 수정된 계약과 일치합니다.

1단계 지적 6건은 아래와 같이 정리됩니다.

1. **초기 실패:** 원인은 여전히 미확인입니다. 다만 아래 세 가지가 확인됩니다.
   - 제품 코드와 설치본은 바뀌지 않았습니다. 시작·종료 시 `verifyModules`로 설치본 26모듈 해시가 일치함을 확인했습니다.
   - 복구는 감사 컨트롤러에만 적용됐습니다(`waitForOwner`: 500ms×30, 실패 시 소유 정지).
   - stop 뒤 `start`로 새 boot가 준비되는 경로는 복구한 컨트롤러로 정식 검증됐습니다. 따라서 T-1의 합격 근거는 인계받은 프로세스가 아니라 재기동 경로에 있습니다.
   
   남는 한계도 있습니다. 첫 install 기동은 인계 확인(`execution-adopt`: 시작 시각, 명령줄, 포트 소유)으로 대체됐습니다. 초기 컨트롤러 원문은 보존되지 않았고, 감사 사본은 수정 후 버전입니다.
2. **새 등록 미관측:** 해소. (a)에서 첫 설치 전 Run 값과 VBS가 없었음을 확인했습니다. `priorRunValueExisted=true`는 첫 install이 만든 값을 다시 쓴 시점의 기록이라는 설명이 소스 흐름과 맞습니다.
3. **해시 연결:** 해소. 이 해시는 저장소 HEAD가 아니라 설치본 해시이며 실행 전후로 같습니다. 검사 원문은 (c)로 확인됐습니다.
4. **부하 대표성:** TASK가 모델 작업 2개의 부하를 T04로 명시했으므로 한계로 수용합니다.
5. **루트 교체 skip:** T03은 제품을 바꾸지 않았고 기존 skip이라 T03 범위 밖입니다. handoff로 둡니다.
6. **`execution-failure.json`:** 초기 컨트롤러 실행에서 소유권을 얻기 전에 남은 기록입니다. 그래서 `ownedStopRequested=false`가 맞습니다.

## 지적

- **F1 [blocking]** `execution-run.mjs`가 `lifecycle-observations.json`과 `pre-relogon-final-state.json`에 `devicePreserved: true`를 측정 없이 고정값으로 기록합니다. TASK와 사용자 결정은 기존 운영 device 유지를 요구합니다. 그런데 이 값은 측정되지 않았고, (a)~(e)와 baseline도 device를 다루지 않습니다. 근거 없는 통과 주장은 증거 위조에 해당하는 구멍입니다.
  → 다음 둘 중 하나로 고칩니다. 실측 재실행은 필요 없습니다.
  - device 정본이 config 파일 안에 있음을 소스로 보이면 기존 config 해시가 근거가 됩니다.
  - 아니면 T02 마감 기준점과 현재 device 파일 해시를 읽기 전용으로 대조합니다.
  
  어느 쪽도 못 하면 해당 필드를 "미측정"으로 고치고 증거와 노트에 명시합니다.
- **F2 [should_fix]** S-2 방법이 요구한 기동·재기동 알림 기록이 없습니다. → 사람의 관측을 기록하거나 미관측으로 명시합니다. T04나 재로그온 인수에서 확인해도 됩니다.
- **F3 [should_fix]** `registryOwnedExact`·`runValueExact`는 `ownsRunValue` 결과입니다. 이 함수가 정확 일치를 검사하지 않으면 이름이 과장됩니다. → 함수 의미를 소스로 확인하고, Run 값을 기대 명령 문자열과 직접 비교한 결과를 덧붙이거나 필드 이름을 바로잡습니다.
- **F4 [should_fix]** `logOutputKnownTokenMatches: 0`도 고정값입니다. 실제 근거는 `cli()`가 토큰 일치 시 예외를 던지는 구조입니다. → 근거와 범위(마지막 1000줄, 토큰만)를 주석으로 명시합니다.
- **H1 [handoff]** 초기 준비 확인 실패에 제품의 준비 경합이 관련될 수 있습니다. start가 0을 반환한 직후 lock·status가 아직 초기화되지 않았을 가능성입니다. 원인 미확인 상태로 프로젝트 메모리나 이슈에 재현 조건을 남기고, 재로그온 인수 때 확인합니다.
- **H2 [handoff]** 루트 교체 skip(권한·열린 핸들)은 별도 이슈로 추적합니다.
- **H3 [handoff]** 재로그온 인수는 todo·체크리스트·기준점 보존 방침으로 충분히 이관됐습니다. 승인을 성공으로 대체하지 않는다는 점도 명시되어 있습니다.

## 마감 조건

F1을 해소하면 blocking이 0이 되고, 합의된 병합 전 목표는 달성입니다. 실제 재로그온 자동 기동과 콘솔 비표시는 계속 미실측 상태이며 병합 후 인수 조건으로 남습니다. F1을 고치는 것은 증거 수정이므로, 같은 reviewer가 해당 항목만 재검토합니다.
