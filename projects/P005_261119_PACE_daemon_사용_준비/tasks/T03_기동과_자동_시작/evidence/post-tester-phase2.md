## 1단계 판단과 대조

- **"첫 install→start 경로 미검증"(1단계 필수 항목) → should_fix로 낮춤.**
  - (a)에서 승인 전 상태가 깨끗했다는 것(daemon 정지, Run 값 없음, VBS 없음)이 직접 확인됐습니다.
  - 그 상태에서 첫 install이 실제로 등록과 기동까지 해냈다는 것도 adopt 검증으로 확인됐습니다. 소유 프로세스의 시작 시각이 승인된 호출 이후이고, 실제 포트 소유자이며, 설치본 node와 `daemon run` 명령이었습니다.
  - 정지 상태에서 새로 기동하는 경로는 재기동 단계가 별도로 검증합니다(start exit 0, 새 boot).
  - 남는 공백은 첫 실패가 정확히 어떤 조건에서 났는지뿐입니다.
- **"신규 등록 미관측" → 해소.** `priorRunValueExisted=true`는 첫 시도에서 작업자 자신이 만든 값을 재사용한 기록입니다. (a)와 execution-notes가 서로 맞습니다.
- **"해시와 브랜치 대응" → 해소.** 26개 설치 모듈 해시가 installation-preparation, 실행 전(`verifyModules`), 최종 검증에서 같습니다. 제품 코드와 설치본은 바뀌지 않았습니다.
- **"부하가 유휴 daemon뿐", "skip 9건" → 그대로 한계로 남김.** 다만 TASK가 실제 모델 작업 2개 부하를 T04로 명시했고, skip 9건은 T03과 관련이 없습니다(POSIX/sh, install.sh, Antigravity, 루트 교체 훅).

## 실패 뒤 복구에서 구분할 점

- **운영 등록 재사용:** 첫 시도가 만든 Run 값과 VBS를 `ownsRunValue`와 런처 바이트 비교로 대조한 뒤 재사용했습니다. 다른 사람의 등록을 덮어쓴 것은 아닙니다.
- **제품 코드:** 바뀌지 않았습니다(모듈 해시 3중 일치).
- **합격 기준과 컨트롤러 복구는 다른 것입니다.**
  - readiness polling(500ms × 30회)과 adopt는 감사 컨트롤러를 고친 것입니다. 제품의 합격 동작이 아닙니다.
  - adopt 모드에서 `install --yes --start`는 이미 떠 있는 daemon을 대상으로 다시 실행됐습니다. 그래서 `installExit 0`과 `startConfirmed`는 "이미 실행 중이면 exit 0으로 유지"를 관측한 값이지, 처음 기동을 관측한 값이 아닙니다.
  - 처음 기동 관측은 재기동 단계가 대신합니다.
- **첫 실패 원인은 미확인입니다.**
  - 설치본 start가 status가 running이 되기 전에 exit 0을 돌려준다면, 그것은 제품의 준비 신호 계약 문제입니다.
  - 첫 실행 당시의 컨트롤러 소스(polling 추가 전)와 install 종료 코드는 보존되지 않았습니다.
  - `start-confirmation-failure.json`이 생성됐는지도 받은 자료로는 알 수 없습니다.

## should_fix

1. **`devicePreserved: true`가 하드코딩입니다.** lifecycle과 final-state 두 곳 모두 실제 비교 없이 true를 씁니다. 실제 device 대조로 바꾸거나, 증거 문구를 "미측정"으로 고쳐야 합니다. config와 secret은 해시로 실제 비교했습니다.
2. **로그 검사 범위가 증거보다 좁습니다.** `logOutputKnownTokenMatches: 0`은 `cli()`의 token 검사에만 근거합니다. chat과 사용자 ID는 로그에서 검사하지 않았으므로 증거에 그 범위를 명시해야 합니다.
3. **첫 실패를 정확히 기록해야 합니다.**
   - 첫 install 종료 코드를 남기고, `start-confirmation-failure.json`이 있었는지 확인해야 합니다.
   - 첫 실행 당시 컨트롤러 소스가 없다는 사실도 남겨야 합니다.
   - start가 준비 완료 전에 0을 반환할 가능성은 재현 요약과 함께 이슈나 백로그로 기록해야 합니다(PROJECT 설계: 제품 결함 기록).
