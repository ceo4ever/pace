# T03 독립 리뷰 1단계: 관측 근거 판단

**받은 범위:** 관측 JSON 9개뿐입니다. lifecycle-observations, memory-summary, system-memory-events, repository-check-result, pre-relogon-final-state, execution-failure, initial-owner-verification-gap, repository-sensitive-records-scan, security-check-result입니다. TASK·PROJECT·BR·작업자 결론·소스·원본 로그는 받지 않았습니다. 도구, 명령, 파일 변경, 보조 호출은 쓰지 않았습니다.

**판정:** 조건부 정합입니다. 기동/정지/재기동, 단일 인스턴스, 검사 병행 관측은 대체로 달성했습니다. 다만 등록·기동 경로 자체가 아래 1·2번 때문에 아직 닫히지 않았습니다.

## 목표 정합·달성

| 항목 | 근거 | 판단 |
|---|---|---|
| 시작 등록 | `registryOwnedExact`, `runValueExact`, `launcherExact`, 런처가 설치본 node·bin과 일치, UTF-16LE BOM 확인 | 최종 상태는 충족. 다만 아래 2번 참조 |
| 기동/정지/재기동 | 설치·기동·정지·재기동 종료 코드 0, 정지 후 status 3, lock·port 해제, 재기동 뒤 새 boot | 충족 |
| 단일 인스턴스 | 두 번째 start가 같은 PID·boot 유지, 중복 run은 exit 2로 거부되고 소유자 불변 | 충족 |
| 검사 병행 자원 | `npm run check` exit 0(991 pass, 0 fail, 9 skip), 샘플 152개, 샘플 오류 0, 같은 데몬 유지, 최대 working set 약 92.6MiB, 최소 가용 메모리 약 11.9GiB, OOM 신호 0 | 관측 범위 안에서는 충족 |
| 보존·비밀 | config·device·secret 불변, 로그 토큰 일치 0, 민감값 스캔 0, secret-scan exit 0 | 충족 |
| 이관 항목 | 실제 로그아웃/로그인에 의한 자동 기동과 콘솔 표시는 "not yet observed"로 정직하게 표기됨 | 사용자 이관과 일치 |

## 주요 한계

1. **첫 기동 실패의 원인과 수정 검증이 없습니다.** 첫 시도가 `registration-start` 단계에서 실패했고, 세부 내용은 기록되지 않았습니다(`detailsSuppressed`). 원인으로 제시된 "readiness 검사와 포트 획득의 경쟁"은 추론일 뿐입니다. 이후 수명주기 시험은 이 실패에서 넘겨받은 프로세스로 진행됐습니다. 따라서 "설치 → 기동 → 준비 확인"이 컨트롤러 한 번 실행으로 깨끗하게 통과한 관측은 없습니다. 복구안으로 적힌 "제한된 readiness 폴링과 즉시 소유 정지 fallback"이 구현됐는지, 재검증됐는지도 보이지 않습니다.
2. **새로 등록하는 경로는 관측되지 않았습니다.** 실행 전에 이미 Run 값(`priorRunValueExisted`)과 런처(`launcherExistedBefore`)가 있었습니다. 그래서 이번 관측은 기존 등록을 덮어쓴 경우만 보여 줍니다.
3. **모듈 해시와 검증 대상의 연결이 없습니다.** 모듈 해시가 병합 대상 커밋, 그리고 `npm run check`를 실행한 트리와 같은지 연결해 주는 근거가 없습니다. 1번의 수정이 들어갔다면, 수정 뒤의 해시로 수명주기를 다시 시험했는지가 특히 중요합니다.
4. **자원 관측의 대표성이 제한적입니다.**
   - 부하는 유휴 데몬과 검사 1회뿐이고 실제 Telegram 작업이나 모델 작업은 없었습니다. 상위 목적인 원격 작업 위임 중의 자원 사용은 관측되지 않았습니다.
   - 샘플 간격이 658~5864ms로 목표 5000ms에서 벗어났습니다.
   - 시스템 메모리 이벤트 0건의 근거가 되는 provider가 무엇인지 명시되지 않았습니다.
5. **skip 9건 중 1건은 따로 판단해야 합니다.** 대부분 sh·POSIX·install.sh 전용이라 Windows에서 건너뛴 것은 타당합니다. 그러나 "조회 도중 루트 교체 거부" 시험은 플랫폼 문제가 아니라 루트 교체 훅이 동작하지 않아 건너뛰었습니다. 보안 성격의 검증이라 T03 범위 밖인지 확인해야 합니다.
6. **실패 기록 사이의 관계가 불명확합니다.** `ownedStopRequested: false`이고 등록이 승인대로 남았다는 기록이 있습니다. 이것이 1번의 초기 실패와 같은 사건인지, 이후 실행에서 남은 상태인지 구분되지 않습니다.

## 2단계 전 보완 요청

- 수정된 컨트롤러로 기존 등록이 없는 상태에서 등록부터 준비 확인까지 한 번에 통과한 관측, 그리고 실패 시 소유 정지가 동작하는 관측
- 모듈 해시를 병합 대상 커밋 SHA와 check를 실행한 트리에 묶는 근거
- readiness 경쟁 원인을 뒷받침하는 소스나 로그(비밀은 가린 상태로)
- 루트 교체 skip이 T03 범위 밖이라는 판단
- 메모리 이벤트 provider 명시
- 가능하면 Telegram 작업 1건 이상을 병행한 자원 관측. 없다면 이 공백을 한계로 명시하는 것으로 충분합니다

위 1~3번이 해소되면 병합 가능하다고 판단합니다. 실제 로그아웃/로그인 확인은 합의대로 병합 후 인수 항목으로 남깁니다.
