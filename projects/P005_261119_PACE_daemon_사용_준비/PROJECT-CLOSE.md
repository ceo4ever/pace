## 목표 달성 판정

**상위 목적**: 캡틴이 자리에 없어도 Telegram으로 이 PC의 PACE에 조회와 작업을 맡기고 결과를 받는다.

**목표**: 등록된 워크트리에서 읽기 전용 조회와 승인된 쓰기를 각각 실사용으로 검증한다. 이 목표는 상위 목적에 맞는다. 결정적 응답(`/status`)이나 단위 시험만이 아니라, 실제 봇·실제 모델·실제 승인 버튼으로 일을 끝까지 맡겨 봤다.

**판정: 계약 목표 달성.** 근거는 다음과 같다.
- 실제 Telegram 읽기와 세션 이어가기를 확인했다(T04 S-2·S-2r).
- 캡틴 계정의 인라인 승인 뒤 지정 파일만 바뀌고 결과 알림까지 왔다(T04 S-3r).
- 거절·실제 만료·재기동 뒤 이전 승인이 실행을 막았다(T04 S-4d·S-4e·S-4r).
- 실행 중 쓰기를 강제로 중단해도 needs_review·격리·자동 재실행 없음이 지켜졌다(T04 S-5·S-5g·S-5q). 중단 시점은 첫 편집 전(셸 승인 대기)이었고, 부분 쓰기 뒤 복구는 미확인이라 후속 이슈로 넘겼다.
- 운영 상태로 복원했다(T04 S-6).
- 체인(T01), Telegram 권한(T02), 기동·단일 인스턴스(T03)도 각 TASK-CLOSE에서 독립 판정을 거쳤다.

**실사용이 잡은 제품 결함 세 건**은 모두 main 작은 일로 고친 뒤 실측으로 확인했다.
- launchd PATH: 3970e51.
- 강제 종료 뒤 재기동: 521e3b8.
- 읽기 전용 대화의 작업 폴더 밖 무승인 읽기(보안): a3dfdbd. 캡틴에게 사전 보고했고, 결정대로 작은 수정 뒤 재시험했다.

**미확인·한계**: 계약 밖의 일반 효과라 계약 목표를 줄이지 않고 따로 적는다.
- **부재 중 운영**: KeepAlive가 false라 daemon이 죽으면 자동으로 다시 뜨지 않는다. 쓰기는 매번 캡틴 승인이 필요하다. 부재 중에 누가 재기동하고 누가 승인할지는 운영 결정으로 남는다.
- **읽기 전용 경계**: 보안 수정의 효과는 새 읽기 차단으로 관측된 범위다(새 표식의 셸 `cat`·Read). 수정 전 대화에 이미 들어간 바깥 내용은 이어간 대화에서 다시 답에 나올 수 있다. 어댑터가 권한을 묻는 데 기대며 OS 수준 경계는 없다. 쓰기 모드에서는 편집 도구가 경로를 대조하지 않는다. 둘 다 `BL261124_02`로 넘겼다.
- **로그인 자동 기동(P-3)**: 기준을 캡틴 결정으로 macOS launchd로 바꿨다. 실제 재로그온 자동 기동(RunAtLoad)은 미실측이라 병합 후 인수로 남긴다. 콘솔 비표시는 macOS에 해당 없다.
- **P-2 거절(macOS)**: 허용 밖 계정의 거절은 이전 PC 실측과 단위 시험으로 판정했다(캡틴 결정). macOS 실측은 미확인이다.
- **보존 관측**: T04 T-5 보존은 관측 범위(PACE_HOME 보호 파일·홈 목록) 안에서 판정했다. 구간 밖 출처 귀속은 추정이다(캡틴 결정에 따라 확인·추정·미확인을 나눠 기록).
