## 목적

허브 PM이 대기 중인 작업자의 결정을 맡아 owner 부재 중에도 작업이 이어지게 한다. 실제 owner 판단이나 승인이 필요한 경우에만 그 근거와 선택지를 올리고, 승인 입력 전에는 승인 원문과 대상을 확인한다.

## 재료

- [PROJECT 목적·기준](../../PROJECT.md)과 [BR01 범위·완료 기준](../../../../backlogs/BL261124_05_허브_PM_결정_권한과_어드바이저/BR01_결정_권한_정본과_어드바이저_절차.md)을 정본으로 쓴다. 현재 coordinator 안내는 장애 수신을 owner 전달로 연결하고, 리뷰 미실행 안내는 같은 제공자 대체도 owner에게 묻도록 한다.
- 측정 단위의 비교는 [BL04 BR01](../../../../backlogs/BL261124_04_검토_예산과_재현_근거_지적/BR01_태스크_단위_검토_예산과_범위_재검토.md), 승인 기록은 [HANDOFF](../../../../docs/HANDOFF.md), 민감 경로는 [SECURITY](../../../../docs/SECURITY.md)를 따른다.

## 증명 범위

- 판정 주체: 결정 권한은 BR01·PROJECT의 owner 결정 기록에 근거한다. 이 기록은 결정 요약이며, 실제 승인 게이트에서는 별도로 해당 대상의 owner 원문을 확인해야 한다. 독립 reviewer·tester와 워크트리 PM은 BR01 대조표·새 맥락 응답 원문·시험 실행 결과로 적용 여부를 판정한다. 자동 시험은 프롬프트·출력·계약 문자열과 거부 경로를 검사한다.
- 포함: BR01의 닫힌 목록·기존 위임 예외·실행 전 승인 확인·장애 공동 해결·사후 보고, 모든 참조 전환, workerSpec과 팀 계약, 새 행동 시나리오와 기존 S1~S7 회귀. 원문 없음·대상 불일치·필수 검증 미실행의 승인 경계도 확인한다.
- 범위 밖: PM 결정 강제와 owner 인증 채널 구현 및 팀 계약 v2는 별도 백로그 범위다. 실제 Orca에서 허브-작업자 왕복 1건의 관측은 BR01이 정한 병합 후 인수로 메모리 todo에 남긴다.

## 접근

- [PROJECT의 정본 목록](../../PROJECT.md#설계)대로 정본을 중심으로 고친다. 반복 검토 단계·회수·보고의 세부는 유지하고 실행 고리와 영향 판정을 연결한다. 인접한 CLI 도움말과 에이전트 호출 문서의 기존 미실행·질문 안내도 정본에 맞춰 정정한다.
- BL04 착수 전에는 남은 blocking을 그대로 안고 진행하는 것은 A-3이다. BL04가 독립적인 검토 회차와 증거가 있는 작고 허용된 잔여 영향의 수용을 설계한다. 증거 미확인은 A-3 경계를 유지한다. B의 2회는 공동 시도 초기값이고 검토 원장 회차와 별개다.
- 병합 대기 중에는 S1의 main 도구 수정 커밋도 병합 뒤로 미룬다. 대기 커밋의 검증·승인 대상이 바뀌는 재finish를 피하고, 그동안 허브가 원인 조사·안전한 우회·독립 작업을 결정한다. 프로젝트 하네스의 결정 권한에는 프로필 `rule`보다 정본을 적용한다. 하네스 장애를 푸는 main 작은 수정(S1)도 그 범위에 든다. 그 밖의 업무와 SOUL은 기존 확인 규칙을 따른다.
- 원장 사용 프로젝트의 사후 요약은 `status`, 원장을 쓰지 않으면 프로젝트 요약으로 남긴다. 프로젝트 밖 승인 원문은 로컬 `$PACE_HOME/approvals/` 기록에 대상·범위·원문 출처·지문과 함께 보존한다. 게이트별 근거 파일은 승인 원문을 검증한 뒤 연결하고, 원장이 있으면 팀 로컬 보존 규칙에 맞는 영수증을 쓴다.
- 보안은 명령 입력·권한·경로·전송을 건드리지 않는 문구 변경이다. 기존 실행 분기와 fail-closed 테스트를 대조하고 거부·대상 불일치의 스킬 eval도 실시한다. 리뷰어는 민감 경로 `src/project/harness.ts`·`src/team/store.ts`와 승인 게이트의 우회 여부를 먼저 확인한다. TypeScript·검증 교본의 대역과 실제 출력 일치, 오류 경로 누락 방지를 적용한다.
