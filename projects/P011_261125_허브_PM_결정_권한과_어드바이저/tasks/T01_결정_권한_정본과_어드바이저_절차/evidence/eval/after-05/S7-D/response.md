**사례: 진단 기록 직후, `verify` 실행 전 (normal 단계)**

**담당**
- 워크트리 PM(나)이 맡는다. 허브는 이미 세 차례 근거를 받아 근본 조치를 정했다.
- reviewer는 구현자와 다른 새 맥락이어야 하고, `verify`가 그 검토를 맡는다.

**순서**
1. 수정하기 직전에 조치의 실제 영향을 결정 권한 정본 A와 대조한다. 합의된 목적·목표·범위가 바뀌는지도 함께 본다. `references/decision-rights.md`는 이번에 열지 않았고, SKILL.md와 reviewer.md가 가리키는 내용만 근거로 삼았다.
2. A 밖이면 PM이 직접 확정된 근본 조치를 적용한다. 이미 승인된 조치는 다시 승인받지 않는다. A에 걸리면 `ask`로 허브에 인계하고, 수정은 owner 결정 뒤에 한다. 이때 해당 A 번호와 증거·불확실성을 붙인다.
3. 조치를 적용한 뒤 `pace agent verify`를 실행한다.
   - 진단 뒤 첫 `verify`는 새 기준 **전체 검토**다. 이전 지적으로 purpose를 좁히지 않는다.
   - 작성자의 대응이나 자체 판정은 purpose에 넣지 않는다.
   - 같은 대상은 같은 경로로 `verify`를 이어 원장을 잇는다.
   - 다른 제공자가 미실행(종료 10)이면 사유를 남기고 `--allow-same-provider`(`cross: false`)로 잇는다.
4. 결과를 읽는다.
   - pass(blocking 0)면 진행한다. 다만 목표 달성 판정은 따로 한다.
   - fail이면 지적을 반영하고 재검토한다.
   - 종료 0에 `escalation.stage: ask_user`가 나오면 그 호출에서 즉시 대응한다.

**명령·기록**
- 지금은 `review-note --decision`을 쓰지 않는다. decision은 `verify`가 fail로 끝나 `ask_user` 단계가 열린 뒤에만 입력한다. 진단은 이미 기록했으므로 `review-note --diagnosis`를 다시 쓰지 않는다.
- owner 응답이 필요했다면 그 원문을 진단 근거나 `pace project log`에 연결한다.
- 차수별 원문은 `review-records/`에 보존하고, 증거 경로를 TASK-CLOSE와 review 로그에 연결한다.

**회신·보고**
- 지금 보낼 회신이나 보고는 없다.
- 최종 사후 보고는 TASK-CLOSE 리뷰 절과 C의 사후 요약에 4요소로 남긴다. 4요소는 무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과다.

**질문·승인 대기**
- 질문 0건, 승인 대기 0건이다. A 밖 조치라고 보았을 때의 수이고, A에 걸리면 owner 결정 1건이 필요하다.
- 진행 기록(`pace memory status`)은 태스크를 멈추거나 끝낼 때 갱신한다.

**자동 첨부와 읽은 범위**
- 이 세션 시작 시 사용자 계정 컨텍스트(이메일)가 자동 첨부되었고, 그 값은 적지 않는다.
- `skills/pace-project-dev/SKILL.md`를 1–93줄 읽었다. `references/reviewer.md`를 1–125줄 읽었다. 다른 파일은 읽지 않았다.
- 전체 바이트는 도구로 확인하지 않아 적지 않는다.
