**읽은 범위와 첨부**
- 자동 첨부: userEmail이 자동 첨부되었다. 값은 쓰지 않는다. 사용하지도 않는다.
- `SKILL.md`는 1–93줄 전체를 읽었다.
- `references/reviewer.md`는 1–125줄 전체를 읽었다.
- `references/decision-rights.md`는 1–46줄 전체를 읽었다.
- `references/` 아래에서 `interrupted|diagnose`를 Grep했다. 이 검색에서 읽은 파일은 `reviewer.md`뿐이다.
- 다른 사례의 응답·평가표·TASK·마감 문서는 읽지 않았다.
- 전체 바이트 수는 도구로 확인하지 않았으므로 적지 않는다.
- 이번 시험은 읽기 전용이다. 수정·질문·메모리 기록·커밋·전송은 하지 않았다.

**공통**
- 담당은 워크트리 PM이다. 같은 대상의 반복 검토는 `pace agent verify`의 원장(`REVIEW-LOG.jsonl`)이 단계를 계산한다. PM은 그 신호를 읽고 따른다. (reviewer.md 반복 실패 절, "단계 읽기")

**사례 1: normal 단계, 구간의 fail이 `interrupted` 1건뿐**
- 담당: 워크트리 PM.
- 단계 판정: `interrupted`는 연속 fail 집계에 들어가지만 실제 blocking은 아니다. 1건이므로 단계는 normal이다. diagnose와 ask_user는 열리지 않는다.
- 실제 명령:
  - 중단 복구만 남은 normal이므로 다음 검토는 전체 검토다. 그래서 `pace agent verify`(task 대상이면 `--kind task`)를 다시 호출한다. 원장에 같은 경로로 이어 간다.
  - 고칠 지적 원문이 없으므로 수정 전 A 대조는 새 조치가 생길 때만 한다.
- 하지 않는 것:
  - `review-note --diagnosis`와 `--decision`은 쓰지 않는다.
  - `--void`도 쓰지 않는다. pass와 중단 복구는 무효 처리 대상이 아니다.
  - PRE-REVIEW.json에 옮기지 않는다. `interrupted`는 판정 원문이 없어 시도로 옮기지 않고, 횟수·보고에만 반영한다.
- 기록: 중단 복구 1건은 실제 blocking과 구별해서 `pace project log`와 TASK-CLOSE 리뷰 기록에 남긴다.
- 회신·보고: 허브 보고는 필요 없다. 장애나 같은 실패 3회에 해당하지 않는다.
- 질문 0건, 승인 대기 0건.

**사례 2: 같은 상황에서 복구로 3회가 돼 종료 16·`diagnose`**
- 담당: 워크트리 PM이 처리한다. 근본 조치는 허브가 B로 정한다.
- 단계 판정: `interrupted`도 연속 fail에 집계되므로 3회째에 diagnose가 열린다. 종료 16은 아직 기록되지 않은 단계에서 다시 호출했을 때의 차단이다. `recovered`로 처음부터 16이 나와도 같은 단계를 따른다. 진단 전에는 verify를 다시 돌리지 않는다.
- 순서:
  1. 실패 원문과 차수별 기록을 모은다. 중단 복구와 실제 blocking을 구별한다. 이 경우 실제 blocking은 없을 수 있다.
  2. 원인 층(structure·planning·design·other)을 가린다. 중단 복구가 반복된 점으로 보아 structure(도구·실행 환경)가 유력하다. 근거를 확인해 정한다.
  3. 근거와 진단을 허브에 보낸다. 허브는 B로 재현한 뒤 근본 조치를 정하고 회신한다.
  4. 조치를 적용하기 전에 A-1부터 A-5로 대조한다. 도구 수정이 A-3(안전 기준 약화)에 걸리는지도 함께 본다.
     - A 밖이면 PM이 결정하고 진단 증거에 근거를 남긴다.
     - A에 해당하면 허브가 owner에게 해당 번호를 붙여 요청하고, 회신까지 그 조치만 보류한다. 독립 작업은 이어 간다.
  5. 진단을 기록한다: `pace agent review-note --target <대상> --diagnosis --layer <층> --summary <진단·조치> --file <진단 증거>`. 이 기록 직후는 normal이다.
  6. 확정된 조치를 적용하고 `verify`를 다시 호출한다. 새 기준의 전체 검토이며, 이전 지적으로 purpose를 좁히지 않는다.
- 후속 분기:
  - pass면 마감 절차로 간다.
  - fail이면 `ask_user` 단계가 열린다. A 밖이면 PM이 `--decision --by pm`을 기록한다. A에 해당하면 6요소(대상·실패 추이·진단과 고친 층·남은 지적 성격·선택지·추천과 이유)를 붙여 허브를 거쳐 요청한다. 승인 원문을 대조한 뒤 `--decision --by user`를 입력한다.
- 보고: 사후 보고 4요소(반복된 것·고친 층·채우거나 덜어낸 것·재검증 결과)를 TASK-CLOSE 리뷰 절과 허브의 C 사후 요약에 남긴다. 허브 결정은 "(main 판단)"으로 기록한다.
- 제한:
  - `--void`는 도구 결함이 증명될 때만 쓸 수 있다. diagnose 단계에서는 도구가 void를 거부하므로, 진단으로 넘어간다.
  - 도구 결함이 원인이면 허브가 B로 도구를 먼저 고친다. 병합 대기 중이면 main 커밋은 병합 뒤로 미룬다.
- 질문과 승인 대기 수:
  - 허브 회신 대기 1건(근본 조치 B).
  - A-밖: owner 질문 0건, 승인 대기 0건.
  - A-해당: owner 질문 1건, 승인 대기 1건.
