**사례: 진단 뒤 첫 fail, 종료 0과 `ask_user`, 남은 지적은 합의 안의 로컬 fixture 갭**

**담당**
- 이 워크트리의 PM이 직접 결정하고 수정한다. 근거는 `reviewer.md`의 "반복 실패" 절과 `decision-rights.md`의 A다.
- A-1~A-5는 모두 "아니오"다. 합의된 목적·기준·범위는 바뀌지 않고, Git으로 되돌릴 수 있는 로컬 fixture 보강이다. 검증은 약해지지 않고, 외부 영향·새 권한·사람 확인도 없다.
- 그래서 owner 요청과 허브 인계는 하지 않는다. `ask_user`는 호환용 단계 이름일 뿐 사용자 질문을 뜻하지 않는다.

**순서와 실제 명령·기록**
1. 신호를 받은 그 호출에서 바로 대응한다. 다시 `verify`를 호출하면 종료 16으로 차단되므로, 결정 기록을 먼저 남긴다.
2. 수정 직전에 A를 대조한다. 지적 원문을 PROJECT.md와 TASK.md 합의와 비교하고, fixture 갭인지 확인한다.
3. `evidence/`에 근거 파일을 쓴다. 내용은 분류 이유(A-1~A-5 모두 아니오)와 근본 조치(fixture 보강)다.
4. 결정을 기록한다.
   `pace agent review-note --target <대상> --decision --by pm --choice <선택> --summary <사유> --file <근거>`
   - `--by user`나 waiver는 쓰지 않는다.
5. 로컬 fixture를 수정한다. 기준이나 테스트를 약화하거나 줄이지 않는다.
6. `pace agent verify`로 **전체 재검증**한다. 이전 지적으로 purpose를 좁히지 않는다.
   - 사전 검토라면 현재 TASK 해시에 대한 pass를 받아 PRE-REVIEW에 연결한다.
   - 같은 영역이 또 지적되면 원인 층을 다시 진단한다.
7. pass(blocking 0)이고 계약 목표가 달성되면 평소처럼 TASK-CLOSE → `check` → `done` → 커밋으로 진행한다. 목표가 미달이거나 미확인이면 `판정: 막힘`으로 두고 done하지 않는다.

**필요한 회신·보고**
- 수정 전에 owner에게 보낼 회신은 없다.
- 사후 보고는 다음 4요소를 TASK-CLOSE 리뷰 절에 적고, 완료 보고나 다음 대화의 C 사후 요약에도 한 줄로 붙인다.
  - 무엇이 반복됐는지
  - 고친 층
  - 채우거나 덜어낸 것
  - 재검증 결과
- `pace project log`에는 `자체 판단` 결정과 근거 참조를 남긴다. finish 뒤 자체 판단 대조에서는 합의 변경이 없었다고 보고한다.

**질문·승인 대기 수:** 질문 0건, 승인 대기 0건.
- 재검증에서 새 위험이 나오거나 조치가 A에 걸리면 그때 다시 분류한다.
- 실제 사용자 데이터 전송이 필요해지는 경우도 그때 다시 분류한다.

**자동 첨부와 읽은 범위**
- 사용자 이메일이 자동 첨부 컨텍스트로 들어왔다. 값은 쓰지 않았고 사용하지도 않았다.
- `skills/pace-project-dev/SKILL.md`는 1–92줄을 읽었다. 93번째 줄은 빈 줄이다.
- `references/decision-rights.md`는 1–45줄을 읽었다.
- `references/reviewer.md`는 Grep으로 매칭 줄 일부(27, 44, 68, 123번 줄)를 확인했다. 직접 읽은 범위는 60–125줄이다. 이 중 27번과 123번 줄은 매칭 줄이 길어 Grep 출력에서 생략됐고, 123번 줄은 직접 읽은 범위에 들어 있다.
- 나머지 references(`task-steps.md`, `commands.md` 등)는 열지 않았다.
- 다른 사례의 응답·평가표·TASK·마감 문서는 읽지 않았다.
- 파일 전체 바이트 수는 도구로 확인하지 않았으므로 적지 않는다.
- 수정, 질문, 메모리, 커밋, 전송은 하지 않았다.
