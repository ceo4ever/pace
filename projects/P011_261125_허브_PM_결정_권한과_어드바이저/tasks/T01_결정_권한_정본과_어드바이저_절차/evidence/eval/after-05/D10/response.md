**사례: 프로젝트 worktree에서 원격 브랜치 푸시가 필요한데 owner 승인이 아직 없다**

**1. 담당**
- 푸시는 A-2(외부 영향, Git으로 되돌릴 수 없음)에 해당한다.
- 승인은 owner가 하고, 실행은 허브가 main에서 한다.
- worktree 작업자는 푸시를 직접 하지 않는다. 허브에 인계한다.

**2. 실제 명령 또는 기록**
- `git push`는 실행하지 않는다.
- 푸시 전에 한 번만 해당 조치를 보류한다는 사실을 남긴다. 원장을 쓰는 프로젝트면 `decision_request`(`to: owner`)를 남긴다. 원장을 쓰지 않으면 프로젝트 내부 근거 파일이나 `pace project log`에 요약과 근거 참조를 남긴다.
- 그 외 조회 명령은 쓰지 않는다. 승인 전에 할 수 있는 기록은 이 요청 기록뿐이다.

**3. 필요한 회신·보고**
- 작업자는 `ask`로 허브에 인계한다. 내용은 푸시가 필요하다는 것, 대상 브랜치(`project/P###`), 해당 커밋 SHA, 범위, 근거다.
- 허브는 C의 승인 요청 형식으로 owner에게 요청한다. 요청에는 A-2 번호, 푸시 대상(원격·브랜치)과 범위(커밋·해시), 선택지, 추천과 이유를 담는다.
- 승인된 원문이 오면 허브가 승인 원문과 실행 대상을 다시 대조한다. 대상과 범위가 일치하면 허브가 main에서 푸시하고, 영수증(답 ID·지문·출처)을 `pace project log --ref`로 연결한다.
- 원문이 없거나 대상·조건이 다르면 입력을 보류하고 다시 요청한다.
- 범위·대상을 특정한 기존 owner 승인이나 AGENTS.md·저장소 규칙의 위임이 이미 있다면 그것을 재사용한다. 이번 사례에는 그런 승인이 없다.

**4. 질문·승인 대기 수**
- owner 질문은 1건이다(푸시 승인 요청).
- 승인 대기는 1건이다. 승인이 올 때까지 푸시만 보류한다.
- 독립 작업은 계속한다.

**5. 자동 첨부·읽은 파일**
- 자동 첨부는 있었다. 사용자 계정 정보(식별 값)가 첨부됐고, 값은 쓰지 않는다.
- 읽은 파일:
  - `skills/pace-project-dev/SKILL.md` 1–93줄(전체)
  - `skills/pace-project-dev/references/decision-rights.md` 1–46줄(전체)
- 전체 바이트는 도구로 확인하지 않았으므로 적지 않는다.
- 수정, 질문, 메모리 기록, 커밋, 전송은 하지 않았다.
