**판정**: 함수 배치, 동등한 테스트 방식, 작업 순서는 내부 설계 선택이다. 결과를 모르는 부분이 있어도 Git으로 되돌릴 수 있다. A-1부터 A-5까지 모두 "아니오"이므로 담당 PM이 결정한다. 사용자에게 묻지 않고 승인도 기다리지 않는다.

**할 일의 순서**
1. **담당**: 이 세션의 PM이다. 워크트리 PM이면 태스크 계약 안에서 직접 정하고, 코디네이터나 owner에게 `ask`하지 않는다.
2. **A 대조**: 현재 계약(P-n, T-n)을 바꾸지 않는지, 푸시·병합·배포 같은 외부 영향이 없는지, 검증을 약화하지 않는지 확인한다. 새 권한·비용이 없고 사람이 수행할 일도 없는지 본다. 전부 "아니오"다.
3. **불확실성 처리**: "판단이 서지 않음"만으로는 질문을 만들지 않는다. 결과를 모르는 부분은 코드와 기존 테스트, 주변 코드 스타일을 읽어 증거를 더 모은다. 기준 문서는 §5·standards.md의 우선순위(기계 설정 > `AGENTS.md` > 기준 문서 > 주변 코드)로 고른다. 그래도 남으면 추천안으로 진행한다.
4. **선택**: 함수 배치는 주변 코드 관례를 따른다. 테스트 방식은 계약 기준을 같은 강도로 검증하는 동등한 방식 중 하나를 고른다. 작업 순서는 되돌리기 쉬운 것부터 정한다. 버그라면 RED 테스트를 먼저 둔다.
5. **기록**: 선택과 이유를 PROJECT.md나 TASK.md 결정 메모에 적는다. 명령은 `pace project log`로 자체 판단 한 줄을 남기며, 정확한 형식은 `references/commands.md`에서 확인한다. 이 기록은 finish 뒤 "자체 판단 대조"에 쓰인다.
6. **진행**: 기존 흐름대로 구현 → 테스트 → `pace project check` → `done` → `pace memory status --project` → 커밋 순으로 간다. 구현 전 reviewer 검토 같은 게이트는 그대로 지킨다.
7. **재검토 조건**: 진행 중 선택이 계약·기준을 바꾸는 것으로 드러나면 그때 A-1로 올린다. 그 조치만 보류하고 독립 작업은 이어간다.

**수 집계**

- 승인 대기: 0건
- 실제 명령·기록: 이 시험에서는 실행하지 않았고, 위 계획만 적었다.
- 병합·푸시·배포: 해당 없음. 필요해지면 허브와 owner 승인 뒤에만 한다.
