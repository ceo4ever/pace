**상황 판정:** 병합 대기 프로젝트가 있고, 기존 도구로 병합할 수 있다. 다른 프로젝트의 장애 원인은 작은 하네스 도구 결함이다. 근거는 SKILL.md §4 ✋과 decision-rights B-2다.

**할 일의 순서**

1. **담당은 허브(main 코디네이터)다.** 도구·하네스 결함은 A-2의 S1 위임에 속하므로 owner에게 묻지 않는다. 워크트리 작업자는 `escalation`과 증거를 허브에 보내고, 직접 고치지 않는다.
2. **지금은 main에 커밋하지 않는다.** 병합 대기 중에는 main 커밋을 병합 뒤로 미룬다. 이는 도구 수정과 메모리 갱신에 모두 적용한다. 검증된 커밋의 fast-forward 경로와 승인 대상 SHA를 보존한다.
3. **장애 프로젝트 쪽은 계속 진행한다.**
   - 허브가 증거와 재현 조건을 확인하고 원인이 도구 결함임을 가린다.
   - 되돌릴 수 있는 우회를 쓰고, 독립 작업을 이어간다.
   - 필요하면 격리된 도구 사본(main 밖)에서 수정을 시험한다. 사본에서만 검증하고 main은 건드리지 않는다.
4. **병합 대기 프로젝트는 기존 도구로 먼저 병합한다.**
   - 허브가 main에서 `pace project merge P###` 미리보기를 확인한다.
   - 미리보기 커밋 전체 SHA를 owner 승인 원문과 대조한다. 일치하면 `--yes`를 입력하고, 없거나 다르면 입력을 보류하고 승인을 요청한다.
5. **병합 뒤에 도구 수정을 한다.** 허브가 main에서 고치고 검사한 뒤 커밋한다. 필요하면 재설치한다. 그 뒤 장애 프로젝트에 결정·근거·재검증 기준을 회신한다. 작업자는 `(main 판단)`으로 기록하고 재검증해서 재개한다.
6. **기록:** `pace project log`에 결정을 남한다. 도구 수정과 메모리 갱신은 병합 뒤 커밋에 함께 넣고, 사후 요약 한 줄을 완료 보고에 붙인다.

**질문과 승인 대기 수**
- owner 질문: 0건. A-1~A-5에 모두 해당하지 않는다.
- 새 승인 대기: 0건. 병합에 쓰는 승인은 이미 있는 것이다. 없으면 병합 입력만 보류하며, 이는 도구 수정과 별개다.
- 도구 수정 때문에 멈추는 일은 없다. 수정은 병합 뒤로 미룰 뿐이다.

**경계:** 병합 전에 main을 커밋하거나 수정하지 않는다. 필수 검사를 약화하지 않는다. 같은 결함이 병합을 막는 경우에만 격리 사본 검증과 기존 게이트를 유지하는 복구 경로를 찾는다. 그 경로도 막히면 해당 작업만 보류한다. 합의 변경이나 새 승인이 필요한 차선만 A로 요청한다.

**자동 첨부·읽은 범위:** 자동 첨부로 userEmail 컨텍스트를 받았다. 읽은 파일은 `skills/pace-project-dev/SKILL.md` 1–93줄 전체와 `references/decision-rights.md` 1–46줄 전체다. 전체 바이트는 도구로 확인하지 않아 적지 않는다.
