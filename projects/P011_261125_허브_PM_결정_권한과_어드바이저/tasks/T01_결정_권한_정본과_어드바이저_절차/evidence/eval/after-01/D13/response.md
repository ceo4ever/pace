**전제:** 이 시험은 읽기 전용이라 아래 명령은 하나도 실행하지 않았습니다. 질문을 보내지도 않았고, 파일 수정·기록·메모리 갱신·커밋도 하지 않았습니다. 아래는 상황이 발생했을 때 할 일의 순서입니다.

## 사례 1. TASK 사전 검토에서 다른 제공자를 쓸 수 없고 같은 제공자는 가능한 경우

- **담당:** 워크트리 PM이 맡습니다. 작성자와 다른 제공자를 먼저 시도하는 쪽도 PM입니다. 이 대체는 기존 위임(B1)이라 A-3에 걸리지 않으므로 결정 주체는 PM입니다.
- **순서와 명령**
  1. 다른 제공자로 `pace agent verify --kind task --author-agent <claude|codex> --target <TASK.md> --purpose-file <상위 목적 글> --out <기록>`을 호출합니다. 종료 10(미실행)을 받습니다.
  2. 미실행 사유와 출력 사본(`--out`)을 `evidence/`에 남기고 `pace project log`에 기록합니다.
  3. 같은 대상에 `pace agent verify --kind task ... --allow-same-provider`를 실행하거나 호스트의 별도 새 세션으로 검토합니다. 이 검토는 `cross: false`로 기록합니다. 제공자를 몰래 바꿔 쓰지 않습니다.
  4. 1단계에는 상위 목적과 TASK.md만 줍니다. 첫 판단을 받은 뒤 2단계에서 PROJECT와 브리프를 줍니다.
  5. 결과가 fail이면 지적을 반영하고 `verify`를 다시 호출해 자동 재검토를 받습니다. 한 검토 주기 안에서는 경로를 섞지 않습니다.
  6. `PRE-REVIEW.json`에 시도를 순서대로 적습니다.
     - 다른 제공자의 `unavailable` 시도는 이유와 증거를 붙입니다.
     - 같은 제공자 시도는 `cross:false`로 적습니다.
     - 증거는 `review-records/R<n>.json`입니다.
  7. 마지막 항목이 pass(blocking 0)이고 현재 TASK 해시와 일치할 때만 구현합니다.
- **질문·승인 대기:** 0건입니다. 단, 실행된 교차 검토가 fail이면 같은 제공자 대체로 해소할 수 없습니다.

## 사례 2. 백로그 검토에서 다른 제공자를 쓸 수 없고 같은 제공자는 가능한 경우

- **담당:** 백로그 작성 PM이 맡습니다. 결정 주체는 사례 1과 같은 이유로 PM입니다.
- **순서와 명령**
  1. `pace agent verify --author-agent <..> --target <BACKLOG 파일> --purpose-file <상위 목적 글> --out <기록>`을 호출합니다. 종료 10을 받습니다.
  2. 미실행 사유를 기록합니다.
  3. `--allow-same-provider` 또는 호스트의 별도 새 세션으로 상위 목적 우선의 독립 검토를 합니다. 결과에 `cross: false`를 기록합니다.
  4. blocking, should_fix, note마다 반영 여부와 이유를 남깁니다.
  5. 목표나 전략 이견이 합의를 바꾸는지 A-1로 판정합니다.
  6. 원본 문서를 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행합니다.
- **질문·승인 대기:** 0건입니다.

## 사례 3. 다른 제공자와 같은 제공자 새 세션을 모두 호출할 수 없는 경우

- **담당:** PM이 A-3으로 판정하고 owner가 결정합니다. 작업자는 `ask`로 코디네이터에게 인계하고, 허브가 owner에게 결정을 요청합니다. 단독 PM은 직접 요청합니다.
- **순서**
  1. 양쪽 미실행 증거(사유와 출력)를 기록합니다.
  2. 사전 검토 관문을 보류합니다. TASK 쪽은 구현하지 않습니다. 백로그 쪽은 검토를 마친 것으로 처리하지 않습니다.
  3. 독립 작업은 이어갑니다.
  4. A-3 번호와 함께 결정 요청을 한 건 보냅니다. 요청에는 확인한 증거와 남은 불확실성을 적고, 선택지와 추천을 붙입니다.
- **경계**
  - 검토를 생략하거나 PM이 스스로 pass 처리해서는 안 됩니다.
  - 검토가 한 번도 실행되지 않았다면 PRE-REVIEW `waiver`는 성립하지 않습니다.
  - owner가 답하면 실행 전 승인 확인으로 원문과 현재 TASK 해시를 대조한 뒤 기록합니다.
- **질문·승인 대기:** TASK 검토와 백로그 검토 중 해당하는 쪽마다 결정 요청 1건과 대기 1건이 생깁니다. 둘 다 막혔다면 2건입니다. 단, 한 번에 묶어 보낼 수 있으면 1건으로 줄입니다.
