## 판단

"상황" 항목이 제목만 있고 내용이 비어 있습니다. 사례가 없어서 담당, 명령, 승인 대기를 하나로 정할 수 없습니다. 임의로 사례를 만들면 SKILL.md의 규모 판단(§1)을 건너뛰게 되므로 만들지 않았습니다.

## 사례가 주어졌을 때 할 일의 순서 (SKILL.md 기준)

1. **규모 판단 (§1)**: 작은 일, 태스크 없는 프로젝트, L 프로젝트 중 하나로 분류합니다.
   - 작은 일: 프로젝트 없이 바로 고치고, 저장소 검사 명령을 돌린 뒤 커밋합니다.
   - 태스크 없는 프로젝트: PROJECT.md와 PROJECT-CLOSE.md만 씁니다.
   - L 프로젝트: 태스크로 나눕니다.
2. **main에서 프로젝트 준비 (§2)**:
   - 담당: 프로젝트를 맡은 에이전트(PM)가 합니다.
   - 명령: `pace project new "<이름>" [--from ...]`
   - 분석과 설계를 PROJECT.md에 쓰고, 결정 메모에 출처와 함께 남깁니다.
   - 백로그나 대화로 이미 확정된 내용이면 승인 답을 기다리지 않고 `pace project start P###`를 실행합니다.
   - main에서 worktree 파일을 절대 경로로 고치지 않습니다.
   - Orca 안이면 worktree 작업자를 띄우고 이 세션은 코디네이터가 됩니다.
3. **worktree에서 태스크 수행 (§3)**:
   - 단계는 분석 → 설계 → 구현 → 테스트 → 마감 순입니다.
   - 설계 뒤에는 별도 reviewer의 사전 검토(blocking 0)가 있어야 구현합니다.
   - 테스트 단계에서는 tester와 reviewer를 새 맥락으로 배정합니다.
   - 마감은 `pace project check`, `pace project done` 순서로 하고, 메모리 갱신(`pace memory status --project --body ...`)과 `feat(P###/T0n): …` 커밋을 같은 커밋에 넣습니다.
4. **마감과 병합 (§4)**:
   - PROJECT-CLOSE.md를 쓰고 `pace project finish P###`를 실행한 뒤 자체 판단 대조를 합니다.
   - ✋ merge는 허브가 owner 승인 원문과 미리보기를 대조한 뒤에만 실행합니다. Orca 작업자는 `worker_done`으로 끝냅니다.
   - ✋ 배포가 있으면 별도 승인을 받습니다.
5. **결정 범위 밖의 일 (§6)**: 기준이나 범위가 바뀌면 `ask`로 코디네이터에게 넘기고, 해당 조치만 보류한 채 독립 작업은 계속합니다.

## 대기 수

- 질문: 사례 내용을 요청하는 1건.
- 승인 대기: 0건. 실제 행동은 하지 않았습니다.
- 사례가 주어지면 merge와 배포에 승인 대기가 각각 최대 1건씩 생깁니다.

## 첨부와 읽은 범위

- 자동 첨부: 사용자 이메일(userEmail) 컨텍스트를 받았습니다. 본문에서는 사용하지 않았습니다.
- 읽은 파일: `skills/pace-project-dev/SKILL.md` 1~93줄 전체. 이 파일 외에 읽은 파일은 없습니다.
- references는 사례가 비어 있어 열지 않았습니다.
- 전체 바이트 수는 확인하지 않았으므로 적지 않습니다.
