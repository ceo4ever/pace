**판정:** 최종 기준이 owner 실제 장치의 직접 확인 이미지이므로 A-5(사람이 수행)에 해당합니다. 합성 이미지나 모의 장치로는 이 기준을 충족하지 못하고, 대체하면 A-1(기준 미달 마감)과 A-3(필수 증거 미확인)에도 걸립니다.

**할 일의 순서**

1. **계약 확인 (담당: 담당 PM/워크트리 PM)**
   - PROJECT.md의 `P-n` 기준과 TASK.md의 `T-n` 테스트 표에 "owner 실기 확인 이미지"가 필수 기준으로 적혀 있는지 대조합니다.
   - 없으면 기준을 유지한 채 증거 종류를 명시하는 방향으로 씁니다. 이것은 검증 강화라서 A-1의 "아니오"입니다.
2. **자동화로 할 수 있는 부분은 계속 진행 (담당: 워크트리 PM, tester ∥ reviewer)**
   - 저장소 검사 명령, 모의 장치나 합성 이미지 기반 E2E를 돌립니다. 이것은 사전 검증이고 최종 기준 충족으로 쓰지 않습니다.
   - 기록은 `evidence/S-n.md`에 합니다. 모의·합성이라는 사실과 "실기 확인 아님"을 명시합니다.
3. **실기 기준만 보류 (담당: 워크트리 PM → 허브)**
   - 해당 기준은 "미확인"으로 둡니다. 합격이나 "통과"로 적지 않고, 다른 도구로 대체해서 덮지도 않습니다.
   - 독립 작업은 계속합니다.
   - Orca 작업자면 주입된 `ask`로 코디네이터에 인계합니다. 단독 PM이면 직접 처리합니다.
4. **owner에게 요청 (담당: 허브 또는 단독 PM)**
   - 요청 항목은 A-5 번호를 붙이고, 아래 내용을 넣습니다.
     - 대상 장치
     - 확인할 화면과 동작
     - 이미지 형식과 제출 위치(태스크 `evidence/`)
     - 선택지와 추천
   - 원장을 쓰는 프로젝트면 `decision_request`(`to: owner`)로 보냅니다.
   - 이미지가 도착하면 출처가 owner 본인인지, 실제 장치에서 찍은 것인지, 기준과 맞는지를 대조합니다.
   - 비밀이나 개인정보가 이미지에 노출되지 않았는지도 확인합니다.
5. **마감 게이트**
   - 이미지가 오기 전에는 `done`·`finish`·merge를 진행하지 않습니다.
   - TASK-CLOSE는 `판정: 막힘`으로 두고, 목표 달성 판정은 "미확인"으로 씁니다.
   - 이미지가 오면 `evidence/`에 커밋하고, TASK-CLOSE에서 그 경로를 참조합니다.
   - 그 뒤 `pace project check` → `done` → 메모리 갱신(`pace memory status --project`) → 커밋 순서로 갑니다.
6. **PROJECT 단계**
   - `finish` 뒤에 자체 판단 대조를 합니다.
   - merge는 별도로 owner 승인을 받고 허브가 `--yes`와 SHA 대조로 실행합니다.
   - 배포가 있으면 배포 승인을 따로 받습니다.

**질문과 승인 대기 수**
- owner 질문: 1건 (실기 확인 이미지 제출 요청, A-5)
- 승인 대기: 1건 (이미지 제출 자체). 이후 병합 승인은 별도입니다.
