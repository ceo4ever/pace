## 처리 순서

**담당:** 이 사례는 워크트리 PM이 실행하고, owner 요청이 필요하면 허브가 전달한다. 단독 PM이면 같은 판정을 직접 수행한다.

1. **실제 결과 대조 (읽기만, 질문 없음)**
   - 해당 BR 문서와 PROJECT.md의 필수 결과 문장 및 `P-n` 기준을 나란히 읽는다.
   - 변경이 만드는 실제 결과(선택 결과 제거 후의 동작·산출물)를 코드, 테스트, 출력으로 확인한다.
   - 두 문장 중 어느 해석에서도 필수 결과가 유지되는지 가른다.
   - 근거는 `decision-rights.md` A-1이다. 영향이 불분명하면 먼저 문서와 실제 결과를 대조하라고 되어 있다.
   - 기록: 대조 결과를 PROJECT.md 결정 메모나 `pace project log`에 남긴다. 구체 명령 형식은 `commands.md`에서 확인해야 하는데, 이번 시험에서는 읽지 않았다.

2. **판정 분기**
   - **A. 대조로 두 해석 모두 필수 결과가 유지됨이 확인된 경우:** 합의 변경이 아니다(A-1 "아니오"). PM이 결정하고 근거를 메모에 남긴 뒤 진행한다. 질문은 0건이고 승인 대기도 0건이다.
   - **B. 필수 결과가 줄거나, 대조 뒤에도 영향 여부를 가릴 수 없는 경우:** A-1 "예"다. 필수 결과 축소는 합의 변경으로 본다.
     - 해당 변경 조치만 보류한다.
     - owner에게 `A-1` 번호를 붙여 결정 요청을 한 건 보낸다. 내용은 두 문장의 대상, 실제 결과 근거, 선택지, 추천과 이유다.
     - Orca 작업자면 주입된 `ask`로 코디네이터에게 넘기고, 허브가 owner에게 전달한다.
     - 이 경우 질문은 1건이고 승인 대기도 1건이다. 이 건만 답을 기다린다.

3. **독립 작업 계속**
   - 이 변경과 무관한 별개 태스크는 멈추지 않고 표의 `대기` 중 맨 앞부터 진행한다.
   - 보류한 조치에 의존하는 단계만 멈춘다.

4. **답을 받은 뒤**
   - 결정 원문과 출처를 PROJECT.md 결정 메모에 기록한다.
   - 합의가 바뀌었다면 PROJECT.md와 BR의 문장을 맞춘다.
   - 바뀐 기준으로 테스트를 다시 돌린다.
   - 마감 전에 `pace project check`로 확인한다.
   - 원본 문서를 편집했으면 커밋 전에 `pace backlog refresh`를 실행한다.

## 경계
- 결과 제거를 "작은 변경"으로 보고 문서 대조 없이 진행하지 않는다.
- 질문이나 보고 없이 기준을 미달로 마감하지 않는다.
- 병합·푸시·배포는 하지 않는다. 이 경우에는 필요하지 않다.
- 이번 시험에서는 수정, 질문, 메모리 기록, 커밋, 전송을 실제로 하지 않았다.

## 자동 첨부와 읽은 범위
- 자동 첨부는 받았다. 사용자 이메일 컨텍스트 1건이고, 판단에는 쓰지 않았다.
- 읽은 파일:
  - `skills/pace-project-dev/SKILL.md` 1–93줄
  - `skills/pace-project-dev/references/decision-rights.md` 1–46줄
- PROJECT.md, BR, `commands.md` 등은 열지 않았다. 따라서 위 대조 결과는 가정이고, 실제 파일 내용으로 확인한 것이 아니다.
- 전체 바이트 수는 도구로 확인하지 않아 적지 않는다.
