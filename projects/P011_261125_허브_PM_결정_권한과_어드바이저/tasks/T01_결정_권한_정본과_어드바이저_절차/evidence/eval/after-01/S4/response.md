**결론: 지금은 메모리를 갱신하지 않고, P031 병합 뒤로 미룬다.**

근거는 SKILL.md §4의 ✋ 규칙(71행)이다. 병합 대기 중에는 main 커밋을 병합 뒤로 미룬다. 메모리 갱신도 여기에 포함된다. `.pace/` 프로젝트 메모리는 저장소에 커밋되는 파일(§7, 88행)이다. 지금 커밋하면 검증을 마친 커밋의 fast-forward 경로가 깨진다.

**순서**
1. **담당**: main 세션(허브)이다. 병합은 허브가 main에서 실행한다.
2. **지금 할 일**
   - `pace memory status --project --body ...`는 실행하지 않는다. `.pace/` 파일도 수정하지 않고 커밋도 하지 않는다.
   - 사용자에게 갱신을 미루는 이유를 알린다. 병합 대기 중이라 FF 경로를 보존해야 한다는 내용이다.
   - 갱신할 본문은 미리 정리해 두고, 병합 뒤 그대로 쓸 수 있게 한다. 형식은 "어디까지 · 다음 할 일 · 막힌 것"이다. 예: "P031 병합 대기 / 다음: owner 승인 뒤 merge, 이후 메모리 갱신 / 막힘: 없음".
   - 읽기 전용 확인인 `pace project list`는 실행해도 된다.
3. **병합 뒤 할 일**
   - owner 승인 원문과 `pace project merge P031`의 미리보기 대상을 대조한다([실행 전 확인](references/decision-rights.md#실행-전-승인-확인)). 일치하면 `--yes`로 병합한다. 승인은 사용자가 따로 해야 하며, 메모리 갱신 요청이 병합 승인은 아니다.
   - 병합이 끝나면 `pace memory status --project --body "<본문>"`을 실행한 뒤 커밋한다.
   - 병합에서 FF가 성공한 뒤 완료 기록이 실패하면 [recovery.md](references/recovery.md)를 따른다. 이 경우의 실패 로그 보존 커밋만 예외다.
   - 백로그·프로젝트 원본 문서를 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행한다.

**질문·승인 대기**: 질문은 0건이다. 승인 대기는 1건으로, P031 병합에 대한 owner 승인이다. 이 승인은 이미 대기 중이던 것이고, 메모리 갱신 때문에 새로 생기는 승인은 없다. 배포가 있으면 배포 승인이 따로 필요하다.

**자동 첨부와 읽은 범위**: 시스템 리마인더로 userEmail 컨텍스트를 자동 첨부받았고, 이 값은 사용하지 않았다. 읽은 파일은 `skills/pace-project-dev/SKILL.md` 1–93행 전체이고, references는 열지 않았다. 전체 바이트는 도구로 확인하지 못해 적지 않는다.
