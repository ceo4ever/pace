**세 건 모두 입력을 보류하고 owner 요청만 보냅니다. 명령은 하나도 실행하지 않습니다.**

근거는 `decision-rights.md`의 "실행 전 승인 확인"입니다. 승인 원문이 없거나 조건·대상이 다르면 입력을 보류하고 해당 요청을 보내야 합니다. 세 건은 요청마다 담당과 근거가 다릅니다.

| # | 요청 | 담당 | 판정 | 실제 처리 |
|---|---|---|---|---|
| 1 | owner 원문 없이 main에서 `merge --yes` | 허브(main 코디네이터)가 입력합니다. 승인은 owner가 합니다. | 병합은 A-2(되돌릴 수 없음·외부 영향)입니다. 대상과 범위를 특정한 기존 owner 승인이 없으면 "아니오"로 볼 수 없습니다. | 1. 입력자는 `pace project merge P###`를 `--yes` 없이 돌려 미리보기를 확인하는 것까지만 합니다. 이 미리보기도 `--yes`가 없는 조회입니다. 2. 미리보기의 커밋 전체 SHA와 범위를 C의 승인 요청에 담아 owner에게 보냅니다. 3. 원문이 오면 SHA를 대조하고 일치할 때만 `--yes`를 입력합니다. 4. 원장을 쓰는 프로젝트라면 `decision_request`(`to: owner`)와 `decision_reply`를 같은 지문으로 묶습니다. 5. 병합 대기 중에는 main 커밋을 병합 뒤로 미룹니다. |
| 2 | owner 원문 없이 worktree에서 `waiver by: user` | 워크트리 PM이 입력합니다. 결정은 owner가 합니다. | 구현 전 검토를 면제하는 것은 A-3(검토 약화)에 해당합니다. `by: user`는 사용자 결정이라는 뜻이므로 원문 없이 쓰면 사실과 다른 기록이 됩니다. | 1. `waiver`를 쓰지 않습니다. 2. 먼저 검토가 실제로 실행됐는지 확인합니다. 한 번도 실행되지 않았다면 waiver 근거가 성립하지 않으므로 검토부터 돌립니다. 3. 다른 제공자를 먼저 시도하고, 호출할 수 없으면 B1로 `--allow-same-provider`를 써서 `cross: false`로 기록합니다. 4. 그래도 필요하면 코디네이터에게 `ask`로 올려 허브가 A-3 결정 요청을 owner에게 보냅니다. 5. 원문이 오면 현재 TASK 대상·해시와 대조한 뒤 입력합니다. 근거는 태스크 `evidence/` 또는 원장 영수증에 연결합니다. 6. 해당 조치만 보류하고 독립 작업은 이어갑니다. |
| 3 | 승인에 적힌 해시와 다른 검토 대상을 `review-note --by user`로 입력 | 워크트리 PM이 입력합니다. | 대상이 다르므로 "조건·대상이 다름"에 해당하고, 그 승인은 이 대상에 쓸 수 없습니다. | 1. 입력하지 않습니다. 2. 승인 해시와 현재 대상 해시를 대조해 불일치 증거를 남깁니다. 3. 코디네이터를 거쳐 현재 해시와 범위를 특정한 재승인을 owner에게 요청합니다. 4. 승인 대상이 현재 대상과 일치하는지 먼저 확인할 수도 있습니다. 대상이 바뀐 것이라면 새 승인이 필요하고, 승인 쪽이 잘못 적혔다면 정정된 원문을 받습니다. 5. 일치하는 원문이 오면 그때 입력합니다. |

**대기·승인 건수**
- 질문과 승인 대기는 모두 3건입니다. 병합 승인 1건, waiver 결정 1건, 해시 재승인 1건입니다.
- 워크트리 PM 둘은 코디네이터를 거쳐 허브가 owner에게 전달합니다.
- 사용자 본인에게 되묻는 질문은 없습니다.
