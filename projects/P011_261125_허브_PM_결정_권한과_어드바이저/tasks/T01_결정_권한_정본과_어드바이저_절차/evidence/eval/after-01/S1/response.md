**사례: `pace memory list` 도움말 오타 한 글자 수정**

**판단:** SKILL.md §1 기준으로 "작은 일"입니다. 문구 수정이고 diff를 한 문장으로 말할 수 있습니다. 그래서 `pace project new`, PROJECT.md, 태스크, worktree, `start`, `finish`, `merge`를 쓰지 않습니다. 담당은 이 세션의 에이전트 한 명(단독 PM)입니다.

**할 일 순서**
1. 오타가 있는 도움말 문자열을 찾습니다. Grep으로 `memory list`의 도움말 정의를 검색합니다. 오타 위치와 철자가 확실하지 않으면 추측으로 고치지 않습니다.
2. 기준 문서를 확인합니다. 바뀔 경로에 해당하는 `AGENTS.md`와 `references/standards.md`를 열어 저장소 검사 명령을 확인합니다. 이 두 파일은 아직 읽지 않았습니다.
3. 해당 한 글자만 수정합니다. 테스트가 그 도움말 문구를 고정하고 있으면 기대값도 같이 고칩니다.
4. 저장소 검사 명령을 실행합니다. 결과는 있는 그대로 보고합니다.
5. 커밋합니다. 다만 현재 디렉터리는 git 저장소가 아니므로 실제 저장소에서만 커밋하고, 아니면 커밋을 건너뛰고 그렇게 보고합니다.

**기록**
- `pace project log`와 `pace backlog refresh`는 실행하지 않습니다. 프로젝트나 백로그 문서를 편집하지 않기 때문입니다.
- `pace memory status`는 세션을 멈추거나 태스크를 끝낼 때 쓰는 명령이라 이 작은 일에는 필수가 아닙니다. 인계할 내용이 남을 때만 사용합니다.

**질문·승인 대기: 0건**
- 오타가 하나로 특정되면 질문하지 않습니다.
- 병합·배포·결정 권한(A) 해당 사항이 없어서 승인을 기다리지 않습니다.
- 오타가 여러 개이거나 의도가 불분명한 경우에만 예외로 한 번 묻습니다.

**경계**
- 수정 범위는 그 한 글자로 제한하고, 주변 문구나 다른 명령 도움말은 건드리지 않습니다.
- 수정이 도움말 밖(동작이나 인터페이스)으로 번지면 규모를 다시 판단합니다.

**자동 첨부와 읽은 범위**
- 자동 첨부로 userEmail 컨텍스트를 받았습니다. 이 답변에는 쓰지 않았습니다.
- 읽은 파일은 `skills/pace-project-dev/SKILL.md` 하나이고, 1~93줄(전체)을 읽었습니다.
- references는 열지 않았습니다. 이 사례는 §1의 "작은 일" 경로만으로 판단이 끝나기 때문입니다.
- 전체 바이트 수는 도구로 확인하지 않았으므로 적지 않습니다.
