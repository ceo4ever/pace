**판단:** 허브가 재현하고 근거를 붙여 회신했고 TASK 범위 안이므로 A-1~A-5에 모두 "아니오"다. owner 질문과 승인은 필요 없다. 허브 결정을 `(main 판단)`으로 적용한 뒤 재검증하고 태스크를 재개한다. 질문은 0건, 승인 대기도 0건이다.

**순서**

1. **담당: 워크트리 PM.**
   - 회신에서 교체 범위, 관련 회귀 검사 명령, 근거, 재검증 기준을 확인한다.
   - TASK.md 계약(`T-n`, 테스트 표)과 대조해서 범위가 계약 안인지 본다. 허브가 이미 정한 사항은 다시 따지지 않는다.
2. **기록(적용 전).**
   - `pace project log P### T0n --type decision --msg "fixture 지연 재현 결과에 따라 교체 범위 <…> 적용" --src "main 판단" [--ref <프로젝트 내 근거 파일>]`
   - 원문 출력과 비밀은 복제하지 않는다.
3. **담당: 워크트리 PM(구현).**
   - 허브가 정한 범위의 fixture만 교체한다. 범위를 넓히지 않는다.
   - 선언된 저장소 검사 명령 체계는 그대로 쓴다.
4. **재검증.**
   - 허브가 정한 관련 회귀 검사 명령을 그대로 실행하고 종료 코드와 결과 위치를 남긴다.
   - 필요하면 저장소 검사 명령과 E2E도 돌린다. 변경 범위가 달라졌으므로 재검사 사유가 성립한다.
   - 재검사의 사유·범위·담당을 기록한다.
   - 전에 통과한 같은 대상의 검사는 반복하지 않는다.
   - 테스트 단계라면 tester ∥ reviewer를 새 맥락으로 다시 배정한다.
   - `escalation` 출력이 있으면 그것을 먼저 따른다.
5. **기록(적용 후).**
   - 결과를 `--type review` 또는 `change`로 같은 태스크 번호에 남긴다.
   - 공동 시도 1회(허브 회신 → 워크트리 적용 → 재검증)를 센다. 상한은 2회다.
6. **재개.**
   - 통과하면 태스크를 이어서 진행한다. TASK-CLOSE 작성 → `pace project check` → `done` → `pace memory status --project --body ...` 갱신 → 커밋 `feat(P###/T0n): …` 순서다.
   - 메모리는 같은 커밋에 넣는다.
7. **실패하거나 증거가 부족할 때.**
   - 같은 실패가 3회 반복되거나 재검증이 실패하면 근거와 함께 허브에 `ask`로 인계한다.
   - 2회 뒤에도 풀리지 않으면 되돌릴 수 있는 차선을 택한다. 필수 태스크 보류나 기준 미달 마감이 되면 A-1이므로 해당 조치만 보류하고 독립 작업은 이어간다.

**경계**
- 푸시·병합·배포·외부 전송은 하지 않는다. 병합은 허브가 owner 승인 뒤 수행한다.
- 검사·독립 검토를 생략하거나 약화하지 않는다.
- main 파일을 절대 경로로 고치지 않는다.
- 도구·하네스 수정은 허브 몫이다.
- 허브 회신 범위를 벗어나 합의 목적·기준이 바뀌면 그 조치를 보류하고 `ask`로 올린다.

**첨부·읽은 범위**
- 시스템이 자동 첨부한 것은 userEmail 컨텍스트 하나다. 이 시험에서는 쓰지 않았다.
- 읽은 파일은 다음과 같다.
  - `skills/pace-project-dev/SKILL.md` 1–93줄(전체)
  - `references/decision-rights.md` 1–45줄(전체)
  - `references/verification.md` 1–18줄(전체)
  - `references/commands.md`는 grep으로 1–15줄 부근만 확인했다.
- 전체 바이트 수는 도구로 확인하지 않았으므로 적지 않는다.
