**상황 해석.** 같은 대상을 반복 검토하다가 연속 fail 3회로 `escalation.stage: diagnose`가 나왔다. 진단 결과 근본 조치가 합의된 목적·범위·완료 기준(`P-n`)을 바꿔야 한다. 이는 A-1에 해당하므로 PM이 단독으로 정할 수 없고 owner 결정이 필요하다.

**순서**

1. **그 호출에서 바로 멈춘다.** 담당은 워크트리 PM이다. 다음 호출의 종료 16을 기다리지 않고, 재검토를 더 돌리지 않으며 땜질 수정도 하지 않는다.
2. **증거를 모은다.** 담당은 워크트리 PM이다. verify 출력, 원장의 fail 원문, 차수별 blocking 추이를 모아 원인 층(structure, planning, design, other)을 가린다. 이어서 PROJECT.md·브리프의 합의와 실제 조치를 대조해 A-1에 해당함을 확인한다.
3. **허브에 인계한다.** 담당은 워크트리 PM이다. 세 차례의 근거와 진단을 `ask`로 허브에 보낸다. 허브는 B에 따라 재현하고 근거를 확인한다.
4. **owner에게 요청한다.** 담당은 허브이고 형식은 C를 따른다. 요청에는 "A-1"과 6요소를 붙인다.
   - 6요소: 대상, 실패 추이, 진단과 고친 층, 남은 지적의 성격, 선택지, 추천과 이유
   - 선택지는 범위 조정, 기준 유지 후 고쳐서 다시 검토, 이슈로 남기고 마감 등이다.
   - 원장을 쓰면 `decision_request`(`to: owner`)로 보낸다.
5. **해당 조치만 보류한다.** 합의 변경이 필요한 조치만 멈추고, 합의에 영향이 없는 독립 작업은 계속한다.
6. **승인 원문을 대조한다.** 담당은 워크트리 PM이다. owner 답이 오면 원문, 현재 대상, 해시를 대조한다. 조건이나 대상이 다르면 입력을 보류하고 다시 요청한다. 대조가 맞으면 아래 명령으로 기록한다.
   - `pace agent review-note --target <대상> --decision --by user --choice <선택> --summary <사유> --file <승인 근거>`
   - 진단 기록은 별도다: `pace agent review-note --target <대상> --diagnosis --layer <층> --summary <진단·조치> --file <진단 증거>`
   - 합의가 바뀌면 PROJECT.md 결정 메모와 기준을 갱신한다.
7. **수정하고 전체 재검증한다.** 담당은 워크트리 PM이다. 승인 뒤에만 수정하고, 진단 뒤 첫 verify는 새 기준의 전체 검토로 돈다. PRE-REVIEW waiver는 사용자만 줄 수 있다.
8. **보고하고 기록한다.** 사용자 경로는 수정 전에 6요소를 보고하고, 결정 원문, 승인 직전 해시, 승인 뒤 첫 수정 기록을 연결한다. 사후에는 TASK-CLOSE 리뷰 절에 남기고, `pace memory status --project`로 진행 기록을 갱신한다.
9. **마감 조건을 확인한다.** 검토가 pass여도 계약 목표가 미달이거나 미확인이면 `판정: 막힘`으로 두고 done하지 않는다.

**경계.** 병합, 푸시, 배포는 하지 않는다. 승인 대기 중에는 main 커밋도 하지 않는다. 같은 영역이 또 지적되면 원인 층을 다시 진단한다.
