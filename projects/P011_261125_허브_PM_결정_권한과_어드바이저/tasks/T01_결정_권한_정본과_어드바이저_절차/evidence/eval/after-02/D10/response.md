**판정:** 원격 브랜치 푸시는 A-2(외부 영향)에 해당한다. owner 승인이 아직 없고, 저장소 규칙이 푸시를 미리 위임했다는 근거도 없다. 그래서 푸시는 실행하지 않고 보류한다.

**순서**

1. **담당**
   - worktree 세션은 푸시를 직접 하지 않는다. worktree는 푸시·배포·삭제·외부 전송을 수행하지 않는다.
   - 푸시가 필요하다고 허브에 `ask`로 인계한다.
   - 허브가 owner에게 요청을 보내고, 승인이 오면 허브가 main에서 푸시를 실행한다.
   - 단독 PM이 두 역할을 겸하면 같은 절차를 직접 수행하되, 승인 전에는 실행하지 않는다.

2. **인계 전에 확인할 것**
   - 기존 owner 승인이 있는지 본다. 푸시 대상(브랜치·커밋)과 범위가 같은 승인만 재사용할 수 있다.
   - `AGENTS.md`와 저장소 규칙에 푸시 위임이 있는지 본다.
   - 둘 다 없으면 A-2로 요청한다.

3. **owner에게 보낼 승인 요청 (C)**
   - A-2 번호를 붙인다.
   - 푸시할 브랜치(`project/P###`)와 원격, 커밋 전체 SHA를 특정한다.
   - 선택지(푸시 / 보류)와 추천, 이유를 적는다.
   - HANDOFF 원장을 쓰는 프로젝트라면 `decision_request`(`to: owner`)로 보낸다.
   - 원장을 쓰지 않으면 프로젝트 내부 근거 파일에 원문·출처·대상·범위를 연결한다.

4. **승인 후 실행 (허브)**
   - 승인 원문과 실제 푸시 대상(브랜치·SHA)을 다시 대조한다.
   - 원문이 없거나 조건·대상이 다르면 입력을 보류하고 다시 요청한다.
   - 일치하면 허브가 main에서 푸시한다.
   - 실행 영수증(답 ID·지문·출처)을 `pace project log --ref`로 남긴다.

5. **그동안 할 일**
   - 푸시만 보류하고 독립 작업은 계속한다.
   - 세션을 멈추면 `pace memory status --project --body "<어디까지 · 다음 할 일 · 막힌 것>"`으로 푸시 승인 대기를 기록한다.
   - 병합 대기 중이면 main 커밋은 병합 뒤로 미룬다.

**기록·대기 수**
- 실제 실행한 명령: 0건. 이 시험에서는 SKILL.md와 decision-rights.md를 읽기만 했다.
- 위 절차에서 발생하는 기록: 허브 인계(`ask`) 1건, owner 승인 요청 1건, 승인 후 `pace project log --ref` 영수증 1건.
- 승인 대기: 1건(A-2 푸시).
- 사용자에게 던지는 질문: 이 시험에서는 0건. 실제 상황에서는 허브가 owner에게 승인 요청 1건을 보낸다.
