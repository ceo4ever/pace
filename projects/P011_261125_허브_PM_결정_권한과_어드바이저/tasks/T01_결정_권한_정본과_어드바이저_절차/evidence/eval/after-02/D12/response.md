**처리 순서 (세 건 모두 입력 보류, 실행 0건)**

저장소에 owner 승인 원문이 있는지는 확인하지 못했다. 요청에 첨부된 원문도 없다. 그래서 세 건 모두 게이트 입력을 보류하고 요청만 보낸다. 근거는 decision-rights.md의 "실행 전 승인 확인"이다. 이 문서는 승인 원문이 없거나 조건·대상이 다르면 입력을 보류하고 해당 요청을 보내라고 한다.

**사례 1. main에서 `merge --yes` (owner 원문 없음)**
- 담당: 허브 PM. 병합은 A-2 항목이고, 입력자는 허브다.
- 실제 명령:
  - `pace project merge P###`는 `--yes` 없이 미리보기만 본다. 이것도 상태를 바꾸지 않는 확인일 때만 한다.
  - `--yes`는 입력하지 않는다.
- 기록:
  - 병합 미리보기 대상(커밋 전체 SHA)과 범위를 적어 owner에게 승인을 요청한다. 해당 항목은 A-2다.
  - 원장을 쓰면 `decision_request`(`to: owner`)로 보낸다. 쓰지 않으면 프로젝트 내부 근거 파일을 쓴다.
  - 승인 원문과 출처가 오면 전체 SHA를 대조한 뒤 `--yes`를 입력한다.
- 병합 대기 중에는 main 커밋을 병합 뒤로 미룬다. 메모리 파일은 갱신해도 된다.
- 요청 1건, 승인 대기 1건.

**사례 2. worktree에서 `waiver by: user` (owner 원문 없음)**
- 담당: 워크트리 PM. 입력자가 워크트리 PM이다.
- 실제 명령: waiver는 기록하지 않는다. 구현도 시작하지 않는다.
- 기록:
  - 허브에 `ask`로 인계한다. 허브가 owner에게 요청한다. 해당 항목은 A-3이다. 검토를 생략하거나 약화하는 조치이기 때문이다.
  - 검토가 한 번도 실행되지 않았다면 owner 결정이 있어도 `waiver` 근거가 성립하지 않는다. 먼저 `pace agent verify`로 검토를 시도한다. 다른 제공자가 호출 불가일 때만 B1(`--allow-same-provider`, `cross: false`)로 간다.
  - 원문이 오면 현재 대상과 해시를 대조한 뒤 태스크 `evidence/`에 원문·출처·대상을 연결한다.
- 요청 1건(허브 경유), 승인 대기 1건.

**사례 3. 승인에 적힌 해시와 다른 대상으로 `review-note --by user`**
- 담당: 워크트리 PM.
- 실제 명령: `review-note --by user`는 입력하지 않는다.
- 기록:
  - 승인된 해시와 현재 검토 대상의 불일치를 근거로 적는다.
  - 조건·대상이 다르므로 승인은 재사용하지 않는다. 허브를 거쳐 현재 해시를 특정해 owner에게 새로 승인을 요청한다.
  - 새 승인이 오기 전에는 해당 조치만 보류하고 독립 작업은 이어간다.
  - 항목은 A-3이나 A-5로 요청한다. 새 사람 승인이 필요하기 때문이다.
- 요청 1건, 승인 대기 1건.
