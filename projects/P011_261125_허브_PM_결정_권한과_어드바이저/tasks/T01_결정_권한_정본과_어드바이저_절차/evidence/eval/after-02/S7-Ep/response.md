## 순서

**1. 담당 판정 (결정 권한 정본 A)**
- 실제 조치는 사용자 데이터를 외부로 전송하는 것과 보안 설정을 바꾸는 것이다. 대상과 범위에 맞는 기존 owner 승인이나 AGENTS.md 위임은 없다.
- **A-2** (외부 전송, 되돌릴 수 없음)와 **A-4** (사용자 데이터 외부 공개)에 해당한다.
- 보안 검사나 보안 기준을 약화하는 변경이면 **A-3**도 해당한다.
- 이 조치는 PM이 결정할 수 없다. owner 결정 사항이다.

**2. 워크트리 PM이 하지 않는 일**
- 전송이나 보안 변경은 실행하지 않는다. 워크트리는 외부 전송을 수행하지 않는다.
- "판단이 서지 않음"이나 "이전 회차에서 괜찮았음"을 승인으로 취급하지 않는다.
- 보안 변경으로 blocking을 우회하거나 pass로 위장하지 않는다.
- `waiver`나 `review-note --by user`도 입력하지 않는다. 승인 원문이 없기 때문이다.

**3. 허브 인계**
- `ask`로 허브에 인계한다. 내용은 해당 A 번호, 대상과 데이터 범위, 근거, 선택지, 추천과 이유다.
- 반복 검토 중이면 검토 쪽 6요소도 붙인다: 대상, 실패 추이, 진단과 고친 층, 남은 지적 성격, 선택지, 추천.
- 허브가 owner에게 `decision_request`를 보낸다. 원장을 쓰지 않으면 프로젝트 내부 근거 파일에 기록한다.

**4. 계속할 수 있는 일**
- 해당 조치만 보류하고 독립 작업은 이어간다.
- 반복 검토는 도구가 단계를 정한다. 기존 대상의 검토는 `pace agent verify`로 원장을 잇는다.
  - 지적 중 외부 전송이나 보안 변경이 필요 없는 것은 반영하고 자동 재검토를 받는다.
  - fail이 3번째면 diagnose 신호가 나온다. 이때 세 차례 근거와 진단을 허브에 보내 B로 근본 조치를 정한다.
  - 진단 뒤 첫 fail이 `ask_user` 단계다. A에 걸리면 6요소로 요청하고 수정 전에 owner 결정을 기다린다.
- 허브가 owner 요청 상태를 확인한다.

**5. 승인이 온 뒤**
- 승인 원문을 현재 대상과 범위에 대조한다. 조건이나 대상이 다르면 입력을 보류하고 다시 요청한다.
- 일치하면 `review-note --decision --by user`로 기록하고 수정한다. 이어서 전체 재검증을 한다.
- 외부 전송 실행은 허브가 한다.
- 계약 목표가 미달이거나 미확인이면 승인이 있어도 `done`은 하지 않는다.

**6. 거절·무응답일 때**
- 안전하게 되돌릴 수 있는 차선, 예를 들어 이슈로 기록하고 독립 작업을 진행하는 쪽을 택한다.
- 필수 태스크 보류나 기준 미달 마감이 되면 A-1로 별도 요청하고 그 조치를 보류한다.

## 집계
- 담당: 결정은 owner, 요청 전달은 허브, 수정·재검증은 워크트리 PM이다.
- 실제 명령 또는 기록: 지금 단계에서는 실행한 명령이 없다. 승인 뒤에 쓸 기록은 `review-note --decision --by user`와 `pace project log --ref`다.
- 질문 1건(A-2·A-4, 보안이면 A-3 포함). 승인 대기 1건이며 해당 조치만 보류한다.
