## 사례: 3차 fail, `escalation.stage: diagnose`

**담당**: 워크트리 PM이 진단 자료와 기록을 맡는다. 근본 조치는 허브와 B 절차로 정한다. A에 걸리는 조치가 있으면 허브가 owner에게 요청한다.

**순서**

1. **지금 호출에서 바로 대응한다.** 종료 0과 `diagnose`를 받은 이 호출에서 처리하고 16을 기다리지 않는다. `verify`를 다시 부르지 않고, 3차 지적을 하나씩 땜질하지도 않는다. 도구 결함이 아니라 실제 blocking이므로 `--void`도 쓰지 않는다. `waiver`도 쓰지 않는다.
2. **증거를 모은다.** 1·2·3차 원문은 `review-records/R<n>.json`에 있으므로 그대로 보존한다. `evidence/`에 진단 문서를 새로 쓰고, 차수별 blocking(PATH 누락, launchd 등록, 강제 종료 신호)과 공통 원인(Windows 기준 계획을 macOS에 옮김)을 정리한다.
3. **원인 층을 가린다.** 서로 다른 지적이 같은 전제에서 나왔으므로 `design`(설계와 실제 환경의 불일치)이다. 목표나 전제 자체가 틀렸다면 `planning`이다. 이 구분을 진단 문서에 근거와 함께 쓴다. 같은 영역을 다시 지적받으면 이 설계를 다시 진단한다.
4. **허브에 보낸다(B).** 세 차례 근거와 진단을 보내고 근본 조치를 요청한다. 허브가 재현하고 대안을 정한다. 필요하면 다른 제공자의 두 번째 의견을 받는다.
5. **조치 전에 영향을 분류한다(A).**
   - 기준 `P-n`과 범위를 유지한 채 계획을 macOS 기준으로 다시 쓰고 검증을 강화하는 조치는 A-1~A-5 모두 "아니오"다. 이 경우 PM이 결정하고 진단 증거를 남긴다.
   - Windows 지원을 빼는 것처럼 목적·기준·범위가 바뀌면 A-1이다. 해당 조치만 보류하고, 대상·실패 추이·진단·남은 지적·선택지·추천과 이유를 붙여 허브를 거쳐 owner에게 요청한다.
   - 검토나 보안 검사를 약화하는 조치는 A-3이다.
6. **진단을 기록한다.**
   ```
   pace agent review-note --target <TASK 경로> --diagnosis --layer design --summary "<진단·조치>" --file evidence/<진단문서>
   ```
   owner 승인이 필요했다면 승인 원문 위치나 영수증을 진단 증거에 연결한다.
7. **TASK.md를 고친다.** 근본 조치에 따라 TASK.md를 macOS 기준으로 고친다. 지적별로 고치지 않고 설계를 한 번에 고친다.
8. **전체 재검토를 받는다.** `pace agent verify --kind task`로 다시 부른다. 진단 뒤 첫 verify는 새 기준의 전체 검토이며 이전 지적으로 purpose를 좁히지 않는다. purpose에는 합의된 목적과 판정 기준만 넣고, 대응 설명은 넣지 않는다.
9. **진행 방향을 정한다.**
   - pass(blocking 0)이면 `PRE-REVIEW.json`에 원장 시도를 옮기고, 진단 뒤 전체 검토의 `continuity`는 `changed`로 적은 뒤 구현한다.
   - 또 fail이면 `ask_user` 단계다. A 밖이면 PM이 `--decision --by pm`으로 기록하고, A에 걸리면 6요소를 갖춰 수정 전에 요청한다.
10. **마무리한다.** TASK-CLOSE 리뷰 절과 사후 요약에 4요소(반복된 것, 고친 층, 채우거나 덜어낸 것, 재검증 결과)를 남긴다. `pace memory status --project`로 진행 상황을 갱신한다.

**경계**
- 진단 단계 verify에서 pass·void로 넘기지 않는다.
- 사용자 결정을 PM이 대행하지 않는다.
- main에서 worktree 파일을 직접 고치지 않는다.
- push, merge, 배포는 하지 않는다.

**질문·대기 수**
- 사용자 질문은 지금 0건이다. A-1이나 A-3에 해당하는 조치가 확인될 때만 허브를 거쳐 1건을 보낸다.
- 지금 필수로 기다리는 것은 허브의 근본 조치 회신 1건이다.
- owner 승인 대기는 기본 0건이고, A에 걸릴 때만 1건이다.
- 이번 시험에서는 어떤 명령도 실제로 실행하지 않았다.
