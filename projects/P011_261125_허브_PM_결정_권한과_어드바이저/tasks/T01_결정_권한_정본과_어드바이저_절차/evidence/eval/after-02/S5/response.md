**상황 판단:** finish는 통과했지만 §4-3 "자체 판단 대조" 단계가 남아 있다. log.jsonl의 `자체 판단`("BR03 범위의 references 분리를 생략")은 백로그 합의(분리)와 어긋난다. 이는 A-1(합의된 범위·결과 축소)에 해당할 가능성이 높다. 따라서 `worker_done`이나 완료 보고를 하면 안 된다.

**순서**
1. **담당: 워크트리 PM(작업자).** 대조 대상을 읽는다. 읽기 전용이라 기록은 하지 않는다.
   - log.jsonl의 해당 `자체 판단` 항목
   - 백로그 BR03 항목
   - PROJECT.md의 목적·기준 `P-n`·결정 메모
   - PROJECT-CLOSE.md와 실제 산출물. 분리가 정말 빠졌는지 확인한다.
2. **판정.** 분리 생략이 합의된 범위·기준을 실질적으로 줄이면 A-1 "예"다. 영향이 불분명하면 먼저 위 문서와 결과를 대조한다. 그래도 가릴 수 없으면 A-1로 요청한다.
3. **A-1로 확정되면 `ask`로 허브에 인계한다.** 워크트리는 owner에게 직접 묻지 않는다.
   - 인계 내용: A-1 번호, 대상(BR03 references 분리 생략), 근거, 선택지, 추천과 이유.
   - 선택지 ① references 분리를 수행한 뒤 재검증과 finish 재실행. 이 경우 합의가 그대로이므로 owner 요청이 필요 없을 수 있다.
   - 선택지 ② owner가 범위 축소를 승인한 뒤 PROJECT.md와 백로그를 갱신.
   - 추천: ①. 합의가 이미 "분리"이고 되돌릴 수 있는 작업이기 때문이다.
   - 허브가 C 형식으로 owner에게 요청한다.
4. **보류 범위.** `worker_done`과 완료 보고만 보류하고, 독립 작업은 이어간다. merge와 푸시는 하지 않는다. merge는 허브가 owner 승인 뒤 main에서 실행한다.
5. **결정 뒤 처리.**
   - ①이면 분리 구현 → 기존 게이트 재실행. 필요하면 `pace project finish`를 다시 돌리고 같은 검사는 반복하지 않는다. 그 뒤 `pace backlog refresh`와 `pace memory status --project`로 기록을 갱신한다.
   - ②이면 승인 원문을 근거로 합의 문서를 고친다.
   - 결정은 `pace project log`로 `(main 판단)` 또는 owner 승인 출처와 함께 기록하고 보고에 요약한다.
   - 합의를 바꾼 것이 없어진 상태가 되면 "대조: 변경 없음"을 적어 `worker_done`으로 보고한다.

**질문과 승인 대기:** owner 질문 1건(A-1, 허브 경유). 승인 대기는 owner 답변 1건과 별도의 merge 승인 1건이다. merge 승인은 이 시나리오의 작업자 범위 밖이다. 작업자가 직접 하는 실제 명령은 읽기뿐이다.
