이 시험에서는 아무것도 실행하거나 기록하지 않았고, 아래는 읽은 규칙에 따라 할 일을 순서대로 적은 것이다.

**읽은 범위**
- 자동 첨부: 사용자 이메일 컨텍스트가 자동으로 붙어 있었다. 값은 쓰지 않는다.
- `SKILL.md` 1–93줄 전체, `cross-verify.md` 1–10줄 전체, `task-steps.md` 1–12줄 전체, `decision-rights.md` 1–46줄 전체를 읽었다.
- `commands.md`와 `reviewer.md`, `backlog.md`는 Grep으로 일치한 줄만 봤다. `commands.md` 3·12·14줄과 `reviewer.md` 27·29·99·118·121·123줄이다. `backlog.md`는 일치한 줄이 없었다.
- 전체 바이트는 확인하지 않아서 적지 않는다.

**사례 1: TASK 검토에서 다른 제공자는 불가, 같은 제공자 새 세션은 가능**
- 담당: 워크트리 PM(작성자)이 직접 처리한다. 이 경우는 A-3에 해당하지 않아 PM이 결정한다(B1).
- 순서:
  1. 먼저 다른 제공자를 시도한다. 호출이 안 되면 미실행 사유를 기록한다.
  2. 같은 제공자의 별도 새 세션으로 `pace agent verify`에 `--allow-same-provider`를 붙여 TASK.md를 검토시킨다. 호스트에 별도 새 세션 기능이 있으면 그것을 써도 된다.
  3. 결과에 `cross: false`를 기록한다.
  4. blocking은 고친 뒤 `verify`를 다시 돌린다. pass(blocking 0)이거나 사용자 결정 waiver일 때만 구현한다.
  5. should_fix는 반영하거나 이유를 남긴다.
  6. 대상, 판정, 지적 처리, 검토 방식을 TASK 기록에 남긴다.
- 실제 기록: 미실행 사유와 `cross: false`를 TASK의 PRE-REVIEW 기록과 검토 원장에 남긴다. 계획에 없던 결정이면 `pace project log P### T0n --type decision --msg "…" --src "자체 판단" [--ref …]`도 쓴다.
- 회신·보고: 사후 요약에 "다른 제공자 미실행, 같은 제공자 새 세션으로 대체(cross:false)"를 한 줄 넣는다. 지금 owner에게 보낼 요청은 없다.
- 질문과 승인 대기: 0건.

**사례 2: 백로그 검토에서 다른 제공자는 불가, 같은 제공자 새 세션은 가능**
- 담당: 백로그 작성자. 허브가 main에서 하는 경우도 같고, 별도 승인은 필요 없다.
- 순서:
  1. 다른 제공자를 먼저 시도한다.
  2. 호출이 안 되면 이유와 미실행을 기록한다.
  3. `pace agent verify --author-agent <claude|codex> --target <BACKLOG 파일> --purpose-file <상위 목적 글> --out <기록> --allow-same-provider`로 새 세션 검토를 연다.
  4. 결과에 `cross: false`를 기록한다.
  5. 지적(blocking, should_fix, note)마다 반영 여부와 이유를 남긴다.
  6. 목표·전략 이견은 합의를 바꾸는지 A-1로 판정한다.
- 실제 기록: `--out`으로 지정한 검토 기록 파일에 사유와 `cross: false`를 남긴다. 백로그 원본을 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행한다.
- 회신·보고: 사후 요약에 같은 제공자 대체 사실을 적는다.
- 질문과 승인 대기: 0건.

**사례 3: 다른 제공자도 같은 제공자 새 세션도 모두 호출 불가**
- 이 경우는 A-3 "예"(독립 검토 생략)다. 같은 제공자 대체를 가정해 진행하지 않고, 몰래 대체하거나 검토를 생략하지도 않는다.
- 담당: 작업자는 `ask`로 허브에 넘기고, 허브가 owner에게 요청한다.
- 순서:
  1. 두 경로 모두 미실행이라는 사유와 증거를 기록한다.
  2. 해당 관문만 보류한다. TASK 검토라면 PRE-REVIEW를 보류하고 구현에는 들어가지 않는다. 백로그 검토라면 그 검토를 보류한다.
  3. 독립 작업은 계속한다.
  4. 허브가 `decision_request`(`to: owner`)를 보낸다. 내용은 A-3 번호, 대상과 근거, 선택지, 추천과 이유다. 선택지는 재시도 대기, 호출 환경 복구, 사용자 결정 waiver다.
- 주의: 검토가 한 번도 실행되지 않았으면 PRE-REVIEW `waiver`의 근거가 성립하지 않는다. owner 답이 와도 그것만으로 waiver를 입력하지 않는다. 현재 계약을 다시 확인하고 보완 관측이나 적법하게 변경된 계약에 따라 판정한다. waiver가 가능한 경우에도 owner 승인 원문과 대상, 해시를 대조한 뒤에 `by: user`로 입력한다.
- 보고: owner 응답을 받기 전까지 이 관문은 보류 상태로 보고한다.
- 질문과 승인 대기: owner 결정 요청 1건과 응답 대기 1건. 사례가 TASK와 백로그 둘 다면 각각 1건씩이다.

**공통 경계**
- 파일은 수정하지 않았고, 질문하거나 메모리에 쓰거나 커밋하거나 전송하지도 않았다.
- 다른 사례의 응답, 평가표, TASK, 마감 문서는 읽지 않았다.
