**사례 C(3차 fail, diagnose 단계) 처리 순서**

**담당**
- 담당은 워크트리 PM이다. 근본 조치가 합의 범위 변경(A-1)에 해당하므로 결정 주체는 owner다.
- owner 요청은 허브가 전달한다(decision-rights.md A절, SKILL.md §6).

**순서**
1. 종료 0과 `escalation.stage: diagnose` 신호를 받은 호출에서 바로 대응한다. `verify`를 다시 부르지 않는다. 아직 기록되지 않은 단계에서 호출하면 종료 16으로 차단된다.
2. 세 차수의 원문과 blocking을 `review-records/`에서 모아 원인 층을 가린다.
   - 층은 **design**이다. Windows 기준 계획을 macOS에 옮겼고, 이는 설계와 실제 환경·제품 동작이 어긋난 경우다.
   - 같은 영역이 재지적됐으므로 지적별 땜질은 멈춘다.
3. 근본 조치를 A로 분류한다.
   - 대상 합의(범위·`P-n`) 변경이므로 A-1 "예"다.
   - 다른 A 항목은 해당 없음으로 대조해 기록한다.
4. 세 차례 근거와 진단을 허브에 `ask`로 보낸다.
   - 허브는 B에 따라 재현한 뒤, A-1 owner 결정 요청(C의 6요소)을 보낸다.
   - 6요소는 대상, 실패 추이, 진단과 고친 층, 남은 지적 성격, 선택지, 추천과 이유다.
5. 회신 전까지 범위 변경 조치만 보류하고, 합의에 영향이 없는 독립 작업은 계속한다.
   - 합의 밖 수정은 하지 않는다.
   - 승인 직전 대상 해시(또는 diff 없음)를 기록한다.
6. owner 회신을 받으면 원문과 현재 대상·범위를 대조한다. 어긋나면 입력을 보류하고 다시 요청한다.
7. 승인 원문의 위치나 영수증을 `evidence/`의 진단 증거 파일에 연결하고, 그 내용을 `pace project log`로도 남긴다.
8. 진단을 기록한다.
   ```
   pace agent review-note --target <대상> --diagnosis --layer design --summary "<진단·조치>" --file <진단 증거>
   ```
   - diagnose 단계이므로 `--decision`은 쓰지 않는다. `--decision`은 진단 뒤 fail로 `ask_user`가 열린 뒤에만 쓴다.
   - `--void`도 쓰지 않는다. 도구 결함이 아니므로 해당 없다.
   - PRE-REVIEW `waiver`도 해당 없다.
9. 승인된 범위 변경을 PROJECT.md 등 정본에 반영한 뒤 `verify` 전체 검토로 넘어간다. 진단 뒤 첫 검토는 새 기준 전체 검토이고, 이전 지적으로 purpose를 좁히지 않는다.

**보고**
- 수정 전: 허브를 거쳐 owner에게 6요소를 보낸다.
- 완료 뒤: TASK-CLOSE 리뷰 절과 C의 사후 요약에 4요소를 남긴다. 4요소는 무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과다.

**대기 수**
- 질문 1건과 승인 대기 1건이다. 둘 다 허브를 거치는 owner A-1 결정 하나다.
- 워크트리 PM이 사용자에게 직접 묻는 일은 0건이다.

**자동 첨부와 읽은 범위**
