**담당**: 허브 PM(main 코디네이터)이 맡는다. 워크트리 작업자는 `escalation`으로 장애를 넘기고, 회신을 받으면 재검증한 뒤 태스크를 재개한다.

**판정**: 질문은 하지 않는다. A-1~A-5 모두 "아니오"다.
- A-2: 작은 도구 수정은 S1 위임에 해당한다.
- A-3: 같은 필수 검사를 하므로 안전 기준을 약화하지 않는다.

**순서**
1. 작업자의 `escalation`, 계약, 재현 조건, 증거 원문을 읽는다. 허브가 저장소에서 직접 재현한다(B-1).
2. 원인이 도구 결함임을 확인한다. 합의와 영향에 A를 적용한다.
3. 병합 대기 프로젝트는 기존 도구로 그대로 병합할 수 있다. 검증 대상인 도구를 바꾸지 않는다.
4. 격리한 도구 사본에서 장애를 재현하고 수정한 뒤, 같은 필수 검사(저장소 검사 명령, 필요하면 RED→GREEN)를 수행한다.
5. 근거는 `pace project log`로 "(main 판단)" 형식에 남긴다. 결정, 근거, 재검증 기준이 들어간다.
6. 작업자에게 회신한다. 내용은 결정, 근거, 격리 사본의 수정 내용, 재검증 기준이다. 작업자는 회신을 "(main 판단)"으로 기록하고, 적용한 뒤 재검증해서 태스크를 재개한다. 이것이 공동 시도 1회이고 상한은 2회다.
7. 병합 대기 중이므로 main 도구 수정 커밋과 메모리 커밋은 병합 뒤로 미룬다. 메모리 파일은 갱신하되 커밋하지 않는다.
8. 병합 전에 `pace project merge P###` 미리보기를 확인한다. 대상 SHA 전체와 owner 승인 원문을 대조한 뒤에 `--yes`를 입력한다. 원문이 없거나 대상이 다르면 입력을 보류하고 요청한다.
9. 병합 뒤에 도구 수정을 main에서 커밋하고, 필요하면 재설치한다. 메모리 커밋도 이때 한다. 다른 프로젝트 작업자에게 적용과 재검증을 안내한다.
10. 완료 보고의 사후 요약에 "도구 수정을 병합 뒤로 미룸"과 격리 사본 검증 결과를 한 줄씩 적는다.

**대기 수**: 질문 0건. 승인 대기는 병합의 owner 승인 1건뿐이고, 이미 받은 승인이 대상 SHA와 일치하면 대기 없이 진행한다. 도구 수정에는 승인 대기가 없다.

**첨부와 읽은 범위**
