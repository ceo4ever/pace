**사례: worktree 작업자, 태스크 표에 T01 `대기`**

**담당:** worktree 작업자 세션의 PM. 태스크 계약 안의 실행은 자율로 하고, SKILL.md §3·§6에 따라 합의가 바뀌는 결정만 허브에 올립니다.

**순서 (읽기 전용이라 실제로 실행하지 않고 계획만 적음)**
1. **분석**
   - 실제 명령: `pace project task P### "<T01 표의 이름 그대로>"`. 표의 `대기` 행과 이름이 같으면 그 번호로 열리고, 표 상태가 `진행`이 됩니다.
   - 기록: TASK.md에 목적과 재료를 씁니다. T01은 첫 태스크라 앞 태스크 TASK-CLOSE의 "남긴 것"은 없습니다.
2. **설계**
   - 기록: TASK.md에 기준 `T-n`, 테스트 표(기준마다 시나리오 한 줄 이상), 접근을 씁니다. 기준 문서는 §5 규칙(standards.md)으로 고릅니다.
   - **구현 전 검토:** 작성 PM과 다른 제공자의 reviewer에게 `pace agent verify`로 TASK.md를 검토받습니다. blocking은 고친 뒤 verify를 다시 불러 재검토받습니다. pass(blocking 0)이거나 사용자 결정으로 `waiver`가 붙었을 때만 구현합니다.
   - 대상, 판정, 지적 처리, 검토 방식은 태스크 기록에 남깁니다.
   - 다른 제공자를 호출할 수 없으면 이유와 미실행을 기록하고 `--allow-same-provider`로 진행합니다(`cross: false`). 두 제공자 경로가 모두 미실행이면 A-3 결정 요청을 허브로 올리고 사전 검토 관문을 보류합니다.
3. **구현**
   - 주변 코드 스타일을 따르되 안티패턴은 대조합니다.
   - 버그면 실패하는 테스트(RED)부터 씁니다.
4. **테스트**
   - 저장소 검사 명령과 E2E를 수행합니다.
   - tester와 reviewer를 새 맥락으로 동시에 배정하고, reviewer는 `verify`로 받습니다. 출력에 `escalation`이 있으면 먼저 따릅니다. 없으면 fail이나 blocking을 고치고 **둘 다** 다시 돕니다.
5. **마감**
   - TASK-CLOSE.md를 씁니다. "리뷰"에는 차수별 한 줄과 교본 대조 한 줄을 적습니다.
   - `pace project check P### T01`을 통과한 뒤 `pace project done P### T01`을 실행합니다.
   - `pace memory status --project --body "<어디까지 · 다음 할 일 · 막힌 것>"`으로 진행 상황을 갱신합니다.
   - TASK-CLOSE, 상태, 메모리를 한 커밋 `feat(P###/T01): …`로 묶습니다.
6. 다음 `대기` 태스크가 있으면 이어서 진행합니다. 모든 태스크가 `완료`이면 PROJECT-CLOSE.md를 쓰고(목표 달성 판정 포함) `pace project finish P###`를 실행합니다.
   - finish가 통과하면 log.jsonl의 `자체 판단` 결정을 합의와 대조합니다.
   - 그 뒤 `worker_done` 보고에 "대조: 변경 없음"(또는 변경 내용)을 적습니다.

**필요한 회신·보고**
- 막히면 `ask`로 허브에 인계합니다. 허브가 `(main 판단)`으로 회신하면 그렇게 기록하고 재검증한 뒤 태스크를 재개합니다.
- 완료 때는 `worker_done`과 완료 보고를 올립니다. PM이 대신 정한 되돌릴 수 있는 선택은 사후 요약에 한 줄씩 담습니다.

**경계**
- merge, push, 배포는 하지 않습니다. 병합은 허브가 owner 승인 뒤 main에서 `--yes`로 실행하고, 작업자는 finish 통과 뒤 `worker_done`으로 끝냅니다.
- A-1~A-5에 해당하면 해당 조치만 보류하고 독립 작업은 이어갑니다.
- 같은 실패가 3회 반복되면 근거와 함께 허브에 올립니다.
- main에서 worktree 파일을 절대 경로로 고치지 않습니다.
- 병합 대기 중에는 main 커밋을 병합 뒤로 미룹니다.

**질문·승인 대기 수:** 시작 시점에는 0건입니다. T01 착수에 승인이 필요하지 않기 때문입니다. A에 걸리는 상황이 생길 때만 허브를 통해 owner에게 요청합니다.
