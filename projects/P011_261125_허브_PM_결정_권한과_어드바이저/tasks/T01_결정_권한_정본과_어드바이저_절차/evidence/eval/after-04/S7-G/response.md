**전제와 공통 사항**
- 자동 첨부: 시스템 리마인더로 사용자 계정 정보(이메일)가 자동 첨부됐다. 값은 적지 않고 사용하지도 않는다.
- 읽은 파일과 줄 범위: `SKILL.md` 1–93(전체), `references/reviewer.md` 1–123(전체), `references/decision-rights.md` 1–45(전체). 다른 파일은 열지 않았고, 전체 바이트는 도구로 확인하지 않아 적지 않는다.
- 담당: 워크트리 PM이다. `review-note --by user`와 `waiver`의 입력자도 워크트리 PM이다. 허브는 owner 요청과 회신 전달만 맡는다.
- 이번 건은 실제 사용자 데이터 취급이므로 A-4에 해당한다. owner 답은 이미 받았다.
- 입력 전 확인:
  - owner 원문이 현재 대상과 범위에 맞는지 대조한다. 대상 해시는 승인 직전 값을 남긴다.
  - 조건이 다르거나 원문이 없으면 입력을 보류하고 허브를 통해 다시 요청한다.
  - 고칠 내용에 승인받지 않은 실제 사용자 데이터 전송이 필요하면 그 조치만 보류한다. owner 결정을 먼저 받고, 독립 작업은 계속한다.
- 공통 기록 순서:
  1. 승인 원문의 영수증(답 ID·지문·출처)을 태스크 `evidence/`에 둔다.
  2. 수정 전에 `pace agent review-note --target <대상> --decision --by user --choice <선택> --summary <사유> --file <영수증>`을 실행한다.
  3. 승인 뒤 첫 수정 기록을 `pace project log --ref`로 연결한다.
- 질문은 0건, 새 승인 대기도 0건이다.

**① 고치고 다시 검토**
1. 위 공통 기록 순서대로 user decision을 기록한다(`--choice` 고치고 다시 검토).
2. 지적을 수정한다.
3. `pace agent verify`로 전체 재검토를 받는다. 원장이 기준점을 새로 잡고, 이전 지적으로 purpose를 좁히지 않는다.
4. 같은 영역이 또 지적되면 원인 층을 다시 진단한다.
5. 보고: 수정 전에 6요소(대상·실패 추이·진단과 고친 층·남은 지적 성격·선택지·추천과 이유)를 보고한다. 끝나면 TASK-CLOSE 리뷰 절과 C의 사후 요약에 4요소(무엇이 반복됐는지·고친 층·채우거나 덜어낸 것·재검증 결과)를 남긴다.

**② 고치고 구현 진행(사전 검토)**
1. 공통 기록 순서대로 user decision을 기록한다.
2. TASK를 수정한다.
3. 고친 뒤 TASK 해시를 Node 명령으로 구한다. 그 해시가 owner가 승인한 대상인지 확인한다.
4. 승인 대상과 일치하면 `PRE-REVIEW.json`에 최상위 `waiver`를 붙인다. 내용은 by user, 날짜, 사유, `evidence/` 승인 근거, 고친 뒤 TASK 해시다. 기존 시도 이력은 그대로 둔다.
5. waiver는 실행된 검토(pass·fail)가 있을 때만 성립하고 사전 검토 게이트에만 쓴다. 이 경우는 해당한다.
6. 이후 TASK가 바뀌면 waiver는 무효이고 다시 승인을 받아야 한다.
7. 해시가 다르면 waiver를 입력하지 않고 재승인을 요청한다.
8. 구현은 waiver를 붙인 뒤에 시작한다. 구현 후 검토는 사전 검토와 별도의 새 맥락에서 받는다.
9. 보고: 수정 전에 6요소를 보고하고, 사후 요약은 ①과 같다.

**③ 이슈로 남기고 마감(구현 후)**
1. 공통 기록 순서대로 user decision을 기록한다. 구현 후 검토에는 waiver를 쓰지 않는다.
2. user decision과 원문을 TASK-CLOSE 리뷰 절에 연결한다. 남은 blocking은 이슈와 "남긴 것"에 기록한다.
3. 계약 목표가 미달이거나 미확인이면 `done`을 하지 않는다. `판정: 막힘`으로 두고 보완 관측·수정을 요청한다. 검토 pass와 목표 달성 판정은 따로 합산한다.
4. 필수 태스크 보류나 기준 미달 마감으로 번지면 A-1에 해당한다. 그 조치만 보류하고 허브를 통해 새로 owner 요청을 한다. 이 경우에만 질문이 1건 생긴다.
5. 목표가 달성·확인됐을 때만 `check` → `done` → 진행 상황 갱신 → 커밋 순서로 간다.
6. 보고: 수정 전에 6요소를, TASK-CLOSE와 C의 사후 요약에 4요소를 남긴다.
