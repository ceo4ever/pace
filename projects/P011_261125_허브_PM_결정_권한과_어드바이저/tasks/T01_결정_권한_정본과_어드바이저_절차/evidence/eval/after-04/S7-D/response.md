**상황: `review-note --diagnosis`를 기록한 직후이고 `verify`는 아직 실행 전이다.**

**담당**
- 담당은 워크트리 PM(나)이다.
- 허브는 진단 전에 B로 근본 조치를 정할 때 이미 거쳤다. 지금은 이미 확정된 조치를 적용하는 단계다.
- 이 시점의 단계는 normal이다(`reviewer.md` 74행).

**순서**
1. **`--decision`은 쓰지 않는다.** `review-note --decision`은 다음 검토가 fail로 끝나 `ask_user` 단계가 열린 뒤에만 입력한다.
2. **수정 직전 영향 분류.**
   - 확정한 근본 조치를 합의된 목적·목표·범위·`P-n`과 A-1~A-5로 대조한다. 이미 승인된 구체적 조치는 다시 승인받지 않는다.
   - 새 영향이 있으면 다시 분류한다.
   - A 밖이면 그대로 적용한다.
3. **근본 조치를 적용한다.** 대상은 TASK.md 등이다. 허브 미해결 항목이 있으면 `(main 판단)`으로 기록한다.
4. **`pace agent verify`를 실행한다.**
   - 같은 대상, 같은 경로로 원장을 잇는다. 이 호출이 진단 뒤 새 기준 전체 검토다.
   - `purpose`에는 합의된 상위 목적과 판정 기준만 넣고, 이전 지적이나 내 대응·자체 판정은 넣지 않는다.
   - 사전 검토면 `--kind task`를 쓴다.
5. **판정에 따라 진행한다.**
   - **pass:** blocking이 0이면 진행한다. 사전 검토 pass는 PRE-REVIEW.json으로 옮기고, `continuity`는 `changed`(reason: 진단 뒤 새 기준 전체 검토)로 쓴다.
   - **fail:** 종료 0과 `ask_user` 신호가 나온다. 이 호출에서 곧바로 조치 영향을 A로 분류한다.
     - A 밖이면 `evidence/`에 근거를 쓰고 `review-note --decision --by pm`을 기록한 뒤 전체 재검증한다.
     - A에 걸리면 해당 조치만 보류한다. 허브를 거쳐 6요소(대상·실패 추이·진단과 고친 층·남은 지적 성격·선택지·추천과 이유)와 A 번호로 owner에게 요청한다. 승인 원문과 현재 대상을 대조한 뒤 `--by user`로 기록한다.

**기록·회신·보고**
- 진단 근거와 조치는 이미 review-note에 기록돼 있다.
- 필요한 owner 응답 원문은 진단 근거나 `pace project log`에 연결한다.
- 사후 보고는 4요소(무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과)를 TASK-CLOSE 리뷰 절과 C의 사후 요약에 남긴다.
- 차수별 원문은 `review-records/`에 보존한다.
- 허브에는 조치 적용과 재검증 결과를 회신한다.

**대기 수**
- 질문은 0건이다. 승인 대기도 0건이다.
- 다만 fail 뒤 A에 걸리면 허브를 거친 owner 요청이 1건 생긴다. 이 경우 해당 조치만 보류한다.
