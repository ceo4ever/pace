## 사례: 허브가 재현한 하네스 도구의 작은 결함 (병합 대기 프로젝트 없음)

**담당**: 허브 PM(main 코디네이터)이 맡는다. 근거는 decision-rights.md의 B-3과 A-2의 S1 위임이다. 워크트리 작업자는 재현 증거와 함께 `escalation`이나 질문만 올린다. 이 사례에서는 허브가 이미 원인을 재현했다.

**순서**
1. **A 대조(B-2)**: 합의 변경(A-1), 외부 영향(A-2), 안전 기준 약화(A-3), 사용자 자산(A-4), 사람 수행(A-5)에 해당하는지 확인한다. 작은 수정은 도구 결함을 푸는 일이다. AGENTS.md가 main 커밋과 main 설치를 위임했으므로 A-2는 '아니오'다. 보안 검사·필수 테스트·독립 검토를 약화하는 수정이라면 A-3으로 판정해 owner에게 요청한다. 이 사례는 그런 수정이 아니다.
2. **병합 대기 확인**: 병합 대기 프로젝트가 없으므로 main 커밋을 미룰 이유가 없다(SKILL §4 ✋).
3. **수정**: 허브가 main에서 도구를 고친다. 규모는 SKILL §1의 '작은 일'이므로 프로젝트를 만들지 않는다. 먼저 수정할 대상 파일을 열어 본다. 실패하는 테스트(RED)를 먼저 만들고, 저장소 검사 명령을 실행한다.
4. **커밋과 설치**: main에 커밋하고 필요하면 main에서 재설치한다. 위임 범위 밖인 푸시·병합·배포는 하지 않는다.
5. **기록**: `pace project log P### [T##] --type decision --msg "<한 줄>" --src "main 판단"`으로 남긴다. 작업자가 보낸 원문이나 비밀은 복제하지 않는다. 관련 프로젝트가 없으면 프로젝트 기록 대신 커밋 메시지와 회신에 근거를 적는다. 메모리를 바꿨다면 같은 커밋에 넣는다.
6. **회신**: 허브가 작업자에게 결정·근거·재검증 기준을 회신한다. 작업자는 이를 `(main 판단)`으로 기록하고 적용 후 재검증한 뒤 태스크를 재개한다. 이 "회신 → 적용 → 재검증"이 공동 시도 1회이며 상한은 2회다. 2회가 지나면 차선으로 돌리고 필수 태스크가 걸리면 A-1로 요청한다.
7. **보고**: owner에게는 사후 요약 한 줄만 다음 대화나 완료 보고에 붙인다. 승인 요청은 하지 않는다.

**질문·승인 대기 수**: 질문 0, 승인 대기 0.
