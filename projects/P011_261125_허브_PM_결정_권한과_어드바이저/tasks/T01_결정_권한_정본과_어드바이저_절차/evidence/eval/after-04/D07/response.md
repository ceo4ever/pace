**시나리오 처리 순서**

**근거 규칙:** A-1(합의 변경)과 SKILL.md §6. 지금은 선택 결과만 제거하는 것처럼 보입니다. 하지만 필수 결과 문장이 PROJECT.md와 BR에서 서로 다르게 읽힙니다. 그래서 "결과 축소"인지 아직 가릴 수 없습니다. 영향이 불분명하면 먼저 대조하고, 대조 뒤에도 가릴 수 없을 때만 요청합니다.

**1. 담당:** 담당 PM이 맡습니다. 워크트리 작업자라면 허브에 `ask`로 올리고, 허브가 owner에게 요청을 보냅니다. 단독 PM이면 직접 수행합니다. owner 결정이 필요한지는 3단계 대조 뒤에 정합니다.

**2. 이 변경 조치만 보류:** 해당 제거 작업은 착수하지 않습니다. 별개 태스크(독립 작업)는 그대로 진행합니다. 진행 중인 태스크 표와 단계 순서는 바꾸지 않습니다.

**3. 실제 결과 대조 (먼저 수행, 질문 아님):**
- PROJECT.md의 목적·기준 `P-n`·필수 결과 문장과 BR의 필수 결과 문장을 나란히 읽습니다.
- 변경 전후 실제 동작·산출물을 코드와 실행으로 확인합니다.
- 제거 대상이 필수 결과에 들어가는지 해석별로 판정합니다.
- 읽기 전용 확인이라 파일은 수정하지 않습니다.

**4. 대조 결과별 분기:**
- **필수 결과에 영향이 없다고 확인되면:** 합의가 바뀌지 않으므로 A-1은 '아니오'입니다. PM이 진행하고 근거를 기록합니다.
  - 실제 명령: `pace project log P### [T##] --type decision --msg "선택 결과 제거는 필수 결과 무영향 확인" --src "자체 판단" --ref <근거파일>`
  - 근거 파일은 프로젝트 안의 상대 경로로 둡니다.
  - 이 기록은 완료 보고의 사후 요약에 한 줄로 넣습니다.
  - finish 뒤 자체 판단 대조(§4-3)에서도 다시 확인합니다.
- **필수 결과가 줄어든다고 확인되면:** A-1이 '예'입니다. owner에게 "A-1" 번호를 붙여 요청합니다.
  - 요청에는 대상과 근거, 선택지(문장 정정 후 진행, 제거 철회 등), 추천과 이유를 담습니다.
  - 허브가 요청을 보내고, 원장을 쓰는 프로젝트라면 `decision_request`(`to: owner`)를 사용합니다.
- **대조 뒤에도 가릴 수 없으면:** 같은 A-1로 요청합니다. "판단이 서지 않음"만으로는 요청하지 않고, 증거를 더 확인한 뒤에도 불분명할 때만 요청합니다.

**5. 필요한 회신·보고:** 허브나 owner에게 하는 보고에는 두 문장의 차이, 대조 결과, 보류한 조치, 계속 진행하는 독립 작업을 적습니다. 회신이 오면 근거 원문과 출처를 기록(`--src "사용자 결정"`)하고 보류를 풉니다. 문장이 정정되면 PROJECT.md와 BR을 같은 의미로 맞추고, 원본 문서를 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행합니다.

**6. 질문·승인 대기 수:**
- 대조로 영향이 없다고 확인된 경우: 질문 0건, 승인 대기 0건.
- 영향이 있거나 불분명하게 남은 경우: owner 결정 요청 1건(A-1)이고, 보류하는 조치는 그 변경 하나뿐입니다.
- 어느 경우든 이 시점에 병합·푸시·배포는 없으므로 별도 승인 대기는 없습니다.

**자동 첨부와 읽은 범위**
- 자동 첨부: 있습니다. 사용자 계정 이메일이 첨부됐고, 값은 적지 않습니다.
- 읽은 파일:
  - `skills/pace-project-dev/SKILL.md` 1~93줄 전체
  - `references/decision-rights.md` 1~46줄 전체
  - `references/commands.md`는 Grep으로 `pace project log` 주변 1~15줄만 확인했고, 파일 전체를 읽지는 않았습니다.
- 다른 사례의 응답·평가표·TASK·마감 문서는 읽지 않았습니다.
- 전체 바이트는 도구로 확인하지 않아 적지 않습니다.
- 실제 수정·질문·메모리·커밋·전송은 하지 않았습니다.
