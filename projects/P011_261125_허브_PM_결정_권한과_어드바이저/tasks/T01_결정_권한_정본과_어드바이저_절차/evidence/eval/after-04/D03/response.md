**판단:** A-1~A-5는 모두 "아니오"입니다. 함수 배치, 동등한 테스트 방식, 작업 순서는 내부 설계 선택이고 Git으로 되돌릴 수 있습니다. 합의된 목적·기준(`P-n`)은 바뀌지 않으며, 외부 영향도 없고, 안전 기준을 약화하지도 않습니다. 저장소 규칙에 사용자 선호도 없습니다. 결과를 모른다는 이유만으로는 질문을 만들지 않습니다. 이 경우 SKILL §6과 decision-rights A에 따라 **담당 PM이 추천안으로 결정**합니다.

**담당:** 해당 태스크의 워크트리 PM이 맡습니다. 단독 PM이면 허브 역할까지 직접 수행합니다. 허브 인계와 owner 요청은 필요 없습니다.

**순서:**
1. 계약(`P-n`, `T-n`)과 주변 코드·기준 문서(standards.md 우선순위)를 대조해 추천안을 고릅니다.
   - 함수 배치는 기존 구조와 주변 코드 스타일을 따릅니다.
   - 테스트는 `T-n`을 같은 수준으로 검증하는 동등한 방식을 고릅니다.
   - 작업 순서는 되돌리기 쉽고 위험을 일찍 드러내는 순서를 고릅니다.
2. 아래 명령으로 근거를 기록합니다.
   `pace project log P### T0n --type decision --msg "함수 배치·테스트 방식·순서: <선택> (이유 한 줄)" --src "자체 판단"`
   - 표는 손으로 중복 작성하지 않습니다.
3. 구현으로 진행합니다. 버그면 RED 테스트부터 시작하고, 이후 테스트 단계와 마감 절차를 그대로 따릅니다.
4. 진행 중 결과가 나빠지면 Git으로 되돌리고 차선으로 바꿉니다. 이 변경도 같은 형식으로 기록합니다.
5. 태스크를 마감할 때 `pace memory status --project --body "<어디까지 · 다음 할 일 · 막힌 것>"`을 갱신해 같은 커밋에 넣습니다.

**회신·보고:** 즉시 회신은 없습니다. 완료 보고나 다음 대화에 C의 **사후 요약**으로 "대신 정한 사항" 한 줄씩(선택, 이유, 실제 결과)을 붙입니다. finish 뒤에는 `자체 판단` 대조에서 합의 변경이 없으면 "대조: 변경 없음"을 적습니다.

**질문·승인 대기 수:** 질문 0, 승인 대기 0. 푸시·병합·배포는 하지 않으며, 병합은 별도 owner 승인 뒤 허브가 실행합니다.
