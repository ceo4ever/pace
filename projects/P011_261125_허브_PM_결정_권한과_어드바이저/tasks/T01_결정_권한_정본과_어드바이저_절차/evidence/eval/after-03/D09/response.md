**공통 전제:** 공동 시도(허브 회신 → 워크트리 적용 → 재검증)가 2회 모두 실패했다. 그래서 `decision-rights.md` B-4의 상한에 도달했다. 새 시도는 하지 않는다. 읽기 전용 시험이라 아래는 실행하지 않고 순서만 적는다.

## 옵션 1: 계약상 명시된 선택 태스크 보류 (독립 태스크 있음)

- **담당:** 워크트리 PM이 실행하고 기록한다. 허브는 이미 B 회신을 마쳤다.
- **A 판정:** 선택 태스크 보류는 계약에 명시된 차선이다. 합의된 목적, 범위, `P-n`을 바꾸지 않는다. 따라서 A-1은 "아니오"다. A-2~A-5도 해당하지 않으므로 owner 요청은 만들지 않는다.
- **순서:**
  1. 해당 태스크를 PROJECT.md 태스크 표에서 `보류`로 바꾼다.
  2. 보류 사유, 2회 시도 증거, 재개 조건을 이슈로 기록한다. 기록은 `pace project log`로 남기고, 허브 판단은 "(main 판단)"으로 표시한다.
  3. `pace memory status --project --body "<어디까지 · 다음 할 일 · 막힌 것>"`으로 진행 기록을 갱신한다.
  4. 남은 독립 태스크를 표의 `대기` 중 맨 앞부터 이어간다.
  5. 원인이 풀리면 보류 태스크를 재개한다. 해소 조건은 도구 수정, 환경 복구, 결정 증거다.
- **마감 시:** 모든 태스크가 `완료` 또는 `보류`가 되면 PROJECT-CLOSE.md를 쓴다. 목표 달성 판정도 따로 쓰고, 보류분은 한계로 적는다. 이후 `finish`와 자체 판단 대조로 간다.
- **질문과 승인 대기:** 질문 0건, 승인 대기 0건이다.

## 옵션 2: 필수 태스크 보류 후 필수 결과 없이 마감

- **담당:** 워크트리 PM이 `ask`로 허브에 인계한다. 허브가 C 형식의 결정 요청을 owner에게 보낸다. 워크트리 PM이 직접 owner에게 요청하지는 않는다.
- **A 판정:** 필수 태스크 보류와 기준 미달 마감은 A-1에서 "예"다. 결과 축소에도 해당한다. 필요하면 A-3(필수 증거 미확인)도 함께 대조한다.
- **순서:**
  1. 해당 조치(필수 태스크 보류, 기준 미달 마감)만 보류한다.
  2. 허브에 `ask`로 올린다. 근거는 2회 실패 증거, PROJECT.md 기준과 실제 결과의 대조, 영향받는 `P-n`이다.
  3. 허브가 owner에게 A-1 번호를 붙여 요청한다. 요청에는 대상과 근거, 선택지(계약 변경 / 보완 관측·재설계 / 마감), 추천과 이유를 담는다.
  4. 독립 작업이 있으면 회신을 기다리는 동안 계속한다. 없으면 대기한다.
  5. owner 회신은 같은 요청 지문으로 묶어 기록한다. 원장을 쓰면 `decision_request`/`decision_reply`를 쓴다. 쓰지 않으면 프로젝트 내부 근거 파일에 원문과 출처를 남긴다.
  6. 회신이 적법한 계약 변경이면 변경된 계약으로 다시 판정한다. 필수 결과가 여전히 미확인이면 보완 관측으로 판정한다. 검토가 한 번도 실행되지 않았다면 `waiver` 근거가 성립하지 않는다.
- **금지:** 목표 미달이나 미확인을 게이트 통과로 덮고 마감하지 않는다. 승인 전에는 PROJECT-CLOSE와 `finish`로 가지 않는다.
- **질문과 승인 대기:** 질문 1건(허브를 거쳐 owner에게), 승인 대기 1건이다.
