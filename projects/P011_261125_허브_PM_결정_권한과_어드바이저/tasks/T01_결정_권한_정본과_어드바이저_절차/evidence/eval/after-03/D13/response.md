**전제**: 실제 명령은 실행하지 않았고 순서만 답합니다. 해당 제공자 호출은 이미 시도했고 불가능했다고 가정합니다.

## 사례 1. TASK 사전 검토 (구현 전)
- **담당**: 워크트리 PM이 TASK.md를 쓰고, 별도 reviewer가 검토합니다. reviewer는 같은 제공자의 새 세션입니다.
- **순서**
  1. 다른 제공자를 호출하지 못한 이유와 미실행 사실을 기록합니다.
  2. `pace agent verify --author-agent <claude|codex> --target <TASK.md> --purpose-file <상위 목적 글> --out <기록> --allow-same-provider`를 실행합니다. 호스트가 별도 새 세션을 지원하면 그 세션을 써도 됩니다.
  3. 결과를 `cross: false`로 기록합니다. 제공자는 결과의 모델·제공자 출처로 확인합니다. 다른 제공자인 척 쓰지 않습니다.
  4. blocking은 수정한 뒤 `verify`를 다시 호출합니다. pass(blocking 0)가 되면 구현으로 넘어갑니다.
  5. should_fix는 항목마다 반영 여부와 이유를 남깁니다.
  6. 대상, 판정, 지적 처리, 검토 방식을 태스크 기록에 남깁니다.
- **질문·승인 대기**: 0건입니다. 이 대체는 B1이 이미 위임했고 A-3에서 "아니오"입니다.
- **주의**
  - 연속 fail로 `escalation`이 붙으면 반복 실패 절차를 따릅니다.
  - 이미 실행된 교차 검토가 fail이었다면 같은 제공자 새 세션으로 대체할 수 없습니다.

## 사례 2. 백로그 검토 (큰 산출물)
- **담당**: 작성자가 백로그를 쓰고, 같은 제공자의 새 세션이 상위 목적 우선으로 독립 검토합니다.
- **순서**
  1. 사례 1과 같습니다. 미실행 사유를 기록하고 `--allow-same-provider`로 새 세션을 엽니다. `cross: false`로 기록합니다.
  2. goal-review 순서를 지킵니다. 1단계 결과를 회수한 뒤에 2단계 작업 문서를 주고, 모든 자료를 한 번에 주지 않습니다.
  3. blocking·should_fix·note 항목마다 반영 여부와 이유를 남깁니다.
  4. 지적에 따른 조치가 합의된 목적·범위를 바꾸는지 A-1로 판정합니다. 바꾸면 `ask`로 허브에 올립니다.
  5. 백로그 원본을 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행합니다.
- **질문·승인 대기**: 기본은 0건입니다. A-1에 걸리는 경우에만 해당 조치를 보류하고 요청을 보냅니다.

## 사례 3. 둘 다 호출할 수 없을 때
다른 제공자와 같은 제공자 새 세션이 모두 미실행인 경우입니다.
- **해석**: A-3의 "예"입니다. 안전 기준 약화에 해당합니다.
- **하지 않을 일**
  - 검토를 생략하지 않습니다.
  - PM 자체 검토로 대체하지 않습니다.
  - `waiver`를 쓰지 않습니다. 검토가 한 번도 실행되지 않았으므로 waiver 근거가 성립하지 않습니다.
- **순서**
  1. 두 경로의 미실행 사유를 기록합니다.
  2. 작업자는 `ask`로 허브에 인계하고, 허브가 owner에게 C 형식으로 결정을 요청합니다.
  3. TASK는 사전 검토 관문을 보류하므로 구현에 들어가지 않습니다. 백로그는 해당 검토 결과에 의존하는 조치만 보류합니다.
  4. 독립 작업은 계속합니다.
- **질문·승인 대기**: 각 사례마다 1건입니다. TASK 검토와 백로그 검토가 둘 다 불가하면 최대 2건이고, 같은 원인이면 한 번에 묶어 요청해도 됩니다.

## 공통 경계

- 이 답변에서 수정, 질문, 메모리 기록, 커밋, 전송은 하지 않았습니다.
