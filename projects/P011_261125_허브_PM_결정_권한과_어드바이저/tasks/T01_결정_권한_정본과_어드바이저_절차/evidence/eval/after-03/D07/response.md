**사례: "선택 결과만 제거"로 보이는 변경에서 PROJECT.md와 BR의 필수 결과 문장이 서로 다르게 읽히는 경우**

판정 근거는 `decision-rights.md`의 A-1입니다. 필수 결과를 줄이는 조치는 합의 변경이라 '예'입니다. 영향이 불분명하면 먼저 PROJECT.md·브리프와 실제 결과를 대조해야 합니다. 대조 뒤에도 영향 여부를 가릴 수 없을 때만 owner에게 요청합니다.

**순서**
1. **담당: 워크트리 PM(작업자).** 아직 질문하지 않고, 어떤 조치도 실행하지 않습니다. 먼저 읽기 전용으로 확인합니다.
   - PROJECT.md의 목적·기준 `P-n`과 BR 필수 결과 문장 원문을 나란히 대조합니다.
   - 제거 대상이 실제로 어떤 결과를 내는지 코드와 현재 동작으로 확인합니다. 필요하면 테스트나 E2E를 읽기 전용으로 실행해 증거를 `evidence/`에 둡니다.
   - 확인으로 범위 영향이 좁혀지는지 봅니다.
2. **갈래 ①: 대조 결과 필수 결과가 유지되는 경우.** 제거가 선택 결과에 한정되고 `P-n`이 그대로면 A-1은 '아니오'입니다. PM이 결정하고 기록합니다.
   - `pace project log P### [T0n] --type decision --msg "선택 결과만 제거, 필수 결과·P-n 유지(근거: …)" --src "자체 판단" --ref <증거 상대파일>`
   - 이 기록은 finish 뒤 자체 판단 대조(§4-3) 대상이 됩니다.
3. **갈래 ②: 대조 뒤에도 필수 결과가 줄어드는지 가릴 수 없거나 줄어드는 경우.** A-1로 `ask`를 허브에 보냅니다. 허브가 owner에게 C 형식(A-1 번호, 대상과 근거, 선택지, 추천과 이유)으로 요청합니다.
   - 선택지는 (a) 필수 결과를 유지하고 제거 범위를 줄이는 것, (b) 필수 문장을 합의 변경으로 정정하는 것입니다.
   - 추천안과 이유를 함께 적습니다.
   - 원장을 쓰는 프로젝트면 `decision_request`(`to: owner`)를 사용합니다.
   - 회신이 오면 `--src "사용자 결정"`으로 기록합니다. 문서가 바뀌면 `pace backlog refresh`를 실행합니다.
4. **보류 범위와 독립 작업.** 해당 제거 조치만 보류합니다. 별개 태스크는 태스크 표의 순서대로 계속 진행합니다.
5. **경계**
   - 정본 PROJECT.md와 BR을 임의로 고쳐 문장을 맞추지 않습니다.
   - 필수 태스크를 보류하거나 기준 미달로 마감하지 않습니다.
   - 병합·푸시는 하지 않습니다. 병합과 배포는 별도의 owner 승인 뒤 허브가 수행합니다.
   - 영향이 불분명하다는 이유만으로 질문하지 않고, 조사부터 합니다.

**질문과 승인 대기 수**
- 갈래 ①: 질문 0건, 승인 대기 0건.
- 갈래 ②: owner 질문 1건(A-1), 승인 대기 1건. 대기하는 것은 해당 제거 조치뿐입니다.
