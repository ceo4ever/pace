**상황 판단.** 2차 재검토 원문은 등급이 없는 서술이다. `reviewer.md`의 재검토 범위 규칙을 적용하되, 등급은 내가 임의로 붙이지 않는다.

**1. 담당과 순서 (워크트리 PM)**
1. 원문을 고치거나 요약하지 않고 `review-records/R2.json`(차수별 고유 증거 경로)에 그대로 보존한다. 비밀·민감정보를 검사하고, 원문이 없거나 복사할 수 없으면 복원하지 않고 그 한계를 적는다. 보존은 새 파일 한 건 쓰기로 처리한다.
2. 원문이 등급 없는 서술이라 형식이 `reviewer.md`의 반환 형식(판정·F 등급)과 어긋난다. 이 형식 결함은 `verify`가 원장에 판정(verdict)을 남겼는지로 확인한다.
   - 원장에 판정이 있으면 그 판정을 따른다.
   - 원장에 판정이 없으면(`unknown`) 집계에 넣지 않는다. 그 원문은 PRE-REVIEW 시도로 옮기지 않고, 같은 대상을 `verify`로 다시 검토한다.
   - PM이 직접 등급을 매겨 판정을 대신하지 않는다.
3. 지적별 처리는 다음과 같다. 지금 구현 전 사전 검토인지, 구현 후 검토인지는 대상 경로로 확인하고 같은 경로로 이어 간다.

| 지적 | 처리 |
|---|---|
| 직전 지적 1 (해소) | 처리 이력에 "해소"로 기록한다. |
| 직전 지적 2 (부분 해소) | 직전 blocking이 남은 것이므로 이번 수정 대상이다. 남은 부분만 고친다. |
| 고친 줄에서 생긴 새 문제 1 | 수정이 만든 새 결함이므로 이번 수정 대상이다. |
| 바뀌지 않은 절의 새 지적 1 | 이번 판정·수정 대상이 아니다. note로 남기고, 직전 blocking 해소나 이번 수정 줄과 무관한 한 고치지 않는다. 결함 가능성이 크면 낮은 등급으로 내리지 않고 handoff나 should_fix로 TASK-CLOSE "남긴 것"에 연결한다. |

4. 수정 직전에 각 조치가 합의된 목적·범위·기준에 미치는 영향을 확인한다.
   - 영향이 A에 걸리면 `ask`로 허브에 인계하고, 해당 조치만 보류한다. 독립 작업은 이어 간다.
   - A 밖이면 PM이 결정하고 `pace project log`에 남긴다.
5. 수정 뒤 `pace agent verify --kind task`(사전 검토 대상일 때)를 다시 호출한다. 도구가 직전 fail 원문과 바뀐 줄로 자동 재검토를 한다. 이때 purpose에는 합의된 목적만 넣고 내 대응이나 자체 판정은 넣지 않는다. 도구 밖 서브에이전트 판정은 원장에 남지 않으므로 쓰지 않는다.
6. 아래 사항을 기록한다.
   - 지적별 등급·판정 근거·반영/미반영 이유·수정 위치·재검토 결과를 연결한다.
   - 증거 경로를 TASK-CLOSE 리뷰와 review 로그에 연결한다.
   - 바뀐 줄 목록은 재검토 대상 범위의 근거로 같이 보존한다.
7. 연속 fail 횟수는 원장이 센다. 이번이 2차이므로 아직 diagnose 단계는 아니다. 3차 fail에서 `escalation`이 붙으면 반복 실패 절차(진단 → 허브 B → `review-note --diagnosis`)로 전환한다.
8. 같은 지적이 절차나 열람 문제로 두 번 이어지면 3회를 기다리지 않는다. 재검토를 중단하고 증거와 함께 허브에 이관한다.

**2. 실제 명령·기록**
- 증거 파일 쓰기(R2 원문, 처리 이력)와 수정 뒤 `pace agent verify` 재호출
- `pace project log`(처리 결과 기록)
- 필요하면 `pace agent review-note`(진단·결정 단계에서만)

**3. 질문과 승인 대기**
- 현재 시점에서 사용자에게 묻는 질문은 0건, 승인 대기는 0건이다.
- 수정이 A(합의된 목적·기준·범위 변경)에 걸리는 것으로 판명되면 그때 해당 조치만 허브 경유 1건으로 요청한다. 병합·배포는 이번 범위가 아니다.

**4. 이번에 하지 않는 것**
- 원문 등급을 추정해 붙이는 것
- 바뀌지 않은 절의 새 지적을 이번 fail 사유로 합산하는 것
- 파일 수정, 커밋, 전송, 메모리 기록. 이 시험은 읽기 전용이다.
