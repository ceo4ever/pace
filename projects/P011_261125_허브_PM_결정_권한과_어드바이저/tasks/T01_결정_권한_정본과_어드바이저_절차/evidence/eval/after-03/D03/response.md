**사례: 함수 배치, 동등한 테스트 방식, 작업 순서 선택 (내부 설계, Git으로 되돌릴 수 있음, 저장소 규칙에 선호 없음)**

**판정**
- 결정 주체는 담당 PM이다. 근거는 `decision-rights.md` A의 다섯 질문이다.
  - A-1: 합의된 목적·범위·`P-n`을 바꾸지 않는다.
  - A-2: worktree의 Git으로 되돌릴 수 있고, 외부로 나가는 것도 없다.
  - A-3: 필수 테스트나 검토를 약화하지 않는다. 동등한 테스트 방식을 고르는 것은 검증을 유지한 채 하는 선택이다.
  - A-4, A-5: 새 권한·비용·사람 확인이 필요 없다.
- 다섯 질문에 모두 "아니오"이므로 owner에게 묻지 않는다. 결과를 모른다는 이유만으로는 질문을 만들지 않는다(A 말미: 조사 뒤 되돌릴 수 있는 선택은 PM이 추천안으로 진행하고 이유를 기록한다).

**순서**
1. 판단 전에 증거를 더 모은다. 읽기만 한다.
   - 현재 계약인 TASK.md의 `T-n`과 테스트 표
   - `standards.md`의 우선순위(기계 설정 > `AGENTS.md` > 기준 문서 > 주변 코드 > 교본)
   - 주변 코드 스타일과 안티패턴
   - 선호가 없다는 것을 `AGENTS.md`에서 확인한다.
2. 계약(`T-n`)을 유지하는 후보 중 하나를 추천안으로 정한다. 기준은 주변 코드와의 일관성, 변경 폭이 작은 쪽, 기존 테스트 방식과 같은 쪽이다. 보안·성능 문제가 있거나 따를 주변 코드가 없으면 교본을 따른다.
3. 이유를 한두 줄로 기록한다.
   - 실제 명령: `pace project log` (형식은 `commands.md`). 결정은 "자체 판단"으로 남는다.
   - TASK.md 접근 절에도 같은 내용을 적는다.
4. 구현 전 검토 계약은 유지한다. 접근이 TASK.md에 들어가면 `pace agent verify`로 reviewer 검토를 받고, pass일 때만 구현한다. 이 검토는 생략하지 않는다(A-3).
5. 구현과 테스트는 기존 순서를 따른다. 테스트 방식을 바꿔도 기준마다 시나리오 한 줄 이상이라는 조건은 지킨다.
6. 태스크 마감 때 `pace memory status --project --body "..."`를 갱신해 같은 커밋에 넣는다. finish 뒤에는 자체 판단 결정을 합의와 대조하고, 보고에 "대조: 변경 없음"을 적는다.

**경계**
- 선택하다가 `P-n`·범위·기준이 바뀌거나 필수 검증이 약해지면 그 조치만 보류한다. 그때는 A-1이나 A-3으로 허브를 통해 owner에게 묻고, 독립 작업은 계속한다.
- 푸시·병합·배포는 이번 사례에 없다. 필요해지면 허브에 인계한다.
