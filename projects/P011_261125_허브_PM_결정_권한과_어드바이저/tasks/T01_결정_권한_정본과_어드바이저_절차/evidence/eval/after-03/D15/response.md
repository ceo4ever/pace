**상황 판단:** main에 병합 대기 프로젝트가 있다. 다른 프로젝트의 장애 원인은 작은 하네스 도구 결함이다. 병합 대기 프로젝트는 기존 도구로 병합할 수 있으므로, 그 결함이 병합을 막지는 않는다. 근거는 SKILL.md §4 ✋와 decision-rights.md B-3이다.

**순서**

1. **담당 확인.** 허브 PM(main 코디네이터)이 맡는다. 워크트리 작업자는 `escalation`이나 `ask`로 재현 조건과 증거만 허브에 보낸다. 같은 세션이 두 역할을 맡았다면 그 세션이 허브 절차를 직접 수행한다.
2. **재현과 원인 층 판별(B-1, B-2).** 허브가 저장소에서 장애를 재현한다. 환경 문제인지 도구 결함인지 가린다.
3. **A 항목 대조.**
   - A-2: S1 위임이 적용된다. 작은 도구 수정을 허브가 main에서 고치고 커밋하며, 필요하면 재설치하는 조치는 owner 요청 없이 수행할 수 있다.
   - A-3: 이 수정이 보안 검사·필수 테스트·검토를 약화하지 않는지 확인한다.
   - A-1, A-4, A-5: 해당하는지 확인한다.
   - 전부 "아니오"면 PM이 결정하고, 근거는 "(main 판단)"으로 기록한다.
4. **수정은 하되 main 커밋은 미룬다.** 병합 대기 중이므로 도구 수정 커밋은 병합 뒤로 미룬다. 지금 main에 커밋하지 않는다. 메모리 파일은 갱신하되 그 커밋도 병합 뒤로 미룬다. 수정 작업 자체는 격리 사본에서 한다.
5. **병합은 기존 도구로 진행한다.** 허브가 main에서 `pace project merge P###`를 실행해 미리보기를 확인한다. 미리보기의 커밋 전체 SHA를 owner 승인 원문과 대조하고, 일치할 때만 `--yes`를 입력한다. 원문이 없거나 대상이 다르면 입력을 보류하고 승인을 요청한다. 도구 결함 수정이 병합의 선결 조건이 되지는 않는다.
6. **병합 뒤 처리.** FF가 성공하면 미뤄 둔 도구 수정을 main에 커밋하고 필요하면 재설치한다. 완료 기록이 실패하면 recovery.md를 따른다.
7. **회신과 재개.** 허브가 결정·근거·재검증 기준을 작업자에게 회신한다. 작업자는 "(main 판단)"으로 기록하고 적용 뒤 재검증해서 태스크를 재개한다. 이 과정이 공동 시도 1회이고 상한은 2회다. 막힌 조치만 보류하고 독립 작업은 계속한다.
8. **사후 요약.** PM이 대신 정한 사항과 실제 결과를 한 줄씩 다음 대화나 완료 보고에 붙인다.

**경계**
- 병합 대기 중에 도구 수정 커밋을 main에 만들지 않는다.
- 병합 승인은 병합 대상 SHA 기준으로만 사용한다. 도구 수정 승인과 섞지 않는다.
- 워크트리는 푸시·배포·삭제·외부 전송을 하지 않는다.
- main에서 worktree 파일을 절대 경로로 고치지 않는다.

**질문과 승인 대기:** 도구 수정에 관한 owner 질문은 0건이다. 승인 대기도 0건이다. 병합 `--yes`는 기존 owner 승인 원문과 SHA가 일치할 때만 입력하고, 일치하지 않으면 승인 요청 1건이 생긴다.

**자동 첨부와 읽은 범위:** 자동 첨부로 userEmail 컨텍스트를 받았고, 이 답변에는 쓰지 않았다. 읽은 파일은 두 개다.
- `skills/pace-project-dev/SKILL.md` 1–93줄
- `skills/pace-project-dev/references/decision-rights.md` 1–46줄
