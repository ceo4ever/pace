## 사례 1: normal 단계, 구간의 fail이 `interrupted` 1건뿐

- **담당**: 워크트리 PM이 맡습니다. 허브 보고, 진단, 결정 기록은 필요 없습니다.
- **판단**: fail은 1건이라 3회 기준에 못 미칩니다. 단계는 normal이고 `escalation`도 없습니다. `interrupted`는 연속 fail 집계에는 들어가지만 실제 blocking과는 구별합니다. 이 건을 blocking처럼 수정하지 않고, 이전 지적으로 purpose를 좁히지도 않습니다.
- **실제 명령**: 같은 대상에 `pace agent verify`를 다시 호출합니다. 중단 복구만 남은 normal 상태라서 다음 검토는 **전체 검토**입니다. 호스트 reviewer로 대체하지 않습니다. 호스트 reviewer는 원장에 남지 않기 때문입니다.
- **기록**: `review-note`를 쓰지 않습니다. 검토 결과(판정·지적 처리·방식)는 TASK 기록이나 TASK-CLOSE 리뷰 기록에 남깁니다.
- **질문과 승인 대기**: 질문 0건, 승인 대기 0건.

## 사례 2: 같은 상황에서 복구로 3회가 돼 종료 16, `diagnose`

- **차단 해석**: 종료 16은 기록되지 않은 `diagnose` 단계에서 다시 호출했다는 뜻입니다. 재호출이나 우회를 하지 않고, 아래 순서대로 `diagnose`를 먼저 처리합니다. `recovered`로 처음부터 16이 나와도 같은 단계를 따릅니다. 중단 복구 3회는 fail 집계에 들어갑니다.
- **순서**
  1. 실패 원문과 차수별 blocking을 모아 원인 층을 가립니다. 층은 structure, planning, design, other(근거 명시) 중 하나입니다. `interrupted`는 실제 blocking과 구별해서 적습니다. 중단이 반복됐다면 structure(도구·검토 방식)가 유력하니 오류 원문을 읽고 도구를 직접 재현해 봅니다. 이것은 읽기와 재현 단계입니다.
  2. `evidence/`에 진단 증거 파일을 씁니다. 세 차례의 근거와 진단을 담습니다.
  3. 세 차례 근거와 진단을 `ask`로 허브에 보냅니다. 허브가 B로 근본 조치를 정합니다.
  4. 근본 조치를 A로 대조합니다. A 밖이면 PM이 결정하고 진단 증거를 남깁니다. A에 걸리면 허브가 C로 owner에게 요청하고, 결정이 나온 뒤에 조치합니다. 이때 해당 A 번호와 증거, 남은 불확실성을 붙입니다. 해당 조치만 보류하고 독립 작업은 이어갑니다.
  5. 진단을 기록합니다.
     ```
     pace agent review-note --target <대상> --diagnosis --layer <층> --summary <진단·조치> --file <진단 증거>
     ```
     A에 걸린 경우 decision 대신 확인된 승인 원문 위치나 원장 영수증을 진단 증거에 연결합니다.
  6. 진단 뒤 첫 `pace agent verify`는 새 기준의 **전체 검토**로 돌립니다. 이전 지적으로 purpose를 좁히지 않습니다.
  7. 진단 뒤에도 fail이면 `ask_user` 단계로 갑니다. A 밖이면 PM이 `evidence/` 근거 파일에 분류 이유와 근본 조치를 쓰고 `--decision --by pm`으로 기록한 뒤 전체 재검증하고 사후 보고합니다. A에 걸리면 6요소를 붙여 허브를 거쳐 요청합니다.
- **경계**: 모든 수정 직전에 합의된 목적·목표·범위와 조치의 영향을 확인합니다. 목적·범위 변경은 A-1 또는 §6으로 올립니다. 계약 목표가 미달·미확인이면 done하지 않고 `판정: 막힘`으로 둡니다. 커밋, merge, 배포는 하지 않습니다.
- **질문과 승인 대기**: 허브 인계 1건(`ask`). 승인 대기는 근본 조치가 A에 걸릴 때만 1건이고, 걸리지 않으면 0건입니다.
