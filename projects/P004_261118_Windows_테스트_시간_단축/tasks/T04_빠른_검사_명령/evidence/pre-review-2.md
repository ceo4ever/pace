## B-1 checks 신뢰·셸 경계: **해소**

- **신뢰 기준 일치**: checks를 선택한 기준 commit의 map에서 읽습니다. 빠른 경로는 작업본 map이 JSON 데이터로 기준 map과 같을 때만 허용합니다. 따라서 작업본에서 새로 넣은 명령은 빠른 경로로 즉시 실행되지 않고, 전체 선언과 같은 기준을 씁니다. 1차의 비대칭이 제거됐습니다.
- **셸 고정**: `runDeclaredShell`은 이미 export되어 있고, Windows에서는 Git 설치 경계의 sh, 그 밖에서는 `sh -c`로 실행합니다. 정의서 전체 검사(`run = runDeclaredShell`)와 같은 셸이므로 cmd와의 의미 차이가 없습니다. S-2의 POSIX 구문 sentinel이 이를 검출합니다.
- **기존 계약 개정**: `test-map.md`의 셸 금지를 checks에만 예외로 개정하고, 전체 명령은 계속 정의서에 둡니다. 사용자가 신뢰해 명시하는 선언이라는 정의로 충돌이 정리됐습니다.
- **안전 범위**: 명령 본문 외의 스크립트(예: 작업본 `package.json`)는 격리하지 않습니다. 이는 기존 전체 검사와 같은 한계이고 문서에 "샌드박스 아님"으로 명시됩니다. 범위 안에서 안전하게 구현할 수 있다고 판단합니다.

## B-2 main이 없는 저장소와 실행 전 오류: **해소**

- **기준 선택**: 기준을 로컬 main → master → 검증된 HEAD commit 순으로 읽기 전용으로 고르고, SHA를 고정합니다. 다음 경우의 판정이 표로 확정됐습니다.
  - 저장소 밖, unborn HEAD, ref 조회 오류는 3
  - 선언 부재, 셸 확보 실패, spawn 실패는 3
  - 실행이 시작된 뒤의 실패는 1
- **기존 동작 보존**: `runDeclaredCheck`의 revision 인자는 선택 사항이고, 생략하면 종전처럼 main을 씁니다. 새 메타데이터는 필드 추가뿐이라 기존 all/finish의 ok·output이 보존됩니다. 생명주기 변경도 없습니다.
- **구현 가능성**: 실행 시작 여부는 `spawnSync` 결과의 구조값(`pid`/`error.code`/`status`/`signal`)으로 구별할 수 있습니다. 출력 문구 파싱이 필요 없으므로 구현할 수 있습니다(세부 값은 미검증, 아래 SF-2).
- **시험 범위**: S-3이 master/trunk, unborn, 저장소 밖, 손상 ref를 설치형 CLI로 덮습니다. 1차에서 지적한 `main` 샘플만으로 통과하는 허점이 제거됐습니다.

1. **PACE 자체 빠른 경로가 활성화되는 조건**
   - 기준 map은 main의 map입니다. main의 map에는 checks가 없으므로, `project/P004` worktree에서는 병합 전까지 `changed`가 항상 전체 검사로 전환됩니다.

   - 문서에는 "채택 map은 기준 브랜치에 있어야 활성화된다"를 PACE 개발 흐름의 예로도 적습니다.
2. **중단과 구조 상태의 판정 표현**
   - checks는 `spawnSync`로 동기 실행되므로 실행 중에는 부모의 신호 처리기가 돌지 않습니다. 콘솔 Ctrl+C는 부모 자체를 신호로 종료시킬 수 있어 종료코드가 1이 아닐 수 있습니다.
   - 표의 "중단은 1"은 자식만 신호나 timeout으로 끝난 경우로 한정합니다. 부모가 신호를 받은 경우는 "비성공 종료, 후속 실행 없음"으로 적어야 합니다.
   - ETIMEDOUT, ENOBUFS는 실행 시작 후 실패(1)로, pid 0/ENOENT는 미시작(3)으로 매핑하는 규칙을 시험으로 고정합니다.
3. **HEAD 폴백의 신뢰 의미 문서화**: main과 master가 모두 없으면 기준이 현재 브랜치 HEAD가 됩니다. 이 경우 "커밋된 선언만 실행"일 뿐 리뷰된 기준이라는 보호는 없습니다. 이를 채택 문서의 신뢰 경계 절에 한 줄로 적습니다.
