# T04 사전 검토 — 1단계(판정 보류)

**제공자/모델**: Anthropic, Claude Opus 5.5 (`claude-opus-5-5`). 도구 실행·파일 열람·수정은 하지 않았고, 제시된 TASK 본문만 근거로 삼았습니다.
**자동 첨부 맥락(유형만)**: 사용자 계정 식별 정보, 실행 환경(플랫폼·셸·작업 경로·날짜), 영속 메모리 설정. 검토 판단에는 사용하지 않았습니다.

## 1. 목적 정합

- 목적, T-1~T-3, S-1~S-9가 상위 목적과 대체로 일치합니다. 다른 Git 저장소에서의 빠른 관련 시험, 불확실할 때 실제 전체 선언으로의 전환, finish 전체 검사 보존이 모두 반영되어 있습니다.
- 다음 사항은 이미 잘 막혀 있습니다.
  - npm·TypeScript 하드코딩 회피와 `checks` 명시 의무화
  - "권고 문구"가 아니라 실제 전체 실행으로 전환
  - checkout 소스 CLI 착각 방지(S-6)
- **기준선 불일치**: S-7은 비교 기준으로 "원래 전체 1425.464초"를 씁니다. 그런데 재료에는 T03 이후 중앙값 680.918초가 적혀 있습니다. 현재 전체 기준과도 비교하지 않으면 개선폭이 과장되어 보일 수 있습니다. 두 값을 모두 공개하거나 기준을 명시해야 합니다.

## 2. 실현성

- 기존 runner, `runDeclaredCheck`, 실경로 검증, driver를 재사용하므로 실현 가능성은 높습니다.
- 위험은 아래 공백들에 몰려 있습니다. 특히 설치 진입점과 `checks` 셸 의미가 불명확합니다.

## 3. 조기 계획 공백

### 변경 열거

- **untracked 디렉터리 처리 미명시**: untracked를 파일 단위로 펼칠지(`-uall`) 정해져 있지 않습니다. 디렉터리로 접히면 "디렉터리 → 불확실"이 되어 불필요한 전체 전환이 일어납니다.
- **누락된 Git 상태 처리**: 아래 상태의 처리 결과(전체 전환 또는 3)가 없습니다.
  - unmerged/충돌 항목
  - typechange·모드 변경
  - submodule 포인터 변경
  - Git 미존재 또는 실패
- **커밋된 변경의 누락**: 기준이 작업본뿐이라 커밋 후에는 "변경 없음 → 3"이 됩니다. 브랜치에 커밋된 미검사 변경이 빠지는 한계를 출력과 문서에 명시하는 결정이 필요합니다.
- **Windows 경로 대소문자 매칭 미명시**: 대소문자 비구분 경로와 map glob 매칭 규칙이 없습니다.

### 범위·거짓 성공

- **복합 종료코드 규칙 없음**: 부분 단계와 전체 단계가 섞일 때 최종 코드를 정하는 표가 없습니다. 최소한 다음이 필요합니다.
  - 우선순위가 1 > 3 > 0인지
  - checks 실패 후 시험을 계속 실행할지
  - 부분 3 다음 전체 0이면 최종 0인지
- **암묵 공통 목록의 PACE 가정**: `docs/README.md`·`docs/PROJECT.md`를 암묵 공통으로 두는 것은 PACE 관례를 다른 저장소에 가정하는 것입니다. 목록을 하드코딩하지 말고 `runDeclaredCheck`가 실제로 읽는 선언 위치에서 도출해야 합니다.
- **스키마 호환성 근거 없음**: `checks` 필드를 v1에 추가할 때, 기존 또는 구버전 검증기가 알 수 없는 필드를 거부하는지에 대한 근거가 없습니다.

### 명령·cwd 신뢰

- **신뢰 기준 비대칭**: 전체 선언은 base 우선으로 읽지만 `checks`는 작업본(HEAD 기준 변경 시 전체 전환)의 map에서 읽습니다. 이 비대칭을 의도로 볼지, 같은 기준으로 맞출지 결정해야 합니다.
- **셸 의미 미명시**: `checks` 명령을 Windows에서 cmd로, POSIX에서 sh로 실행하는지 정해져 있지 않습니다. 기존 전체 선언과 같은 셸 경로를 재사용한다는 명시가 필요합니다.
- **제한 시간 출처 없음**: `checks`의 제한 시간 기본값과 설정 가능 여부가 없습니다.
- **cwd 검증 범위**: cwd의 junction/symlink 탈출 검증을 `checks.cwd`에도 동일하게 적용하는지 S-5에서 확인해야 합니다.

### 설치 진입점

- **실제 진입 방식 불명확**: "`bin/pace.ts` 호출"이라고만 되어 있고, 설치된 `pace` 명령이 실제로 어떻게 해석되는지가 없습니다. 확인할 항목은 다음과 같습니다.
  - Windows 셔임(`.cmd`/PowerShell) 여부
  - 어떤 Node 플래그나 로더로 .ts를 실행하는지
- **의존성 상태 차이**: APP_PARTS 복사본에 설치 시와 같은 의존성 상태(`node_modules` 유무)가 있는지 불명확합니다. 셔임과 의존성이 빠지면 S-6이 sandbox와 제품 경로의 차이를 놓칠 수 있습니다.

### 변경 대상 열거

- "대상은 src/test-runner, CLI help…" 수준이라 구체 파일이 없습니다. 다음을 파일 단위로 열거해야 합니다.
  - CLI 디스패치 위치와 map 스키마 검증 위치
  - 수정할 개발 스킬·문서 파일 목록
  - PACE 자체 `.pace/test-map.json`의 `checks` 내용
  - 수정 금지 대상(finish, 하네스)

## 4. 누락 증거

- `runDeclaredCheck`가 다른 저장소에서 전체 선언을 어디서 읽는지, "base 우선"의 정확한 의미
- 기존 test-map 검증기가 알 수 없는 필드를 어떻게 처리하는지
- 설치된 `pace` 명령의 실제 실행 체인(셔임, 런타임 플래그, 의존성)
- PACE `package.json`에 `typecheck` 스크립트가 있는지 여부(S-7의 tsc 측정 전제)
- S-7 대표 변경(`src/scout/card.ts`)이 현재 map에서 단일 단위로만 매핑되는지

최종 판정은 2단계에서 내리겠습니다.
