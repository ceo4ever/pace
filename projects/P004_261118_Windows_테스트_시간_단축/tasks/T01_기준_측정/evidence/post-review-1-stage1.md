## 3. 발견 사항

### A. 기준선 신뢰성과 출처 — 공개 보완이 필요합니다

**A1. 기준 측정 중에 다른 작업이 함께 돌았고, 이것이 기록되지 않았습니다.**

- **겹침 1 — 1회차와 self-test:**
  - 1회차 구간: 08:56:19 ~ 약 09:20:23
  - 같은 구간에 `self-test-final-2026-11-18T09-13-16-012Z` 실행이 있었습니다. fixture용 Node 실행, PowerShell, symlink 생성이 포함됩니다.
  - 1회차만 19초 느린 것과 시점이 겹칩니다.
  - 중앙값은 3회차 값이므로 결과에 미치는 영향은 작아 보입니다. 다만 "같은 PC·조용한 상태"라는 전제에 대한 공개가 빠져 있습니다.
- **겹침 2 — 보조 프로파일과 중첩 진단:**
  - 보조 프로파일 구간: 10:08:56 ~ 10:32:49
  - 같은 구간에 중첩 진단이 두 번 실행됐습니다(10:22:48에 약 181초, 10:27:49).
  - 이 시간대에 실행된 파일들의 보조 파일 시간은 외부 부하 아래에서 측정된 것입니다.
  - 보고서는 "실패를 포함한 기술적 분해"라고만 적었을 뿐, 동시 부하는 언급하지 않았습니다.
- **한계:** `run-N-host.json`은 각 회차 시작 직전의 스냅샷뿐이라, 회차 도중의 간섭을 잡지 못합니다.

**A2. 기준선을 만든 측정 코드의 출처가 남아 있지 않습니다.**

- `argv-order.md`에 따르면 측정 도구는 기준 실행 도중에 수정됐습니다. 09:13 self-test가 수정판입니다.
- 즉, 오래 실행되던 기준 프로세스는 수정 전 코드로 돌았습니다.
- `environment.json`에는 `measure.ts`·`report.ts`의 해시나 diff가 없습니다.
- 그래서 "바뀐 것은 reporter 위치뿐이고 기준 경로(`execute`/`parse`/`validResult`)는 동일하다"는 주장을 산출물로 입증할 수 없습니다.

**A3. 재사용 기준선에 필요한 상태 기록이 부족합니다.**

- `git diff --stat`은 추적되지 않은 파일을 보여주지 않습니다. 그런데 test glob은 추적되지 않은 시험 파일도 실행할 수 있습니다.
- 따라서 `git status --porcelain`(또는 동등한 기록)이 필요합니다.
- 이후 회차(t02/final)가 같은 환경인지 자동으로 대조하는 장치도 없습니다. 비교 대상은 Node·npm 버전, 전원 계획, Defender 상태 등입니다.

### B. 위치 파악의 품질

**B1. 파일 단위 시간의 근거가 약합니다.**

- 파일 단위 시간은 단일 보조 실행 1회에서만 나왔습니다. 그 실행은 실패 1건을 포함했고, A1의 동시 부하도 받았습니다.
- 가장 큰 파일인 project-harness(540초, 전체의 약 38%)를 포함해, 정상 파일 시간에는 표본이 1개뿐입니다.

**B2. "설명되지 않는 간극 28.6초" 산식은 전제를 밝히지 않았습니다.**

- 이 산식은 파일이 순차 실행될 때만 의미가 있습니다.
- 파일 합계(1403.8초)가 벽시계 시간(1432.4초)과 거의 같은 것으로 보아, 현재 Windows 동시성은 1로 보입니다. T03의 "4·8 비교" 계획도 이와 맞습니다.
- 그러나 보고서와 `profile-arguments` 요약 어디에도 실제 동시성 값이 적혀 있지 않습니다. 동시성이 바뀌면 이 산식은 의미를 잃습니다.

**B3. 두 번째로 큰 비용의 내부가 파악되지 않았습니다.**

- playbook-maker 묶음(177초, 약 12%)의 내부 .mjs 19개 시간 분포가 정리돼 있지 않습니다.
- 진단 TAP 원문은 있지만 파일·시험별 집계가 없습니다.
- Orca 60초 제한과 최대 4회 재시도 가설은 측정되지 않았습니다.
- 이 부분은 T02/T03으로 넘겨도 되지만, 인계 목록에 명시돼야 합니다.

**B4. `parse` 인벤토리가 suite와 실패 요약 줄을 걸러내지 못할 가능성이 있습니다.**

- **suite 혼입:** spec 출력은 suite를 끝낼 때도 `✔ 이름 (ms)` 줄을 남깁니다. 그러면 기준 인벤토리와 "비계측 정상 시험 시간" 순위에 suite가 섞일 수 있습니다. 보조 표는 `kind !== "suite"`로 거르지만, 기준 표는 거르지 못합니다.
  - "954개 정상 시험 그룹"이라는 기술이 suite 수(totals.suites)와 맞는지 검증해야 합니다.
- **실패 이중 계상:** 실패가 있는 실행에서는 spec 끝의 failing tests 재출력이 같은 실패를 한 번 더 집계할 수 있습니다.
- **오인 가능성:** `-` 기호 허용은 일반 로그 줄을 시험으로 오인할 여지가 있습니다.

**B5. 같은 이름의 시험을 등장 순번으로 맞추는 방식은 순차 실행에서만 안정적입니다.**

- 이후 동시성을 바꾼 회차와 기준선을 시험 단위로 대조하면 짝이 어긋날 수 있습니다.
- 파일 식별자가 기준 출력에 없다는 한계가 "재사용 기준선"의 시험 단위 비교력을 직접 제한합니다.
- 이후 단계의 비교 방법(예: 보조 이벤트 기반 대조)을 미리 정해 둘 필요가 있습니다.

### C. 경미·견고성

- **C1. `totalsMatch`가 판정만 남깁니다.**
  - 불일치/일치만 남기고 어떤 키가 다른지는 남기지 않습니다.
  - "총 건수는 같고 pass→fail 1건"이라는 문서의 주장을 보고서만으로 확인할 수 없습니다.
- **C2. 기준선 경로 해석 기준이 서로 다릅니다.**
  - `--profile-only` 경로는 measure에서 cwd 기준으로, report에서 저장소 루트 기준으로 해석됩니다.
  - 루트가 아닌 곳에서 실행하면 링크가 어긋납니다. 절대경로로 저장해야 합니다.
- **C3. profile-only 폴더의 `summary.json`이 실질 판정과 다를 수 있습니다.**
  - 보조 실행이 실패해도 `valid: true`가 됩니다(원본 복사).
  - 보고서와 종료 코드에서는 구분되지만, 이 폴더를 기준선으로 오인할 여지가 있습니다.
- **C4. self-test가 검증하지 않는 경로가 있습니다.**
  - signal 종료, spawn error, cancelled > 0, 실제 Windows `cmd /c npm` 경로는 검증하지 않습니다.
- **C5. 중첩 진단의 대표성이 확인되지 않았습니다.**
  - `diagnose-nested.ts`의 argv와 동시성이 wrapper(`playbook-maker.test.ts:17`)의 실제 호출과 같은지 확인되지 않았습니다.

### 잘 된 점

- 계측이 없는 기준 경로를 지켰습니다.
- 오염된 환경 변수가 있으면 실행을 거부합니다.
- 실패하면 즉시 중단하고 원시 자료를 보존합니다.
- 임의의 timeout으로 실패를 숨기지 않습니다.
- reporter 인자 순서 결함을 실증하고, 기준선과 분리해 보완했습니다.
- 추정과 실측을 일관되게 구분했습니다.
- T03 인계 조건이 구체적입니다. 단언 완화나 skip을 금지하고, 실패 주입 검증을 요구합니다.

## 4. 증거: 관측됨 vs 누락

**관측된 것(이 단계에서 본 것):**
- 측정·보고·진단 코드
- 기준 `summary.json`
- profile-only의 `profile-summary.json`과 `report.md`
- 원인 표본, 중첩 실패, 인자 순서 문서

**2단계에서 필요한 것:**

| 누락 | 용도 |
|---|---|
| 기준 폴더의 `results.json`, `run-1~3.log`, `run-N.json`, `environment.json`, `run-N-host.json` | 963/954/0/9와 종료 코드를 원문으로 확인하고, commit·dirty·Node 버전을 확인 |
| `profile-analysis.json` | 차이 2건과 totals 불일치 키를 확인(C1) |
| 기준 실행 당시의 measure.ts 버전 근거 | A2 |
| 측정 시간대의 다른 프로세스 실행 기록 또는 공개 문구 | A1 |
| `scripts/test.ts`의 Windows 동시성 값 | B2 |
| suite 수와 기준 인벤토리 항목 수 | B4 |
| 계획 계약, 시험표, 마감 문서 | 완료 기준 대조 |

## 6. 1단계 소견 (최종 판정 아님)

- **기준선 3회 자체:** 상위 목적의 핵심 요건(완전·실패 0·3회·안정적인 중앙값)을 충족한 것으로 보입니다.
- **문제가 되는 부분:**
  - 측정 중 동시 작업이 공개되지 않았고(A1), 측정 코드의 출처를 입증할 수 없습니다(A2).
  - 위치 파악의 근거 강도가 약하며(B1, B4), 간극 산식의 전제가 명시되지 않았습니다(B2).

- **최종 판정 보류:** 구현 게이트 판정은 4절의 누락 증거와 계획 문서를 받는 2단계에서 내리겠습니다.
