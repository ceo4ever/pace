# T01 재검토 — 사후 독립 리뷰

이번 검토도 도구 없이 읽기 전용으로 진행했습니다. 판단 근거는 작성자의 판정이 아니라 제시된 후보 스냅샷입니다.

## 판정: **PASS** (blocking 0, should_fix 0)

- 이전 should_fix 4건(SF-1~4)은 모두 해소되었거나, 근거를 갖춘 한계로 정리되었습니다.
- tester가 지적한 T-3 결함(요약은 정상인데 개별 결과가 빠진 경우를 성공으로 받아들이던 문제)은 이제 기준선과 보조 프로파일 양쪽에서 거부됩니다.
- 수정으로 생긴 새 차단 결함은 찾지 못했습니다.
- 긴 3회 검사의 재실행은 요구하지 않습니다.

## 1. T-3 수정 검증: 개별 결과 누락 거부

**기준선 (`measurement-data.ts`의 `checkInventory`, `parseText`)**
- 요약의 7개 키가 모두 0 이상의 정수인지 확인합니다.
- `pass + fail + cancelled + skipped + todo`의 합이 `tests`와 같은지 확인합니다. Node의 판정 집계는 서로 겹치지 않으므로 이 산식은 맞습니다.
- 판정별로 실제 행 수와 요약 수가 같은지, 전체 행 수가 `tests + suites`와 같은지 확인합니다.
- 따라서 요약이 그대로여도 행이 하나 빠지면 `complete=false`가 되고, `measure.ts`의 `validResult`가 거부합니다.
- 실패 재출력 부분은 첫 번째 `tests N` 요약 줄 앞에서 잘라 중복 계산을 막습니다.
- `ms` 단위를 반드시 요구하고 `-` 기호를 제외해, 일반 로그 줄을 결과로 잘못 읽는 경우를 줄였습니다.

**보조 프로파일 (`report.ts`)**
- 루트 요약이 정확히 1개인지 확인합니다.
- 루트 수준과 entryFile별로 각각 완전성을 대조합니다. 파일 요약 집합과 결과 파일 집합이 같아야 합니다.
- 기준 회차와 이름·판정 차이가 0이어야 하고, 키별 총계가 같아야 합니다.
- 보조 결과는 `baselineValid`가 참일 때만 유효합니다. 기준선이 무효이면 보조도 무효입니다.

**저장된 결과의 재검증**
- 원시 로그를 다시 파싱하고, `results.json`의 인벤토리와 총계, 중앙값·최소·최대와 다시 대조합니다.
- `--profile-only`도 시작 전에 같은 검증을 강제합니다.
- 그래서 결과 파일만 손상되거나 바뀐 경우도 막힙니다.

**결함 검출 시험**
- self-test는 다음 경우를 모두 다룹니다: 기본 출력 행 누락, 저장 행 누락, 보조 이벤트 누락(요약 tests=2, 인벤토리 1), 총계 불일치, 잘린 JSON.
- 정상 대조군은 종료 0, 결함을 넣은 경우는 모두 종료 1과 `valid=false`를 기대합니다.
- 검출이 실제 파서 출력에 근거하므로, 결함 주입 시험이 의미가 있습니다.

**0이 아닌 종료 코드의 의미**
- 기준선이 유효하고 보조가 실패한 기존 자료는 다음과 같이 처리됩니다.
  - `summary.json`에 `kind: baseline-only`, `valid: true`
  - 보고서에 "기준 유효 true / 보조 유효 false"를 따로 표시
  - 전체 종료 코드 1
- 실패를 성공으로 바꾸지 않고, 기준선의 유효성도 흐리지 않습니다.

**시험 범위 약화 여부**
- 도구는 시험을 고르거나, 건너뛰거나, 걸러내지 않습니다. 판정을 더 엄격하게 할 뿐입니다.
- 소스 시험이나 실행기를 바꾼 흔적도 없습니다.

## 3. 비차단 제안

1. **suites가 0이 아닐 때의 처리**
   - 기본 출력에서 suites가 0이 아니면 무조건 거부합니다. 안전한 방향의 판정이지만, T02~T05에서 `describe`가 추가되면 기준 측정 자체를 할 수 없게 됩니다.
   - MEASURE.md에 "suite가 생기면 이벤트 기반 판정 경로를 추가한 뒤 비교한다"는 조건을 적어 두기를 권합니다.
2. **가짜 행과 실제 누락이 겹치는 경우**
   - 이론상, 시험 stdout에 결과 행처럼 보이는 줄이 하나 섞이고 동시에 같은 판정의 실제 행이 하나 빠지면 개수가 맞아 통과할 수 있습니다.
   - 보조 실행과의 이름 대조가 이를 보완하므로, 보조 실행이 없는 경우의 한계로 문서화하는 정도면 충분합니다.
3. **`privacy-check.md`의 계정 별칭**
   - 이 문서가 로컬 계정 별칭을 본문에 그대로 적고 있습니다. 경로를 유지하기로 한 결정과는 별개로, 검토 문서에는 "로컬 계정 경로 2종"처럼만 적어도 됩니다.
4. **실제 OS 수준의 오류 주입**
   - 신호 종료와 spawn 오류는 실제로 주입해 보지 않았습니다. 판정 코드는 단순하고 작성자도 이 점을 밝혔으므로 차단 사유는 아닙니다.
