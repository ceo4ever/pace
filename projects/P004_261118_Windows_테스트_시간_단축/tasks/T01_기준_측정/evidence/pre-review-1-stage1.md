# 1단계: 독립 목표 평가 (T01 기준 측정 계획 v1)

**모델·첨부 컨텍스트:** 저는 Opus 5.5(`claude-opus-5-5`)입니다. 자동 첨부 컨텍스트로 사용자 계정 이메일 정보 1건이 있었습니다. 이 검토에는 쓰지 않았고 여기에 옮기지도 않습니다. 도구는 사용하지 않았습니다. 측정 결과는 아직 없는 것으로 보고 평가했습니다.

## 1. 목표 정렬

전반적으로 잘 정렬되어 있습니다.

- **변경 없이 측정:** 시험과 실행기를 바꾸지 않고 측정만 한다는 원칙이 재료와 접근 절에 분명히 있습니다.
- **기준선 요건:** 3회 실행, 중앙값, 실패 0건, 같은 PC라는 요건이 T-1과 S-1에 반영되어 있습니다.
- **느린 작업 위치 파악:** T-2(파일·시험 상위 항목, 원인 표본)가 맡습니다.
- **재사용성:** T-3(단일 명령, 원시 근거)이 맡습니다.
- **실패 처리:** 실패를 재실행으로 덮지 않고, 불완전한 결과를 제외하고, fixture로 종료 코드 전달을 검증합니다. 모두 "통과·실패 동작 보존"이라는 상위 목표에 맞습니다.

## 2. 이 계획으로 목표를 달성할 수 있는가

**조건부로 가능합니다.** 다만 아래 공백이 남으면 기준선의 유효성이나 재사용성이 흔들릴 수 있습니다.

### (가) reporter가 기준선 시간을 오염시킬 수 있음 — 가장 중요

- 벽시계 3회를 reporter를 켠 상태로 측정하면, 기준선은 일반 `npm run check`가 아니라 "계측된 실행"의 시간이 됩니다.
- reporter 주입(예: 환경 변수 상속)이 시험이 띄우는 자식 node 프로세스에까지 퍼지면 출력과 시간이 모두 바뀔 수 있습니다. 출력이 바뀌면 시험 결과 자체가 달라질 위험도 있습니다.
- 계획에는 "짧은 사전 실행으로 확인"이 있지만, 다음이 정해져 있지 않습니다.
  - 무엇을 기준선 시간으로 삼을지(계측 없는 실행인지, 계측 실행인지)
  - 오버헤드를 어떻게 정량화할지(on/off 비교 횟수와 허용치)
- 후속 태스크의 "절반" 판정이 이 정의에 직접 달려 있으므로 기준 절에 명시해야 합니다.

### (나) "실패 0건 3회"의 시도 정책이 모호함

- "재실행으로 치환하지 않음"과 "실패 0건 3회 확보"가 함께 있지만, 간헐 실패가 1회 나왔을 때의 처리가 정의되어 있지 않습니다.
  - 기준선을 연속 3회로 할지, N회 중 성공 3회로 할지
  - 모든 시도를 공개할지
  - 중단 조건을 무엇으로 할지
- 코디네이터에게 판단을 넘기기 전에 미리 정할 수 있는 정책입니다.

### (다) 커버리지 보존 비교용 근거가 부족함

- T-1은 통과·실패·건너뜀의 **개수**만 기록합니다.
- 후속 태스크에서 "커버리지 보존"을 증명하려면 개수만으로는 부족합니다. 파일·시험 **식별자 목록**과 각각의 결과를 기준 인벤토리로 남겨야 diff로 비교할 수 있습니다. 이것은 T-3의 재사용 근거에 포함되어야 합니다.

### (라) 원인 표본이 실측인지 추정인지 구분되지 않음

- 실행기와 시험을 바꾸지 않으면 spawn, git 준비, 대기 시간을 직접 계측하기 어렵습니다. 그러면 "코드 근거 연결"이 추정에 머물 수 있습니다.
- 다음을 요구 사항으로 두는 것이 좋습니다.
  - 실측 근거(이벤트 시간, 외부 추적)와 코드 독해에 기반한 가설을 구분해 표기
  - `--test-concurrency=1` 조건에서 **타입 검사 / 시험 파일 합계 / 설명되지 않는 간극**으로 총 시간을 분해
- 이 정도면 첫 태스크의 위치 파악으로 충분합니다.

### (마) 동일 호스트 조건의 기록 항목이 빠져 있음

- Windows에서는 다음 요인이 spawn과 git 시간에 크게 영향을 줍니다.
  - Defender 실시간 검사 상태
  - 전원 계획
  - 백그라운드 부하
  - 하드웨어 식별 정보
- 바꾸지 말고 **기록만** 하라는 항목이 필요합니다.
- 3회 측정의 분산(최소·최대)도 함께 남겨야, 이후 "절반" 판정이 잡음 범위를 벗어났는지 판단할 수 있습니다.

### (바) 측정 도구의 견고성

- `npm`(Windows에서는 `npm.cmd`)을 경유할 때 종료 코드가 제대로 전달되는지 확인해야 합니다.
- 실행이 멈췄을 때의 타임아웃·중단 처리와 그때 결과를 어떻게 기록할지가 S-3 fixture 범위에 없습니다.

## 3. 아직 없는 근거 (현 단계에서 정상)

- 사전 조건 확인 결과: symlink 권한, git·npm 버전
- reporter on/off 오버헤드와 자식 프로세스 상속 영향 확인
- fixture 검증 출력
- 실제 3회 측정 원시 로그, 결과 JSON, 중앙값·분산
- 시험 인벤토리, 상위 항목 표, 시간 분해

## 4. 공백을 메울 위치

| 공백 | 반영 위치 |
|---|---|
| (가) 기준선 시간 정의·reporter 오버헤드 | **기준 T-1**에 정의 추가, 접근의 사전 실행 단계에 정량 기준 |
| (나) 시도·간헐 실패 정책 | **기준 T-1**과 접근(모든 시도 기록) |
| (다) 시험 식별자 인벤토리 | **기준 T-3**과 S-3 기대 결과 |
| (라) 실측·가설 구분, 시간 분해 | **기준 T-2**와 S-2 |
| (마) 호스트 조건·분산 기록 | 접근의 환경 정보 저장 항목, S-1 기대 결과 |
| (바) 종료 코드·타임아웃 | S-3 fixture 범위 |
| 원인 심층 계측(실행기 수정 필요분) | 이 태스크 밖. 후속 태스크로 넘기되 PROJECT 결정 메모에 명시 |

**1단계 결론:** 방향과 범위는 목표에 맞습니다. (가)와 (나)를 기준 절에 확정하고 (다)를 재사용 근거에 넣으면, 유효하고 재사용 가능한 기준선이라는 첫 태스크 목표를 충족할 수 있는 계획으로 판단합니다.
