# 2단계: PROJECT·BR01 대조 검토 (T01 기준 측정 계획 v1)

이번 단계도 도구는 쓰지 않았고 파일도 바꾸지 않았습니다. 계정 식별자는 포함하지 않습니다.

## 판정: **fail (조건부)**

- **blocking 1건, should_fix 3건**입니다.
- blocking 1건은 기준·접근 절에 한두 줄을 추가하면 해소됩니다. 해소되면 구현을 허용합니다.
- 새 범위는 요구하지 않습니다.

## 독립 목표 정렬

- 계획은 PROJECT 목적(같은 PC에서 `npm run check` 중앙값 절반, 판정·검증 범위 보존)과 BR01 범위에 정렬되어 있습니다.
  - 3회 실행, 실패 0건, 파일·시험 시간, 원인 분류, 단일 명령
  - 시험·실행기 변경 제외
- PROJECT 설계가 요구하는 비교 조건도 계획에 그대로 반영되어 있습니다.
  - 실행별 전용 임시 폴더
  - 같은 PC·도구·커밋·명령
  - 이후 비교 측정에서도 같은 방식 사용
- 벽시계를 타입 검사를 포함한 `npm run check` 바깥에서 재는 것도 PROJECT 목적의 비교 대상과 일치합니다.

## 구현 준비 상태와 실제 목표의 구분

- **구현 준비:** blocking 1건만 고치면, 이 계획은 BR01 완료 기준을 측정할 수 있는 절차가 됩니다.
- **실제 목표(P-1 실측, P-6 절반):** 아직 측정되지 않았습니다.
  - 실패 0건 3회가 실제로 확보될지는 모릅니다.
  - 기준 중앙값과 분산도 모릅니다.
  - 절반 달성 가능성을 보여 주는 근거는 이 계획 어디에도 없습니다.
- T01이 끝나도 증명되는 것은 "유효한 기준선과 재사용 가능한 측정법"까지입니다. 목표 달성은 아닙니다.

## 비교를 무효화할 수 있는 측정 의미·잡음 문제

### B-1 (blocking): 기준선 시간의 의미가 계측 방식에 따라 달라질 수 있음

**문제**
- 계획은 reporter를 소스 실행기 밖의 실행 환경으로 전달하고, 자식 시험에 상속되는지는 "짧은 사전 실행으로 확인"한다고만 적었습니다.
- 확인 결과가 어떤 조건이면 통과인지, 실패하면 무엇을 하는지가 없습니다.

**비교가 깨지는 경로**
- reporter가 시험이 띄우는 자식 node 프로세스에 상속되면, 기준 중앙값은 일반 `npm run check`가 아니라 "자식마다 계측이 붙은 실행"의 시간이 됩니다.
- 이후 태스크는 바로 그 자식 프로세스 수와 실행 방식을 바꿉니다.
  - T05: CLI 시험을 함수 호출로 전환
  - T03: 동시 실행 수 변경
- 그러면 계측 비용이 줄어든 만큼 개선이 과대평가되고, P-6 절반 판정이 거짓으로 통과할 수 있습니다.
- 상속된 reporter가 자식 출력을 바꾸면 통과·실패 판정 자체도 달라질 수 있습니다.

**조치 (기준 T-1 또는 접근에 명시)**
1. 사전 실행의 합격 조건: reporter가 최상위 시험 실행에만 붙고 자식 프로세스에는 전달되지 않음을 확인해 기록합니다.
2. 이 조건을 만족하지 못하면 기준선 측정을 진행하지 않고 판단을 올립니다.
3. 기준선 시간은 이 조건을 만족한 실행에서 얻은 `npm run check` 전체 벽시계 중앙값으로 정의합니다. 이후 태스크도 같은 정의를 쓴다고 명시합니다.

### S-1 (should_fix, 잡음 통제): 비교 조건 확인용 호스트 상태 기록

**문제**
- Windows에서는 다음 요인이 프로세스 기동과 git 시간을 크게 바꿉니다.
  - Defender 실시간 검사 상태
  - 전원 계획
  - 측정 중 다른 무거운 작업 여부
- 기준선과 최종 측정 사이에 이 상태가 달라지면 비교가 오염되는데, 지금 계획으로는 사후에 알아낼 수 없습니다.

**조치**
- 환경 기록 항목에 위 상태를 **변경하지 않고 기록만** 하도록 추가합니다.
- 결과표에 회차별 시간(실행 순서 포함)과 최소·최대를 함께 표시합니다.

## 비교 의미와 관련된 근거 보완

### S-2 (should_fix): 시험 식별자와 결과 인벤토리를 보고서 형식에 고정

**문제**
- P-6은 시작과 최종의 통과·실패·건너뜀과 **시험 식별자 변화**를 대조합니다.
- 계획의 T-1·S-1은 개수만 명시합니다.

**조치**
- 파일·시험 식별자별 결과(통과·실패·건너뜀)를 원시 근거와 보고서의 고정 항목으로 지정합니다.
- T-3의 "같은 표"에 이 목록을 포함합니다.

### S-3 (should_fix): 원인 분류의 근거 등급 표기

**문제**
- 실행기와 시험을 바꾸지 않으면 프로세스 기동, git, 대기 시간을 직접 나누어 재기 어렵습니다.

**조치**
- T-2·S-2의 원인 표본에 "이벤트 시간으로 실측"과 "코드 독해로 추정"을 구분해 표기합니다.
- 총 시간을 다음 세 부분으로 분해한 값을 함께 남깁니다. 동시성 1 조건이므로 합산이 성립합니다.
  - 타입 검사
  - 시험 파일 시간 합계
  - 설명되지 않는 간극

## 선택 사항 (판정과 무관)

비교 유효성에는 영향을 주지 않는 공학적 세부입니다.

- `npm.cmd` 경유 시 종료 코드 전달과 실행 중단 처리를 fixture에서 추가로 확인
- 하네스의 Windows 전체 검사 시간 제한에 걸린 실행을 "불완전"으로 명시하는 표기
- 타입 검사 캐시나 파일 캐시 같은 첫 회 효과는 회차별 시간 기록(S-1)으로 관찰하면 충분합니다. 별도 워밍업 규칙은 요구하지 않습니다.
