## 판독기 오류 두 건의 분리와 benchmark 무변경 확인

**1. `validate-wrapper.mjs` (집중 검증)**
- 사용자 메시지(`generatedMessage:false`)를 잘못 가정해 exit 1로 끝났다.
- 실행된 판독기 원문을 보존했다.
- 재실행 없이 SHA와 124행 stack 대조로 정정했다(`newTestExecutions: 0`).
- 시험 결과 자체는 바뀌지 않았다. **판독기만 고친 수정**으로 판정한다.

**2. `verify-final.mjs` (최종 판독)**
- 반올림한 literal을 엄격 비교해서 exit 1로 끝났다.
- 첫 시도 원문, launcher, `final-views`를 보존했고, 결과는 새 `final-v2-views`에 따로 기록했다.
- 코드가 기존 출력 폴더를 덮어쓰면 단언으로 멈추도록 되어 있다.
- 기준선은 원 run 값에서 다시 계산한 중앙값으로 단언한다.
- **판독기만 고친 수정**으로 판정한다.

**benchmark가 바뀌지 않았다는 확인**
- binding과 manifest의 run-1/2/3 log SHA(`461d…`, `27b1…`, `d560…`)가 일치한다.
- `resultsSha256 5b4b…`도 일치한다.
- 판독기 SHA는 `15bf…` → `bb7e…`로, 측정 종료 뒤에 바뀐 것으로 구분되어 있다.
- 609개 소스 SHA는 측정 전후 같다.
- 두 오류는 서로 독립적으로 기록되어 있다. 어느 쪽도 시간 표본을 고치거나 다시 고르지 않았다.

## 이전 실패와 소스 위험의 기록 유지

- **보존된 이전 기록:** 다음 원문이 TASK와 결과 문서에 남아 있다.
  - 함수 세트 3회차 실패, 무효 2세트
  - stale-lock(원인 미확정)
  - preload 진단기 오류, 순서 실수
  - 이전 TASK 계획본 2개
- **과대 주장 없음:** 인과나 원인을 확정한다는 주장이 없다.
- **재선택 아님:** 새 세트는 사전 검토 통과와 main 승인 뒤의 새 label/609 세트다. 자동 재선택이나 과거 성공 합산에 해당하지 않는다.
- **wrapper 수정은 판정 완화가 아니다:**
  - 문자열 동일성을 파일 실체 동일성으로 바꿨다(정규 파일, bin 부모, native 경로, dev/ino).
  - "PATH 조회가 설치 래퍼를 찾는다"는 의도는 그대로다.
  - `&&` 연결과 원래 표기의 stderr 기록으로 실패가 더 잘 드러난다.
- **잔여 위험 (문서화됨):**
  - 같은 fixture 안 자식 프로세스의 모듈 상태 재사용(정적 감사 범위 한정)
  - inode 단독 음성 미검증
  - comparator가 파일 단위가 아니라 이름/판정 단위로 비교함(스스로 공개)

## 한계

1. **일반화 불가:** 단일 Windows PC의 새 3회 관측이다. 다른 OS나 PC의 속도나 판정을 주장하지 않는다. 플랫폼별 판정 보존은 Windows skip 사유 동일로만 확인했다.
2. **얇은 여유:** 기준 대비 약 0.51%p다. 계약 기준이 이 3회이고 3회 모두 기준을 만족하므로 재실행은 불필요하다.
3. **T05 단독 기여 아님:** 50.5% 감소는 T02~T05의 누적 효과다. T05 단독 기여는 좁은 1쌍(11.9%)으로만 기록됐다.
4. **commit 아닌 작업 트리:** 측정 소스는 HEAD `46fdf68` 위의 작업 트리이며 609개 트리 SHA `9ddc…`로 묶여 있다. 마감 commit의 실행 소스가 이 SHA와 같다는 점을 TASK-CLOSE에 연결해야 한다(새 gate가 아니라 기록 사항).
5. **tester 판정은 별도:** TASK S-7/T-3의 독립 tester 판정은 본 리뷰 범위 밖이다.
6. **열람 범위:** comparison 결과 2~5번째 비교는 잘린 본문이라 `verified: true`와 형식만 확인했다. raw log 본문은 digest로만 대조했다.
