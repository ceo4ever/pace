## 2. wrapper 시험 변경 평가

이번 변경은 "변경하지 않은 시험"이었던 파일을 측정 전에 실제로 수정한 것이다. 원래 실패의 원인은 추정하지 않는다. 아래는 변경 내용 자체만 평가한 것이다.

**의도 보존 여부: 보존된다고 판단한다.**

- **기존 검사:** `command -v pace` 결과의 첫 줄을 POSIX 경로 문자열로 정확히 비교했다.
- **새 검사:** 같은 의도, 즉 "PATH 조회가 설치된 bin의 래퍼를 찾았는가"를 파일 실체로 비교한다.
  - `cygpath -aw`로 조회 결과를 Windows 경로로 바꾼다.
  - `lstat`로 그 경로가 정규 파일인지 확인한다.
  - 부모 폴더의 realpath가 bin과 같은지, 파일의 realpath가 기대 래퍼와 같은지 확인한다.
  - 마지막으로 dev/ino(bigint)가 같은지 확인한다.
- **경로 표기 차이:** 짧은 이름과 긴 이름 같은 표기 차이에는 관대해진다. 다른 파일을 같은 파일로 잘못 받아들이는 경로는 보이지 않는다.
- **오히려 강화된 점:**
  - 명령을 `;` 대신 `&&`로 연결해 중간 단계 실패가 가려지지 않는다.
  - 조회한 원문 경로를 stderr에 남긴다.
  - 조회 결과가 경로가 아니면 `lstat`에서 예외가 나므로 실패 쪽으로 처리된다.
- **유지된 것:** 시험 이름, skip 조건, version 비교, hook과 인자 단언.
- **음성검사:** wrong-file 변이는 bin 부모 단언에서 실패했다.

**한계 (nit 수준)**

- inode만 다른 경우를 따로 거부하는지는 시험되지 않았다. manifest에도 같은 한계가 공개되어 있다.
- 단언에 `version.stderr`를 사용자 메시지로 넘겨 기본 식(expression) 메시지가 사라진다. 이 때문에 첫 검증기가 도구 오류를 냈다. 진단성의 문제이지 정합성 문제는 아니다.

**이 변경에 대한 정당성 판단은 2차로 넘긴다.**
- 이전 실패 세트를 보고 시험을 고친 뒤 새 3회로 판정한 구조다.
- 이것이 "자동 재선택"이 아니라 개정 계약에 따른 정당한 새 세트인지는 지금 판단할 수 없다. 개정 TASK와 main의 결정을 봐야 한다.
- 이전의 실패 세트는 원문 그대로 보존·공개되어 있어야 한다.

## 3. 소스 binding과 검증 도구

- **binding 일관성:**
  - HEAD `46fdf68`이 전후 같다.
  - 609개 소스 트리 해시는 `9ddc…`이며, 측정 전후 차이는 `captured` 시각뿐이다.
  - 함수 전환 세트의 `3b52…`과 다른 것은 wrapper 변경을 반영한 결과로 설명된다.
  - 측정 시작부터 binding까지 약 35분으로, 회차 3번에 걸린 시간과 맞는다.
- **commit이 아닌 작업 트리 기준:**
  - binding은 작업 트리에 대한 것이고 commit이 아니다.
  - git status에는 brain, memory, dashboard, PROJECT, log 같은 비소스 수정과 helper 미추적 파일이 함께 보인다.
  - 재현은 609개 트리 해시에 의존한다. 비소스 수정이 측정 범위 밖이라는 근거는 이번 자료로 확인할 수 없다.
- **검증기의 사후 수정:**
  - `verify-final.mjs`는 측정이 끝난 뒤 수정됐다(SHA `15bf…` → `bb7e…`).
  - 첫 시도의 exit 1은 원값 기준과 반올림한 문서 숫자를 비교한 도구 결함이었다.
  - 현재 코드는 원 기준 run에서 다시 계산한 중앙값과 같은지를 단언하고, 원값끼리 `×2 ≤` 비교를 한다. 시간 표본을 바꾸지 않은 읽기 전용 정정으로 보이며, 공개도 적절하다.
  - 기준 후보를 하나로 고정하는 것(valid, 3회, `reusedBaseline` 아님, 후보 정확히 1개)도 적절하다.
- **확인하지 못한 것:**
  - `compare-regression.mjs`의 의미와 출력
  - `caseSource=test/changed-test.test.ts` 경로의 역할
  - 각 회차 environment(같은 PC, Node/npm 버전, TMP 격리, override 없음)의 원문
  - 위 항목들은 "비계측 원래 `npm run check`, 같은 조건"이라는 판단의 전제다. 이번 자료에서는 수치로만 확인했다.

## 4. 재실행 없이 독립 판단이 가능한가

**가능하다고 본다. 조건은 다음과 같다.**

- 수치 기준, 실패와 취소 0건, skip 동일이라는 판단은 보존된 원본 metadata와 원값 재계산만으로 할 수 있다. 여유가 작긴 해도 3회 모두 임계 안이므로 재실행할 필요가 없다.
- 다음 세 가지는 2차 자료나 원문 대조로 확인해야 한다. 재실행이 필요한 사항은 아니다.
  - 회차별 comparator 결과(기존 시험의 이름, 판정, 사유 보존)
  - raw log SHA와 원문 environment의 일치
  - wrapper 변경을 허용하는 개정 계약의 존재
- 이전의 함수 전환 코드 판정(blocking 0, should_fix 0)은 이번 자료로 바뀌지 않는다.
- 이전 세트의 T-3/P-6 실패 기록은 유지되어야 한다. 이번 결과가 그 실패를 지우는 것으로 다루지 않는다.
