## 1. 의미 동등성 (직접 `main` 대 실제 CLI)

**확인된 강점**
- 오류 계약은 실제 `runCli`와 나란히 비교한다. 비교 항목은 status, stdout, stderr 원문(경고 포함), signal, error다. 사례는 exit 2 하나와 exit 1 두 개다.
- fault 주입(`--import fault.mjs`)을 쓰는 호출은 diff상 `runCli`로 남아 있다. 따라서 `fs.renameSync` 패치가 직접 호출용 자식 프로세스로 새지 않는다. 적절하다.
- 다음 호출이 생기면 실패로 처리된다(fail-safe):
  - 제품 코드가 `process.exit`를 부름 → 예기치 않은 종료
  - `stdio: inherit`로 하위 프로세스를 띄우거나 fd에 직접 씀 → raw 출력 감지
  - 요청이 끝난 뒤 비동기 출력 → raw 출력 감지

  거짓 통과로 이어지지는 않는다.

**잔여 위험 (심각도 순)**

| # | 심각도 | 내용 |
|---|---|---|
| S1 | 중 | **같은 HOME이면 자식 하나가 블록 전체에서 재사용된다.** 제품 모듈의 수준 캐시(경로, git 루트, 설정, 메모이즈)가 main 호출과 worktree 호출 사이, 부모의 git 커밋 사이로 넘어갈 수 있다. 프로세스-당-호출에서는 구조적으로 불가능했던 상태 공유다. 세대(generation)와 문맥 검증은 cwd, env, 출력 복원만 보고 모듈 내부 상태는 보지 않는다. 변환한 3개 블록이 통과한다는 사실이 현재 무해함을 부분적으로 뒷받침할 뿐, 보증은 아니다. |
| S2 | 중 | **성공 경로의 동등성은 직접 비교하지 않는다.** CLI와 함수의 1:1 비교는 오류 3건뿐이다. `done`, `BL 생명주기` 블록에서는 모든 호출이 직접 호출로 바뀌었다. 이 블록 안에서 `start`, `finish`, `merge --yes`, `done`의 성공 경로는 실제 프로세스로 실행되지 않는다. "대표 실제 CLI 보존"이 다른 테스트 파일이나 블록에 의존하는지는 이 자료만으로 확인할 수 없다. |
| S3 | 중 | **진입점 처리가 중복되어 있다.** `pace: <message>` 출력과 `UsageError ? 2 : 1` 변환을 `project-call-process.ts`가 따로 구현한다. `task` 결과 뒤의 `사전 검토: v1` 제거도 `runCli`와 따로 구현한다. 지금은 일치하지만 `cli.ts`의 최상위 처리나 `runCli`가 바뀌면 조용히 어긋날 수 있다. 공용 함수를 import하는 편이 안전하다. |
| S4 | 저~중 | **`process.argv`와 `execArgv` 차이.** 자식은 `execArgv: []`로 뜨고 `process.argv[1]`은 `project-call-process.ts`다. 제품이 `process.execPath` + `argv[1]`로 자기 자신을 다시 실행하거나(훅, 런처 등) `argv`를 읽으면 동작이 달라진다. `runCli`가 별도 Node 플래그를 쓰는 경우에도 차이가 생긴다. 이 자료로는 확인할 수 없다. |
| S5 | 저 | **`process.exitCode`를 버린다.** 반환값만 status로 쓰고 `exitCode`는 복원한다. 어떤 하위 명령이 반환 대신 `exitCode`로 상태를 알리면 CLI와 결과가 갈린다. 오류 3건에서는 드러나지 않았다. |
| S6 | 저 | **프로세스당 한 번만 나는 경고와 UTF-8 경계.** `emitWarning`류 경고는 블록의 첫 호출에만 포착된다. `Uint8Array` 조각마다 `toString`하므로 멀티바이트 경계에서 문자가 깨질 수 있다. 문자열 쓰기 위주라 실영향은 낮다. |

## 2. 프로세스 상태, 타임아웃, 출력 격리

- **env, cwd, write, exitCode 복원:** 복원과 `restored` 검증은 견고하다. 키 개수와 값 일치를 모두 본다.
- **출력 상한:** 오류가 `console.log` 내부에서 삼켜져도 `overflow` 플래그로 다시 확인한다. 적절하다.
- **타임아웃:**
  - 호출 60초, close 5초 동안 정상 종료하지 않으면 scope 전체를 poison한다.
  - 이후 `close()`가 오류를 던져 `ctx.after`가 테스트를 실패시킨다.
  - `Promise.race`로 반환된 뒤에도 백그라운드의 `operation()`은 계속 돈다. 하지만 poison으로 다음 호출이 막히므로 실해는 없다.
  - 기존 `runCli`의 타임아웃과 같은 값인지는 확인할 수 없다.
- **(관찰) Windows 고유의 새 실패 유형 가능성:** 오래 사는 자식은 제품의 fd 누수나 디렉터리 핸들을 호출 사이에 계속 쥐고 있다. 프로세스-당-호출에서는 매번 해제되던 것들이다. 이것이 뒤 호출의 rename, rm에서 `EBUSY`/`EPERM`을 낼 수 있다. 반대로 제품의 누수를 드러내는 효과도 있다. 위 3번째 전체 실행 실패와 연결짓지는 않는다.
- **(관찰) 첫 호출 cwd 의존:** 자식의 cwd는 scope 첫 호출의 cwd로 고정된다. 첫 호출이 worktree이고 그 worktree가 나중에 제거되면 `chdir(saved.cwd)`가 실패해 infra 오류가 난다. 현재 3개 블록은 모두 main에서 시작하므로 해당하지 않는다. fail-safe 쪽이라 거짓 통과는 없다.
- **가독성:** `BL 생명주기` 블록의 루프 안 `const direct = mode === "direct"`가 바깥의 `direct` scope를 가린다. `runDirect`를 미리 꺼내 두어 동작은 맞다. 다만 no-shadow 린트 위험이 있고 오독하기 쉽다.
- **`task` 호환 처리:** `existsSync(file)`은 부모 cwd 기준이라 출력 경로가 상대경로면 조용히 건너뛴다. `runCli`도 같은 방식이라면 동등하다(확인할 수 없음).

## 3. 결과 산출물 평가

- **`project-harness` 단일 파일 전체 실행:** status 0, 494초, 소스 변경 없음이 확인된다.
- **정지 바인딩:** HEAD가 같고, 609개 파일 트리를 검증했으며, 차이는 `captured` 타임스탬프 하나뿐이다. 바인딩은 일관된다.
- **선택 4개 케이스 × 3회:** 모두 통과했고 소요 시간 편차도 작다. 대략 P025 64초, done 20초, BL 26초, 신규 7초다.
- **절감 효과는 이 자료로 입증되지 않는다:**
  - 비교 대상인 baseline 요약 자체가 `valid: false`이고 범위가 "baseline-only"다.
  - 비교 형태가 단일 실행 494초 대 중앙값 704초여서 같은 범위끼리 비교한 것인지 이 자료만으로는 알 수 없다.
  - 변환한 3개 블록의 변환 전 블록별 소요 시간이 없어 블록 단위 절감도 확인할 수 없다.
- **신규 검증 테스트:** 약 7초의 비용을 더한다.

## 4. Telegram 롤백 검증 (좁힌 버전)

- **개선된 점:**
  - "두 번째 save" 같은 순서 의존을 없앴다. 대신 "메모리 표에 n3가 있는 첫 save"라는 의미 조건으로 주입한다.
  - 주입 횟수를 1로 확인한다.
  - `createForumTopic` 1회, 의도가 디스크에 먼저 기록됐는지, 실패 뒤 롤백 상태를 모두 단언한다.
  - 이전보다 명확하게 좁혀졌다.
- **진단성 약점:** save 훅 안의 `assert`나 `loadTelegramState(...)!`가 실패하면, 그 예외가 제품 쪽에서는 "디스크" 저장 실패로 처리된다. 결국 `injected === 1` 불일치로만 드러나 원래 실패 메시지를 잃는다. 탐지는 되지만 원인 파악이 어렵다.
- **구현 순서 결합:** "표 저장 시점에 메모리 의도는 undefined"라는 단언은 내부 순서에 결합되어 있다. 계약으로 의도한 것이라면 문제없다.
- **결과 미포함:** 이 자료에는 `telegram-flow` 실행 결과가 들어 있지 않아 통과 여부를 관측할 수 없다.
