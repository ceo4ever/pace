# T05 함수 전환 TASK 사전 검토

**검토자:** Anthropic · Claude Opus 5.5 (`claude-opus-5-5`). 도구, 실행, 편집은 쓰지 않았습니다.
**자동 첨부 맥락:** 사용자 계정 이메일 범주가 붙었으나 사용하지 않았고 값도 쓰지 않습니다.

## 판정: **불통과(fail)** — blocking 2 · should_fix 4

두 차단 사항은 모두 TASK 문장 수준에서 고칠 수 있습니다. 범위를 넓히거나 제품을 바꿀 필요는 없습니다.

- 계획 판단: 전환 범위, CLI 보존 목록, 정리·감사 설계는 대체로 건전합니다.
- 아직 모르는 것: 시간 효과, 새 세 회의 결과, 과거 stale-lock 실패와 대시보드 실패의 정확한 원인. 이번 판정에서 확정하지 않습니다.

## 1. 건전한 부분
- **범위:** 전환은 73블록 중 3블록뿐이고, 나머지 70블록은 byte 동일 목록과 SHA로 고정합니다. 전 과정 시험(new→merge)이 실제 CLI로 남아 BR05의 "명령별 대표 CLI"를 충족합니다. EIO의 실제 NODE_OPTIONS 주입 4회도 유지합니다.
- **새 파서 없음:** 실제 `main(["project",…])`을 직접 await합니다. bin 진입 경로는 대표 시험이 검증합니다.
- **감시와 정리:** 호출별 60초 deadline에 초기화 시간을 포함하고, 겹친 요청은 거부하며, 자동 재시작과 재시도를 하지 않습니다. 소유 자식만 종료하고, after 훅에서 close를 확인한 뒤 임시 root를 지웁니다. Windows에서는 cwd 잠금 때문에 이 순서가 맞습니다. 임의 자손을 완전히 회수하지 못한다는 한계도 공개했습니다.
- **집계:** 996 = 995 + 1, 987 통과, skip 9, 609 = 607 + 2. 예외는 정확히 2파일과 helper 2개로 제한됩니다.
- **감사:** 기계 변환한 예상 본문과 byte를 비교하고 음성검사를 합니다. 이 설계는 단언을 지우거나 약화하는 변경을 잡을 수 있습니다.

## 2. blocking

**B1 모듈·프로세스 전역 상태 격리가 계획에 없습니다**

- 기존에는 호출마다 새 프로세스라 모듈 상태가 매번 초기화됐습니다. 재사용 자식에서는 `cli.ts` 모듈 그래프가 처음 한 번만 평가됩니다.
- 다음과 같은 상태가 요청 사이에 남을 수 있습니다.
  - import 시점에 env/HOME/PACE_HOME/cwd에서 계산한 상수
  - 메모이즈된 설정·프로필·선언
  - 모듈 Map/싱글턴
  - 등록된 process 리스너와 타이머
- 이런 상태가 남으면 전환된 시험이 통과해도 다른 경로를 검증하게 될 수 있습니다. 오류가 드러나지 않는 방향이라 위험합니다.
- S-3의 fixture 2개는 new/list만 확인하므로 done/finish/merge 경로를 대변하지 못합니다.
- **최소 해소안 (아래 셋 중 하나)**
  1. `projectCommand`의 import 그래프에서 top-level의 env·cwd·homedir 읽기와 캐시를 정적으로 감사하고, 그 목록과 판정을 TASK에 연결합니다.
  2. 전환 블록마다 새 자식을 쓰고, 재사용은 한 블록 안의 호출 사이로만 한정합니다.
  3. 요청마다 리스너와 타이머 수를 기록하고, 변화가 있으면 실패 처리하는 검사를 추가합니다.

**B2 예외→상태 변환 계약이 모호합니다**

- `bin/pace.ts`는 예외를 `UsageError→2`, 그 밖의 예외는 `1`로 바꾸고, stderr에 `pace: <message>\n`을 씁니다.
- TASK의 "예외는 실패로 전달"은 두 가지로 읽힙니다. 이 매핑을 재현한다는 뜻인지, runDirect가 예외를 그대로 던진다는 뜻인지 정해야 합니다.
- done 시험에는 막힘·실패 입력의 status와 무변경 단언이 다수 있을 것입니다. 해석에 따라 단언 보존 여부가 직접 갈립니다.
- **최소 해소안**
  - 자식이 bin과 동일하게 상태 코드와 stderr를 매핑한다고 명시합니다.
  - 자식 내부 오류(IPC나 timeout)는 그와 구별되는 시험 실패로 둡니다.
  - S-3에서 같은 잘못된 명령을 실제 CLI와 runDirect로 각각 실행해 status와 stderr가 같은지 대조합니다.

## 3. should_fix

**SF-1 출력 캡처 방식과 요청 경계를 명시합니다.**
- `process.stdout.write` 후킹으로 잡으면 `fs.writeSync(1)` 출력과 stdio를 상속한 하위 프로세스(선언 셸, git) 출력을 놓칩니다.
- pipe로 잡으면 IPC 응답 뒤에 늦게 도착한 출력이 다른 요청에 섞일 수 있습니다.
- 방식을 정하고, 전환 호출의 출력 단언이 그 방식 안에서만 성립하는지 감사 결과를 기록합니다.

**SF-2 "같은 단언 실패"를 판정 가능하게 정의합니다.**
- 전환 전후 실패 위치(시험 파일 행과 assert 메시지)가 같아야 합니다.
- 그보다 앞선 단언은 통과해야 합니다. 그래야 설정 실패를 검출로 세지 않습니다.
- 자식이 import한 `cli.ts` 실제 경로가 소유 사본 안에 있음을 기록합니다. 원본을 import하면 직접 호출 쪽에는 변이가 적용되지 않습니다.

**SF-3 M3은 전환 경로를 검증하지 않습니다.**
- `writeFileAtomic`의 정리 경로는 EIO 주입이 있을 때만 작동합니다. 그런데 EIO 주입은 유지되는 runPace 실제 프로세스 쪽에서만 일어납니다. 따라서 M3은 전환 전후가 자명하게 같습니다.
- 둘 중 하나로 정리합니다.
  - M3을 "유지 경로 확인"으로 다시 분류하고, EIO 시험에서 전환 호출(finish/merge 복구)이 단언에 기여하는 변이를 하나 지정합니다.
  - 또는 M1/M2만 BR05 표본으로 삼고, EIO 블록의 전환 부분은 미표본이라고 공개합니다.

**SF-4 반환 형태와 비정상 경로를 맞춥니다.**
- runDirect가 runCli(spawnSync)와 같은 필드(`status`, `stdout`, `stderr`, `signal`, `error`)를 반환하는지, 전환 블록이 이 필드를 사용하는지 대조합니다.
- 제품 경로에서 도달할 수 있는 `process.exit`, 그리고 timeout으로 자식이 종료된 뒤 같은 파일의 이후 호출이 연쇄적으로 실패하는 상황은 "보이는 실패"로 처리한다고 명시합니다.

## 4. 차단이 아닌 선택·사전 확인
- 중첩 콜백 안의 runCli를 await로 바꾸면 컴파일 오류로 드러납니다. 감사 도구가 이를 거부하는지 음성검사로 확인하면 충분합니다.
- 전환 전후 각 1회의 시간 비교는 판단 근거로만 씁니다. 전체 기여는 새 세 회로만 판정한다는 TASK 서술이 이미 맞습니다.
- 과거 무효 2세트, 진단 결과, stale-lock 원인 미확정은 그대로 보존하고, 새 세트와 섞지 않는 원칙도 유지합니다. 추가 요구는 없습니다.

## 5. 증거 한계

- 따라서 B1의 실제 영향(캐시가 있는지), B2에서 예외를 던지는 호출이 몇 개인지, SF-1의 상속 출력 단언이 있는지는 확인하지 못했습니다. 위험이 존재하는지만 판단했습니다.
