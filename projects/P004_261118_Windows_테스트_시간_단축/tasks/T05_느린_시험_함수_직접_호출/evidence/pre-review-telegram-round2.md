# T05 수정 TASK 사전 검토 (중단 뒤 최소 수정 경로)

**검토자:** Anthropic · Claude Opus 5.5 (`claude-opus-5-5`). 도구, 편집, 시험 실행은 쓰지 않았습니다.
**자동 첨부 맥락:** 사용자 계정 이메일 범주가 붙었으나 사용하지 않았고 값도 쓰지 않습니다.

## 판정: **통과(pass)** — blocking 0 · should_fix 4

이 판정은 수정 계획이 착수 가능한지에 대한 것입니다. 새 세 회의 결과는 아직 측정되지 않았고, 과거 실패의 실제 원인도 확정되지 않았습니다.

## 1. 진단의 타당성: 그럴듯하고 근거가 정직함

시험 본문 662–688행과 진단 기록이 서로 들어맞습니다.

**경합 구조**
- 683행 이전, 시험은 `/bind` 실패 안내가 `mock.texts()`에 나타나면 곧바로 `fail2` 횟수 주입으로 교체합니다.
- 그런데 mock은 응답하기 전에 요청을 기록하고, adapter는 응답을 받은 뒤 `advance`에서 offset을 저장합니다.
- 따라서 안내가 관측된 시점은 offset 저장이 끝났다는 신호가 아닙니다. 이 구조적 틈은 소스만 읽어도 성립합니다.

**재현 결과**
- 진단 사본에서 `/bind` 응답만 지연시키자 count0은 offset, count1은 의도 저장에서 실패했습니다.
- 그 결과 제품은 "상태를 저장하지 못해 토픽을 만들지 않았다"라고 정확히 안내했습니다. 그러나 시험은 다른 문구("저장하지 못했다"와 "/bind n3")를 기다리므로 6초 timeout이 납니다. 관측된 오류 위치(`until`, 683행)와 일치합니다.
- 제품은 의도 저장 실패에 맞는 올바른 동작을 했습니다. 이는 결함이 제품이 아니라 시험의 순번 가정에 있다는 판단을 뒷받침합니다.

**증거 관리**
- manifest의 세 기록은 원본 SHA가 같고 진단·mock SHA만 다르며, `worktreeUnchanged`가 true입니다.
- 실패한 19-29 진단 원문을 보존했고, 그것을 원인 해소로 취급하지 않았습니다.
- 역사적 실행 순서를 확정하지 않는다고 명시했습니다. 진단과 근거 관리 모두 적절합니다.

**한계**
- 전체 부하 아래에서 같은 순서가 일어났다는 증명은 아닙니다.
- 원인이 달랐다면 새 세트가 다시 실패할 수 있습니다. 그 경우에도 기존 중단 절차가 그대로 적용됩니다.

## 2. 술어 주입의 단계 선택: 방향은 맞고 단언 보강 필요

`topics`에 n3가 처음 들어간 저장에서 한 번만 실패시키는 방식은 저장 순번과 무관합니다. 각 저장이 어떻게 처리되는지는 다음과 같습니다.

| 저장 | 술어 판정 | 결과 |
|---|---|---|
| `/bind`의 offset 저장 | n3 없음 | 통과 |
| `/new`의 의도 저장 (provisioning만 설정) | n3 없음 | 통과 |
| 표 저장 | n3 있음 | 1회 예외 |
| 롤백 뒤 offset 저장 | n3 없음 | 통과 |

- **한 번만 작동하는 것이 필수인 이유:** 롤백 제거 변이에서 n3가 남아도 다음 저장은 실제 저장으로 넘어갑니다. 그래서 기존 단언 "메모리에서만 등록된 채 남지 않는다"가 변이를 잡고, 반복 예외가 실패 원인을 흐리지 않습니다.
- **남는 위험:** 표가 메모리에 반영된 뒤 실제 저장 전에 `await`가 끼어 다른 저장이 먼저 실행되면, 그 저장이 n3가 든 상태를 보고 예외를 삼킬 수 있습니다. 소스를 보지 못해 확인하지 못했습니다. 아래 SF-1로 단언해 막아야 합니다.

## 3. should_fix

**SF-1 주입 단계 단언**

주입이 일어나는 순간 다음을 함께 단언합니다.
- `provisioning.n3 === true`
- n3가 든 의도 저장이 그 전에 실제로 성공했음(예: 실제 저장 횟수 ≥1과 직전 상태)
- 주입 1회, `createForumTopic` 1회

수정한 실제 파일로도 S-5 통제 지연 trace를 남깁니다. 지금은 사본에서만 남아 있습니다.

**SF-2 `/bind`의 `fail=1` 순번 주입 정당화**

이 주입도 같은 부류의 순번 가정입니다. 범위를 넓히지 않고, 기존이나 S-5 trace로 다음을 기록하면 됩니다.
- 교체 직후 첫 저장이 `/bind` 상태 저장이라는 근거
- 그 앞에 대기 중인 offset 저장이 없다는 근거

근거가 반대로 나오면 수정하지 말고 중단한 뒤 다시 묻습니다.

**SF-3 TASK 내부 일관성**

기존 문서 일부가 새 예외 1파일과 충돌합니다.
- S-1의 조건 "변경 없는 실행 소스"
- S-2의 방법 "T04 comparator"
- S-3의 기대 "본문 보존"
- 접근 1과 5

하위 절 한 문장으로 이를 대체한다고 처리하기보다 표 자체를 갱신하는 것이 맞습니다.
- S-3은 "606개 동일 + 예외 1개 정확한 SHA 쌍"으로 바꿉니다.
- 템플릿 규칙에 따라 T-2 변경 이유를 PROJECT 결정 메모에 남깁니다.
- 이 변경은 BR05의 함수 전환이 아니라 시험 결함 수정입니다. 따라서 '바꾼 시험 검출력'은 변이 결과로 따로 기록하고 전환 수 0을 유지합니다.

**SF-4 보조 comparator의 예외 검증을 결정적으로**

"대상 1건 외 본문 동일"을 기계적으로 정의합니다. 예를 들어 대상 시험 블록 바깥의 byte가 원본과 같은지, 원래 단언 문장 literal이 모두 남아 있는지로 판정합니다.

측정 전에 음성 smoke를 두 가지 넣습니다.
- 다른 시험 파일을 바꾸면 거부되는지
- 대상 파일의 다른 시험을 바꾸면 거부되는지
