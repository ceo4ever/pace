# 두 번째 장치 검증 결과와 실행 순서 오류

불필요한 realpathSync wrapper를 제거했다. 작은 장치 확인에서 realpathSync 본체와 native 함수는 모두 호출됐지만, 반환 경로의 문자열 동일 단언은 실패했다. 본체는 ROOT-U~1 형식, native는 root-user 형식의 동일한 Windows 디렉터리를 돌려줬다. 두 반환 경로의 stat dev/ino가 같은지 읽기 대조해 동일 디렉터리임을 확인했다. 이 작은 검사 결과 자체는 status1로 보존하며 통과로 고치지 않는다.

PM은 작은 검사 도구의 실패를 확인하고 다음 단계를 멈춰야 했지만, 연속 도구 호출에서 반환을 판정하지 않고 좁은 시험을 진행했다. 승인된 선행 조건의 실행 순서를 지키지 못한 실수다. 이를 숨기지 않고 전체 단계는 중지했다.

좁은 실제 대상1회는 `dashboard-trace-2026-11-18T20-31-07-176Z`이며 원래 단언·skip을 유지해 통과했다.8개 자식 모두code0/signal null, 실제 argv의 file URL --import와 READY의PID/URL/실제preload SHA가 일치했다. stderr는 각 READY 한 줄뿐이다. 실제 실행 전체 파일의 대상 블록 앞뒤 byte가 원본과 같아서6자식 등 다른 시험에 preload가 들어가지 않았음을 검증했다. corrected-native-narrow-proof.json에 연결했다.

관측기 진입은 입증됐고 원래 stale-lock 실패는 이번 좁은 범위에서 재현되지 않았다. 그러나 작은 장치 확인이 실패했고 순서도 어겼으므로 PM이 조건 충족을 자의적으로 선언해 전체 진단을 시작하지 않는다. 추가 좁은/전체 실행은 없었다. 실제 제품/시험은 변경하지 않았다.

main이 관측기를 더 보정하며 반복하지 말라고 한 원칙에 따라, 필요하면 API 래핑을 전부 제거하고 대상8자식 stderr/상태만 수집하는 안으로 축소할 수 있다. 기존 원문과 모든 진단기 오류는 그대로 남기며 원래 비계측 실패 세트의 원인을 해결했다고 주장하지 않는다. 다음 범위 판단을 요청한다.
