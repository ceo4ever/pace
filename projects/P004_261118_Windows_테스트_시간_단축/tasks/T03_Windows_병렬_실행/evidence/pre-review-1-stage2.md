## 2. 핵심 질문별 평가

### 객관적 선택과 안정성 검증: 충족

- **비교 4회:** 4→8→8→4 순서로 실행합니다. 모두 종료 0이고 실패·취소가 0이어야 하며, 중앙값을 사전 규칙으로 비교합니다. 사후에 재량이 개입할 여지가 없습니다.
- **5회 검증:**
  - 선택값을 기본값과 unit 기대값에 반영한 뒤 코드를 고정하고, override 없이 새로 5회 실행합니다.
  - 이 방식은 **실제 기본 경로**(`npm run check` 그대로)를 검증하므로 계약 취지에 정확히 맞습니다.
  - S-4 표본을 섞지 않는 원칙도 명시되어 있습니다.
- **남은 점:** 재시작 단위가 문언상 모호합니다(SF-4).

### 실제 runner 전달: 방향은 맞음, 규칙이 미확정

- **npm 경계는 사전 확인으로 실증되었습니다.**
  - `npm run check -- -- --test-concurrency=4`에서 인자가 `&&` 뒤의 `npm test`에만 붙습니다.
  - 그 결과 runner argv는 `["--test-concurrency=4"]`이고, typecheck에는 인자가 전달되지 않습니다.
  - 실제 `check` 스크립트 구조(`npm run typecheck && npm test`)와 같은 모양입니다.
- **사전 확인이 증명하지 않는 부분:** runner→node 배치와 실제 동시 실행입니다. 사전 확인 문서 자체가 이를 명시합니다. 이 둘은 S-1·S-2의 몫입니다.
- **현재 결함:** `testArguments`는 extra 전체를 glob **뒤에** 붙입니다. 기존 첫 시험은 `--test-name-pattern=예시`가 glob 뒤에 오는 모양을 그대로 단언합니다. 즉 형식만 고정할 뿐, 실제 전달 실패를 숨기는 상태입니다.
- 계획은 이 결함을 바로잡겠다고 하지만, 옵션과 파일이 섞인 인자를 나누는 규칙이 없습니다(SF-1).

### check 범위 보존: 충족

- override 경로도 typecheck와 전체 glob을 그대로 실행합니다.
- 인벤토리 대조 기준이 있습니다: T02의 968건, skip 9건과 사유, 19개 중첩, 의도한 이름 변경·추가 목록.
- 단, 병렬 실행에서 대조 방식이 순서에 의존하면 위험합니다(SF-3).

### Git EOL 증거 보존: 방향 타당, 검증 범위 보강 필요

- **사전 확인 결과:**
  - 원본 = blob이고, autocrlf checkout 필터를 거치면 바이트가 바뀌는 것이 재현되었습니다.
  - 사용자 Git 설정은 바꾸지 않았습니다.
- 따라서 P004 evidence 경로에 한정해 `-text`를 두는 것은 필요하면서도 범위가 최소인 조치입니다. diff 가독성을 유지하려면 `binary`보다 `-text`가 낫습니다.
- **보강할 점:** 사전 확인은 LF 파일 하나, checkout 방향 하나만 봤습니다(SF-5).
