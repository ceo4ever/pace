# T03 사전 검토 (Phase 1, 독립·읽기 전용)

**검토 주체:** Anthropic, Claude Opus 5.5 (`claude-opus-5-5`). 도구는 사용하지 않았습니다.

**첨부 맥락:** 계정 식별 정보 형태의 자동 첨부 맥락이 있었습니다. 내용은 검토에 쓰지 않았고 여기에 옮기지 않습니다. 저장소, 코드, 증거 파일은 제공되지 않았습니다. 따라서 아래 판단은 TASK 계획 문서 하나만 근거로 합니다.

**최종 게이트:** Phase 2로 유보합니다. 이 문서는 승인이나 반려가 아닙니다.

---

## 1. 계획과 실측의 구분

| 구분 | 내용 |
|---|---|
| **선행 실측 (T01·T02, 문서 기재값)** | 기준 3회 중앙값 1425.464초(963건, 실패 0, skip 9). T02 단회 1423.024초(968건). 19개 `.mjs` 181건 통과. 옵션이 첫 파일 뒤에 오면 해석되지 않는 현상 관측. |
| **T03 실측** | **없음.** 4·8 시간, 선택값, 5회 안정성, 보조 프로파일, CRLF 필터 결과는 모두 미래 계획입니다. |
| **주의** | "4 또는 8로 빨라진다"는 가정일 뿐입니다. 실제 이득 규모는 미확인입니다. 타입 검사 단계와 중첩 19개 파일의 직렬 비용이 상한을 정할 수 있습니다. |

## 2. 목표 정합성

- **정합:** 범위 보존(T-1), 4·8 비교와 반복 안정성(T-2), 재현 가능한 증거(T-3)가 상위 목적의 세 축에 대응합니다.
- **정합:** ABBA 순서(4→8→8→4), 비교 표본을 5회 검증에 섞지 않는 원칙, 재시도로 실패를 은폐하지 않는 원칙, P-6 최종 달성을 T03 범위에서 분리한 점이 적절합니다.
- **미흡:** "materially faster"를 판정하는 기준이 없습니다. 4와 8이 모두 1 대비 이득이 미미할 때의 결론 경로도 없습니다(아래 G1).

## 3. 실행 가능성

전반적으로 실행 가능합니다.

- 측정량은 비교 4회, 검증 5회, 프로파일 1회입니다. 병렬로 단축된다면 동일 PC에서 하루 안에 수용 가능한 수준입니다.
- 기존 T01 도구를 재사용하므로 신규 위험이 작습니다.
- 위험은 주로 옵션 전달 경계와 공유 상태 경합에 있습니다. 둘 다 이미 시험 계획에 들어 있습니다.

## 4. 실질 보완점 (우선순위순, 보완 위치 명시)

### 높음

**G1. 기준선과 최소 이득 기준이 없습니다.** → 위치: 기준 T-2, 접근 3번째 항목
- 현재 선택 규칙은 4와 8 중 하나를 고를 뿐입니다. 선택값이 1보다 충분히 빠른지는 판정하지 않습니다.
- T01 기준선은 다른 시점의 측정이라 드리프트가 섞입니다.
- 제안: 같은 세션에 concurrency=1을 최소 1회 기준점으로 넣습니다. 또는 T01 대비 비교의 한계를 명시합니다.
- 제안: "선택값 중앙값이 1 대비 X% 미만으로 개선되면 기본값을 바꾸지 않고 결과만 기록한다"는 경로를 추가합니다.

**G2. "5% 이상"이 노이즈와 구분되지 않습니다.** → 위치: 접근 3번째 항목
- 2회 중앙값은 곧 평균이라 변동에 취약합니다.
- 제안: "8의 최댓값이 4의 최솟값보다 작고, 동시에 중앙값 차이가 5% 이상"처럼 범위 겹침 조건을 넣습니다. 겹치면 4를 선택합니다.

**G3. S-2의 "서로 다른 PID"는 동시 실행 증명이 아닙니다.** → 위치: 테스트 S-2
- Node 테스트 러너는 concurrency=1에서도 파일마다 별도 프로세스를 띄웁니다.
- 제안: 시간 겹침을 직접 증명합니다. 예를 들어 두 표본 파일이 서로의 marker 파일을 제한 시간 안에 기다리는 배리어를 둡니다. 이 방식이면 concurrency=1일 때는 RED, 2일 때는 GREEN이 됩니다.

**G4. 옵션을 glob 앞으로 옮길 때 extra 인자 분류 규칙이 없습니다.** → 위치: 접근 1번째 항목, S-1
- extra에는 옵션과 추가 파일이 섞여 들어옵니다.
- 정할 것:
  - `-`로 시작하는 토큰의 분류 방식
  - `--test-name-pattern value`처럼 두 토큰으로 된 옵션의 처리
  - `--` 이후 인자의 처리
- 기본 `--test-concurrency=1`과 override가 함께 들어오면 마지막 값 우선 동작에 의존하게 됩니다. override가 있으면 기본값을 **대체**하도록 명시하고, unit으로 고정합니다.

**G5. 중첩 실행의 동시성 곱이 검토되지 않았습니다.** → 위치: 재료, 접근 2·3번째 항목, S-6
- 19개 `.mjs` 중첩 시험이 내부에서 `node --test`를 다시 띄운다면, 외부 N × 내부 기본값만큼 프로세스가 과다 생성될 수 있습니다. 내부 기본값은 코어 수−1입니다.
- 이 경우 시간 이득이 상쇄되거나 시간 초과·취소가 늘 수 있습니다.
- 제안: 내부 호출의 동시성이 명시되어 있는지, `NODE_TEST_CONTEXT`·`NODE_OPTIONS`가 상속되는지 확인하는 항목을 추가합니다.

### 중간

**G6. 실패 시 복귀 경로가 불완전합니다.** → 위치: 기준 T-2, 접근 3·4번째 항목
- S-4 수정 후 4·8 **양쪽 모두** 새 묶음으로 재시작하는지 명시해야 합니다.
- S-5 도중 실패하면 5회 카운터를 초기화한다는 규칙이 필요합니다.
- 4가 반복 실패할 때의 대안(1 유지 후 종료하고 원인을 후속 과제로 넘김)을 정해야 합니다. 이 대안이 없으면 태스크가 끝나지 않을 수 있습니다.

**G7. 결과 순서가 바뀌어도 대조가 틀리지 않아야 합니다.** → 위치: 접근 3번째 항목, S-4
- 병렬에서는 파일 간 출력 순서가 바뀝니다.
- "이름/순번 대조"는 파일 단위로 정규화하거나 순서와 무관한 다중집합 비교여야 합니다. 그렇지 않으면 거짓 불일치가 납니다.

**G8. "지원되는 기본값"의 범위가 불분명합니다.** → 위치: 기준 T-3, S-7
- 4나 8 같은 고정값은 이 PC의 코어 수와 메모리에 묶입니다.
- 코어가 더 적은 Windows 환경에서 8은 과다 할당입니다.
- 제안: 코어 수, 메모리, 디스크, Defender 실시간 검사 상태를 측정 metadata에 기록하고, 지원 범위를 문서화합니다. 고정값과 `min(N, availableParallelism)` 중 무엇을 택할지도 결정 메모로 남깁니다.

**G9. 공유 상태를 사전에 정적 점검하지 않습니다.** → 위치: 접근 3번째 항목
- 현재 계획은 RED가 나온 뒤에만 고칩니다. 실패 한 번에 전체 회차(수 분 이상)를 소모하게 됩니다.
- 제안: 고정 포트, 저장소 내 파일 쓰기, 고정 경로 lock, 전역 Git 설정 접근을 착수 전에 grep으로 목록화합니다. 이는 실패를 예측하는 용도일 뿐이고, 증거는 여전히 RED로 확보합니다.

**G10. 5회 무실패의 통계적 의미를 과장하지 말아야 합니다.** → 위치: S-5, S-7
- 5/5 성공은 "흔한 flake가 없다" 정도만 뒷받침합니다. 드문 경합은 배제하지 못합니다(대략 rule of three 수준).
- 문서에는 "안정성 증명"이 아니라 "관측 범위 내 실패 0"으로 표현합니다.

### 낮음

**G11. 비Windows 실행은 이 PC에서 실측할 수 없습니다.** → 위치: S-1, S-7
- 인자 재배치는 모든 플랫폼에 영향을 줍니다.
- unit 가상 플랫폼 검증의 한계를 명시합니다. 가능하면 Linux CI나 WSL 1회 확인을 후속으로 남깁니다.

**G12. `.gitattributes`의 형태를 확정해야 합니다.** → 위치: S-3
- `-text`와 `binary` 중 무엇을 쓸지 정합니다(diff 가독성이 필요하면 `-text`).
- 이미 커밋된 evidence가 재정규화 대상이 되지 않음을 확인합니다. 기존 해시를 바꾸지 않는다는 원칙과 맞춰야 합니다.

**G13. 이중 `--` 경로에 관한 증거 요건입니다.** → 위치: S-2
- `npm run check -- -- --test-concurrency=N`의 전달은 Windows npm(cmd 셸 경유)에서 깨지기 쉽습니다.
- S-2가 이를 다루지만, 실제 사용한 npm·Node 버전과 셸을 metadata에 고정하는 것을 기대 결과에 명시하는 편이 좋습니다.

## 5. 종합 의견 (Phase 1)

- 계획의 방향과 증거 규율(원문 보존, 표본 분리, 재시도 금지, 귀속 절제)은 상위 목적과 잘 맞습니다. 실행 가능성도 충분합니다.
- 착수 전에 문서에서 보완할 것을 권장합니다:
  - **G1~G5:** 기준선과 이득 판정, 노이즈를 견디는 선택 규칙, 동시성 증명 방식, 인자 분류와 override 대체, 중첩 동시성
  - **G6:** 실패 시 종료 경로
- 나머지는 착수 중 보완해도 됩니다.
- 최종 판정은 Phase 2에서 내립니다.
