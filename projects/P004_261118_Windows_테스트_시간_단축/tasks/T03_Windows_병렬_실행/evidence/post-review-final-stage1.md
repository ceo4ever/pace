# T03 최종 검토 1단계 (독립 사후 판정, 게이트 보류)

## 맥락 공개
이 검토자는 같은 T03의 중간 검토 세 차례(1단계, 2단계, 비교 재검토)에 참여했습니다. 따라서 4·8 비교 결과와 도구 설계를 이미 알고 있으며, 완전히 독립된 맥락이라고 주장하지 않습니다. 이번 판단은 위에 제시된 현재 산출물만을 근거로 합니다. 수정된 TASK와 작성자 최종 문서는 아직 받지 않았습니다.

## 2. 선택 경로 평가: 8 실패 뒤 4로 전환

**타당한 점**
- 실패 원문이 보존되었고, `assess-selected.ts`가 그 실패(`status 1`, `fail 1`)를 오히려 단언합니다. 실패를 지우지 않습니다.
- 전환 결정은 측정 전에 등록되었습니다. 결정 파일 SHA와 taskHash가 `candidate4-validation-launch.json`에 묶여 있습니다.
- 4가 실패하면 즉시 중단한다는 규칙이 있어, 성공할 때까지 후보를 바꿔 가는 선택 편향을 막습니다.
- 4는 비교 2회와 기본값 5회, 합계 7회 연속으로 정상이었습니다.

**계약상 질문 (2단계에서 확인할 것)**
- 원래 TASK의 접근은 "실패 관측은 보존하고 **고친 뒤** 새 검증 묶음"과 "적합한 값이 없으면 1 유지 후 main 판단"입니다. 원인을 고치지 않고 다른 후보로 전환하는 경로는 원 TASK에 없습니다.
- main 승인은 있으므로, 수정된 TASK·PROJECT 결정 메모에 이 변경과 이유가 정본으로 반영되었는지 확인이 필요합니다.
- BR03 범위의 "불안정 시험을 찾아 원인을 고친다"는 미충족 상태로 남습니다.

## 3. 잔여 위험

1. **8 실패의 원인을 모릅니다.** 진단 대조군(단일 E2E 1건 180초, 181건 묶음)은 모두 통과했고 재현되지 않았습니다.
   - 이것만으로는 동시성 압박 때문인지(timeout, 자원 경합), 동시성과 무관한 잠재 flaky인지 구분할 수 없습니다.
   - 후자라면 4에서도 낮은 빈도로 다시 나타날 수 있습니다. 7회 무실패는 그 가능성을 배제하지 못합니다.
2. **실패한 시험이 장시간 브라우저 E2E입니다.** 단독으로 약 180초가 걸려 임계 경로에 가깝습니다. 동시성이 높을수록 이 시험의 자원 민감도가 커질 수 있습니다. 후속 태스크나 최종 3회에서 관찰할 대상입니다.
3. **진단 hook의 동등성은 서술로만 확인됩니다.** "actions·retries·assertions 불변"이라는 설명만 있고 코드는 제시되지 않았습니다.

## 4. 코드·도구 관찰

**나머지 코드**
- `scripts/test.ts`의 Windows 기본값은 4입니다. 비Windows 기본값은 변하지 않았고, 명시 override 경로와 test-command 기대값이 일치합니다.
- 종료·신호 코드는 바뀌지 않았습니다.
- 새 blocking 결함은 관측되지 않았습니다.

**`assess-selected.ts` (nit)**
- `selected === 4`와 `excludedCandidate === 8`이 하드코딩되어 있어 이번 결정 전용 검증기입니다. 결정 파일에서 값을 받도록 하면 재사용할 수 있습니다.
- `source-boundary.json`은 수집 뒤에 추가된 검증기라는 점이 공개되어 있습니다. 수집 전에 등록된 검증은 아니므로, 증거 등급을 그만큼 낮춰서 봐야 합니다.

**`reconcile-profile-initial-result.json`**
- 원인은 LF blob과 CRLF 작업본 해시를 비교한 검증기 오류이며, 원문이 보존되었습니다.
- 수정된 reconcile 코드는 제시되지 않았습니다. 정규화 방식이 실제 내용 동일성을 보장하는지는 2단계에서 확인해야 합니다.

## 5. 1단계 증거의 한계

- **8 실패 원문**(raw 로그, 실패 시험 이름, 오류 메시지)과 `pre-review-2-stability.md`를 받지 않았습니다. "healer" 실패의 성격은 간접 서술로만 알고 있습니다.
- **보조 프로파일**이 어느 동시성으로 실행되었는지 명시가 없습니다(코드상 기본값 4로 추정). 병목·중첩 비용 분석 결과도 이번 산출물에 없습니다. S-6이 요구하는 "주요 병목 공개"는 미확인입니다.
- **5회 raw 원문**은 받지 않았습니다. 메타데이터, npm 줄, 평가 JSON만 확인했습니다.
- **S-7**(순차 도입 이력 조사, 문서·브레인 갱신)은 아직 보지 못했습니다.
- **호스트 상태**는 시작·종료 스냅숏과 회차별 부하 기록뿐입니다. 조용한 호스트임을 증명하지 않습니다.

## 6. 잠정 소견 (게이트 아님)

- **관측상 충족된 것:** 기본값 4로 override 없이 고정 소스에서 연속 5회 정상, 실패·취소 0, 범위·skip 보존, 보조 프로파일 분리. 이는 T-2·S-5·S-6의 관측 요건에 부합합니다.
- **정본 반영 확인이 필요한 것:** 8에서 4로의 전환이 원 TASK 접근과 다르다는 점.
- **원인 미해결:** 8 실패. 2단계에서는 한계·후속으로 명시되었는지를 확인 대상으로 둡니다.

2단계에서 받을 자료는 다음과 같습니다.
- 수정된 TASK와 결정 메모
- 8 실패 원문
- 보조 프로파일 병목 결과와 실행 동시성
- reconcile 수정 코드
- S-7 문서·브레인
