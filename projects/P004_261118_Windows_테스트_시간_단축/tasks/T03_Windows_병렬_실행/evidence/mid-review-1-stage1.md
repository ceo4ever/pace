# T03 중간 코드 리뷰 (Phase 1, 읽기 전용)

> 자동 컨텍스트: 계정 식별 정보 범주가 첨부되었습니다. 이 리뷰에는 사용하거나 기재하지 않았습니다.

## 요약
인자 재배치(`testArguments`), 실제 npm 경로의 겹침·필터·실패 전달 RED/GREEN, ABBA(4→8→8→4) 직렬 순서, 실패 시 즉시 중단·원문 보존 설계는 방향이 타당합니다. 다만 **비교 그룹이 첫 회차에서 실패할 가능성이 높은 결함 하나**와, **"통제된 비교"라는 주장을 약하게 만드는 공백 몇 가지**가 있습니다.

## 차단 가능성
1. **`toolHashes` 누락 의심.** `sourceFingerprint`는 `host.toolHashes`를 요구합니다. 그런데 보이는 `measure.ts` diff의 `host` 객체에는 해당 필드가 없습니다. 이 diff가 전부라면 1회차 직후 `Missing source/tool hashes`로 그룹이 실패합니다. preflight 문서는 "도구5개 SHA"를 기록한다고 하므로, diff 밖에 구현이 있는지 확인이 필요합니다. 없다면 주장과 코드가 불일치합니다.

## 높음
2. **유효 동시성의 회차별 증거가 없습니다.** `requestedConcurrency`와 `nodeArguments`는 측정기가 *계산한* 값이지, 실제 자식 Node가 받은 argv가 아닙니다. npm 전달이 실패해 기본값 1로 돌더라도 범위 대조는 통과하고, 결과는 "4/8"로 기록됩니다. 실제 npm 경로 확인은 fixture와 일회성 `measure-option-validation.json`뿐입니다. 실행기가 최종 argv를 로그에 남기고 비교기가 이를 대조하는 방식을 권합니다.
3. **소스 fingerprint 범위가 좁습니다.** 해시 대상은 `test/**/*.test.ts`, `scripts/test.ts`, `helpers.ts`뿐입니다. 테스트 대상 소스(src 등), `package.json`의 `check` 스크립트, tsconfig, lockfile이 바뀌어도 "소스 동일"로 판정됩니다. 특히 `-- --test-concurrency` 전달은 실제 `check`가 "typecheck && npm test" 순서일 때만 test로 갑니다. fixture는 이 순서를 가정하지만 실제 `package.json`은 검증되지 않았습니다.
4. **기준 1 대비 판단이 없습니다.** 선택 규칙은 4와 8 중 하나만 고릅니다. 4가 현행 1보다 실질적으로 빠른지는 같은 조건에서 측정하지 않으며, 1 유지는 실패 경로에만 있습니다. 상위 목적(실질적 비용 절감)에 비추면 같은 그룹 안의 1 대조군 또는 명시적 최소 개선 기준이 필요합니다.

## 중간
5. **호스트 동일성을 대조하지 않습니다.** 회차마다 power scheme, Defender, Node/npm 버전, 코어 수를 기록하지만 네 회차 간 일치 여부는 단언하지 않습니다.
6. **새 겹침 시험이 고동시성 전체 실행에서 flaky할 수 있습니다.** 이 시험은 전체 회귀 안에서 중첩 npm(typecheck 포함)을 두 번 띄웁니다. 그런데 배리어 마감은 3초, 프로세스 타임아웃은 20초입니다. 동시성 8의 Windows 부하에서는 두 번째 워커 기동이 3초를 넘어 거짓 실패가 날 수 있고, 무재시도 규칙 때문에 그룹 전체가 무효가 됩니다. 실패 원인 구분용 로그(진입 시각 등)가 실패 시에도 남는지 확인이 필요합니다.
7. **표본 크기와 임계값.** 설정당 2표본, 5% 임계값은 Windows 잡음(Defender 스캔, 캐시 워밍) 범위 안일 수 있습니다. 문서가 한계를 밝히고 있지만, 4 그룹 두 값의 분산을 함께 기록해 잡음 대비 차이를 보여 주는 편이 좋습니다. 1회차 콜드 캐시 효과는 ABBA로 일부만 상쇄됩니다.
8. **`scopeComparison`의 대조 범위.** 이름·판정 다중집합만 비교하므로 파일 귀속과 suite 수는 기준과 대조되지 않습니다. 같은 이름의 케이스가 파일 간에 바뀌어도 통과합니다(문서에 일부 인정됨). 실행 기준 시간은 `npm run check` 전체, 즉 typecheck 포함이라 동시성 효과가 희석됩니다.

## 낮음
- `readRuns`는 `run.log` 경로가 존재하면 보관본 대신 원래 경로를 읽습니다. 보관본 우선이 더 안전합니다.
- `compare.ts`의 `toolHashes` 키가 절대 경로라 로컬 사용자 경로가 evidence에 남고, 이식성도 떨어집니다. 상대 경로를 권합니다.
- 알 수 없는 `--opt=value`는 무검증으로 통과합니다. 의도된 동작이면 문서화가 필요합니다.
- `--` 구분자 뒤에 glob을 두는 형태는 반환 배열만 검증하고, Node 실제 동작은 검증하지 않습니다.
- `.gitattributes`의 `**/evidence/** -text`는 범위가 저장소 전체 evidence입니다. 의도와 일치하는지 확인이 필요합니다.

## 미해결 질문 (현재 벤치마크 종료 후 확인 대상)
- `toolHashes`는 어디서 기록되며, 왜 diff에 없습니까?
- 실제 `package.json`의 `check` 정의와 인자 전달 위치는 어떻게 되어 있습니까?
- 4 선택의 정당화 기준은 무엇입니까? 기준 1 대비 최소 개선폭이 정해져 있습니까?
- 겹침 시험의 3초 마감은 동시성 8 Windows 부하에서 충분합니까?

결론과 판정은 phase 2의 계약·disposition 확인 후로 보류합니다.
