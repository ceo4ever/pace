## 직렬 도입 경위의 확인 범위

Windows의 파일 동시성 1은 최초 공개 커밋 28192e5부터 존재한다. 이력과 브레인 조사에서 구체적인 도입 이유는 확인하지 못했다. 주석의 Windows 전용 직렬 실행 사실을 안정성 원인 설명으로 확대하지 않는다. P004 T02에서 해결한 중첩 공용 TMP 간섭은 외부 동시성 1에서도 관측됐으므로, 과거 직렬 선택의 이유나 병렬화가 만든 결함이라고 단정할 근거가 아니다.

## 실제 동시성과 임시 경계

Node 옵션은 파일 glob보다 앞에 전달한다. 이름 필터가 단지 argv에 포함됐는지만 확인하면 부족하다. P004는 실제 npm→runner→worker 경계에서 두 worker의 서로 다른 PID와 진입·해제 시간 구간이 겹치는 barrier를 검증했다. 동시성 1에서 이 검증은 실패하고 2에서 통과해야 하며, 제외 대상 sentinel과 실패 종료 전달도 확인한다. 플랫폼 기본값과 사용자 명시 override는 구별한다.

Node 24의 test launcher 자체에는 --import가 실행되지 않고 파일 worker에서 실행될 수 있다. 중첩 원래 19파일은 worker마다 기존 helper를 명시 preload해 독립 TMP/HOME을 소유하게 했고, worker 19개와 종료 정리 19개를 실제 trace로 대조했다. launcher까지 더해 20개여야 한다는 진단 도구의 최초 가정은 틀렸으며 원래 실패 판정과 교정한 재검증을 모두 보존했다. 전역 NODE_OPTIONS로 계측을 상속시키지 않는다. 자기 임시 누수 단언과 peer 간섭 구별은 [[작업-하네스-실측-함정]]의 임시 폴더 경계와 함께 본다.

## 속도 후보와 안정성 후보를 구별한 실측

P004의 같은 Windows PC·Node 24.22.3 비교는 4→8→8→4 순서로 각각 두 번 수행했다. 모두 970건 중 961통과·실패0·기존 skip9였고, 중앙값은 4가 697.559초, 8이 645.735초였다. 사전 5% 속도 규칙으로는 8이 후보였다. 그러나 별도 무override 기본값 8의 첫 전체 실행은 내부 healer popup이 done 대신 step-failed여서 종료1·실패1로 중단됐다. 후속 좁은 관측 1건과 원래 19파일의 181건은 통과했지만 원인은 확인되지 않았다.

안정성 우선이라는 main 판단으로 8을 현재 후보에서 제외하고, TASK 재검토 뒤 기본값 4를 새 연속 다섯 회 검증했다. 이전 비교 표본을 새 묶음에 합치지 않았고, 다섯 회 모두 970건·961통과·실패/취소0·동일 skip9였다. 중앙값 680.918초, 범위 680.448~685.689초이며 기존 범위와 skip 사유를 원본으로 재검증했다. 이 관측은 4가 원인 미확정 오류를 고쳤다는 주장이나 앞으로의 무실패 보장이 아니다. 같은 후보에서 실패를 재시도로 교체해 성공만 고르지 않는다.

## 병렬 측정의 해석 경계

T01 기준선 중앙값 1425.464초 대비 T03 새 기본값 4 묶음은 47.768%다. Git 준비 재사용·중첩 격리·runner 변경을 합친 누적 관측이며 변경별 단독 기여도는 아니다. 단계 이후 변경을 포함하는 최종 목표 판정과 구별한다. 같은 실행의 파일 내부 시간을 합해 벽시계와 빼거나 중첩 시간을 다시 더하면 병렬 실행을 중복 계산한다. 파일별 보조 프로파일은 병목 순위 관측으로 쓰며 정상 성능 중앙값에 섞지 않는다.

시험 파일 목록/SHA, runner/helper/측정 도구, commit, 실제 npm 호출과 환경을 함께 남긴다. 시작·종료 소스 대조는 중간 변경과 복원을 계속 감시하는 장치가 아니다. 호스트 작업 부하 전체를 통제했다고 주장하지 않는다. 원본 증거는 프로젝트 evidence에 한정한 Git text 변환 해제로 byte를 보존하고, 같은 이름 시험은 다중집합과 보조 파일 식별자를 함께 대조한다. 성능·실패 표본 해석은 [[프로젝트-지표-해석과-세션-기록-함정]]과 연결된다.
