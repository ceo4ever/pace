# T02 변경 계획 재검토 — 중첩 playbook 선행 수정

## 판정
- **결과: pass (조건부)**
- **blocking: 0**
- **should_fix: 4**

제안한 두 변경은 guard 소스, 19개 파일 목록, 건수·skip 단언, 동시성을 건드리지 않습니다.
1. 중첩 argv에 `--import helpers.ts`를 추가한다.
2. 실패 메시지에 출력 전체를 담는다.

따라서 실제 시험별 단언과 skip 정책을 약화하지 않습니다. 다만 수정이 의도대로 동작하는지 가리는 검증 한 가지(SF-1)와 새로 생기는 실패 경로의 관측(SF-2)이 계획에 빠져 있습니다. 둘 다 S-8을 보강하면 되는 수준이라 막힘으로 보지 않았습니다.

## should_fix

**SF-1. 각 중첩 파일 프로세스가 고유 루트를 받는지 검증하지 않음 (가장 중요)**
- 참조: TASK의 「사용자 승인 선행 범위」 둘째 문단, S-8, `diagnose-guard.ts`의 argv, `helpers.ts` 시작부의 상속 검증 블록.
- 문제:
  - `--import`를 `node --test`의 runner 부모에 주면 helpers는 우선 **runner 부모**에서 실행됩니다. 부모는 자기 tempRoot를 만들고 TMP·OWNER·PARENT를 설정합니다.
  - 파일별 자식이 고유 루트를 받으려면 자식 프로세스도 execArgv의 `--import`를 받아 helpers를 다시 실행해야 합니다. 그래야 상속 검증을 통과해 형제 `pace-test-run-*`를 만듭니다.
  - 자식에게 `--import`가 전달되지 않으면 19개 자식이 모두 **부모 루트 하나를 공용 TMP로 공유**합니다. 그러면 nested 파일 사이의 간섭이 그대로 남습니다.
  - 현재 isolated 진단은 파일 1개, 공용 루트 주입 구조입니다. 위 두 경우 모두에서 통과하므로 둘을 구별하지 못합니다. `trace.guardTmp`가 공용 루트와 다르다는 사실만 보여 줍니다.
  - S-5나 S-8이 한 번 성공해도 확률적 성공과 구별되지 않습니다.
- 조치: S-8에 다음 확인을 추가하십시오.
  - 실제 19개 실행에서 파일별 자식의 `tmpdir()`가 **서로 다르고**, runner 부모 루트와도 다름을 확인합니다. 예: 진단 preload로 각 자식의 pid·tmpdir를 기록하거나, 실행 중 생성된 형제 루트 수를 셉니다.
  - 또는 2개 이상 파일로 peer 진단을 돌려, 다른 nested 파일이 만든 폴더가 guard 목록에 보이지 않음을 확인합니다.

**SF-2. helpers의 exit 정리가 중첩 .mjs에 새 실패 경로를 추가함**
- 참조: `helpers.ts`의 `process.once("exit")` 블록, S-8.
- 문제:
  - 지금까지 .mjs 파일에는 종료 시 정리가 없었습니다. preload 후에는 각 자식이 종료할 때 자기 루트를 `rmSync`로 지우고, 실패하면 `exitCode=1`과 throw로 끝납니다.
  - Windows에서 손자 프로세스나 열린 핸들 때문에 EBUSY·EPERM이 나면, 이전에 통과하던 파일이 **실패로 바뀔 수 있습니다**. fail-closed라 결과를 숨기지는 않지만, 수정의 부작용이 새 불안정으로 보일 수 있습니다.
  - helpers를 쓰지 않고 spawn한 손자는 `activeChildren`으로 추적되지 않습니다. 이들은 부모 파일의 루트를 TMP로 씁니다.
  - preload는 `PACE_HOME`을 파일별 기본값으로 바꾸고 `PACE_PROFILE`을 삭제합니다. .mjs 시험의 환경이 바뀝니다.
- 조치:
  - S-8의 기대 결과에 "정리 실패나 루트 보존 메시지 0, 실행 뒤 실행 소유 TMP에 남은 `pace-test-run-*` 0"을 넣으십시오.
  - 19개 파일 중 `PACE_HOME`·`PACE_PROFILE`·`tmpdir()`에 의존하는 곳이 없음을 확인해 기록하십시오. grep 수준이면 됩니다.
  - 정리 실패가 관측되면 flake로 넘기지 말고 원문을 보존한 뒤 판단을 올리십시오.

**SF-3. 실패 출력 처리 보강**
- 참조: `playbook-maker.test.ts`의 `spawnSync` 호출과 `assert.equal(result.status, 0, ...)`.
- 문제:
  - `spawnSync`의 기본 `maxBuffer`는 1 MiB입니다. 출력이 이를 넘으면 ENOBUFS로 자식이 종료되고 `status`가 null이 됩니다. "출력 전체 보존"이 이 상황에서는 깨집니다.
  - 지금 메시지에는 `result.error`와 `signal`이 빠져 있어, 이런 종료나 시간 초과의 원인을 구별할 수 없습니다.
  - 출력 전체가 증거 로그에 들어가면 다른 위험도 생깁니다. 실패한 diff에 guard 시험의 합성 주민번호 형태(`RRN`)가 찍히면 비밀 검사에 걸릴 수 있습니다. 해당 시험은 이를 피하려고 값을 분할해 두었습니다.
- 조치:
  - `maxBuffer`를 명시적으로 크게 잡으십시오.
  - 메시지에 `status`, `signal`, `error?.message`, stdout·stderr 전체를 포함하십시오.
  - 증거 로그 비밀 검사에서 합성 값이 검출되면 처리 절차를 TASK에 한 줄 적어 두십시오.

**SF-4. 기준 문서의 정합성**
- 참조: TASK의 「재료」 마지막 항목, 기준표, S-6~S-8의 "검증 기준" 열, 문서 머리 주석("기준을 바꿀 때만 고친다(PROJECT.md 결정 메모에 이유)").
- 문제:
  - 「재료」에는 아직 "T03에서 해결한다. T02는 그 시험/skip/실행 동시성을 바꾸지 않는다"라고 적혀 있어 새 절과 모순됩니다.
  - S-6~S-8은 Git fixture 기준인 T-2에 매달려 있습니다. 중첩 수정의 합격 조건(격리, 단언 비약화, 출력 보존)이 독립 기준으로 존재하지 않습니다.
- 조치:
  - 기준 T-4를 추가하고 S-6~S-8을 T-4에 연결하십시오. T-4는 다음을 담습니다.
    - 중첩 파일별 TMP 격리
    - 원래 누수 단언과 skip·건수 보존
    - 실패 출력 전체 보존
  - 「재료」의 해당 항목을 승인 내용에 맞게 고치십시오.
  - PROJECT.md 결정 메모에 2026-11-18 승인과 이관 범위를 기록하십시오. T03 표의 해당 부분도 조정합니다.

## 문제 삼지 않은 항목
- **동시성:** 중첩 runner의 기본 병렬도는 그대로입니다. 동시성 4·8 비교와 전체 5회 검증은 T03에 남아 있어 승인 범위와 맞습니다.
- **진단 도구의 범위:** `fs.readdirSync` 패치는 진단 전용이며 실제 argv에는 들어가지 않습니다. `diagnose-guard.ts`는 TEMP·PACE_HOME을 자체 `mkdtemp`로 격리하고, 상속 변수를 지운 뒤 30초 timeout으로 실행합니다. 범위가 제한되어 있습니다.
- **진단 폴더 공개:** OS TMP에 남긴 `pace-p004-guard-*` 증거 폴더는 이미 공개되어 있습니다. 마감 때 위치와 정리 여부만 기록하면 됩니다.
- **성능 분리:** 이 진단을 성능 측정에서 분리한 것은 적절합니다.
- **기존 판정 유지:** 원래 Git fixture 범위에 대한 이전 판정(pass, should_fix 4)과 이력은 그대로 유효합니다.

## 목표 정합성

- S-5 종료 0을 유지하는 데 필요한 최소 범위로 보입니다. 단언, skip, 실행 시험 수, 제품 동작은 바뀌지 않습니다.
