# T02 사전 검토 — 1단계 (읽기 전용, 도구 미사용)

## 검토자 정보
- **제공자/모델:** Anthropic, Claude Opus 5.5
- **자동 첨부 문맥:**
  - 사용자 계정 식별 정보 1건(이메일). 검토에는 쓰지 않았습니다.
  - 실행 환경 정보: Windows 11, PowerShell, 임시 작업 디렉터리, 비 Git 디렉터리.
  - 파일 기반 메모리 디렉터리 안내.
- 지시에 따라 파일, 메모리, 외부 도구는 사용하지 않았습니다. 이 검토의 근거는 제공된 TASK 문서뿐입니다.

## 1. 방향과 목표의 정합성
**대체로 정합합니다.**
- 상위 목표는 다음 셋입니다.
  - 반복되는 Windows Git 준비 비용을 줄인다.
  - 공유 가변 상태를 만들지 않는다.
  - 실제 Git 준비를 검증하는 시험은 보존한다.
- 계획은 이 셋에 각각 대응합니다.
  - 원본은 프로세스별로 한 번 준비하고, 호출마다 독립 복사본을 준다.
  - clone, hardlink, shared object를 배제한다.
  - init/commit을 검증하는 경로와 dashboard-init 등은 제외한다.
- project-harness(540초)는 단일 파일 중 가장 긴 것으로 보입니다. 파일 단위 병렬 실행에서 임계 경로일 가능성이 높으므로, 이 파일을 대상으로 고른 것은 타당합니다.
- 측정 해석을 단회 관측과 후속 3회 중앙값으로 나눈 점도 적절합니다.

## 2. 실현 가능성 (결과 예측과 구분)
**구현 자체는 가능해 보입니다.** 다만 다음은 아직 근거가 없는 미래의 결과이며, 실현 가능성과 섞으면 안 됩니다.
- 실제 시간 절감 폭은 미지수입니다.
- Windows에서는 cpSync로 `.git`을 복사하는 비용도 작지 않습니다. 작은 파일이 많고, Defender 검사가 붙기 때문입니다. 특히 기본 템플릿의 hooks 샘플 약 10여 개가 매번 복사됩니다.
- 따라서 "프로세스 6회 기동"을 "파일 수십 개 복사"로 바꾸는 것이 실제로 이득인지는 S-4 이전에는 알 수 없습니다.
- 착수 전에 **상한 추정**이 필요합니다. 호출당 준비 시간 × 실제 호출 횟수를 구하면 540초 중 준비가 차지하는 비율이 나옵니다. 문서도 "루프 횟수와 다름"을 인정하고 있으니, 실제 실행 횟수를 세야 합니다.
- 이 비율이 작으면 목표 기여도도 작습니다. 그 경우 T02의 우선순위나 기대치를 조정해야 합니다.

## 3. 주요 위험

### (1) 커밋 동일성 변화 — 검증 보존에 가장 큰 위험
- 지금은 fixture마다 다른 시각에 커밋하므로 SHA와 커밋 시각이 서로 다를 수 있습니다.
- 전환 후에는 모든 복사본이 **같은 SHA와 같은 커밋 시각**을 가지며, 그 시각은 시험 시작보다 이를 수 있습니다.
- 다음 경우에는 판정이 조용히 바뀔 수 있습니다.
  - 시험이나 CLI가 HEAD SHA를 고유 키, 캐시 키, 상태 식별자로 쓰는 경우
  - 여러 fixture 간 차이를 전제하는 경우
  - 시각 순서를 비교하는 경우
- 필요한 근거: 66개 호출 위치와 CLI 쪽에서 SHA, 커밋 시각, 로그를 쓰는 곳의 감사 결과.

### (2) config 3회의 범위
- 3회의 config 호출이 repo-local인지 `--global`(private HOME)인지 문서에 나와 있지 않습니다.
- global이라면 복사본에는 그 설정이 따라오지 않습니다. 이후 commit을 하는 시험이 다르게 동작할 수 있습니다.
- local이라면 복사로 보존되므로 문제없습니다.
- 필요한 근거: 현재 repoFixture의 config 대상.

### (3) HOME/bin 문맥 등록 설계의 모호성
- "첫 대상의 private HOME/pace bin 문맥을 원본의 정확한 경로에만 등록"이라는 문장이 다음 두 가지를 분명히 하지 않습니다.
  - 원본 준비에 쓰인 HOME이 무엇인지
  - 두 번째 이후 복사본이 각자의 HOME/bin을 어떻게 받는지
- 첫 호출이 원본 준비와 대상 생성을 함께 하면서 문맥이 섞일 여지가 있습니다.
- 경로를 키로 쓰는 조회 구조라면 Windows 경로 정규화 차이가 오매칭의 원인이 됩니다. 단축 이름(`ROOT-U~1`), 대소문자, 구분자가 그 예입니다.
- 필요한 근거: 다음을 보여 주는 의사 코드나 순서도.
  - 문맥 등록 시점
  - 조회 키
  - 정규화 방식

### (4) 형태 키(cache key)
- "동일 형태"를 무엇으로 판정하는지 명시되어 있지 않습니다. repoFixture가 인자에 따라 파일 구성이 달라진다면, 키가 그 인자를 모두 포함해야 합니다.
- 키가 충돌하면 다른 형태의 원본을 받게 되며, 이는 조용한 오류입니다.
- 권장: callback 식별만으로 키를 정하지 말고, 명시적인 형태 키를 쓰거나 형태마다 별도 인스턴스를 만드십시오.

### (5) 파일 내 동시성
- 지연 생성이 async이고 같은 파일 안의 시험이 concurrency 옵션으로 동시에 돌면 이중 준비나 반쯤 준비된 원본 읽기가 생길 수 있습니다.
- 해결책은 둘 중 하나입니다.
  - Promise를 메모이즈하고, 실패 시 메모를 해제한다.
  - 동기 구현임을 명시한다.
- S-2는 실패 후 재시도만 다루고, 동시 요청은 다루지 않습니다.

### (6) 원본 무결성 감시 부재
- "읽기 전용으로 취급"은 강제되지 않는 약속입니다.
- prepare가 원본 경로를 받으므로 문맥 등록 등에서 원본을 실수로 변경할 수 있습니다.
- 권장: 시험 모드에서 원본의 트리와 해시 스냅샷을 비교하거나, 최소한 S-1에 "다른 형태와 다른 호출 후에도 원본 불변" 단언을 넣으십시오.
- 실제 read-only 속성을 부여하는 방식은 Windows에서 정리 실패(EPERM) 위험이 있으므로 피하는 편이 맞습니다.

### (7) index stat 정보
- 복사 후에는 mtime, dev, ino가 달라집니다. 첫 `git status`/`diff`에서 index를 다시 계산하고 다시 쓸 수 있습니다.
- 판정은 Git이 보정하므로 대체로 안전합니다.
- 다만 다음 시험에는 영향이 있을 수 있습니다.
  - index 파일 불변이나 mtime을 단언하는 시험
  - racy-git 경계에 민감한 시험
- 감사 항목에 포함하는 것을 권장합니다.

### (8) 자기완결성 검사의 범위
- 현재 거부 목록은 symlink, worktree `.git` 파일, alternates, 절대 경로 worktree/hooks입니다.
- 다음도 점검 대상에 넣을 만합니다.
  - `core.worktree`
  - `core.hooksPath`
  - `include.path`
  - `core.fsmonitor`/untracked cache 관련 설정
- 템플릿을 비우면(`--template=` 등) 복사 파일 수가 줄어 비용과 위험이 함께 줄어듭니다. 단, 이는 init 형태를 바꾸는 일입니다. 기존 시험이 hooks 디렉터리 존재 등을 전제하지 않는지 확인이 필요합니다.

### (9) T03 가설과의 간섭
- 원본 디렉터리는 기존 프로세스별 tempRoot 안에 있어야 합니다. 공용 TMP 최상위에 새로 만들면 중첩 playbook guard의 TMP 전후 비교에 새 항목으로 잡힐 수 있습니다.
- 문서에 "기존 helper 정리 범위 안"이라고 되어 있으나, **TMP 최상위에 새 항목을 만들지 않는다**는 점을 명시적인 기준으로 두는 편이 좋습니다.

### (10) 시험 수 변화의 해석
- 새 git-fixture 시험이 추가되면 963건과 직접 비교할 수 없게 됩니다.
- T-3에 차이 설명이 이미 있으나, 인벤토리를 대조하는 절차(이름 집합 diff)가 S-5에 구체적으로 적혀 있지 않습니다.

## 4. 빠진 근거 요약
| 항목 | 필요한 이유 |
|---|---|
| repoFixture/repo 실제 실행 횟수와 호출당 준비 시간 | 기대 효과의 상한(목표 기여도) |
| 66개 위치 중 init/commit/SHA/시각/index에 의존하는 시험 목록 | "검증 보존" 주장의 근거 |
| config 3회의 범위(local/global) | 복사본 동등성 |
| HOME/bin 문맥 등록·조회 의사 코드와 경로 정규화 | 문맥 오매칭 방지 |
| 형태 키 정의, 동기/비동기 여부와 파일 내 concurrency 사용 여부 | 캐시 정확성 |
| Windows에서 cpSync `.git` 복사 비용 사전 견본 | 방향의 경제성(S-4 이전 위험 신호) |

## 5. 1단계 소견
- 방향은 목표와 맞고, 설계 원칙도 올바릅니다. 독립 복사, 실패를 캐시하지 않음, 검증 경로 제외, 과대 주장 금지가 그 원칙입니다.
- 실현 가능성은 있다고 봅니다. 다만 **효과 크기**와 **검증 보존**은 아직 증명되지 않았습니다. 특히 위험 (1)~(4)는 조용한 판정 변화로 이어질 수 있어 착수 전에 보강하는 것을 권장합니다.
- 최종 계획 판정(gate)은 지시에 따라 2단계로 미룹니다.
