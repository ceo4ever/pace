# T02 사후 코드 리뷰 (1단계, 독립 검토, 도구·편집 미사용)

**검토자 정보:** Claude Opus 계열 모델입니다. 자동으로 붙은 문맥은 세 종류입니다.
- 사용자 계정 정보: 검토에 사용하지 않았습니다.
- 실행 환경 정보: 플랫폼, 작업 디렉터리, 날짜.
- 영속 메모리 설정: 읽기 전용 검토라 기록하지 않았습니다.

계획·계약 문서는 받지 않았으므로 아래 판단은 diff와 증거 파일만 근거로 합니다.

---

## 1. 결론 요약

- **범위 증명:** helper가 실제 Git 저장소를 준비하고 독립 복사본을 돌려주며, 원본과 복사본이 분리된다는 점은 신규 테스트 5건이 통과해 입증했습니다. 범위 증명은 대체로 성립합니다.
- **워크플로 승인:** 전체 검사가 **실패했습니다**. 결과는 968건 중 pass 958, **fail 1**, skip 9이고 `fullCheckSatisfied: false`입니다. 따라서 승인 조건은 충족되지 않았습니다. 범위 증명과 승인은 별개로 다뤄야 합니다.
- **실패 내용:** `playbook-maker .mjs 테스트가 실제로 실행되고 모두 통과한다`가 pass에서 fail로 바뀌었습니다. 중첩 실행 결과는 181건 중 1건 실패입니다. wrapper가 출력 끝부분만 보존하기 때문에 **어느 내부 테스트가 실패했는지, 원인이 무엇인지는 확정할 수 없습니다.** 이번 diff 때문인지, 일시적 실패인지, 환경 문제인지 추정하지 않겠습니다.

## 2. 달성된 결과 (관측)

- **준비 단위 성능:** 직접 준비는 중앙값 약 333ms, 캐시 사용 시 약 24.7ms입니다. 첫 호출(cold)은 404ms로 직접 준비보다 느립니다. 교대 순서로 10회씩 측정했고, 콜백 실행 횟수는 10회에서 1회로, Git 호출은 60회에서 6회로 줄었습니다.
- **격리 검증:** 한 복사본에서 작업 파일, config, index, ref, object를 변경하거나 손상시켜도 다른 복사본과 원본은 영향을 받지 않았습니다. 원본 digest도 변하지 않았습니다.
- **실패 처리:** 준비 실패나 최초 복사 실패가 캐시되지 않고, 다음 호출에서 정상적으로 다시 준비됩니다.
- **거부 경로:** 비어 있지 않은 대상, 링크, 소유하지 않은 대상, gitfile, alternates, 커밋이 없는 원본을 거부합니다.
- **project-harness:** 원본 전용 HOME과 복사본별 HOME이 분리되어 `--global` config가 섞이지 않습니다.
- **목록 비교:** 기존 963건이 그대로 있고 5건이 추가되었으며, skip 목록도 같습니다.

## 3. 입증되지 않은 가정

1. **전체 시간 단축은 아직 근거가 약합니다.** 1,390s는 기준 1,424~1,442s보다 약 2.4~3.6% 짧지만, 1회 측정이고 실패가 포함된 실행입니다. 효과 크기는 `repo()`/`repoFixture()` 호출 수에 약 300ms를 곱한 값으로 추정되는데, 이 호출 수는 측정되지 않았습니다.
2. **벤치마크 fixture가 실제 fixture와 다릅니다.** agent-chain은 `-b main`도, config도 없습니다. 측정 결과의 `limits` 항목도 이를 명시합니다.
3. **모든 복사본이 같은 commit SHA와 커밋 시각을 공유합니다.** 이전에는 저장소마다 SHA가 달랐습니다. 저장소 간 SHA 차이나 "테스트 시작 이후 커밋"에 의존하는 기존 테스트가 없다는 점은 전체 통과로만 간접 확인할 수 있는데, 이번 실행은 실패했습니다.
4. **복사본의 index stat가 실제 파일과 다릅니다.** `cpSync`는 기본적으로 타임스탬프를 보존하지 않으므로, 처음 `status`를 실행할 때 재해시와 index 재기록이 일어납니다. 의미상 문제는 없어 보이지만 index mtime이나 inode에 의존하는 테스트에는 영향이 있을 수 있습니다.
5. **경로 판정은 `tempRoot`가 이미 realpath로 정규화되어 있다는 전제에 기대고 있습니다.** Windows 8.3 짧은 이름(`ROOT-U~1`)과 `realpathSync.native` 결과가 비교되기 때문입니다. 관련 테스트는 통과했으므로 현재 환경에서는 성립합니다.

## 4. 함정 및 계층별 공백

| 계층 | 내용 |
|---|---|
| **검증/워크플로** | 전체 검사 1건 실패. 재실행과 중첩 로그 전체 보존이 필요합니다. 승인 전에는 차단 요소입니다. |
| **증거 수집(wrapper)** | 출력을 stdout 2000자, stderr 500자로 잘라 내부 실패를 식별할 수 없습니다. T02 코드가 아니라 하네스의 관측성 문제입니다. |
| **테스트 선택 맵** | `git-fixture` unit의 sources는 `test/helpers.ts`, tests는 자기 테스트뿐입니다. `helpers.ts`를 바꿨을 때 agent-chain이나 project-harness가 선택 실행에 포함되는지는 다른 unit 정의에 달려 있는데, 확인되지 않았습니다. |
| **신규 테스트 이식성** | `process.env.PACE_TEST_TMP_PARENT!`가 없으면 `undefined`가 전달되어 TypeError가 나고, `/empty owned/` 단언이 실패합니다. node-test runner로 단독 실행할 때 이 환경변수가 설정되는지는 입증되지 않았습니다. |
| **helper 설계** | ① 콜백에 `firstDestination`을 넘겨 오용 여지가 있습니다. 사후 `checkDestination`이 막아 주긴 합니다. ② 실패한 candidate나 일부만 복사된 대상을 정리하지 않습니다. tempRoot 정리에 의존합니다. ③ 실패한 원본의 `fixtureContexts` 항목이 남습니다. ④ 자기완결 검사가 `commondir`과 `http-alternates`를 확인하지 않습니다. ⑤ HEAD 검사 timeout 5s는 Windows 백신 환경에서 불안정해질 수 있습니다. |
| **비용 배치** | 처음 호출하는 테스트가 cold 비용(약 400ms 이상)을 떠안습니다. timeout이 빡빡한 테스트라면 위험합니다. |
| **사소** | 주석 "파일 프로세스/형태별" 문구가 어색합니다. |

## 5. 권고 (1단계 기준)

1. 중첩 출력을 전체 보존하도록 한 뒤 전체 검사를 재실행해 실패 테스트를 특정해야 합니다. 그전에는 승인을 보류하는 것이 맞습니다.
2. 실패를 특정한 다음에 이번 diff와 관련이 있는지 판정해야 합니다. 판정 순서는 이렇습니다.
   - playbook-maker가 `helpers.ts`나 바뀐 fixture에 의존하는지 확인합니다.
   - 기준 커밋에서도 재현되는지 확인합니다.
3. 전체 시간 효과를 주장하려면 실제 호출 수를 세고, 통과한 실행을 여러 번 비교해야 합니다.
4. test-map에서 `helpers.ts` 변경 시 소비 테스트가 함께 선택되는지 확인하고, 신규 테스트의 환경변수 의존도 점검해야 합니다.
