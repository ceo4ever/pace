# 팀 측정과 회고

적용: `src/project/team-*.ts`와 팀 지표를 호출하는 stats·finish. 소통 원장은 [HANDOFF](HANDOFF.md), 원본과 실행 경계는 [TEAM](TEAM.md)을 따른다.

실패만 남은 owner 전달 요청은 도달 관측 0과 별개로 해결되지 않은 결과다. `failed_only_owner_requests`의 총량은 수집 범위가 닫히고 요청 결과가 확인됐을 때 표시한다. 모호한 결과가 있으면 관측된 실패 시도와 분류를 남기고 총량을 미확인으로 둔다. 비교는 양쪽에서 실패만 남은 요청이 0으로 확인될 때 부담 방향을 판정한다. 실패 시도 뒤 성공한 요청은 failed-only가 아니다. 답변 영수증의 선택 period는 응답 시각을 포함하고 측정 단위와 같아야 하며, decisionReplyId가 있으면 실제 owner의 같은 요청 응답 ID·구간·선후 시각과 대조한다. 응답 근거의 좁은 기간과 전체 수집 범위의 동일 기간 확인은 별개다.

팀 프로젝트의 worktree finish는 `TEAM-FINISH.json`에 최종 Git tree(영수증 자신 제외), 마감 전 부모 커밋, 전체 검사 상태를 기록한다. 검사가 선언되어 통과하면 checkStatus는 passed, 선언이 없어 실행하지 않았으면 not-run이다. 병합 미리보기는 통과·미실행·이전 기록 없음을 구별한다. rebase/검사 뒤 팀·회고 자료가 바뀌면 커밋 후 finish를 다시 실행한다. 팀 merge는 worktree 유무와 관계없이 대상 커밋의 영수증·트리·단일 부모를 대조하고 승인한 SHA를 병합한다. 이후 같은 트리의 빈 커밋이 생겼거나 과거 영수증에 부모가 없으면 worktree에서 다시 마감한다. 미채택 프로젝트도 확인한 커밋의 SHA로 fast-forward한다. 병합 사이 추가로 진행된 브랜치와 작업 폴더는 보존한다. fast-forward 전에 PACE가 남긴 거부 로그만 추가된 경우에는 같은 승인 커밋으로 재시도할 수 있다. 해당 로그가 남은 작업 폴더는 보존하고, 다른 미커밋 변경이 있으면 병합을 보류한다. finish 뒤 회고 삭제나 후속 내용 수정은 재마감을 요구한다. 실제 인덱스 대신 임시 인덱스로 자기 파일을 제외하며 기존 다른 소유자의 파일을 덮어쓰지 않는다. 같은 계정의 의도적 영수증 위조를 막는 인증 장치는 아니다. 팀 없는 옛 프로젝트에는 소급하지 않는다.

최종 회고·측정 JSON에서 사용한 메타데이터 영수증, 사건·소통 원장, 팀 정의는 사전 검토 커밋의 일반 Git 파일이어야 하며 검증한 작업 파일과 같아야 한다(CRLF/LF 차이 허용). 무시된 입력이 증명에 필요하면 기록할 자료를 먼저 확인한다. 검사 명령이 HEAD를 바꾸거나 staged/unstaged 변경을 만들면 검토·커밋 후 재마감을 요구한다. 기존 다른 용도의 finish 파일이 있으면 마감 전에 충돌을 알린다. 팀 미리보기를 확인한 뒤 `pace project merge P### --yes --commit <미리보기의 전체 SHA>`로 승인 대상을 명시한다. 새 finish는 새 SHA로 다시 확인한다. 소유 worktree가 없고 FF 전인 merge 거부는 main 정본을 보존하고 호출자에게 오류를 반환한다. FF 뒤 상태 기록 실패의 복구 로그는 기존처럼 남긴다.

팀 finish에 앞서 PM이 검토한 변경과 회고·영수증을 직접 골라 커밋한다. staged, unstaged 또는 미추적 변경이 있으면 마감이 보류되며 인덱스·HEAD·기존 로그·작업 파일을 보존한다. 검사를 통과하면 하네스는 자신이 생성한 상태·지표·소통 기록·마감 영수증과 적용되는 생성 출력만 최종 마감 커밋에 담는다. 미채택 프로젝트는 기존 목차 갱신과 마감 절차를 사용한다.

팀 마감과 병합의 기록 커밋은 `git rev-parse --path-format=absolute`와 `git hook run --ignore-missing`을 지원하는 Git에서 확인했다. P009의 전체 회귀는 Git 2.55.0에서 실행했다. 구형 Git과 `commit.template`의 동작 차이는 미확인이다.

팀 채택과 Git 이력은 프로젝트 번호를 기준으로 작업 브랜치와 기준 브랜치에서 확인한다. 기준에만 채택 이력이 있거나 필요한 팀 입력이 사라졌으면 해당 근거를 확인할 때까지 진행을 보류한다.

팀 마감은 시작 시 확인한 기준 SHA로 rebase한 뒤 그 후보에서 태스크, 백로그, 마감 문서, 정본과 보안 요건을 검사한다. 완료 태스크의 계약·마감 문서를 후보에서 읽고, 마감 문서의 `evidence/` 링크가 후보에 있는 일반 파일이나 Git 디렉터리를 가리키는지 확인한다. 사전 검토 기록과 각 시도·예외의 증거도 같은 후보의 비어 있지 않은 일반 파일이어야 한다. 같은 저장소의 모든 worktree에서 등록한 원문 보호 경로를 후보 tree 및 기준 SHA에서 새로 편입되는 중간 커밋에 대조한다. 내용이나 실행 비트가 바뀌어도 같은 보호 경로를 검사한다. 등록된 공개 Git 내용과 일치하는 파일을 허용하며, 과거 공개 기록은 CRLF와 LF를 대조한다. 팀 병합은 현재 보호 목록을 다시 확인한 승인 SHA에 fast-forward하고, 이후 기록 커밋에는 하네스의 출력 경로만 포함한다. 병합 훅이나 동시 작업이 다른 변경을 만들면 그 변경을 보존하고 상태 기록은 실패로 보고한다.

팀 finish는 측정 설정, 로그의 사용자 답·원장 거울 및 팀 회고에 연결된 영수증의 허용 키와 메타데이터 형식을 검증한다. 있는 영수증에 원문 필드가 섞였거나 안전성을 확인할 수 없으면 마감을 보류한다. 실제 파일이 사라진 과거 로그 참조는 안전한 상대 경로인 경우 부재로 기록한다. 조회 판정에 사용하지 않은 정상 로그 영수증은 Git에 없는 상태도 허용한다.

조회와 마감은 과거 로그의 상대 경로에서 점과 중복 구분자를 정리해 같은 파일을 대조한다. 로그 행 자체는 보존한다. 역슬래시를 경로 구분자로 읽을 때에는 POSIX에서 역슬래시가 이름에 들어간 별도 파일도 마감 전에 확인한다.

조회·마감·병합 및 Git 이력은 해당 프로젝트 번호의 역할 시작 행을 채택 근거로 사용한다. 다른 프로젝트의 행은 기존 기록에 남아 있어도 현재 프로젝트의 채택을 확정하지 않는다.

최종 집계와 회고 검증기가 실제 사용한 자료는 필수 Git 입력이다. 반복 지적 산출에 읽은 TASK-CLOSE도 포함한다. 사용자 답의 ref는 실제 도달 근거로 채택된 경우에만 포함하며 다른 요청이나 기간으로 탈락한 답은 미확인을 유지한다. 팀 보안 검사와 의존성 감사는 전후 파일·인덱스 지문을 대조한다. 실제 FF 성공은 실행 경로의 명시 상태로 확인한다. FF 뒤 복구 중 로그 충돌이면 양쪽 기록을 보존하고 복구 결정을 받은 뒤 재마감하고 새 SHA를 확인한다.

입력 추적은 경로뿐 아니라 판독기가 실제 사용한 UTF-8 내용의 지문을 보존한다. 동일 입력을 다시 읽을 때 내용이 달라지면 보류하고, 최종 스테이징에서 고정한 Git tree의 일반 blob과 대조한다(CRLF/LF 차이만 허용). 검사한 커밋과 최종 인덱스의 전체 트리 차이는 마감이 만든 출력 경로로 제한한다. 그 밖의 staged 변경이 있으면 사용자 인덱스를 보존하고 마감을 보류한다. 마감 커밋 뒤에도 검사한 부모와 입력·트리 결합을 대조하며, 그때 실패하면 생성 커밋을 보존해 재확인을 요구한다. 미채택 프로젝트는 보안 검사의 정상 산출물을 기존 목차 갱신 단계에 포함한다. 보안 검사 뒤 작업본과 새 커밋의 팀 채택, 등록 원문 또는 마감 범위 밖 변경이 발견되면 목차 갱신 전에 보류한다.

Team finish는 기존 src 필드의 `finish:<24자리 hex>`로 시도를 구별한다. 실패 복원은 log.jsonl 본문을 되감지 않고 같은 시도의 실패 gate를 추가한다. 통계의 완료 시각은 같은 프로젝트·태스크·src의 실패로 취소된 성공만 제외하고 Git 메시지 근사로 되살리지 않는다. 다른 시도의 성공·동시에 추가된 행·실제 실패 수와 식별자 없는 과거 기록은 유지한다. 원문 삭제나 새 이벤트 종류/스트림을 만들지 않으며 시도 식별자는 인증 수단이 아니다. 실패 뒤 남은 로그/문서 변경은 검토·커밋하고 재마감한다.

불완전하거나 모순인 리뷰 로그는 Team 회고의 유효한 TASK-CLOSE 관측을 0으로 덮지 않는다. 수치 미확인을 별도 후보로 표시하고 Team 품질은 null을 유지한다. 팀 없는 기존 집계는 기존 의미로 읽는다. 사용자 답은 최초 요청과 직접 참조한 제안 이후여야 팀 도달로 인정한다. 원장 답 또는 이를 인용한 영수증에 명시된 태스크는 직접 참조한 제안의 태스크와 일치해야 한다. 다른 태스크의 중계는 그 중계 제안에 대한 답으로 연결한다. 귀속이 불명확한 답과 별개로 확인된 도달은 관측으로 남긴다. 기존 리뷰의 slash 구분자는 수용하되 분수·소수·중복 수치는 거부한다.

요청 판정기의 같은 원장 snapshot·근원 시각·owner 방향 신호를 측정이 공유하고 비교는 그 결과 snapshot을 소비한다. 전달 terminal은 같은 요청의 prepare 이후여야 한다. 시각 순서가 모순된 신고도 응답 증빙의 재사용 대조에 포함하며 실패 관측은 보존한다. 다른 요청의 상태 메시지 등도 같은 외부 응답을 신고했으면 중복 대조에 포함한다. 요청 ID가 생략돼도 원장이 확인한 상태·범위 확인·결과·종결의 data.re와 입력·승인 위임의 근거에서 요청을 찾는다. 명시 ID와 참조가 다르면 두 요청 연결을 유지하고 귀속 미확인으로 표시한다. 기간 경계와 응답 재사용도 같은 연결을 사용한다. 이 연결을 코디네이터 자체 답을 확인할 때에도 사용하므로 연결된 사용자 전달 시도가 있으면 미해결을 상쇄하지 않는다. stats snapshot의 deliveryClaims에는 전송 성공 행마다 요청과 응답 식별 지문, 도달에 쓰인 여부, 여러 요청에 걸친 귀속 미확인 여부를 한 번만 남긴다. 여러 요청에 걸친 응답은 독립 도달을 확정하지 못하며 중복 대조에 쓰인다. 비교는 같은 저장소의 제공된 표본 전체에서 지문을 대조한다. 수집 미확인이나 목록 일부 손상 때에도 구조가 유효한 신고는 중복 대조에 남긴다. 해당 신고를 자기 표본의 도달 근거로 확정하려면 요청 수집 확인이 필요하다. 다른 요청과 겹친 증빙 외에 도달에 쓸 증빙이 없는 표본은 도달 총량, 실패만 남은 요청의 총량, 비교 방향을 보류하고 관측은 보존한다. 소통 종류별 발생 수는 구간 내 행을 세며 열린 위임은 구간 끝까지의 위임·종결 기록에서 계산한다. 채택 여부는 `team-contract.ts`의 동일한 필드/사건 판정으로 작업 파일과 Git 대상을 읽는다. Snapshot은 파일 내용·선택 입력의 부재·역할과 실제 TASK-CLOSE 목록까지 대조해 검증 뒤 추가된 미검증 입력을 봉인하지 않는다. 영수증의 반복 의미 판독과 비교 묶음의 원본 지문도 같은 read snapshot을 사용한다. 원문 로컬 보존·수신 의도/도달·수집 누락/null·failed-only·확인된 자체 응답의 구별은 유지한다.

회고 셀의 inline 링크는 목적지와 선택 제목의 문법까지 대조한다. 목적지 뒤의 제목은 공백으로 구분한 큰따옴표·작은따옴표·괄호 형식이어야 한다. 잘못된 HTML 말미를 제목으로 숨기지 않는다. 정의 수정의 역할은 원본 또는 참여 기록에 존재해야 하며, 변경/이유 영수증의 실제 제안 의미는 사람이 검토한다.

## 집계

| 판정 | 확인하는 내용 | 근거가 부족할 때 |
|---|---|---|
| 요청 도달 총량 | 닫힌 구간, 별도 확인자의 수집 범위, 같은 입력 지문과 해결된 요청 | 확인된 도달과 실패 관측을 유지하고 총량은 미확인 |
| 손작업·승인·품질 총량 | 같은 구간의 완전한 수집과 별도 확인 증거 | 확인된 관측값만 표시 |
| 역할별 활동 | 같은 역할에 결합된 동일 구간의 실행·활동 근거 | 미확인으로 표시하고 회고에서 사용 여부 확인 |
| 비교 방향 | 같은 조건, 전후 각 2건 이상, 확정된 중요 총량과 안정된 품질 | 미확인 이유와 추가 표본 계획을 표시 |

`pace project stats P### --json`의 선택 `team`과 텍스트·METRICS의 팀 절은 역할 시작/참여 소통/to/requestId/명시 입력이 있는 프로젝트만 사용한다. 없는 옛 프로젝트의 사건·FIFO 대기·출력 형태는 유지한다. 미채택 프로젝트에서 선택 역할 원본을 읽지 못하면 역할 관측의 한계를 표시하고 기존 사건·대기·소통 기본 집계를 반환한다. 역할 start는 PROJECT 머리 열0 최상위 필드 `- 팀 측정: v1`과 start data의 `teamMetricsVersion:1`을 남긴다. marker·TEAM-MEASUREMENT.json·버전 start 중 하나라도 있으면 새 회고 계약을 요구한다. marker 하나를 지워도 해제되지 않는다. 코드 fence·주석·본문 예시는 marker로 읽지 않는다. 옛 버전 없는 역할 시작에는 회고를 소급하지 않는다. 이 표지는 이력 조작에 대한 인증 장치가 아니다.

요청은 requestId로 중복 제거하고 사용자 답→실제 사람 경로 성공→실패만→미확인 순으로 분류한다. 원질문이나 원장 제안 없이 남은 사용자·코디네이터 답도 요청 ID가 있으면 미확인 관측으로 남긴다. 뒤늦은 질문은 이미 기록된 답을 인정하지 않는다. 같은 시각이면 같은 사건 로그의 앞선 요청 행을 확인한다. 서로 다른 기록이 같은 시각이면 실제 원장 답의 decisionReplyId와 요청·태스크·시각을 대조해 확인된 연결을 인정한다. 선후를 확인할 연결이 없으면 도달과 자체 답 판정은 미확인이다. 영수증을 읽어도 판정에 쓰이지 않았으면 요청 수집 지문과 마감의 필수 Git 입력에 포함하지 않는다. 원질문에 태스크가 없는 요청은 이후 유효한 답의 근거로 분류한다. 명시 태스크의 질문보다 먼저 기록된 미지정 답은 같은 요청 ID가 있어도 그 업무에 귀속하지 않는다. 뒤따른 유효 답은 관측으로 보존하고 영향을 받는 대표 업무의 총량을 보류한다. 팀 projection의 by:user answer ref는 typed 영수증이고 requestId가 같아야 한다. 옛 handoffs 기본 집계의 비어 있지 않은 ref 규칙과4분류는 호환용으로 유지하므로 팀에서는 근거가 부족한 옛 답이 미확인으로 낮아질 수 있다. 두 집계를 합쳐 쓰지 않는다. 전달 실패는 attemptId별 관측이다. 도달 reached는 관측 하한이며 reachedTotal과 snapshot counts.owner_questions는 닫힌 범위·다른 확인자의 request_coverage·미확인 요청 없음일 때만 신고 총량이다. marker만 있고 기록이 없으면 관측0/총량null이고, 기록을 모두 수집했다는 명시 확인 없이0을 개선 판정에 쓰지 않는다. 실패 뒤 성공은 도달1·실패시도1이다. 수신 의도는 log Q/E와 원장 decision_request를 같은 ID로 중복 제거한다. 질문 사건 수는 기존 log 사건 수다. 수신 의도·질문 사건·식별자 없는 옛 사건·코디네이터 수신/자체 답을 각각 둔다. Orca 코디네이터 영수증은 사용자 도달이 아니다. BR01 원장의 unconfirmed/legacy4분류는 그대로 보존한다. 다만 닫힌 전체 수집범위 안에서 명시 확인된 coordinator_answers는 원장 미확인과 별도 축인 comparisonUnconfirmed에서 제외한다. 그 답이 자체 처리였다는 근거가 없거나 전달 답일 수 있으면 제외하지 않는다. 같은 요청에 by:user 답(ref 누락 포함), to:owner 또는 수신자 없는 질문/에스컬레이션, 사용자 대상 decision_request/중계, 사용자 경로 전달시도(시작/불명 포함) 중 하나라도 있으면 자체 처리 대조에서 제외한다. 열린 범위나 전체 request_coverage 미확인일 때에는 비교 미해결도 줄이지 않는다. 도달 관측 수는 측정 구간으로 한정한다. 자체 처리 신고의 신뢰 대조는 같은 요청 ID의 전체 기록을 보아 구간 밖의 사용자 신호도 있으면 미확인으로 내린다. 나중 답을 과거 구간의 도달 수에 더하지 않지만 독립 처리였다는 결론의 확신은 보수적으로 철회한다. 이 구분으로 코디네이터가 처리한 요청을 사용자 도달로 세지 않으면서 해당 범위의 도달 신고 총량0을 비교할 수 있다. 과거 기준선에 이 확인이 없으면 소급 적용하지 않는다. 질문·승인·손작업 열이 겹칠 수 있어 사용자 개입 총합은 null이다. actor/영수증/complete는 신고이며 사람 인증이 아니다.

역할별 시간·도구별 출력은 명시 역할 결합 관측과 현재 period에 맞는 refs가 있을 때만 reported로 표시한다. 과거 구간 영수증만 있으면 null/이유를 낸다. 역할 원본/start 인자만 있으면 null이고, cwd/구간 토큰은 별도 근사다. 이름 검증에는 전체 역할 이력을 쓰되 현재 측정 구간 밖 start만으로 현재 참여를 선언하지 않는다. 미참여 선언 역할은 unconfirmed 후보이며 자동 삭제하지 않는다. 소통 종류·역할별 빈도는 이름순이며 성적순이 아니다.

## 필수 역할 비참여와 호출 기록

팀 채택 프로젝트에서 [필수 역할 표지](TEAM.md#필수-역할-표지)를 읽는다. 허브 쪽 또는 조건부 역할의 비참여는 stats JSON의 `team.requiredRoleNonParticipation`과 stats 텍스트·마감 `METRICS.md` 팀 절에 별도로 남긴다. 시작 기록·소통 원장으로 참여가 선언됐거나 역할 활동 영수증을 확인했으면 기존 역할 관측을 유지한다. 비참여 분류를 받은 역할은 회고의 필수 `unusedRoles` 후보에서 제외한다. 회고에서 이 분류의 근거를 찾을 때는 같은 구간의 team stats JSON을 본다.

| JSON 상태 | 표시 | 근거 |
|---|---|---|
| `condition-not-triggered` | 호출 조건 미발생 | 해당 역할의 호출 조건이 성립하지 않았다는 측정 구간 영수증 |
| `unconfirmed` | 기록 부족(미확인) | 해당 구간의 유효한 증거가 없거나 조건 미발생과 미사용 신고가 충돌함 |
| `unused` | 실제 미사용 | 해당 역할을 쓸 수 있는 상황에서 호출하지 않았다는 측정 구간 영수증 |

증거는 프로젝트 폴더 안의 기존 v1 `team-evidence` 영수증을 사용한다. `purposes`는 `role-observation`을 포함하고 `period.start/end/unit`은 조회 구간과 일치해야 한다. 출처의 `sourceRef`는 `role-observation:<role>:condition-not-triggered:<locator>` 또는 `role-observation:<role>:none:<locator>`다. 영수증은 같은 구간의 프로젝트 `note`에서 `src: "team-role-nonparticipation"`과 프로젝트 기준 상대 `ref`로 연결한다. 파일 경로는 슬래시로 구분한다. JSON의 각 분류 행은 `{role,status,refs}`로 관측에 쓴 영수증을 남긴다. 신고는 실제 사용 여부의 인증 수단이 아니며 관측 범위가 바뀌면 다시 대조한다.

호출 로그는 프로젝트 사건 로그의 `role`, `to`, `requestId` 및 소통 원장을 채우지 않는 별도 자료로 수집한다. 이 필드는 역할 시작·질문·답과 실제 인계가 있을 때 그 사건에 사용한다. 팀 채택은 기존 `hasTeamContract`로 판정한다. 팀 채택 프로젝트의 호출 집계는 역할 이름으로 기존 관측에 연결하고, 미채택 프로젝트의 호출 데이터는 별도 호출 집계로 낸다. 호출 기록만 있을 때는 팀 `METRICS.md` 절과 팀 회고·마감 요구를 만들지 않는다. 실제 역할·질문·요청 사건이나 소통 원장이 있는 미채택 프로젝트의 기존 팀 요약은 계속 제공한다. 호출 형식과 수집기는 BL261125_01 BR03에서 이 경계를 적용한다.

## 측정 입력

팀 품질의 JSON `snapshot.observed_counts`, stats 텍스트와 METRICS는 같은 구간에 유효한 리뷰와 게이트 행의 수를 관측으로 표시한다. 현재 구간의 품질 감사 영수증으로 뒷받침된 부분 신고도 감사 관측으로 남긴다. 수집이나 행 형식이 불완전하면 확인된 관측만 표시하고 해당 총량을 보류한다. 유효 관측이 없는 부분 수집은 0으로 채우지 않는다.

프로젝트 폴더 `TEAM-MEASUREMENT.json`은 version1, 선택 comparison/period/counts/observed_counts/coverage/request_coverage/log_coverage/quality_audit/role_observations/coordinator_answers를 받는다. UTF-8 일반 파일32KiB 이하, 링크/중복 키/비밀 후보/미지 필드는 거부한다. 배열은32개 이하, 역할 도구 출력은8개 이하이다. JSON null은 미확인, 명시 부분0은 관측0/총량null이다. 수집 없음은 관측도 null이다. 새 팀 사건 로그는 UTF-8·JSONL·중복 키·필드·사건 형식을 엄격 검사한다. 손상/미지원 행은 조회 오류2와 마감 보류이며 자동 삭제/수정하지 않는다. 로그 파일 부재는 미수집 경고와 도달/로그품질 총량null, 명시 빈 파일은 빈 수집이다. review 행에 blocking/should_fix·pass/fail·reviewer/tester 판정 수치가 빠지거나 gate 행의 ok가 없으면 해당 팀 로그 품질은 미확인이다. 메시지 문구를 읽어0으로 보정하지 않으며 비교의 품질 alias도 null을 유지한다. 기존 팀 없는 사건/FIFO 읽기는 바꾸지 않는다.

counts 키는 owner_manual_role_corrections, owner_file_edits, owner_command_runs, coordinator_extra_instructions, normal_role_assignment, owner_approvals, owner_merge_approvals, owner_deploy_approvals, owner_scope_approvals이다. 앞 네 개는 부담, 나머지는 정상 배정/유형별 승인이다. 각 coverage는 `{status:complete|partial|unknown,reportedBy,verifiedBy?,confirmationRef?,refs:[]}`. 닫힌 동일 구간·다른 확인 주체·confirmationRef·비어 있지 않은 refs가 있어야 신고 총량을 표시한다. confirmationRef와 refs 중 하나 이상에 기록된 period.start/end/unit도 최종 집계 구간과 모두 같아야 한다. 요청 수집·손작업·감사품질 및 자체답의 비교 확인에 같은 구간 대조를 적용하며 다른 업무/merge 전의 짧은 구간 확인을 재사용하지 않는다. 자기 확인은 총량이 되지 않는다. observed_counts는 관측 하한이고 총량을 넘을 수 없다.

period는 `{start:ISO|null,end:ISO,unit:project-start-to-merge|representative-task,closed:boolean,completionRef?}`. 프로젝트 전체는 실제 start→merge이고 미병합은 미완료다. 시작은 같은 ISO 시각인지 대조하고 종료/닫힘은 실제 merge 사건에서 다시 도출한다. 입력 end는 수집 시점이며 미래 merge 시각을 미리 맞추지 않는다. 대표 업무는 명시 구간/완료 영수증이 필요하다. 미래/프로젝트 밖 구간은 거부한다. 요청의 최초 근원이 구간 밖이면 나중 답/영수증만 잘라 넣어 도달 수를 올리지 않는다.

request_coverage는 같은 coverage 형식이며 요청 기록 수집 범위의 확인이다. quality_audit는 `{blocking_sum:number|null,rereviews_after_fail:number|null,coverage}`. 로그 blocking과 감사 합을 별도 출처로 보존한다. role_observations는 `{role,workMs:number|null,outputTokens:[{tool,output:number|null}],coverage}`. 역할은 원본/시작 기록에 있어야 한다. coordinator_answers는 `{requestId,coverage}` 목록으로, 같은 요청의 명시 코디네이터 답·사용자 방향 반대 신호 없음·확인 영수증을 대조한다. 같은 신고 행에서 confirmationRef와 refs 중 최소한 하나의 영수증이 각각 requestId와 현재 period를 함께 충족해야 하며 다른 요청 영수증을 재사용해 확인을 만들 수 없다. 여러 refs 또는 중복 신고 행에 요청/구간 조건을 나눠 충족해도 비교 확인으로 인정하지 않는다. 전달 답을 자체 답으로 추정하지 않는다.

근거 ref는 프로젝트 안16KiB 이하의 typed JSON 영수증이다. `{version:1,kind:"team-evidence",sourceRef:"서비스:짧은-ID",hash:"SHA256",requestId?,decisionReplyId?,purposes?:[],period?:{start,end,unit}}`만 받는다. 완료 영수증의 period는 해당 표본의 ISO 시각/단위와 같아야 하며 다른 구간에 재사용하면 닫힘을 인정하지 않는다. sourceRef에 file:/.git/원문 경로를 넣지 않는다. 로컬 지문은 `local:<SHA256>`이다. 본문·상세 제안·사용자 답은 이 파일로 복사하지 않는다. 마감의 근거로 쓰는 영수증은 PM이 검토해 후보에 직접 커밋한다. 원문이 없는 clone에서도 메타데이터 회고 관문은 검증되며 원문 재감사는 원문을 보관한 곳에서 수행한다.

### 요청 수집 확인

비교는 확인·지원 영수증과 선언된 완료 영수증의 경로를 수집 지문이나 구간 닫힘과 독립적으로 검사한다. 위험한 경로나 링크는 다른 증빙이 빠지거나 일치하지 않아도 입력 오류2다.

완료와 요청 수집 지원에 같은 영수증을 쓸 수 있다. 각 용도와 같은 기간을 적는다. 한 번의 stats 또는 비교는 영수증 경로마다 최초 판독을 공유한다. 처음 누락되거나 손상됐거나 상한을 넘은 파일은 같은 조회에서 확인 근거로 승격하지 않는다. 로그 수집·감사·손작업 등 해당 파일에 의존하는 총량을 보류하고 다른 유효한 관측을 남긴다. 최초에 판독한 영수증은 보고 전에 지문을 다시 대조해 도중 변경을 발견하면 조회를 보류한다.

닫힌 구간을 실제로 확인한 뒤 `pace project stats P### --json`에서 `team.requestCoverageInputHash`와 `team.period`를 읽는다. 요청 수집의 `confirmationRef`에는 별도 v1 영수증을 연결한다. 기존 `hash`에 조회한 지문을, `sourceRef`에는 `request-coverage:<감사 가능한 출처 locator>`를 적는다. `purposes`는 `["request-coverage"]` 하나로 두고 `period`에는 같은 start·end·unit을 쓴다. `refs`에는 같은 용도와 구간의 기존 지원 영수증을 둔다. 다른 용도의 출처·지문을 이 규칙으로 바꾸지 않는다. stats는 확인한 요청 수집 영수증의 상대 경로·검증된 입력 지문·영수증 지문과 수집 자료 지문을 team.snapshot.requestCoverage로 내보낸다. 입력 지문은 비교의 저장소 식별자, 비공개 수집 자료의 지문, 지원 영수증과 대표 업무의 완료 영수증 상대 경로·지문, 공개 응답 증빙 목록, 요청 총량·관측·미해결 수를 결합한다. 비교 JSON과 함께 확인 영수증과 support에 적힌 지원 영수증을 보존한다. 유효한 지원 영수증이 없는 구간에서는 입력 지문을 발급하지 않는다. 비교는 결합 지문을 다시 계산하고 영수증 바이트가 일치할 때 용도·구간을 대조한다. 옛 stats, 일부 빠진 확인 필드, 빠지거나 바뀐 요청 증빙·수치, 교체·누락된 확인 또는 지원 영수증은 관측값을 남기고 요청 총량과 방향을 보류한다. stats와 compare는 16 KiB를 넘겼거나 내용이 손상된 일반 요청 수집 영수증에도 같은 규칙을 적용한다. stats의 요청 수집 지원 영수증이 빠지거나 손상된 경우에도 관측을 남긴다. 링크나 위험한 영수증 경로는 입력 오류다. 이전 지문 방식으로 확인했다면 현재 stats로 다시 수집 지문을 조회하고 확인한다. 독립 수기 v1은 기존 신고 기준을 따른다.

조회와 확인은 같은 입력을 사용한다. 지문은 유효 구간, 프로젝트의 요청 관련 사건, 소통 원장과 원장 부재 여부, 요청 판정과 대표 업무 범위 확인에 채택한 영수증을 결합한다. 원장 밖의 단순 게이트·리뷰 행은 제외한다. 이전 요청이나 나중에 드러난 연결도 집계를 바꿀 수 있으므로 같은 구간을 재조회해 대조한다. 확인 당시 자료와 달라지거나 기존 영수증에 입력 바인딩이 없으면 관측과 이유를 남기고 도달·실패만 남은 요청의 총량과 비교 방향을 보류한다. 로그가 없으면 지문은 null이며, 손상된 요청 자료는 조회 오류다. 지문은 실제 확인 주체를 인증하지 않는다.

stats가 보존하는 요청 수집 결합 지문에는 비교 목적·조건·호스트·정의·기록 경계 등 비교 맥락도 포함한다. 저장한 표본의 전후 맥락을 함께 바꿔도 기존 영수증으로 비교 방향을 확정할 수 없다. 이전 방식으로 만든 stats를 대조할 때는 현재 입력으로 다시 조회해 확인한다.

서로 다른 요청에서 외부 출처 locator와 응답 ID가 함께 같거나, 출처가 달라도 응답 ID와 응답 지문이 함께 같으면 그 증빙의 자동 도달을 보류한다. 수신 대상의 별칭으로 응답을 나누지 않는다. 다른 출처의 같은 로컬 ID라도 응답 지문이 다르면 별개로 대조한다. 다른 구간에서 쓰인 같은 증빙도 확인한다. 확인된 별도 답, 다른 유일한 전송 근거, 실패 시도 관측은 그대로 집계한다.

팀 집계에서 사용자 전달은 제안과 전송 시작·완료가 같은 요청, 태스크, 발신자를 가리키고 수신자가 선언된 사용자 경로와 일치해야 인정한다. 외부 전송의 불명 상태를 거쳐 확인한 경우 그 시각까지 포함해 제안 이후 원장 순서대로 확인한다. 시각이나 머리의 값이 충돌하면 해당 도달과 실패만 남은 요청의 집계를 보류하며 독립 확인 답과 실패 시도 관측을 보존한다.

원질문 없이 사용자 전송이 남으면 원장 참조를 따라 연결한 요청도 미확인으로 집계한다. 직접 적은 ID와 참조로 이어진 ID 모두 도달 총량을 보류할 수 있다.

## 비교

`pace project compare-team --before before.json --after after.json --kind role-automation|team-adoption|definition-change [--before-context annotation.json] [--after-context annotation.json] [--json]`은 보고서만 출력한다. 파일을 수정하거나 순위를 매기지 않는다. 입력 출처는 stats-declared-reported/independent-reported/mixed-reported로 구별하며 직렬화된 신고 출처이지 생성기·사람 인증이 아니다. 독립 v1 counts는 수기 신고값이며 stats에서 확인된 총량과 근거 수준이 다르다. stats JSON의 team.snapshot 또는 독립 v1 기준선을 받는다. team.snapshot 봉투나 stats 전용 요청 증빙을 가진 입력은 measurementKind가 빠져도 stats 확인 규칙을 적용한다. 최신 평면 표본에서 출처 필드가 모두 빠져도 관측 시각이나 stats 수집 요약 필드가 남으면 같은 규칙을 적용한다. 날짜를 함께 기록한 독립 수기 표본은 measurementKind에 independent-reported-v1을 명시할 수 있다. stats 전용 수집 요약 필드가 포함된 경우에는 수기 표지가 있어도 stats 확인 규칙을 적용한다. 여러 표본은 `{version:1,samples:[snapshot,...]}`으로 1~32개를 묶는다. 비교 입력 JSON 파일은 각각 32 MiB 이하다. 동일 저장소/조건의 겹치지 않는 명시 구간만 허용하며 같은 구간 중복을 거부한다. N은 이 기록 수에서 도출하고 sampleCount 신고 숫자로 늘리지 않는다. 일부 표본의 관측이 빠지면 관측 열에는 알려진 값만 합한 하한을 표시한다. 총량은 모든 표본의 수집 확인이 필요하다. 전후 N이 다르면 합계의 감소를 개선으로 부르지 않고 unknown이다. 묶음 안 공유 끝/시작 경계는 닫힌 구간 중복으로 거부하고 전후 구간 중복도 unknown이다. 모든 비교 표본의 closed는 typed 완료 영수증이 있어야 인정한다. 프로젝트 전체도 수기 closed:true만으로 닫힘을 인정하지 않는다. stats의 실제 merge 사건으로 구간이 닫혔더라도 비교할 때에는 해당 완료 메타데이터 영수증이 필요하다. 실제 merge 후 TEAM-MEASUREMENT.json의 period.completionRef와 그 영수증의 period를 실제 start/end/unit에 맞춰 기록하고 stats JSON을 다시 조회한다. 최신 snapshot에 주석을 붙이거나 임의로 closed를 바꿔 완료를 만들지 않는다. completionRef는 비교 JSON이 있는 폴더 기준이다. stats의 team.snapshot은 검증한 완료 영수증의 SHA-256을 completionProofSha256에 저장한다. 독립 v1 표본도 완료 영수증 원본의 CRLF를 LF로 바꾼 바이트에서 같은 지문을 기록한다. 비교 JSON을 옮길 때 해당 metadata 영수증도 함께 옮긴다. 기존 파일에 지문이 없거나 완료 영수증이 누락·교체되면 관측을 남기고 그 표본의 신고 총량과 비교 방향을 보류한다. 위험 경로나 잘못된 지문 형식은 입력 오류2이다. 단일 스냅샷은 sampleCount99라도 단일 사례다. 표본 기록 자체의 실제성은 현장 감사 대상이다. 표본별 관측 하한이 nonnull 신고 총량보다 크면 합산 전에 입력 오류2이다. 수집 지문이 맞지 않는 stats 요청 총량은 먼저 미확인으로 낮추어 관측을 보존한다. 잘못된 조건/형식/지문은 종료2, 미확인 결과는 정상 보고0이다.

comparison 필드: study, conditionCode, definition, unit, workType, sizeBand, host, sampleCount, recordingBoundary, qualitySource(event-log|audited-verdicts), qualityScopeHash, additionalSamplePlanRef. 식별자는 짧은 typed 코드다. 조건은 역할 자동화 message-role→start-role, 팀 도입 no-team→team, 정의 수정 before-change→after-change이다. 서로 섞으면 거부한다. 동일 저장소/정의/단위/업무/크기/호스트/기록 경계/품질 출처·범위와 닫힌 구간을 대조한다.

품질 변화는 어느 방향도 자동으로 좋다고 하지 않는다. event-log를 골라도 감사 재검토 수가 미수집이면 개선 결론은 unknown이다. 로그 실패 사건을 감사 재검토 수로 대체하지 않는다. 부담 지표가 일관되게 줄고 품질/근거가 안정된 충분한 합성 조건에서만 observed-burden-improvement, 늘면 observed-burden-worsening이다. 품질 변화·중요 총량 누락·혼재/동률·표본 각2건 미만이면 unknown과 이유·추가 표본 계획을 낸다. 2건은 통계적 효과 입증 문턱이 아니다. 저장소가 다르면 증감을 숨긴다. v1 repository는 기존 기준선과 같은 로컬 main 경로 식별자이므로 JSON 공유 시 경로가 보이고 clone 위치가 달라져도 다른 저장소로 보수 판정한다. 안정 논리 ID로 다른 clone을 동등화하는 기능은 이 버전에 없다. 수치/관측 하한/로그31·감사48 같은 다른 출처는 항상 구별한다. 인과 효과는 별도 현장 판단이다.

T01 두 v1 입력은 원본을 바꾸지 않고 읽는다. 한글 condition/빠진 호스트·업무 조건을 추정하지 않는다. annotation은 comparison 없는 legacy 원본에만 `{version:1,sourceSha256,sourceRef,comparison,reachability?:{file,sha256}}`로 원본 바이트 지문에 고정한다. 최신 snapshot의 조건/도달 수를 주석으로 덮어쓸 수 없다. reachability는 annotation 옆 안전한 상대 JSON 파일이고 지문을 대조한다. T01 reachability-v2의 counts.reached_reply/reached_delivery/unknown을 명시 연결할 수 있다. legacy 요약 출처 신고라는 한계를 유지한다. 연결하지 않은 legacy owner_questions는 수신 의도이므로 도달 수로 승격하지 않는다. 누락 manual은 null, AI-sql의 명시 observed0은 총량null로 유지한다. 닫힘 정보 없는 옛 구간은 닫힌 구간으로 합성하지 않는다. 단일 사례는 unknown과 추가 계획이 정상 결과다.

## 회고와 BR07 인계

PROJECT-CLOSE의 실제 `## 회고` 절의3열 pipe 표(header·separator 포함)에 `| 팀 | [팀 회고](TEAM-RETROSPECTIVE.json) | 요약 |`을 둔다. 코드 fence·HTML·주석 속 예시 행과 header/separator 없는 bare행은 인정하지 않는다. 코드 블록 안의 주석은 코드 원문이며 fence 구조를 바꾸지 않는다. 표·heading에 주석을 섞지 말고 별도 주석 줄을 사용한다. 고정 입력은 다음 형태다.

```json
{"version":1,"metricRef":"METRICS.md","unusedRoles":[{"role":"maker","coverage":"unconfirmed","refs":[]}],"recurringFindings":[],"definitionChanges":[],"noChangesReasonRef":"reason-receipt.json"}
```

반복 지적은 기존 프로젝트 전체 개선 후보 기준이고 미사용 역할은 측정 구간의 참여 선언 기준이다. 두 범위를 합산하거나 같은 범위라고 해석하지 않는다. finish는 현재 측정 구간의 알려진 unusedRoleCandidates를 unusedRoles에 모두 언급하도록 대조한다. 반복 개선 후보 중 gate/review도 각각 정규 code와 현재 count가 일치해야 한다. code는 gate-security, gate-checks, review-blocking, review-should-fix, review-tester-fail처럼 kind와 소문자 코드의 기호/공백을 하이픈으로 바꿔 연결한다. 목록을 비워 알려진 후보를 생략할 수 없다. 신고 count는 현재 지표 count와 정확히 같아야 한다. 실패한 check/done/finish 시도도 게이트 count에 들어가므로 다른 이유로 마감이 실패했다면 stats를 다시 조회해 회고 count를 갱신한 뒤 재시도한다. 각 항목의 의미/원인과 실제 수정 여부는 여전히 사람이 판단한다.

unusedRoles는 coverage observed-none(비어 있지 않은 범위 영수증 필요) 또는 unconfirmed이다. recurringFindings는 `{code,count:2이상,coverage:"reported",refs:[]}`이고 refs가 필요하다. 표준 게이트·리뷰 코드는 현재 지표의 반복 후보와 정확히 일치해야 한다. 별도 조사에서 신고한 지적은 자체 코드와 근거를 사용한다. definitionChanges는 `{role,changeRef,reasonRef}`1~3개 또는 빈 배열+noChangesReasonRef 하나이다. 두 방식을 함께 쓸 수 없다. 모든 ref는 위 typed metadata 영수증이며 자동 역할 수정/삭제를 하지 않는다. 고정 metricRef는 finish 생성 목적지이므로 최초 파일 존재를 요구하지 않는다.

BR07의 회고 단계는 METRICS 팀 절·회고 JSON·영수증의 범위/누락을 읽고 미사용 후보·반복 지적의 실제 의미를 인터뷰한다. 정의 수정 후보1~3개를 승인 범위와 대조한 뒤 별도 적용/원본 호출 검증/새 비교를 수행한다. unconfirmed는 삭제 근거가 아니고 reported count는 독립 감사 완료가 아니다. 실제 두 저장소 도입 효과·스킬 회고 실행은 P009 T08의 현장 관측이다.
## 근거의 일관성과 구간 경계

새 수치/소통 식별자는 `owner`이며 기존 `user` 사건 작성자는 같은 사람이다. T01의 이전 v1 원본 키는 adapter에서만 대응하고 원본을 고치지 않는다. 전후 비교는 before의 모든 구간이 after보다 앞설 때만 방향을 판정한다. 메시지의 리뷰 판정/수치와 구조 data가 충돌하거나 누락되면 로그 품질을 미확인으로 둔다. 코디네이터 자체 답은 같은 요청의 질문 이후 답이 있어야 한다. 회고의 `observed-none`은 현재 stats 구간과 결합한 영수증이 필요하며 구간을 모르면 `unconfirmed`로 남긴다.

표지와 회고 표는 같은 Markdown 구조 투영을 사용한다. 코드 fence·HTML block의 예시를 제외하고 실제 주석은 구조 경계를 보존해 처리한다. 필드/표는 템플릿의 일반 텍스트 형태로 작성한다. 진행 중 start→merge 전체 구간은 조회 때 종료가 늘어나므로 이전에 고정한 역할 영수증의 숫자가 현재 구간과 맞지 않으면 미확인으로 보인다. 고정 대표 업무 구간의 부분 역할 관측을 사용할 수 있으며 이를 전체 총량으로 확대하지 않는다.


로그 품질 총량에는 별도 `log_coverage`가 필요하다. 요청 수집 확인을 리뷰/게이트 수집 확인으로 재사용하지 않는다. 닫힌 동일 기간에 결합한 확인 영수증·근거가 없으면 파일이 존재해도 해당 기간 품질은 null이다. 같은 행의 canonical review 메시지와 data가 충돌해도 null이다. 사용자 답은 최초 요청 이후에만 팀 도달로 인정한다. 비교 입력은 미래 종료를 거부한다.

구조 투영은 템플릿의 ATX heading과 표를 읽으며 회고의 기계 표 구간에서는 Setext/가로선을 명확한 형식 오류로 보류한다. ATX 제목 또는 빈 줄로 정리한다. 미완성/여러 줄 코드와 주석이 섞여 구조를 확정할 수 없는 문법은 보류하고 일반 텍스트로 정리한다. HTML 속성 속 주석 문자열은 문서 주석 상태를 바꾸지 않는다. rebase/검사 후 최종 지표를 쓰기 전에 같은 상태의 회고 후보를 다시 검사한다. 현재 관측/참여한 역할은 observed-none으로 신고할 수 없다.

비교 품질 가드는 감사 재검토와 별도로 `review_failures`(로그 리뷰 실패)를 포함한다. 어느 값이든 달라지거나 수집 범위가 없으면 방향을 확정하지 않는다. 새 팀의 리뷰 숫자는 음이 아닌 정수 토큰을 정확히 한 번 받아 소수·음수·지수·중복을 자르지 않는다. 미채택 프로젝트의 기존 리뷰 문구 입력은 유지하고, 형식이 맞지 않는 옛 리뷰는 팀 품질을 입증하지 않는다. gate의 표준 메시지/구조/ok가 충돌해도 품질은 미확인이다. 질문과 연결되지 않은 답/전송은 미확인 요청으로 보존하고 요청 전 상태 메시지 전송은 팀 도달로 승격하지 않는다. PI/CDATA/선언 HTML 블록은 예시로 제외한다. 새 역할 문구는 사용자로 생성하지만 호칭만 다른 기존 책임 문단은 읽을 수 있으며 JSON/CLI 사람 식별자의 이전 값 호환과는 별개다.

표지는 열0의 최상위 메타데이터 필드만 인정하며 하위 목록 예시를 채택으로 해석하지 않는다. 네 칸/탭 들여쓰기 코드는 블록 경계에서 불투명하게 처리해 그 안의 주석 기호가 실제 표지·제목·표를 가리지 않는다. 요청 ID가 없는 by:user·by:coordinator 답은 미연결 관측으로 센다. by:agent 수신 확인은 기존대로 요청 답에서 제외한다. 새 팀 회고의 기계 표 구간은 템플릿의 ATX 제목과3열 표를 사용한다. Setext/가로선 분류를 추측하지 않으며 일반 본문이나 기존 팀 없는 마감 전체를 이 문법으로 제한하지 않는다.

팀의 project-start-to-merge 닫힘은 엄격한 로그의 cli 성공 start/merge 사건으로만 도출한다. 기존 시간 지표의 Git 커밋 메시지 근사는 옛 출력에 유지하지만 새 팀 총량의 완료 증거로 쓰지 않는다. 품질 가드는 로그의 blocking·should_fix 합, 리뷰 실패, 감사 재검토, 게이트 실패를 구분해 모두 비교하며 합계가 안전 정수 범위를 넘으면 미확인이다. 값 없는 중복 등급명도 허용하지 않는다.

블록 들여쓰기는 탭을4열 기준으로 계산한다. HTML 주석 블록은 종료 줄 전체까지 불투명하며 그 뒤 문자를 다시 제목/표로 해석하지 않는다. 회고 기계 구간의 밑줄/구분선 전용 행(`=`, `-`, `*`, `_` 계열)은 ATX 제목 또는 빈 줄로 정리한다. sourceRef 검증은 스킴 대소문자와 경로 구분자를 정규화하며 FILE·로컬 경로·private Git 경로를 출처 metadata로 쓰지 못한다.

감사 blocking을 비교 기준으로 골라도 로그 blocking 축을 함께 대조한다. 양쪽에 수집된 감사 blocking도 event-log 선택으로 숨기지 않는다. 필수 로그값 누락 또는 어느 수집 축의 변화도 개선/악화를 확정하지 않는다. 성공 merge가 성공 start보다 앞선 모순 기록은 조회 오류2이며 닫힌 구간이 아니다.

일반 inline HTML 태그는 실제 다음 ATX 절 경계를 가리지 않는다. 독립된 generic HTML 태그처럼 절 소속을 확정하기 어려운 입력은 회고 기계 구간 경계로 보류하므로 표 앞에서는 일반 텍스트를 사용한다. 문단 안 미완성 주석은 빈 줄/새 블록을 넘어 다음 절을 숨기지 않는다. 기존 소통 요약과 팀 측정이 함께 표시되면 집계 경계를 설명하며 서로 합산하지 않는다.

기호만 있는 `-` 같은 빈 목록 행도 회고 기계 구간의 지원 밖 입력이다. 모두 실제 Setext/가로선이라는 뜻은 아니며 ATX 제목 또는 빈 줄로 정리한다. inline 주석을 지운 결과에 원래 없던 ATX 시작을 만들지 않고 원문 시작 구분자를 먼저 확인한다.

기계 입력의 제목과 표 행은 템플릿처럼 열0에 쓴다. 프로젝트 머리는 목록의 들여쓰기 범위와 탭 열을 확인하여 실제 첫 본문 제목에서 끝난다. 같은 목록 경계 판독을 회고에도 적용한다. 번호 2 이상으로 시작하는 새 목록은 일반 문단을 중단하지 않는다. 목록 안에서 열린 코드·HTML 블록은 목록 밖 제목까지 이어지지 않는다. 머리의 목록에 들여쓴 제목과 활성 표지가 함께 있거나 회고 기계 구간에 들여쓴 제목이 있으면 보류한다. 일반 텍스트 또는 열0의 실제 절로 정리한다. 표는 빈 줄/실제 블록 경계 다음에 시작한다. 원문의 이스케이프된 파이프는 셀 내용이고 구분자가 아니며, 이미 열린 다른 열 수의 표 안에서 헤더처럼 보이는 행을 새3열 표로 읽지 않는다. inline 주석/코드 투영으로 원문 표의 열 수를 줄이지 않는다.

팀 영수증 sourceRef는 슬래시/역슬래시가 없는 `서비스:짧은-ID` 또는 `local:SHA256`이다. URL/파일 경로 대신 그 출처의 짧은 ID나 로컬 지문을 쓴다. 엄격한 팀 사건 읽기는 문자열 필드의 실제 JSON 타입을 검사하며 배열/객체를 문자열 정규식으로 강제 변환하지 않는다. 팀 없는 기존 로그 읽기의 관용성은 그대로다.

실패 전송 기록과 근거 없는 사용자 답이 함께 있으면 실패 시도 수를 보존하되 팀 요청 도달은 미확인이다. 실패 영수증이 불완전한 답의 의미를 해소하지 않는다. 비교는 표본별 품질 벡터를 보존한다. 현재 형식에는 대응 표본 관계가 없으므로 품질 변동이 있으면 합계가 같아도 방향을 보류한다. 같은 분포처럼 보여도 대응/품질 동등성을 자동 인증하지 않는다. stats-declared-reported와 independent-reported의 차이 또는 혼재도 수집 경로 동등성 미확인으로 unknown이며, 경로 통일·품질 대조의 추가 계획을 낸다. 원 수치·출처는 그대로 표시한다.

연속한 pipe 행 묶음은 단일 후보 표다. 앞쪽이 지원 밖 표라고 그 안의 헤더 모양 행을 새 회고 표로 다시 읽지 않는다. 새 표는 빈 줄로 분리한다. 요약의 원문 열 수와 화면에 보이는 내용의 존재를 별도로 확인하므로 주석/빈 태그만 있는 요약은 보류한다.

요약 셀은 일반 텍스트/Markdown 링크로 쓴다. 숨김 스타일이나 HTML 엔터티의 실제 표시를 추측하지 않으며 HTML 태그·주석·엔터티가 있으면 일반 텍스트로 정리하도록 보류한다.

헤더·근거 링크 이름·요약은 표시 가능한 일반 텍스트를 포함해야 한다. 빈 이름의 링크·제어/형식 문자·inline 코드·HTML 표현은 기계 셀에서 보류하며 텍스트로 정리한다. `A<B` 같은 일반 비교 문구와 이름 있는 `[범위](<https://example.invalid/scope>)`는 실제 HTML 태그와 구별한다. Markdown 블록 닫힘·빈 줄·표 구분의 공백은 ASCII space/tab이며 NBSP 같은 Unicode 공백으로 코드나 HTML 예시를 닫거나 표를 만들지 않는다.

최초 요청 기준 코호트 밖의 요청이 구간 안에 활동하면 경계 미확인으로 표시하고 도달 신고 총량과 부담 방향을 보류한다. linked/unconfirmed에는 이 별도 경계 요청이 포함되며 crossBoundaryObserved로 구별한다. 실제 구간 안의 역할 참여·실패 시도·소통 종류 관측은 최초 요청의 시각으로 지우지 않는다. Team 없는 옛 전역 소통 집계와 직접 legacy 판독의 의미는 유지한다.

회고의 절 소속은 투영된 LF/CRLF 행을 그대로 순회해 정한다. JavaScript multiline 정규식의 U+2028/U+2029 경계를 Markdown 제목으로 재해석하지 않는다. 셀은 Unicode default-ignorable 문자·BRAILLE PATTERN BLANK만으로 표시 내용을 채울 수 없다.

투영 전에 CRLF·단독 CR을 LF로 정규화해 Markdown의 실제 줄 경계를 보존한다. 원본 파일은 다시 쓰지 않는다. 채움 문자에 Markdown 장식이나 링크 목적지만 붙여도 표시 내용으로 인정하지 않으며, inline/reference 링크 이름 자체에 표시할 내용이 있어야 한다. 경계 활동0건에는 총량/방향 보류 문구를 붙이지 않는다.

셀의 링크 이름은 이스케이프와 균형 대괄호·링크 대상·인용 제목을 구별해 읽는다. 링크 대상/제목의 문자열을 이름의 표시 내용으로 세지 않으며, `\[`로 쓴 일반 예문은 링크로 오인하지 않는다. 이미지·미완성 링크·16단계보다 깊은 셀 중첩은 이 기계 형식의 지원 밖이므로 일반 텍스트로 정리한다. 전체 PROJECT-CLOSE의 공통 하네스 절 검사는 여전히 LF/CRLF 형식을 사용한다. 단독 CR 정규화는 팀 투영의 경계 안전을 위한 것이며 전체 하네스의 단독 CR 지원을 뜻하지 않는다.

참조 링크 모양은 이름의 표시 내용을 보수적으로 검사하며 문서 밖 참조 정의의 실제 해석/해결을 인증하지 않는다. 링크가 아닌 대괄호 예문은 `\[`로 의도를 분명히 한다. 필수 근거 링크는 이와 별개로 고정 TEAM-RETROSPECTIVE.json 목적지와 실제 typed 입력을 검증한다.


영수증의 `purposes`는 증명 용도를 명시한다. 완료는 `completion`, 답은 같은 requestId의 `owner-answer` 또는 `coordinator-answer`, 전체 수집은 `request-coverage`/`log-coverage`, 감사는 `quality-audit`, 역할 관측은 `role-observation`, 손작업/승인은 해당 counts 키다. 전체 용도는 같은 period와 requestId/decisionReplyId 없음이 필수다. 완료만 또는 개별 요청 영수증으로 빈 로그의 전체 도달·품질0을 확인할 수 없다. 복합 전체 감사는 필요한 용도를 명시적으로 열거한다. purposes 없는 기존 locator는 읽을 수 있지만 총량·완료 권한은 없다. 이 필드도 참여자의 신고이며 진위 인증은 아니다.

같은 requestId에 서로 다른 명시 태스크가 있으면 도달을 unknown으로 남긴다. 한 태스크의 같은 요청 중계와 태스크 없는 프로젝트 거울 기록은 계속 중복 제거한다. 팀 회고 후보는 TASK-CLOSE와 로그 출처 수치를 함께 보존한다. 출처 겹침이 미확인이면 종류별 큰 값을 후보 하한으로 쓰며 합산 총량으로 주장하지 않는다. 완전한 리뷰 행 한 건도 과거 마감 지적을 지우지 않는다. 현재 기간의 품질 총량은 별도의 기간/수집 확인이며 프로젝트 전체 리뷰 이력 대체 증명이 아니다.

명시 Team 채택(표지·측정 입력·새 버전 start)의 기본 handoffs 소통 요약과 팀 측정은 같은 최초 요청 코호트를 쓴다. 미채택 프로젝트의 소통 요약은 기존 전역 신고 집계를 유지한다.

원장 중계는 검증된 relayOf를 따라 같은 요청에 귀속한다. 같은 ID를 가진 별도 질문·에스컬레이션을 원장 거울로 연결하려면 사건 ref의 team-evidence 영수증에 해당 원장 decision_request의 `sourceRef: "handoff:<행 ID>"`, `requestId`, `hash: <그 행의 bodyHash>`를 기록한다. 거울의 명시 Task는 해당 제안 행과 같아야 하며, 질문 로그 시각은 원장 행 이후여야 한다. 영수증에 선택 기간이 있으면 로그 시각과 측정 단위를 대조한다. 원문은 영수증에 쓰지 않는다.

같은 ID·Task만 있는 로그는 거울 연결 미확인이다. 명시 Task 충돌과 같은 Task의 모호한 출처를 표시하고, 참조가 검증된 원장 답·전달의 관측은 남긴다. 연결이 미확인인 관측을 도달 총량으로 승격하지 않는다. 기본 소통 요약에도 구간 경계와 연결 미확인 건수를 표시한다. 로그만 있는 같은 Task/프로젝트 범위 기록의 신고 집계는 별도 원장 연결 증명이 아니다.

로그 답변에 명시 Task가 있으면 그 Task에서 같은 요청이 처음 시작한 시각 이후여야 한다. 뒤늦게 같은 ID의 태스크 질문이 생겨도 먼저 기록된 답을 소급 연결하지 않는다. 사용자 답과 코디네이터 자체 답에 같은 귀속 조건을 쓴다. 직접 참조한 제안과 원장 응답의 연결은 원장 판정에 남긴다.

이전에 팀 마감이 검증된 프로젝트는 후속 커밋에서 채택 파일과 팀 마감 영수증을 함께 빼도 기존 프로젝트로 병합할 수 없다. 병합은 대상의 같은 프로젝트 경로에서 선조의 유효 영수증과 당시 tree도 확인한다. 팀 측정 입력을 복원하고 finish를 다시 실행해 새 승인 SHA를 받는다. 기존 다른 용도의 파일은 팀 이력의 근거가 되지 않는다.

역할 관측은 `role-observation` 목적, 같은 기간, `sourceRef: "role-observation:<role>:activity:<출처 locator>"`를 대조한다. 예를 들어 `role-observation:builder:activity:fixture:run-1`이다. 수집 상태가 unknown이면 수치는 미확인이다. 회고의 관측 없음은 같은 역할의 `role-observation:<role>:none:<출처 locator>`를 요구하며 활동 영수증을 사용하지 않는다. 둘 모두 참여자 신고이며 회고 후보의 실제 의미는 사람이 대조한다.

처음 팀으로 검증한 finish에서 rebase/검사 뒤 현재 채택 근거가 없어지면 회고를 생략하거나 봉인하지 않고 보류한다. 재시도는 현재 파일과 접근 가능한 Git 선조의 채택 근거를 확인한다. 기존 미채택 로그의 관대한 판독을 유지하고, 팀 품질은 한 행에 판정자 역할 하나만 허용하며 pass에는 blocking 0을 요구한다.

과거 표지는 해당 Git 문서의 Markdown 문맥에서 유효한 v1이었는지 확인한다. 삭제된 미지원 표지 버전은 과거 채택으로 기록하지 않는다. 현재 문서의 형식 오류와 Git 조회 실패는 보류한다.


대표 업무는 시간창만으로 단독 업무임을 확인할 수 없다. 완료 영수증의 기존 sourceRef에 `representative-scope:<출처 locator>`를 사용해 같은 기간의 단독 업무 수집 범위를 신고한다. 예를 들어 `representative-scope:fixture:isolated-document`이다. 태스크 번호가 없더라도 단독 문서 업무의 범위가 확인되면 사용할 수 있다. 기간에 여러 독립 Task, Task와 귀속 불명 사건, 또는 같은 요청 ID의 모호한 원장·로그 연결이 섞이면 stats는 관측과 사유를 보존하고 해당 총량과 방향을 보류한다. 비교 JSON은 같은 영수증과 범위 미확인 사유를 함께 읽는다. 원본 기록과 기존 기준선을 고치지 않는다.

프로젝트 범위의 요청과 태스크 요청의 시작을 각각 확인한다. 앞선 질문은 뒤에 확인된 같은 요청의 시작이 될 수 있다. 이미 유효한 프로젝트 답이 뒤 태스크의 시작보다 이르면 시간창 관측으로 보존하고 그 태스크의 대표 업무 총량은 보류한다. 연결이 없는 같은 시각의 로그는 기록 순서도 대조한다. 검증된 원장 제안과 그 거울은 실제 제안의 태스크를 사용한다. 비교에서 재사용된 응답 증빙이 원래의 신고 관측 수에 남는 경우에는 고유 도달의 하한을 별도로 확인해야 한다는 안내를 표시한다.

검증된 원장 중계의 태스크에서 제안 이후 기록한 사용자/코디네이터 답은 원래 요청을 따른다. 독립 요청의 Task 충돌 판정과 중계 답 허용 시각은 구별한다. 활동 증빙이 있는 역할은 시간·출력 수치가 0이어도 같은 기간의 관측 없음으로 신고할 수 없다.

팀 채택 Git 이력은 프로젝트 번호로 확인한다. 폴더 이름을 변경해도 이전 경로의 유효한 채택 및 마감 관문을 유지한다. rebase에서 새로 편입된 선조 이력도 검사 뒤 확인한다.

팀 측정과 명시 채택 프로젝트의 소통 요약은 자신이 참조하는 제안부터 최초 요청까지 중계 시각이 순서대로인 답과 전송을 도달로 인정한다. 미채택 프로젝트의 기존 소통 요약은 기존 신고 집계를 유지한다. 측정과 회고는 원장의 최초 관측(파일 또는 부재)을 같은 입력 추적에 둔다. 원장이 새로 생기거나 사라져 관측이 달라지면 마감을 보류한다. 불투명 HTML 예시 블록은 연 태그를 닫았을 때 끝나며 다른 태그의 닫는 줄이 회고 표를 활성화하지 않는다. 코디네이터 자체 답과 실패 전달 시도는 관측 열에 표시하고 전체 총량은 미확인이다.

HTML raw 태그의 `/>`도 예시 블록을 열 수 있다. 회고 입력 칸에는 일반 텍스트 이름과 닫는 대괄호가 유효한 고정 JSON 직접 링크를 쓴다. 끊어진 원장 링크는 작업 폴더에서도 입력 오류다.

요청에 귀속되지 않은 다른 태스크의 답은 별도 연결 미확인이다. 같은 구간에서 유효한 답의 관측은 유지하며 전체 도달 총량은 보류한다. 코디네이터 자체 답 영수증은 원장 사용자 답의 `decisionReplyId`를 사용하지 않는다. 팀 채택 표지는 현재와 과거 모두 프로젝트의 실제 머리까지만 판독한다.
