**자동 첨부와 읽은 범위**
- 자동 첨부: 사용자 이메일 컨텍스트가 붙어 있었습니다. 값은 쓰지 않고, 사용하지도 않았습니다.
- 읽은 파일:
  - `skills/pace-project-dev/SKILL.md` 1–93줄(전체)
  - `references/decision-rights.md` 1–45줄(전체)
  - `references/verification.md` 1–18줄(전체)
- 전체 바이트 수는 도구로 확인하지 않아 적지 않습니다.
- `commands.md`는 열지 않았습니다. 그래서 `pace project log`의 정확한 인자 형식은 적지 않았고, 기록할 때 그 문서에서 확인해야 합니다.

**공통 전제**
- 근거는 decision-rights B-4입니다. 허브 회신 → 워크트리 적용 → 재검증을 마쳐야 공동 시도 1회이고 상한은 2회입니다.
- 이 상황은 2회를 모두 소진했으므로 같은 조치를 세 번째로 반복하지 않습니다.
- 이후는 차선을 고르는 단계입니다.

**옵션 1: 계약상 명시된 선택 태스크 보류, 독립 태스크 남음**
- **담당**: 워크트리 PM이 결정합니다. A의 다섯 항목 모두 '아니오'이므로 owner 결정은 필요 없습니다. 허브는 장애 근거를 확인하고 회신한 상태로 유지합니다.
- **행동**
  1. 선택 태스크를 `보류`로 두고, 이슈로 기록합니다. 근거는 2회 시도 내용과 재검증 실패 증거, 계약상 선택 태스크라는 점입니다.
  2. 독립 태스크를 이어서 수행합니다. 태스크 표의 `대기` 중 맨 앞부터, 분석 → 설계 → 구현 → 테스트 → 마감 순서입니다.
  3. 보류 결정은 `pace project log`로 남깁니다. 허브가 정한 부분은 "(main 판단)", PM이 정한 부분은 "자체 판단"으로 구분합니다.
  4. 진행 상황은 `pace memory status --project --body …`로 갱신합니다.
  5. 도구 수정이나 환경 복구, 결정 증거처럼 원인이 풀렸다는 근거가 생기면 보류 태스크를 재개합니다.
- **회신·보고**
  - owner에게 즉시 보내는 요청은 없습니다.
  - 보류를 한 줄 사후 요약으로 정리해 다음 대화나 완료 보고에 붙입니다(C).
  - finish 뒤에는 자체 판단 대조를 하고, 결과를 보고에 적습니다.
- **질문 0건, 승인 대기 0건.**

**옵션 2: 필수 태스크 보류 후 필수 결과 없이 마감**
- **담당**: 결정은 owner가 합니다. 이 조치는 A-1(합의 변경)에 해당합니다. 워크트리 PM이 `ask`로 허브에 인계하고, 허브가 owner에게 `decision_request`를 보냅니다.
- **행동**
  1. 필수 태스크 보류와 기준 미달 마감을 owner 회신 전까지 실행하지 않습니다. PROJECT-CLOSE 작성과 `finish`로 넘어가지 않고 그 조치만 보류합니다.
  2. 독립 태스크가 있으면 계속 진행합니다. 없으면 해당 지점에서 대기합니다.
  3. 요청과 보류 사실은 `pace project log`로 기록합니다.
  4. owner 회신이 오면 실행 전 승인 확인으로 원문과 대상·범위를 대조한 뒤 따릅니다.
  5. 합의가 적법하게 바뀌면 그 계약으로 다시 판정합니다. 합의가 그대로이고 원인이 풀리면 태스크를 재개합니다.
- **회신·보고(C 결정 요청)**
  - 요청에는 A-1 번호를 붙입니다.
  - 대상은 필수 태스크이고, 근거는 2회 공동 시도의 실패 증거와 영향받는 기준 `P-n`입니다.
  - 선택지는 ①원인 해소 후 재개, ②합의 변경(범위·기준 축소) 후 마감, ③보류 유지입니다.
  - 추천안과 이유를 함께 적습니다.
- **질문 1건(owner에게 A-1), 승인 대기 1건.**

**경계**
- 두 옵션 모두 같은 조치를 세 번째로 시도하지 않습니다.
- 옵션 2에서 owner 승인 없이 PM이 필수 결과 없이 마감하는 일은 금지입니다.
- 이 시험에서는 수정·질문·메모리 저장·커밋·전송을 하지 않았습니다.
