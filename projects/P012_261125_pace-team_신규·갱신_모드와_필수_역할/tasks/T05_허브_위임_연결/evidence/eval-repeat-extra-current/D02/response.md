**결론:** A-1~A-5는 모두 "아니오"다. 질문 0건, 승인 대기 0건이다. 워크트리 PM이 허브 회신(B3)을 적용하고 재검증한 뒤 태스크를 재개한다.

**1. 담당**
- 허브 PM은 이미 재현, 원인 판별, 교체 범위와 회귀 검사 명령 지정, 근거 회신까지 마쳤다.
- 워크트리 PM은 적용, 재검증, 기록, 태스크 재개를 맡는다.
- 병합·푸시·배포는 이 건과 무관하다. 허브 몫이고 owner 승인이 있어야 하며, 워크트리는 하지 않는다.

**2. 순서와 실제 명령·기록**
1. 허브 회신의 근거, 교체 범위, 명령이 TASK 계약(기준 `T-n`) 안에 있는지 대조한다. 범위 밖이면 그 부분만 보류하고 `ask`로 허브에 올린다. 이 상황은 범위 안이다.
2. 회신을 기록한다.
   `pace project log P### T0n --type decision --msg "fixture 지연: 허브 지정 범위만 교체, 회귀 검사 <명령>" --src "main 판단" --ref <프로젝트 내 근거 상대경로>`
   원문 출력과 비밀은 복제하지 않는다.
3. 허브가 정한 범위의 fixture만 교체한다. 다른 파일은 건드리지 않고, 보안 검사와 필수 테스트를 약화하지 않는다.
4. 허브가 지정한 회귀 검사 명령을 그대로 실행한다. 종료 코드와 결과 위치를 `evidence/`에 남긴다. 이것이 공동 시도 1회의 재검증이다(상한 2회).
5. 재검증이 통과하면 태스크를 재개한다. 변경이 코드·테스트에 닿았으므로 재검사 사유·범위·담당을 기록하고, 해당 부분부터 tester ∥ reviewer를 다시 돈다. 이미 통과한 동일 검사는 반복하지 않는다.
6. 마감할 때는 TASK-CLOSE 작성, `pace project check P### T0n`, `pace project done P### T0n`, `pace memory status --project --body "…"` 순으로 한다. 이후 `feat(P###/T0n): …` 커밋에 같은 커밋으로 넣는다.
7. 병합 대기 중이면 main 커밋은 병합 뒤로 미룬다.

**3. 회신·보고**
- 허브에는 적용 범위, 재검증 명령과 종료 코드, 결과 위치를 짧게 회신한다. 실패하면 2회차 근거와 함께 보낸다.
- 이 결정은 "(main 판단)"으로 기록하고, 완료 보고의 사후 요약에 한 줄 포함한다.
- 2회 뒤에도 실패하면 안전하게 되돌릴 수 있는 차선을 고른다. 필수 태스크 보류나 기준 미달이면 A-1로 올린다.

**4. 자동 첨부와 읽은 범위**
- 자동 첨부는 있었다. 사용자 계정 이메일이 시스템 리마인더로 붙었고, 값은 적지 않는다.
- 읽은 파일은 다음과 같다.
  - `skills/pace-project-dev/SKILL.md` 1~93줄(전체)
  - `references/decision-rights.md` 1~46줄(전체)
  - `references/verification.md` 1~19줄(전체)
  - `references/commands.md` 1~16줄(전체)
- 다른 references는 열지 않았다. 다른 사례의 문서도 읽지 않았다.
- 전체 바이트 수는 도구로 확인하지 않아 적지 않는다.
