**결론:** 허브 PM이 처리한다. 도구 수정 커밋은 병합 뒤로 미루고, 병합 대기 프로젝트는 기존 도구로 먼저 병합한다. 질문은 0건이다. 승인 대기는 병합에 대한 1건뿐이다.

**담당**
- 허브 PM(main 코디네이터)이 맡는다. 워크트리 작업자는 장애 근거를 `escalation`이나 `ask`로 올리고 회신을 기다린다.
- 근거는 SKILL.md §6과 decision-rights.md B-3, A-2의 S1 위임이다.

**순서와 실제 명령·기록**
1. **A 판정:** 합의 변경은 없다(A-1 아니오). 수정은 S1 위임 범위라 A-2도 아니오다. 검사를 약화하지 않으므로 A-3도 아니오다. A-4와 A-5도 해당 없음이다. 따라서 owner 질문은 하지 않는다.
2. **재현:** 작업자가 올린 증거 원문과 재현 조건을 확인한 뒤, 격리한 도구 사본(main 작업트리 밖)에서 장애를 재현한다.
3. **수정과 검증:** 같은 격리 사본에서 결함을 고친다. 버그이므로 실패하는 테스트(RED)를 먼저 만든다. 그다음 같은 필수 검사를 수행한다. 필수 검사, 보안 검사, 독립 검토는 생략하지도 약화하지도 않는다.
4. **main 커밋 보류:** 병합 대기 중이므로 도구 수정 커밋과 재설치는 병합 뒤로 미룬다. 메모리 파일은 갱신하되 커밋하지는 않는다. 수정은 격리 사본에만 있고 main의 검증 대상은 그대로다.
5. **병합 대기 프로젝트 처리:** 기존 도구로 병합한다.
   - 허브가 main에서 `pace project merge P###`를 실행해 미리보기를 확인한다.
   - 미리보기의 커밋 전체 SHA를 owner 승인 원문과 대조한다.
   - 대상과 범위가 일치하면 `--yes`를 입력한다. 승인 원문이 없거나 대상이 다르면 입력을 보류하고 승인을 요청한다.
6. **병합 뒤:** main에서 도구 수정을 커밋하고 필요하면 재설치한다. 이때 `pace project log --ref`로 기록을 남긴다. 병합 FF 뒤 완료 기록이 실패하면 recovery.md를 따른다.
7. **회신:** 허브가 작업자에게 결정, 근거, 재검증 기준을 회신한다. 막힌 조치만 보류하고 독립 작업은 계속한다. 작업자는 회신을 `(main 판단)`으로 기록하고, 도구가 적용된 뒤 재검증해서 태스크를 재개한다.
8. **보고:** 완료 보고나 다음 대화에 사후 요약 한 줄을 붙인다. 내용은 "도구 결함을 격리 사본에서 재현·검증했고, 병합 뒤 커밋했다"이다. 공동 시도는 상한 2회다.

**승인·질문 대기:** 질문은 0건이다. 병합 승인만 1건 대기한다. 기존 owner 승인이 대상에 맞으면 그 승인을 재사용하고, 없으면 병합 승인 요청을 보낸다. 도구 수정 자체는 승인을 받지 않는다.

**자동 첨부와 읽은 범위**
- 자동 첨부는 있었다. 사용자 계정 정보(이메일)가 system-reminder로 붙었고, 그 값은 쓰지 않았다.
- `skills/pace-project-dev/SKILL.md`는 1~93줄 전체를 읽었다.
- `references/decision-rights.md`는 1~46줄 전체를 읽었다.
- 다른 references는 열지 않았다. 전체 바이트 수는 도구로 확인하지 않아 적지 않는다.
- 수정, 질문, 메모리 기록, 커밋, 전송은 하지 않았다.
