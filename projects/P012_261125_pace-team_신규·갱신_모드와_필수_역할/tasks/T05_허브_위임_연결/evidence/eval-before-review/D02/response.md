**읽은 자료.** `skills/pace-project-dev/SKILL.md`는 1~92줄 전체를 읽었다. `references/decision-rights.md`는 1~45줄, `references/verification.md`는 1~18줄을 읽었고, `references/commands.md`는 `project log` 관련 부분만 Grep으로 확인했다. 자동 첨부 컨텍스트가 있었고, 그 값은 쓰지 않는다. 전체 바이트는 도구로 확인하지 않았다. 다른 사례의 파일은 읽지 않았다.

**사례: 허브가 재현·결정하고 근거와 함께 회신함 (TASK 범위 안)**

1. **담당 구분**
   - 허브 PM은 재현, 원인 판별, 교체 범위 결정, 회귀 검사 명령 지정, 회신까지 마쳤다. 이는 decision-rights B-3에 해당한다.
   - 워크트리 PM(나)은 회신을 적용하고 재검증한 뒤 태스크를 재개한다. 검증 책임은 나에게 있다(verification.md).
   - A 다섯 항목은 모두 "아니오"다. 교체와 검사는 TASK 범위 안이고, 합의·외부 영향·안전 기준·사용자 자산·사람 수행에 걸리지 않는다. 그래서 owner 요청은 만들지 않는다.

2. **실제 순서**
   1. 허브 회신에서 교체 범위, 회귀 검사 명령, 근거를 확인한다. 이 회신이 TASK 계약과 어긋나는지만 대조한다.
   2. 지정된 범위만 교체한다. 범위 밖은 건드리지 않는다.
   3. 허브가 지정한 회귀 검사 명령을 실행하고 종료 코드와 결과 위치를 확인한다. 저장소 검사 명령과 필요한 E2E도 수행한다.
   4. 기록은 다음 명령으로 남긴다.
      - `pace project log P### T0n --type decision --msg "fixture 지연 교체 범위·회귀 검사 확정(허브 재현 근거)" --src "main 판단" [--ref 근거 파일]`
      - 재검증 결과는 `--type review` 또는 해당 type으로 같은 태스크에 기록한다.
      - 원문 출력, 세션, diff, 비밀은 복제하지 않는다.
   5. 구현 변경이 있으므로 tester ∥ reviewer를 새 맥락으로 다시 돌린다(SKILL §3-4). 단, 같은 대상에서 이미 성공한 검사는 반복하지 않는다. 재검사는 사유·범위·담당을 기록하고 해당 부분부터 한다.
   6. 마감 순서는 TASK-CLOSE 작성 → `pace project check P### T0n` → `pace project done P### T0n` → `pace memory status --project --body "…"` → 커밋 `feat(P###/T0n): …`이다. 메모리는 같은 커밋에 넣는다.

3. **회신·보고**
   - 허브에는 적용 결과와 재검증 결과를 짧게 회신한다. 이것은 공동 시도 1회의 마지막 단계(회신 → 적용 → 재검증)다. 상한은 2회다.
   - 완료 보고나 사후 요약에는 "허브 판단(main 판단)에 따라 교체·검사 수행" 한 줄을 넣는다.
   - 재검증이 실패하면 근거와 함께 허브에 다시 보낸다. 같은 실패가 3회면 B로 올린다.

4. **경계**
   - push, merge, 배포는 하지 않는다. merge는 허브가 owner 승인 후 실행한다.
   - main 파일은 고치지 않는다.
   - 합의(목적·기준·범위)가 바뀌는 사실이 나오면 그때만 A-1로 허브에 인계한다.

5. **대기 수**
   - 질문 0건, 승인 대기 0건이다. 이번 사례는 모두 TASK 범위 안이므로 멈추지 않고 진행한다.
   - 이번 시험은 읽기 전용이라 실제 수정·기록·메모리·커밋·전송은 하지 않았다.
