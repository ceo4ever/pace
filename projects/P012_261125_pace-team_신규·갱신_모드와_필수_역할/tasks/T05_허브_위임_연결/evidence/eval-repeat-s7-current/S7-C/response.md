# 시험 답안: 3차 fail, `escalation.stage: diagnose` 신호 이후

## 담당
- **워크트리 PM(나)**: 진단 작성, 수정, 기록, 재검토 호출을 맡는다.
- **허브**: 세 차례 근거와 진단을 받아 B 절차로 근본 조치를 정하고 회신한다.
- **owner**: 이번 경로에는 개입하지 않는다.

## 순서
1. **신호를 받은 이 호출에서 바로 대응한다.** 종료 0과 `diagnose`는 이미 기록된 단계다. 진단을 기록하기 전에 `verify`를 다시 부르면 종료 16으로 차단되므로 부르지 않는다.
2. **증거를 모은다.** 1~3차 fail 원문(`review-records/R1~R3.json`)과 차수별 blocking(PATH 누락, launchd 등록, 강제 종료 신호)을 읽는다. 원문은 추정 복원하지 않는다.
3. **원인 층을 `design`으로 판별한다.**
   - 합의된 환경은 처음부터 macOS였다.
   - 근본 원인은 Windows의 PATH·등록·종료 방식을 그대로 적용한 설계다.
   - 환경 결정 자체가 틀린 것은 아니므로 `planning`이 아니다.
   - 지적별 땜질은 하지 않는다.
4. **허브에 보고한다.** 세 차례 근거와 `design` 진단을 허브로 보낸다. 제안하는 근본 조치는 macOS 기준 설계 재작성이다. 구체적으로 PATH는 macOS 방식으로, 등록은 launchd 방식으로, 종료는 macOS 신호 방식으로 다시 쓴다. 이 보고는 질문이 아니라 B 절차의 근거 전달이다.
5. **수정 직전에 조치를 A-1~A-5로 대조한다.**
   - 합의된 목적·범위·기준 `P-n`은 그대로이고 환경 정합성만 맞춘다. 외부 영향, 안전 기준 완화, 사용자 자산, 새 사람 승인도 없다. 따라서 모두 "아니오"다.
   - 결론은 PM이 결정하고 owner에게 묻지 않는다.
   - 허브 판단 중에 A에 걸리는 항목이 나오면 그 조치만 보류하고 owner 요청을 허브를 거쳐 보낸다.
6. **진단 증거 파일을 쓴다.** `evidence/`에 세 차례 원문 요약, `design` 층, 근본 조치, A 분류 이유, 허브 회신을 담는다. 회신은 "(main 판단)"으로 표기하고 `pace project log`에도 남긴다.
7. **진단을 기록한다.**
   - `pace agent review-note --target <대상> --diagnosis --layer design --summary "<진단·조치>" --file evidence/<진단 파일>`
   - 이 기록 직후 단계는 normal이 된다.
   - `--decision`은 이 시점에 쓰지 않는다.
8. **확정한 근본 조치를 적용한다.** macOS 기준으로 설계를 다시 쓰고 TASK.md나 대상 문서를 고친다.
9. **다음 검토를 받는다.** `pace agent verify`를 같은 대상 경로와 같은 경로(verify)로 호출한다.
   - 새 기준의 **전체 검토**다. `rereview_of`는 없고, 이전 지적으로 purpose를 좁히지 않는다.
   - purpose에는 합의된 상위 목적과 판정 기준만 넣고 작성자의 대응은 넣지 않는다.
   - 차수별 원문은 `review-records/`에 보존한다.

## 다음 검토 뒤 (참고)
- **pass**: PRE-REVIEW 이력에 옮기고, 진단 뒤 전체 검토이므로 continuity는 `changed`로 적는다.
- **fail**: 진단 뒤 첫 fail이라 종료 0과 `ask_user` 단계가 열린다.
  - A 밖이면 PM이 `--decision --by pm`으로 기록한다.
  - A에 해당하면 6요소를 갖춰 허브를 거쳐 owner에게 요청하고 회신을 기다린다.
- **사후 보고**: TASK-CLOSE 리뷰 절과 C의 사후 요약에 4요소를 적는다. 무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과다.

## 필요한 회신·보고

- 허브 판단 중 A에 걸리는 조치가 나오면 그 건만 owner 결정 대기로 바뀐다.
