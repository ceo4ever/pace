**사례: 2차 재검토 결과가 등급 없이 서술형으로 왔을 때**

**담당**
- 워크트리 PM이 처리한다. 허브 에스컬레이션은 연속 fail이 3회가 되거나, 같은 절차·열람 지적이 두 번 이어질 때만 한다.
- 직전 지적 2가 blocking이었다면, 부분 해소는 해소가 아니다. 남은 부분은 여전히 blocking이다.

**순서**
1. 원문을 이번 차수 고유 증거 경로(`review-records/` 또는 `evidence/`)에 그대로 보존한다.
   - 보존 전에 비밀·민감정보를 검사한다.
   - 요약이나 추정으로 복원하지 않는다.
2. 이 재검토가 `pace agent verify`의 자동 재검토(`rereview_of` 있음)로 받은 것인지 확인한다.
   - 도구 밖 판정이면 원장에 남지 않는다.
   - 그 경우 `verify`로 다시 받는다.
3. 서술에 등급이 없으므로 PM이 임의로 낮추지 않는다. 같은 reviewer에게 반환 형식(`판정`, `F# [등급]`)으로 등급을 다시 받는다. 불확실한 결함은 낮은 등급으로 내리지 않는다.
4. 재검토의 범위 규칙(reviewer.md:49)에 따라 네 항목을 나눈다.

   | 항목 | 처리 |
   |---|---|
   | 지적 1 해소 | 종결로 기록한다. |
   | 지적 2 부분 해소 | 남은 부분을 blocking으로 보고 수정한다. |
   | 바뀐 줄에서 생긴 새 문제 | 재검토 범위 안이므로 수정 대상이다. 등급은 reviewer가 매긴다. |
   | 바뀌지 않은 절의 새 지적 | note로만 남긴다. 이번 판정·수정 대상이 아니다. |

   - 바뀐 줄 목록은 새 문제가 정말 바뀐 줄에서 나왔는지 대조하는 데 쓴다.
   - 바뀐 줄 밖이면 note로 내린다.
   - 이 note를 근거로 범위를 넓히지 않는다.
5. 수정 직전에 조치가 합의된 목적·범위·기준을 바꾸는지 A-1로 대조한다.
   - 바뀌면 허브를 거쳐 질문한다.
   - 바뀌지 않으면 PM이 결정하고 근거를 남긴다.
6. blocking 2건(지적 2의 남은 부분, 새 문제)을 수정한다.
   - 수정 뒤 `verify`를 다시 호출해 자동 재검토를 받는다.
   - 수정 위치와 처리 이력을 TASK-CLOSE와 review 로그에 증거 경로로 연결한다.
   - 지적마다 등급·내용·근거, 반영 여부와 이유, 수정 위치를 적는다.
7. 연속 fail이 3회가 되어 `escalation`이 붙으면 [반복 실패 절](skills/pace-project-dev/references/reviewer.md)을 따른다.
   - 근거와 진단을 허브에 보내 B로 근본 조치를 정한다.
   - 진단 뒤 첫 verify는 전체 검토다.

**기록 명령**
- `pace project log`에 검토 차수, 지적별 처리, 연속 fail 수를 남긴다.
- 필요하면 `pace agent review-note`를 쓴다. 이번 단계에서는 `--diagnosis`나 `--decision`은 쓰지 않는다.
- 이번 시험에서는 실제로 실행하지 않는다.

**회신·보고**
- reviewer에게: 등급 재요청, 수정 뒤 재검토 요청.
- 허브에게: 지금은 보고할 것이 없다. 3회 fail이나 A 해당 시에만 보고한다.
- 사후 요약(C)에 "무엇이 반복됐는지·고친 층·채우거나 덜어낸 것·재검증 결과"를 남긴다.
- 바뀌지 않은 절의 note는 handoff나 TASK-CLOSE "남긴 것"으로 넘긴다.

**질문·승인 대기**
- 질문 0건, 승인 대기 0건이다.
- A에 걸리는 조치가 나오면 그때만 허브를 통해 질문한다.

  - `skills/pace-project-dev/SKILL.md` 1–93줄 전체.
