**시나리오 답변 (실행 없음, 읽기만 함)**

**담당:** 워크트리 PM(나)이 직접 결정한다. `decision-rights.md` A-1~A-5를 실제 조치에 대조하면 모두 "아니오"다.
- 합의된 목적·기준·범위는 그대로이고 검증만 강화한다(A-1 아니오).
- 로컬 fixture 보완이라 외부 영향이나 되돌릴 수 없는 일이 없다(A-2 아니오).
- 보안 검사·독립 검토를 생략하거나 약화하지 않는다(A-3 아니오).
- 새 권한, 비밀 노출, 비용이 없다(A-4 아니오).
- 사람만 할 수 있는 확인이 필요 없다(A-5 아니오).

따라서 사용자나 허브에 결정을 묻지 않는다. `ask_user`는 호환용 단계 이름일 뿐이고, 필요한 결정 기록을 먼저 남기면 된다(`reviewer.md` 반복 실패 절).

**순서와 실제 명령·기록:**
1. 종료 0과 `ask_user` 신호를 받은 그 호출에서 바로 대응한다. 아직 기록되지 않은 단계에서 `verify`를 다시 부르면 종료 16으로 막힌다.
2. 수정 직전에 합의(PROJECT.md·TASK.md)와 조치의 영향을 대조한다. 결과는 "합의 변경 없음, 기준 유지, 검증 강화"다.
3. `evidence/`에 근거 파일을 쓴다. 내용은 분류 이유(A 전부 아니오)와 근본 조치(fixture 갭 보완)다.
4. 아래 명령으로 기록한다.
   `pace agent review-note --target <대상> --decision --by pm --choice <선택> --summary <사유> --file <근거>`
   - `--by`는 pm이다. user로 적지 않는다.
   - PM 결정은 waiver가 아니다. 사전 검토 단계라면 현재 TASK 해시에 대한 pass를 받아 PRE-REVIEW에 연결해야 한다.
5. 로컬 fixture를 보완한다. 범위를 넓히거나 기준을 낮추지 않는다.
6. 같은 대상에 `pace agent verify`를 다시 호출해 전체 재검증을 받는다. 도구 밖 reviewer로 경로를 바꾸지 않는다.
   - pass(blocking 0)면 진행한다. 그 판정은 목표 달성 확인을 대신하지 않으므로 goal-review 판정은 따로 한다.
   - 같은 영역이 또 지적되면 원인 층(structure/planning/design/other)을 다시 진단한다.
7. 검토 차수마다 원문을 `review-records/`에 보존하고, `pace project log`에 결정·근거를 남긴다.

**회신·보고:**
- 사용자 수정 전 보고(6요소)는 하지 않는다. 이 경로는 PM 경로다.
- TASK-CLOSE 리뷰 절과 C의 사후 요약에 4요소를 남긴다: 무엇이 반복됐는지 / 고친 층 / 채우거나 덜어낸 것 / 재검증 결과.
- 허브에는 진행 상황만 알린다. 결정을 요청하는 것이 아니다.

**대기 수:** 질문 0건, 승인 대기 0건. 독립 작업은 멈추지 않는다.

**자동 첨부와 읽은 범위:**
- 자동 첨부: 있었다. 사용자 계정 식별 정보(이메일)이며 값은 적지 않는다. 외부로 보내지 않았다.
- `skills/pace-project-dev/SKILL.md`: 1~92줄 전체
- `references/reviewer.md`: 1~125줄 전체
- `references/decision-rights.md`: 1~45줄 전체
- 전체 바이트는 도구로 확인하지 않아 적지 않는다.
- 다른 사례의 파일은 읽지 않았다.
