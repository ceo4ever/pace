**사례: 선택 결과 제거 변경에서 PROJECT.md와 BR의 필수 결과 문장 해석이 갈릴 때**

**담당**
- 담당은 워크트리 PM(태스크 수행자)입니다. 허브는 owner 요청을 전달할 때만 나섭니다.
- 이 결정은 A-1(합의 변경) 판정입니다. 영향이 불분명하면 먼저 PROJECT.md·BR과 실제 결과를 대조하라고 되어 있습니다(`decision-rights.md` A-1).

**순서**
1. 해당 변경만 보류합니다. 별개 태스크는 계속 진행합니다(SKILL §6).
2. 읽기 전용으로 대조합니다. 대상은 PROJECT.md의 목적·기준 `P-n`, BR의 필수 결과 문장, 그리고 변경 전후의 실제 결과입니다. 제거되는 결과가 필수 결과인지, 기준 `P-n`에 묶이는지 확인합니다.
3. 대조 결과로 갈립니다.
   - **영향 없음이 확인되면**: PM이 결정합니다. 근거를 `pace project log`에 `자체 판단`으로 남깁니다. 변경 후 finish 뒤의 자체 판단 대조와 완료 보고(C 사후 요약)에 한 줄 넣습니다. owner 질문은 0건입니다.
   - **필수 결과 축소로 확인되거나, 대조 뒤에도 가릴 수 없으면**: A-1로 owner에게 요청합니다. 워크트리 작업자는 `ask`로 허브에 인계하고, 허브가 owner에게 보냅니다. 요청에는 A-1 번호, 대상과 근거, 선택지, 추천과 이유를 담습니다. 선택지는 (a) 문장을 BR 쪽으로 해석해 결과를 유지, (b) PROJECT.md 쪽으로 해석해 제거, (c) 두 문서를 합의 변경으로 정정하는 것입니다.

**실제 명령·기록**
- 대조는 파일 읽기뿐이라 수정하지 않습니다.
- 결정과 근거는 `pace project log`로 기록합니다. 형식은 `references/commands.md`를 확인해 따릅니다.
- 문서를 고치게 되면 커밋 전에 `pace backlog refresh`를 실행합니다.
- 승인 근거는 프로젝트 내부 근거 파일에 원문·출처·대상·범위로 연결합니다. 참여 소통 원장을 쓰는 프로젝트라면 `decision_request`와 `decision_reply`로 묶습니다.

**회신·보고**
- owner 회신이 오면 승인 원문과 조치 대상을 다시 대조한 뒤 변경을 진행하거나 취소합니다.
- 회신 전에는 해당 변경을 시작하지 않습니다.
- 허브에는 보류한 조치와 계속하는 독립 태스크를 보고합니다.

**질문·승인 대기 수**
- 대조로 영향 없음이 확인되면 질문 0건, 승인 대기 0건입니다.
- 불분명하거나 필수 결과 축소로 확인되면 질문 1건(A-1 한 건으로 묶음), 승인 대기 1건입니다. 대기하는 것은 해당 변경뿐입니다.
- 어느 쪽이든 별개 태스크는 막히지 않습니다.

**첨부·읽은 범위**
- 사용자 컨텍스트(`userEmail`)가 자동 첨부됐고, 값은 쓰지 않습니다.
- `skills/pace-project-dev/SKILL.md`는 1~92행(파일 끝까지)을 읽었습니다.
- `references/decision-rights.md`는 1~46행(전체)을 읽었습니다.
- 다른 references와 다른 사례의 문서는 읽지 않았습니다.
- 전체 바이트는 도구로 확인하지 않아 적지 않습니다.
