**이 시험에서 한 일**
- 자동 첨부는 있었다. 사용자 계정 정보가 시스템 컨텍스트로 붙었고, 값은 적지 않는다.
- 읽은 파일은 4개다. 전체 읽기는 줄 범위가 곧 전체이고, 전체 바이트는 측정하지 않았다.
  - `skills/pace-project-dev/SKILL.md` 1–92
  - `references/cross-verify.md` 1–9
  - `references/task-steps.md` 1–11
  - `references/decision-rights.md` 1–45
- 파일 수정, 질문, 메모리 기록, 커밋, 전송은 하지 않았다. 다른 사례의 문서도 읽지 않았다.

**공통 전제**
- 먼저 다른 제공자를 시도했고 호출이 불가능했다. 이는 B1 대체 조건이다. A-3 판정은 "아니오"다.
- 그래서 사용자에게 묻지 않고, 승인도 기다리지 않는다. 질문 0, 승인 대기 0이다.

**사례 1. TASK 구현 전 검토**
- **담당**: 워크트리 PM이 reviewer를 배정한다. 작성자는 워크트리 PM이다.
- **실행**:
  1. 다른 제공자 호출 실패의 이유와 미실행을 기록한다.
  2. 같은 제공자의 새 세션으로 `pace agent verify --author-agent <claude|codex> --target <TASK.md> --purpose-file <상위 목적 글> --out <기록> --allow-same-provider`를 실행한다. 호스트에 별도 새 세션 기능이 있으면 그것을 써도 된다.
  3. 결과에 `cross: false`를 기록한다.
  4. 구현은 pass(blocking 0)이거나 사용자 결정 waiver가 있을 때만 한다. blocking은 수정하고 `verify`를 다시 호출한다.
  5. should_fix는 반영 여부와 이유를 항목마다 남긴다.
  6. 대상, 판정, 지적 처리, 검토 방식(`cross: false`)을 TASK 기록에 남긴다.
- **회신·보고**:
  - 연속 fail로 `escalation`이 붙으면 반복 실패 절차를 따른다.
  - 목적이나 범위 변경은 §6으로 올린다.
  - 허브에는 보고하되 승인은 요청하지 않는다.
- **주의**: 같은 제공자 검토를 다른 제공자 검토인 것처럼 적지 않는다. 검토가 한 번도 실행되지 않았다면 waiver 근거가 성립하지 않는다.

**사례 2. 백로그 검토**
- **담당**: 백로그 작성자의 PM이다. 허브와 워크트리 중 누구인지는 파일에서 확인되지 않는다.
- **실행**: 사례 1과 같다. 다만 `--target`은 BACKLOG 문서로 한다. `--purpose-file`은 상위 목적 글로, 상위 목적 우선 검토를 유지한다.
- **기록**: `cross: false`와 미실행 사유를 남긴다.
- **회신·보고**: 지적마다 반영 여부와 이유를 남긴다. 목표·전략 이견은 실제 조치가 합의를 바꾸는지 A-1로 판정한다. 백로그 원본 문서를 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행한다. 커밋은 이 시험에서 하지 않는다.

**사례 3. 둘 다 호출할 수 없을 때** (다른 제공자와 같은 제공자 새 세션 모두 불가)
- 검토를 생략하거나 대체하지 않는다. A-3은 "예"다.
- 검토 관문, 즉 구현 착수나 백로그 확정은 보류한다. 독립 작업은 계속한다.
- 워크트리 작업자는 `ask`로 허브에 인계한다. 허브는 owner에게 C의 결정 요청을 보낸다. 요청에는 다음을 담는다.
  - A-3 번호
  - 대상과 근거
  - 선택지
  - 추천과 이유
- 원장을 쓰는 프로젝트는 `decision_request`(`to: owner`)를 쓴다.
- 질문 1, 승인 대기 1이다.
- owner 회신 뒤에도 게이트 요건과 현재 계약을 다시 확인한다. 검토가 한 번도 실행되지 않았다면 PRE-REVIEW waiver 근거는 성립하지 않는다.
- 필수 결과가 여전히 미확인이면 보완 관측 또는 적법하게 변경된 계약으로 다시 판정한다.
