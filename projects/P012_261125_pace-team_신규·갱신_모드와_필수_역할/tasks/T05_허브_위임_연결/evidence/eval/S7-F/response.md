## 사례 1: normal 단계, 구간의 fail이 `interrupted` 1건뿐

- **담당**: 워크트리 PM이 직접 처리한다. 허브 보고, 진단, 사용자 결정은 필요 없다.
- **판단 근거**
  - 중단 복구는 연속 fail 집계에 들어가지만 실제 blocking과는 다르다.
  - 중단 복구만 남아 있고 단계가 normal이면 다음 검토는 전체 검토다(`reviewer.md` "단계 읽기").
  - 1건이라 `escalation`은 없다.
- **실제 명령**: `pace agent verify`를 같은 대상, 같은 경로로 다시 호출한다.
  - 도구 밖 reviewer로 바꾸지 않는다.
  - purpose는 상위 목적과 판정 기준만 넣고, 이전 지적이나 자체 판정은 넣지 않는다.
- **기록**
  - `pace project log`에 대상, 제공자, 결과를 남기고, 중단 복구 1건은 blocking과 구별해 적는다.
  - PRE-REVIEW를 옮겨 적을 때는 `interrupted` 항목을 시도로 옮기지 않고 횟수와 보고에만 반영한다.
- **회신·보고**: 이 시점에는 없다. 결과가 fail이면 지적을 반영하고 verify를 다시 부른다.
- **질문 0 · 승인 대기 0**

## 사례 2: 중단 복구가 3회가 되어 종료 16, `diagnose`

- **담당**: 워크트리 PM이 근거를 정리해 허브에 보낸다. 근본 조치는 허브가 B로 정한다.
- **하지 않을 것**
  - verify를 다시 호출하지 않는다. 기록되지 않은 단계에서 다시 호출하면 종료 16으로 차단된다.
  - `--void`를 쓰지 않는다. diagnose 단계와 중단 복구는 void 대상이 아니다.
  - `review-note --decision`을 쓰지 않는다. decision은 `ask_user` 단계에서만 쓴다.
  - 지적별로 땜질하지 않는다.
- **순서**
  1. 3회의 중단 원문과 오류 문구를 모은다. 실제 blocking이 아니라 실행 중단이 반복됐으므로 원인 층은 대개 `structure`(도구나 검토 방식)로 본다. 근거로 확정하고, 다르면 해당 층을 쓴다.
  2. 근거와 진단을 허브에 보낸다(B). 이 보고는 사실상 1건이다.
  3. 근본 조치를 A로 대조한다. A 밖이면 PM이 결정하고 진단 증거를 남긴다. A에 걸리면 허브를 거쳐 owner 결정을 받은 뒤 적용한다. 이 경우에만 승인 대기가 생긴다.
  4. `evidence/`에 진단 증거 파일을 쓰고, 승인 원문이 있으면 그 위치를 연결한다.
- **실제 명령**
  - `pace agent review-note --target <대상> --diagnosis --layer structure --summary "<진단·조치>" --file <진단 증거>`
  - 기록 직후는 normal이다. 확정한 조치를 적용하고 `pace agent verify`로 새 기준 전체 검토를 한다. 이전 지적으로 purpose를 좁히지 않는다.
  - `pace project log`에도 진단을 기록한다.
- **회신·보고**
  - 사후 보고는 4요소로 TASK-CLOSE 리뷰 절과 C의 사후 요약에 남긴다. 4요소는 무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과다.
  - 재검증의 결과도 같이 보고한다.
- **질문과 승인 대기**
  - 질문은 0건이다. 허브에 보내는 근거 보고는 1건이다.
  - A 밖이면 승인 대기는 0건이다. A에 걸리면 owner 결정 1건을 기다린다.
