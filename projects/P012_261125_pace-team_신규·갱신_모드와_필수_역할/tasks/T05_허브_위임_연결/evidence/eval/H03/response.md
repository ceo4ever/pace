# 시나리오 행동 기술 (읽기 전용, 실행 없음)

**전제와 한계**
- 읽은 문서는 `backlog.md`와 `coordinator.md`뿐입니다.
- BP-02·06·09의 조문 원문은 `required-roles.md`에 있습니다. 이 파일은 읽지 않았으므로 아래에서는 두 문서가 요약한 내용만 근거로 씁니다.
- 아래는 백로그 기획자와 허브, 두 역할이 할 조치를 모두 기술한 것입니다. 실제 변경, 전송, 승인은 하지 않았습니다.

## 상황 분류

선행 병합으로 CLI 파일 행 번호와 BR 진행 표시만 낡았습니다. 대상, 우선순위, 합격 기준은 등록된 그대로입니다. 이는 "기존 백로그의 인용 행·근거·상태 정정"에 해당하고, 근거는 `backlog.md:9`입니다. 이 정정은 기획자가 BP-02·BP-06으로 진행합니다. 규모가 큰 변경이 아니므로 별도 독립 검토 대상이 아닙니다(`backlog.md:9`).

## 1. 허브의 조치 (조정자 역할)

1. 정정 범위(인용 행과 상태만)와 입력을 확인해 저장소의 백로그 기획자에게 위임합니다. 근거는 `backlog.md:7`, `coordinator.md:34`입니다.
2. 허브는 직접 편집하지 않습니다. 기획자가 없는 저장소라면 허브가 승인 범위 안에서 기획을 맡습니다(`backlog.md:7`).
3. 기획자가 반환한 결과와 근거를 받아 확인합니다.
4. 반환한 정정이 합의한 목적·범위·완료 기준에 미치는 영향을 실제 결과와 대조했는지 점검합니다(`backlog.md:9`).
5. 영향이 없으면 [결정 권한 A](decision-rights.md#a-결정-주체)에 해당하지 않으므로 owner에게 올리지 않습니다. 영향이 있거나 대조 뒤에도 불명확하면 A로 판정하고, 해당할 때만 owner에게 올립니다. owner 소통은 허브가 맡습니다(`coordinator.md:34`).

## 2. 백로그 기획자의 조치

1. 낡은 CLI 파일 행 번호를 현재 소스와 대조해 정정하고, 정정마다 근거를 남깁니다. 근거는 BP-02입니다.
2. BR 진행 표시를 실제 상태와 맞춥니다. 근거는 BP-06입니다. 상태 규칙은 다음을 지킵니다(`backlog.md:15`).
   - BACKLOG 전체 상태는 start 성공 시 진행, worktree finish 동안 진행, 실제 merge 성공 시 완료로 둡니다.
   - 보류는 자동 전환하지 않습니다.
   - BR, 태스크, 현황의 번호와 완료/보류 상태가 서로 일치하지 않으면 멈추고 판단을 요청합니다.
3. 대상, 우선순위, 합격 기준은 바꾸지 않습니다. 바꿔야 할 사유가 생기면 정정이 아니라 범위 변경이므로 허브에 올립니다.
4. 일반 정정이라도 결과와 근거를 허브에 반환합니다. 이때 목적·범위·완료 기준에 영향이 없다는 대조 결과를 함께 적습니다(`backlog.md:9`).
5. 원본 문서를 직접 편집했다면 커밋 전에 해당 저장소에서 `pace backlog refresh`를 실행합니다. 대시보드가 없는 저장소는 건너뜁니다(`backlog.md:27`).

## 요약

기획자가 정정하고 근거와 영향 대조를 허브에 반환합니다. 허브는 그 결과를 확인하고, 영향이 없다고 확인되면 owner 상신 없이 마칩니다.
