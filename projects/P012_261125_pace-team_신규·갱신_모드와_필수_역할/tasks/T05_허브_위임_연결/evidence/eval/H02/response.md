# 행동 시나리오: 기존 백로그 최신화 (읽기 전용 설명)

실제 변경·전송·승인은 하지 않았고, 아래 파일만 읽었습니다.
- `skills/pace-project-dev/references/backlog.md` (이하 backlog.md)
- `skills/pace-project-dev/references/coordinator.md` (이하 coordinator.md)
- `.pace/team/agents/pace-backlog-planner.md` (기획자 원본)
- `skills/pace-project-dev/references/decision-rights.md` (A 판정 기준. backlog.md와 coordinator.md가 링크로 가리킵니다.)

`required-roles.md`의 BP 정본은 열지 않았습니다. BP 번호는 위 문서가 인용한 내용만 근거로 씁니다.

## 역할 구분

- **허브 PM**은 main 코디네이터입니다. 범위를 확인해 기획자에게 위임하고, 반환을 받아 A로 판정하며, owner 소통을 맡습니다 (backlog.md:7, coordinator.md:34).
- **백로그 기획자**는 maker입니다. 허브의 main 쪽에서 일하며 정정 작업과 근거 대조표 작성을 맡습니다 (기획자 원본:14, 16-26).
- 두 역할은 분리되어 있습니다. 기획자는 owner 결정을 대행하지 않고 결정 근거와 선택지만 허브에 보냅니다 (BP-08, 기획자 원본:32). 허브가 기획자의 일을 대신하는 경우는 기획자가 없는 저장소뿐입니다 (backlog.md:7).

## 순서

**1. 허브: 위임 전 확인 (backlog.md:7, BP-09)**
- 목적·범위와 기록의 쓰기 권한을 확인합니다.
- 기획자에게 owner 원문 인용, 확정 결정, 남은 질문을 넘깁니다 (기획자 원본:46).
- 입력에 "정정 범위 = 상태·행 번호"를 명시합니다. 최초 제공 범위 확대는 남은 질문으로 따로 표시합니다.

**2. 기획자: 실행 전 대조 (기획자 원본:36-42)**
- 위임 지시가 근거와 같은 범위인지 확인합니다. 상태·행 번호 정정은 요청받았으므로 진행합니다.
- 범위 확대 항목은 요청받지 않았습니다. 이 항목은 실행하지 않고 보류하며, 미확인 해석을 승인된 것으로 바꾸지 않습니다 (기획자 원본:38).

**3. 기획자: 정정 (BP-02, BP-06, backlog.md:9)**
- 현재 main에서 인용 파일·행, 심볼, CLI 옵션, 선행 프로젝트 병합 상태를 각각 확인합니다 (BP-02).
- 근거마다 확인·낡음·미확인과 직접 확인한 위치를 적고, 낡은 사실은 실제 근거로 갱신합니다.
- BACKLOG.md 진행 현황과 BR 상태를 함께 확인합니다 (BP-06).
- 갱신 뒤 `pace intent check`로 관련 원본을 검사하고 `pace backlog refresh`로 현황을 다시 만듭니다 (BP-06).
- 완료 백로그는 편집하지 않습니다 (BP-08). `INDEX.md`와 `index.md`는 직접 편집하지 않고 재생성합니다.
- 프로젝트 착수와 커밋·푸시도 하지 않습니다 (BP-08).
- 원본 문서를 직접 편집했다면 `pace backlog refresh`도 실행합니다 (backlog.md:27).

**4. 기획자: 반환 (BP-09, backlog.md:9)**
- 일반 정정의 결과와 근거도 허브에 반환합니다.
- 반환물은 근거 대조표(확인·낡음·미확인), 백로그 간 점검표, BR 분량 비교입니다.
- 합의한 목적·범위·완료 기준에 미치는 영향을 실제 결과와 대조해 함께 적습니다.
- 범위 확대 건은 owner용 질문으로 정리합니다. 선택지, 추천, 이유를 `HANDOFF: 허브 PM | 결정 | 근거` 형식으로 보냅니다 (기획자 원본:48).

**5. 허브: A 판정 (backlog.md:9, decision-rights.md A)**
- 일반 정정은 합의를 바꾸지 않으므로 A에 해당하지 않습니다. 허브는 반환을 확인하고 닫습니다.
- 범위 확대 건은 확정된 최초 제공 범위를 바꾸므로 **A-1(합의 변경)**에 해당합니다. 영향이 불분명하면 먼저 PROJECT.md·브리프와 실제 결과를 대조하고, 대조 뒤에도 불명확하면 A-1로 요청합니다.
- 이 판정은 허브가 합니다. 기획자는 결정을 대행하지 않습니다 (BP-08).
- 결정 대기 동안 해당 조치만 보류하고 독립 작업은 계속합니다 (decision-rights.md:7).

**6. 허브: owner 요청 (decision-rights.md C)**
- 요청에는 A-1 번호, 대상과 근거, 선택지, 추천과 이유를 담습니다.
- owner에게 가는 질문은 코디네이터가 직접 보냅니다 (coordinator.md:34).
- 참여 소통 원장을 쓰는 프로젝트라면 `decision_request`(`to: owner`)를 사용합니다. 원장을 쓰지 않으면 프로젝트 내부 근거 파일에 원문과 출처를 연결합니다 (decision-rights.md:29-30).
- 실제 사용자 답이 있어야 도달로 셉니다 (coordinator.md:57). 로그에 owner를 적은 것만으로는 도달이 아닙니다.

**7. owner 답 이후**
- 승인되면 그 범위만큼 기획자에게 정정을 위임하고 3~4단계를 반복합니다.
- 규모가 큰 변경이 되면 별도 독립 검토로 보냅니다 (backlog.md:9, coordinator.md:34). 작성자와 다른 reviewer를 쓰며 다른 제공자를 우선합니다. 검토 지적은 BP-07·BP-08에 따라 기획자에게 전달합니다.
- 반려되면 기존 범위를 유지하고, 결정 근거를 기록에 남깁니다.

## 허브가 하지 않는 일

- 범위 확대를 "상태 정정의 연장"으로 보고 기획자가 임의로 반영하게 두지 않습니다.
- 낡은 행 번호를 추정으로 채우지 않습니다. 직접 확인하지 못한 항목은 "미확인"으로 남깁니다.
