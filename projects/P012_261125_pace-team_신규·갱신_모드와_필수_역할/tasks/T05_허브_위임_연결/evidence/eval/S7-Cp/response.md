# 3차 fail, diagnose 단계: 행동 순서

**자동 첨부와 읽은 범위**
- 자동 첨부는 사용자 계정 정보 컨텍스트 1건이다. 값은 쓰지 않으며 이 사례에서 쓰지 않는다.
- 읽은 파일은 세 개다.
  - `skills/pace-project-dev/SKILL.md` 1–93줄(전체)
  - `references/reviewer.md` 1–125줄(전체)
  - `references/decision-rights.md` 1–45줄(전체)
- 다른 사례의 응답, 평가표, TASK, 마감 문서는 읽지 않았다.
- 전체 바이트는 도구로 확인하지 않았으므로 적지 않는다.

**담당:** 워크트리 PM이 진단과 증거 정리를 맡는다. 허브 PM은 B 절차와 owner 요청 전달을 맡고, owner는 A-1 결정을 한다. 이 PM은 owner에게 직접 묻지 않는다.

**순서**
1. 3차 fail을 기록한 verify 출력의 `escalation.stage: diagnose`를 확인한다. 아직 `verify`를 다시 부르지 않는다. 다시 부르면 종료 16으로 차단된다. 이 시점은 `review-note --decision` 단계도 아니다.
2. 세 차수의 `review-records/R<n>.json` 원문과 차수별 blocking을 모은다. 지적별 땜질은 멈춘다.
3. 원인 층을 `design`으로 가린다.
   - 근거는 이미 합의한 macOS 환경에 Windows 설계(PATH, 서비스 등록, 종료 방식)를 옮겨 여러 지적이 난 것이다.
   - 환경 결정 자체가 틀린 것은 아니므로 `planning`이 아니다.
   - 진단 문서는 `evidence/diagnose-<대상>.md`에 쓴다. 내용은 실패 원문, 차수별 blocking, 층 판정, 근본 조치(macOS 기준 설계 재작성)다.
4. 조치 전에 A로 분류한다. 근본 조치가 합의 범위를 바꾸므로 **A-1은 "예"**이고, 이 조치만 보류한다. PM이 자체 결정하거나 `--by pm` 결정으로 처리하지 않는다. 범위와 무관한 독립 작업은 계속한다.
5. 허브에 `ask`로 인계한다. 아래 6요소와 A-1 번호를 붙이고, 허브가 C 형식으로 owner에게 요청한다.
   - 대상
   - 실패 추이(3회 연속 fail, 차수별 blocking 수)
   - 진단과 고칠 층(design)
   - 남은 지적의 성격(Windows 설계 이식에서 나온 공통 원인)
   - 선택지(범위를 바꿔 macOS 기준으로 재설계, 범위 유지 등)
   - 추천과 이유
6. `pace project log`로 진단과 A-1 보류, 허브 인계를 기록한다.
7. owner 회신을 기다린다. 이 사례에서 **질문은 허브 경유 1건, 승인 대기는 1건**이다.
8. 회신이 오면 승인 원문과 현재 대상을 대조한다. 원문이 없거나 조건·대상이 다르면 입력을 보류하고 다시 요청한다. 맞으면 승인 원문 위치나 영수증을 진단 증거에 연결한다. diagnose 단계에서는 decision 대신 이 연결을 쓴다.
9. 다음 명령으로 진단을 기록한다.
   `pace agent review-note --target <대상> --diagnosis --layer design --summary "<진단·조치>" --file evidence/diagnose-<대상>.md`
10. 승인된 범위 변경과 macOS 기준 설계 재작성을 적용한다. PROJECT.md와 TASK.md의 합의 문서도 함께 맞춘다.
11. `pace agent verify`를 다시 부른다. 이것은 새 기준 **전체 검토**이며 이전 지적으로 purpose를 좁히지 않는다.

**필요한 회신과 보고**
- 허브에는 ask(6요소)를 보내고 허브 회신은 `(main 판단)`으로 기록한다.
- 사후에는 4요소(무엇이 반복됐는지, 고친 층, 채우거나 덜어낸 것, 재검증 결과)를 TASK-CLOSE 리뷰 절과 C의 사후 요약에 남긴다.
- 사용자 경로이므로 승인 직전 대상 해시와 승인 뒤 첫 수정 기록도 연결한다.
- 재검증에서 새 위험이 나오면 수정 전에 다시 A로 분류한다.

**경계**
- 파일 수정, 질문, 메모리 저장, 커밋, 전송은 이 시험에서 하지 않았다. 위는 계획일 뿐이다.
- PRE-REVIEW `waiver`는 이 단계에 쓰지 않는다.
- 승인 전에 범위 변경 수정을 하지 않는다.
- 검토 pass가 나와도 목표 달성 판정은 따로 한다.
