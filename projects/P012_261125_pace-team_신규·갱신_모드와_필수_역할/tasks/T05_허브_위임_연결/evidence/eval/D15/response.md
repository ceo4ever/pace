**자동 첨부와 읽은 범위**
- 시스템 리마인더로 사용자 이메일이 자동 첨부됐다. 값은 적지 않는다.
- `skills/pace-project-dev/SKILL.md`를 1–93줄 전체 읽었다.
- `references/decision-rights.md`를 1–46줄 전체 읽었다.
- 그 밖의 파일은 열지 않았다. 전체 바이트 수는 도구로 확인하지 않아 적지 않는다.

**이 사례의 순서**

1. **담당**
   - 허브 PM이 맡는다. 같은 세션이 허브와 워크트리 역할을 겸하면 그 자리에서 수행한다.
   - 근거는 decision-rights B-3과 S1 위임이다. 작은 도구·하네스 결함은 허브가 결정해 수정한다.
   - A-2는 S1 위임에 해당하므로 "아니오"다. owner에게 물을 필요가 없다.

2. **먼저 확인할 것**
   - A-3: 수정이 필수 검사나 독립 검토를 약화하는지 본다. 이 사례는 같은 필수 검사를 그대로 수행하므로 "아니오"다.
   - A-1: 병합 대기 프로젝트의 합의와 기준에 영향이 없는지 본다.
   - 장애를 허브가 저장소에서 확인한 방법으로 재현한다. 작업자의 escalation에 있는 재현 조건과 증거 원문을 확인한다.

3. **실제 명령과 기록**
   - main에는 커밋하지 않는다. 병합 대기 중 main 커밋은 병합 뒤로 미룬다는 ✋ 규칙(SKILL §4)과 B-3에 따른 것이다.
   - 격리한 도구 사본(저장소 밖)에서 결함을 재현하고 수정한다. 같은 필수 검사를 수행한다. 이 사본은 기존 게이트와 검증 대상을 건드리지 않는다.
   - 병합 대기 프로젝트는 기존 도구로 그대로 병합한다. 허브가 main에서 `pace project merge P###`를 실행하고, 미리보기 커밋 전체 SHA와 owner 승인 원문을 대조한 뒤 `--yes`를 입력한다. 승인 원문이 없거나 대상이 다르면 입력을 보류하고 승인을 요청한다.
   - 병합 뒤에 도구 수정을 main에 커밋한다. 필요하면 재설치한다.
   - 결정과 근거는 `pace project log`로 "(main 판단)"으로 기록한다.
   - 메모리 파일은 갱신하되 그 커밋은 병합 뒤로 미룬다.

4. **회신과 보고**
   - 장애를 보고한 작업자에게 결정, 근거, 재검증 기준을 회신한다. 막힌 조치만 보류하고 독립 작업은 이어간다.
   - 작업자는 회신을 `(main 판단)`으로 기록하고, 적용 뒤 재검증해서 태스크를 재개한다.
   - 허브 회신, 워크트리 적용, 재검증을 마치면 공동 시도 1회다. 상한은 2회다.
   - owner에게는 사후 요약 한 줄로 "되돌릴 수 있는 PM 결정: 격리 사본에서 수정·검증, main 커밋은 병합 뒤로 미룸"을 붙인다. 별도 결정 요청은 아니다.

5. **질문과 승인 대기 수**
   - 도구 수정 자체의 질문은 0건, 승인 대기도 0건이다.
   - 병합 승인은 별개다. 이미 받은 owner 승인이 대상에 맞으면 재사용하므로 추가 질문은 0건이다. 승인이 없을 때만 병합 건으로 1건 요청한다.

**경계**
- 병합 대기 중에 main에서 도구를 직접 고쳐 커밋하지 않는다.
- 검사나 검토를 생략하거나 약화하지 않는다.
- 푸시, 배포, 외부 전송은 하지 않는다.
- 이 시험에서는 실제 수정, 질문, 메모리 기록, 커밋, 전송을 하지 않았다.
