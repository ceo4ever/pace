**사례: worktree 작업자, T01 대기**

- **담당:** 워크트리 PM(이 세션)이 T01 전 단계를 자율로 맡는다. 구현 전 검토와 테스트의 reviewer·tester는 새 맥락의 별도 에이전트다. reviewer는 작성 PM과 다른 제공자를 우선한다. main에서 worktree 파일을 절대 경로로 고치지 않고, merge·푸시·배포도 하지 않는다. merge는 허브가 맡는다.

- **실제 명령·기록(순서):**
  1. **분석:** `pace project task P### "<표의 T01 이름 그대로>"`. 표의 `대기` 행과 이름이 같아야 같은 번호로 열린다. 그다음 TASK.md에 목적·재료를 쓰고, 앞 태스크가 없으므로 TASK-CLOSE의 "남긴 것"은 읽지 않는다.
  2. **설계:** 기준 `T-n`, 테스트 표(기준마다 시나리오 한 줄 이상), 접근을 쓴다. 기준 문서는 §5/standards.md로 고른다. 새 형식 TASK면 증명 범위·판정 주체도 먼저 쓴다.
  3. **구현 전 검토:** `pace agent verify`로 별도 reviewer에게 TASK.md를 검토받는다. pass(blocking 0)이거나 사용자 결정 waiver일 때만 구현한다. blocking은 고치고 `verify`를 다시 부른다. should_fix는 반영하거나 이유를 남긴다. 대상·판정·지적 처리·검토 방식은 태스크 기록에 남긴다.
  4. **구현:** 주변 코드 스타일을 따르고 안티패턴과 대조한다. 버그면 실패하는 테스트(RED)부터 쓴다.
  5. **테스트:** 저장소 검사 명령과 E2E를 돌리고, tester ∥ reviewer를 새 맥락으로 배정한다. 출력의 `escalation`을 먼저 따른다. 없으면 fail·blocking을 고치고 둘 다 다시 돈다.
  6. **마감:** TASK-CLOSE.md를 쓴다. 리뷰는 차수마다 한 줄, 교본 대조는 한 줄 적는다. 이어서 `pace project check P### T01`, `pace project done P### T01`, `pace memory status --project --body "<어디까지 · 다음 할 일 · 막힌 것>"` 순으로 실행한다. 마지막으로 `feat(P###/T01): …` 커밋 한 번에 TASK-CLOSE·상태·메모리를 함께 넣는다.
  7. 다음 `대기` 태스크가 있으면 이어서 진행한다. 모두 `완료`(또는 `보류`)면 PROJECT-CLOSE.md(목표 달성 판정 포함)를 쓰고 `pace project finish P###`를 실행한다. 실패하면 고치고 다시 실행하되 직전·직후에 같은 검사를 따로 반복하지 않는다. 통과하면 log.jsonl의 `자체 판단` 결정을 합의와 대조하고, 변경이 없으면 보고에 "대조: 변경 없음"을 적는다. 그다음 `worker_done`으로 끝낸다.
  8. 백로그·프로젝트 원본 문서를 직접 편집했다면 커밋 전에 `pace backlog refresh`를 실행한다.

- **회신·보고:** 완료 시 `worker_done` 보고에 사후 요약(PM이 정한 설계 선택·보류, 자체 판단 대조 결과)을 담는다. 장애나 같은 실패 3회는 근거와 함께 허브로 보낸다.

- **질문·승인 대기 수:** 현재 0. 착수 결정은 이미 확정된 것으로 보므로 승인 답을 기다리지 않는다. 다음 경우에만 `ask`로 허브에 인계하고 해당 조치만 보류한다. 독립 작업은 계속한다.
  - A-1: 합의된 목적·기준·범위가 바뀌는 경우
  - A-2: 되돌릴 수 없거나 외부로 나가는 조치
  - A-3: 검토·보안 검사를 생략하거나 약화하는 경우. 두 제공자가 모두 미실행이면 여기에 해당한다. 반대편 제공자를 호출할 수 없으면 `--allow-same-provider` 또는 같은 제공자의 새 세션으로 대체하고 `cross: false`로 기록한다.
  - A-4: 새 권한·새 계정·새 유료 비용
  - A-5: 사람만 할 수 있는 확인

  merge·배포는 사람 승인 뒤 허브가 실행한다.
