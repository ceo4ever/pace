**자동 첨부와 읽은 범위**
- 자동 첨부는 사용자 이메일 컨텍스트 1건이다. 파일에서 읽은 값이 아니고, 값은 쓰지 않는다.
- 읽은 파일은 세 개다.
  - `SKILL.md` 1–93줄(전체)
  - `references/reviewer.md` 1–125줄(전체)
  - `references/decision-rights.md` 1–45줄(전체)
- 전체 바이트는 도구로 확인하지 않았으므로 적지 않는다.
- 이 답변에서 수정·질문·메모리·커밋·전송은 하지 않았다.

**순서**

1. **신호 수신 (담당: 워크트리 PM)**
   - 3차 fail 호출이 종료 0과 `escalation.stage: diagnose`를 냈으므로 바로 대응한다. 아직 단계가 기록되지 않은 상태에서 `verify`를 다시 부르면 종료 16으로 막힌다.
   - 4차 `verify`나 PATH·launchd·종료 신호를 지적별로 땜질하는 수정은 하지 않는다.

2. **증거 모음 (담당: 워크트리 PM)**
   - `review-records/R1~R3.json` 원문과 차수별 blocking(PATH 누락, launchd 등록, 강제 종료 신호)을 확인한다.
   - 원문이 없으면 추정 복원하지 않고 그 한계를 적는다.

3. **원인 층 판정 (담당: 워크트리 PM)**
   - 층은 `design`이다. 합의된 환경이 처음부터 macOS였고, 거기에 Windows의 경로·등록·종료 방식을 적용한 것이 원인이기 때문이다.
   - 환경 결정 자체가 틀린 경우가 아니므로 `planning`이 아니다.
   - 판정 근거와 진단은 `evidence/`의 진단 파일에 쓴다.

4. **허브 인계 (담당: 워크트리 PM → 허브 PM)**
   - 세 차례 근거와 진단을 허브에 보내 B로 근본 조치를 정한다. 실제 환경 기준(macOS PATH, launchd, SIGTERM 계열 종료)으로 설계를 다시 쓰는 방향이다.
   - 허브는 회신에 결정·근거·재검증 기준을 담고, 작업자는 이를 `(main 판단)`으로 기록한다.

5. **조치 전 A 분류 (담당: 허브와 워크트리 PM)**
   - 이 조치는 설계를 실제 환경에 맞추는 것이다. 목적·기준(`P-n`)·범위는 그대로이고, 검토를 줄이지 않고, 외부 전송·새 권한·사람 확인도 없다. 그래서 A-1~A-5 모두 "아니오"다.
   - PM이 결정하고 근거를 기록한다.
   - 설계 재작성 중 실제 launchd 등록처럼 시스템에 영향을 주는 실행이 생기면, 그 시점에 A를 다시 분류한다.

6. **진단 기록 (담당: 워크트리 PM)**
   - `pace agent review-note --target <TASK.md 경로> --diagnosis --layer design --summary "<macOS 기준 재설계>" --file <진단 증거>`를 실행한다.
   - 이 호출 직후는 normal 단계다. `--decision`은 쓰지 않는다. 그건 이후 fail로 `ask_user`가 열린 뒤에만 쓴다.
   - `pace project log`에도 같은 내용을 남긴다.

7. **수정과 전체 재검증 (담당: 워크트리 PM, 검토는 reviewer)**
   - 수정 직전에 합의 대조를 한 뒤 TASK.md 설계를 macOS 기준으로 다시 쓴다.
   - `pace agent verify`를 다시 부른다. 진단 뒤 첫 검토는 새 기준 전체 검토다. 이전 지적으로 purpose를 좁히지 않고, 작성자의 자체 판정도 넣지 않는다.
   - 허브 회신 → 워크트리 적용 → 재검증이 공동 시도 1회이고, 상한은 2회다.

8. **결과에 따른 분기**
   - pass(blocking 0)이면 구현으로 간다.
   - fail이면 `ask_user` 단계가 열린다. 그때 조치를 다시 A로 분류한다.
     - A 밖이면 `--decision --by pm`으로 기록하고 전체 재검증한다.
     - A에 걸리면 6요소(대상·실패 추이·진단과 고친 층·남은 지적 성격·선택지·추천과 이유)를 붙여 수정 전에 허브를 거쳐 owner에게 요청한다.

9. **사후 보고 (담당: 워크트리 PM → 허브 → owner)**
   - 4요소(반복된 것·고친 층·채우거나 덜어낸 것·재검증 결과)를 TASK-CLOSE 리뷰 절과 사후 요약에 남긴다.

**대기 수**
- 질문 0건, 승인 대기 0건이다. 진단 단계의 조치는 A 밖이라 owner 승인을 기다리지 않는다.
- 허브 회신은 승인이 아니라 B 절차의 결정 회신이다.
- 8번에서 fail이 나오고 조치가 A에 걸릴 때만 owner 질문이 생긴다.
