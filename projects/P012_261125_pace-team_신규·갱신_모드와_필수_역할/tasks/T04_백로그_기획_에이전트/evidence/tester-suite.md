파일은 바꾸지 않았습니다. 셸 도구가 없어 SHA와 테스트는 다시 계산하거나 실행하지 못했습니다. 제출된 기록을 읽고 서로 대조한 결과입니다.

## 전체 검사: 네 번 시도, 세 번 실패, 한 번 통과

`whole-test.txt`에는 시도가 네 개 있습니다.

| 시도 | 명령 | tests | pass | fail | skip | 실패한 시험 |
|---|---|---|---|---|---|---|
| final | `npm run check` | 1390 | 1372 | 1 | 17 | 호출 프로세스 강제 종료 때 독립 감시자의 자식 그룹 회수 |
| confirm | `npm run check` | 1390 | 1372 | 1 | 17 | S-19d getUpdates 실패(409) |
| controlled | `typecheck && npm test -- --test-concurrency=4` | 1390 | 1372 | 1 | 17 | 실제 래퍼 SIGKILL 때 그룹 종료+free 뒤 CLI 회수 |
| **lowconc** | `typecheck && npm test -- --test-concurrency=2` | 1390 | **1373** | **0** | 17 | 없음 |

- **합계:** 1373 + 0 + 17 = 1390이 맞습니다. 앞의 세 시도도 1372 + 1 + 17 = 1390입니다.
- **유형 검사:** lowconc는 `tsc -p tsconfig.json`이 출력되고 오류가 없으며, `&&` 체인 뒤에 시험이 실행됐으므로 tsc가 성공한 것으로 추론됩니다. 종료 코드가 직접 기록된 것은 아닙니다.
- **시도 구분:** 최종 전체 검사 결과는 마지막 시도인 lowconc의 통과입니다. 앞의 실패 3건은 지우지 않고 그대로 이력에 남깁니다. `final`이라는 이름의 시도는 실제로는 실패했습니다.

## 남는 한계

1. **lowconc는 1회 관측입니다.** 같은 동시성으로 반복한 기록이 없어서, 동시성 2에서 항상 통과한다고는 말할 수 없습니다.
2. **동시성 4와 기본값에서 실패한 사실은 사라지지 않습니다.** `npm run check`의 기본 설정이 실패하는 상태라면 그 자체가 후속 과제입니다. 기본 동시성에서 통과한 기록은 없고, 계약이 `npm run check`를 명시한다면 lowconc는 그 명령이 아닙니다. 이 부분은 계약 문구를 확인해야 합니다. 이 폴더의 `eval-plan.md`에는 계약 문구가 없습니다.
3. **패치 없는 기준 상태의 전체 검사 기록은 여전히 없습니다.** 불안정이 패치와 무관하다는 직접 증거는 아니고, 패치가 역할·요건 문서, JSON, 생성물, 시험 1건만 바꾼다는 점에 의한 간접 추론입니다.
4. **skip 17건:** `PACE_SKIP_BROWSER_E2E=1`이 원인이라는 설명은 있으나 17건 전부가 그 시험인지는 기록에 없습니다. 네 시도 모두 17건으로 같아 시도 간 변동은 없습니다.
5. **재시험 proof에는 실행 소스 해시가 없습니다.** `reaper-retest.txt`, `wizard-retest.txt`, `lock-retest.txt`, `boundary-retest.txt`는 모두 1/1 pass이고 fail 0, skip 0입니다. 다만 `lock-retest.txt`는 controlled 시도의 실패 시험에 해당합니다.
6. 발췌본이라 원본 로그가 아니며, 바이트 해시는 재계산하지 못했습니다.
