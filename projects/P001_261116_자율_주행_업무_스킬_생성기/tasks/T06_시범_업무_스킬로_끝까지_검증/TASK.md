## 설계 결정

- **구성**: 작업 폴더(저장소 밖 임시) → `pace-playbook-maker`로 인터뷰(`interview.json`)·흐름 뼈대(`initFlow`)·실제 화면 수행·가림 캡처·승인·`generatePlaybook` → 시범 플레이북(스킬 폴더 한 벌) → `pilot/`로 복사. 측정 도구 `pilot/harness/`(저장소 안 프로젝트 도구, 스킬이 아님): `run-session.mjs`(헤드리스 세션 실행·stream-json 수집·소요·도구 호출 집계), `truth.mjs`(같은 시각 GitHub 공개 API 정답), `score.mjs`(추출 정확도·지표 요약·중앙값), `scrub.mjs`(원본 기록의 사용자 경로·토큰 가림). 도구는 결과 값이 아니라 지표만 `evidence/`에 남긴다.
- **정답과 정확도 판정**: 정답은 `truth.mjs`가 GitHub 공개 API로 세션 시작 직전과 끝난 직후 두 번 가져온다(시각 붙임) — 기본 브랜치(`GET /repos/{r}`의 `default_branch`), 별 개수(`stargazers_count`), 그 브랜치의 최신 커밋(`GET /repos/{r}/commits/{branch}`의 `sha` 앞 7자·메시지 첫 줄·`commit.committer.date`의 UTC 날짜). 세션 출력(표)을 대조해 다섯 필드가 맞는지 센다: 브랜치·해시·제목은 일치, 별 개수는 페이지 표기("12.3k")의 반올림 범위 안(두 시점 값 모두 허용), 날짜는 UTC 일(day) 단위(시점 차이로 하루 어긋나는 경계는 두 시점 정답 중 하나와 맞으면 인정). 측정 중 최신 커밋이 바뀌면 브랜치·해시·제목·날짜는 **시작 정답 묶음 또는 끝 정답 묶음 중 하나와 통째로** 일치해야 정확이다(필드마다 두 시점을 섞은 조합은 존재하지 않는 커밋이므로 오답 — 별 개수는 두 시점 모두 허용하는 표기 범위를 따로 적용). 한 필드라도 다르거나 비었거나 다른 저장소 값이면 성공이 아니다. 판정기 자체는 단위 검증(S-10)한다: 필드별 오답·누락·다른 저장소·표기 경계·시점 차이(시작 묶음·끝 묶음 각각 통과)와 **혼합 시점 오답(시작 해시+끝 제목)**을 각각 실패/통과로 가린다.
- **완료 처리 원칙**: P-6 미충족·T-4 미충족, 또는 T-6의 필수 공존 검증(7번째 호출)이 미승인으로 미확인이면 T06 목표 달성은 **미달**로 보고하고 그대로 코디네이터·사용자 결정으로 올린다 — 기준을 낮추거나 완료로 처리하지 않는다.
- **측정 규칙(고정)**: 세션마다 시간 제한 15분 — 넘으면 실패로 보고 시간은 15분으로 센다. 실패·시간 초과 표본도 중앙값 계산에서 빼지 않는다. **P-6 충족 = 플레이북 3회 모두 정확 + 플레이북 3회의 시간 중앙값·도구 호출 중앙값이 지도 없음 3회(실패 표본 포함)의 중앙값보다 모두 작음.** 비교 결과를 보고하는 것과 P-6 충족 판정은 별개이며 하나라도 아니면 미충족으로 보고한다. 지도 없음이 3회 모두 성공하고 플레이북 군이 더 느리면 그대로 미충족이다.
- **독립성 통제**: 두 군의 프롬프트 틀·모델·허용 도구·시간 제한·작업 폴더 구성을 같게 고정해(`harness/prompts/`에 원문 보관) 입력별로 인접 실행하고 순서를 교차한다(입력1 플레이북→지도 없음, 입력2 지도 없음→플레이북, …). 세션 init 이벤트의 자동 노출 맥락(도구·스킬·지침 목록)과 `claude --version`·모델 값을 기록해 두 군이 같은지 확인한다. 작업 폴더에는 CLAUDE.md·프로젝트 지침이 없고(격리 임시 폴더) 세션마다 새 Orca 탭이다. 플레이북 군은 stream-json에서 `agent/index.json`·`agent/S0n.json`을 실제로 `Read`했는지 확인해 읽지 않은 표본은 "지도 미사용"으로 표시한다(그 표본은 플레이북 성공으로 세지 않는다 — 다시 돌려야 하면 6회 밖이라 묻는다).
- **지표**: 성공 여부·소요 시간(첫 호출~최종 답)·읽은 지도 분량(`Read`한 플레이북 파일의 바이트 합 — 보조)·도구 호출 수(stream-json의 `tool_use`)·화면 탐색 횟수(`orca` 호출 중 스냅샷·스크린샷·eval 읽기 호출 수)·추출 정확도. **결과는 있는 그대로 기록한다** — 위 측정 규칙으로 P-6 충족 여부를 판정하고 기준을 낮추지 않는다.
- **작성 입력과 주행 입력 분리**: 플레이북은 `ceo4ever/pace`로 만들고 주행 세션은 다른 입력 3종만 쓴다. 주행 세션에는 플레이북 폴더와 입력만 주고 만든 세션의 맥락·대화·사람 보완은 주지 않는다. 플레이북에 입력별 값(저장소 이름·커밋 값)이 들어가지 않는다 — 자리표시(`<owner/repo>`)만.
- **사람 확인 지점**: 초기 작성의 캡처 승인은 사람이 이미지를 확인한 해시로만 한다(스킬 규칙) — 시범 캡처(공개 페이지)의 대기 이미지 경로를 캡틴(코디네이터)에게 보내 확인 답을 받은 해시로 승인한다. 확인 전에는 승인하지 않는다.
- **변경 학습 확인**: 실제 변경이 없으므로 시범 플레이북 복사본의 **원본 `steps.json`**에서 한 요소의 선택자를 현재 페이지에 없는 낡은 값으로 바꾸고 `buildFlow`로 지도를 정상 재생성해(생성물 `agent/*`는 직접 고치지 않는다 — 단일 원본 원칙) **선행 조건**을 확인한다: 재생성한 지도는 `checkAgentFresh`를 통과하고 실제 DOM에서만 그 선택자가 요소를 못 찾는다(손상이 최신성 검사 `stale-map`이 아니라 화면 수행에서 드러난다). `box`는 원본이 아니라 캡처 기록에서 오므로 손상은 선택자 한 종류로 한다. 그 지도로 `driveWithHealing`(T05)으로 실제 GitHub 페이지에서 치유·반영하고, 반영 뒤 같은 입력으로 다시 주행해 진단 없이 통과함을 본다. **복구하지 못하면 T-4는 미충족이다** — 그 사실과 이유는 그대로 기록하되 완료로 인정하지 않는다(목표 달성 판정에서 미달로 보고). 검증은 네 단계로 나눠 관찰한다: ① 손상 전 정상 주행(정확) ② 손상 직후 실제 진단 실패(주행이 해당 단계에서 멈추고 진단 종류가 나옴 — 주행 생략·진단 우회가 아님) ③ 복구·반영(원본 `steps.json`의 선택자 변경, 지도 재생성·`checkAgentFresh`, `history.md` 항목) ④ 정확한 재주행(추출 결과가 정답과 일치, 치유 호출 0).
- **사례 저장소 무영향(P-7)**: 임시 `PACE_HOME`·임시 HOME에 PACE 현재 소스를 설치한 상태에서 ① 사례 저장소 흐름 9개를 T01 `compare-identity.mjs`로 다시 비교(생성물 바이트 동일, 현재 생성기 — `agentView` 없는 흐름은 출력이 그대로) ② 사례 저장소 테스트 4종(`tools/flow`·`tools/{service-a,service-b,service-c}`)을 실행해 `case-baseline.txt`와 같은 통과 건수 ③ 사례 저장소 작업 사본 `git status` 0줄·HEAD 불변 ④ `~/.claude/skills`(실제 HOME)가 `home-skills-before.txt`와 같고 임시 HOME에는 `pace-playbook-maker`가 추가로 보임 ⑤ **공존**: 임시 HOME의 기존 스킬 항목(사례 저장소 맥락에서 쓰는 프로젝트 스킬 4개 폴더와 홈 스킬 목록)의 **파일별 해시**가 설치 전후 같고 5개 스킬의 `name`이 서로 다르다 ⑥ **7번째 호출**(캡틴 결정 대기): 설치 후 임시 HOME을 쓰는 사례 저장소 맥락의 새 `claude -p` 세션(읽기 전용·`Read`만)이 스킬 목록에서 프로젝트 스킬 4개와 `pace-playbook-maker`를 각각 구별해 말하고 기존 업무 스킬 안내(시작 시 `flow/overview.md`)를 가리킨다 — 세션 기록 증거. 출력은 비식별(흐름·서비스는 번호만).
- **사례 저장소 인계 문서**: 사례 저장소가 시제품 스킬을 `pace-playbook-maker`로 바꾸는 방법 — 어댑터 import 9곳의 변경 위치 `file:line`(사례 저장소 작업 사본에서 읽어 적는다)·`agentView` 켜기·낡은 안내 문구 정리·검사 명령. **사례 저장소 이름·경로가 들어가므로 저장소 밖 `~/.pace-private/`에만 두고** 추적 파일에는 "인계 문서: 로컬 보관(비공개)"와 검사 요약(변경 위치 개수·명령 종류)만 적는다. 구성 요소(스킬 이름·지도·플레이북)는 일반 용어로 쓴다.
- **문서·브레인**: `docs/README.md`·`docs/ARCHITECTURE.md`의 구성 요소 표에 `pace-playbook-maker`(`tools/` 도구와 참조 문서 4종)를 추가한다 — 하네스 라벨(`검사`·`보안 검사`·`worktree 준비`) 이름은 바꾸지 않는다. 브레인(`.pace/brain/`)에 구조·함정·결정 페이지를 더하고 `pace brain lint`를 맞춘다.
- **값이 새지 않는 경로**: 시범 작성·주행·학습 전 과정에서 저장된 모든 파일(인터뷰·steps.json·지도·캡처·history·상태·세션 기록)에 민감 형식 실값 0건 — 같은 `scanSensitive` 검사를 시범 폴더 전체에 적용한다. 공개 정보(저장소 이름·커밋 해시 앞 7자·제목·날짜·별 개수)는 시각이 붙은 정답과 세션 출력 표로 증거에 남겨 정확도 판정을 다시 검토할 수 있게 하고, 세션 기록에는 사용자 경로·토큰을 가린다. 플레이북·지도에는 입력별 값을 쓰지 않는다.
- 하지 않는 것: 사례 저장소 실제 전환(사례 저장소 세션), 실제 HOME 설치, 추가 시범 업무, 쓰기·로그인이 필요한 업무.

## 접근

- 새 파일: `pilot/`(시범 플레이북·`harness/{run-session,truth,score,scrub}.mjs`·실행 스크립트), `evidence/*`, `~/.pace-private/HANDOFF_*`(추적 밖), 브레인 페이지. 기존 변경: `docs/README.md`·`docs/ARCHITECTURE.md` 표, 필요하면 `pace-playbook-maker` 참조 문서의 시범에서 드러난 보정(스킬 버전 표기 유지).
- 사전 검토는 최대 2회(`pace agent verify --kind task`) + 필요 시 캡틴 승인 반영 확인 1회. 경계 사례는 구현 후 검토·증거로 넘긴다. 측정 세션 호출은 6회로 한정하고 넘기려면 다시 묻는다.
