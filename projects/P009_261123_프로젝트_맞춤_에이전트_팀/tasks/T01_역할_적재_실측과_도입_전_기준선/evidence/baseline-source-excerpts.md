# AI SQL — 설계 문서 (v0.1, 2026-10-16)

## 7. SQL 실행 파이프라인

모든 실행 경로(에디터, UI 편집, AI, MCP, Import)는 아래 파이프라인 하나만 통과한다.

```
입력 SQL
 → ① split      문장 분리 (문자열·주석·백틱·DELIMITER 처리)
 → ② classify   문장별 kind 판정
 → ③ policy     연결 write_policy × source × kind → allow | require_approval | deny
 → ④ approve    필요 시 Approval 생성 → UI 승인 대기 (WS 이벤트)
 → ⑤ execute    문장별 순차 실행, 결과를 탭 단위로 스트리밍
 → ⑥ record     runs / statements / approvals 기록 + afterExecute 훅
```

### 7.1 다중 문장 → 결과 탭 (요구사항 3)
- 실행 한 번이 `run` 하나가 되고, 문장마다 `statement`와 **결과 탭**이 하나씩 생긴다.
- 탭에는 상태 아이콘, 결과 행 수/영향 행 수, 소요 시간, 오류 메시지를 표시한다.
- 오류가 나면 기본은 **중단**하고, 나머지 문장은 `skipped`로 표시한다. 설정으로 "계속"을 선택할 수 있다.
- 세션 상태를 유지하기 위해 같은 run 안의 문장은 **같은 DB 연결**에서 실행한다(SET, 임시 테이블, `USE` 유지).
- 결과는 WS로 스트리밍한다. 탭마다 기본 최대 행 수(`LimitResultsValue`)를 적용하고, "더 보기"로 추가 페이지를 가져온다.

### 7.2 분류 규칙 (보수적)
| kind | 예 | 기본 정책 |
|---|---|---|
| read | SELECT(잠금 절 없음), SHOW, DESCRIBE, EXPLAIN(ANALYZE 제외), USE | 자동 실행 |
| write | INSERT, UPDATE, DELETE, REPLACE, LOAD DATA, SELECT … INTO / FOR UPDATE, CALL | 승인 |
| ddl | CREATE, ALTER, DROP, TRUNCATE, RENAME | 승인(강화 경고) |
| admin | GRANT, REVOKE, KILL, SET GLOBAL, FLUSH, SHUTDOWN | 승인(강화 경고) |
| unknown | 파서 실패, 판정 불가 | **승인** (안전 측) |

- `CALL`이나 저장 함수가 포함된 SELECT는 부작용이 있을 수 있다. 그래서 `write`로 분류한다.
**위험 SQL**은 WHERE 없는 UPDATE/DELETE, 파괴적 DDL(DROP·TRUNCATE·ALTER·RENAME), admin을 말한다. 위험 SQL은 강화 확인을 거친다(대상 이름 직접 입력).

**정책 매트릭스** (2026-10-16 확정, 구 Q3). 출처 `ai`·`mcp`는 AI로, `editor`·`ui`·`import`는 사람으로 본다.

| 연결 쓰기 정책 \ 실행 주체 | read | 일반 write | 위험 SQL | 비파괴 DDL(CREATE 등) | unknown |
|---|---|---|---|---|---|
| `approve` (기본) · AI | 자동 | 승인 | 승인 + 강화 확인 | 승인 | 승인 |
| `approve` (기본) · 사람 | 자동 | UPDATE/DELETE는 확인 대화상자, 그 외는 바로 실행 | 강화 확인 | 바로 실행 | 확인 대화상자 |
| `approve-all` · AI/사람 | 자동 | 승인 | 승인 + 강화 확인 | 승인 | 승인 |
| `read-only` · 모두 | 자동 | 차단 | 차단 | 차단 | 차단 |

- "확인 대화상자"는 Sequel Ace의 `ShowWarningBeforeDeleteQuery`에 해당하는 간단한 확인이다. 영향 행 분석은 하지 않으며 감사 로그의 `approvals`에도 남기지 않는다. 실행 기록은 `statements`에 남는다.
- "승인"은 §7.3의 영향 분석 + 승인 카드이며 `approvals`에 기록한다.
- 연결 `write_policy = read-only`이면 read 외의 문장은 모두 `deny`한다. 추가로 **DB 세션에 `SET SESSION TRANSACTION READ ONLY`**를 적용해 이중으로 막는다.

### 7.3 승인 미리보기 (영향 분석)
- **UPDATE/DELETE**: 같은 WHERE 조건으로 `SELECT COUNT(*)`를 실행해 예상 영향 행 수를 구하고, 앞쪽 일부 행을 샘플로 보여준다. 샘플 노출은 연결 설정을 따른다.
- **WHERE 없는 UPDATE/DELETE**: "전체 행 대상"으로 강조한다. 이때는 확인 문구를 직접 입력해야 승인된다.
- **DDL**: 대상 객체와 현재 CREATE 구문을 보여준다.
- **실행 옵션: 트랜잭션 실행** (DML 기본 켜짐)
  - `START TRANSACTION`으로 시작해 실행하고, 실제 영향 행 수가 예상과 다르면 `ROLLBACK`한다. 이때 카드에 "롤백됨 · 실제 N행"을 표시하고 다시 승인을 받는다. 같으면 `COMMIT`한다.
  - 트랜잭션을 지원하는 엔진(InnoDB 등)의 DML에만 적용한다. MySQL에서 DDL은 암묵적으로 커밋되므로 DDL과 비트랜잭션 엔진(MyISAM 등)에서는 이 옵션을 비활성화하고 사유를 표시한다.
  - **구현 (2026-10-19)**: 큐리(ai·mcp)가 요청한 INSERT·UPDATE·DELETE·REPLACE에 항상 적용한다. 정확한 예상 행 수(COUNT)가 있을 때만 비교하고(EXPLAIN 추정은 비교하지 않음), 같은 실행의 문장이 실패해도 모두 되돌린다. 되돌리면 run·문장 상태가 `rolled_back`, 승인 기록에 `outcome`(실제·예상 행 수)을 남기고 카드에 표시한다. 다시 승인은 큐리가 새로 제안한다(도구 결과 `rolled_back`). 같은 연결에 커밋 안 한 변경이 있으면 실행하지 않는다(`TX_PENDING`).
- **Query 자동 커밋** (2026-10-19): 설정 `query.autocommit`(기본 켬) + 연결별 `config.autocommit`(없으면 설정). Query(`editor`) 실행에만 적용한다.
  - 끄면 실행 연결에 `SET autocommit = 0`. 변경이 생기면 Query 아래 트랜잭션 줄(문장·행 수·경과 시간, 5분 넘으면 경고)에 [커밋]·[롤백].
  - Content 편집 등 다른 출처는 Query에 열린 트랜잭션(수동 커밋·직접 연 `START TRANSACTION`)이 있으면 따로 연결해 바로 반영한다. 같은 행이 잠겨 있으면 5초 뒤 `TX_LOCKED`로 알린다.
  - 열린 트랜잭션이 있을 때 DDL 등 암묵 커밋 문장은 확인을 받는다. 연결 탭을 닫거나 창을 닫을 때 경고한다. 열린 트랜잭션이 있으면 자동 커밋으로 되돌리지 않는다(`TX_PENDING`, 커밋·롤백은 된다).
- **실행 옵션: 사전 백업** (기본 꺼짐)
  - UPDATE/DELETE 실행 직전에 같은 조건으로 대상 행을 조회한다. 그 행을 되살리는 SQL을 `approval_backups`에 저장한다.
  - 기록 화면에서 "백업 SQL 열기"로 복원할 수 있다. 복원도 일반 쓰기와 같이 승인을 거친다.
  - 대상이 1만 행을 넘거나 50MB를 넘으면 옵션을 비활성화하고 "Export 사용"을 안내한다. 이 한도는 설정에서 바꿀 수 있다.
  - 백업 데이터는 로컬 SQLite에만 저장하고 AI에게 전달하지 않는다.
- **승인 범위**: 승인은 **문장 원문의 해시**에 묶인다. 승인 후 SQL이 바뀌면 다시 승인을 받아야 한다.
- **만료**: 승인 요청이 설정 시간(기본 10분) 동안 처리되지 않으면 `expired`로 바뀐다.

### 7.4 결과 제한 · 스크롤 페이징 (2026-10-18)

- **Query 결과**: 하단 "☑ 결과 제한 [N] 행" — 하위 탭마다 따로, 새 탭은 설정값(`query.maxRows`)으로 시작. 끄면 무제한(`maxRows: 0`).
  - 쿼리는 서버에서 **한 번만 끝까지** 실행한다. 첫 500행만 이벤트로 보내고, 나머지(상한까지)는 서버의 임시 파일(`<dataDir>/results`, NDJSON + 500행마다 위치 색인)에 둔다 → 화면이 스크롤 끝에 가까워지면 `GET /api/runs/:runId/results/:seq`로 1,000행씩 받아 붙인다. 다시 실행하지 않으니 페이지 사이 순서·중복 문제가 없고, 커서를 열어 두지 않아 테이블 잠금(MDL)을 오래 잡지 않는다.
  - 보관 결과 삭제: 같은 탭에서 다시 실행·탭 닫기(화면이 요청), 세션 닫기, 30분 미사용, 서버 재시작. 긴 조회는 만 행마다 `progress` 이벤트("N행 읽는 중").
  - 전체 복사·엑셀은 아직 받지 않은 행까지 받아서(20만 행까지).
  - `pageRows`를 주지 않는 실행(AI·MCP 등)은 예전처럼 상한까지 한 번에.
- **Content**: 페이지 넘김 대신 무제한 스크롤 페이징(`table.pageSize`씩 `LIMIT/OFFSET`). 페이지 순서를 고정하려고 기본 키를 정렬 끝에 둔다. 전체 행 수는 첫 페이지에서만 센다. 셀을 고치면 그 행이 있는 페이지만 다시 받아 바꿔 끼운다(스크롤·받아 둔 행 유지), 행 추가·삭제·새로 고침은 처음부터.
- **화면 메모리 보호**: 받아 온 행은 화면에 남겨 다시 받지 않는다. 20만 행을 넘으면 자동으로 더 받지 않고 [계속 불러오기]. 그리드는 가상 스크롤이라 그리는 행 수는 화면만큼.
- **Query 결과 받기 설정** (`table.fetchMode`, 설정 › 테이블 · 결과 — Query 결과에만): `scroll`(기본, 위와 같음) / `all` — 첫 페이지를 바로 보여 주고 나머지를 백그라운드로 1만 행씩 받는다(100만 행까지, 그 뒤는 [계속 불러오기]). DB는 이미 끝났고 서버 보관분에서 읽으므로 DB 부하는 없다. 1만 행마다 0.1초 쉬고, 그 결과가 안 보이면(다른 하위 탭·브라우저 탭) 쉬었다가 이어 받는다. 하단에 진행 막대와 [일시정지]/[다시 받기]/[멈춤](멈추면 스크롤할 때만).
- **Content는 늘 스크롤할 때마다** (2026-10-18 결정): 테이블 하나를 훑는 화면이라 앞부분만 보는 경우가 대부분이고, 백그라운드로 다 받으면 DB에 조회를 수십~수백 번 보내게 된다.
  - Content는 단일 기본 키·정렬 없음이면 keyset(`WHERE pk > 마지막 값`)으로 받아 뒤로 가도 느려지지 않는다. 정렬했거나 복합 키면 OFFSET.
  - 측정(2026-10-18, MySQL 8.4 로컬, 5컬럼 100만 행): Content 첫 화면 0.36초 · 전부 5.5초, Query(`SELECT *`) 첫 화면 1.3초 · 전부 3.2초, 브라우저 메모리 약 390MB, 다 받은 뒤 끝으로 스크롤 0.04초.
  - Query의 첫 화면은 서버가 문장을 끝까지 읽은 뒤에 온다(결과를 파일에 다 쓴 다음). 아주 느린 쿼리는 그동안 진행 표시만 보인다.

## 10. 보안

- **바인딩과 인증**: `127.0.0.1`에만 바인딩한다. 기동할 때 랜덤 토큰을 만들고, 브라우저는 실행 URL로 토큰을 받는다. 모든 API, WS, MCP에서 이 토큰을 검증하고 `Origin`도 확인한다.
  - 화면은 실행 URL의 `#token=`을 `POST /api/auth/login`으로 **HttpOnly · SameSite=Strict 쿠키**(`aisql_token_<port>`)로 바꾼다. 화면 스크립트는 토큰을 읽을 수 없다. MCP·도구·테스트는 `Authorization: Bearer`를 그대로 쓴다.
  - Electron(P3): 화면을 같은 `http://127.0.0.1:<port>`에서 불러오고, 메인 프로세스가 `session.cookies.set`으로 쿠키를 넣는다. 서버·화면 코드는 바꾸지 않는다.
- **세션 유지**: DB 세션은 사용자가 닫을 때까지 유지한다(시간으로 닫지 않음). 열린 세션은 `open_sessions`(v10)에 기록하고, 서버를 다시 켜면 `:sid` 요청이 처음 올 때 같은 ID로 다시 연결한다. 빠른 연결의 설정·비밀번호는 SecretStore(`quick:<id>`)에 암호화해 둔다. 30일 쓰지 않은 기록은 정리한다. AI 대화용 세션은 기록하지 않는다.
  - 쉬는 소켓은 풀이 닫는다(`maxIdle: 1`, `idleTimeout: 60s`). 실행 연결은 트랜잭션·세션 상태(변수, 임시 테이블, 잠금 등)가 없을 때만 2분 뒤 풀에 돌려준다.
  - MySQL 세션 상태는 새 연결로 옮길 수 없다. 실행 연결이 끊겼을 때 트랜잭션·세션 상태가 있었으면 다음 실행을 멈추고 `SESSION_STATE_LOST`로 알린다(모르고 자동 커밋으로 실행되지 않게). `USE db`·시간대·읽기 전용은 새 연결마다 다시 적용된다.
- **SQL 생성**: 서버가 만드는 SQL(행 편집, 필터, DDL 빌더)의 식별자는 `escapeId`로 감싼다. 값은 바인딩 파라미터로 넘긴다. 사용자가 직접 쓴 SQL은 원문 그대로 파이프라인에 넣는다.
- **비밀 정보**: 로그, 기록, AI 컨텍스트에 비밀번호나 키를 넣지 않는다. 연결 config에서 비밀은 분리해 저장한다.
- **AI 격리**: AI는 파이프라인을 우회할 수 없다. MCP 도구가 유일한 접근 경로이고, 쓰기는 반드시 Approval을 거친다. 에이전트의 파일·터미널 기능은 꺼 둔다.

# AI SQL — 배포 · 인증 · 구독 아키텍처 (초안 v0.1, 2026-10-17)

## 1. 목표와 원칙

**목표**
- 한 엔진(코어 + 서버)으로 세 가지 배포 형태를 지원한다: 로컬 웹, 데스크톱 앱, 클라우드 웹.
- 계정 기반 구독으로 과금하고, 데스크톱과 클라우드 웹은 같은 계정을 쓴다.
- 클라우드에서도 고객의 **사설망 DB**(사내망·VPC·로컬)에 접속할 수 있어야 한다.

**원칙** (확정)
1. **DB 비밀번호는 클라우드에 저장하지 않는다.** 비밀번호는 엔진이 도는 곳(내 PC나 고객 측 커넥터)에만 둔다. 클라우드가 침해되더라도 고객 DB 자격증명이 유출되지 않게 하기 위해서다.
2. **엔진은 인바운드 포트를 열지 않는다.** 로컬에서는 `127.0.0.1`에만 바인딩한다. 커넥터는 클라우드로 **나가는 연결만** 만든다. 고객 방화벽 설정이 필요 없게 하기 위해서다.
3. **인증의 종류를 섞지 않는다.** "누구인가(계정)", "무엇을 쓸 수 있나(구독)", "이 화면·기기가 이 엔진을 써도 되나(엔진 접근)"를 각각 다른 수단으로 증명한다.
4. **오프라인에서도 일한다.** 데스크톱 앱은 구독을 확인한 뒤 일정 기간 동안 네트워크 없이도 동작해야 한다.

## 4. 주요 흐름

### 4.1 데스크톱 앱 실행 (B)
1. 셸(Electron)이 무작위 ③을 만들고 내장 엔진을 띄운다. 엔진은 `127.0.0.1`의 랜덤 포트에 바인딩된다.
2. 셸이 창을 열고 ③을 메모리로 주입한다. URL에는 넣지 않는다.
3. 저장된 ②가 유효하면 바로 사용한다. 만료가 다가오면 백그라운드에서 ①로 클라우드에 갱신을 요청한다.
4. ②가 없거나 유예 기간이 지났으면 로그인 화면(①)을 띄운다. 무료 요금제 기능은 로그인 없이도 쓸 수 있게 할지는 D3에서 정한다.
5. 엔진은 기능을 실행할 때 ②의 `plan`과 `features` 클레임으로 허용 여부를 판정한다(§5).

### 4.2 클라우드 웹에서 사설 DB 조회 (C)
1. 사용자가 브라우저로 로그인한다(①). 클라우드가 조직과 요금제를 확인한다.
2. 고객 측 커넥터가 미리 클라우드에 **아웃바운드 연결**을 유지하고 있다(④).
3. 브라우저가 클라우드 API를 호출하면, 클라우드는 해당 조직의 커넥터로 요청을 **중계**한다.
4. 커넥터(= 엔진)가 자기 SecretStore의 DB 비밀번호로 DB에 접속한다. 실행 파이프라인(정책·승인·기록)을 그대로 거쳐 실행하고, 결과를 돌려준다.
5. 클라우드는 중계만 한다. DB 비밀번호는 클라우드로 오지 않는다. 결과 데이터는 클라우드에 저장하지 않는다(D6).

### 4.3 커넥터 등록 (C)
1. 관리자가 클라우드 화면에서 **1회용 등록 코드**를 발급한다(유효시간 짧음).
2. 고객 서버에서 커넥터를 실행하고 등록 코드를 입력한다(Docker 또는 설치형, D5).
3. 커넥터가 키쌍을 만들어 공개키를 등록한다. 이후 ④로 인증한다.
4. 관리자는 커넥터를 언제든 폐기할 수 있다. 폐기된 커넥터는 중계 대상에서 즉시 제외된다.

### 4.4 AI 에이전트 연결 (P2, 모든 형태)
- 내장 AI 패널은 엔진이 ACP 클라이언트로 에이전트를 실행하고, 내부적으로 MCP 도구를 넘긴다. 이때 ⑤를 자동으로 쓴다.
- 외부 에이전트(사용자의 Claude Code)는 설정 화면에서 발급한 ⑤로 엔진의 `/mcp`에 붙는다.
- 쓰기 SQL 승인은 항상 사용자 화면에서 받는다(DESIGN §7·§8).

### 4.5 AI 에이전트 — 배포 형태별 (2026-10-18)

내장 AI 패널은 **에이전트 CLI와 그 로그인이 엔진과 같은 컴퓨터에 있어야** 동작한다(DESIGN §8.6: 엔진이 CLI를 자식 프로세스로 띄우고, 계정은 `CLAUDE_CONFIG_DIR`·`CODEX_HOME` 폴더로 고른다). 그래서 엔진이 사용자 PC에 있는 A·B에서는 그대로 되고, 엔진이 클라우드·고객 서버에 있는 C에서는 다른 방식이 필요하다.

| 형태 | 내장 AI 패널 (ACP) | 외부 에이전트 (MCP) | 비고 |
|---|---|---|---|
| A. 로컬 웹 | 가능 (현재) | 가능 — `127.0.0.1/mcp` + ⑤ | |
| B. 데스크톱 앱 | 가능 — 구조 동일 | 가능 | 아래 "B 패키징" 참고 |
| C. 클라우드 웹 | **불가** (지금 방식) — 아래 C-①·② | C-① 원격 MCP | |
| D. 자체 호스팅 | 서버에 CLI·로그인이 있으면 가능하나 권장하지 않음 | 가능 | 서버 공용 계정 문제 → C와 같은 방식 권장 |

**B 패키징 (P3에서 처리)**
- 내장 Claude 어댑터 실행: 지금은 `process.execPath`(Node)로 띄우는데, Electron에서는 Electron 실행 파일이 된다 → `ELECTRON_RUN_AS_NODE=1` 또는 `utilityProcess`로 실행.
- PATH: Dock에서 띄운 앱은 PATH가 짧다 → 로그인 셸 PATH를 읽는 처리는 이미 있음(`shellPath()`).
- Mac App Store 불가: 앱 샌드박스가 다른 프로그램 실행을 막는다 → DMG + 공증(notarization)으로 직접 배포.
- 계정 폴더(`<dataDir>/ai-accounts`)·Codex 잠금 환경은 그대로 쓴다.

**C 클라우드에서 AI를 쓰는 방식**

에이전트 CLI와 사용자의 구독 로그인(Claude Pro·Max, ChatGPT 등)은 사용자 PC에 있다. 클라우드 서버가 그 로그인을 대신 쓸 수 없고, 개인 구독을 제3자 서버가 대신 쓰는 것은 각 회사 약관상 문제가 될 수 있다(확인 필요, D10). 그래서 아래 셋 중에서 고른다.

| 방식 | 구조 | 키 저장 | 장점 | 단점 |
|---|---|---|---|---|
| **C-① 원격 MCP** (추천, 기본) | 클라우드가 MCP 서버(`https://…/mcp`)를 연다. 사용자의 Claude(claude.ai 커넥터, Claude Code, 기타 MCP 클라이언트)가 **OAuth**로 붙는다. 도구·정책·승인은 지금과 같고, 승인은 클라우드 웹 화면(🔔)에서 | 없음 (에이전트가 자기 구독으로 실행) | 지금 "외부 에이전트(MCP)"를 그대로 확장. 약관·비용 부담 없음 | 앱 안 사이드 패널 경험은 없다(대화는 사용자의 Claude 쪽) |
| **C-② 로컬 실행 + 클라우드 연결** | 사용자 PC의 데스크톱 앱(또는 작은 로컬 커넥터)이 에이전트를 실행하고, 클라우드 엔진의 MCP에 붙는다. 화면은 데스크톱 앱 또는 클라우드 웹 | 없음 (자기 PC 로그인) | 앱 안 사이드 패널 경험 유지 | 사용자 PC에 설치가 필요 |
| C-③ 서버 측 에이전트 | 서버에서 Claude Agent SDK 등을 API 키로 실행 | **있음** (회사 키 또는 사용자 키) | 설치 없이 사이드 패널 | "앱은 키를 저장하지 않는다" 원칙과 충돌, 사용량 정산·남용 방지 필요 |

- **추천**: C는 ①을 기본으로, 앱 안 패널이 필요한 사용자에게 ②를 제공한다. ③은 팀·기업 요금제에서 요구가 확인될 때 별도로 검토한다(D10).
- **C-① 설계 메모**
  - 인증: MCP 표준의 OAuth 2.1(동적 클라이언트 등록 + PKCE)로 ①계정 세션과 연결. 지금의 ⑤ 정적 토큰은 로컬(A·B)에만.
  - 범위: 토큰마다 "커넥터 + 연결 + DB"로 묶는다(지금 ⑤와 같은 단위). 쓰기 정책·노출 수준·마스킹은 커넥터의 엔진이 집행한다.
  - 승인: 변경 제안은 클라우드 웹의 승인 알림으로. 사용자가 웹을 열고 있지 않으면 `wait_for_approval`이 대기 → 만료(10분). 모바일 알림은 이후 검토.
  - 경로: 에이전트 → 클라우드 MCP → 중계 → 커넥터(엔진) → DB. 결과 데이터는 클라우드에 저장하지 않는다(D6).
- **C-② 설계 메모**
  - 데스크톱 앱(B)이 이미 엔진과 ACP 호스트를 갖고 있으므로, "클라우드 커넥터의 DB에 붙는 원격 연결"을 하나 추가하는 형태가 가장 간단하다(AI 도구는 클라우드 MCP로).
  - 사내망 DB는 어차피 커넥터(④)가 필요하므로 같은 경로를 쓴다.

## 6. 데이터 위치와 보안 경계

| 데이터 | A 로컬 웹 | B 데스크톱 | C 클라우드 웹 |
|---|---|---|---|
| DB 비밀번호·SSH 키 | 내 PC (암호화) | 내 PC (OS 키체인) | **커넥터** (클라우드 X) |
| 연결 즐겨찾기(비밀 제외) | 내 PC | 내 PC (+선택 동기화) | 클라우드 |
| 실행 기록·승인 감사 로그 | 내 PC SQLite | 내 PC SQLite (+선택 업로드) | 커넥터 SQLite + 클라우드 요약(D6) |
| 쿼리 결과 행 | 저장 안 함 | 저장 안 함 | 중계만, 저장 안 함 |
| AI 대화 | 내 PC | 내 PC | D6 |

- **설정 동기화**(B·C): 즐겨찾기·폴더·색·쿼리 즐겨찾기는 동기화할 수 있다. 비밀번호는 동기화하지 않고 기기마다 입력한다(제안).
- **감사 로그**(팀 요금제): 승인 기록을 클라우드에 모아 보는 기능이 팀 단위 과금 포인트가 될 수 있다. SQL 원문을 업로드할지는 D6에서 정한다(민감 정보 포함 가능).
