# AI SQL DB 접속·권한 운영 내부 검토 메모

## 개요

검토 목적은 로컬 AI SQL을 운영할 때 연결 자격 증명, 화면 인증, AI 실행 승인 가운데 무엇을 현재 동작으로 기대할 수 있는지 구별하는 것입니다. 대상은 개발자 본인이 쓰는 로컬 웹앱과 Electron이며 SaaS 출시 판단은 포함하지 않습니다. 자료 기준은 ai-sql-client 커밋 eb24060c의 AGENTS.md, docs/PROJECT.md, docs/DESIGN.md, docs/DEPLOYMENT_AUTH.md입니다. 이 메모는 문서를 대조한 결과이며 실제 서버 실행, DB 접속, 패키지 시험 또는 현재 구현 코드 감사 결과가 아닙니다.

PROJECT의 개요와 범위는 로컬 우선 웹앱·Electron·AI 패널·PostgreSQL을 현재 범위로 설명합니다. 반면 AGENTS와 PROJECT의 문서 표는 DEPLOYMENT_AUTH를 배포·인증·구독 초안으로 소개하며, 여러 기능을 제안 또는 이후 단계로 구별합니다. 운영자가 초안의 기능을 현재 제품에 있다고 가정하면 계정 폐기나 접근 통제가 이미 된다고 오해할 수 있습니다. 따라서 이 메모에서는 현재 설계에 명시된 동작, 미래 제안, 실측이 필요한 사항을 나누어 봅니다.

## 현재 문서 서술 경계

DESIGN §7의 실행 파이프라인은 에디터·UI 편집·AI·MCP·Import를 공통 경로로 설명합니다. 문장을 나누고 종류를 판정한 뒤 연결의 쓰기 정책, 요청 출처, SQL 종류에 따라 허용·승인 필요·거부를 정하고, 필요한 승인을 받은 뒤 순서대로 실행하고 기록합니다. 정책의 결과는 출처별로 다릅니다. DESIGN §7.2는 사람 경로의 비파괴 DDL은 approve 정책에서도 직접 실행하고 UPDATE·DELETE 확인 대화상자는 approvals 기록과 구별한다고 설명합니다. read-only는 DB 세션 읽기 전용 설정으로도 막는다고 서술합니다. 이 설계가 운영에서 지켜지는지 보려면 기능별 화면만 볼 것이 아니라 동일 변경 요청이 각 진입점에서 같은 정책을 거치는지 확인해야 합니다. 여기서는 설계의 공통 경계를 확인했을 뿐 각 경로의 실제 강제를 재검증하지 않았습니다.

DESIGN §10은 서버의 루프백 바인딩, API·WS·MCP 토큰 확인과 Origin 검사, 비밀과 연결 설정의 분리, AI의 파이프라인 우회 금지를 설명합니다. 같은 절의 화면 인증 설명은 URL 해시의 토큰을 로그인 API로 교환하여 HttpOnly·SameSite=Strict 쿠키로 쓰고, MCP·도구·테스트는 Bearer를 유지하는 방식입니다. 화면 JavaScript가 토큰을 읽을 수 없다는 설계와 외부 도구의 인증 방식을 같은 것으로 취급해서는 안 됩니다. 운영 점검도 화면 세션과 도구 접속을 따로 확인해야 합니다.

DB 세션의 수명은 화면 인증과 별도로 확인할 필요가 있습니다. DESIGN §10은 사용자가 닫을 때까지 DB 세션을 유지하고, 재시작 뒤 같은 세션 ID로 재연결하며, 빠른 연결의 비밀은 SecretStore에 둔다고 설명합니다. 트랜잭션·세션 상태가 있던 MySQL 실행 연결이 끊기면 다음 실행을 멈추고 SESSION_STATE_LOST를 알려야 한다는 경계도 있습니다. 따라서 화면이 다시 열렸다는 사실만으로 실행 연결의 트랜잭션이나 임시 상태가 복구되었다고 안내하면 안 됩니다.

## 초안 제안 경계

DEPLOYMENT_AUTH §3의 자격 증명 표는 사용자 로그인, 라이선스, 로컬 엔진 토큰, 에이전트 토큰, DB 자격 증명을 서로 다른 수단으로 분리합니다. 이 구별은 운영 문구에서도 유지해야 합니다. 로컬 엔진 토큰을 재발급했다고 DB 비밀번호가 바뀌는 것은 아니며, 향후 클라우드 계정의 구독 상태가 현재 DB 계정 권한을 대신하는 것도 아닙니다. 문서에는 에이전트별 토큰 범위·폐기와 라이선스 검증 등이 미래 단계 또는 제안으로 남아 있습니다. 초안 안에도 구현됨으로 표시된 항목이 있으므로 문서 전체를 미래로 묶어서는 안 됩니다. 에이전트 토큰은 §3에서 P2라고 하지만 §4.5에는 현재 정적 토큰과 로컬 연결 가능 서술도 있어 개별 항목별 대조가 필요합니다. 현재 사용 가능 여부를 이 메모만으로 확정하지 않습니다.

같은 초안의 토큰 저장 위치에는 브라우저 localStorage라는 설명이 남아 있지만 DESIGN §10의 화면 인증은 쿠키 방식입니다. 이는 문서 사이의 차이로 기록해야 하며, 이 자료만으로 어느 서술이 나중인지 단정하지 않습니다. 토큰 수명도 DESIGN의 기동 시 생성과 초안의 고정·재발급 가능 설명이 다릅니다. 최신 동작을 확정하려면 실제 인증 구현과 시험을 확인하는 후속 작업이 필요합니다. 이 메모는 불일치하는 설명을 근거로 localStorage의 토큰을 직접 찾아보거나 사용자 인증 파일을 읽지 않습니다. 운영 안내를 배포하기 전에 설명의 기준일과 정본을 맞추는 것이 필요합니다.

DEPLOYMENT_AUTH §4·§6은 원격 커넥터, 클라우드 중계, 결과 비저장, 라이선스·설정 동기화 등을 제안합니다. 초안 §1에서 확정 원칙으로 표시한 비밀번호 비클라우드 원칙을 검토할 수는 있으나 원격 배포가 현재 사용 가능하거나 별도 검증 없이 안전하다고 결론 내릴 수는 없습니다. 고객 사설망 DB 연결, 연결별 권한 범위, 원격 MCP 접근과 폐기 동작은 이후 기능별로 승인·설계·실측해야 할 사항입니다. 로컬 사용 준비와 클라우드 출시 준비를 같은 체크리스트로 닫지 않는 편이 좋습니다.

## 운영 점검

로컬 운영 전에는 실행 위치와 데이터 폴더를 먼저 확인해야 합니다. PROJECT 환경 표는 개발 서버, 로컬 서버, 데스크톱, 데이터 위치를 나누어 설명합니다. PROJECT 환경 표는 실행·개발·데스크톱의 미확인 표시도 포함합니다. 문서상 기능 목록과 실제 실행 확인 상태를 구별하고, 실제 데이터 경로에 무심코 시험 명령을 실행하지 않도록 AGENTS의 workspace 명령 규칙과 Docker 필요 조건을 함께 확인하는 운영 절차를 제안합니다. 실제 Claude 시험은 비용이 발생하므로 별도 확인이 필요합니다. 이 메모 작성에서는 패키지 명령이나 실제 에이전트·DB를 실행하지 않았습니다.

접속 문제를 받으면 먼저 어느 인증 경계인지 분류하는 방식이 유용합니다. 화면 로그인 문제, MCP Bearer 문제, DB 계정·SSH 문제, SQL 쓰기 정책·승인 문제를 구별하면 잘못된 토큰 폐기나 비밀번호 변경을 줄일 수 있습니다. 지원 기록에는 증상·진입점·비밀 없는 오류 코드와 사용한 문서 기준만 남기고 토큰·비밀번호·키·SQL 결과 행을 복사하지 않습니다. 사용자 데이터가 필요한 조사는 이 메모 범위 밖에서 별도로 승인과 기록 경계를 정해야 합니다.

AI의 변경 SQL은 문서상 승인 카드 경계를 거쳐야 합니다. 운영자가 AI 요청 성공 메시지만 보고 실행 완료를 판단하지 않도록 승인 대기, 거부, 실제 실행, 기록 상태를 구별해 안내할 필요가 있습니다. 승인하지 않은 요청이 실행되지 않는지, 연결의 쓰기 정책을 AI가 우회할 수 없는지는 실제 통합 시험으로 증명해야 합니다. 문서의 존재가 이 검증을 대체하지는 않습니다.

DB 계정의 최소 권한도 앱의 쓰기 정책과 구별해야 합니다. DEPLOYMENT_AUTH §9는 향후 커넥터 위험에 대해 최소 권한 DB 계정을 권장하지만, 현재 로컬 연결에서 읽기 전용 DB 계정을 자동 분리하는지까지 이 자료만으로 확인할 수는 없습니다. 앱의 승인 카드가 DB 서버 자체의 계정 권한을 축소한다고 가정하지 말고, 실제 도입 단계에서 DB 계정의 허용 권한을 별도로 확인할 항목으로 남겨야 합니다.

## 결정 필요 사항

첫째, 사용자용 인증 안내의 정본과 기준일을 정하고 DEPLOYMENT_AUTH의 서로 다른 저장 위치 설명에 DESIGN §10과의 차이를 표시할 필요가 있습니다. 이는 문서 정리 제안이며 이번 메모에서 원본을 변경하지 않았습니다. 둘째, 로컬 사용 준비를 확인할 때 화면·MCP·DB·SQL 승인별로 어떤 실제 시험 결과를 제시할지 정해야 합니다. 문서가 현재 구현이라고 부른 내용도 운영 배포 전에는 해당 시험 근거와 연결하는 것이 좋습니다.

셋째, 향후 원격 커넥터·클라우드 기능은 현재 로컬 앱의 확인된 동작과 별도의 출시 기준으로 관리해야 합니다. 에이전트 토큰 범위·폐기, 결과 보관 경계, 라이선스와 DB 권한의 구별은 그 단계에서 결정할 사항입니다. 이번 결과는 기존 자료에 근거한 내부 검토 메모 1건이며 기능 승인이나 보안 인증이 아닙니다. 후속 운영 안내에서는 실제 확인한 항목과 문서에만 남아 있는 항목을 구별해 독자가 다음 확인 작업을 고를 수 있도록 정리하는 것이 좋습니다.
