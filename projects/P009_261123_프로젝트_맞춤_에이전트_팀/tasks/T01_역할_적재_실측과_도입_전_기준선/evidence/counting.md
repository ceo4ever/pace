# 비교 집계의 고정 정의

2026-11-23, 역할 적용·문서 작성 전 고정. 당시 수신자 계층을 고정한 역사적 기록이다. BR09 승인 뒤 최신 도달 정의는 아래 후속 절과 reachability-contract-update.md를 따른다.

| 항목 | 포함 | 제외·미확인 | 근거 |
|---|---|---|---|
| 캡틴 질문/결정 요청 | captain에게 실제 도달한 question·escalation | coordinator가 대신 답한 것은 제외, 수신자 없고 메시지로도 판별 못 하면 미확인 | 캡틴 답 또는 성공 전송 증거, 요청 연결 |
| 캡틴 승인 | 병합·배포·범위 변경 등 실제 사람 승인 | 코디네이터 결정은 캡틴 승인 아님 | approval 또는 결정 사건/Orca 메시지 |
| 캡틴 손작업 | 역할 재지시·직접 파일 수정·명령 대신 실행 각각 | 초기 계약 지시 자체는 수동 보정 아님 | note 및 메시지/파일 근거 |
| 수동 지시 | 계약·브리프 밖의 보정 지시 | 정상 역할 배정·승인은 별도 집계 | Orca 메시지와 계약 대조 |
| 품질 | blocking 합, fail 뒤 재검토 횟수, 실행 게이트 실패 | 미실행은 통과 아님, 알 수 없는 값은 미확인 | review-records·게이트 출력 |

## 중복 없이 세기

작업자 질문은 to=coordinator, 캡틴 전달은 to=captain 한 건으로 기록하고 연결 파일에 원질문의 시각·태스크·로그 행을 연결한다. 원문과 비밀은 복사하지 않는다. captain 수신자 행수는 captain 사건을 세며 실제 도달은 답/성공 전송 증거로 판정하고 원질문과 전달을 합산하지 않는다. 캡틴 답을 받은 코디네이터가 전달 질문에 대한 answer를 기록한 뒤 작업자에게 reply하고, 작업자는 원질문에 대한 answer를 한 번 기록한다. 두 question에는 두 answer가 대응해야 열린 대기가 남지 않는다. 답 사건에는 to를 붙이지 않는다.

합성 대조: 동일 요청 A의 coordinator 원질문 1행→captain 전달 1행과 수신자 생략 질문 B 1행이 있다면 수신자 행수는 captain1·coordinator1·생략1이다. 답/전송 근거가 없으면 이 행수로 실제 도달 개입1을 주장할 수 없다. 전체 기존 stats 질문 수는 3으로 그대로다. 전달을 포함한 합계 2를 캡틴 개입으로 세거나 B를 0으로 세면 실패다.

## 문서 업무 원장과 CLI 대응

baseline-ai-sql-client.json의 events 각 항목은 업무 시작/종료 사이만 포함한다. question.to는 project log의 to에 대응하고 answer는 같은 범위의 answer로 연결한다. approval은 CLI/사람 승인 근거, manual은 note와 Orca 메시지 시각으로 연결한다(새 manual CLI 종류를 만들지 않는다). review는 독립 검토 원문과 blocking·재검토, gate는 실행 명령·종료 코드에 대응한다. 문서 외 T01 사전 검토·기능 구현 사건은 포함하지 않는다.

사건이 없으면 원장 빈 배열과 구간의 P009 로그·Orca 메시지 조회를 근거로 두고, 접근할 수 없는 세션은 미확인 건수/범위로 구분한다. 수동 집계와 로그 장치 차이를 숨기지 않는다. T08도 같은 수동 원장과 to 로그/메시지를 대조한다.

## 비교 조건과 한계

기준선은 P009의 Codex Orca 작업자가 팀 배정 없이 ai-sql-client 문서 자료를 읽고 한국어 3,000~5,000자 내부 검토 메모 1건을 작성한다. T08은 동일 경로·자료 범위·분량·문서 게이트·별도 Claude 2단계 검토로 다른 운영 주제를 작성하고 ai-sql-client 팀 원본을 workerSpec prompt 방식으로 전달한다. 이는 prompt 역할 사용의 관찰이며 native 적재 증명은 별도의 호스트 실측 표로 판단한다.

기준선과 T08의 AGENTS·CLAUDE·관련 운영 지시 파일 해시와 차이를 보고한다. 경로가 같아도 T02~T07 변경으로 내용이 달라질 수 있다. P009에서 작성하고 대상 저장소는 읽기만 한다. 단일 표본·주제 난이도·누적 세션 맥락·측정을 아는 작성자의 자기 보고 편향 때문에 인과 추정이나 일반 생산성 순위를 만들지 않는다.

품질 합산은 실제 판정별로 사전 reviewer·구현 후 reviewer·tester의 blocking을 합한다. 같은 판정의 로그 요약과 원문을 다시 더하지 않는다. fail 뒤 다음 판정 호출만 재작업으로 세고 pass 뒤 should_fix 확인은 포함하지 않는다. 과거 묶음 로그의 stats 값은 참고치로 별도 둔다. P009 이후에는 captain 전달 질문 행이 추가되므로 과거 프로젝트의 전체 질문 사건 수와 직접 개입/생산성 비교를 하지 않는다. 수신자별 자동 집계·METRICS 기준 변경 주석·짝 불일치 경고는 T06 인계 사항이다.

캡틴 개입의 단일 합계에서는 같은 요청의 질문과 그 답인 승인/결정을 한 번만 센다. 질문·승인 각 열은 별도 기술값이며 서로 더하지 않는다. 병합처럼 질문 원장이 없는 별도 승인은 별개로 세되 연결을 모르면 총합은 미확인으로 둔다. 손작업도 동일 요청의 대행인지 연결 근거를 보고 중복을 제거한다. by는 기록자, to는 실제 수신자이므로 직접 캡틴에게 질문하는 일반 CLI 호출도 허용한다. by/to 조합 강제는 현재 계약에 없고 작업자 경유 규약과 수신자 근거를 별도로 검증한다.

## BR09 승인 뒤 요청 단위 도달 정의

최신 유일한 분류 정의는 BR01이다. 같은 요청을 ID로 묶어 캡틴 답 근거가 있으면 도달, 없고 to:captain 성공 전송 근거가 있으면 도달, 없고 실패 전송만 있으면 전송 실패, 그 밖은 미확인이다. captain 의도 로그만으로 도달을 세지 않는다. 실패 시도 수는 별도이며 성공 후에는 도달1이다. 후속 P002 대조 입력은 baseline-roblox-reachability-v2.json, 관측/미확인 경계는 reachability-contract-update.md다. 기존 수신자 축10/4/2와 도달 축10/0/0/6은 더하지 않는다. 코디네이터 답 확인4도 캡틴 답/전송 증거는 없으므로 전체 요청의 도달 축에서는 미확인이다. 일반 승인8은 질문과 겹치므로 다시 더하지 않고, 질문과 안 겹치는 병합 승인1 및 미확인 손작업은 별도 둔다.
