## 1단계 독립 목표 대조 (읽기 전용, 파일 수정 없음)

**읽은 범위와 노출 범위**
- 이 호출에서 파일을 직접 열지 않았고, 프롬프트에 붙은 `impl-diff.patch` 본문만 읽었다. TASK, 테스트 표, 작성자 자체 판정은 받지 않았고 읽지도 않았다.
- 호스트가 자동으로 붙인 `CLAUDE.md`/`AGENTS.md`, gitStatus, 사용자 이메일이 맥락에 있었다. 이메일은 쓰지 않았다.
- 읽기 전용이라고 해서 작업 문서 접근이 차단되거나 격리됐다는 뜻은 아니다.
- 테스트와 `npm run check`는 실행하지 않았다. 아래 판정은 diff를 읽은 결과이고, 실행으로 확인한 것은 아니다.

**목표 달성: 달성 (코드 읽기 기준, 실행은 미확인)**

**독립 목표 대조**
- **승인 대상만 추가:**
  - `workspace add`는 계획을 보여 주고 `[y/N]` 또는 `--yes`를 받은 뒤에만 등록한다.
  - `approveWorkspacePlan`은 확인 뒤 상태가 바뀌었는지 다시 비교한다.
  - 비활성 후보와 복제된 AGENT 정의는 거부한다.
- **기존 ID 없는 설정 보존:**
  - `registryId`는 선택 필드이고, 이름이 같아도 디렉터리 신원이 같을 때만 승격한다.
  - 승격 때 Telegram 결속을 설정보다 먼저 보강한다.
- **포트 소유자만 설정 쓰기:**
  - 정지 중에는 `acquireInstance`로 소유한 구간에서만 쓴다.
  - 실행 중에는 Gateway를 거쳐 daemon의 `tx` 안에서 쓴다.
  - install 마법사의 설정 쓰기도 `withStoppedDaemon`으로 묶었다.
- **ID·경로·동일성 비교:**
  - 기동은 `reloadAllowed`에서 비교한다.
  - 수락과 조회는 `resolveTarget`과 `workspaceRootInfo`, 버튼·토픽 매칭에서 비교한다.
  - 실행 직전은 `checkIdentity`에서 비교한다.
  - 이동한 옛 경로는 `registeredWorkspaceRoot`의 경로 불일치로 막힌다.
- **재승인 뒤 토픽 이어 가기:** 같은 ID로 다시 add하면 `bindingMatches`가 기존 `{name, registryId}` 결속을 인정한다. 다른 ID의 결속은 차단한다.
- **인증·Origin·정보 비노출:**
  - Gateway는 기존 토큰과 Origin 거부를 그대로 쓰고, 새 메시지는 인증 뒤 경로로만 열린다.
  - 오류 문구는 `workspaceErrorText`로 일반화해 경로를 노출하지 않는다.
- **설정 실패 상태:** 저장 실패는 `ok:false`로 보고하고 성공으로 표시하지 않는다. 일부 단계만 반영된 경우에는 안내 문구를 낸다.

**지적**

1. **should_fix** — 어댑터의 FS 워커 격리가 약해졌다. `workspaceRootInfo`가 `workspaceProblem`을 호출하면서, 요청마다 이벤트 루프에서 동기 파일 호출(등록부 읽기, `realpath`, AGENT 검증)이 일어난다. 원래 이 함수는 "파일 시스템 호출 없음"이 계약이었고 느린 파일 시스템은 `FsWorker`와 타임아웃으로 격리했다. 지연된 마운트에서 daemon 전체가 멈출 수 있다. 신원 확인을 워커로 옮기거나 짧은 캐시를 두고, 이 계약 변경을 문서에 남기는 것이 좋다.
2. **should_fix** — 기동 시점의 동일성 기준이 없다. `reloadAllowed`에서 `workspaceProblem`은 `allowedRoots`를 비우고 다시 만드는 도중에 호출되므로 `expected`가 항상 비어 있다. 기동 때는 등록부 경로와 AGENT ID만 비교하고 dev/ino 비교는 건너뛴다. 실행 중에 쓰이는 baseline은 기동 직후의 현재 상태일 뿐, 승인 시점의 신원이 아니다. `reloadAllowed`가 다시 불리면 바뀐 디렉터리를 그대로 기준으로 삼는다. 의도라면 문서에 명시하고, 아니라면 승인 신원을 영속화해야 한다.
3. **note** — Gateway `workspace_add`는 토큰 소지자(기기 관리자)가 이미 활성 등록된 ID를 요청에 담으면 사용자 확인 화면 없이 추가할 수 있다. 승인 증명은 CLI의 `[y/N]`·`--yes`에만 있다. 토큰 소지자가 관리자라는 모델에서는 수용 가능하지만, 이 점을 명시하면 좋다.
4. **note** — 전역 등록부와 `.pace/AGENT.md` 생성은 Gateway 경로에서 daemon 소유 구간 밖(CLI 쪽 `approve`)에서 일어난다. 설정 쓰기는 아니라서 목표에는 맞는다. Gateway 단계가 실패하면 등록만 남고, 이 경우는 안내 문구가 있다.
5. **note** — `forumTitle`이 확인 화면 표시를 위해 실제 Telegram `getChat`을 호출한다. 범위 밖이라는 "운영 호출"이 개발·테스트 중 호출을 뜻한다면 맞다. 제품 동작으로서의 호출까지 가리킨다면 범위 해석을 확인해야 하므로 사용자에게 물어볼 항목이다. 현재는 2.5초 타임아웃, 토큰·chat id 제거, 실패 시 일반 문구로 처리하고, 테스트는 fake fetch를 쓴다.
6. **note** — `telegram init`/`reset-offset` 등 기존 쓰기 경로가 포트 소유를 요구하는지는 이 diff만으로 확인할 수 없다. 이번 변경은 새 쓰기 경로만 소유 규칙으로 묶었다.

**전략의 다른 길:** 승인 시점의 dev/ino를 설정에 저장하는 방법이 있었다(2번과 연결). 이번 선택은 설정 형식 변경이 작아 합리적이다. 다만 재기동 뒤 신원 비교가 약해지는 대가가 있다.

**빠진 것·추적성:** 목표의 각 항목(승인, 보존, 소유, 4개 비교 지점, 재승인, 인증, 실패 상태)이 코드와 테스트로 추적된다. 빠진 것은 위 1·2번뿐이고, 둘 다 blocking은 아니다.

**올릴 단계:** 올릴 계획·목표 수정은 없다. 1·2번은 구현 단계에서 처리하면 된다. 5번의 범위 해석만 사용자에게 확인한다. 2단계 작업 문서 검토는 이 호출이 아니라 호출자가 별도로 전달해야 하고, 이 호출만으로 두 단계가 실행됐다고 주장하지 않는다.
