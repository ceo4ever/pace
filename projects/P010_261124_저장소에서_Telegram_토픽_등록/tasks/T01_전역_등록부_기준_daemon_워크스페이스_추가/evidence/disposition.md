# T01 독립 검토 지적 처리

## 사전 검토

- [1단계 원문](../review-records/R1.json)은 Claude로 `pace agent verify --kind task`를 실행했다. TASK 해시와 제공자, 판정은 [사전 검토 기록](../PRE-REVIEW.json)에 연결했다.
- 1단계 세션 재개가 등록된 ID를 찾지 못해, 1단계 판정 원문과 PROJECT·BR 대조 지시를 새 Anthropic 세션에 넘겼다. [2단계 원문](pre-review-stage2.json)에서 blocking 0을 확인했다.
- 마법사의 기기 설정 쓰기와 offset 초기화에 포트 소유권을 적용했다. 승인한 이름·ID·경로·디렉터리 신원을 재검증한다. 대기 작업의 실행 직전에도 확인한다.
- 확인 화면, Gateway의 인증·Origin 거부, 점유된 포트에서 직접 쓰지 않음, 파일 저장 실패, 동일 디렉터리의 기존 결속 보강과 다른 경로의 거부를 자동화했다. [검증 코드](../../../../../test/daemon-workspace.test.ts).
- 새 명령의 첫 단위 실행은 도입 전 exit 1로 실패했다. 기대값은 계획 출력 exit 0이었고 실제 CLI는 명령이 없어 exit 2를 반환했다.

## 구현 검토

- [1차 원문](reviewer-r1.md) 지적에 따라 승인한 디렉터리 신원을 설정에 저장하고, Telegram의 파일 읽기 전후 등록부 검증을 파일 워커에 넣었다. 설정과 토픽의 쓰기 경합도 별도 확인했다.
- [재검토 1단계 원문](reviewer-r2.md)을 회수한 뒤 [재검토 2단계](reviewer-stage2.json)는 같은 제공자의 별도 세션에서 PROJECT·BR01·TASK와 대조했다. blocking 0과 should_fix 0을 확인했다.
- `--yes`는 BR01에서 합의한 명시 승인 방식이다. 에이전트가 사용하는 경우 사람이 계획을 확인하도록 운영 안내를 유지한다. 직접 쓴 `registryId`에 승인 신원이 빠진 데이터는 `workspace add`로 신원을 보강할 수 있다.
- 코어 요청과 시작 직전에는 기존 동기 경로 확인에 등록부·정의 대조가 추가된다. Telegram 직접 파일 읽기는 작업 스레드에서 마감을 적용한다.
- 구현 검토 도구의 원본에는 코드 diff 전체가 포함된다. 비밀 검사기가 코드 표현식을 비밀 의심 형식으로 분류해 판정 본문 원문을 위 Markdown으로 이관했다. diff와 도구 원장은 로컬 임시 검토 폴더에 보존했다. 커밋의 소스 diff로 변경 범위를 재현할 수 있다.
- [독립 tester 1차](tester-orca.md)는 62건 통과와 별개로 승인 거부 무변경·등록 이름 재사용·실패 복구·다른 활성 ID 결속 차단의 시험 공백을 지적했다. 보강 후 [2차](tester-orca-r2.md)에서 T-3의 실패가 설정을 읽는 단계에만 닿았음을 확인했다. 실제 원자적 교체 지점에서 EIO를 주입한 뒤 [3차](tester-orca-r3.md)가 63건·T-1~T-4 통과로 판정했다.
- [최신 전체 재검토](reviewer-r3-stage2.json)의 운영 문서 지적을 반영했다. 설치 마법사의 세부 쓰기와 offset 명령을 모두 점유 중에 다시 실행하는 매트릭스는 추가하지 않았다. T01 기준의 쓰기 소유권은 CLI·Gateway 경합과 마법사의 기기 이름 쓰기 거부로 검증했다.
- [원자적 교체 시험 독립 대조](reviewer-atomic.md)는 blocking 0이다. 구형 토픽 승격 뒤 설정 실패가 겹치는 중간 상태, 임시 파일의 개별 개수와 드라이버 내부 오류 코드 문구는 이 시험의 관측 범위에 포함하지 않았다. 시험은 새 항목에 대해 원자적 교체 실패·기존 설정 및 코어·토픽 파일 보존·같은 요청 재시도를 직접 검증한다. 임시 파일 제거는 `writeFileAtomic`에 위임한다.
