# P010 T02 공통 구현 — 독립 1단계 목표 대조

## 첫 판단
- **독립 목표 대조**: 산출물의 실제 흐름은 상위 목적과 맞다. 다음 순서로 이어진다.
  1. 사용자가 계획을 확인한다.
  2. CLI가 `--yes` 또는 `[y/N]` 승인으로 요청을 만든다.
  3. 코어가 등록 신원을 대조한다.
  4. 포럼 증명(`forumProof`)이 일치할 때만 `createForumTopic`을 호출한다.
  5. 첫 조회가 읽기 전용으로 실행된다.
- **목표 달성**: **달성(코드·모의 시험 수준).** 실제 P-5는 **미확인**이다. 사용자도 미검증이라고 밝혔고, 나도 시험을 실행하지 않았다.
- **올릴 단계**: 2단계 작업 문서 검토로 올려도 된다. 아래 should_fix 항목은 호출자가 판단해 반영하면 된다.

## 근거 (diff 정독 기준)
- **원자적 의도 저장**: `createWorkspaceTopic`이 API 호출 전에 `commit`으로 `provisioning[name] = registryId`를 디스크에 저장한다. 저장에 실패하면 `intent-write-failed`로 생성하지 않는다. 시험에서 Bot API가 요청을 받은 시점의 디스크 의도를 확인한다.
- **중복 없는 회복**
  - 응답이 유실되거나 결과가 불명하면 의도를 남기고 `/bind`로만 회복한다.
  - 이름·스레드 검증이 어긋나도 `unknown`으로 처리하고 재발행하지 않는다.
  - 결속 저장이 실패하면 commit이 스냅숏으로 되돌려 의도가 유지된다.
  - 같은 이름의 요청은 `topicRequests`로 합류시킨다. 재기동 뒤에도 재발행하지 않는 시험이 있다.
  - 정리 저장이 실패해도 의도가 남아 중복 생성을 막는다.
- **인증·권한**
  - Gateway는 토큰 인증과 Origin 거부를 유지한다.
  - `forum` 필드는 64자리 hex 형식만 받는다. `null`이면 `unconfirmed-forum`으로 처리한다.
  - General의 `/new <이름>`은 daemon 설정에 있는 이름만 받고, 등록부·승인 경로 불일치(stale)는 거부한다.
  - 접근 권한은 읽기 전용 기본값을 유지한다. `/write` 승인 경계도 시험이 확인한다.
- **정보 비노출**
  - Telegram API 오류 원문을 코드(`TopicState`)로 대체했다.
  - 로그의 `commit_failed`에서도 오류 원문을 뺐다.
  - `createForumTopic`에는 `chat_id`와 `name`만 보낸다.
  - 시험이 경로·토큰·chat id·토픽 번호의 비노출을 대조한다.
- **전략의 다른 길**: 의도를 파일에 두고 단일 비행(single-flight)으로 중복을 막는 현재 전략이 타당하다. 대안인 "생성 전 포럼 토픽 조회"는 Bot API에 목록 조회가 없어 불가능하다. 현재 선택이 맞다.
- **결정 추적**: `forumKey`는 "포럼이 바뀌면 토픽 번호를 재사용하지 않는다"는 목표로, `forumProof`는 "확인한 포럼만"이라는 목표로 이어진다. 두 결정 모두 목표까지 추적된다.

## 지적

1. **should_fix** — `forumKey` 불일치 복구 경로가 없다.
   - 어댑터 기동은 거부되는데, 승인된 재설정 수단이 없다. `reset-offset`도 `forumKey`를 보존한다. 문서는 "운영자가 확인"이라고만 한다.
   - 포럼을 정당하게 바꿔야 할 때 상태 파일을 손으로 고치게 된다.
   - 명시적 재결속 명령이나 문서의 구체적 절차가 필요하다.

2. **should_fix** — `forumKey`가 없는 기존 상태를 현재 포럼으로 소급해 찍는다(`adapter.ts` 로드 분기).
   - 과거에 chat을 바꾼 상태 파일이라면 다른 포럼의 결속표가 현재 포럼의 것으로 승격된다.
   - 이 위험이 있다는 점을 문서에 적거나, 첫 찍기 전에 확인을 거치는 게 안전하다.

3. **should_fix** — `--yes` 경로에서 사람이 포럼 이름을 본다는 보장이 없다.
   - `--yes`는 미리보기를 건너뛰고 `resolveForum`을 호출한다. 그래서 "사용자가 확인한 포럼"은 절차(문서)에만 의존한다.
   - 기계 검증은 설정된 chat과 daemon의 chat이 같은지만 확인한다. 사람이 승인한 포럼과 같은지는 확인하지 않는다.
   - 포럼 증명을 계획 단계에서 `--yes`에 실어 보내는 방식(예: 미리보기가 증명 접두를 출력)을 검토할 만하다.
   - 사용자 승인 범위의 결정이므로 합의가 필요하다.

4. **should_fix** — 일반 `/new <이름>` 경로에서 `ensureWorkspaceTopic`이 거부(예: fs 워커 오류)로 끝나면 `newCommand`가 잡지 않는다.
   - 사용자 응답 없이 디스패치 오류가 될 수 있다. Gateway 쪽은 `try/catch`가 있다.
   - 가장 바깥에서 `unknown` 계열로 정리하길 권한다.

5. **note** — `rejectedTopicState`가 메시지 정규식으로 원인을 분류한다. `definite`의 정의(예: 429·5xx 처리)는 이 diff에 없어 확인하지 못했다. 429·5xx가 definite로 분류되면 의도가 지워져 중복 생성 위험이 생긴다. `api.ts`를 2단계에서 확인해야 한다.

6. **note** — 시험 공백이 있다.
   - 서로 다른 `registryId`가 같은 이름으로 경합하는 `conflict` 분기 시험이 없다.
   - `[y/N]` 대화형 승인의 포럼 증명 일치 시험이 없다.
   - `forumKey` 소급 찍기 시험이 없다.

## 한계와 노출 범위
- 읽은 것은 위 diff뿐이다. 프로젝트 소스는 열지 않았고 아무 파일도 고치지 않았다. 테스트도 실행하지 않았다.
- `api.ts`의 `definite` 정의, `registerWorkspace`의 코어 신원 대조, `fsworker`의 `validate` 구현은 diff 밖이라 검증하지 못했다.
- 호스트가 자동 첨부한 맥락(CLAUDE.md·AGENTS.md, git 상태·최근 커밋, 사용자 이메일)은 이 검토에 노출됐다. TASK·테스트 표·작성자 자체 판정·지적 대응은 받지도 읽지도 않았다.
- 이 호출은 1단계뿐이다. 2단계는 호출자가 별도로 진행해야 한다. 검토 주체가 바뀌면 제공자·독립성 수준·변경 이유를 기록해야 한다. 읽기 전용이 완전 격리를 뜻하지는 않는다.
