## 1단계 독립 목표 대조 (읽기 전용)

**읽은 범위**
- 호출 프롬프트에 포함된 diff 전문만 읽었습니다. 저장소 파일, TASK 문서, 테스트 표, 작성자 판정은 읽지 않았고 도구도 호출하지 않았습니다.
- 자동 부트와 메모리는 "자식 세션 부트 생략" 표시만 보였습니다. 호스트 첨부 맥락인 `AGENTS.md`와 `gitStatus`는 노출됐습니다.
- 테스트는 실행하지 않았습니다. 아래 판단은 코드 읽기에 근거합니다.
- 이 호출은 1단계만입니다. 2단계는 실행하지 않았습니다.

**독립 목표 대조**
- 상위 목적: 미등록 저장소에서 승인된 로컬 등록 한 번으로 read-only Telegram workspace에 안전하게 연결한다.
- 이번 초점: 포럼 확인 실패 뒤 기존 결속 표시, 생성 결과 불명의 고정 진단.

**목표 달성: 달성** (코드 읽기 기준, 실행은 미확인)

**근거**
1. **포럼 확인 실패 뒤 기존 결속 표시**
   - CLI는 포럼 확인에 실패하면 `proof=null`을 보냅니다.
   - 데몬은 실행 중이어도 `forum !== forumProof(secret)`이면 `unconfirmed-forum`을 돌려주고 생성은 시도하지 않습니다.
   - `bound`는 `isWorkspaceBound(entry)`로 먼저 구해 둡니다. 같은 registryId의 결속이 이미 있으면 `기존 결속`과 이번 사유를 함께 출력합니다. 사실과 일치합니다.
   - 어댑터가 없거나 정지 상태일 때도 같은 경로를 탑니다.
   - 포럼이 바뀐 경우 어댑터가 기동을 거부해 `미결속`과 `unavailable`이 나옵니다. 거짓 결속 표시는 없습니다.
   - 오프라인 경로는 `forumKey` 일치를 확인한 뒤에만 `기존 결속`을 표시하고, 불일치하면 `상태 확인 불가`로 보수적으로 처리합니다.
2. **생성 결과 불명**
   - 생성 전에 디스크에 의도(registryId)를 먼저 저장합니다.
   - 불명, 저장 실패, 중단 뒤 재시도 경로는 모두 Bot API를 다시 부르지 않고 고정 문구 `unknown`을 냅니다. 재기동 뒤에도 의도가 남아 중복 생성이 없습니다.
   - 같은 이름의 동시 요청(General과 Gateway)은 `topicRequests`로 합류하고, 다른 registryId면 `conflict`로 거부합니다.
3. **비노출**
   - API 원문 대신 결과 코드만 전달합니다. `commit_failed` 로그에서 오류 원문을 제거했고 로그는 `reason` 고정값만 씁니다.
   - 테스트에 `hiddenValues`로 home, 경로, 토큰, chat id, 스레드 ID 비노출 단언이 있습니다.
4. **범위**
   - General `/new`는 경로 입력을 막고 daemon에 이미 있는 이름만 받습니다. 새 저장소 등록은 로컬 승인 한 번으로 모입니다. 목적과 일치합니다.

**지적**
- **note**: Gateway 경로에서 이미 결속된 경우(`already-bound`)는 `기존 결속`이 아니라 `결속 완료`로 표시됩니다. `docs/DAEMON.md`의 "기존 결속" 설명은 포럼·어댑터 확인 문제가 있을 때로 한정되어 모순은 아닙니다. 다만 사용자가 "새로 만들었는지"와 "원래 있었는지"를 구분하지 못합니다.
- **note**: 버전 이전의 레거시 의도 `true`가 남은 상태에서 registryId가 있는 add를 하면 `conflict` 문구가 나옵니다. 원인 설명이 약하고 `/bind`로 복구할 수 있다는 안내가 없습니다. 드문 경로입니다.
- **note**: Gateway가 생성 호출을 기다리는 시간은 CLI 38초가 상한입니다. API `totalMs`가 이보다 길면 CLI는 연결 끊김 문구를 내고, 데몬은 계속 진행해 결과가 반영될 수 있습니다. 안내가 "같은 add로 확인"이라 안전하지만, 실제 `totalMs` 값은 diff에서 확인하지 못했습니다.
- **note**: 데몬이 어댑터 없이 떠 있을 때 상태 파일에 같은 registryId의 결속이 있어도 `미결속`으로 표시됩니다. `docs/DAEMON.md`의 "daemon이 이미 알고 있으면"과 일치하지만 사용자에게는 보수적으로 보입니다.

**전략 대안**
- 포럼 증명을 token 포함 해시로 대조하는 방식은 적절합니다. 대안으로 데몬이 직접 getChat을 호출할 수도 있지만, 그러면 CLI가 승인한 포럼과 실행 중 포럼의 동일성을 확인하기 어려워집니다. 현재 방식이 더 낫습니다.

**빠진 것**: blocking 수준은 없습니다. 실제 Bot API와 실행은 확인하지 못한 한계가 있습니다.

**올릴 단계**: 올릴 단계 없음. 2단계 작업 문서 검토는 호출자가 별도로 진행합니다.
