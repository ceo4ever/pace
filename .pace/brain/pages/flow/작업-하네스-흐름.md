## 흐름

| 단계 | 어디서 | 명령 | 게이트·기록 |
|---|---|---|---|
| 정의 | main | `pace project new "<이름>" [--from <BL 폴더 또는 앞부분>]` | PROJECT.md(목적·재료·기준 P-n·설계·바꿀 정본·태스크 표). 재료에 브레인 관련 페이지 후보를 자동으로 넣는다 |
| 착수 결정 | main | 백로그 지시·대화로 확정한 출처 | 결정 메모에 근거를 남기고 바로 start. html-plan은 복잡한 설계를 보여 주는 선택 도구 |
| 착수 | main | `pace project start P###` | 상태 `정의` → `진행`, 정의 커밋, worktree `../<저장소>.wt/P###`·브랜치 `project/P###`, 정의서의 `worktree 준비` 실행. 출처를 CLI decision으로 기록하고 Git 내부 commit-msg 훅을 설치한다. Orca 안(터미널·채팅 세션 — `ORCA_STRUCTURED_SESSION=1`, 채팅 코디네이터는 폴링 없이 Orca가 깨울 때 처리)이면 작업자 세션을 띄우고 main은 코디네이터. 작업자 도구는 `--agent` > PROJECT.md `- 작업자:` > 정의서 `작업자 도구:` > 지금 세션 |
| 태스크 | worktree | `pace project task P### "<이름>"` → 구현·테스트(tester ∥ reviewer 새 맥락) → TASK-CLOSE → `pace project check P### T0n` → `pace project done P### T0n` → 커밋 | 표의 `대기` 계획 행은 그 번호로 연다. 프로젝트 브랜치의 태스크 태그 커밋은 훅에서 check를 거친다. check = 판정 통과·기준 T-n 모두 통과·4절·증거 파일. done = check 통과 때만 TASK.md·표 상태, 같은 번호 BR·BACKLOG.md 표, 앞 태스크 커밋 칸 |
| 마감 | worktree | `pace project finish P###` | 태스크 check·완료 태스크 태그 커밋 존재, PROJECT-CLOSE(P-n·보안·정본 반영·브레인 행), 정본 반영 ↔ diff, 브레인 갱신 후보(바뀐 파일을 근거로 가진 페이지), 비밀 노출, 브레인 lint, `보안 검사`, `의존성 감사`(선언됐고 잠금 파일이 base 대비 바뀐 때만), 목차, main 위로 rebase, `검사`, 커밋 칸 해시(rebase 뒤), PROJECT-CLOSE 지표 링크·해석 관문 및 별도 METRICS.md·projects/METRICS.md 재생성, `병합 대기` 커밋 |
| 병합 | main | `pace project merge P###` → 승인 → `--yes` | 미리보기는 환경 선언 변경과 지워질 무시 항목(`ls-files --directory` — 무시된 폴더는 `node_modules/` 한 줄, 낱개 파일은 이름, 앞 20곳·총수)을 표시. ff-only, 병합 승인 대기·전체 경과와 상세/비교 지표 재생성, worktree·브랜치 정리, 상태 `완료` 커밋 |
| 기록·지표 | 어디서나 | `pace project log P### [T##] --type …`, `pace project stats P###` | 단계 시작·종료·게이트·승인은 CLI가, 결정·변경·리뷰·질문은 에이전트가 `log.jsonl`에. stats는 러닝 시간(승인 대기 분리)·게이트 실패·도구별 토큰 |

## 왜 이렇게 나눴나

- 착수 승인 대기를 없애고 확정된 출처를 바로 수행 근거로 쓴다(사용자 결정). 사람 승인은 병합·배포에 남긴다.
- 엔진은 각 LLM 도구(계획·서브에이전트·리뷰·브라우저), PACE는 계약·게이트·기록만 — 도구가 바뀌어도 기준이 흩어지지 않게.
- 글쓰기는 에이전트, 번호·폴더·형식 확인·git은 명령 — 기계적 실수를 명령이 막는다.
- worktree 세션이 프로젝트를 맡는다 — main 세션이 절대 경로로 worktree를 고치면 실수가 잦았다(실측).
- 정의서는 `docs/README.md` 하나로 고정하고 기준 문서는 문서 표의 용도·적용 범위로 고른다.

## 관문의 한계와 보호

약속으로만 남던 커밋 순서를 commit-msg 훅과 finish의 태그 커밋 존재 검사로 보완했다. 사용자 훅·링크·git 외부·상대 hooksPath는 보존하고, pace 부재는 경고 후 통과시켜 기존 환경을 깨지 않는다. 훅은 우회 가능하므로 보안 경계가 아니라 실수 예방이며, finish도 완료 태스크에 태그 이력이 있는지만 확인한다. 훅에서 check할 때는 로그를 쓰지 않아 staged 커밋 뒤 미커밋 로그를 만들지 않는다.

승인된 구현을 main에 먼저 반영한 프로젝트에서는 완료 태스크의 커밋이 main..HEAD 구간에서 사라져도 현재 HEAD의 조상으로 남는다. 태그 커밋 존재 검사는 HEAD에서 도달 가능한 이력으로 확인한다. main 선반영을 누락으로 오인하지 않으며, 태그 자체가 없거나 다른 브랜치에만 있는 커밋은 계속 거부한다. 선반영 마감에서 재현했고 회귀 검사로 세 경우를 구분한다.

선언 명령은 실행 전에 출력하고 작업본 선언이 base와 다르면 base 것을 사용한다. base 선언이 실제로 없으면 작업본 것을 실행하지만 조회 실패는 부재와 구분해 중단한다. 작업본이 바꾼 명령 문자열을 실행하지 않기 위한 보호이며, 명령이 호출하는 작업본 스크립트·도구·환경까지 격리하지는 않는다.

## 백로그·브리프를 나눈 이유

2026-10-25 백로그가 폴더와 파일을 함께 뜻하고 후보 한 파일에서 프로젝트 여러 개가 나온 혼선을 줄이기 위해 **백로그(BL 폴더) → 프로젝트, 브리프(영어 brief, BR 파일) → 같은 번호 태스크**로 맞췄다. 개요는 BACKLOG.md, 이름은 BL{YYMMDD}_{일자별 NN}_이름/BR{NN}_이름.md이다. `new --from`은 BL 폴더·유일 앞부분만 받고 BACKLOG.md 출처와 BR 번호의 T 대기 행을 만든다. BR 제목도 브레인 후보 검색에 넣는다.

끝난 백로그에는 브리프를 덧붙이지 않는다. 새 묶음은 새 BL, 작은 개선은 메모리 idea나 대화로 발의한다. 기존 후보 모음은 남은 후보를 idea로 옮겨 닫았다. 과거 프로젝트의 출처와 5칸 표는 이력을 보존하며, 새 표는 4칸이다. `done`은 BL 출처에서 T01→BR01과 BACKLOG 현황을 함께 바꾸고, 파일·행 누락이나 외부 링크에서는 상태를 쓰기 전에 멈춘다. 검증: test/backlog.test.ts·test/project-harness.test.ts·test/brain.test.ts.

## 작업자 모델 설정

작업자 모델·effort는 `PACE_HOME/worker-settings.json`에 사용자 공통으로 보관하며 `pace worker show|set|reset`으로 관리한다. 실행별 옵션이 공통 설정보다 우선하고, `--effort default`는 공통 effort를 무시한다. 초기 모델은 src/core/worker-settings.ts의 defaults를 따르며 실제 해석값은 pace worker show로 확인한다. 기본값을 복제해 고정하지 않는다. 설치는 `app/`만 교체해 이 설정을 보존한다.

## 형식 게이트와 독립 목표 대조

문서 템플릿을 개발 업무의 예시로 명시하고 명령용 최소 구조를 보존했다. 하네스를 쓰지 않는 작은 일은 대화로 충분하고, 쓰는 경우 본문/산출물 형식은 업무에 맞게 고른다. 정본은 skills/pace-project-dev/references/document-shape.md다. 위 명령 표와 BL/BR 상태 매칭은 바뀌지 않았다.

검토 지침의 정본은 skills/pace-project-dev/references/goal-review.md다. 작성자 기준표를 먼저 읽으면 그 기준에만 맞는 결과를 목표 달성으로 오인할 수 있어 상위 목적/목표+결과로 첫 판단을 회수한 뒤 작업 문서와 대조한다. 상위 목적은 기준이고 어긋난 목표/전략/계획이 수정 대상이다. 합의 변경은 사용자에게 올린다. 마감의 목표 달성 판정은 기준 대조와 별개이며, 하네스의 형식 통과가 의미 판정을 대신하지 않는다. 기존 agent verify는 첫 목표 대조 호출에 재사용하고 두 번째 작업 문서 인계는 호스트 검토 절차로 한다. 프롬프트만으로 파일 접근이나 두 단계 실행이 강제됐다고 주장하지 않는다.

### 독립 검토의 사전 노출과 원문 보존

실제 인계 첫 시도는 자동 부트가 작성측 성공 요약을 전달해 독립 첫 판단으로 인정하지 않았다. 자식 부트 억제 뒤에도 호스트 하네스의 git 상태/커밋 제목·자동색인 등은 남을 수 있어 자동맥락과 읽은 범위도 고지한다. 새 맥락·첫판단 회수 후 작업문서 공개는 관측할 수 있지만 완전 격리/일반 효과를 보장하지 않는다. 같은 검토자가 수정분을 다시 읽는 검증도 새 블라인드 실험이 아니다.

첫 판단 출력명을 재사용해 앞선 시도 원문을 덮어쓴 사고가 있었다. 검토자·시도별 고유 경로를 지정하고 기존 파일이 있으면 덮어쓰지 않는다. 유실된 원문은 추정 복원하지 않고 실제 실패 보고와 유실 고지를 별도 출처로 보존한다.

기존 하네스는 목표 달성 절의 존재/값/의미를 감시하지 않는다. 목표 미달/미확인일 때 작성자·독립검토·PM이 TASK-CLOSE 판정을 막힘으로 두어야 하고, 그 판정에 대한 기존 check/done 거절이 연결된다. 잘못 통과라고 썼을 때 기계가 목표 미확인을 잡아 준다는 보장은 없다.

## 검증 책임과 중복 실행

허브와 워크트리의 검토 배정이 섞이고, finish 성공 출력의 상세 로그를 확보하려 동일 전체 검사를 반복하려는 일이 있었다. 검증 책임의 정본은 `skills/pace-project-dev/references/verification.md`의 역할과 검증 책임이다. 워크트리 PM이 검증·독립 검토·finish를 맡고 허브는 대상·결과·증거·미해결 사항을 확인해 승인된 병합을 수행한다.

필수 finish 검사는 유지하되, 이미 실행·통과가 확인된 동일 대상의 검사를 상세 로그 확보만을 위해 반복하지 않는다. 관련 변경이나 구체적 검증 누락이 생겼을 때 사유·범위·담당을 정해 재검사한다. main 직접 작업과 도구 권한 때문에 허브가 호출을 대행하는 경우에도 검증 소유자를 구분한다.

## 사전 검토 기록 관문

새 TASK의 v1 마커와 PRE-REVIEW.json은 최종 검토 판정·blocking·TASK 상태 외 본문 해시·내부 증거 파일을 check/done/finish와 커밋 훅에서 확인한다. 변경 후에는 새 대상에 대한 검토가 필요하며 기존 마커 없는 태스크는 옛 검사로 호환한다. 작성자와 검토 제공자·대체 사유·재검토 연속성을 기록으로 대조한다.

이 관문은 실수 예방이다. 마커와 기록을 함께 지우거나 기록을 위조할 수 있고 검토 원문의 진위·의미·실제 구현 전 시점이나 같은 세션 여부는 검증하지 못한다. 독립 검토와 의미 판정은 PM의 책임이다. 정본은 skills/pace-project-dev/references/reviewer.md, 근거는 src/project/pre-review.ts와 test/pre-review.test.ts다.

## 프로젝트별 검사 선택

`.pace/test-map.json`에 수동으로 단위·공통을 선언한다. 선택은 전체 회귀가 아니며 미분류·미지원·전제 미확인은 성공이 아니다. `pace test all`은 기존 검사 선언의 base 우선 경계를 재사용한다. Node의 빈 테스트 파일은 파일 래퍼가 통과로 집계될 수 있으므로 실제 테스트 요약을 구분한다. 테스트 실행은 신뢰 경계가 아니며 Python 테스트가 결과 채널을 위조할 수 있다. [근거: src/test-runner/, skills/pace-project-init/references/test-map.md]

## Windows의 선언 명령과 사전 검토 해시

Windows에서는 PATH의 절대 경로에서 찾은 Git의 설치 경계 안에서 sh를 찾아 절대 경로로 실행한다. 셸을 찾지 못하면 실패 원인을 출력한다. 선언 자체는 POSIX 셸 의미를 유지하며 임의 현재 폴더의 sh를 우선하지 않는다. 사전 검토 본문 해시는 CRLF를 LF로 정규화해 계산하므로 Windows 체크아웃에서 기존 LF 기록과 일치한다. 정규화 전 CRLF 원본 해시로 저장된 기록은 재검토해야 한다. ## 증명 범위와 결정 기록 보강

P008의 TASK 형식 v2는 기준·테스트 앞에 증명 범위와 판정 주체를 두고 게이트·verify·수동 reviewer가 같은 표지로 호환 경계를 읽는다. 구조 검사와 의미 판정을 분리하고, 구조 누락 단건 뒤는 전체 검토로 열어 미평가 안전을 숨기지 않는다.

## 프로젝트 업무 역할과 전달/관측 경계

작업자 도구와 팀 구성원 이름은 다른 선택이다. 구성원은 start --role > PROJECT 머리의 작업자 역할 > 없음이며 자동 lead를 만들지 않는다. 기존 worktree에 역할을 명시해 실행하려면 --launch가 필요하고, 단순 기존 경로 안내는 새 실행/적재를 뜻하지 않는다. 프로필 파일을 바꾸거나 native shared settings를 교체하지 않고 원본 읽기 지시와 별도 model/effort 인자를 전달한다.

새 branch는 체크아웃될 커밋 원본, 복구 branch는 해당 ref, 기존 worktree는 실제 실행 checkout의 역할/PROJECT를 읽는다. 준비와 병합 뒤 실행 직전에 지문/설정을 다시 확인하고 달라지면 작업자를 띄우지 않고 worktree를 보존한다. 역할 tier의 model은 사용자 tier override 다음 일반 model/default, effort는 tier override 다음 tier 문자열이며 명시 옵션이 각 필드에 우선한다. effort default는 인자 생략이다.

start의 role 객체는 전달 상태와 실제 런타임 관측을 구분한다. planned/arguments/unconfirmed/rejected와 runtimeObserved=false는 사건 작성 시점의 사실이고, 세션 model/effort·역할 행동은 후속 증거로 대조한다. command ok와 worker 실행 성공도 다르므로 rejected를 성공으로 세지 않는다. 기본값과 같은 관측만으로 설정 인자의 인과 효과를 주장하지 않는다. prompt/tools 안내는 호스트 권한 제한이 아니고 역할 정의도 보안 경계가 아니다.
