## 결정

독립 검토가 같은 대상에서 거듭 fail하면 지적을 하나씩 막는 땜질이 반복된다(P005 T04 사전 검토 v2 9회·v3 11회, P001 14회). P007은 이를 도구와 스킬로 끊었다. 아래 P007 단계는 예산 제도가 적용되는 태스크·백로그 밖의 일반 산출물에 유지된다.

- **원장을 유일 근거로**: `pace agent verify`가 대상 폴더 `REVIEW-LOG.jsonl`에 판정을 자동으로 쌓고 결과·대상 스냅숏을 `review-records/`에 남긴다. 작성자 수작업 기록(PRE-REVIEW 시도)은 원장에서 옮겨 적는다.
- **재검토 기준점은 도구가 고른다**: 마지막 pass·결정·진단 뒤 구간의 가장 최근 fail. 직전 원문과 바뀐 줄을 주고 "직전 blocking 해소와 그 수정의 새 결함만" 판정하게 한다(현재 산출물 전체는 맥락). 호출자가 기준 기록을 고르게 하면 오래된 기록을 넘길 수 있다.
- **단계**: 연속 3회 fail이면 diagnose(원인 층 structure·planning·design·other 진단), 진단 뒤 fail이면 ask_user(결정 필요 — 영향 분류로 PM/user 선택). 단계를 연 호출은 종료 0과 `escalation`, 다음 호출은 종료 16.
- **버린 길**: 단계와 무관한 무효 처리(`--void`)·호스트와 verify를 섞어 PM이 손으로 세기 — 원장 옆에 평행 상태를 만들어 단계 우회·기준점 불일치가 생겼다. void는 normal 단계의 실행된 fail만.

## 실측

- 매 회 새 맥락 전체 검토는 고칠 때마다 새 갈래를 찾았다(수렴하지 않음). 범위를 지정한 재검토는 직전 지적만 다뤄 blocking이 3→1→1로 줄었다.
- 3회 실패 원인은 대부분 design 층이었다: 다른 OS 기준 계획을 옮김(T04), 경로 금지 목록 땜질 → rename 교체로 부류 제거(P007 T01), 시나리오 경계를 한 줄씩 덧붙임 → 사례 표(T02), 원장 밖 우회로(T02).
- 진단 뒤 전체 검토도 새 갈래를 찾아 사용자 결정까지 가는 일이 많았다 — 사용자 결정 게이트가 실제로 반복을 끊었다.

## 함정

- 결함 주입 tester가 작업본 파일을 복사·복원하는 동안 작성자가 같은 파일을 고치면 수정이 지워질 수 있다 — tester는 스크래치패드 복사본에서 주입한다.
- 대상 diff 파일 경로를 차수마다 바꾸면 원장이 매번 새 대상으로 센다 — 같은 경로를 갱신해 쓴다.
- macOS launchd는 시스템 기본 PATH만 준다 — plist에 등록 때 PATH를 넣는다(main 3970e51, T04 사전 검토에서 발견).
- 알려진 한계: goal-review 2단계(호스트) blocking은 원장에 안 들어간다(이슈).

## 증명 범위와 결정 주체를 나눈 이유

P008은 새 TASK 형식 v2에 증명 범위·판정 주체를 먼저 적어 검토가 목적에 필요한 증명에 집중하도록 했다. 표지 없는 옛 TASK는 호환하며, 구조 누락을 한 건만 지적한 뒤에는 아직 평가하지 못한 목적·안전까지 전체 검토로 연다. 충분한 범위의 확장 제안은 should_fix이며 확장 승인·반영 의무는 아니다. 사람의 정답을 작성자나 자동 검사가 대행하지 않는다.

진단 뒤 fail을 매번 사람 결정으로 올리면 일반 갭도 중단되어 근본 조치·재검증을 PM에게 맡긴 취지와 어긋났다. PM/user를 새 결정에 반드시 기록하고 옛 주체 없는 결정은 unknown으로 남기는 이유는 P005의 옛 PM 결정을 사용자 승인으로 오귀속하지 않기 위해서다. ask_user 이름은 호환 때문에 유지하되 주체를 뜻하지 않는다.

검토 원장의 단계·기록·보고 형식은 reviewer 반복 실패 절을 따른다. P011에서 조치의 영향 분류를 skills/pace-project-dev/references/decision-rights.md의 A로 옮겼다. 원장 회차는 진단 시점을 알려 주고, owner 결정은 닫힌 목록의 실제 영향으로 고른다. 심각한 결함은 허브가 재현·원인 판별로 돕고 PM 경로는 근본 조치·재검증·사후 요약으로 닫는다. 승인 입력자는 실행 전에 owner 승인 원문과 대상 해시를 대조한다. 공동 시도 상한은 허브 회신·적용·재검증 주기를 세며 검토 원장 회차와 별개다.

실측은 실제 다른 제공자의 행동 순서 응답과 소스 CLI 합성 fixture를 구별한다. fixture의 cross 메타데이터를 실제 모델 판정으로 오해하지 않으며, 승인 입력도 실제 사람 승인으로 보고하지 않는다. 사람 원문의 진위·모델의 일반적 규칙 준수는 기계가 보장하지 않는다.

## P013의 단계별 예산과 공동 검토

태스크 사전·사후와 백로그의 일반 예산은 단계별로 센다. T02a의 공동 시도는 단위 합산 두 회이며, 모든 유형의 마지막 유효 판정과 일치하는 허브 적용 기록을 확인한다. 검증 생략·완화와 미확인 증거·잔여 blocking 수용은 A-3 요청으로 차단한다. B1은 별도 상태 없이 같은 제공자 사용과 교차 미실행 사유를 실제 시도에 보존한다. T03은 단계별 질문과 유효한 지적의 구조를 판정·고아 복구·재검토에 공통으로 적용한다. T09(T02b)는 지적 ID·원래 위치와 변경 지문으로 수정 확인을 묶고, 지적별 또는 단위 합산 문턱에서 기존 진단 원장을 쓴다. 그 뒤 실패하면 같은 단위를 보류하고, 새 맥락 근본 검토와 한정 재검증을 최대 두 차례 수행해 끝낸다. 같은 기준에 필요한 수정과 재검증은 실행·보고한다. 실제 A-1 승인으로 계약이 바뀌면 해당 단계 일반 예산만 재개한다.

## 검토 신호와 사용자 선택

필요한 수정과 독립 재검증은 합의한 기준을 지키는 조치다. 회차 문턱에서 구조 진단·재검증 범위를 남기고 진행 결과를 보고한다. 합의한 기준·범위를 실제로 바꾸는 A-1, 필수 검증 생략·완화 또는 미확인 결과·잔여 blocking 수용을 선택하는 A-3에 해당할 때 허브가 owner 결정을 올린다. 도구가 반환한 상태가 경로를 결정한다. 기존 `ask_user`는 실제 영향으로 분류하고, 예산 관리 단위의 `upper_review`는 독립 원인·해결안과 적용 후 한정 확인을 연결한다.

## 문제 해결자 호출과 검토 이력

P014는 예산 안 조기 신호가 한 회차에 함께 나오면 워크트리 PM이 자문을 한 번 받고, 일반 소진부터는 허브가 공동 시도마다 새 기회를 맡도록 나눴다. 조기 자문을 구조 진단으로 쓰면 다음 실패가 상위 근본 검토를 너무 일찍 열 수 있다. 조기 해법은 프로젝트 사건과 호출 원장의 동일 시도 ID로 연결하며, 실제 독립 재검증을 기존 검토 회차로 계산한다. 구조 진단 뒤 실패의 상위 호출은 허브가 맡고 같은 호출을 근본 검토의 call_ref로 연결한다.

2026-11-27 P014 T04에서 합성 검토를 source CLI로 판정해 조기·상위 발동을 재현했다. 각각 담당 PM의 독립적인 실제 전문가 호출에서 지정 모델과 effort를 확인했으며, 외부 review-record도 진단 뒤 실패에서 종료 0으로 상위 검토를 열고 다음 진입을 종료 16으로 막았다. 호출과 근본 검토 원장의 대조로 주체·발동·반환 관계를 확인할 수 있다. 합성 원장의 검출 범위와 실제 실패 반복 감소는 별개다.

## 구현 후 reviewer 묶음 점검 (P017)

2026-11-28 P017에서 사후 reviewer는 TASK 기준 `T-n`을 다시 판정하지 않고 TASK와 구현 diff로 경계·상태·흐름 세 묶음 12항목(RA·RB·RC)을 묻게 됐다. 이전 사후 R1은 실행 증거를 요구해 unknown이 반복됐다(재생에서 기존 5건 모두 unknown → 새 프롬프트 0/12). 답은 defect(위치 있는 질문 안 지적)·none(따라간 경로)·not_applicable(이유)이고, 빈 관측·상태 이름만·위치 없는 지적은 unknown이다. 비-diff와 같은 해시 fail 재요청은 예약 전에 거부한다. 패치만 주는 재생은 패치 밖 기존 잠금에 의존하는 흐름(C) 결함을 판정하지 못한다 — 재생 입력에 base 트리를 더한다. 사후 예산 소진·최신 pass 뒤 필수 재호출과 헝크 없는 diff에는 도구 경로가 없다(owner 한계 수용).
