## 빠른 검사는 작업본의 명시 매핑이다

설치된 PACE의 `pace test changed`는 staged·unstaged·ignore되지 않은 untracked 작업본 변경에 관련된 모든 단위의 전체 시험을 실행한다. 커밋된 브랜치 차이를 비교하는 명령이 아니다. 실제 Node/Python driver와 프로젝트 cwd를 쓰며 변경→단위→파일·명령·시간·부분/전체 판정을 남긴다. import 전이 의존성을 추론하는 대신 사용자가 모든 소속과 공통 helper/설정/생성 입력을 map에 명시한다. 공통·미분류·삭제/rename·충돌·type/mode·gitlink·구성/지원 불확실성은 실제 전체 검사로 전환한다. 무시한 입력의 자동 검증은 주장하지 않는다.

## checks를 허용한 이유와 기준 커밋

초기 test-map은 단위 선택 데이터였고 임의 셸 명령을 금지했다. 다른 저장소의 타입/린트/선행 검사를 PACE 전용 npm/tsc로 하드코딩하지 않기 위해 명시적인 `checks: [{cwd, command}]`에만 예외를 허용했다. 단위 runner에는 임의 명령을 추가하지 않았고 전체 검사 정본은 정의서에 남긴다. 필드 부재는 전체 전환, 빈 배열은 선행 검사가 없다는 명시 선언이다. 기존 file/unit과 구형 v1 소비자는 종전 의미를 유지한다.

작업본에 새 명령을 넣어 즉시 실행하는 신뢰 비대칭을 피하려고 checks와 전체 선언의 기준을 맞췄다. 로컬 main→master→검증한 현재 HEAD commit을 고정하며, 기준 map과 작업본 JSON이 같은 때만 빠른 경로를 활성화한다. map을 기준 브랜치에 커밋해야 한다. PACE 프로젝트 worktree의 새 map도 main에 반영되기 전에는 전체 전환한다. HEAD 대체 기준은 현재 커밋이며 리뷰된 기준을 뜻하지 않는다. 명령이 읽는 작업본 스크립트/환경까지 격리하는 샌드박스는 아니다.

## 기존 하네스를 보존한 실행 상태

다른 Git 저장소의 master/trunk에서도 전체 전환이 가능해야 하므로 새 changed 경로에서만 선택 commit을 별도로 선언 조회에 전달한다. SHA를 openRepo의 브랜치명 검증에 태우지 않는다. 기존 인자 없는 all/finish의 main 정책·생명주기·ok/output은 유지하며 정의서 파일 목록을 공유한다. 기존 하네스 흐름과의 관계는 [[작업-하네스-흐름]]을 본다.

checks는 기존 정의서와 같은 Windows Git 설치 경계의 sh/POSIX sh를 사용한다. cwd는 실제 저장소 안으로 제한하고 파일명을 명령문에 보간하지 않는다. pid/status/error/signal에서 실행 전 확인 불가3과 시작 후 실패1을 구별한다. 실제 Windows Git sh의 자기 SIGTERM은 Node signal 필드가 아니라 status3840으로 관측됐으므로 출력 문구/특정 signal 문자열로만 판정하지 않는다. 실제 실패·timeout·출력 상한·중단은 후속 전체 성공으로 덮지 않는다. 부분 결과만 확인할 수 없으면 전체를 실제 실행하고 그 범위를 표시한다. 부모 자체 OS 신호 종료는1과 다른 비성공 코드일 수 있다.

## 경로 집합만으로 삭제와 추적 가시성을 알 수 없다

독립 검증은 초기 전체991건이 green이어도 선택 누락이 남았음을 보였다. git rm --cached 뒤 파일이 남으면 status에 D와같은경로??가함께나온다. 경로Set으로합치고파일존재만보면삭제가사라진다. 수정본은status/raw D와중복상태를경로집합과별도로보존해전체전환한다.

assume-unchanged로숨긴B가실제시험에서실패해도보이는A만으로부분0이가능했다. 읽기전용ls-files -v -z의소문자태그/S와sparse checkout·sparse-index설정을확인하고, 하나라도불확실하면전체를실행한다. 플래그를해제하거나index를다시쓰지않는다. 회귀는숨은B의실제실패와전체실행실패1, flags/index byte불변을함께확인한다. ignore정책과의구별을사용자문서에명시했다.

예기치않은실행경계예외는성공으로바꾸지않고, 이미관측한실패/중단1을단조롭게보존한다. 사전검사뒤선택파일이사라지는시나리오도확인불가3/후속미실행으로검증한다. Node:test 내부환경을CLI fixture에그대로상속하면자식전체Node시험이재귀실행으로생략될수있어, 사용자CLI조건에맞게NODE_TEST_CONTEXT를제거해야했다.

## 설치 경로와 실측을 확인한 방법

P004 T04는 APP_PARTS와 같은 bin/src/templates/skills/package.json을 소유 임시 app에 복사하고, 별개 Git cwd에서 실제 Node 진입점과 공백 경로 .cmd를 호출했다. runtime app에는 node_modules가 없다. 복사된 실제 Node/Python driver에 관측 prefix만 붙인 별도 시나리오와 pristine 실행을 구별해 실제 app 경로와 SHA를 확인했다. 사용자 홈 설치/업그레이드나 POSIX 셔임 실행의 실기는 이 Windows fixture와 구별한다.

수정 v2 PACE 소스 사본의 main에 checks map을 커밋하고 card 소스만 바꾼 새3회는 실제 npm typecheck와 두 파일11건을 실행해 중앙14.794초였다. 준비4.686초는 분리했다. 원래 전체1425.464초와 최근 전체680.918초 양쪽 대비를 공개하되 범위가 다른 개발 workflow 지연이다. 같은 범위 개선이나 최종 절반 목표로 해석하지 않는다. v2 전체995건은986통과·실패/취소0·기존skip9,710.712초였다. 기존970건 판정/skip와 기존95개 시험 byte를 보존했고,607개실행소스의files SHA배열동일성과시각메타데이터차이를구별했다. 초기991건/710.587초·빠른14.687초및당시소스를별도로보존했으며v2증거로재사용하지않았다.
