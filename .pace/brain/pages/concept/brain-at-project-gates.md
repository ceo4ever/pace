## 결정
- 메모리는 부트가 매 세션 주입하지만 브레인은 지침으로만 '필요할 때 찾게' 되어 있어 놓치기 쉬웠다(2026-10-23 세션: 옛 백업은 직접 여러 번 뒤지고 브레인 검색은 두 번).
- 매 세션 비용(부트 주입)은 늘리지 않고, 브레인이 가장 필요한 두 순간을 하네스가 챙긴다.
  - `pace project new`: 프로젝트 이름(과 --from BL 출처의 BACKLOG.md·BR 브리프 제목)으로 검색해 최대 5개를 PROJECT.md 재료에 '확인 전 후보'로 넣는다. 결과 없음·검색 실패도 한 줄로 남긴다.
  - `pace project finish`: PROJECT-CLOSE 정본 반영 표의 브레인 행을 본다. 반영이면 .pace/brain/pages/ 변경(커밋 전 포함), 해당 없음이면 이유. main 직접 프로젝트도 확인한다.

## 함정
- 검색이 단어 단위라 후보에 잡음이 섞인다(예: '설치 복사'의 1순위가 프로필 페이지). 그래서 후보는 분석 단계에서 에이전트가 거른다.
- 템플릿 기본 행(브레인)이 첫 칸을 채워, 반영 칸까지 본 뒤에 '정본 반영 표가 비었다'를 판정해야 한다(리뷰 지적).
- 옛 템플릿으로 PROJECT-CLOSE를 쓴 진행 중 프로젝트는 브레인이 있는 저장소에서 finish가 브레인 행을 요구한다 — 메시지에 고칠 방법이 있다.

## 근거 변경 후보를 finish에서 다시 보는 이유

finish는 브랜치 변경 파일과 위키 sources의 교집합(디렉터리 근거의 하위 파일 포함)으로 갱신 후보를 알리도록 보강했다. lint의 날짜 비교만으로는 같은 날의 수정·아직 커밋하지 않은 변경을 놓치므로, 프로젝트가 끝나는 시점의 변경 집합도 사용한다.

브레인 행을 "해당 없음"으로 두면 각 후보의 전체 상대 페이지 경로와 여전히 유효한 이유를 비고에 적는다. 막연한 "새 결정 없음"으로 검토가 생략되는 것을 막으면서, 주장이 그대로인데 형식상 다시 쓰게 하지는 않는다. "반영"은 기존처럼 위키 페이지 변경을 확인한다.

한계: main 직접 프로젝트는 비교할 프로젝트 브랜치가 없어 커밋 전 변경만 본다. 체리픽·rebase의 author 날짜 순서, 충돌 해결 merge의 파일 목록, 특수한 이름 변경 표기와 복잡한 심볼 꼬리는 자동 점검의 근사다. 후보 알림은 의미 검토를 대신하지 않는다. [[brain-pull-not-push]]의 query → file back과 함께 쓴다.
